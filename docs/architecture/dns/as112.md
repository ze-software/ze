# AS112 DNS Sink

The as112 plugin answers the RFC 7534 and RFC 7535 zones: the reverse-DNS sink
for RFC 1918 and link-local space, and the `EMPTY.AS112.ARPA` DNAME
redirection. It builds on the shared harness in `internal/core/dnsserver`
(`server-harness.md`) and on the address-ownership registry.

## The response code says where the query name sits

Every zone this node serves holds its records at the apex and nothing below it:
RFC 7534 Section 3.5's zone files put an SOA and an NS set at `@` in
`db.dd-empty` and `db.dr-empty`, and an SOA, an NS set and the TXT strings at
`@` in the two `db.hostname.as112.*` files. Three answers follow from that.

| Query name | Answer |
|------------|--------|
| A served zone's apex, for a type it holds no record of | NOERROR, empty answer, the zone SOA in the authority section |
| A name inside a served zone, below its apex | NXDOMAIN, the zone SOA in the authority section |
| A name under no served zone | REFUSED, AA clear, nothing in any section |

Sinking the reverse query for a private address is the statement that the name
does not exist, which is what these empty zones exist to make. RFC 2308 Section
3 requires the SOA in the authority section on both negative answers, and RFC
7535 Section 6 counts on that caching.

## Zone boundary matching

Zone membership uses `dns.IsSubDomain(zone, name)`, never a string-suffix
comparison. A suffix comparison treats a sibling name such as
`evil10.in-addr.arpa.` as in-zone and answers for it where the correct answer
is REFUSED. This is a correctness defect with a security effect, not a style
choice.

## YANG listener anchors must materialize in the Tree

The listener anchors are `list ... { config false; ze:listener; }` directly
under `container as112`. The first form used `config false` wrapper containers.
A wrapper container holds no operator-typeable content, so it never
materializes in the parsed config Tree, and the cross-service port-conflict
detection through `RegisterListenerDefault` and `CollectListenersWithDefaults`
was a permanent no-op.

## The on-box carve-out covers the anycast address

`isOnBox` recognizes the plugin's own anycast addresses, not loopback alone.
The health probe queries the real anycast address on purpose. Whether the
kernel presents 127.0.0.1 or the anycast address as the apparent source of a
same-box query depends on routing. If the kernel presents the anycast address
and `allow-from` is configured, a loopback-only carve-out denies the probe, the
health check fails, and BGP withdraws a healthy route.

## Address family is a parameter, not a constant

`defaultHealthTarget` and `wildcardHostsForFamily` derive the probe target and
the wildcard host from the configured family. One hardcoded wildcard or target
address breaks the IPv6-only and the IPv4-only deployment while the dual-stack
default keeps passing. Any single-stack-capable service needs the same
treatment.

## Command handlers parse their own keyword arguments

The CLI dispatcher does not strip keyword tokens before an RPC handler sees
them. `parseHealthArgs` follows `parseTCPCheckArgs` in
`internal/plugins/diag/cmd/tcp_check.go`. A new plugin RPC handler that accepts
a `keyword <value>` form needs its own parse function.

## Two traps recorded from review

- `servedZones` rebuilt a 22-entry table with nested string building on every
  query. It is computed once into a package-level value. A hot-path allocation
  is easy to miss while reviewing for correctness.
- The request counter undercounted denied queries, because the `allow-from`
  denial branch returned before the increment. A metric defect has no
  behavioral symptom. Check every early return for counter consistency.
