# Feature Gates

How a compile-out-able feature is declared, wired and proven. A compile-out-able
feature is a subsystem that a build can drop from the `ze` binary through a
`//go:build ze_<feature>` tag, for a smaller binary and a smaller attack
surface.

The obligations are stated in `ai/rules/plugins.md`, section "Feature-Gate
Registration". This page holds the mechanism.

## The inventory is `feature-gates.txt`

The repo-root file `feature-gates.txt` declares every gated package and is the
only place a gate is declared. Read it for the current tag list; no other list
is maintained by hand.

Most features need one line. A feature with owned sidecar packages repeats the
tag:

```
ze_gnmi  internal/component/gnmi
ze_gnmi  internal/plugins/gnmi-cmd
```

The format is `<build-tag>` then `<gated-package>`. Tags are `ze_<feature>` by
convention. The generator gates both `<pkg>` and `<pkg>/yang` when those
packages are discovered: the direct package covers RPC and registration side
effects, and the YANG package covers config or command schema.

## Two readers, and everything else derives from them

`internal/le/repo/featuretags` parses the manifest. `Gates` answers the `<tag> <pkg>`
rows, `DaemonTags` answers the gate tags a daemon build carries, and
`DaemonBuildTags` answers the `-tags` string for a named personality. No other
Go file opens `feature-gates.txt`.

`feature-tags` is the second reader, and the bootstrap needs it. No le build
exists in `bin/builds/` before the launcher builds one, so the launcher cannot
ask a Go helper which tags to compile it with. The root `ze` and `le` launchers
and the two Docker images source that one file; the `le` launcher sources the
copy in the HEAD export it compiles, and `feature-tags` is one of the inputs
whose git tree hash keys each build.
`TestTheShellWalkAndTheGoReaderAnswerTheSameTags` holds the two readers to one
answer, and `TestOnlyOneShellFileParsesTheFeatureManifest` refuses a third.

## Committed plugin source population

`repoinventory.ReadCommitted` resolves HEAD once and retains its source blobs.
Membership comes from the transitive import graph of `cmd/ze` under the Linux
le context: `ze_le`, every manifest gate, `GOOS=linux`, `GOARCH=amd64`,
`Compiler=gc`, and cgo disabled. Release and tool tags also participate in file
selection. A Darwin host therefore does not lose Linux-only registration files.

Registration metadata is read from reachable initialization declarations, not
from every lexical `Registration` literal or from the reader process's registry.
Initialization includes named and blank package-variable initializers and
arguments evaluated before an immediate closure. Named init helpers, local and
imported constants, string concatenation, slice references and append expressions
retain their declaration identities. Family names also support returned slices
and the bounded canonical-name projection used by FlowSpec. Engine functions
identify their defining package; embedded YANG references identify their committed
source rather than assuming the schema sits beside the engine.
An expression the reader cannot resolve, an ambiguous schema source or changed
registration metadata refuses the inventory instead of publishing a smaller
host-dependent list. Source reads do not export or compile a checkout.

Executable calls use one bounded normalized callee for parentheses and immutable

defining file and package. Arguments keep their caller scope. A function value
merely passed or returned is not executed. Aliases of the registration APIs
still refuse when their execution ownership is unsupported. An opaque callee
or local, parameter, indexed, returned or import-shadowing receiver cannot
inherit the standard-library boundary from a missing import lookup: a package
selector must prove its lexical import binding. Unsupported owners refuse
without publishing partial membership; this is not a method or value interpreter.
Following a callable initializer also requires an immutable binding: a reused
short declaration is a write to its existing object, and an escaping address
refuses rather than guessing which function a pointer write installs.

### Approved external-effect contract

The Git-only external-effect analysis below is the approved implementation
contract. Its new discriminating fixtures precede the producer changes; the
existing real-root refusal remains until the analysis and its tests are complete.

External execution is modeled as arbitrary use of every callable and writable
location it can reach through ordinary Go references or static imports. This is
an explicitly bounded trust contract, not a conclusion drawn from signatures or
library names. Unsafe reference fabrication, `go:linkname`, runtime symbol access,
dynamic loading and arbitrary native capability manufacture are outside its
authority. Retained escapes outside this model refuse. The inventory reads no
host GOROOT, copies no standard-library source and has no inert-library whitelist.

Each opaque origin needs a source certificate for its possible static access to
the registration sinks. Retained import paths from both sink packages to that
origin establish the cycle certificate: a static import back to either sink
would create a Go import cycle. Alternatively, an origin outside the certified
parent-module namespace may use a public-entry certificate when both sinks lie
behind that namespace's exact `internal` path segments. Closed module and provider
selection must prove that every parent-qualified import resolves to retained
source. An outside importer, including any hidden dependency, must then enter
through a retained public package before reaching either internal sink.

The public-entry certificate includes every potentially importable public parent
package and the full retained import-initializer closure of each entry, including
blank imports and internal dependencies. Its exported constants, globals,
functions and types contribute all transitive values, methods and writable
locations. Initializers already selected by the ordinary root retain their
certain, once-only classification; other activations remain possible effects.
Package-main entries remain conservative roots. Retained packages outside the
parent namespace, including vendor internals, keep their independent static
roots unless an exact package-to-origin cycle excludes them.
Opaque imports discovered in an entry's initializer closure, including blank
imports, add their origins to the same ambient fixed point. Every new origin
requires its own certificate and entry analysis before the closure can succeed.

Neither certificate proves isolation from callbacks or shared state. A neutral
retained package can hold an installer callback or mutable registration metadata.
All retained internal bodies and assignments remain in the capability analysis,
even when their packages are not independently accessible static entries. Only
proved import-cycle or internal-access restrictions may exclude an entry. A
restriction on the direct external importer does not exclude an unknown permitted
transitive importer. Missing selected package identity, source ownership or build
selection refuses rather than assuming no hidden import.

An independent committed nested module is outside the root module's package
selection. Its source and vendor directories do not enter the potential import
universe. A certain or recursive potential import that crosses its module
boundary refuses the inventory instead of borrowing the parent module's identity.
Nested module declarations are parsed from committed manifests. An unresolved
import matching a nested module's declared namespace refuses before potential
package exclusion; a dotless module name is not evidence of standard-library
ownership. Malformed nested declarations also refuse uncertain identity.
Root replacements and workspaces still refuse before these boundaries apply.
For vendor descendants, module boundaries apply only above the first `vendor`
path segment. Root vendor packages remain subject to `vendor/modules.txt`, and
an unresolved nested vendor tree still refuses despite a copied `go.mod`.
A directory whose path ends at `vendor` remains an ordinary package path,
including its local module boundary if it carries a `go.mod`.

One monotone capability pool includes those static roots, all references passed
externally and all retained assignments to accessible roots. Callbacks may execute
immediately, later or concurrently; possible registration is uncertainty, never
certain membership. Each opaque return slot and interface receiver carries the
entire input, receiver and ambient capability union. Writable references taint
dependent metadata and execution ownership. Returned values are not assumed fresh,
and a named scalar's methods are not assumed harmless. Without a permanent
ambient unknown, both branches remain analyzed; return, panic and failure paths
do not prune effects.

An exposed function value also reveals its parameter and result types through
ordinary reflection, even when its body ignores a parameter or returns a nil
pointer. One exposure hook inspects retained function and closure signatures
in their defining scope; bound method signatures omit the captured receiver.
Typed-nil function values retain their concrete type without an implementation
node. Their type authority and each struct field's type authority preserve exact
generic substitutions through binding, field projection and flattening.
An actual retained call also preserves its declared result types when the
returned expression is nil or an untyped constant. This result authority includes
only Results, in the callee's defining scope, and survives direct use or inferred
local bindings without exposing the callee's parameters or receiver. Ordinary
and certified assembly call results use the same boundary after their existing
execution-ownership checks.

Generic instantiation retains proved type arguments as deferred descriptor
authority. An opaque call or an exposed instantiated function promotes that
authority. An unexposed local instantiation does not. A type argument includes
interface signature types, even though a nil interface value has no concrete
descriptor. An unproved type kind retains ordinary value-index evaluation.
This transfer grants neither backing storage nor ordinary callee ownership.

A standard-library named type is external on every route that names it: a
bare selector (`sync.Pool`), an instantiation (`atomic.Pointer[T]`,
`iter.Seq2[K, V]`), a pointer to one, a field or an embedded field of that
type, and a composite literal of it. Its source is not an analyzer input, so
the type is modelled the way an external call is: it contributes its import's
origin and may reach the ambient pool, and its type arguments are still walked
as retained types, so `atomic.Pointer[hook]` keeps the methods of `hook`. A
keyed literal of such a type evaluates every key that could be a value and
treats only an identifier that binds nothing in scope as a field name. A
question only the declaration answers (the range kind of the type, the type of
one of its fields) refuses with the reason that the type has no retained
declaration. A selector into a module package the inventory does not retain
still refuses as an unresolved import binding.

Reflection authority is separate from actual callable ownership. Its exported
methods, opaque origins and unresolved type facts enter the ambient pool only
when exposed. Ordinary retained calls still execute only their actual function
values. Descriptor inspection follows pointer, array, slice, map, channel and
struct field types, function signatures, interface methods and the signatures
of accessible exported methods. It grants no existing writable backing storage;
inspecting a channel element type is not a channel value transfer. A nil interface
value alone reveals no concrete runtime type, while a concrete holder's field
descriptor still reveals that interface's method signature types.
The reflection summary resolves the value root's exact substituted
representation before collecting generic argument authority; a nil generic
interface contributes no reflected argument methods.

Aliases preserve the target's methods; a new defined type does not inherit its
underlying named type's methods. A real field or element descriptor edge exposes
that child's own methods. A named frame is therefore its exact retained
declaration, its resolved substitutions and its method and value-root flags.
The walk does not expand another field-value tree; unresolved identities remain
explicit uncertainty, refused when exposed.
Each query collects descriptor facts into its own output-owned union, including
method signatures. Valid argument visits retain their order before the frame is
entered; an argument ownership preflight preserves the existing unknown-only
invalid-argument return. Local uncertainty does not cancel sibling traversal.

The walk treats the type graph by reachability. Each exact frame is walked once
per analysis, and its contribution (methods with their defining sources,
standard-library origins, the first refusal and its site) is the union of what
its own walk meets and what the frames it reaches contribute. Tarjan's
algorithm computes it: a frame met again while it is still open is a cycle and
adds nothing on that path, the frames of one strongly connected component share
one union, and the analysis keeps that union for every member once the
component's first frame completes. Every later visit, from any query, joins the
kept union, so a finite graph costs one walk however many paths reach a frame.
The contribution reads no ambient pool, binding, settled type value or incoming
depth, so it is the same from every query. A union's first refusal is the first
the walk met in source order, a kept union joined at the point the walk reached
it; a component keeps the first refusal of the walk that computed it, so every
member and every later query reaching it carries that refusal, and an unsited
one is sited at the type expression that joins it. Frames and arguments are
interned for the analysis: two arguments are one term when they are the same
retained expression with every type parameter it mentions bound to the same
term. The only depth bound left is on that term: an instantiation that grows
without end, such as `grow[T]` holding `*grow[[]T]`, reaches a new frame on
every step with an argument nested one level deeper, and the first frame whose
argument nests past 128 levels refuses with `reflection type capability depth
exceeds 128`. A query that starts at an expression depth of 128 or more refuses
with the same reason, as the value flow that asks it does.

The observation horizon is completed initialization. Without a proved ordering
boundary, delayed callbacks and retained writes to exposed roots remain possible
before that horizon; the bounded analysis conservatively includes later writes
too. Binding-sensitive summaries reach a bounded fixed point over the captured
source identity and ambient pool. A visited declaration alone proves neither an
effect-free second invocation nor a completed recursive summary. Every previously
collected registration and metadata value is revalidated against that final
closure. Unknown effects, mutable dependencies or exhausted bounds refuse the
whole report, with no partial population. This contract certifies registration
effects only, not termination or absence of file, network and system effects.

A nonempty unknown in the monotone ambient capability pool permanently refuses
the whole report. Remaining effect expansion may then stop without admitting any
operation; local unknown values, field-ownership obligations and provisional
failures do not establish that condition. The refusal retains any currently
recorded issue preferred by the existing issue ordering; otherwise it reports the
unresolved ambient unknown without an execution-source position, and effects not
visited need not receive a diagnostic. The reason still names where it came
from: each unknown carries the committed expression that first produced it (the
innermost expression, type or descriptor walk that saw it), the first reason
keeps its site through every join, and the refusal message reads
`committed inventory <file>:<line>: external registration capability is unknown:
<reason>` with the usual fix. The site changes only the message, never which
issue the ordering prefers.

Positional retained struct literals map each value to its declared field slot,
including grouped names and proved alias or defined-type chains. A projected
field retains its own capabilities, reads and references without borrowing a
sibling callback or the holder's methods. Unresolved positional layouts refuse
at construction, so a later field projection cannot erase that uncertainty.
An element, key or value literal that elides its type takes the type its
enclosing literal states, as the Go specification defines it: the element type
of an array or slice, the key or value type of a map, through retained aliases
and defined types, and `T` when that type is `*T`, in which case the literal is
`&T{...}`. Nested elisions (`[][]T{{{...}}}`) take each level's type in turn. A
generic collection substitutes its argument only where the element type is the
type parameter alone or a pointer to it. A standard-library collection states a
type the analyzer has no declaration for, so its elided elements take the
standard-library literal's treatment above. The formal-provenance proof reads
an elided literal's keys under the same stated type. Where the enclosing type
cannot state the elided one, a generic element type that names its parameter
inside a larger type (`[]map[string]E`), an empty elided literal remains a zero
construction and a nonempty one refuses as `nonempty elided literal layout is
unresolved`, sited at the element. Positional generic-struct and
embedded-field layouts remain unsupported.

Root field names are separate from aggregate reachable capabilities. Collection
keys and elements, named child fields and generic arguments contribute their
capabilities without adding their field names to the holder. Keyed literals
populate only proved direct struct members, including names in a retained generic
struct declaration. Retained field selection proves the receiver's static root
and direct member before consuming a field value; an asserted type cannot borrow
another interface alternative's field. Unsupported owner shapes refuse explicitly.
Indexed or ranged values retain all aggregate capabilities, but carry a separate
field-ownership obligation until an actual element-field summary is available;
a type-only empty callback field cannot discharge it. Nested fields preserve
their own obligations without contaminating an unrelated scalar sibling.
A channel is modelled as the same kind of reference container as a slice,
whatever its direction (`chan T`, `chan<- T`, `<-chan T`): its possible contents
are the flattened capability of its element type. A send stores the flattened
sent value into every location the channel operand names, as an indexed
assignment stores into a slice element, and enters the retained-write equations
the same way; a send whose channel location is unresolved refuses. A receive
(`<-c`, a `select` case, `for v := range c`) reads the channel's contents and
carries that root-field obligation too, so a received whole value cannot borrow
an earlier inert field from the same binding. A received value passed as an
argument to a retained function still refuses its formal provenance.
Flattening copies every visited node's capabilities into one output-owned union,
dropping field names and their selector obligations at each node. Its unchanged
128-edge cutoff excludes that node's capabilities, preserves the first unknown
encountered and continues traversing siblings. The type walk treats the type
graph by reachability, as the reflection walk does: a frame is the exact
declaration, its interned arguments, the method flag and the reflection
setting, a cycle re-enters an open frame, and the only depth bound inside the
walk is the argument nesting bound above, refused as `type capability depth
exceeds 128`.
A recursive type, such as goyang's `Statement` holding `[]*Statement`, has the
least fixpoint of its own walk as its capability. A reference back to a named
type the walk is still computing, with the same resolved arguments and method
flag, answers that frame's current estimate, flattened, so a children field
carries every method, origin, ambient capability, unknown and site the type
carries. Answering it with nothing would publish a children field with no
capability. Estimates start empty, live for one walk, and take each round's
flattened value. Frames that re-enter one another form a component, and only
its outermost frame repeats: an inner frame that read an outer estimate returns
after one round, and the outer frame repeats the whole component until a round
grows no estimate, so mutual and nested recursion cost a few rounds, not a
power of the nesting depth. A frame still growing after eight rounds refuses
with `cyclic retained type capability shape`. A frame whose rounds read no
outer estimate is final; the walk keeps its value, unknown included, and
answers a later visit of the same exact frame with it: no guard inside the
walk depends on how deep the frame was met. The table belongs to the whole
analysis, so every `typeMethods` call shares it, and a slot also names the
ambient pool it read: a walk
reads the pool for unbound type parameters and standard-library types, and
`growAmbient`, the pool's one writer, advances its version on every growth,
so a value read from a smaller pool is never answered. Polymorphic recursion
(`type grow[T any] struct{ next *grow[[]T] }`) never repeats a frame, so it
still refuses, at the argument nesting bound.

Parameter provenance includes every exact retained direct caller, including
dormant callers, through equations that keep the caller's execution owner.
An actual nil argument is evidence; an absent binding or an early empty recursive
summary is not. Relevant indirect callable uses and unsupported caller shapes
refuse instead of silently reducing that caller population. A method value
`x.M` is the one indirect use that binds part of the population: it fixes M's
receiver to `x` where it is taken, with the equation a call `x.M()` writes,
while M's parameters still come from the value's unseen callers and refuse.
Primitive scalar
parameters acquire their own type methods without borrowing ambient references;
reference-bearing parameters exposed externally retain the full ambient union.
At stabilization, every demanded forwarding component must reach a real argument
or explicit external authority, and every outgoing provenance obligation must be
complete. This admits a nil-grounded cycle while refusing an ungrounded cycle.

Retained caller indexing reuses one private declaration resolver for its captured
snapshot. Mutation queries capture the complete selected file and import census,
then lazily index each needed file's full preorder assignments, range assignments
to existing bindings, increments and address expressions. A completed empty file
index is distinct from an unbuilt one. The exact declaring-file population, files
that import the owning package and the existing alias checks remain authoritative.
Both existing range key and value targets count as writes; fresh `:=` bindings
remain separate. Completed results are memoized by
package, declaring file, local binding identity, declaration name and mutation
policy. A clean all-writes result cannot certify a callable whose address escapes.
No provisional result, mutable AST, other reader or later snapshot shares that
cache; unsupported policies refuse before source access.

Type ownership uses a separate private structural index of the complete selected
source: exact package and declaration identities map to their owning files,
including nested type declarations, and each package retains its original ordered
receiver declaration list. Completed package binding tables retain every parser
scope map key and exact object, including non-type shadows, absent/nil objects
and sticky ambiguity between distinct objects. An empty selected package remains
distinct from an unindexed package's original pure lookup fallback. Exact lexical
objects take precedence before package fallback, without rescanning discarded
bindings. Lexical bindings, duplicate-name refusals, imports,
receiver alias/generic checks and recursion bounds still run in their existing
contexts. This index stores no capability, substitution, ambient, lexical-scope
or depth-dependent result. An unavailable declaration owner still refuses.

A second reader-local table completes each captured package's receiver census
once, resolving receivers from depth 0: the walks that ask treat the type graph
by reachability, so a frame's methods do not depend on how deep it was met. It
resolves every original row
and groups successful tuples by exact type declaration. Shape and resolution
failures remain in one shared list, with each row's original ordinal.
Private, generic and bodyless declarations remain source facts in that census.

Each method query merges its exact target list with the shared failure list in
original order. Both collectors retain visibility, shape, error-before-target,
generic and bodyless checks. Matching method signatures still traverse the

## The one invariant

A feature is compile-out-able only when nothing always-on (untagged, non-test)
imports its package, for any reason: lifecycle or a borrowed helper. Always-on
code reaches it only through build-tag-gated registration. One direct `import`
from untagged code pins the package into every binary and defeats the
compile-out. `./le arch tier check` fails on any such importer.

When always-on code needs a non-lifecycle helper the feature exports, the helper
is extracted to an always-on home first (an `internal/core/*` leaf), and the
feature is gated after. The registry work is the easy half.

## Procedure: add a feature gate

1. **Extract first.** Search for always-on importers of the feature package.
   Move every non-lifecycle helper they use to an always-on `internal/core/*`
   leaf. Re-check until only gated construction remains.
2. **Pick the shape.** A construction registry, or a seam. See below.
3. **Add lines to `feature-gates.txt`** for every owned package that has to
   vanish: the main package plus sidecars such as the command-schema package
   under `internal/plugins/<x>-cmd`.
4. **Create the gated files** for the shape: `service_<x>.go` plus
   `register_<x>.go`, or an `*_infra.go` seam plus gated registration. Each one
   carries `//go:build ze_<x>`. A feature-only helper lives inside a gated file,
   or a no-feature build flags it U1000-unused.
5. **Run `./le repo update`.** It emits `all_ze_<x>.go`, regenerates
   the derived tag lists from the manifest, and gives each plugin the gate now
   covers its row in the gated-plugin table (see "Naming a plugin the build
   left out"). Then run `./le verify worktree`.
6. **Write present and absent build-tag tests**:
   `cmd/ze/hub/build_tag_<x>_present_test.go` (`//go:build ze_<x>`) and
   `_absent_test.go` (`//go:build !ze_<x>`). The absent test asserts through
   `go tool nm` that zero feature symbols are linked.

Step 3 is the only declaration point. Everything else derives.

## The registration shapes

**Listener service, the default (looking glass, web).** The feature plugs into
the construction registry in `cmd/ze/hub/service_registry.go`. A gated
`service_<x>.go` builds a `Service`: the `Reconfigurable` listener-migration
contract plus `Name` and `Shutdown`. The `init()` in `register_<x>.go` calls
`registerService("<x>", build<X>Service, wireMigrator)`. The hub iterates the
registry in `buildServices(deps)` and routes the built service through
`registerBuiltService`. Generic inputs cross the boundary as plain values in
`serviceDeps`, and an always-on handle is widened to `Reconfigurable`, as
`setWeb` and `setLG` do. A second construction path, such as a
`ze start --web` standalone mode, goes through a nil-able seam var that the
gated registration sets.

**Seam (ssh, gNMI).** A seam covers a construction shape the listener registry
cannot express. ssh is built inside shared daemon startup, interleaved with
always-on AAA, authz and accounting, and owns an interactive session, so it uses
`ssh_infra.go` (`sshBuild`, `sshWirePostStart`, `sshBuildStandalone`). gNMI has
richer constructor dependencies, a reload notification hook, and no listener
live-migration contract, so it uses `gnmi_infra.go` (`gnmiBuild`,
`gnmiReloadNotify`). Always-on code calls the seam when it is non-nil. With the
tag off the vars stay nil and the feature is skipped.

**Core-level seam (telemetry).** When more than one start site in different
components reaches a gated feature, the seam var lives in the always-on leaf
both sites already import rather than in the hub. The Prometheus exporter
(`ze_telemetry`) starts from the hub standalone path and from the BGP reactor
path, so its hook `metrics.StartExporter` lives in `internal/core/metrics`, and
the hub's gated `register_telemetry.go` wires the gated exporter into it. The
metric collection API, the registry and the `NopRegistry` dummy, stays in that
always-on leaf so dependents keep working while the exporter is gated. A core
leaf holding a nil-able hook var that a gated component `init()` sets keeps
`./le arch tier check` green, because it is a value rather than an import.

**Plugin compile-out (routing protocols).** When the feature is already a
self-registering plugin the generator discovers, gating is blank-import
partitioning and there is no new `register_<x>.go` or seam. Each owned directory
is its own `feature-gates.txt` line under the shared tag, because a protocol
spans several discovered directories:

```
ze_ospf  internal/plugins/ospf
ze_ospf  internal/plugins/ospf/cli
ze_ospf  internal/plugins/ospf/transport
ze_ospf  internal/plugins/ospf/v3/transport
```

The plugin's `.go` files are not source-tagged. `./le repo update` moves
their blank imports into `all_<tag>.go`, and dead-code elimination drops the
unreferenced packages when the tag is off.

There are two composition roots: the generated `all.go` and the hand-written
`cmd/ze/ze_core_dispatch.go`. A protocol with a programmatic `cli` package (isis,
ospf) moves its dispatch-root CLI blank import into a per-protocol gated
companion `cmd/ze/dispatch_<proto>.go` (`//go:build ze_core && ze_<proto>`).
Miss that root and the package stays linked. A plugin that registers its CLI
through the plugin registry's `CLIHandler` has only the one root, the generated
`all.go`, and needs no dispatch companion. `ze_vrrp` is the single-plugin case:
the plugin plus its `transport` sidecar, two manifest lines, no `cli` package.

Routing protocols are also the first gated packages that are `sdk.NewWithConn`
engines, and the first multi-package features whose sub-packages import each
other. `./le arch tier check` therefore counts the generated `all_<tag>.go` as a
registration importer, and skips same-tag importers in the disable-able check,
because a package importing its own sibling is intra-feature.

## Extract-then-gate at subsystem scale

Gating the BGP subsystem is the same blank-import partitioning, but the one
invariant does not hold going in: 27 always-on files imported a BGP package.
Three techniques clear them, in this order of preference. Aim for the fewest
source-tagged files, not the fewest edits.

1. **Transitive package drop, no tag.** A manifest line moves the package's
   blank imports into `all_<tag>.go`, and dead-code elimination does the rest.
   A whole plugin qualifies: `flowspec-firewall` needed one line and no source
   change.
2. **Core-leaf move, no tag.** A contract that always-on consumers share with
   the feature moves to an always-on `internal/core/*` leaf, and consumers
   change an import path only. `ze_bgp` needed three:
   `internal/core/bgp/routeaction` (the route-action vocabulary sysrib and every
   FIB backend use), `internal/core/bgp/msgtype` (the message-type codes MRT
   classifies by) and `internal/core/bgp/ribevents` (the best-change contract
   sysrib and flow export subscribe to). Move the leaf, not the package:
   `bgp/message` imports `plugin/registry`, so relocating it wholesale would be
   a core-tier violation.
3. **Inversion-of-control seam, no tag on the always-on side.** Where always-on
   code reaches into the feature, invert it: the always-on side exposes a
   nil-able hook and the gated code self-registers from its own `init()`. A nil
   seam needs a correct no-feature behavior, not only a nil check. `ze_bgp`
   inverted five: `ze config dump|diff|validate` tree resolution, peer
   validation, the graceful-restart marker writer, the MRT RIB-dump provider,
   the web hex-packet decoder, and the IGP next-hop cost sysrib used to push
   into BGP best-path.

Two traps appear only at this scale:

- **A feature-gated file is still an always-on pin for a different gate.**
  `cmd/ze/hub/service_ssh.go` (`//go:build ze_ssh`) imported `bgp/config`.
  `dep_audit.file_requires_tag` is per-tag and flags that file correctly: a
  `ze_ssh`-on, `ze_bgp`-off build genuinely fails to compile.
- **Removing an always-on import can unlink an `init()` nobody else pulls in.**
  `bgp/config` registers the reactor factory and was linked only because the hub
  imported it. Blank-importing it from `bgp/plugin` cycles in test, so it is
  linked from `cmd/ze/infra_bgp.go` instead: a `package main` root can never be
  imported back, so the edge is always safe there.
- **A seam link gates on the FEATURE tag alone, not on the personality tag.**
  `cmd/ze/infra_bgp.go` carries `//go:build ze_bgp` while its neighbor
  `cmd/ze/dispatch_bgp.go` carries `//go:build ze_core && ze_bgp`, because
  `ze_core` selects the CLI dispatch personality and only the CLI registration
  belongs to it. The two were one file until 2026-09-03, and the wider gate left
  the seams unfilled in every non-`ze_core` binary: the test harness
  (then its own tagged personality) drives the config editor in-process, so
  `infra.ValidateBGPPeers` answered nil there and an editor `.et` asserting a
  refused commit could not pass. A test binary that links its own composition
  root needs the same edge, which is what
  `internal/component/cli/testing/all_import_bgp_test.go` carries.

## Dependent gates and dependent files

**A dependent gate (`ze_bmp`, `ze_radius`).** A gated package that lives inside
another gate's package tree and imports it can only be built when the parent
gate is on. `ze_bmp` imports `bgp/message` and `bgp/types` and monitors the BGP
RIB, so it exists only in a `ze_bgp` build. The generator detects the nesting
per package (`parentTagOfImport`: the longest gated package of another tag that
is a path-prefix of the import) and emits a compound constraint, so
`all_ze_bmp.go` carries `//go:build ze_bgp && ze_bmp`. That is what makes
`-tags ze_bmp` without `ze_bgp` drop BMP rather than drag the whole engine back
in through BMP's blank import. The dependency is derived from the package path,
so the manifest line stays the ordinary `ze_bmp <pkg>` with no new column. The
present build-tag test carries the same compound constraint as the group file,
so it never runs in a `ze_bmp`-without-`ze_bgp` build.

**A tag may mix independent and dependent packages.** `ze_radius` gates
`internal/component/radius` (RADIUS system auth, usable alone) and
`internal/component/l2tp/plugins/authradius` (needs the BNG). The generator
splits such a tag's group by per-package constraint: `all_ze_radius.go` carries
the plain tag with the independent imports, and `all_ze_radius_ze_l2tp.go`
carries `//go:build ze_l2tp && ze_radius` with the nested subset. A tag whose
packages all share one constraint keeps the single `all_<tag>.go` file.

**Dependent files inside another feature.** When a feature of plugin A exists
only because feature B exists, A's files carry B's tag and each one gets a
counterpart. The cos dynamic RADIUS-CoS handler is `//go:build ze_l2tp` with a
no-op stub, because with no BNG session events there is nothing to react to. The
diag l2tp capture branches live in `capture_l2tp.go` and `capture_raw_l2tp.go`
with stubs that answer "l2tp is not included in this build". The web VPN and
L2TP pages have not-in-this-build stub renderers so the workbench routes stay
valid. A stub answers honestly and names the missing feature.

**Subsystem-builder seam (`ze_l2tp` hub construction).** When the hub constructs
a feature, parsing params and calling `eng.RegisterSubsystem`, rather than
blank-importing it, a hub-local nil-able hook carries the construction:
`bng_infra.go` `bngRegister`, filled by the gated `register_l2tp.go` `init()`.
It is the ssh and gNMI seam shape, carrying only generic values across the
boundary: config trees, the engine handle, portal entries.

## Naming a plugin the build left out

A binary cannot name a plugin it was built without, because the plugin's
registration is compiled out with the plugin. A refusal that has to say "rebuild
with `ze_bgp`" therefore cannot ask the registry. It reads a generated table
that no build tag removes:
`internal/component/plugin/registry/gated_plugins_gen.go`.

The table maps every gated plugin name to the build tags that must all be set
for a binary to carry it. A nested gate gives a compound row, in the order the
composition root's `//go:build` line states it: the enclosing gates sorted,
then the plugin's own gate. `bgp-bmp` reads `ze_bgp`, `ze_bmp`, and
`l2tp-auth-radius` reads `ze_l2tp`, `ze_radius`. An ungated plugin has no row,
because every build carries it.

`registry.GatedPluginTags(name)` is the lookup. It answers the tags and
`true` for a gated plugin. It answers no tag and `false` for any other name: an
ungated plugin, which `registry.Lookup` finds, or a name no build of this tree
registers, such as an external plugin or a typo. A caller tells those two apart
with `Lookup` and never prints a tag for either.

`./le plugin gated-table update` generates the table, and `./le repo update`
runs it after `./le plugin imports update`. It joins two facts that are each
declared once. Registration names, source directories and the gate manifest
come from one `repoinventory.ReadCommitted` snapshot of HEAD.
`pluginimports.GateIndex` uses the same constraint derivation that writes the
composition root's `//go:build` lines. No row is written by hand, and no host
registry or Docker inventory supplies missing registrations.

`./le plugin gated-table check` refuses a table that disagrees with that
committed manifest or population. Commit changed declarations and composition
imports before deriving their table; dirty declarations do not enter it merely
because a local le binary linked them. `TestGatedRowsKeepTheCommittedManifest`
proves a dirty manifest cannot change the gate attached to a committed plugin.

### Refusing a root whose plugin is compiled out

The generator gates a plugin's package and its `yang/` package together, so a

### Refusing a setting whose provider is compiled out

A plugin can depend softly on another one: the build without the provider
still runs the owner, and refuses only the setting that needs the provider.
The owner declares that setting as a `ConfigNeed` on its registration, beside
the `OptionalDependencies` entry that names the provider
(`plugin-system.md`, "Registration fields").

The same need decides whether the provider is pulled where it is compiled in:
`registry.ResolveDependencies` pulls an optional provider a need lists only
when the config holds that need, judged by the same evaluator
(`config.ConfigNeedHolds`). So one declaration drives the pull, the startup
order and the refusal, and flow export with enrichment off never starts the
BGP RIB (`plugin-system.md`, "Dependencies").

A need's path may cross a YANG list: the list keyword is followed by
`registry.AnyEntry` (`*`), and the need holds when any entry carries the value.
The BGP-LS exporter uses it for `bgp-ls-export domain * source`, so a domain
naming `isis` is refused in a build without `ze_isis`, and pulls IS-IS in a
build with it, only while some domain names it.

The config component judges every declared need in `refuseAbsentOptionalProviders`,
and both doors a config passes call it: `LoadConfig` at boot and at every
reload, and `VerifyPluginConfigMapTransition` at `ze config validate`, editor
commit and API commit. The config is lowered for the check only when some
compiled-in registration declares a need.

When the setting is in the config and no provider of the need is registered,
the config is refused before any plugin starts, with an error that unwraps to
`ErrAbsentOptionalProvider`:

```
config: "flow-export enrichment bgp true" needs plugin bgp-rib, and this build does not include it
  flow-export cannot act on this setting without it, so ze refuses the config rather than run a setting that does nothing
  fix: rebuild ze with build tag ze_bgp added to its -tags list, or remove "flow-export enrichment bgp true" from the config
```

| Provider | What the fix line names |
|----------|-------------------------|
| One gated provider | Its tag, from `GatedPluginTags` |
| A provider under a nested gate | Every tag it needs: `build tags ze_bgp and ze_bmp` |
| Any-of providers | Each provider as an alternative with its own tag: `build tag ze_flowexport, or with build tag ze_trafficusage` |
| A provider no gate names and the build does not register | No tag: a line says no build tag adds it, and the fix is to remove the setting |

The check is about the build only. One provider of an any-of need compiled in
meets it even when the config does not configure that provider: an
unconfigured flow source stays the doctor warning it is today. An any-of need
also pulls none of its providers when it holds: the providers are
alternatives, and the one the operator configured loads from its own config
root (`ConfigNeed.PullsProvider` in `internal/component/plugin/registry`). A node that is
absent or of another shape means the need does not hold. A declared need with
no config to judge refuses with `ErrConfigNeedUnevaluated` rather than pass.

## Declaring a cross-gate coupling

A plugin that consumes something only a plugin under another gate produces is
coupled to it. A build without the producer's gate still runs the consumer,
which then receives nothing and says nothing. Flow export's BGP enrichment was
the case that found it: it subscribed to `ribevents.BestChange`, which only
`bgp-rib` emits, and a build without `ze_bgp` left the AS fields empty with no
log line.

Every such coupling carries an edge on a registration, chosen by what config
makes the consumer need:

| The consumer | Edge | What a build without the producer does |
|--------------|------|----------------------------------------|
| Depends on the producer's output when a setting holds | `OptionalDependencies` plus a `ConfigNeeds` entry naming the setting | Refuses that setting, naming the tag (see "Refusing a setting whose provider is compiled out"); a full build pulls the provider only while the setting holds |
| Only listens, and works without it | `StartAfter` | Runs; the edge orders the pair when both are selected and never loads the producer |
| Cannot work at all without it | `Dependencies` | Refuses the consumer on every load path, naming the plugin, the dependency and the tag |

There is no allowlist. A benign coupling declares `StartAfter`, which is the
statement that the consumer works alone.

`./le plugin coupling check` finds the couplings that carry no edge. It parses
every shipped Go file under `cmd/`, `internal/` and `pkg/` (not `internal/le`,
not `internal/test`, no `_test.go`), resolves each file's import aliases, and
records four shapes:

| Shape | Producer | Consumer |
|-------|----------|----------|
| `event` | `Handle.Emit` on a package-level handle from `events.Register` or `events.RegisterSignal` | `Handle.Subscribe` on the same handle |
| `registration` | The caller of `pkg.Register*(key, ...)` or `pkg.MustRegister*(key, ...)` into a package a plugin owns | The plugin that owns that package, per key |
| `subscription` | The plugin that owns the package | The caller of `pkg.Subscribe*` into it |
| `seam` | The caller of `pkg.Set<X>` in a package no plugin owns | The caller of `pkg.Get<X>` in the same package |

A use belongs to the plugin whose registering directory is the longest prefix
of the file's directory. The use is a coupling when no producer of the same
item needs only build tags the consumer's own build carries, and no producer
is the consumer itself. Any declared edge between the consumer and one of the
producing plugins satisfies it, in either direction: a relationship the
producer already declares toward the consumer states the coupling and orders
the pair, and a second edge back would be a cycle. Producing code outside every
plugin's directory stands for each plugin built under exactly its gates, so the
VPP backends under `internal/plugins/traffic/vpp` count as `vpp`.

Two results do not fail the check, and the report lists both. A coupling whose
producer is code outside every plugin, such as the L2TP subsystem emitting
`l2tpevents.SessionUp`, is listed as a note: no edge can name a subsystem. A
use taken by code outside every plugin's directory is unjudged, because no
registration could declare its edge.

The check reads what it can resolve statically. A text command dispatched as a
string (the ExaBGP bridge's `send bgp ...`, the DDoS FlowSpec responder), a
namespace subscribed by name, and a handle reached through a local variable are
not seen; such couplings are declared from their own evidence. The stage runs
in the native verification after `plugin gated-table check`.

## What stays ungated on purpose

When other features consume a nil-able seam, or the value types a gated feature
exposes, that contract package stays off the manifest and always-on, and only
the machinery gates. `bfd/api` is the `SetService`/`GetService` seam that BGP,
OSPF and static nil-check, together with `bfd/packet` for its State and Diag
re-exports. `ike/dataplane` is the XFRM programming seam that OSPF's RFC 4552
authentication also uses. Every consumer of such a seam already handles the
absent case, so verify each call site before choosing this shape, and make the
absent-build `nm` needles name the gated sub-packages instead of using the
subtree prefix.
