# Feature Gates

How a compile-out-able feature is declared, wired and proven. A compile-out-able
feature is a subsystem that a build can drop from the `ze` binary through a
`//go:build ze_<feature>` tag, for a smaller binary and a smaller attack
surface.

The obligations are stated in `ai/rules/plugins.md`, section "Feature-Gate
Registration". This page holds the mechanism.

## The inventory is `feature-gates.txt`

The repo-root file `feature-gates.txt` declares every gated package and is the
only place a gate is declared. Read it for the current tag list; no other list
is maintained by hand.

Most features need one line. A feature with owned sidecar packages repeats the
tag:

```
ze_gnmi  internal/component/gnmi
ze_gnmi  internal/plugins/gnmi-cmd
```

The format is `<build-tag>` then `<gated-package>`. Tags are `ze_<feature>` by
convention. The generator gates both `<pkg>` and `<pkg>/yang` when those
packages are discovered: the direct package covers RPC and registration side
effects, and the YANG package covers config or command schema.

## The one invariant

A feature is compile-out-able only when nothing always-on (untagged, non-test)
imports its package, for any reason: lifecycle or a borrowed helper. Always-on
code reaches it only through build-tag-gated registration. One direct `import`
from untagged code pins the package into every binary and defeats the
compile-out. `./le tier check` fails on any such importer.

When always-on code needs a non-lifecycle helper the feature exports, the helper
is extracted to an always-on home first (an `internal/core/*` leaf), and the
feature is gated after. The registry work is the easy half.

## Procedure: add a feature gate

1. **Extract first.** Search for always-on importers of the feature package.
   Move every non-lifecycle helper they use to an always-on `internal/core/*`
   leaf. Re-check until only gated construction remains.
2. **Pick the shape.** A construction registry, or a seam. See below.
3. **Add lines to `feature-gates.txt`** for every owned package that has to
   vanish: the main package plus sidecars such as the command-schema package
   under `internal/plugins/<x>-cmd`.
4. **Create the gated files** for the shape: `service_<x>.go` plus
   `register_<x>.go`, or an `*_infra.go` seam plus gated registration. Each one
   carries `//go:build ze_<x>`. A feature-only helper lives inside a gated file,
   or a no-feature build flags it U1000-unused.
5. **Run `./le repository generate`.** It emits `all_ze_<x>.go` and regenerates
   the derived tag lists from the manifest. Then run `./le verify worktree`.
6. **Write present and absent build-tag tests**:
   `cmd/ze/hub/build_tag_<x>_present_test.go` (`//go:build ze_<x>`) and
   `_absent_test.go` (`//go:build !ze_<x>`). The absent test asserts through
   `go tool nm` that zero feature symbols are linked.

Step 3 is the only declaration point. Everything else derives.

## The registration shapes

**Listener service, the default (looking glass, web).** The feature plugs into
the construction registry in `cmd/ze/hub/service_registry.go`. A gated
`service_<x>.go` builds a `Service`: the `Reconfigurable` listener-migration
contract plus `Name` and `Shutdown`. The `init()` in `register_<x>.go` calls
`registerService("<x>", build<X>Service, wireMigrator)`. The hub iterates the
registry in `buildServices(deps)` and routes the built service through
`registerBuiltService`. Generic inputs cross the boundary as plain values in
`serviceDeps`, and an always-on handle is widened to `Reconfigurable`, as
`setWeb` and `setLG` do. A second construction path, such as a
`ze start --web` standalone mode, goes through a nil-able seam var that the
gated registration sets.

**Seam (ssh, gNMI).** A seam covers a construction shape the listener registry
cannot express. ssh is built inside shared daemon startup, interleaved with
always-on AAA, authz and accounting, and owns an interactive session, so it uses
`ssh_infra.go` (`sshBuild`, `sshWirePostStart`, `sshBuildStandalone`). gNMI has
richer constructor dependencies, a reload notification hook, and no listener
live-migration contract, so it uses `gnmi_infra.go` (`gnmiBuild`,
`gnmiReloadNotify`). Always-on code calls the seam when it is non-nil. With the
tag off the vars stay nil and the feature is skipped.

**Core-level seam (telemetry).** When more than one start site in different
components reaches a gated feature, the seam var lives in the always-on leaf
both sites already import rather than in the hub. The Prometheus exporter
(`ze_telemetry`) starts from the hub standalone path and from the BGP reactor
path, so its hook `metrics.StartExporter` lives in `internal/core/metrics`, and
the hub's gated `register_telemetry.go` wires the gated exporter into it. The
metric collection API, the registry and the `NopRegistry` dummy, stays in that
always-on leaf so dependents keep working while the exporter is gated. A core
leaf holding a nil-able hook var that a gated component `init()` sets keeps
`./le tier check` green, because it is a value rather than an import.

**Plugin compile-out (routing protocols).** When the feature is already a
self-registering plugin the generator discovers, gating is blank-import
partitioning and there is no new `register_<x>.go` or seam. Each owned directory
is its own `feature-gates.txt` line under the shared tag, because a protocol
spans several discovered directories:

```
ze_ospf  internal/plugins/ospf
ze_ospf  internal/plugins/ospf/cli
ze_ospf  internal/plugins/ospf/transport
ze_ospf  internal/plugins/ospf/v3/transport
```

The plugin's `.go` files are not source-tagged. `./le repository generate` moves
their blank imports into `all_<tag>.go`, and dead-code elimination drops the
unreferenced packages when the tag is off.

There are two composition roots: the generated `all.go` and the hand-written
`cmd/ze/ze_core_dispatch.go`. A protocol with a programmatic `cli` package (isis,
ospf) moves its dispatch-root CLI blank import into a per-protocol gated
companion `cmd/ze/dispatch_<proto>.go` (`//go:build ze_core && ze_<proto>`).
Miss that root and the package stays linked. A plugin that registers its CLI
through the plugin registry's `CLIHandler` has only the one root, the generated
`all.go`, and needs no dispatch companion. `ze_vrrp` is the single-plugin case:
the plugin plus its `transport` sidecar, two manifest lines, no `cli` package.

Routing protocols are also the first gated packages that are `sdk.NewWithConn`
engines, and the first multi-package features whose sub-packages import each
other. `./le tier check` therefore counts the generated `all_<tag>.go` as a
registration importer, and skips same-tag importers in the disable-able check,
because a package importing its own sibling is intra-feature.

## Extract-then-gate at subsystem scale

Gating the BGP subsystem is the same blank-import partitioning, but the one
invariant does not hold going in: 27 always-on files imported a BGP package.
Three techniques clear them, in this order of preference. Aim for the fewest
source-tagged files, not the fewest edits.

1. **Transitive package drop, no tag.** A manifest line moves the package's
   blank imports into `all_<tag>.go`, and dead-code elimination does the rest.
   A whole plugin qualifies: `flowspec-firewall` needed one line and no source
   change.
2. **Core-leaf move, no tag.** A contract that always-on consumers share with
   the feature moves to an always-on `internal/core/*` leaf, and consumers
   change an import path only. `ze_bgp` needed three:
   `internal/core/bgp/routeaction` (the route-action vocabulary sysrib and every
   FIB backend use), `internal/core/bgp/msgtype` (the message-type codes MRT
   classifies by) and `internal/core/bgp/ribevents` (the best-change contract
   sysrib and flow export subscribe to). Move the leaf, not the package:
   `bgp/message` imports `plugin/registry`, so relocating it wholesale would be
   a core-tier violation.
3. **Inversion-of-control seam, no tag on the always-on side.** Where always-on
   code reaches into the feature, invert it: the always-on side exposes a
   nil-able hook and the gated code self-registers from its own `init()`. A nil
   seam needs a correct no-feature behavior, not only a nil check. `ze_bgp`
   inverted five: `ze config dump|diff|validate` tree resolution, peer
   validation, the graceful-restart marker writer, the MRT RIB-dump provider,
   the web hex-packet decoder, and the IGP next-hop cost sysrib used to push
   into BGP best-path.

Two traps appear only at this scale:

- **A feature-gated file is still an always-on pin for a different gate.**
  `cmd/ze/hub/service_ssh.go` (`//go:build ze_ssh`) imported `bgp/config`.
  `dep_audit.file_requires_tag` is per-tag and flags that file correctly: a
  `ze_ssh`-on, `ze_bgp`-off build genuinely fails to compile.
- **Removing an always-on import can unlink an `init()` nobody else pulls in.**
  `bgp/config` registers the reactor factory and was linked only because the hub
  imported it. Blank-importing it from `bgp/plugin` cycles in test, so it is
  linked from `cmd/ze/infra_bgp.go` instead: a `package main` root can never be
  imported back, so the edge is always safe there.
- **A seam link gates on the FEATURE tag alone, not on the personality tag.**
  `cmd/ze/infra_bgp.go` carries `//go:build ze_bgp` while its neighbor
  `cmd/ze/dispatch_bgp.go` carries `//go:build ze_core && ze_bgp`, because
  `ze_core` selects the CLI dispatch personality and only the CLI registration
  belongs to it. The two were one file until 2026-09-03, and the wider gate left
  the seams unfilled in every non-`ze_core` binary: the `ze-test` harness
  (`ze_test` plus the feature tags) drives the config editor in-process, so
  `infra.ValidateBGPPeers` answered nil there and an editor `.et` asserting a
  refused commit could not pass. A test binary that links its own composition
  root needs the same edge, which is what
  `internal/component/cli/testing/all_import_bgp_test.go` carries.

## Dependent gates and dependent files

**A dependent gate (`ze_bmp`, `ze_radius`).** A gated package that lives inside
another gate's package tree and imports it can only be built when the parent
gate is on. `ze_bmp` imports `bgp/message` and `bgp/types` and monitors the BGP
RIB, so it exists only in a `ze_bgp` build. The generator detects the nesting
per package (`parentTagOfImport`: the longest gated package of another tag that
is a path-prefix of the import) and emits a compound constraint, so
`all_ze_bmp.go` carries `//go:build ze_bgp && ze_bmp`. That is what makes
`-tags ze_bmp` without `ze_bgp` drop BMP rather than drag the whole engine back
in through BMP's blank import. The dependency is derived from the package path,
so the manifest line stays the ordinary `ze_bmp <pkg>` with no new column. The
present build-tag test carries the same compound constraint as the group file,
so it never runs in a `ze_bmp`-without-`ze_bgp` build.

**A tag may mix independent and dependent packages.** `ze_radius` gates
`internal/component/radius` (RADIUS system auth, usable alone) and
`internal/component/l2tp/plugins/authradius` (needs the BNG). The generator
splits such a tag's group by per-package constraint: `all_ze_radius.go` carries
the plain tag with the independent imports, and `all_ze_radius_ze_l2tp.go`
carries `//go:build ze_l2tp && ze_radius` with the nested subset. A tag whose
packages all share one constraint keeps the single `all_<tag>.go` file.

**Dependent files inside another feature.** When a feature of plugin A exists
only because feature B exists, A's files carry B's tag and each one gets a
counterpart. The cos dynamic RADIUS-CoS handler is `//go:build ze_l2tp` with a
no-op stub, because with no BNG session events there is nothing to react to. The
diag l2tp capture branches live in `capture_l2tp.go` and `capture_raw_l2tp.go`
with stubs that answer "l2tp is not included in this build". The web VPN and
L2TP pages have not-in-this-build stub renderers so the workbench routes stay
valid. A stub answers honestly and names the missing feature.

**Subsystem-builder seam (`ze_l2tp` hub construction).** When the hub constructs
a feature, parsing params and calling `eng.RegisterSubsystem`, rather than
blank-importing it, a hub-local nil-able hook carries the construction:
`bng_infra.go` `bngRegister`, filled by the gated `register_l2tp.go` `init()`.
It is the ssh and gNMI seam shape, carrying only generic values across the
boundary: config trees, the engine handle, portal entries.

## What stays ungated on purpose

When other features consume a nil-able seam, or the value types a gated feature
exposes, that contract package stays off the manifest and always-on, and only
the machinery gates. `bfd/api` is the `SetService`/`GetService` seam that BGP,
OSPF and static nil-check, together with `bfd/packet` for its State and Diag
re-exports. `ike/dataplane` is the XFRM programming seam that OSPF's RFC 4552
authentication also uses. Every consumer of such a seam already handles the
absent case, so verify each call site before choosing this shape, and make the
absent-build `nm` needles name the gated sub-packages instead of using the
subtree prefix.
