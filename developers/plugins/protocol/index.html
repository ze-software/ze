Plugin Protocol

All messages use newline-delimited framing with the wire format #<id> <verb> [<json>]\n.

Wire Format

Every message is a single newline-terminated line:

Message type Format
Request #<id> <method> [<json-params>]\n
Success response #<id> ok [<json-result>]\n
Error response #<id> error [<json-error>]\n
Record answer #<id> <kind> <positional fields>\n: a head, one line for each record, and a terminator

The record answer applies to three methods. It replaces the single success line with a head, zero or more records, and a terminator. Every other method keeps the three forms above.

An answer line carries no verb and no key name. The field after the id is a three-byte word saying what the line IS:

Word The line is
top the head, which opens the answer
row one record the command produced
bad one record it rejected. The walk goes on
end the terminator, which ends the answer
wrn the terminator of a command that completed and states a warning
nay the whole answer to a command text naming no command

The head carries a second three-byte word saying how the records read:

Word The records are
doc one document. The whole answer is that one value
map one map of names to values for each record
tab one positional row for each record, read against the column names

Every field after those is positional and takes one of two shapes. A NUMBER is decimal digits closed by a space or by the end of the line. A TEXT is decimal digits, a colon, then that many BYTES. The count is a BYTE count, never a count of characters. A text of zero bytes is written 0:, so a line's field count never varies:

#43 top doc 0: 0:
|   |   |   |  |
|   |   |   |  +----- column names, 0 BYTES, so the records are not positional
|   |   |   +-------- envelope name, 0 BYTES, so the document carries its own
|   |   +------------ item type doc: the whole answer is one document
|   +---------------- kind top: the head, always the first line
+-------------------- correlation id 43, echoed from the request

#43 row 26:{"running":true,"peers":1}
|   |   |  |
|   |   |  +----- those 26 bytes, the handler's value byte for byte
|   |   +-------- 26, the payload's BYTE count, then its colon
|   +------------ kind row: one record the command produced
+---------------- correlation id 43

#43 end 1 0 0:
|   |   | | |
|   |   | | +----- message, 0 BYTES, so the command stated none
|   |   | +------- 0 rows rejected
|   |   +--------- 1 record produced
|   +------------- kind end: the terminator, always the last line
+----------------- correlation id 43

Neither the head nor the terminator states an outcome. The verdict is DERIVED from what the terminator carries:

The terminator Verdict
✕ done
wrn, no rejected row and no message warning
records and rejected rows, no message ∿
a message over no record error
a message over records aborted
✕ truncated

When the engine cannot build the answer to a dispatch-command, for example because the command's payload is not a JSON object or array, it still writes a head and a terminator whose message names the reason. Your plugin reads error with that message rather than waiting for its timeout.

ipc_protocol.md, "Answer Protocol", carries the same grammar with the buffering threshold and the failure cases beside it.

Method The plugin The engine
dispatch-command reads the answer writes it
dispatch-command-args reads the answer writes it
execute-command writes the answer reads it

One encoding covers both columns, on every connection. Nothing is declared and nothing is negotiated, so a plugin author sets no field and reaches no option.

A plugin READS an engine answer in one of two ways, and both read the same frame. Plugin.DispatchCommandAnswer yields each row as it arrives, which is what bounds the memory of a walk over a large table. Plugin.DispatchCommand and Plugin.DispatchCommandArgs collapse the same answer into the one document a caller that wants the whole payload reads.

A plugin WRITES its own answer to execute-command, and the frame is the same whatever the payload is. A handler that returns a plugin.Records writes one line for each row of the walk. A handler that returns a built value writes that value as the one record of a doc answer, byte for byte.

  • <id> is a monotonically increasing uint64 correlation ID
  • <method> uses YANG-style <module>:<rpc-name> naming (e.g., ze-plugin-engine:declare-registration)
  • JSON payloads are optional (omitted when empty or null)
  • Responses use ok or error as the verb; requests use the method name

Routing: MuxConn multiplexes a single connection for concurrent RPCs. A background reader goroutine routes incoming lines by verb: ok/error responses go to the waiting CallRPC caller by #<id>, while method-name requests go to the Requests() channel.

Examples:

# Plugin sends declare-registration (Stage 1)
#1 ze-plugin-engine:declare-registration {"protocol-version":1,"families":[{"name":"ipv4/flow","mode":"both","afi":1,"safi":133}]}

# Engine answers the protocol version both sides speak
#1 ok {"protocol-version":1,"plugin-name":"flow-export"}

# Engine sends configure to plugin (Stage 2)
#1 ze-plugin-callback:configure {"sections":[{"root":"bgp","data":"{...}"}]}

# Plugin responds OK
#1 ok

# Engine sends event at runtime
#42 ze-plugin-callback:deliver-event {"event":"{\"type\":\"state\",...}"}

# Plugin responds OK
#42 ok

# Error response with payload
#5 error {"code":"error","message":"unknown family: ipv4/unknown"}

Protocol Stages

The SDK handles the 5-stage startup protocol automatically via Plugin.Run().

Ze reads every key of a declaration, and refuses one it does not know. A key ze skipped would start your plugin without what the key declares, so a key outside the tables of this section, at the top of the declaration or inside any entry the tables define, fails Stage 1 with an error that names your plugin and this section. The daemon, show plugin declarations and the conformance check read a declaration the same way. A declaration that carries no protocol-version gets the version refusal instead, the one that names its real problem ("The protocol version", below).

The modules were once one object under schema. Ze reads no value under that key, and a declaration that carries it is refused with the fix: send "schemas":[{"module":...,"namespace":...,"yang-text":...}] in place of "schema":{...}.

The failure policy is what your plugin asks ze to do when your plugin fails. It is voluntary, and a plugin that omits it is carried on without. A value that is none of the three fails the whole registration, so ze never guesses.

You declare ze does May ze start your plugin again?
restart starts the plugin again, bounded at 5 in 60 seconds and 20 in the life of the daemon ✓
ignore logs it and carries on without the plugin ✕
fatal stops ze, which exits 1 ✕

fatal is open to any plugin, whether ze ships it or you wrote it (owner directive, 2026-09-06). An operator who configures your plugin accepts its terms.

Declaring anything other than restart also says your plugin must NOT be started again. An operator whose plugin { external <name> } block writes respawn true for such a plugin gets a daemon that refuses to start, with an error naming your plugin and the policy it declared. Declare restart when your plugin can come back from a crash, which usually means its state lives outside the process.

The session-ready report says your share of a peer's initial routing update is out. It is voluntary. Declare signals-session-ready only when your plugin pushes routes into a peer from that peer's peer-up event. A plugin that pushes on its own schedule leaves it false and owes no report.

A peer counts your plugin only when three facts hold: its attach process block grants you send [ update ] or send [ raw ], you declared signals-session-ready, and it grants you receive [ state ], so you see the peer-up event. Once your routes for that session are sent, dispatch:

request peer <address> plugin session ready session <initial-replay>

<initial-replay> is the token from that peer-up event's initial-replay field (docs/architecture/api/json-format.md). Send one report per peer-up, even when you had nothing to send.

What the report does:

Situation What ze does
You report ze credits the report to your process for that session, once. A second report is not credited again
You report with a token from an older session, or for a session that is going down ze refuses it with an error naming the problem
You report for a peer ze does not have ze credits it to nothing and logs a WARN naming the peer
You never report Ze sends its End-of-RIB marker once its own table is out. For a peer covered by your live-forward fence, live changes remain held until every fence owner reports for the captured session or that session ends

To hold live forwarded changes behind your initial replay, also declare fences-live-forwards: true. Stage 1 refuses that flag without signals-session-ready: true. Send the captured session-ready report after replay is out; it releases the hold for that session. End-of-RIB still waits for no report. Without the fence opt-in, your existing non-fencing behavior remains. Neither flag grants an attachment, a receive subscription or send permission. Removal or replacement ends the old process's declaration. Ze uses your current authenticated Stage-1 flags even when your process name also names a compiled plugin. Forked in-tree programs declare the flags too. Only an Internal runner can use its compiled defaults.

Each CommandDecl has these fields:

Field Type Description
name string Command path the plugin serves
short-help string The one-line SUMMARY. Every surface that shows the command on one line reads it. One line, at most 256 bytes, no control character
description string The LONG explanation the command's own help page prints. At most 4096 bytes, newlines kept, every other control character refused
args []string Argument names, for the help and completion of a command no module defines. A command a -cmd module defines takes its arguments from the module's leaves (commands.md)
completable bool Whether the command supports tab completion
hidden bool Whether the command is left out of help and completion
deprecated-names []string Older spellings that still reach this command
shape string What the answer holds: doc, map, tab or blob
columns []string The answer's keys, in the order a person reads them. Needs a shape that has rows. Maximum 64
address-fields []string The keys whose value holds an IP address or a prefix. Needs a shape. Maximum 16

The last three are optional and additive. A plugin that sends none keeps the behavior it had before they existed. A plugin that sends one the engine refuses fails Stage 1 and does not start.

short-help and description are two texts and neither is derived from the other. The key is description and not help, because help already names the SUMMARY in a completion row on this same protocol. A command entry that still carries help, the summary's spelling before short-help, fails Stage 1 with an error that names short-help. A plugin that sends short-help and no description renders with its summary and an empty explanation. That is what every plugin written before description existed sends. An empty description NEVER renders as an empty summary.

validateHelpDecls reads both texts before any conversion. It refuses a text past its bound, and a control character the text's shape does not allow. The summary reaches the tab-separated shell-completion format and the one-line terminal candidate. A newline, a tab or an ESC in it breaks the format for every row that follows. The alias description below is held to the same one-line rule.

Each PipeDecl has these fields:

Field Type Description
command string Command path the alias sits on. MUST be one of this plugin's own declared commands
name string The word an operator types after the pipe character (kebab-case, 1-64 chars)
description string The one-line summary completion and command help show beside the name. At most 256 bytes, no control character
expansion string An alias: the operator chain the name stands for, as an operator would type it
argument string An operation: what the words after the name may be, one of none, optional, text, count (a positive whole number), fields (field names) or path

An entry states exactly one of expansion and argument; both, or neither, is refused by name. With argument the entry is a pipe OPERATION the plugin's handler runs: the daemon validates the typed words against the kind and sends the operation in the pipe list of execute-command ([{"name":"top-talkers","args":["5"]}], in the order typed, args absent for an operation typed with none), which the Go SDK hands the OnExecuteCommand handler as its pipe parameter. The words never reach args, and the daemon runs every generic operation after them over the answer. A name a generic operator holds is refused, except count, first, last and match, which a command may override with the generic's own argument kind and answer shape. A name an alias of an overlapping path or a global alias holds, a command path that already holds another owner's operations, and one name twice in one message are refused too, and nothing of the list is recorded.

A pipe alias SELECTS and re-sequences the answer the command already returned. It renames no key, sums no numbers and counts no rows, so the command MUST emit the aggregate fields beside the detail rows. One bad entry refuses the whole list and fails the plugin's startup. Read docs/architecture/api/commands.md for the collision rules and the payload obligation.

Wire example:

#1 ze-plugin-engine:declare-registration {"protocol-version":1,"families":[{"name":"ipv4/flow","mode":"both","afi":1,"safi":133}],"commands":[{"name":"flowspec status","short-help":"Show FlowSpec status"}],"wants-config":["bgp"]}
#1 ok {"protocol-version":1,"plugin-name":"flow-export"}

The protocol version. The engine answers Stage 1 with the version both sides speak from then on: the lower of the plugin's protocol-version and its own. A plugin declaring a version above the engine's speaks the answered version. A declaration with no protocol-version is from the text era, before filters declared the route fields they read, and the engine refuses it with one error that names the plugin and the version to declare; the startup tier then stops, as for any plugin failure. Version 1 is the first versioned contract. The Go SDK declares it and refuses an engine that answers any other.

The answer also includes plugin-name, the configured instance name of the authenticated process. It can differ from the implementation's name. The Go SDK exposes this through Plugin.InstanceName() before OnConfigure runs; before the Stage 1 answer it is empty. Use that configured identity in recovery commands that restart the plugin.

Engine sends ze-plugin-callback:configure with a ConfigureInput:

Field Type Description

Each ConfigSection has:

Field Type Description

Wire example:

#1 ze-plugin-callback:configure {"sections":[{"root":"bgp","data":"{\"bgp\":{\"peer\":{...}}}"}]}
#1 ok

Refusing the configuration. Answer with #1 error and the reason when you cannot take what you were sent. That answer is a refusal: ze stops your plugin, and ze itself stops when your registration carries FatalOnConfigError, so an operator who mistyped a value is told rather than left with a router silently missing your feature. Return an error from your OnConfigure handler and the Go SDK writes that response for you.

#1 ze-plugin-callback:configure {"sections":[...]}
#1 error {"code":"error","message":"address family \"ipv6-unicat\" is not a family"}

Never answer ok for a configuration you rejected, and never just close the connection: a lost connection is a transport failure, which says nothing about the configuration and so never stops ze.

Stage 5: Ready (Plugin to Engine)

Plugin sends ze-plugin-engine:ready with an optional ReadyInput:

Field Type Description
subscribe SubscribeEventsInput Optional startup event subscription
transport string "bridge" for internal plugins; pipe closed after ack

The subscribe field allows plugins to register event subscriptions atomically with startup completion. This avoids a race where SignalAPIReady triggers route sends before a separate subscribe-events RPC could be processed.

When transport is "bridge", the engine publishes bridge callbacks on the PluginConn before acknowledging ready. The SDK activates that bridge, runs OnStarted, then closes the startup pipe and begins its bridge event loop. Subsequent generic callbacks flow through bridge.CallbackCh() instead of the MuxConn, so bridge activation alone is not initialization completion.

Wire example:

#3 ze-plugin-engine:ready {"subscribe":{"events":["update","state"],"peers":["*"],"format":"json"},"transport":"bridge"}
#3 ok

After the ready acknowledgement, the SDK activates the DirectBridge for internal plugins, initializes local resources through OnStarted, then enters its event loop. If Stage 1 declared started-handler, the engine sends the empty ze-plugin-callback:runtime-ready callback and waits for its answer before starting a dependent tier. The ordinary callback queue can answer only after initialization succeeds, including when the bridge already reports activated.

For an internal bridge, the engine also joins this answer when no initializer was declared. The SDK default answers through its active bridge loop. The final ready response alone does not prove that the SDK activated its typed slots. This receipt joins activation before startup succeeds.

An initializer may make ordinary engine calls during that wait; socket startup serves them through the same operation registry as the runtime connection. Cross-plugin commands still belong in OnAllPluginsReady.

Query Mode: Answering Without Starting

Ze can start your plugin to ask what it declares, with no hub to connect to. Two commands do it: ze show plugin conformance run "<run string>", which needs no daemon, and show plugin declarations config <file> typed in a session a running Ze serves. With no daemon the second one starts nothing and lists your plugin as not-available. Either way Ze sets ZE_PLUGIN_MODE=declare in your process's environment. Your plugin writes its Stage 1 declaration to stdout, exits 0, and does none of a live start's work: no data initialization, no connection, no bind, no listener, no timer.

What you call

sdk.RunOrDeclare takes your declaration and your start function as two arguments and returns the exit code:

// declaration is what this plugin provides. It is a pure value: no file, no
// socket, no goroutine.
func declaration() *sdk.Registration {
    return &sdk.Registration{
        Commands: []sdk.CommandDecl{{Name: "show acme-monitor status", ShortHelp: "Show monitor status"}},
    }
}

func main() {
    os.Exit(sdk.RunOrDeclare(declaration(), start))
}

// start does everything a live start does, and query mode never calls it.
func start() int {
    p, err := sdk.NewFromEnv("acme-monitor")
    if err != nil {
        return 1
    }
    defer p.Close()
    // ... register callbacks, open files, dial, start timers ...
    if err := p.Run(context.Background(), declaration()); err != nil {
        return 1
    }
    return 0
}

The declaration is the same *sdk.Registration you pass to Plugin.Run, so query mode reads nothing new and adds no second list to keep in step.

What the SDK guarantees

  • Your start function is NOT called under the mode. Side-effecting code inside it is unreachable during a query, not merely discouraged.
  • The line written is the Stage 1 declare-registration message in the protocol's own framing, so the reader parses one format.
  • A declaration naming no command and no pipe still writes the line. "Declared nothing" and "sent nothing" are different answers.

What it does not guarantee

  • Work your main does BEFORE the call runs under a query too. The SDK cannot reach it. Put every side effect inside the start function.
  • Plugin.Run derives wants-validate-open from the callbacks you registered. A query has no Plugin, so state that field in the declaration you pass here when you want it in the answer.
  • A plugin that adopts neither this entry point nor the ze plugin route is reported as having sent nothing. Ze cannot make a binary it does not compile inert, so for third-party code this is enforcement for adopters and convention for everyone else.
  • QueryModeRequested() reports the mode for a plugin that has its own reason to branch. It is a reader, not a guarantee: the branch is yours to place, and anything above it has already run.

Write the declaration line alone

In declare mode, write nothing to stdout except the declaration line. Send every diagnostic, banner and log line to stderr.

The line is #1 ze-plugin-engine:declare-registration, one space, and the declaration as compact JSON, ended by one line feed (LF). A carriage return, a second line, a blank line and white space between the JSON tokens each break the rule. sdk.RunOrDeclare writes the line in this form.

Two readers apply the rule differently. The reader behind show plugin declarations finds the declaration line and skips each other line on stdout, so the daemon side still reads a plugin that writes a banner. The conformance checker is strict: its declaration-line row fails when stdout holds more than the one line, and the row names the rule the output broke. A plugin that passes the strict check is read correctly by every reader. ze show plugin conformance run "<run string>" runs the check (testing.md, "Checking That a Program Is a Valid Plugin").

An OnConfigComplete handler automatically declares config-completion in Stage 1. Its context carries the absolute deadline-ms work bound. Complete cleanup before returning: callback queue admission is not a receipt. Keep operation journals through OnConfigOperationCommit; discard only the matching transaction on accepted completion. Rejected completion follows original undo, after section-owned configuration and filters have been restored. A completion error after acceptance reports an active candidate, not a rollback. Requests and receipts MUST carry an explicit JSON boolean accepted, including false for rejection. Missing or null decisions never invoke SDK cleanup and never acknowledge completion to the engine; they are malformed messages.

Plugins retaining source state MUST declare source-policy-owner in Stage 1, even if they do not implement the lifecycle yet. That unsupported declaration refuses policy changes before publication; pure observers are not owners. In Go, a plugin with no handler sets SourcePolicyOwner: true in the sdk.Registration it passes to Run; the engine then refuses the change and tells the operator to take the peer down around it.

Plugins that defer work after returning from an event handler register OnEventSettlement(func(context.Context) error) before Run. The SDK derives the event-settlement declaration and starts one independent worker with at most 16 waiting requests. The handler MUST finish downstream work before it returns, honor its request deadline and synchronize shared state. Ordinary callbacks and current-selection lookups remain live during this wait. The engine first awaits event application; settlement never replaces that FIFO receipt. A plugin written in another language declares the same support and answers event-settlement with the echoed deadline-ms, explicit status and a cause for failure. An error or missing outcome never confirms completion. OnSourcePolicy(func(context.Context, rpc.SourcePolicyInput) error) automatically declares both ownership and source-policy handler support. All four operations use one registered callback on both transports, not the shutdown OnDrain path.

Requests carry a transaction, operation, captured source identity, target epoch and absolute deadline. The engine sends the earlier of its caller's budget and the request deadline, so the handler's context never outlives the caller. The source identity comprises peer, peer incarnation, session generation, original policy epoch, receive frontier and template generation. Every field MUST be present and non-null; the last two may be zero. Prepare/finalize require explicit target zero. Apply requires a fresh target newer than the captured epoch. Abort carries target zero when the transaction was prepared and never applied: release your prepare pins and change nothing else (no restamp, no eligibility change, no downstream write). After apply, abort carries a fresh target newer than the captured epoch, and you restamp restored state to it. Refuse a zero abort after apply. The coordinator enforces monotonicity between calls. The SDK rejects malformed, unknown and expired requests before calling the owner.

The engine strictly drains event application before prepare, but the handler MUST additionally fence its own workers and downstream writes. It MUST honor the context deadline and return only after the requested work settles. Keep prepare pins through apply; abort restores them (a zero-target abort only releases them), while finalize releases accepted pins. The SDK returns an exact identity/target receipt only after the handler returns. The engine checks the captured process and connection again after acknowledgement. Neither this callback transport nor copied epoch fields alone invalidate routes.

The handler does not run on the callback loop. The Go SDK starts one source-policy worker for the plugin's connection and stops it with the plugin, on both transports, so a handler may wait for events delivered after its request, or call the engine during prepare or apply, without blocking the loop that delivers them. What that means for your handler:

  • It runs concurrently with OnEvent and the other callbacks. Protect the state they share. Every event delivered before the request has already been applied when it starts.
  • Calls never overlap and arrive in the order the engine sent them, so one source's prepare, apply, abort and finalize reach you in order.
  • Its context ends at the request deadline or when the plugin stops. A request that expired while queued fails without calling you.
  • At most 16 requests wait behind the running one. A request beyond that is answered at once with an error receipt saying the queue is full, and your handler never sees it.
  • A panic fails the request, and nothing runs after it: every request already queued gets a failed receipt, then the plugin's connection ends with that error. A plugin written in another language owes the same: answer source-policy without stopping its event delivery.

Retained/replayed received routes MUST preserve their original StoredRoute.SourcePolicyEpoch (source-policy-epoch), never stamp the current epoch onto old work. Zero is unrecorded, independently of session generation.

A peer's AS is not always known when an event is written. A dynamic peer's AS comes from its OPEN, so the OPEN Ze sends, a NOTIFICATION Ze sends in OpenSent and the FSM changes before OpenConfirm carry none. The JSON peer object then omits remote.as, a text line says remote as unknown, and StructuredEvent.PeerAS is the zero rpc.RemoteAS, which means "not yet known" and never AS 0. Read it with PeerAS.ASN(), which answers (uint32, bool), and branch on the bool. An UPDATE always names the AS. Rendered without a branch, it writes the number or unknown through %v, %s and log/slog, and the number or null through encoding/json, where a field tagged omitzero is omitted while the AS is unknown.

Every peer event also carries the engine's stable Peer incarnation as numeric peer-owner in JSON, peer-owner <uint64> in text, and StructuredEvent.PeerOwner internally. It agrees with SourcePolicyIdentity.PeerOwner. A reconnect retains that owner but receives another source-receipt; removing and recreating a peer changes the owner. The address, AS number and socket ports cannot identify the Peer incarnation. Zero is unrecorded and supplies no source authority. A sent event's peer owner identifies its recipient; its original route source remains separate provenance.

A session-down event names the session it ended: session-generation in the JSON and text forms, StructuredEvent.SessionGeneration in the structured one, a nonzero number captured when that session closed. An up carries none. A forwarding plugin that asks the engine to withdraw or replace a departed peer's routes (recovery-source meta on its update command) MUST name that session as recovery-generation meta, a decimal string: the engine refuses a departure without it, and with it owes only routes that session or an older one wrote, so a down handled after the peer reconnected never takes the newer session's routes (docs/architecture/plugin/rib-storage-design.md, "Source-DOWN replacement and sent ordering").

The filter-update batch

One filter-update exchange carries a batch of routes. The request is {"routes":[...]}, each entry one route as FilterUpdateInput describes it (filter, direction, peer, peer-as, fields, raw). The answer is {"verdicts":[...]}, one FilterUpdateOutput per route, at the position of its route.

#7 ze-plugin-callback:filter-update {"routes":[{"filter":"lp","direction":"import","peer":"192.0.2.1","peer-as":65001,"fields":{"prefix":{"ipv4/unicast":["10.0.0.0/24"]}}},{"filter":"lp","direction":"import","peer":"192.0.2.1","peer-as":65001,"fields":{"prefix":{"ipv4/unicast":["10.0.1.0/24"]}}}]}
#7 ok {"verdicts":[{"action":"reject"},{"action":"modify","sets":[{"field":"med","action":"set","value":50}]}]}
  • What a batch holds. Ze sends the routes queued for the plugin when the exchange starts, at most rpc.FilterUpdateBatchMax (64), and splits that FIFO group into contiguous exchanges that each fit the 16 MiB RPC request frame, including its JSON envelope, method and request ID. A lone route goes at once in a batch of one; routes that queue while an exchange is in flight go in the next group. Routes from one source stay in order within and across exchanges, and each verdict stays paired with its original route. A route whose serialized input cannot fit a frame even alone fails only itself under its filter's on-error, not its queued neighbors.
  • One timeout per batch. rpc.FilterUpdateTimeout (5 s) bounds the whole exchange. When it expires, or the plugin answers an error, each route of the batch takes its filter's on-error, one outcome per route.
  • Queue admission and the typed slot. Only the encoded transport creates a per-route rpc.FilterUpdateTimeout (5 s) deadline, before encoding the route and waiting for room in the bounded batch queue. An earlier caller deadline or cancellation still wins. Once admitted, the route waits behind the bounded queue's predecessors and any exchange in flight, then its own exchange, each bounded separately by the batch timeout. An activated typed slot calls the evaluator synchronously under the fast-path contract, with no unused route context or timer. A closed slot fails the route; it never falls back to the queue.
  • One verdict per route. A reply with more or fewer verdicts than the request held routes is malformed: no verdict of it is applied, and each route of the batch takes its filter's on-error. The next batch is judged normally.
  • A route the filter cannot judge. A verdict carrying error (a string) fails that route alone under its filter's on-error; the other routes of the batch keep their verdicts. A nonempty error takes precedence over every other verdict field: no action, sets, raw rewrite or teardown is applied. The Go SDK answers this way when the evaluator fails: answerFilterBatch calls the evaluator OnFilter installed once per route, in request order, and an error it returns or a nil verdict fails that route alone, so a Go filter is written for one route. The same evaluator run internal, through the typed slot, gets the same answer: a returned error, nil verdict or nonempty verdict error fails that route alone, before raw ownership processing, and counts no completed typed judgment. The conformance harness compares these consumer-visible failures rather than the ignored fields of a failed verdict.

  • A declared field the route does not carry is left out of the object.
  • A filter that declared no route field (a raw-only filter) is sent no fields member, and raw is sent only to a filter that declared raw.
  • A field Ze cannot read, such as a malformed attribute, is never sent empty: the filter's on-error decides the route instead of the filter.
  • Stage 1 refuses a declared BGP field this binary cannot write: the community fields need bgp-filter-community, originator-id and cluster-list need bgp-rr, and aigp needs bgp-aigp.
  • The values are the route as the earlier members of the chain left it: a local-preference, med or community an earlier member set, in process or in a plugin, is what this filter reads. raw is still the received body. A filter that declared no reads fails the route under its on-error.

  • A later filter of the chain is sent the value an earlier filter's sets left, not the received one.
  • An increment or decrement starts from the route's value, or from bgp defaults attribute when the route carries none, and stays within 0 and 4294967295. The changes fold in chain order and produce the same UPDATE bytes.
  • The route fails under the filter's on-error, logged and counted, with none of its sets applied, when an entry names a field the filter did not declare, a field the chain's attachment does not let a filter set, or a field no BGP chain sets; when the action is not one the field takes; or when the value has the wrong shape. The other routes are judged on their own.
  • A prefix remove needs only that the filter declares it reads prefix, and a family remove that it reads family. Each drops only what the filter was shown, so neither is a set the filter declares, and both work at a BGP attachment, which lets no filter set prefix or family.
  • The as-path, prefix and family entries are intents Ze resolves with state the plugin does not hold: a prepend uses the local AS and the session's AS number width, "private-peer-as" the peer AS, a prefix remove drops the entry from the body NLRI and from MP_REACH_NLRI (an MP_REACH_NLRI left empty leaves the UPDATE), and a family remove drops that family's MP_REACH_NLRI and MP_UNREACH_NLRI (the body NLRI and withdrawn routes for ipv4/unicast). Prepends add up across the chain to at most 32. A labeled remove drops the entry whose prefix and whole label stack match, label field included (RFC 8277 Section 2.3). A prefix the route does not announce, one with host bits set, or a value whose shape names another kind of NLRI (a label stack for a unicast entry, a plain prefix for a labeled one) fails the route.
  • "action":"withdraw" removes the route rather than only stopping it: on import the engine treats the route's announcements as withdrawn by the peer that sent them, so a version accepted earlier leaves the RIB; on export the route is withdrawn toward that destination. Every route of the UPDATE is withdrawn: one whose MP_REACH_NLRI and MP_UNREACH_NLRI name two families is withdrawn as two UPDATEs, one per family, because one UPDATE carries one MP_UNREACH_NLRI. Both generated withdrawals carry the original policy decision: import does not run the filter again on the attribute-free follow-up. The later filters of the chain are not called.
  • A filter that declares no reads is never called: Ze has no field to send it, so every route the chain asks it to judge fails, and the chain treats the failure as on-error reject whatever the filter declared. Declare at least one field the filter reads, or raw.
  • The route fails the same way when the answer carries sets beside accept, reject or withdraw.
  • A filter that declares raw among its reads may answer "action":"modify" with a whole-body raw rewrite and no sets. A valid rewrite is terminal: the later filters of the chain are not called, the chain's final still decides the route, and the rewrite is sent in place of the received body. Before it can end the chain, Ze checks the UPDATE section framing and applies the receive path's mandatory RFC 9012 Section 13 tunnel checks and normalization. A malformed rewrite is a named member failure, logged and counted on a live run, under that filter's on-error: reject drops the route; accept discards the failed rewrite and continues to later members with the route unchanged. A dry run follows the same decisions and records the member failure without logging or counting it. The same failure rule applies when the filter did not declare raw, when the body is shorter than its two 2-octet length fields or a section extends beyond it, and when an earlier member already set a field: a rewrite made from the received body would discard that change. It also applies when a filter answers raw on a pass over a body that differs from the chain's input ("Filter Run Occasions").
  • teardown on an import route closes the session; on export it is ignored and the action stands.

Filter Run Occasions

An export chain calls a filter once for each route. Two fields of the filter's declaration add occasions, and both default to false. Stage 1 refuses each one on an import-only filter. The request does not name the occasion: the same filter-update message arrives each time.

Field When the filter also runs Which members run What decides the route
readvertise A graceful-restart retention re-advertises its stale routes (the stale readvertise rail) Only the external members that declare it. The route's stale metadata is set A route that reaches the end of those members is sent: the chain's final is not read. A raw answer ends the run and the final decides it, so a chain whose final is reject withholds a raw answer where it would send a set answer
judges-final The export chain rewrote the body, by a set or by a raw answer Only the external members that declare it, in chain order The answer of the pass replaces the answer of the chain. A route that reaches the end of the pass is accepted, because the chain's final already decided it. A raw answer, allowed only when the rewritten body equals the chain's input, ends the pass and the final decides it

A member whose declaration Ze cannot read, because its plugin has gone or no longer declares the filter, runs on both occasions and fails under on-error. Whether it opted in is unknown, and it may be the filter that withholds the route.

The stale readvertise rail. The rail takes its body from what Ze already sent, so the route has passed the chain once. If the destination's export policy changed after the route was sent, the policy of that first run no longer applies. Ze then runs every member that does not declare readvertise, then the chain's final, then the members that declare it over that result, with raw holding the body the rail started from.

The pass over a rewritten body. The pass reads raw as the route the chain received, and every other field from the rewritten body. A filter that declares raw compares the two to see what the chain took off. The pass may reject, withdraw or set. A raw answer is refused when the pass runs over a body that differs from the chain's input, because it would discard the rewrite. The refusal is a member failure under that filter's on-error. show policy test shows the pass.

The pass protects a member's answer from a member that does not declare judges-final. It does not protect that answer from a member that does: the last one in chain order has the last word.

On the stale rail, a member must declare both fields to run in the pass, unless the policy changed, in which case every member that declares judges-final runs. The rail skips the pass when it has one member and that member is the chain's only judges-final member, because it already ran last.

What repeats. A judges-final filter that ran in the chain runs again on every rewritten route. A readvertise filter answers again on bytes it already judged when the route was first sent. A filter that declares both can run more times than that on one route.

What a filter author makes safe to repeat. The filter MUST answer correctly on a route it already changed:

  • A verdict MUST hold on the rewritten body, not only on the body the filter first saw. Read raw to see the route before the chain changed it.
  • A set that adds to the route applies again. A prepend of the AS path in the pass doubles the copies. Compare first, or set a value that the second run leaves as it is.
  • A side effect in the filter (a counter, a log line, a lookup) happens on each run, so it cannot count routes.

A matching subscription on the emitter refuses the operation before publication. Ordinary EmitEvent retains queue-only behavior.

The same emit-event RPC carries await-applied: true and deadline-ms. Success requires applied: true and the exact request deadline. A failed or canceled call can leave partial application. It cannot authorize source cleanup or confirm downstream output. Resolve the named failure before retrying.

Selected output receipts

SelectRoutes is the selected-owner operation; RelayStoredRoute keeps its existing source-owned behavior. Supply the destination's exact UP initial-replay token as destination-session, a monotonic nonzero revision, and native key-nlri advertisement bytes without the source ADD-PATH prefix. The engine derives semantic identity through the registered family codec.

Use kind 1 with a received StoredRoute and engine-issued source receipt, kind 2 with an admitted origin and origin receipt, or kind 3 for selected absence. The engine authenticates these handles; sending a number does not create authority. Received paths preserve original message/policy provenance and the explicit ADD-PATH distinction, including path identifier zero. Stale levels are 1 fresh, 2 stale and 3 LLGR; absence has no stale level. The complete field and validation contract is in Selected-route output.

Keep the input unchanged until return and bound each exchange by rpc.SelectRoutesExchangeSize(input) <= rpc.MaxMessageSize. This reserves both request and worst-case final answer; absence receipts can be larger than their input. SelectRoutesFrameSize continues to measure the request alone. The SDK requires a complete ordered final receipt on both transports. Outcomes are written, suppressed, absent or stale revision; suppression and absence settle the previous selected output's retirement. Success must follow final writer completion. Never wait for a sent-event callback to finish the RPC: a lifecycle callback may already hold that plugin delivery loop. An unsupported reactor returns an error.

Use SelectRefresh to bracket a selected replay on that same owner's stream. Preserve the captured address, peer-owner and destination-session, and name one negotiated family. Action 1 begins and action 2 ends the replay. Await Begin, every final route receipt, then End. Its complete receipt echoes those identities and action; outcome 1 means the marker was written, while 2 means enhanced markers were not negotiated. A zero or missing receipt fails. This uses the effective selecting role and its existing update send grant; it grants no right to send a normal refresh request. If our own OPEN advertised GR, Begin requires this connection's actual completed EOR for that family.

The SDK sets the absolute deadline-ms from the caller's context, capped at thirty seconds per batch. When that context ends, the socket form sends cancel-request for its original correlation ID and method, and joins the remote handler and final writer before returning cancellation. The separate cancellation receipt budget is five seconds. A broken transport or failed join returns rpc.CancellationUnsettledError; report the unresolved destination instead of treating it as settled. A cancellation during a partial request write ends that connection. Typed handlers receive the caller's bounded context and must also finish their writer before returning.

System routing views

Each selected path's ecmp list retains the owning source of every member. The optional member protocol is a registered name for an owner different from the primary. Omission means the primary's protocol owns that member. Consumers resolve supplied names from existing registrations and reject an unknown name. The authority keeps same-target members with different owners until the consumer applies each owner's FIB permission, then renders the target group. Member ownership never changes the primary protocol credited with the prefix.

The system RIB owns the ze-sysrib namespace. Its routing view transfers the daemon's selected routes as values to either an internal or an external consumer. The daemon remains the authority for route admission, import policy, administrative distance and selection.

open accepts an optional reader: selected-feed or local-authority. An empty input selects selected-feed. The authenticated process generation owns the returned session token. Subsequent requests carry that token and cannot choose another plugin's identity. A selected page carries the server epoch, cursor, explicit snapshot, delta or reset phase, and completion flag. The consumer MUST finish the initial snapshot before forwarding and MUST discard its projection on reset. An empty delta preserves the current projection. An explicit reset can advance the cursor to a newer fenced marker. It clears readiness and authorizes no forwarding. Older reset cursors remain invalid.

A refused publication does not by itself authorize reopening. For a benign selected-feed retention reset, a subsequent read on the exact refused session may return rejected-publication, a positive operation identity. The consumer MUST require its exact refused operation and validate the complete Reset page before rebuilding. The proof cannot carry entries, a snapshot or completion. Omission grants no proof; explicit zero and null are invalid. The daemon retains one fully validated refused batch, and only its exact operation, cursor and values can repeat that proof. Malformed attempts, output delivery errors and foreign or replaced leases cannot acquire it. Internal local readers do not use selected-feed publication recovery.

local-authority requires an authenticated internal system RIB with direct access to the daemon's Loc-RIB. It retains no selected snapshot or delta journal. Its direct reader is ready at logical cursor zero. Distance acknowledgment follows authoritative reselection and returns zero. Selected reads require reopening with selected-feed. Both transports provide the same reader choices and refusals. External system RIBs use selected-feed.

Requests require every mandatory field even when its value is zero. read requires explicit cursor and wait-ms fields. Candidate reads and publications also require an explicit cursor. Unknown request fields and null mandatory fields fail before the session changes. An omitted distance list remains empty.

The complete request must fit rpc.MaxMessageSize, including its method and correlation ID. rpc.RouteViewRequestBudget reserves the widest ID and the method header. Direct calls enforce the same bound.

read accepts a record limit from 1 through 4096 and a wait from 0 through 1000 milliseconds. The producer MUST also keep the complete encoded reply within rpc.MaxMessageSize; rpc.RouteViewResultBudget() reserves framing for the widest correlation ID. The same bounds apply to Direct calls. A selected path includes its protocol name and instance, resolved distance, recursive metric and BGP/AIGP metadata, primary and equal-cost targets, labels, SID and repair target. Presence flags preserve zero tags and zero AIGP. Protocol IDs local to a process never cross this boundary. The selected path requires non-null protocol, instance, distance and metric fields. Explicit zero ranking values remain valid. A distance row requires non-null protocol and distance, including an explicit zero distance. Malformed values leave the current decoded value unchanged.

Candidate scans use their own snapshot and cursor. Their entries preserve the existing show rib candidates JSON, including hidden paths and a present zero tag. A candidate scan does not feed selection. distances carries a complete protocol distance declaration and an ordered operation ID. Its acknowledgment follows authoritative application and reselection.

publish wraps the unchanged system best-change JSON with the consumed cursor and operation ID. The consumer MUST retain this operation until acknowledgment. The owner MUST fence stale generations before emission and return an identical retry's acknowledgment without emitting twice. A newer completed read preserves that original acknowledgment. A new operation requires the latest consumed cursor.

Each publication accepts at most 4096 changes. The JSON adapter refuses an excess row before decoding the remaining rows. Device and gateway-zone names must contain valid UTF-8 through both transports.

Publication withdrawals retain an explicit empty protocol field. Device-only ecmp-paths and backup members retain an explicit empty next-hop and name their interface. The publication schema accepts these existing event values. Add and update still require a registered protocol, and each member requires a gateway or interface. Selected-view addresses keep their nonempty address type.

Every emitted batch retains independent storage. A failed withdrawal keeps its ledger entries and blocks replacement until retry succeeds. Owned interface devices and firewall tables

A plugin compiled into ze that owns kernel state asks the interface and firewall components to create it, so the same calls work internal and forked. Only a plugin that granted itself device name prefixes (iface.MustGrantOwnedDeviceNames) or reserved table names (firewall.MustReserveTableNames) from its init() is accepted. A plugin built outside the ze binary cannot make either declaration, so every call it makes is refused. The owner is the plugin's authenticated name: a forked plugin MUST be declared under its registry name.

The bridge and table calls replace the caller's complete set; an empty set withdraws everything the caller holds. FirewallTablesReplace carries its tables as a firewall config section, {"firewall":{"table":{...}}}, the form the operator's firewall config takes. OwnedLinkCreate names the target network namespace by a process id and that namespace's inode number together, and is refused when they disagree.

The three interface calls answer with the kernel's outcome: the bridge set is reconciled and the link is created before the call returns. OwnedLinkCreate answers the host end's name, built from the plugin's first granted prefix, the bridge's interface index and the slot. The peer end is created inside the namespace with its name, hardware address and MTU, then given its addresses, set up, and given one default route per gateway. A refused bridge set or link changes nothing: the previous bridge set stays in place, and a link that fails part way is deleted. When the plugin's process ends, the bridges and links it declared are withdrawn and their devices deleted.

FirewallTablesReplace also answers with the kernel's outcome: the tables are validated as an operator's firewall config is, registered under the plugin's name and reconciled with every other owner's tables, the operator's included, before the call returns. The answer names the kernel tables the plugin now contributes. A refused set changes nothing, because the previous set is registered and reconciled again. A config commit leaves contributed tables in place, the tables of a plugin process that ended are withdrawn, and the firewall's orderly stop removes them with every other Ze table (docs/architecture/api/process-protocol.md, "Owned interface devices and firewall table contribution").

Error Handling

Stage errors: If any stage RPC fails (error response or timeout), the SDK returns an error from Run() with context like "stage 1 (declare-registration): ...".

Runtime errors: Callback handlers return errors via #<id> error {"code":"...","message":"..."}. Unknown methods are rejected with "unknown method: <method>".

Connection errors: EOF or closed connection during the event loop is treated as clean shutdown (engine closes socket to signal exit).

Config reload errors: config-verify and config-apply return structured results with {"status":"ok"} or {"status":"error","error":"..."}. A plugin with no OnConfigVerify handler accepts at config-verify. A plugin that registered neither OnConfigApply nor DeclareAppliesNothing answers both with an error naming the plugin and the roots, so the reload is refused rather than accepted and ignored (handlers.md, "A plugin with no apply handler").

Batched Event Delivery

Events are batched for efficiency. The engine collects pending events from a per-process channel, JSON-quotes each one, and sends them in a single deliver-batch RPC.

#42 ze-plugin-callback:deliver-batch {"events":["<json-event-1>","<json-event-2>",...]}
#42 ok

The SDK unpacks the batch and dispatches each event to the OnEvent handler individually. Both deliver-event and deliver-batch handlers are registered in the callback map when OnEvent is called.

For internal plugins with an active DirectBridge, event delivery bypasses the callback channel entirely: bridge.DeliverEvents(events) calls the onEvent handler directly (hot path). The callback channel is only used for non-event callbacks (execute-command, config-verify, etc.) and bye.

Original accepted redistribution records

OnOriginAdmissionLookup registers a read-only handler before Run. Stage 1 derives its support bit. The callback works through the typed bridge and the same framed public RPC, independently of an ordinary command that awaits it.

Answer only from the original published accepted record. Echo the requested ID, canonical family and prefix, concrete peer and owner, and operation. Missing or stale records return an error. A retiring record answers only its exact withdrawal. Explicit peer scope, BGP class and distance presence prevent missing values from acquiring a different meaning.

The original source metric differs from optional transformed wire MED. Zero distance and initial rule generation are valid explicit facts. Transfer output ownership to the SDK, including communities. The handler MUST honor its context, perform no engine call or I/O, and read no election state under a blocking lock.

A read deadline ends work, not the healthy connection. The SDK sends a refusal within a fresh bounded process budget. Stop still cancels replies, and a real writer failure still closes the connection. A snapshot permits at most 65535 communities, as declared by both Go validation and YANG.

A successful lookup grants no origination or send authority. The engine caller keeps the original process connection and separately verifies publisher, accepted lifetime, actual grants and route build. The complete value contract is in the process protocol.

Scoped origin intake

OnOriginIntake registers an optional mutation handler for a deciding plugin before Run. Each call carries owned original local-build data and an engine-issued receipt for one concrete peer.

An accepted loser returns the full update-route result with an explicit retained receipt and zero Announced. A missing result or bare zero is not acceptance. A removal returns its completed command count.

The handler MUST serialize exact source/key/scope mutations and refuse older generations. It MUST honor cancellation and join every mutation and writer barrier before it returns. The SDK provides a separate bounded worker. CurrentSelection remains read-only and can run during engine calls from intake.

The callback has both a typed slot and the same framed public RPC. Cancellation joins the handler and response attempt before settlement. The complete value, authority boundaries and activation dependencies are documented in the process protocol.

The original source-context belongs to the engine. A reader decodes original AS-path bytes only when as-path-known is true and uses as-path-asn4 for their width. A reader keeps bytes with unknown encoding opaque.

If a configured owner has not completed registration and startup, the engine refuses origination. A known live legacy owner keeps direct origination, as does a peer without an ordinary deciding owner.

The selected-origin writer reconstructs the issued build and uses the existing export and socket writer.

No in-tree provider currently enables this optional callback. Runtime activation still requires the origin domain and its lifecycle barriers, plus a RIB candidate provider. Configured and redistributed producers must preserve their original source provenance before Ze can advertise origin arbitration.
