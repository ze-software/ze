## Description

FIB pipeline: protocol RIB best-path tracking, system RIB selection by admin distance, recursive next-hop resolution (max depth 8, IGP metric accumulation, cascade on NH change), ECMP grouping (equal-cost paths collected into nexthop groups, max 128 members), rich route programming (route type blackhole/unreachable/prohibit, metric, VRF table ID, MPLS labels, SRv6 SID), kernel backend via netlink multipath with route type/metric/table/MPLS-lwtunnel/SRv6-seg6 support, VPP backend via GoVPP with multi-path/route-type/metric/table support, per-producer netlink protocol ownership, crash recovery via stale-mark-sweep, external change monitoring. Selection and programming are separate stages: the system RIB picks one winner for each prefix, then decides whether to program it. `rib { fib-withhold }` naming the winner's protocol is one of the reasons the write is declined, and the Per-protocol FIB withholding row states what withholding leaves intact. The forwarding action (`unicast`, `blackhole`, `unreachable`, `prohibit`) rides one route from the protocol RIB through sysrib into the FIB backend. It is deliberately NOT part of arbitration: selection stays on priority and then protocol name, so a discard route never beats a forwarding one on the strength of being a discard. It IS part of the change comparison, because a prefix that turns into a discard with every other field unchanged must still reach the kernel. A prefix and a PATH own different fields, and the split is at the type rather than at each call site: the label stack and the SRv6 SID belong to the forwarding path, so an equal-cost member promoted over an unreachable winner is programmed with its own, while the protocol, the route type, the metric and the fast-reroute alternate belong to the prefix and come from the winner whichever member takes it. Whether ze holds an install is the PRESENCE of the prefix in its installed map, never the validity of the address there, because a member named by a device alone resolves to an invalid address. The install also records the PROOF it was made under: a next-hop inside a connected covering route resolves to itself, so the address cannot say which rule programmed it, and a cascade that finds a once-proved path now unproved is the one case that withdraws. `show rib` reports it as `route-type`, omitted for an ordinary route, and a Linux discard route names no next-hop, device, multipath or encap. <!-- source: internal/component/sysrib/sysrib.go -- routeType field, recomputeBest, recordOSInstalledWinner, fibEntry, fibInstall, installedPath --> CLI: `show nexthop-table`, `show ecmp-groups`.
