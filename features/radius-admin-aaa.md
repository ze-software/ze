## Description

RFC 2865 RADIUS authentication for operator/admin login (SSH, web, MCP), distinct from the L2TP subscriber RADIUS path. PAP (User-Password hidden per §5.2), CHAP (CHAP-Password §5.3 with a 16-octet CHAP-Challenge §5.40, both generated per login from `crypto/rand`), or EAP with MD5-Challenge or MS-CHAPv2 carried in EAP-Message attributes (RFC 3579 §3.1), selected by the `auth-method` leaf and defaulting to `pap`; RFC 2865 §4.1 and RFC 3579 §3.3 Note 1 permit one credential type and never two, so exactly one is sent and the socket refuses a request carrying two, and §2.2 makes `chap` and `eap-md5` usable only against a server holding the password in cleartext while `eap-mschapv2` needs the NT hash. Ordered server failover with per-server timeout and retries, Access-Accept reply-attribute-to-profile mapping (configurable, default Filter-Id §5.11, or Class §5.25) with a default-profile fallback, an Accept resolving to no profile rejected rather than authorized (an authenticated login always names at least one profile), and explicit-reject vs unreachable distinction so a wrong-password Access-Reject does NOT fall through to local bcrypt while an unreachable server does. Runs as a pluggable `aaa.Authenticator` at chain priority 50 (ahead of TACACS+ 100 and local 200); local bcrypt remains the fallback. `ze doctor` probes reachability (`doctor-radius-admin-unreachable`). Reuses the L2TP RADIUS client, so retransmit, failover, and Response-Authenticator verification behave identically. For the two EAP methods ze is the EAP PEER itself, answering with the password the operator typed rather than relaying frames, so no login transport changes: it splits one EAP packet across consecutive EAP-Message attributes at 253 octets, signs every EAP-bearing Access-Request with the RFC 3579 §3.2 HMAC-MD5, silently DISCARDS a reply whose Message-Authenticator does not verify so a forged packet cannot stop the AAA chain, and answers each Access-Challenge with the State attribute copied byte for byte and never read (RFC 2865 §5.24). The conversation is bounded by the peer's 20-round cap and the login time budget, neither of which a server can raise. EAP-TLS is implemented in the peer and not offered here: it needs an operator certificate and key.
