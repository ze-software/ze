Update report · 15 days

2026-11-09 – 2026-11-23 (15 days)

This update covers two weeks, and several BGP defaults changed to follow the RFCs, so please read the changes below before upgrading.

The work left is kept as a list of items, each either required before the first release or planned for after it. 307 items are now required, up from 298, and 373 are planned for later, up from 348. 49 required items were added, 39 left the list and one moved to the later list. The numbers compare both ends of the period, so an item added and completed in between is not counted, and they count work items, not how close the release is: https://ze-software.net/project/roadmap/

⚠️ Changes to check: BGP

  • RPKI: an Invalid route is no longer dropped unless asked for (RFC 6811 Section 2). For the old behaviour, add bgp { rpki { action { invalid reject; } } }.
  • next-hop auto, the default, now sets Ze as next hop on routes sent to an eBGP peer (RFC 4271 Section 5.1.3). Route server clients and iBGP keep the received next hop, as does next-hop unchanged;.
  • A route whose next hop can not be resolved is no longer selected (RFC 4271 Section 9.1.2). show bgp rib marks it next-hop-unresolvable.
  • Graceful restart is now written graceful-restart { short-lived { restart-time; family ...; } long-lived { family ... { stale-time; } } }, and the old leaves are refused. A bare graceful-restart { } now only helps restarting peers (RFC 4724 Section 3), short-lived { } restores the 120 second restart.
  • The Origin Validation State community is removed from routes received over eBGP (RFC 8097 Section 2), unless the peer sets session { accept-origin-validation-state true; }.

⚠️ More changes to check

  • Ze no longer rewrites a config written in its own older syntax, at start or with ze config migrate, so such a config is refused and should be edited by hand. ExaBGP configs still convert with ze exabgp migrate.
  • The 12 October update said an IPsec config without an unmatched line was rewritten to vpn ipsec unmatched bypass. It now gets the default discard, which drops clear-text management traffic, so add the line before upgrading.
  • gNMI on a non-loopback address now needs a token and TLS, and without a token it is read-only. MCP on a non-loopback address needs TLS.
  • IKEv2 refuses a certificate issued without the IPsec IKE purpose, such as a Let's Encrypt one (RFC 4945 Section 5.1.3.12). It should be reissued.
  • IRR settings moved to system irr { server; refresh-interval; }, and the fetched lists now survive a restart.
  • Refused at commit: a firewall prefix with host bits set (10.10.10.1/30), a tunnel whose remote is 0.0.0.0 or ::, and an interface named by a mirror, bridge, tunnel or PPPoE which is not declared.
  • show bgp gives the peer group under a new group key, description is the peer's own. RIB words such as received and count are now pipes: show bgp rib | received | count. ze config validate shows each refusal with its fix before moving to the new build.

🔒 Security

  • SSH config editor: a user whose system authorization profile denied editing could still set and commit. Each change is now checked. Routers without authorization profiles were not exposed.
  • Appliance web UI: any logged-in account, read-only ones included, could install software or reboot through the /gokrazy/ page. Linux installs were not exposed.
  • MCP: the scope of a bearer-list identity was not enforced, so a read-only identity could run write tools.
  • IPsec: a gateway forwarding for protected hosts sent their traffic from ports 500 and 4500 in clear text (RFC 4301 Section 5.2). Hosts protecting only their own traffic were not exposed.
  • IKEv2: a revoked certificate was accepted, now each pki ca crl is checked. The 7 September update said revocation was checked, which held for EAP-TLS only.
  • IKEv2: a forged message during the handshake could end it (RFC 7296 Section 2.21.2). Established SAs were not exposed.
  • IPsec on VPP installed inbound bypass and discard entries backwards. The kernel backend was not exposed.
  • Fleet: a hub accepted a device claiming an unknown name with an empty token.

📡 Access

  • New: the PPPoE access concentrator runs on VPP, with interface backend vpp. It was tested with pppd, 100 subscribers, a VLAN and RADIUS framed routes, but subscribers on VPP are not rate limited yet.
  • New: clear l2tp session user <name> and clear l2tp session address <ipv4>.
  • Fixed: the 11 May update said RADIUS framed routes are announced in BGP. They were, but no route was installed through the session, so their traffic was dropped.
  • Fixed: WireGuard peers no longer lose their session when Ze restarts.

🛰️ Routing

  • New: BGP aggregation with bgp { aggregate <prefix> { ... } } (RFC 4271 Section 9.2.2.2), not yet tested against another implementation.
  • New: after a restart, route selection waits for End-of-RIB from restarting peers (RFC 4724 Section 4.1).
  • Fixed: the 5 January update said Enhanced Route Refresh was supported, but the markers received were ignored (RFC 7313 Section 4).
  • Fixed: a peer which stops reading no longer holds its session for ever (ze.fwd.write.deadline, 30 seconds).

📚 Closing the RFC gap

Each MUST in the RFCs Ze implements gets a test. When the test is written, the code behind it is broken on purpose to see the test fail, and that check is repeated only when the test itself changes.

  • 53.6% of all the MUSTs have a test checked this way (2,779 of 5,188). This counts every MUST of every RFC Ze implements, including the 1,539 for parts of an RFC Ze does not build today, which need no test until they are built.
  • 76% of the MUSTs for what Ze builds have a test checked this way. This leaves those 1,539 out, so it shows how well the features Ze ships are tested.

The second figure is new. The MUSTs without such a test are now split more precisely, between those the operating system meets for Ze, those with a test still to be checked, and those for parts Ze does not build. The split changes none of the counts of tested MUSTs.

Most of this period's new tests are for IKEv2 (RFC 7296), followed by BGP (RFC 4271 and RFC 7606): https://ze-software.net/quality/rfc-compliance/
