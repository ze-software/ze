# RFC 5216 corrections

Why a requirement row of `rfc/short/rfc5216.md` changed level, text, or citation.
The summary is the working document; this file is the record the level
ratchet reads (`checkLevelRatchet`, `internal/le/rfc/check_ratchets.go`).

Correction 2026-09-21: `RFC5216-5.3-1` was published [MUST]. Section 5.3, Certificate
Validation, states both sides at SHOULD. The server "SHOULD support validating the peer
certificate using RFC 3280" compliant path validation, and "The EAP-TLS peer SHOULD
support validating the server certificate using RFC 3280" compliant path validation. The
row is corrected to [SHOULD].

Correction 2026-09-30: `RFC5216-5.3-1` quoted the whole first paragraph pair of Section
5.3 and so carried three obligations, one of which ze does not meet. It is split on the
main thread's ruling R3. `RFC5216-5.3-1` keeps the server's path validation, "Since the
EAP-TLS server is typically connected to the Internet, it SHOULD support validating the
peer certificate using RFC 3280 [RFC3280] compliant path validation", with its
authenticator-side tests. `RFC5216-5.3-4` takes "Therefore, the EAP-TLS server SHOULD
provide its entire certificate chain minus the root to facilitate certificate validation
by the peer. The EAP-TLS peer SHOULD support validating the server certificate using RFC
3280 [RFC3280] compliant path validation.", with the server-chain and peer-validation
tests moved to it. `RFC5216-5.3-5` is a gap row for the clause ze does not implement,
"including the ability to retrieve intermediate certificates that may be necessary to
validate the peer certificate": ze fetches no intermediate and relies on the peer's
certificate message, the fallback the same section names. The sentences between them
("For details, see ..." and "Where the EAP-TLS server is unable to retrieve ...") state
no obligation and leave the rows.
