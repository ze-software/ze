# RFC 2545 correction records

Correction 2026-10-01: `RFC2545-3-6` is a new row, split from `RFC2545-3-3` under main-thread rulings R3, R55(a) and R56. §3 reads "The link-local address shall be included in the Next Hop field if and only if the BGP speaker shares a common subnet with the entity identified by the global IPv6 address carried in the Network Address of Next Hop field and the peer the route is being advertised to." The address to include is, per the sentence before it, "the link-local IPv6 address of the next hop". When that next hop is another router on the shared subnet, Ze cannot meet the include half: it learns no other router's Link-Local, and until this date it wrote its OWN Link-Local there, pairing another router's global with the speaker's address. Ze now sends that global alone, so the third-party include half is a {gap} row of its own, quoting the same sentence because the clause and the sentence coincide. `RFC2545-3-3` keeps its tests for the include half on the speaker's own global and for the exclude half.

Correction 2026-10-01: the `RFC2545-3-6` {gap} annotation and the Support remaining row said Ze "learns no other router's Link-Local" and sends a third-party global alone, which reads as every rail. That overreaches (main-thread ruling R58(b), from the BGP c19 judge). The gap covers only the rails where Ze WRITES the next hop: an explicit `session next-hop`, and a static or API route naming another router. On the relay rail with next hop unchanged or auto, `precomputeNextHop` (`internal/component/bgp/reactor/peer_forward_facts.go`) arms no next-hop edit (`nhModeNone`), so a received 32-octet field passes as received and carries the third party's own Link-Local. Both texts now name the rails the gap covers and the relay case it does not. The row's quote and level are unchanged.

Correction 2026-10-01: the relay sentence of the `RFC2545-3-6` annotation and of the Support remaining row ("passes as received") became incomplete when BGP continuation 21 fixed a defect against draft-ietf-idr-linklocal-capability Section 4 ("Link-Local IPv6 next hops MUST NOT be included" toward a multihop external peer). `egressNextHopGlobalHalf` (`internal/component/bgp/reactor/forward_next_hop.go`) now removes the Link-Local half of a relayed 32-octet field toward a peer no connected subnet holds, which is also the exclude half of this §3 sentence. Both texts now say the field passes as received to a peer the speaker shares a subnet with and loses its Link-Local otherwise. The row's quote, level and gap are unchanged.
