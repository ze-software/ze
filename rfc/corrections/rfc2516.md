# RFC 2516 corrections

Why a requirement row of `rfc/short/rfc2516.md` changed level, text, or citation.
The summary is the working document; this file is the record the level
ratchet reads (`checkLevelRatchet`, `internal/le/rfc/check_ratchets.go`).

Correction 2026-09-21: `RFC2516-7-1` was extracted as "AC MUST verify SESSION_ID + source
MAC pair on every Session and PADT packet", cited "(Security, §7)". Section 7 is LCP
Considerations and states no such rule; Section 9, Security Considerations, states only
the AC-Cookie and Service-Name advice. The document does state the obligation this row
carries, in two places. Section 4, of the SESSION_ID field: "The value is fixed for a
given PPP session and, in fact, defines a PPP session along with the Ethernet SOURCE_ADDR
and DESTINATION_ADDR." Section 6: "The SESSION_ID MUST NOT change for that PPPoE session
and MUST be the value assigned in the Discovery stage." Same requirement id, same MUST
level, corrected text, and the tests bound to it in
internal/component/l2tp/pppoe/rfc2516_server_test.go prove exactly that pairing. The id keeps its
Section 7 anchor, because an id is permanent and is parsed from the section its line
cites.

Retired 2026-09-26: `RFC2516-x-3` said packets with VER or TYPE other than 0x1 MUST be
silently discarded. Read §4, §5, §8 and the whole text, Appendices A and B included: the
document says only that VER and TYPE "MUST be set to 0x1", which binds the sender and is
carried by RFC2516-x-1 and RFC2516-x-2; no sentence states a receive-side discard, and
no other PPPoE document in `rfc/short/` states it. Both of its tags, in
internal/component/l2tp/pppoe/rfc2516_discovery_test.go, were deleted: the negative unit already
carries the RFC2516-x-1 negative tag, and the positive unit carries the RFC2516-x-7
positive tag.

Retired 2026-09-26: `RFC2516-5.2-3` said a PADO MUST echo Host-Uniq when the PADI carried
it. Read §5.2, §5.1 and the whole text: the only sentence that states it is the Host-Uniq
paragraph of Appendix A, which RFC2516-5.2-1 quotes and which covers both the PADO and
the PADS, so the row was a duplicate. Its two tags in
internal/component/l2tp/pppoe/rfc2516_discovery_test.go were deleted, because each tagged unit
already carries the RFC2516-5.2-1 tag of the same polarity.

Retired 2026-09-26: `RFC2516-5.3-3` said a PADR MUST echo AC-Cookie when the PADO carried
it. Read §5.3, §9 and the whole text: the only sentence that states it is the AC-Cookie
paragraph of Appendix A, which RFC2516-5.3-1 quotes, so the row was a duplicate. Its two
tags in internal/component/l2tp/pppoe/rfc2516_discovery_test.go were deleted, because each tagged
unit already carries the RFC2516-5.3-1 tag of the same polarity.

Retired 2026-09-26: `RFC2516-5.3-4` said a PADR MUST echo the Host-Uniq the Host used in
its PADI. Read §5.1, §5.3 and the whole text: Appendix A says only that the Host "MAY
include a Host-Uniq TAG in a PADI or PADR", which RFC2516-5.1-3 quotes; no sentence
obliges the Host to repeat it in the PADR. Its two tags in
internal/component/l2tp/pppoe/rfc2516_discovery_test.go were deleted; the tagged units still carry
the RFC2516-5.3-1 and RFC2516-5.3-2 tags.

Retired 2026-09-26: `RFC2516-5.5-2` said a PADT MAY contain a Generic-Error tag. Read §5.5
and the whole text: §5.5 says "No TAGs are required", and Appendix A says a Generic-Error
tag "can be added to PADO, PADR or PADS packets", naming no PADT. No test tagged the row.
