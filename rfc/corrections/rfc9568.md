# RFC 9568 corrections

Correction 2026-09-29: `RFC9568-7.2-1` quoted two operations of the §7.2 transmit
list, "Fill in the VRRP packet fields with the appropriate Virtual Router
configuration state" and "Compute the VRRP checksum", and ze meets only the first
for IPv4. The row is split on the main thread's ruling (R17): -1 keeps the lead-in
and the field-fill operation with its tests, and "Compute the VRRP checksum" is now
`RFC9568-7.2-5`, a gap row. For VRRPv3 over IPv4 ze transmits the RFC 5798
pseudo-header checksum rather than the message-only checksum §5.2.8 defines,
because keepalived and the deployed base require that form. The deviation is
disclosed on the Support row and in docs/architecture/vrrp/vrrp-first-hop-redundancy.md.
Same level for both rows.

Correction 2026-09-29: `RFC9568-5.2.8-1` quotes "It MUST verify the VRRP checksum."
(§7.1), and ze verifies it for both address families. What ze does not hold to is
the §5.2.8 definition of the IPv4 checksum, "For the IPv4 address family, the
checksum calculation only includes the VRRP message starting with the Version field
and ending after the last IPv4 address (refer to Section 5.2).", because the receiver
also accepts the RFC 5798 pseudo-header form. On the main thread's ruling (R18) that
sentence is now its own row, `RFC9568-5.2.8-2`, a gap row naming the same disclosed
interop deviation on transmit and receive, and -1 keeps its tests.

Correction 2026-09-30: `RFC9568-8.1.2-6` is a new row. `RFC9568-6.4.3-1` cites §8.1.2
but quotes only the §6.4.3 bullet, so the §8.1.2 sentence "the Active Router MUST
respond to the ARP request with an ARP response that indicates the Virtual Router MAC
address for the Virtual Router" was dropped: what the answer must carry, beyond
answering at all. Extraction site 8.1.2:1, which was excluded as a duplicate of
6.4.3-1, now maps to the new row, and the two wire tests that capture the ARP reply
(non-owner and owner) carry its tags in both polarities.

Correction 2026-09-30: `RFC9568-8.2.2-8` is a new row, for the same reason on IPv6.
`RFC9568-6.4.3-3` cites §8.2.2 but quotes the §6.4.3 bullet with the Router flag, and
the §8.2.2 sentence "the Active Router MUST respond to the ND Neighbor Solicitation
message with the Virtual Router MAC address for the Virtual Router" names no flag.
Site 8.2.2:1 now maps to the new row. Ze meets it, proven on the wire for a non-owner
and an owner Active router; 6.4.3-3 keeps its gap, which is about the Router flag only.

Correction 2026-09-30: `RFC9568-5.2.8-3` is a new row. The R18 split of 5.2.8-1 left the
§5.2.8 IPv6 sentence "For the IPv6 address family, the checksum calculation also
includes a prepended "pseudo-header", as defined in Section 8.1 of [RFC8200]." with no
row. It carries no BCP 14 keyword and defines the checksum, so it is gated at MUST under
D-3, as 5.2.8-2 is, and it is an unsourced id of §5.2.8. The receive half is proven by a
new test that computes both sums independently: the pseudo-header sum is accepted and a
message-only sum is refused. On transmit, ze asks the kernel to fill the IPv6 checksum
(IPV6_CHECKSUM at offset 6, internal/plugins/vrrp/transport/backend_linux.go), and the
tags on this row do not claim that half.
