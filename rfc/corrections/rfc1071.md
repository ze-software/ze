# RFC 1071 corrections

Retired 2026-09-27: `RFC1071-x-1` states no obligation RFC 1071 carries. It said the
OSPF packet checksum is computed over the whole packet excluding the 64-bit
Authentication field, citing RFC 2328 §A.3.1. Read §1, the indented Section 2 text the
heading detector folds into §1, §3, §4 and its subsections, and the IEN-45 appendix:
RFC 1071 never mentions OSPF or an authentication field, and says only which octets a
checksum covers in general. RFC 2328 §A.3.1 states the obligation, and its row
RFC2328-A.3.1-2 already quotes it. Its positive tag on
`TestOSPFPacketChecksumExcludesAuth` (`internal/plugins/ospf/packet/checksum_test.go`)
was deleted, because the same unit already carries an RFC2328-A.3.1-2 positive tag
stating both mutations the RFC1071 tag claimed. Its negative tag on the same unit was
deleted for the same reason: that RFC2328-A.3.1-2 tag names the covered-octet mutation
too, and RFC2328-A.3.1-2 holds its own negative on `TestPacketVerifyChecksum`
(`internal/plugins/ospf/packet/header_test.go`). The half of the row saying the
Checksum field is zeroed during computation is RFC 1071 §1 item (2), which
RFC1071-1-1 quotes.

Retired 2026-09-27: `RFC1071-x-2` states an obligation RFC 1071 does not carry. Read §1, §2, §3 and §4, then the whole text: RFC 1071 computes the Internet checksum and says nothing of OSPF authentication types. RFC 2328 §D.4.3 step (2) states it: "The checksum field in the standard OSPF header is not calculated, but is instead set to 0." Under owner decision D-10 that is now row RFC2328-D.4.3-1 of rfc/short/rfc2328.md, and the one tag, on TestOSPFPacketChecksumZeroForAuType2 in internal/plugins/ospf/packet/checksum_test.go, moved to it.
