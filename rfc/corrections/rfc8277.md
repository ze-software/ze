# rfc8277 correction records

Correction 2026-10-02: `RFC8277-2.2-1`, `RFC8277-2.3-1` and `RFC8277-2.3-2` drop their `{single-polarity: positive}` markers. The markers said no transmission input could carry a wrong S bit, but LabeledUnicast.WriteTo takes label stack ENTRIES, the form a relayed stack arrives in, and nlri.WriteLabelStack rewrites their S bit rather than copying it: §2.2 reads "S: This 1-bit field MUST be set to one on transmission", and §2.3 reads "In all labels except the last (i.e., in all labels except the one immediately preceding the prefix), the S bit MUST be 0." TestRFC8277RelayedStackSBitRewritten (internal/component/bgp/plugins/nlri/labeled/rfc8277_sbit_relay_test.go) hands it entries with the S bit wrong and asserts the octets transmitted, so each row now carries a negative. The second transmitter, nlri.WriteLabelValues through UpdateBuilder.BuildLabeledUnicastNLRIBytes and buildVPNNLRIBytes, is proven by TestRFC8277BuilderLabelLayout (internal/component/bgp/message/rfc8277_label_layout_test.go). Quote, id and level unchanged.

Correction 2026-10-02: the `{single-polarity: positive}` reason of `RFC8277-2-2` named LabeledUnicast.WriteTo as the only transmitter. Two more write the label field: UpdateBuilder.BuildLabeledUnicastNLRIBytes and buildVPNNLRIBytes, both through nlri.WriteLabelValues. The reason now names all three; §2 reads "when advertising the binding of a single label to a prefix, the BGP speaker MUST use the encoding specified in Section 2.2", and each of the three emits that layout for any one-label input. Quote, id and level unchanged.

Correction 2026-10-06: `RFC8277-2.2-3` and `RFC8277-2.2-4` retain their ids and §2.2 quotes. §2.3 repeats the same Rsrv sentence verbatim for every entry of the multi-label encoding: "This 3-bit field SHOULD be set to zero on transmission and MUST be ignored on reception." This is the same field operation over every stack entry, not a new per-occurrence requirement. `TestRFC8277RsrvIgnoredOnReceiveLabelStack` in `internal/core/bgp/nlri/nlrisplit/rfc8277_rsrv_stack_test.go` already tags `RFC8277-2.2-3` in both polarities and checks three labels, the prefix and two-NLRI framing with every Rsrv field zero or set. `TestRFC8277BuilderLabelLayout` in `internal/component/bgp/message/rfc8277_label_layout_test.go` observes zero Rsrv in originated labeled-unicast and VPN stacks. `TestRFC8277RsrvClearedOnRelay` and `TestRFC8277ZeroRsrvRelayedZeroCopy` in `internal/component/bgp/reactor/rfc8277_label_rsrv_test.go` check multi-label relay with nonzero and zero Rsrv fields; `TestRFC8277RsrvClearedOnTheReceivePath` confirms the ingest call. `ExtractLabels` ignores those three bits, `SplitLabeled` uses only S for stack termination, `WriteLabelValues` originates zero bits, and `publishBase` applies `clearLabelRsrv` before relay. The transmission clause of the advisory row `RFC8277-2.2-4` is already included in the full sentence of `RFC8277-2.2-3`; no additional §2.3 id or tag is required. This records the actual multi-label evidence without changing any existing row, tag or verdict, and makes no claim that Multiple Labels Capability negotiation is implemented.

Correction 2026-10-06: `RFC8277-3.2.1-4` remains the unchanged-next-hop withdrawal requirement in §3.2.1. §3.2.2 separately states, after the choice not to propagate a locally selected label stack that a peer cannot handle: "In that case, if a previous route with the same AFI, SAFI, and prefix (but with fewer labels) has already been propagated to that peer, that route MUST be withdrawn from that peer using the procedure of Section 2.4." New row `RFC8277-3.2.2-3` preserves that changed-next-hop branch and its preceding decision sentence. The common withdrawal action does not prove a distinct label-replacement/recipient-count trigger. `mpReachNextHopHandler` in `internal/component/bgp/reactor/filter_delta_handlers.go` changes the next hop while retaining the NLRI, and `BuildLabeledUnicastNLRIBytes` in `internal/component/bgp/message/update_build_labeled.go` encodes the supplied stack; neither supplies that decision or withdrawal. The new row records the missing behavior as a gap beside the existing §3.2.1 gap, rather than retiring the obligation or claiming vacuous conformance. The extraction site `3.2.2:3` now maps to the new row instead of describing a duplicate covered by a row that cites only §3.2.1. No existing tag or verdict is removed, and no absent feature is implemented by this correction.
