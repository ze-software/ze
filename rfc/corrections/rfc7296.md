# RFC 7296 corrections

Why a requirement row of `rfc/short/rfc7296.md` changed level, text, or citation.
The summary is the working document; this file is the record the level
ratchet reads (`checkLevelRatchet`, `internal/le/rfc/check_ratchets.go`).

Correction 2026-08-15: `RFC7296-2.8-1` was extracted at MUST strength. §2.8.1 states the
collision rule as a recommendation: the redundant SA "SHOULD be closed by the endpoint that
created it". Same requirement id, corrected text and level. §2.8.1 defines "lowest" in the
same paragraph, and the definition is part of the rule: an octet-by-octet comparison, "start
by comparing the first octet; if they're equal, move to the next octet, and so on. If you
reach the end of one nonce, that nonce is the lower one."

Correction 2026-08-15: `RFC7296-1.7-2` cited §1.7 and §2.13. Only §1.7 carries the sentence:
"This document adds the restriction in Section 2.13 that all pseudorandom functions (PRFs)
used with IKEv2 MUST take variable-sized keys." §2.13 states the same property as an
assumption, "It is assumed that PRFs accept keys of any length, but have a preferred key
size". §2.13 does carry MUSTs of its own, each already extracted as `RFC7296-2.13-1` to
`RFC7296-2.13-4`, but none of them is this obligation. `RFC7296-2.13-1`'s "a fixed key size
MUST be specified" sits in the paragraph opening "We assume that each encryption algorithm
and integrity protection algorithm uses a fixed-size key", so it governs those algorithms
rather than the PRF's acceptance of variable-sized keys. The citation now names §1.7 alone.

Retired 2026-09-27: `RFC7296-2.1-1` states an obligation RFC 7296 does not carry. Read §2.1 and the whole text: RFC 7296 predates IKE fragmentation and never mentions it. RFC 7383 §2.4 states it: "that peer SHOULD use IKE fragmentation." RFC 7383 has no summary in rfc/short, so under owner decision D-10 the row is retired, and a journal row asks for it to be enrolled. The row carried no tag.

Retired 2026-09-27: `RFC7296-3.8-1` states an obligation RFC 7296 does not carry. Read §3.8 and the whole text: RFC 7296 lists authentication methods 1, 2 and 3 and predates the Digital Signature method. RFC 8247 §3.1 grades method 14, Digital Signature, at SHOULD in its table, and says "Digital Signature [RFC7427] is expected to be promoted". RFC 8247 has no summary in rfc/short, so under owner decision D-10 the row is retired, and a journal row asks for it to be enrolled. The row carried no tag.

Retired 2026-09-29: `RFC7296-3.3.6-1` duplicated `RFC7296-3.3.2-1`. Read §3.3.3 and §3.3.6: both rows quoted the same §3.3.3 span, "A compliant implementation MUST understand all mandatory and optional types for each protocol it supports", through the IKE line of the mandatory Transform Type table, and §3.3.6 states no obligation of its own on the D-H transform. The row is merged into `RFC7296-3.3.2-1`, which keeps its text and level. Its two tags, on TestResponderRequiresKEForDH in internal/component/ike/engine/rfc7296_test.go, moved to `RFC7296-3.3.2-1`.

Correction 2026-09-30: `RFC7296-3.5-5` quoted one span that ran from the ID_FQDN terminator ban across the ID_FQDN character-set sentence and into the next item of the §3.5 ID Type list, ID_RFC822_ADDR. Read §3.5: "All characters in the ID_FQDN are ASCII" carries no BCP 14 keyword, and the list gives each ID type its own entry with its own ban, "The string MUST NOT contain any terminators (e.g., NULL, CR, etc.)." for ID_FQDN and "The string MUST NOT contain any terminators." for ID_RFC822_ADDR. The row now quotes the ID_FQDN entry through its ban, same id and level, and the ID_RFC822_ADDR entry through its ban is the new row `RFC7296-3.5-6`. The two units tagged `RFC7296-3.5-5` in internal/component/ike/engine/rfc7296_wp2_test.go carry both ids, each tag stating the cases that prove it.

Correction 2026-09-30: `RFC7296-3.11-2` quoted "It MUST be zero for IKE (SPI is in message header) or four for AH and ESP.", whose "It" named no field. Read §3.11: the sentence closes the SPI Size field entry, "SPI Size (1 octet) - Length in octets of the SPI as defined by the protocol ID." The span now starts at that field name, same id and level.

Correction 2026-09-30: `RFC7296-2.23-2` quoted "An IPsec endpoint that discovers a NAT between it and its correspondent (as described below) MUST send all subsequent traffic from port 4500", the same sentence `RFC7296-2.23-8` quotes and extraction site 2.23:2 maps to `RFC7296-2.23-8`. The extraction site mapped to `RFC7296-2.23-2`, site 2.23:5, is a different §2.23 sentence: "However, if a NAT is detected, both devices MUST use UDP encapsulation for ESP." Its two tagged units, TestChildSANATTEncapPorts and TestChildSANoNATNoEncap, assert ESP encapsulation with and without a detected NAT, which is that sentence. The row now quotes it, same id and level; the IKE float to port 4500 stays with `RFC7296-2.23-8` and its units in rfc7296_natt_test.go.

Correction 2026-09-30: `RFC7296-2.21.4-7` quoted two sentences of the last §2.21.4 paragraph that bind two different nodes: "A node receiving a suspicious message from an IP address (and port, if NAT traversal is used) with which it has an IKE SA SHOULD send an IKE Notify payload in an IKE INFORMATIONAL exchange over that SA." binds the node that saw the suspicious message, and "The recipient MUST NOT change the state of any SAs as a result, but may wish to audit the event to aid in diagnosing malfunctions." binds the peer that receives that protected Notify. Extraction site 2.21.4:5 maps the second. The row now quotes the second sentence, same id and level [MUST NOT], and keeps its tagged units, which assert that a protected INFORMATIONAL notify changes no SA state. The SHOULD send clause is the new row `RFC7296-2.21.4-8` [SHOULD], recorded as a {gap}: no path in Ze sends a protected Notify over an existing IKE SA in answer to a suspicious message.

Retired 2026-09-30: `RFC7296-2.13-2` binds the specification of a cryptographic transform, which Ze does not implement. Read §2.13: "For algorithms for which not all values are valid keys (such as DES or 3DES with key parity), the algorithm by which keys are derived from arbitrary values MUST be specified by the cryptographic transform." The subject is the transform's defining document, which must state a derivation, and no implementation fills that role. Ze also implements no transform the condition names: every cipher in encryptionRegistry (internal/component/ike/crypto/transform.go) is AES CBC, GCM or CCM, for which every value of the fixed size is a valid key. The row's two tags, on TestSKKeyLengthsComeFromTransforms in internal/component/ike/crypto/rfc7296_test.go, asserted SK_* key sizing, which is `RFC7296-2.13-3` and carried by the same unit's own tags, so they were dropped and that unit keeps its `RFC7296-2.13-3` tags.

Correction 2026-09-30: `RFC7296-2.5-7` quoted "their content MUST be ignored by an implementation running version 2.0", whose "their" named no field. Read §2.5: the sentence opens "Also, for forward compatibility, all fields marked RESERVED MUST be set to zero by an implementation running version 2.0, and their content MUST be ignored by an implementation running version 2.0". The span now starts at that opening, so the row names the RESERVED fields it binds, same id and level. The sending clause at the head of the span stays `RFC7296-2.5-6`'s obligation; this row keeps the receiving one, and its tagged units assert that.

Correction 2026-09-30: `RFC7296-2.10-2` quoted "MUST be at least 128 bits in size", a clause with no subject. Read §2.10: "Nonces used in IKEv2 MUST be randomly chosen, MUST be at least 128 bits in size, and MUST be at least half the key size of the negotiated pseudorandom function (PRF)." The span now starts at the sentence's subject and runs through this row's clause, "Nonces used in IKEv2 MUST be randomly chosen, MUST be at least 128 bits in size", same id and level. The randomness clause it passes through is not this row's obligation; the row's tagged units assert the 128-bit floor alone.
