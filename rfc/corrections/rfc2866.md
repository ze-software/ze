# RFC 2866 corrections

Why a requirement row of `rfc/short/rfc2866.md` changed level, text, or citation, or
was retired. The summary is the working document; this file is the record the
ratchets read (`checkLevelRatchet`, `checkRetiredRequirements`,
`internal/le/rfc/check_ratchets.go`).

Retired 2026-09-27: `RFC2866-3-1` said that accounting failures MUST NOT tear down user
sessions, cited to §3. Section 3 defines the packet format, the authenticators and the
attribute order, and says nothing about sessions. Read §2 (where the extraction walk had
already declared the row unsourced), §2.1, §3, §4.1, §4.2, §5, §5.1 to §5.13 and §7, then
the whole text: the only statement about a failure to record is the §2 rule that the
accounting server MUST NOT send an Accounting-Response, which binds the server, and no
sentence ties a user session's life to the accounting exchange. RFC 2865 and RFC 2869 carry
no such rule either. Its two tags, on TestRFC2866AcctFailureKeepsSession and
TestRFC2866SessionTeardownIndependentOfAccounting
(internal/component/l2tp/plugins/authradius/rfc2866_accounting_test.go), claimed only this
row and were deleted; the tests stay, and still prove that ze keeps a session whose
accounting fails.

Retired 2026-09-27: `RFC2866-x-2` states an obligation RFC 2866 does not carry. Read §4.1, §5.1 and the whole text: RFC 2866 names Interim-Update only as an Acct-Status-Type value and says nothing about where its interval comes from. RFC 2869 §2.1 states it: "It is also possible to statically configure an interim value on the NAS itself." Under owner decision D-10 that is now row RFC2869-2.1-3 of rfc/short/rfc2869.md. The row carried no tag.

Retired 2026-09-29: `RFC2866-4.2-1` binds the RADIUS accounting server, which Ze does not implement. It quoted §4.2, "The Response Authenticator field MUST contain the correct response for the pending Accounting-Request." Read §4.2 and the whole text: the field is written by the party that transmits the Accounting-Response, and the sentence before it says "the RADIUS accounting server MUST transmit a packet with the Code field set to 5 (Accounting-Response)". Ze is only the accounting client (radius/client.go). The client's side of the paragraph is "Invalid packets are silently discarded", which carries no keyword and no row. The two tags, on TestRFC2866AccountingResponseAuthenticatorAccepted and TestRFC2866AccountingResponseAuthenticatorForgeryDiscarded (internal/component/radius/rfc2866_packet_test.go), proved that client discard, not this obligation, so they were dropped under ruling R2. The tests stay.

Correction 2026-09-30: `RFC2866-5-1` quoted the tail of the §5.13 Table of Attributes, Note 1 and the whole legend as one row, so a single verdict stood for four legend lines, two of them obligations and two permissions, over rows it never named (ruling R5). Read §5.13 and its legend: "1 Exactly one instance of this attribute MUST be present." binds the table's two 1 rows, Acct-Status-Type and Acct-Session-Id; "0 This attribute MUST NOT be present" binds its five 0 rows, User-Password, CHAP-Password, Reply-Message, State and CHAP-Challenge; the 0+ and 0-1 lines are MAY permissions and oblige nothing; Note 1 is `RFC2866-4.1-3`. `RFC2866-5-1` now quotes the 1 line alone, keeps its level, citation and tags, and gains TestRFC2866EveryRecordCarriesOneOfEachOneMarkedAttribute and TestRFC2866ExclusionsCannotRemoveAOneMarkedAttribute (internal/component/l2tp/plugins/authradius/rfc2866_attribute_table_test.go). The 0 line is new row `RFC2866-5.13-1` at [MUST NOT], proven by TestRFC2866AccountingRequestOnTheWireCarriesNoZeroMarkedAttribute and TestRFC2866SubscriberTextNeverBecomesAZeroMarkedAttribute in the same file. It overlaps `RFC2866-4.1-2`, which names four of the five from §4.1, and adds CHAP-Challenge. Extraction site 5.13:2 stays mapped to `RFC2866-5-1`, and section 5.13 declares `RFC2866-5.13-1` in `unsourced-ids`, because the legend is one extraction site and a site maps to one row.
