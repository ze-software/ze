# RFC 8955 corrections

Why a requirement row of `rfc/short/rfc8955.md` changed level, text, or citation,
or was retired. The summary is the working document; this file is the record the
level ratchet and the retirement check read (`internal/le/rfc/check_ratchets.go`).

Retired 2026-10-02: `RFC8955-6-2` quotes an RFC 8955 sentence that RFC 9117, which
updates RFC 8955, replaces. Read §6 of RFC 8955, then RFC 9117 §4.2 and §7: §4.2
quotes this sentence ("Section 6 of [RFC8955] states:") and redefines it as a
comparison of the left-most AS of an eBGP Flow Specification route with the
left-most AS of the best-match unicast route, and §7 makes the original rule
optional again. Ze implements the replacement and deliberately accepts the route
server case the original sentence forbids, so no test could prove this row and
none should. Under owner decision D-10 the obligation lives where it is stated:
RFC 9117 is enrolled with row `RFC9117-4.2-1`, and the two tags on
TestFlowSpecAuthorizationFromReceivedUpdates moved there (D-15 approval
2026-10-02), with RFC 8955 extraction site 6:4 now excluded as cross-document.

Correction 2026-10-08: `RFC8955-4.2.2.5-1`, `RFC8955-4.2.2.6-1` and `RFC8955-4.2.2.10-1` separately record the §4.2.2.5, §4.2.2.6 and §4.2.2.10 sentences: "Type 5 component values SHOULD be encoded as 1- or 2-octet quantities (numeric_op len=00 or len=01).", "Type 6 component values SHOULD be encoded as 1- or 2-octet quantities (numeric_op len=00 or len=01)." and "Type 10 component values SHOULD be encoded as 1- or 2-octet quantities (numeric_op len=00 or len=01)." Keep the existing Type 4 identity. These are emission recommendations, not receiving MUSTs. Exact producer and recipient-wire assertions now cover each component's 0/255/256/65535 boundaries; observed width mutations distinguish four-octet emission from the recommended one/two octets. Choosing the shortest permitted width is Ze policy. Legal wider reception remains separate compatibility coverage, not negative emission evidence, so these unconditional emitters carry justified single-positive-polarity annotations. Independent judgments and native bindings are recorded in `rfc/audit/rfc8955.json` and `rfc/discrimination/rfc8955.json`. Unsupported firewall packet-length matching does not exclude encoding duties.

Correction 2026-10-08: `RFC8955-4.2.2.8-1` separately records §4.2.2.8: "Type 8 component values SHOULD be encoded as single octet (numeric_op len=00)." Keep the Type 7 row. Exact 0/255 emission and recipient-wire assertions now establish the single-octet recommendation, and an observed two-octet-emission mutation fails them. Legal wider reception remains an untagged compatibility control, not a receiving-width MUST. Registered text/config producers cover this criterion; the separate route-command grammar does not. Independent judgment and native bindings are recorded alongside the other emission rows. Unsupported firewall ICMP-code matching remains a separate limitation.

Correction 2026-10-08: `RFC8955-7.2-3` records §7.2: "A traffic-rate-packets of 0 should result in all traffic for the particular flow to be discarded." `RFC8955-7.1-4` retains its byte-rate quote with §7.1 alone; both existing §7.2 MUST sites retain their mappings. Subtype 0x800c is distinct from byte-rate subtype 0x8006 despite sharing the discard producer. `TestSelectedFlowSpecZeroPacketRateKernel` now observes real nftables target drops, exact counters, unaffected-flow and positive-rate controls, then reinstalls and observes zero-rate discard before proving withdrawal restores delivery. The runtime-kernel carrier passed without skipping; disabling packet-zero discard produced the intended target-packet leak. Independent judgment and native guest bindings are recorded. This proves direct selected-callback processing for local IPv4 input, not event-subscription delivery, VPN or transit-dataplane support; existing SAFI and predicate limitations remain.
