# RFC 8707 corrections

Why a requirement row of `rfc/short/rfc8707.md` changed level, text, or citation.
The summary is the working document; this file is the record the level
ratchet reads (`checkLevelRatchet`, `internal/le/rfc/check_ratchets.go`).

Correction 2026-09-21: `RFC8707-3-1` was published [MUST]. RFC 8707 states it once, in
section 2, at SHOULD: "The authorization server SHOULD audience-restrict issued access
tokens" to the resource(s) indicated by the resource parameter. The row is corrected to
[SHOULD]. The historical id remains stable; its source citation is Section 2,
not the section number embedded in that id.

Correction 2026-09-21: `RFC8707-3-2` was published [MUST]. RFC 8707 section 2.1 states
only a lowercase should, which section 1.1 excludes from RFC 2119 force: if the server
cannot parse the value(s) or does not consider them acceptable, "it should reject the
request with an error response using the error code" invalid_target. The row is corrected
to [SHOULD].

Correction 2026-09-21: `RFC8707-2-2` was published [MUST]. RFC 8707 section 2 states the
opposite strength for the query component: "It SHOULD NOT include a query component, but
it is recognized that there are cases that make a query component a useful and necessary
part of the resource parameter", such as scoping requests to an application. The row is
corrected to [SHOULD NOT].

Correction 2026-09-21: `RFC8707-5-1` and `RFC8707-5-2` were attributed to
RFC 8707 Section 5, but that section is IANA Considerations and contains no
resource-server JWT audience requirement. Their actual source is
[RFC 7519 Section 4.1.3](https://www.rfc-editor.org/rfc/rfc7519#section-4.1.3):
"Each principal intended to process the JWT MUST identify itself with a value
in the audience claim." It continues: "If the principal processing the claim
does not identify itself with a value in the \"aud\" claim when this claim is
present, then the JWT MUST be rejected." Array support follows its next
sentence: "In the general case, the \"aud\" value is an array of case-sensitive
strings, each containing a StringOrURI value."

The former "canonical URL" wording also contradicted
[RFC 7519 Section 2](https://www.rfc-editor.org/rfc/rfc7519#section-2):
"StringOrURI values are compared as case-sensitive strings with no
transformations or canonicalizations applied." The implementation and tests
now use exact identifier comparison. The two historical identifiers remain
stable, at MUST, with their true source stated in the checklist and extraction
record. No new RFC 7519 identifiers were invented, no audience requirement was
excluded, and the meaningful JWT/HTTP behavior tests remain.

Scope decision 2026-09-21: Thomas selected "Keep present OAuth roles":
MCP resource server and external-AS metadata consumer, without an authorization
server, protected-resource discovery client, response signing or signed metadata.
The role/feature annotations name the producing code and quote each antecedent.
They do not exempt the resource server from checking JWT audiences.
