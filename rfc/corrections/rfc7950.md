# RFC 7950 corrections

Retired 2026-09-27: `RFC7950-7.6.4-1` duplicates an obligation another row of this
summary already states. It cited §7.6.4 and claimed, as a SHOULD, that a leaf with a
default value that is not set uses its default. Read §7.6.4, then §7.6.1, §9.9 and §9.13,
and searched the whole text for every sentence on a default value: §7.6.4 says nothing
of when a default is used; §7.6.1 states it as a MUST, "o If no such ancestor exists
in the schema tree, the default value MUST be used.", with the two further cases and
"When the default value is in use, the server MUST operationally behave as if the
leaf was present in the data tree with the default value as its value." Row
RFC7950-7.6.1-1 quotes all of that, its extraction sites map to it, and
`internal/component/config/rfc7950_leaf_default_test.go` tags it in both
polarities. Kept as a second MUST row it could be backed by no extraction site, since
each site maps to one row. The row had no tags and no verdict, so nothing moved.

Retired 2026-09-30: `RFC7950-9.3.2-1` quoted the sentence of §9.3.2 that defines the
decimal64 canonical form, and the canonical form binds only what an implementation
sends as XML. Read §9.3.2, §9.3.1, §9.1 and §6.1, and searched the whole text for the
canonical form: §9.1 states the only obligation to use it, "When a server sends
XML-encoded data, it MUST use the canonical form defined in this section.", and site
9.1:2 is already excluded because ze emits no XML instance document. Site 9.3.2:1 is
now excluded for the same reason. The two tags, on `TestRFC7950Decimal64Accepted` and
`TestRFC7950Decimal64Refused` in
`internal/component/config/yang/rfc7950_validator_decimal64_test.go`, proved input
parsing, which is the §9.3.1 lexical representation: both moved to the new row
`RFC7950-9.3.1-1`, which quotes §9.3.1 and is listed in `unsourced-ids` because that
section holds no keyword site (owner ruling R5).

Retired 2026-09-30: `RFC7950-8.3.1-1` binds a NETCONF server, which Ze does not
implement. Read §8.3.1, §8.3, §8.1 and §1, then the whole text for "invalid-value": the
row's obligation is the reply, "the server MUST reply with an "invalid-value"
<error-tag> in the <rpc-error>", and ze has no NETCONF server and no rpc-error
producer. Its sibling sites 8.3.1:1, 8.3.1:6 and 8.3.1:7 were already excluded as
feature-out-of-scope for that reason, and site 8.3.1:2 now is too. The seven tags, on
`TestValidateTree_RangeViolation`, `TestValidateTree_PatternViolation`,
`TestValidateTree_LengthViolation`, `TestValidator_ValidatePattern` and
`TestValidator_HoldTimeRange` in `internal/component/config/rfc7950_validator_yang_test.go`,
proved that a value outside the leaf's range, length or pattern is refused, which is
§8.1's "All leaf data values MUST match the type constraints for the leaf": all moved to
`RFC7950-8.1-3` (owner rulings R2 and R5), split out of `RFC7950-8.1-1` below.

Correction 2026-09-30: `RFC7950-8.1-1` quoted the whole of §8.1's constraint list, one
`{gap}` row over obligations Ze meets and obligations it does not, so the leaf-type tags
moved there by the retirement above could not land on it: a `{gap}` row carries no
proof (owner ruling R3). The row is split into three verbatim spans of §8.1.
`RFC7950-8.1-1` keeps the prefix, from "These constraints are enforced in different
ways" to "it MUST be true in the RPC or action reply.", and its gap (sites 8.1:1 to
8.1:5). `RFC7950-8.1-3` is new and quotes "All leaf data values MUST match the type
constraints for the leaf, including those defined in the type's "range", "length", and
"pattern" properties.": Ze meets it, the seven tags prove it, and site 8.1:6 maps to it.
`RFC7950-8.1-4` is new and quotes the rest, from "All key leafs MUST be present for all
list entries." to the "mandatory" bullet; it keeps the gap, since walkTree evaluates no
when, unique or choice, and sites 8.1:7 to 8.1:10, 8.1:12 and 8.1:13 map to it. The
lead-in "The following properties are true in all data trees:" joins no row, because it
states no obligation of its own.

Correction 2026-09-30: `RFC7950-7.6.1-1` quoted all three branches of §7.6.1's default
rule and the "in use" paragraph after them, and Ze meets only some of them (owner ruling
R3). The row is split into four verbatim spans of §7.6.1. `RFC7950-7.6.1-1` keeps the
lead-in and the first branch, "If no such ancestor exists in the schema tree, the
default value MUST be used.", its two tags and site 7.6.1:1. `RFC7950-7.6.1-2` is new,
quotes the case-node branch and carries a gap: `flattenChoiceCases` drops the case node,
so `ApplyDefaults` fills the defaults of every case (site 7.6.1:2).
`RFC7950-7.6.1-3` is new and quotes "Otherwise, the default value MUST be used if the
ancestor node exists in the data tree.": `TestRFC7950LeafDefaultFollowsItsAncestor`
proves it in both polarities, a presence container or list entry that exists gets its
child's default and one that is absent is not created (site 7.6.1:3).
`RFC7950-7.6.1-4` is new, quotes the "in use" paragraph, and carries a gap: Ze
evaluates no "when" and has no "if-feature", so a default the Note says is not in use
stays in use (site 7.6.1:4).

Correction 2026-09-30: `RFC7950-7.6.5-1` quoted all three branches of §7.6.5's mandatory
rule, and Ze meets only part of them (owner ruling 4: YANG is a third-party library and
Ze does not close these gaps). The row is split into three verbatim spans of §7.6.5.
`RFC7950-7.6.5-1` keeps the lead-in and the first branch, "If no such ancestor exists in
the schema tree, the leaf MUST exist.", its three tags and site 7.6.5:1.
`RFC7950-7.6.5-2` is new, quotes the case-node branch and carries a gap:
the validator never reaches a leaf inside a case, because `walkTree` looks each child up
only in the container's own schema entries and goyang keeps case leaves under the choice
(site 7.6.5:2). `RFC7950-7.6.5-3` is new,
quotes "Otherwise, the leaf MUST exist if the ancestor node exists in the data tree." and
carries a gap: the validator checks a mandatory leaf only inside containers present in
the data (site 7.6.5:3).

Correction 2026-09-30: `RFC7950-8.3.3-1` quoted §8.3.3's rule that the final contents
obey every constraint together with the sentence naming the operations that enforce it,
and the tests prove only the first (owner ruling 4). `RFC7950-8.3.3-1` keeps "When
datastore processing is complete, the final contents MUST obey all validation
constraints.", its two tags and site 8.3.3:1. `RFC7950-8.3.3-2` is new, quotes "If the
datastore is "running" or "startup", these constraints MUST be enforced at the end of the
<edit-config> or <copy-config> operation." and carries a gap: LoadConfig and the
web editor commit refuse a type or ze:validate violation, but both grade a missing
mandatory leaf a warning and evaluate no when, unique or choice (site 8.3.3:2).

Correction 2026-09-30: the Support coverage listed "mandatory leaves" among the checks
Ze validates. The validator reports a missing mandatory leaf, but
`SectionValidationError.Blocking` grades it a warning, so LoadConfig, `ze config
validate` and the editor commit all accept the config. The coverage now says so.

Correction 2026-09-30: `RFC7950-11-3` is the split of the §11 reordering ban out of
`RFC7950-11-1`, whose quote covers the revision statement and the metadata update but
not the sentence "In statements that have any data definition statements as
substatements, those data definition substatements MUST NOT be reordered." The parent's
narrowing audit found that obligation dropped, so it is a row of its own, verbatim, at
the MUST NOT the sentence states. It is a {gap}: no repository check compares an
embedded module against its previous revision, and under owner ruling 4 (2026-09-30,
"yang is provided by a third party library we should not try to close the gap") the
gap is recorded, not closed, and its work sits with
plan/spec-config-yang-authoring-checks.md. The judge stamps it `unimplemented`.

Correction 2026-09-30: `RFC7950-9.1-2` is the split of the no-canonical-form rule out
of `RFC7950-9.1-1`, which quotes only "Implementations MUST support all lexical
representations specified in this document." The dropped sentence of §9.1, "If the
data type does not have a canonical form, the format of the value MUST match the data
type's lexical representation", is a row of its own, verbatim and at MUST. It is a
{gap}: the types with no canonical form are not validated by Ze, and under owner
ruling 4 the gap is recorded, not closed (plan/spec-config-yang-type-identityref.md).
The judge stamps it `unimplemented`.

Correction 2026-09-30: `RFC7950-7.2.2-1` is the split of the submodule-inclusion rule
out of `RFC7950-5.1-1`. The parent's narrowing audit found §7.2.2's sentence "A
submodule MUST only be included by either the module to which it belongs or another

crosses two sections, so the §7.2.2 sentence is a row of its own citing §7.2.2. It is a

(plan/pre-release/spec-config-yang-loader-structural-checks.md). The judge stamps it
`unimplemented`.
