# RFC 4659 corrections

Correction 2026-10-09: `RFC4659-8-5` records §8 separately: "When the VPN-IPv6 traffic is to be transported using IPv6 tunneling, the BGP Next Hop Field SHALL contain an IPv6 address." Independent disposition retains an explicit option-(b) implementation gap, not an exemption. Generic VPNv6 origination and cross-peer forwarding exist, but the integrated inter-ASBR label-binding/forwarding path does not. `checkRouteBestChange` does not mirror native VPN routes to the Loc-RIB, and `sysrib.processEvent` does not turn their native-NLRI publications into FIB entries. BGP peering may use either transport family; §3.2.1 leaves the transport policy to the operator. The conditional SHALL remains binding, and no ASBR feature is commissioned. Keep `RFC4659-8-3`, its §3.2.1.1 shared-subnet quotation and its distinct 48-octet gap.

Correction 2026-10-09: `RFC4659-3.2.1.1-1` previously ended before both identifying bullets. Restore "- whose 8-octet RD is set to zero, and - whose 16-octet IPv6 address is set to the global IPv6 address of the advertising BGP speaker." Keep its single-polarity marker and do not add duplicate bullet rows. Whole-row rejudgment now includes `TestRFC4659ConfiguredIPv6TransportNextHopWire`: native configured self and explicit selection reaches real recipient Sessions under both grouping modes, with independently established speaker-owned addresses. Selective wrong-global and nonzero-RD breaks each fail all four cases; the restored cases pass on the runtime kernel. This closes the originator-identity proof gap, not tunnel creation or 48-octet/shared-subnet behavior. Preserve the later link-local-only exception, where the "unspecified address" indicates absence of a global address.

Correction 2026-10-09: `RFC4659-3.2.1.1-3` records §3.2.1.1: "The link-local address shall be included in the Next Hop field if and only if the advertising BGP speaker shares a common subnet with the peer the route is being advertised to [BGP-IPv6]." Existing unicast and received-pair forwarding evidence does not close this VPN origination gap.
