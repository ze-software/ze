# RFC 9552 corrections

Why a requirement row of `rfc/short/rfc9552.md` changed level, text, or citation.
The summary is the working document; this file is the record the level
ratchet reads (`checkLevelRatchet`, `internal/le/rfc/check_ratchets.go`).

Correction 2026-08-25: `RFC9552-8.2.2-3` was extracted at MUST NOT strength. §8.2.2 states
it in lowercase: "A BGP-LS Propagator, even when it has a coexisting BGP-LS Consumer on the
same node, should not perform semantic validation of the Link-" -- the sentence continues
"State NLRI or the BGP-LS Attribute to determine if it is malformed or invalid", broken
there by the RFC's own line wrap. The paragraph immediately above uses
a capitalised SHOULD for logging, so the document distinguishes the two deliberately rather
than by accident. Same requirement id, corrected text and level.

The obligation constrains the PROPAGATOR'S CODE PATH, not the tests that observe it. The
four tagged tests assert an ABSENCE in the live walk -- `iterateAttrTLVs` advances on the
length field alone and `decodeAttrTLV` dispatches on the type code with no knowledge of the
NLRI the attribute rides with -- so they pass because no semantic check exists and would
fail the moment one were added. Testing for the absence of semantic validation is not
performing it. The level moves; the evidence does not.

Correction 2026-10-06: `RFC9552-5.3.1.3-1` quotes the Node Name recommendation only. §5.3.2.7 separately states for the Link Name TLV: "The use of the FQDN or a substring of it is strongly RECOMMENDED." The link is a different named object, so `RFC9552-5.3.2.7-1` now preserves that recommendation separately rather than treating the Node Name row as its proof. The Link Name TLV is optional and the RFC also permits any operator-chosen string. `decodeLinkName` in `internal/component/bgp/plugins/nlri/ls/attr_link.go` decodes the supplied name; `originateAttributes` in `internal/component/bgp/plugins/ls_export/export_encode.go` copies supplied values and provides no FQDN-based link-name selection. `TestLinkNameRoundTrip` in `internal/component/bgp/plugins/nlri/ls/attr_test.go` proves only a string round trip, not this recommendation. The new row records that missing native naming support as a gap, not conformance or permission to implement the optional feature. Existing Node Name evidence is unchanged.

Correction 2026-10-06: `RFC9552-5.3.2.2-3` stands. Immediately before Table 9, §5.3.2.2 states: "The following bits are defined, and the reserved bits MUST be set to zero and SHOULD be ignored on receipt:" Immediately after the same table it states: "The bits that are not defined MUST be set to 0 by the originator and MUST be ignored by the receiver." Both sentences bind the same six reserved bits of the one-octet MPLS Protocol Mask TLV; the latter retains the same transmission MUST and strengthens receipt to MUST. The row quotes that stronger sentence, so no distinct obligation was dropped. `TestRFC9552NativeDefinedFlags` and `TestRFC9552NativeReservedFlagsCleared` in `internal/component/bgp/plugins/ls_export/rfc9552_export_test.go` observe native output preserving 0xc0 and clearing 0x3f through `clearOriginatedReserved`. `TestRFC9552MPLSProtocolMaskDecode` and `TestRFC9552MPLSProtocolMaskReservedIgnored` in `internal/component/bgp/plugins/nlri/ls/rfc9552_attr_flags_test.go` observe L/R decoding and continued TLV decoding with reserved bits set through `decodeMPLSProtocolMask`. The pre-table extraction site is therefore a duplicate of the row quoted from the post-table site, not another requirement. No row, test, tag or verdict changes.
