# RFC 4090 corrections

Why a requirement row of `rfc/short/rfc4090.md` changed level, text, or citation.
The summary is the working document; this file is the record the level
ratchet reads (`checkLevelRatchet`, `internal/le/rfc/check_ratchets.go`).

Correction 2026-09-21: `RFC4090-4.3-2` was published [MUST]. Section 5, Head-End
Behavior, states the node protection flag at lowercase should, not at MUST: "If node
protection is desired, the head-end LSR should set the" node protection desired flag in
the SESSION_ATTRIBUTE object, and clear the flag otherwise. Section 4.3 defines the flag
and its value 0x10; it does not oblige a head-end to set it. The row is corrected to
[SHOULD].

Correction 2026-09-21: `RFC4090-4.1-2` was published [MUST]. Section 5 states both
backup preferences at lowercase should. For one-to-one backup, "the head-end LSR should
include a FAST_REROUTE object and set the" one-to-one backup desired flag, and the
facility backup sentence repeats the same words for its own flag. Section 5 then makes
the absence of the object a lack of preference rather than a violation. The row is
corrected to [SHOULD].

Correction 2026-09-21: `RFC4090-6.5-1` was published [MUST]. Section 6.5.1, Notification
of Local Repair, states the notification at SHOULD: "the PLR SHOULD send a Path Error
message with error code of" Notify (Error code = 25), with sub-code 3. The row is
corrected to [SHOULD].

Retired 2026-09-26: `RFC4090-3.2-2` states no obligation RFC 4090 carries. The row
said the merge point MUST be the NHOP for link protection and the NNHOP for node
protection. Read §3.2, §2, §6, §6.2, §6.4.2 and §7, then the whole text: §2 only
defines the NHOP and NNHOP bypass tunnels, §6 says the PLR SHOULD try node protection
and then link protection, and §6.2 says the backup LSP cannot traverse the protected
node or link. No sentence obliges the merge point to be the NHOP or the NNHOP. Its
three tags, on TestPLRArmsBypass, TestNodeProtectionLocalRepair and
TestNodeProtectionNeedsNodeBypass in internal/plugins/rsvpte/frr_test.go, claimed only
this row and were deleted; the tests stay.

Retired 2026-09-26: `RFC4090-6.5-2` states no obligation RFC 4090 carries. The row
said the PLR MUST NOT tear down the protected LSP on local repair. Read §6.5, §6.4.3,
§6.5.1, §6.5.2 and §7.2, then the whole text for tear-down: §6.4.3 says the PLR "has
to reroute the data traffic onto the bypass tunnel", with no RFC 2119 keyword, and the
only MUST NOT on keeping state is §7.2, which binds the downstream LSR and is row
RFC4090-7.2-1. No sentence forbids the PLR from tearing the LSP down. Its two tags, on
TestLocalRepairSwitchesFIB and TestLocalRepairFallsBackToTeardown in
internal/plugins/rsvpte/frr_test.go, claimed only this row and were deleted; the tests
stay.

Correction 2026-09-26: `RFC4090-7.1-1` and `RFC4090-7.1-2` cited §7.1. Both sentences
are in §7.1.1, Merging Backup Paths using the Sender Template-Specific Method: "If
merging occurs and one of the Path messages merged was for the protected LSP, then the
final Path message to be sent MUST be that of the protected LSP." The citation is
corrected to §7.1.1; level and text are unchanged.

Retired 2026-09-29: `RFC4090-6.3-1` binds the one-to-one backup method, which Ze does
not implement. The row quoted §6.3.3, Local Reroute of Traffic onto Detour LSP: "When
the PLR detects a failure on the protected LSP, the PLR MUST rapidly switch packets to
the protected LSP's backup LSP instead of to the protected LSP's normal out-segment."
§6 makes that method optional, "A PLR MAY support the DETOUR object", and Ze builds no
detour, so the extraction site 6.3.3:1 is now excluded as feature-out-of-scope. Its two
tags, on TestRFC4090FailureSwitchesToBackup in
internal/plugins/rsvpte/frr_rfc4090_test.go, prove the facility backup switch-over, and
moved to the new row `RFC4090-6.4.3-1`, which quotes §6.4.3, Procedures for the PLR during
Local Repair: "When the PLR detects a link or/and node failure condition, it has to
reroute the data traffic onto the bypass tunnel". The sentence carries no RFC 2119
keyword; "has to" states the step the facility method consists of, and the row is
published [MUST] under D-3.

Correction 2026-09-29: `RFC4090-6-7` quoted two clauses of one §6 sentence and the
sentence after it: "The PLR SHOULD set the "bandwidth protection" flag if the backup
path offers a bandwidth guarantee, and, if the path does not, the PLR SHOULD clear the
"bandwidth protection" flag. This MUST be done if the "bandwidth protection desired"
flag was set in the SESSION_ATTRIBUTE object." Ze reserves no bandwidth on a bypass, so
the set clause has no input a test can drive. Under the split ruling the row keeps its
tests and narrows to the clear clause with the MUST sentence that binds it; level
unchanged. The set clause is the new row `RFC4090-6-8` at [SHOULD], which is its own
keyword, marked as a gap to plan/spec-rsvpte-bypass-bandwidth-protection.md. The MUST
form of setting the flag, when the bandwidth is guaranteed and protection was desired,
stays row `RFC4090-4.4-5`, also a gap.
