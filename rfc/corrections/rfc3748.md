# RFC 3748 corrections

Why a requirement row of `rfc/short/rfc3748.md` changed level, text, or citation.
The summary is the working document; this file is the record the level
ratchet reads (`checkLevelRatchet`, `internal/le/rfc/check_ratchets.go`).

Correction 2026-09-01: `RFC3748-7.10-3` was extracted at MUST NOT strength, cited S7.10 of
this document, and named IKEv2. Section 7.10 states no such rule. It states what a method
that derives keys owes, and it opens by making the derivation itself optional: "It is
possible for the peer and EAP server to mutually authenticate and derive keys." RFC 3748
mentions IKE in a lower-layer list and in two references, and in no obligation at all. The
rule the row carries comes from the carrier, RFC 7296 Section 2.16 at
`rfc/full/rfc7296.txt` line 2958, and that document states it as a SHOULD NOT: "EAP methods
that do not establish a shared key SHOULD NOT be used, as they are subject to a number of
man-in-the-middle attacks". The sentence after it says what an implementation does when
such a method IS used, which a MUST NOT would leave unreachable. Same requirement id,
corrected text, level and citation. The id keeps its S7.10 anchor, because an id is
permanent and is parsed from the section its line cites.

Ze acts on the corrected level rather than around it. `eap-md5` is an
`authentication { mode ... }` value an operator can select, it is never a default, and
adopting a configuration that names it writes one warning quoting the Section 2.16 sentence
(`warnKeylessEAPModes`, `internal/component/ike/engine/eap_auth.go`). RFC 7296 Section 2.16
then keys the AUTH payloads from SK_pi and SK_pr rather than from an MSK (`eapAuthSecret`,
same file).

Retired 2026-09-26: `RFC3748-3.1-4` states no obligation RFC 3748 carries. It said the
lower layer MUST provide duplicate detection. Read §3.1, then the whole text, searching
§1, §2.2 and §4.1 and the appendix for every mention of duplicates: §3.1 item [5] says
the opposite, "while it is desirable that lower layers provide for non-duplication, this
is not a requirement", and hands duplicate detection to the Identifier field. The EAP
layer's own duplicate handling is §4.1, which its own row states. The row carried a
not-applicable marker and no test tagged it, so no tag moved.

Retired 2026-09-27: `RFC3748-4-3` states no obligation of its own. It said octets beyond
the Length field MAY be ignored, and RFC 3748 has no such MAY. Read §4, §4.1 and the
whole text for every mention of the Length field and padding: the one sentence is §4's
"Octets outside the range of the Length field should be treated as Data Link Layer
padding and MUST be ignored upon reception", repeated in §4.1, and row RFC3748-4-4
already quotes it, with extraction site 4:2 mapped to it. Quoting the sentence here
would make this row a second MUST over the same obligation. No test tagged this row
and it held no audit verdict or extraction entry, so nothing moved.

Retired 2026-09-27: `RFC3748-7.10-3` states an obligation RFC 3748 does not carry. Read §7.10, then the whole text: RFC 3748 says nothing about which EAP methods IKEv2 may use. RFC 7296 §2.16 states it: "EAP methods that do not establish a shared key SHOULD NOT be used". Under owner decision D-10 that sentence is now row RFC7296-2.16-16 of rfc/short/rfc7296.md. Both tags, on TestRFC3748IKEv2EAPModesSelectAKeyDerivingMethod and TestRFC3748IKEv2NoAuthModeSelectsAKeylessMethod in internal/component/ike/engine/rfc7296_ikev2_method_selection_test.go, moved to it; their two discrimination records were dropped here and re-observed under the new id.

Retired 2026-09-29: `RFC3748-7.10-1` restates the obligation of `RFC3748-7.10-2`. Read §7.10: its one sentence, "an EAP method supporting key derivation MUST export a Master Session Key (MSK) of at least 64 octets, and an Extended Master Session Key (EMSK) of at least 64 octets", is quoted by both rows, so two MUSTs stood over one obligation (owner ruling R5, 2026-09-29). Extraction site 7.10:1 now maps to `RFC3748-7.10-2`, which no longer needs its unsourced-ids entry. The one tag, on TestRFC3748MSKSize in internal/core/eap/rfc3748_test.go, moved to `RFC3748-7.10-2`; it held no discrimination record.

Correction 2026-09-29: `RFC3748-4.1-11` quoted three sentences of §4.1. The first, the Type rule for a Response, is row `RFC3748-4.1-5`, and the second, no Nak after an initial non-Nak Response, is row `RFC3748-2.1-3`, whose §2.1 sentence it repeats (owner ruling R5, 2026-09-29). The row now quotes the third sentence alone, "An EAP server receiving a Response not meeting these requirements MUST silently discard it", which extraction site 4.1:16 already maps to it; "these requirements" are the two rules the other rows carry. Same id, level and citation. Its tags assert that discard: a Response of another Type (TestAuthenticatorDiscardsAResponseOfAnotherType) and a Nak after the initial non-Nak Response (TestRFC3748AuthenticatorDiscardsANakAfterTheInitialNonNakResponse) draw no packet, and a Response of the method Type is processed (TestAuthenticatorProcessesAResponseOfTheMethodType).
