# RFC 8050 corrections

Why a requirement row of `rfc/short/rfc8050.md` changed level, text, or citation,
or was retired. The summary is the working document; this file is the record the
ratchets read (`internal/le/rfc/check_ratchets.go`).

Retired 2026-09-27: `RFC8050-x-5` states no obligation RFC 8050 carries. Read §1,
§2, §3, §4, §4.1, §4.2, §5 and §6, then the whole text: no sentence tells an MRT
parser that does not know the add-path subtypes to skip a record with an unknown
subtype. RFC 6396 does not state it either: its only such rule is §4.3.3, that an
implementation not recognising the AFI and SAFI of a RIB_GENERIC record SHOULD
discard the rest of that record, which is a different rule. No test tagged the
retired row, so no tag moved.

Correction 2026-10-08: `RFC8050-4.2-1` is a normative wire-format definition. §4.2 says "For clarity, the RIB Entries in this subtype are not redefined." Keep the literal row, MUST level, §4.2 reverse entry and existing judgment under owner D-3. DecodeRIBGenericRecord retains the Path Identifier in raw NLRI and decodes unredefined RIB entries. Snapshot Path-ID limitations remain; no demotion or mechanical rejudgment is authorized.

Correction 2026-10-08: `RFC8050-x-4` retains its literal row and MUST level under owner D-3. §2 says "MRT parsers are usually stateless", not always stateless, and "the MRT subtypes are utilized." AddPathFor uses actual directional OPEN context when available; updateContext refuses ambiguous multiple-family ADDPATH without it. Preserve the bounded no-OPEN scope, extraction mapping and existing proof. A Rationale heading does not demote the normative format requirement or justify invented per-family negotiation.
