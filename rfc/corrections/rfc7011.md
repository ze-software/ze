# RFC 7011 corrections

Why a requirement row of `rfc/short/rfc7011.md` changed level, text, or citation.
The summary is the working document; this file is the record the level
ratchet reads (`checkLevelRatchet`, `internal/le/rfc/check_ratchets.go`).

Retired 2026-09-26: `RFC7011-3-1` said an IPFIX Message MUST contain at least one Set.
Read §2, §3, §3.1 to §3.4.3 and the whole text: RFC 7011 says the opposite. §3 reads
"An IPFIX Message consists of a Message Header, followed by zero or more Sets", and the
§2 definition of Set repeats "zero or more Sets follow the Message Header". No sentence
of RFC 7011 or of another IPFIX document in `rfc/short/` requires a Set. Both of its
tags, on TestRFC7011MessageHasAtLeastOneSet and TestRFC7011NoEmptyMessageEmitted in
internal/plugins/flowexport/ipfix/rfc7011_test.go, were deleted, because no row states
the obligation they proved; the tests stay as tests of Ze's own behavior. The row's
negative discrimination record in rfc/discrimination/rfc7011.json went with the tag.

Retired 2026-09-26: `RFC7011-3.4.2-2` said an Options Template Record MUST contain at
least one Scope Field and at least one non-scope Field. Read §3.4.2, §3.4.2.1, §3.4.2.2,
§4 and the whole text. The scope half is the sentence "The Scope Field Count MUST NOT be
zero." in §3.4.2.2, which row RFC7011-3.4.2-1 already carries. No sentence requires a
non-scope Field. The row carried no tag.

Retired 2026-09-26: `RFC7011-10-4` said IPFIX Messages over UDP SHOULD fit within the
path MTU. Read §10, §10.3 and §10.3.3 and the whole text: the only sentence that states
it is the §10.3.3 "The maximum size of exported messages MUST be configured such that
the total packet size does not exceed the PMTU.", which row RFC7011-10.3.3-1 already
carries at its real MUST level. The row carried no tag.

Retired 2026-09-26: `RFC7011-x-3` said PR-SCTP MUST NOT be used for Template Records.
Read §8.3, §10.2, §10.2.2, §10.2.6 and the whole text. No sentence prohibits PR-SCTP by
name; the obligation is §8.3 "Template Sets and Options Template Sets MUST be sent
reliably, using SCTP ordered delivery.", which row RFC7011-10-2 now carries, and §10.2.6
limits partial reliability to "IPFIX Messages containing only Data Sets", which row
RFC7011-x-8 carries. The row carried no tag.

Retired 2026-09-26: `RFC7011-x-4` said an Exporting Process over TCP MUST handle
backpressure from congestion control. Read §10.4, §10.4.1 to §10.4.5, §11.4 and the
whole text. §10.4.1 describes backpressure and says the Exporting Process "can buffer"
or "can decide to drop" records; its only obligation is that dropped Data Records MUST
be accounted for, which row RFC7011-10.4.1-1 carries. No sentence obliges an exporter to
handle backpressure. The row carried no tag.

Retired 2026-09-26: `RFC7011-x-6` said an Exporting Process over TCP SHOULD use
long-lived connections. Read §10.4, §10.4.4, §10.4.5 and the whole text: no sentence
recommends long-lived TCP connections. The only "long-lived" in RFC 7011 is the §11.1
Heartbeat advice for DTLS Transport Sessions. The row carried no tag.

Retired 2026-09-26: `RFC7011-11-2` said it is RECOMMENDED that Exporting and Collecting
Processes use TLS or DTLS for all communications. Read §11, §11.1 to §11.8 and the whole
text: no sentence recommends TLS or DTLS for all communications. §11.1 makes TLS and
DTLS support mandatory (rows RFC7011-11.1-1 and RFC7011-11.1-2), §11.3 makes mutual
authentication mandatory when they are used (row RFC7011-11-1), and §11.5 describes
deployments where they are not an option. The row carried no tag.

Retired 2026-09-30: `RFC7011-x-1` quoted a sentence that carries no obligation. Read §7
and the whole text: "In most cases, the length of the Information Element will be less
than 255 octets. The following length-encoding mechanism optimizes the overhead ..." is
descriptive, and RFC 7011 never mandates the one-octet form for a length of 0 to 254;
§7 says the length may also be carried in three octets. The obligation of that paragraph
is the sentence before it, extraction site 7:1, "Where an Information Element has a
variable length, the following mechanism MUST be used to carry the length information
for both the IANA-assigned and enterprise-specific Information Elements.", which the new
row RFC7011-7-2 quotes with the same {not-applicable} finding (no template field uses
Field Length 65535). Site 7:1 now maps to RFC7011-7-2. The row carried no tag and no
audit verdict, so no tag moved. Stem size: 8 of 65 rows retired since 2026-09-26,
under the D-7 15% line.

Correction 2026-09-30: `RFC7011-8-3` quotes the exporter half of §8.4's sentence,
"Template Withdrawals (Section 8.1) MUST NOT be sent by Exporting Processes exporting
via UDP". The narrowing audit of spec-rfc-verdict-test-fix-pass found the rest, "and
MUST be ignored by Collecting Processes collecting via UDP", dropped. It gets no row:
it binds a Collecting Process, and Ze implements none. The IPFIX code in
internal/plugins/flowexport encodes and sends; no Ze code listens for or decodes an
IPFIX Message. The row keeps its text.

Correction 2026-09-30: `RFC7011-7-2` and `RFC7011-7-1` carried `{not-applicable}`, and
the independent judge of spec-rfc-verdict-fix-services refused it. Both bind the
Exporting Process, which is the role Ze fills; what Ze lacks is the condition, a
variable-length Information Element. That is an optional feature Ze declined, not a
role it does not hold (ai/rules/rfc-compliance.md, "An OPTIONAL feature outside the
owner's agreed scope"), so both rows now carry `{feature-declined}` quoting Section 6.2's
"Information Elements of type octetArray and string may be exported using any length"
and naming the two template builders: every field has a fixed Field Length, none is
65535, and no exported Information Element is an octetArray or a string. The row texts
are unchanged.
