# RFC 1332 corrections

Why a requirement row of `rfc/short/rfc1332.md` changed level, text, or citation.
The summary is the working document; this file is the record the level
ratchet reads (`checkLevelRatchet`, `internal/le/rfc/check_ratchets.go`).

Correction 2026-09-21: `RFC1332-3.1-1` was extracted at MUST NOT strength. Section 3.1
states the rule at SHOULD NOT strength: "This option SHOULD NOT be sent in a
Configure-Request if a Configure-Request has been received which includes either an IP-
Addresses or IP-Address option." The row now carries that level and those words. Its
`{not-applicable}` note went with the gate it excused: ze still has no IP-Addresses
(Type 1) send path, because internal/component/l2tp/ppp/ipcp.go defines only options
3/129/131 and WriteIPCPOptions emits only those, but an advisory row owes no coverage
annotation. Same requirement id, same Section 3.1 anchor, corrected level and text.

Correction 2026-09-29: `RFC1332-2.1-3` quoted two sentences of Section 2.1, and the
second has a different performer. The row keeps the first, "The maximum length of an IP
packet transmitted over a PPP link is the same as the maximum length of the Information
field of a PPP data link layer frame.", with its level and its tests, which assert the
MTU `afterLCPOpen` installs on the pppN device. The second, "Larger IP datagrams must be
fragmented as necessary.", moves to the new row `RFC1332-2.1-4`, anchored to Section
2.1, because the Linux IPv4 output path fragments on that MTU and no further value Ze
writes decides it; it carries a lower-layer annotation naming that layer and
`afterLCPOpen`. Extraction site 2.1:2 now maps to `RFC1332-2.1-4`, and `RFC1332-2.1-3`,
whose sentence carries no keyword, is listed under the section's unsourced ids.
