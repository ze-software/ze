# RFC 2865 corrections

Why a requirement row of `rfc/short/rfc2865.md` changed level, text, or citation,
or was retired. The summary is the working document; this file is the record the
ratchets read (`checkLevelRatchet`, `checkRetiredRequirements`,
`internal/le/rfc/check_ratchets.go`).

Retired 2026-09-26: `RFC2865-x-1` said to "use constant-time comparison for authenticator
verification", cited to "Implementation Constraints", which is not a section of RFC 2865.
Read §3 (the Response Authenticator), §4.2, §4.4 and §8 Security Considerations, then the
whole text: no sentence mentions timing or constant-time comparison, and §3 only defines
the MD5 value the NAS compares. The row stated a Ze implementation choice at SHOULD level,
not an RFC obligation. It carried no test tag, no extraction mapping and no audit verdict,
so nothing moved.

Retired 2026-09-27: `RFC2865-2.5-2` states an obligation RFC 2865 does not carry. Read §2.5 and the whole text: RFC 2865 says nothing about backing off between retransmissions. RFC 5080 §2.2.1 states it: "implementations SHOULD support congestive backoff." RFC 5080 has no summary in rfc/short, so under owner decision D-10 the row is retired, and a journal row asks for it to be enrolled. The row carried no tag.

Retired 2026-09-27: `RFC2865-3-5` states no obligation RFC 2865 carries (owner decision D-2). Read §3, then the whole text for every sentence about a source address: each one binds the server, "A RADIUS server MUST use the source IP address of the RADIUS UDP packet to decide which shared secret to use" among them, and none tells a client to drop a response from another address. RFC 5080 §2.2.1 and §2.2.2 were read too: a client processes the first response with a valid Response Authenticator, and no source-address rule appears. Its three tags, on TestRFC2865ResponseSourceAddress in internal/component/radius/rfc2865_test.go and TestClientExchangeAccept in internal/component/radius/client_test.go, were removed; the tests stay.

Correction 2026-09-30: `RFC2865-1.1-2` cited "§1.1, restated at §5.6", but its quote is the §1.1 sentence alone and the §5.6 obligation, "A NAS is not required to implement all of these service types, and MUST treat unknown or unsupported Service-Types as though an Access-Reject had been received instead.", was in no row: the narrowing audit of 2026-09-28 called it dropped. Read §1.1 and §5.6: §1.1 binds any Access-Accept authorizing an unavailable service, through whichever attribute authorizes it, and §5.6 binds the Service-Type attribute, including a value the NAS does not know. The §5.6 sentence is now row `RFC2865-5.6-1`, and extraction site 5.6:1 maps to it rather than being excluded as a duplicate of `RFC2865-1.1-2`, whose citation is now §1.1. The new row is proven on the L2TP LNS by TestRFC2865SupportedServiceTypeIsHonored and TestRFC2865UnknownOrUnsupportedServiceTypeIsARejection (internal/component/l2tp/plugins/authradius/rfc2865_unavailable_service_test.go). `RFC2865-1.1-2` keeps its tags and gains a second service, the framing: an Access-Accept for Framed-User over a Framed-Protocol other than PPP was honored by the LNS, a defect fixed in authradius/handler.go.

Retired 2026-09-30: `RFC2865-3-4` binds the RADIUS server, which Ze does not implement. It quoted §4.2, "The Response Authenticator field MUST contain the correct response for the pending Access-Request. Invalid packets are silently discarded." Read §4.2 and §3: the Response Authenticator is written by the party that transmits the Access-Accept, the RADIUS implementation that judged the Access-Request ("If all Attribute values received in an Access-Request are acceptable then the RADIUS implementation MUST transmit a packet with the Code field set to 2 (Access-Accept)."), and Ze runs no RADIUS authentication server. This is ruling R11, applied as RFC2866-4.2-1 was retired on 2026-09-29. The client's side of the paragraph is its second sentence, "Invalid packets are silently discarded.", which carries no keyword; it is now row `RFC2865-4.2-1` at MUST under D-3, a receiver rule stated in the indicative, declared unsourced for §4.2 in rfc/extraction/rfc2865.json. The two tags of the retired row, on TestClientAuthenticatorVerify (internal/component/radius/client_test.go), proved that discard (a reply signed with the wrong secret is dropped and the client retransmits; the correctly signed reply is accepted), so they moved to `RFC2865-4.2-1` under a D-15 approval. The test body is unchanged.

Correction 2026-09-30: `RFC2865-5-8` quotes the §5 text-type sentence, "Text of length zero (0) MUST NOT be sent; omit the entire attribute instead.", and the string-type sentence of the same section, "Strings of length zero (0) MUST NOT be sent; omit the entire attribute instead.", was in no row: extraction site 5:7 was excluded as a duplicate, and the narrowing audit of 2026-09-28 called it dropped. The two sentences bind two data types: text is UTF-8, string is binary octets, and State, Class, Proxy-State and CHAP-Challenge are strings. The string sentence is now row `RFC2865-5-9`, site 5:7 maps to it, and it is proven by TestRFC2865ZeroLengthStringIsOmitted and TestRFC2865OneOctetStringIsSent (internal/component/radius/rfc2865_zero_length_string_test.go). `RFC2865-5-8` keeps its text, level and tags.

Correction 2026-09-30: `RFC2865-4.1-3` quoted only "An Access-Request MUST contain either a User-Password or a CHAP- Password or a State.", and the audit of 2026-09-29 found that the MS-CHAPv2 unit proved a request the row as written forbids. Read §4.1: the paragraph closes with the relief that governs every extension credential, "If future extensions allow other kinds of authentication information to be conveyed, the attribute for that can be used in an Access-Request instead of User-Password or CHAP-Password." A row quote is one verbatim span, so the row now quotes the whole paragraph from its first sentence to that relief. The middle sentence, "An Access-Request MUST NOT contain both a User-Password and a CHAP-Password.", rides along only because the span joins them; its obligation is row `RFC2865-4.1-4`, unchanged. The level stays MUST. The extension credentials Ze sends are the RFC 2548 MS-CHAP2-Response (TestRFC2865MSCHAPv2AccessRequestCarriesTheExtensionCredential, already tagged) and the RFC 3579 EAP-Message, now proven on the admin EAP login by TestRFC2865EAPAccessRequestCarriesTheExtensionCredential (internal/component/radius/rfc2865_eap_credential_test.go). The row's other tags are unchanged.
