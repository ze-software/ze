# RFC 1877 corrections

Retired 2026-09-26: `RFC1877-x-1` states no obligation RFC 1877 carries. Read the
Abstract, §1, §1.1, §1.2, §1.3, §1.4, the References and the Security
Considerations: no sentence says the link must stay usable for IPv4 with or without
DNS. The nearest is §1.1, "By default, no primary DNS address is provided.", which
describes a default and binds nobody, and RFC 1661 states no such rule either. Its
two tags, on `TestIPCPDNSIsOptional` and `TestIPCPIPAddressRejectIsFatal` in
`internal/component/l2tp/ppp/ncp_test.go`, were deleted with their two
discrimination records; the tests stay.

Retired 2026-09-26: `RFC1877-x-2` states no obligation RFC 1877 carries. Read the
whole text as above: §1.1 to §1.4 give each option's Length as 6 and say nothing of
an option received with another Length. RFC 1661 §6 states that rule and contradicts
the row: "If a negotiable Configuration Option is received in a Configure-Request,
but with an invalid or unrecognized Length, a Configure-Nak SHOULD be transmitted
which includes the desired Configuration Option with an appropriate Length and
Data." That is row `RFC1661-6-1`, and Ze's Nak meets it, so the `{gap}` this row
carried described a defect Ze does not have. The row had no tags.

Retired 2026-09-26: `RFC1877-x-3` states no obligation RFC 1877 carries. Read the
whole text as above: §1 says the options are "designed to be identical in format and
behavior to option 3 (IP-Address)", and states no Configure-Ack rule. RFC 1661 §5.2
does: "The acknowledged Configuration Options MUST NOT be reordered or modified in
any way." Its positive tag on `TestRFC1877ConfigureAckEchoesAcceptable`
(`internal/component/l2tp/ppp/rfc1877_dns_options_test.go`) moved to
`RFC1661-5.2-2`, and its negative tag, which proves an unacceptable request is not
Acked, moved to `RFC1661-5.2-1`.

Retired 2026-09-26: `RFC1877-x-4` states no obligation RFC 1877 carries. Read the
whole text as above: no sentence states a Configure-Reject rule. RFC 1661 §5.4 does:
"All recognizable and negotiable Configuration Options are filtered out of the
Configure-Reject, but otherwise the Configuration Options MUST NOT be reordered or
modified in any way." Its positive tag on
`TestRFC1877ConfigureRejectEchoesUnsupportedOnly` moved to `RFC1661-5.4-2`, and its
negative tag, which proves the recognized option is left out of the Reject, moved to
`RFC1661-5.4-1`.

Retired 2026-09-26: `RFC1877-x-5` states no obligation RFC 1877 carries. Read the
whole text as above: no sentence says either side may ignore the options by
Configure-Reject. RFC 1661 §5.4 states it, at MUST rather than MAY: an option "not
acceptable for negotiation (as configured by a network administrator)" means "the
implementation MUST transmit a Configure-Reject", row `RFC1661-5.4-1`, whose level
governs. The row had no tags.
