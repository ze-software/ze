# RFC 7947 corrections

Why a requirement row of `rfc/short/rfc7947.md` changed level, text, or citation.
The summary is the working document; this file is the record the level
ratchet reads (`checkLevelRatchet`, `internal/le/rfc/check_ratchets.go`).

> Correction 2026-08-15: `RFC7947-x-3` was extracted at MUST strength. RFC 7947
> Section 2.2.3 states it as a recommendation: the attribute "SHOULD be propagated
> to other route server clients, and the route server SHOULD NOT modify its value".
> The stronger form was a misquote. Same requirement id, corrected text and level.
> The recommendation is stated against RFC 4271 Section 5.1.4, which otherwise has an
> external speaker discard a metric received from one neighboring AS rather than pass
> it to another. Section 5.1.4 separately REQUIRES a configured removal mechanism, so
> a route server that honors this recommendation by default and still lets an operator
> remove the metric explicitly satisfies both sections.

> Correction 2026-08-14: `RFC7947-x-3` read `single-polarity: positive` on the
> ground that no `mods.Op(4, ...)` existed in the reactor, so no MED-rewrite
> behavior could be asserted as a negative. One exists now. RFC 4271 Section
> 5.1.4 forbids relaying a received metric to another neighboring AS, and
> `applyFactsMED` (internal/component/bgp/reactor/forward_med.go) enforces it,
> with `medPropagationAllowedTo` gating the strip on the exact condition RFC 7947
> Section 2.2.3 exempts. The confining negative is therefore real: one UPDATE,
> two external receivers, the route server client keeping the metric and the
> ordinary eBGP neighbor losing it (test/plugin/med-not-propagated-across-as.ci).

> Correction 2026-07-23: `RFC7947-x-1` was previously extracted at MUST-NOT
> strength. RFC 7947 Section 2.2.2.1 says "SHOULD NOT" and states outright that
> it "is a recommendation rather than a requirement", existing only for backwards
> compatibility with clients that cannot accept a non-adjacent leftmost AS
> (Section 2.2.2.2). The stronger form was a misquote; same requirement id,
> corrected text and level.

Correction 2026-09-27: `RFC7947-x-4` was extracted at MUST strength as "Per-client
import/export policy must be applied on each redistribution", cited "(Key
Requirements)", a heading RFC 7947 does not have. No sentence of the RFC states it
as a MUST. Section 2.1 states the policy step as a recommendation: "The route server
SHOULD forward UPDATE messages from its Loc-RIB or Loc-RIBs to its clients as
determined by local policy." Section 2.3, which discusses per-client policy, says
that neither it nor its subsections "form part of the normative specification of
this document". Same requirement id, corrected text, section and level.

Retired 2026-10-08: `RFC7947-x-6` states no normative permission of RFC 7947. Read §2.3 and §2.3.2.2.2: "Neither Section 2.3 nor its subsections form part of the normative specification of this document; they are included for information purposes only." The row describes RFC7911 rather than a MAY binding this implementation; the later send-only recommendation is informative too. The independent source inventory found no tag or audit entry to move. The §2.3.2.2.2 extraction reason no longer cites this retired row; the section has zero sites and no reverse entry. There is no replacement RFC7947 or RFC7911 identity, and existing RFC7911 obligations and evidence remain unchanged. The retired identity is permanently unavailable for reuse.
