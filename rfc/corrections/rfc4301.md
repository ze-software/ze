# RFC 4301 corrections

Why a requirement row of `rfc/short/rfc4301.md` changed level, text, or citation,
or was retired. The summary is the working document; this file is the record the
ratchets read (`checkLevelRatchet`, `checkRetiredRequirements`,
`internal/le/rfc/check_ratchets.go`). Format: `rfc/corrections/README.md`.

Retired 2026-09-29: `RFC4301-5.1-2` binds only nested-SA processing, a role Ze does
not fill. Read §5.1 step 4, §4.4.1 and §5.2: the sentence applies to a packet the
forwarding function "may cause ... to be passed back across the IPsec boundary, for
additional IPsec processing, e.g., in support of nested SAs". Ze configures no nested
SAs, neither in Go nor through XFRM bundles, so no packet of Ze's re-crosses the
boundary (main-thread ruling R15). Its extraction site 5.1:2 is excluded as
`binds-another-role`. Its two tags, on TestRFC4301BypassReturnTrafficHasAnSPDIEntry
and TestRFC4301BypassSPDIEntryIsNeverAnUnmirroredCopy in
internal/component/ike/engine/rfc4301_bypass_return_test.go, were deleted: those
units prove the SPD-I half of a bypass entry, which `RFC4301-4.4.1-11` states and
their other tags already claim.

Retired 2026-09-29: `RFC4301-5.2-5` binds only nested-SA processing, a role Ze does
not fill. Read §5.2, §4.4.1 and §5.1: the sentence applies to a packet the inbound
forwarding function "may cause ... to be sent (outbound) across the IPsec boundary
for additional inbound IPsec processing, e.g., in support of nested SAs". Ze
configures no nested SAs, neither in Go nor through XFRM bundles, so no packet of
Ze's re-crosses the boundary (main-thread ruling R15). Its extraction site 5.2:4 is
excluded as `binds-another-role`. Its two tags, on
TestRFC4301InboundBypassReturnTrafficHasAnSPDOEntry and
TestRFC4301BypassSPDOEntryIsNeverAnUnmirroredCopy in the same file, were deleted:
those units prove the SPD-O half of a bypass entry, which `RFC4301-4.4.1-12` states
and their other tags already claim.

Correction 2026-09-30: `RFC4301-4.4.2-1` carried a `{single-polarity: positive}` marker, and its tags read the inbound SPD policy only. Read §4.4.2: "For each of the selectors defined in Section 4.4.1.1, the entry for an inbound SA in the SAD MUST be initially populated with the value or values negotiated at the time the SA was created." A transport-mode inbound state carried no selector, and a transport-only secpath passes the kernel's inbound policy check, so a decrypted packet on a port or protocol outside the negotiated pair was delivered. That defect is fixed in installChildSA (internal/component/ike/engine/child.go). The row keeps its text, id and level, and its marker is gone: both polarities are proven against a real XFRM stack in internal/component/ike/engine/rfc4301_sad_selector_linux_test.go, in tunnel mode through the inbound require-policy and in transport mode through the state selector. The "or values" half, an answer carrying more than one traffic selector pair, is the new gap row `RFC4301-4.4.2-2`.

Retired 2026-09-30: `RFC4301-4.4.1-9` binds only a decorrelated SPD, and decorrelation is an optional feature Ze does not use. Read §4.4.1, "Decorrelation": "This RFC does not require a compliant implementation to make use of decorrelation." The sentence the row quoted applies "when an SPD entry is decorrelated". Ze keeps the SPD ordered: xfrmPolicyFromParams (internal/component/ike/dataplane/xfrm_linux.go) writes each entry as one kernel XFRM policy with its priority, and the kernel performs the ordered search that `RFC4301-4.4.1-10` states. Its extraction site 4.4.1:10 is excluded as `feature-out-of-scope`. Its two tags, on TestRFC4301BoundarySPDEntryCarriesSelectorDirectionOrderAndTemplate and TestRFC4301BoundarySPDEntryIsRefusedRatherThanWidened in internal/component/ike/dataplane/rfc4301_boundary_linux_test.go, were deleted: they proved that no decorrelated group exists, which is the absence of the condition rather than the linking.

Retired 2026-09-30: `RFC4301-4.1-8` binds only the multicast de-multiplexing algorithm of §4.1, and multicast SAs are an optional feature Ze does not implement. Read §4.1: "If an IPsec implementation supports multicast, then it MUST support multicast SAs using the algorithm below for mapping inbound IPsec datagrams to SAs. Implementations that support only unicast traffic need not implement this de-multiplexing algorithm." The sentence the row quoted sets the indication that chooses between the algorithm's SPI plus destination and SPI plus destination plus source lookups, which exists only inside that algorithm. Ze negotiates unicast Child SAs only, over IKEv2 with no GDOI group key management, and the kernel finds each inbound SA by SPI, destination and protocol (xfrmStateFromParams, internal/component/ike/dataplane/xfrm_linux.go); `RFC4301-4.1-6` already records the algorithm as not applicable. Its extraction site 4.1:4 is excluded as `feature-out-of-scope`. Its two tags, on TestRFC4301BoundarySADEntryCarriesWhatTheKernelLooksUp and TestRFC4301BoundarySADEntryIsRefusedRatherThanInstalledWrong in internal/component/ike/dataplane/rfc4301_boundary_linux_test.go, were deleted: they proved that the SAD entry copies its address pair and that an unknown mode builds no entry, neither of which is how the indication is set.

Correction 2026-09-30: `RFC4301-4.1-12` restores the obligation retired above as `RFC4301-4.1-8`, same text and level under the next free ordinal, because a retired id is never allocated again. The retirement read multicast SAs as an optional feature Ze does not implement, and that reading was wrong (ruling R24). Ze installs multicast SAs by manual configuration: the OSPFv3 RFC 4552 installer, buildIPsecInterfaceSAs in internal/plugins/ospf/ipsec_install.go, keys one manually keyed SA to ff02::5 and one to ff02::6, and §4.4.2 states "The SAD can support multicast SAs, if manually configured." So the §4.1 condition "If an IPsec implementation supports multicast, then it MUST support multicast SAs using the algorithm below for mapping inbound IPsec datagrams to SAs." holds for Ze, `RFC4301-4.1-6` is judged on that path too, and the indication this row governs is set as a side effect of that manual SA configuration. Extraction site 4.1:4 is mapped to this row. Its proof is TestRFC4301MulticastSASourceMatchingIsSetByManualConfiguration in internal/plugins/ospf/rfc4301_multicast_sa_linux_test.go; the two IKE dataplane tags deleted at the retirement stay deleted, because they proved neither how the indication is set nor a multicast SA.

Retired 2026-09-30: `RFC4301-4.4-1` quoted a framing sentence, not an obligation of its own. Read §4.4: "The model described below is nominal; implementations need not match details of this model as presented, but the external behavior of implementations MUST correspond to the externally observable characteristics of this model in order to be compliant." Each externally observable characteristic of the model is a requirement in its own §4.4.x row: the SPD in `RFC4301-4.4.1-1`, `RFC4301-4.4.1-4`, `RFC4301-4.4.1-10`, `RFC4301-4.4.1-11`, `RFC4301-4.4.1-12` and the §4.4.1.1 selector rows, the SAD in `RFC4301-4.4.2-1` and the §4.4.2.1 data item rows, the PAD in the §4.4.3.x rows (main-thread ruling R22). Its extraction site 4.4:1 is excluded as `not-a-requirement`. Its two tags, on TestRFC4301BoundarySPDEntryCarriesSelectorDirectionOrderAndTemplate and TestRFC4301BoundarySPDEntryIsRefusedRatherThanWidened in internal/component/ike/dataplane/rfc4301_boundary_linux_test.go, were deleted rather than moved, because each characteristic they named already carries its own tag on the same unit: the order is `RFC4301-4.4.1-10`, the selector with its direction and its template are the §5.1 and §5.2 step rows, and the refusal of a selector the kernel cannot express is `RFC4301-4.4.1.1-3`.

Correction 2026-09-30: `RFC4301-5.2-2` carried `{not-applicable}` with the reason that the kernel verifies the inner packet against the inbound policy Ze installs. The whole-stack rule counts exactly that as Ze meeting the requirement (ruling R23), so the marker is gone and the row keeps its text, id and level. Read §5.2 step 4: "Then match the packet against the inbound selectors identified by the SAD entry to verify that the received packet is appropriate for the SA via which it was received." Both polarities are proven against a real XFRM stack in internal/component/ike/engine/rfc4301_sad_selector_linux_test.go: in tunnel mode through the inbound require-policy createFirstChildSA installs (TestRFC4301TunnelModeInboundSelectorsAreEnforcedByTheRequirePolicy), in transport mode through the selector installChildSA writes on the inbound state (TestRFC4301TransportModeInboundSADEntryDropsPacketsOutsideItsSelectors).

Correction 2026-09-30: `RFC4301-4.4.2.1-1` quoted the lead-in "The following data items MUST be in the SAD:", a pointer to a list of sixteen items, and its tags claimed several items at once. Read §4.4.2.1: each item is a bulleted entry of its own. The row keeps its id and its MUST level (the lead-in's keyword binds each item) and now quotes the first item, "Security Parameter Index (SPI): a 32-bit value selected by the receiving end of an SA to uniquely identify the SA." The other fifteen items are new rows `RFC4301-4.4.2.1-4` to `RFC4301-4.4.2.1-18`, each quoting its item verbatim. Ten are items Ze installs and are proven one item at a time in internal/component/ike/dataplane/rfc4301_sad_items_linux_test.go: the SPI (`-1`), the sequence number counter width (`-4`), the anti-replay window (`-6`), the AH transform (`-7`, Ze installs AH for OSPFv3 under RFC 4552, so the item's condition "only if AH is supported" holds), the ESP encryption, integrity and combined mode transforms (`-8`, `-9`, `-10`), the mode (`-12`) and the tunnel header addresses (`-18`). The SPI negative found a defect: `xfrmStateFromParams` built a state for SPI 0, which RFC 4303 Section 2.1 says "MUST NOT be sent on the wire", so a peer proposing SPI 0 got an outbound SA that sent it; the tunnel header negative found that a mixed IPv4 and IPv6 pair was installed. Both are refused now. Five items Ze does not hold are `{gap}` rows: the stateful fragment checking flag (`-13`), the bypass DF bit (`-14`), the DSCP values (`-15`), the bypass DSCP (`-16`) and the path MTU (`-17`). The sequence counter overflow item (`-5`) and the lifetime item (`-11`) are met by the kernel's non-ESN overflow refusal and by the engine's soft and hard lifetime, and carry no tag yet. The row's two old tags, on TestRFC4301BoundarySADEntryCarriesWhatTheKernelLooksUp and TestRFC4301BoundarySADEntryIsRefusedRatherThanInstalledWrong in internal/component/ike/dataplane/rfc4301_boundary_linux_test.go, were deleted: the positive named five items in one claim, and the negative proved the integrity item, which `-9` now carries.
