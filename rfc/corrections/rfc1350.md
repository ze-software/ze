# RFC 1350 row corrections

Retired 2026-09-30: `RFC1350-5-2` binds a host that receives an octet file and then returns it, which Ze does not implement. §5 reads "If a host receives a octet file and then returns it, the returned file must be identical to the original." Ze's TFTP server refuses WRQ (`serve` in `internal/plugins/tftpserver/handler.go`) and Ze has no TFTP client, so it never receives a file and the round trip cannot occur (main-thread ruling R2). Its two tags, on `TestTFTPReadRequest` and `TestTFTPReadLargeFile`, showed only that a stored file is sent unchanged, which no row of RFC 1350 states, so they were dropped. Extraction site 5:2 is now excluded as binds-another-role, and the Enrolment reason counts ten MUST rows, eight met.

Correction 2026-11-14: `RFC1350-5-5` reverses the retirement of `RFC1350-5-2` above, which was wrong on both of its grounds. §5 still reads "If a host receives a octet file and then returns it, the returned file must be identical to the original." The sentence binds a TFTP host that receives files, and Thomas put uploads (write requests) to Ze's TFTP server in scope on 2026-10-31: `ai/META-DECISIONS.md` makes the RFC 1350 requirements that bind a receiver owed work, never declined. That Ze refuses WRQ today (`serveRequests` in `internal/plugins/tftpserver/handler.go` answers it with an Illegal Operation error) is the absence of an owed feature, so the honest kind is a gap and not `binds-another-role`; and Ze has had a TFTP client since fec7380fb1 (`internal/core/fetch/tftp.go`), so "Ze has no TFTP client" is no longer true either. The retired id stays retired, because a retirement paragraph is permanent and §5's ordinals were allocated up to -4, so the obligation returns as `RFC1350-5-5`, `[MUST]` with a `{gap}`, owned by `plan/post-release/features/spec-tftp-server-uploads.md`. Extraction site 5:2 maps to `RFC1350-5-5` instead of being excluded, and the Enrolment reason counts eleven MUST rows, eight met.

Correction 2026-11-14: `RFC1350-2-3` was moved within RFC 1350 on 2026-09-27 (f4a4cea195) with no record of it here. It once claimed "Duplicate ACKs must be silently ignored; must not resend next DATA block" under "Section 2 / RFC 1123 Section 4.2". That claim is RFC 1123 §4.2.3.1, which RFC 1350 cites as reference [4] and does not restate: "the sender (i.e., the side originating the DATA packets) must never resend the current DATA packet on receipt of a duplicate ACK". RFC 1123 has no summary in rfc/short, and no release profile lists it, so no row is written there. The obligation RFC 1350 itself carries is the §5 sentence the row now quotes, "All packets other than duplicate ACK's and those used for termination are acknowledged unless a timeout occurs [4].", so the citation moved from §2 to §5 and the text became that verbatim span. The id keeps its §2 spelling because ids survive a citation correction, and extraction section 5 declares it unsourced there. Same id and level; its tags and its discrimination record stand.
