# Drain policy for the RFC extraction backlog.
#
# Read by internal/le/rfc.Check on every `./le rfc check`.
# Owned by plan/spec-rfcgate-0-umbrella.md and ultimately by Thomas.
#
# THIS FILE CARRIES POLICY ONLY: a start date and a rate. Two fields, nothing else.
# It may NEVER gain a per-stem row, a count, a stem list, or a register column. The moment
# it names an RFC it has become the hand-kept registry the 2026-07-29 resolution rejected,
# and a reviewer should treat such a row as a defect rather than an extension. Who has
# been signed off is DERIVED from rfc/extraction/*.json and published by
# `./le rfc extraction-status`; it is never written down twice.
#
#   start  YYYY-MM-DD the drain clock begins counting from.
#   rate   Entries per calendar month. The required floor is
#          ceil(rate x whole calendar months since start), CAPPED at the WHOLE ENROLLED
#          SET -- never at the remaining backlog. A remainder cap counts every sign-off
#          twice (it raises the cumulative total AND lowers the bar that total is measured
#          against), which collapses the whole comparison to `signed >= enrolled / 2`.
#          The check still retires itself once the backlog is drained, by a different
#          route: a drained corpus has signed == enrolled, and the floor can never exceed
#          enrolled, so the comparison is satisfied from then on without a removal commit.
#
# The rate SHIPS AT 0, so the comparison lands inert (owner decision D5). Arming it is a
# one-line commit that sets a non-zero rate, taken after the first fleet batch has
# measured real throughput -- and Thomas takes it. Guessing a rate now would either be so
# low it forces nothing or so high it reds the tree on unrelated work, and
# ai/rules/rfc-compliance.md records what happens to a rule in the second
# category: it gets removed rather than obeyed.
#
# THE MEASUREMENT D5 ASKED FOR EXISTS NOW. Four RFCs were walked end to end on 2026-08-30
# (rfc1877, rfc2918, rfc4760, rfc5880), spanning all three registers and 7 KB to 110 KB of
# source. End-to-end cost was 6.2 to 12.4 minutes each, a spread of 2.0x. Read from the
# slowest walk, a rate of 2 costs a session 25 minutes each month. The full table is in
# plan/spec-fixit-rfc-drain-quota-never-armed.md, section "WP-2 Measurement".
#
# OWNER RULING, 2026-08-31: the rate STAYS AT 0 for now. Thomas was given the measured
# rate of 2 and ruled that a schedule is premature while the RFC surface is itself
# incomplete: a quota that forces sign-offs over code known to be buggy buys a signature
# rather than conformance.
#
# THE TRIGGER, in his words: "we need our first 100% coverage before locking the gate
# for the RFC verification". So arming waits on ONE enrolled RFC reaching full coverage,
# not on a date and not on a backlog count. Until one document has been taken all the
# way, nobody knows what "done" costs for a whole RFC, and a rate is a claim about that
# cost. The four walks measured what a SIGN-OFF costs, which is a different and smaller
# thing: a sign-off bounds what a summary missed, and coverage is every gated
# requirement actually proven.
#
# What the trigger measures is not recorded here, because this file carries policy only
# and a definition would go stale against the checks that own it. Read
# docs/contributing/rfc-conformance-gates.md and ai/RFC-REQUIREMENTS.md, which are
# derived and cannot drift.
#
# So this is no longer an unmeasured quota. It is a measured one, held by a stated
# trigger. Whoever arms it does NOT need to re-measure the walk cost -- read the table,
# pick the rate, and reset `start` to the arming date, because the floor is CUMULATIVE
# from `start` and an old date bills the tree for every month the quota was inert.
#
# `start` was reset to 2026-08-31 on the same ruling, so the stale date cannot ambush
# the next person to set a rate.

start 2026-08-31
rate 0
