# RFC 5304 - IS-IS Cryptographic Authentication

## Meta

| Field | Value |
|-------|-------|
| RFC | 5304 |
| Title | IS-IS Cryptographic Authentication |
| Status | Standards Track |
| Date | October 2008 |
| Obsoletes | RFC 3567 |
| Updates | RFC 1195 |
| Updated by | - |

**Purpose:** RFC 5304 extends the IS-IS authentication mechanism (ISO 10589,
RFC 1195) to allow HMAC-MD5 (RFC 2104) authentication of IS-IS Protocol Data
Units, in addition to the cleartext-password method the base specification
already defines. It allocates the HMAC-MD5 authentication type, specifies how
the Authentication Value is computed, and adds protocol changes (notably
around LSP purges) to make the authentication effective. It replaces the
Informational RFC 3567 and is on the Standards Track.

**Scope:** Authentication information is carried in the IS-IS Authentication
TLV, type 10. The length of the TLV is variable and its value depends on the
authentication algorithm. The first octet of the value is the authentication
type. Type 0 is reserved, type 1 indicates a cleartext password, and type 255
is used for routing domain private authentication methods. The remainder of
the TLV value is the Authentication Value (Section 1).

## Authentication TLV (Type 10)

| Field | Size | Meaning |
|-------|------|---------|
| Type | 1 octet | 10 (Authentication Information TLV) |
| Length | 1 octet | Variable; for HMAC-MD5 the length field is 17 |
| Authentication Type | 1 octet (first value octet) | 0 = reserved, 1 = cleartext password, 54 = HMAC-MD5, 255 = routing domain private |
| Authentication Value | remainder | Algorithm-dependent; 16 octets for HMAC-MD5 |

## HMAC-MD5 Authentication Type (Section 2)

Quoting Section 2 verbatim: "The authentication type used for HMAC-MD5 is 54
(0x36). The length of the Authentication Value for HMAC-MD5 is 16, and the
length field in the TLV is 17."

The IANA registry "IS-IS Authentication Type Codes for TLV 10" (Section 4)
records the same assignment:

| Authentication Type Code | Value | Reference |
|--------------------------|-------|-----------|
| Reserved | 0 | ISO-10589 |
| Cleartext Password | 1 | ISO-10589 |
| ISO 10589 Reserved | 2 | ISO-10589 |
| HMAC-MD5 Authentication | 54 | RFC 5304 |
| Routeing Domain private authentication method | 255 | ISO-10589 |

## Digest Computation (Section 2)

HMAC-MD5 takes a key K and text T (RFC 2104):

- K is the password for the PDU type, as specified in ISO 10589.
- T is the IS-IS PDU to be authenticated with the Authentication Value field
  (inside the Authentication Information TLV) set to zero.

Before authentication is computed: "the Authentication Type is set to 54 and
the length of the TLV is set to 17 before authentication is computed."

LSP-specific zeroing: "When LSPs are authenticated, the Checksum and Remaining
Lifetime fields are set to zero (0) before authentication is computed. The
result of the algorithm is placed in the Authentication Value field."

To authenticate an incoming PDU (Section 2): a system saves the values of the
Authentication Value field, the Checksum field, and the Remaining Lifetime
field, sets these fields to zero, computes authentication, and then restores
the saved values.

## Per-PDU Authentication Strings (Section 2)

| PDU type | Authentication string used |
|----------|----------------------------|
| Level 1 Sequence Number PDU | Area Authentication string (as in Level 1 Link State PDUs) |
| Level 2 Sequence Number PDU | Domain authentication string (as in Level 2 Link State PDUs) |
| IS-IS Hello PDU | Link Level Authentication String (MAY differ from that of Link State PDUs) |

The HMAC-MD5 result for IS-IS Hello PDUs SHALL be calculated after the packet
is padded to the MTU size, if padding is not disabled. Implementations that
support the optional checksum for Sequence Number PDUs and IS-IS Hello PDUs
MUST NOT include the Checksum TLV (Section 2).

## MUST / MUST NOT (Section 2)

- "An implementation that implements HMAC-MD5 authentication and receives
  HMAC-MD5 Authentication Information MUST discard the PDU if the
  Authentication Value is incorrect."
- "ISes (routers) that implement HMAC-MD5 authentication and initiate LSP
  purges MUST remove the body of the LSP and add the authentication TLV."
- "ISes implementing HMAC-MD5 authentication MUST NOT accept unauthenticated
  purges."
- "ISes MUST NOT accept purges that contain TLVs other than the
  authentication TLV."

These purge restrictions prevent a hostile system from receiving an LSP,
setting the Remaining Lifetime field to zero, and re-flooding it, thereby
initiating a purge without knowing the authentication password (Section 2).

## MAY (Section 2)

- An implementation MAY have a transition mode where it includes HMAC-MD5
  Authentication Information in PDUs but does not verify it. This is a
  transition aid for networks deploying authentication.
- An implementation MAY check a set of passwords when verifying the
  Authentication Value, providing a mechanism for incrementally changing
  passwords.
- An implementation that does not implement HMAC-MD5 authentication MAY
  accept a PDU that contains the HMAC-MD5 Authentication Type.

## Implementation Note (Section 2.1)

Just after a password rollover, the router or IS-IS process may restart,
restarting the LSP Sequence Number from 1 with the new password. Neighbours
reject those new LSPs because the Sequence Number is smaller, and the router
cannot increase its own Sequence Number because it fails to authenticate its
own old LSP (sent back by neighbours under the old password). A possible
solution: if an inbound LSP with an authentication failure carries the local
System ID and a higher Sequence Number than the local process holds, the
process SHOULD increase its own LSP Sequence Number accordingly and re-flood.
Because this could also be triggered by an active attack, it is recommended
that a counter be kept on this case.

## Security Considerations (Section 3)

The mechanism improves security against passive attacks compared with
cleartext passwords but is not perfect: it does not prevent replay attacks
(though IS-IS mechanisms typically reject old information), does not protect
against compromised, malfunctioning, or misconfigured routers, and does not
provide confidentiality (privacy is not a requirement for a routing
protocol). Security depends entirely on the strength of the algorithms, the
strength and confidentiality of the key, and correct implementation
(Sections 3.1, 3.2). Implementations should support at minimum a key of
printable ASCII of 80 bytes or less (Section 3.3). A Key-ID field (as in
OSPFv2 / RIPv2) was considered but rejected for this document given the
installed base (Section 3.4).
