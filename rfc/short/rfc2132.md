**Purpose:** Defines the format and semantics of configuration parameters carried in the options field of DHCP and BOOTP messages. Options use a tag-length-value (TLV) encoding to deliver subnet masks, routers, DNS servers, lease times, and DHCP protocol control fields.

**Scope:** All DHCP/BOOTP message types. Section 9 options are DHCP-specific; all others apply to both DHCP and BOOTP.

## Wire Format

### Option TLV Encoding (Section 2)

All options except Pad (0) and End (255) use this format:

```
+------+------+------+------+------+---
| Code |  Len |  d1  |  d2  | ...  |
+------+------+------+------+------+---
  1 oct  1 oct  Len octets of data
```

| Field | Offset | Size | Type | Constraints |
|-------|--------|------|------|-------------|
| Code | 0 | 1 | uint8 | Option type code |
| Len | 1 | 1 | uint8 | Length of data (does NOT include Code and Len bytes) |
| Data | 2 | Len | varies | Option-specific payload |

**Fixed-length options** (no Len byte): only Code 0 (Pad) and Code 255 (End).

**Magic cookie:** First 4 octets of the options field MUST be `99.130.83.99` (hex `0x63825363`) in network byte order.

### Pad Option (Section 3.1)

```
+-----+
|  0  |
+-----+
```

Single octet, no length field. Used for alignment.

### End Option (Section 3.2)

```
+------+
| 255  |
+------+
```

Single octet, no length field. Marks end of valid options. Subsequent octets SHOULD be filled with Pad (0).

### Subnet Mask, Option 1 (Section 3.3)

```
 Code   Len        Subnet Mask
+-----+-----+-----+-----+-----+-----+
|  1  |  4  |  m1 |  m2 |  m3 |  m4 |
+-----+-----+-----+-----+-----+-----+
```

| Field | Offset | Size | Type | Constraints |
|-------|--------|------|------|-------------|
| Mask | 2 | 4 | IPv4 address | Per RFC 950 |

**Constraint:** "If both the subnet mask and the router option are specified in a DHCP reply, the subnet mask option MUST be first." (Section 3.3)

### Router Option, Option 3 (Section 3.5)

```
 Code   Len         Address 1               Address 2
+-----+-----+-----+-----+-----+-----+-----+-----+--
|  3  |  n  |  a1 |  a2 |  a3 |  a4 |  a1 |  a2 |  ...
+-----+-----+-----+-----+-----+-----+-----+-----+--
```

| Field | Offset | Size | Type | Constraints |
|-------|--------|------|------|-------------|
| Address N | 2 + (n*4) | 4 | IPv4 address | Minimum length 4, MUST be multiple of 4 |

Routers SHOULD be listed in order of preference.

### Server Identifier, Option 54 (Section 9.7)

```
 Code   Len            Address
+-----+-----+-----+-----+-----+-----+
|  54 |  4  |  a1 |  a2 |  a3 |  a4 |
```

The identifier is the IP address of the DHCP server. Included in DHCPOFFER so clients can distinguish between lease offers. Clients include it in DHCPREQUEST to indicate which offer is accepted.

### Client Identifier, Option 61 (Section 9.14)

```
 Code   Len   Type  Client-Identifier
+-----+-----+-----+-----+-----+---
|  61 |  n  |  t1 |  i1 |  i2 | ...
+-----+-----+-----+-----+-----+---
```

| Field | Offset | Size | Type | Constraints |
|-------|--------|------|------|-------------|
| Type | 2 | 1 | uint8 | ARP hardware type (1 = Ethernet); 0 = non-hardware identifier |
| Identifier | 3 | n-1 | opaque | MUST be unique per subnet |

Servers SHOULD treat identifiers as opaque objects. Type field SHOULD be one of the ARP hardware types from STD 2 [22].

## Encoding Rules

- All multi-octet quantities are in **network byte order** (big-endian) (Section 2)
- Options containing NVT ASCII data SHOULD NOT include a trailing NULL (Section 2)
- Options 0 (Pad) and 255 (End) have no length octet; all others MUST have a length octet (Section 2)
- IP address list options (3, 4, 5, 6, etc.) MUST have length as a multiple of 4
- Option codes 128-254 are reserved for site-specific options (Section 2)

## Decoding Rules

1. Verify magic cookie `0x63825363` at start of options field
2. Read tag byte
3. If tag is 0 (Pad): skip, continue
4. If tag is 255 (End): stop parsing
5. Otherwise: read length byte, then read `length` bytes of data
6. Receiver MUST be prepared to delete trailing NULLs from ASCII options (Section 2)
7. Receiver MUST NOT require trailing NULL in ASCII data (Section 2)
8. If Option Overload (52) is present, parse `file` and/or `sname` fields as additional options after completing the standard options field

## Validation

| Check | Valid | Invalid Action |
|-------|-------|----------------|
| Magic cookie | `0x63825363` | Not a DHCP options field |
| IP address list length | Multiple of 4 | Malformed option |
| Subnet mask before router | Option 1 before option 3 | MUST reorder (Section 3.3) |
| Max DHCP Message Size | >= 576 | Reject value |
| DHCP Message Type | 1-8 | Unknown message type |
| Client-identifier uniqueness | Unique per subnet | Binding collision |

## MUST Requirements

### Tx (Sender)

- "If both the subnet mask and the router option are specified in a DHCP reply, the subnet mask option MUST be first." (Section 3.3)
- Router option "length MUST always be a multiple of 4" (Section 3.5)
- DNS server option "length MUST always be a multiple of 4" (Section 3.8)
- All IP address list options: length MUST be a multiple of 4 (Sections 3.5-3.13, 8.2, 8.3, 8.5, 8.6, 8.9, 8.10, 8.12-8.21)
- Static route option "length MUST be a multiple of 8" (Section 5.8)
- Policy filter option "length MUST be a multiple of 8" (Section 4.3)
- Server "MUST try to insert the requested options in the order requested by the client" (Section 9.8, Parameter Request List)

### Rx (Receiver)

- "the receiver of such options MUST be prepared to delete trailing nulls if they exist" (Section 2)
- "The receiver MUST NOT require that a trailing null be included in the data" (Section 2)
- "Servers not equipped to interpret the vendor-specific information sent by a client MUST ignore it" (Section 8.4)
- "Servers not equipped to interpret the class-specific information sent by a client MUST ignore it" (Section 9.13)

### Validation

- "Any options defined subsequent to this document MUST contain a length octet even if the length is fixed or zero" (Section 2)
- "each client's client-identifier MUST be unique among the client-identifiers used on the subnet to which the client is attached" (Section 9.14)

## SHOULD/MAY

- [SHOULD] "Options containing NVT ASCII data SHOULD NOT include a trailing NULL" (Section 2)
- [SHOULD] Routers "SHOULD be listed in order of preference" (Section 3.5)
- [SHOULD] DNS servers "SHOULD be listed in order of preference" (Section 3.8)
- [SHOULD] Identifiers "SHOULD be treated as opaque objects by DHCP servers" (Section 9.14)
- [SHOULD] Client identifier type "SHOULD be one of the ARP hardware types defined in STD2" (Section 9.14)
- [MAY] Client "MAY list the options in order of preference" in Parameter Request List (Section 9.8)
- [MAY] Client identifier "MAY consist of type-value pairs similar to the 'htype'/'chaddr' fields" (Section 9.14)

## Server Implementation Notes

### Minimum Options for a Typical DHCP Server Response

A DHCP server OFFER/ACK will typically include:

| Option | Code | Purpose |
|--------|------|---------|
| Subnet Mask | 1 | Client's subnet mask |
| Router | 3 | Default gateway(s) |
| DNS Server | 6 | DNS resolver(s) |
| Domain Name | 15 | Client's domain |
| Lease Time | 51 | Lease duration in seconds |
| Message Type | 53 | DHCPOFFER (2) or DHCPACK (5) |
| Server Identifier | 54 | Server's own IP address |
| T1 (Renewal) | 58 | When client should start renewing (typically 0.5 * lease) |
| T2 (Rebinding) | 59 | When client should start rebinding (typically 0.875 * lease) |

### Option Ordering

1. DHCP Message Type (53) SHOULD appear first per RFC 2131 guidance
2. Subnet Mask (1) MUST appear before Router (3) if both present
3. Respond to Parameter Request List (55) options in the order the client requested
