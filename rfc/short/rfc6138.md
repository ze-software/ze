**Purpose:** Refines the LDP IGP synchronization mechanism of RFC 5443 for
broadcast (multi-access) links. On such links the IGP advertises a single
cost to the pseudonode, so the RFC 5443 "advertise maximum cost" trick can be
applied only to the link as a whole, not to an individual peer. When a new LDP
peer comes up on a broadcast network this can black-hole traffic that flows
through other, already-established peers. RFC 6138 instead has the router whose
link is coming up *withhold* the link-to-pseudonode advertisement until LDP is
operational with all peers on the segment, unless removing the link would
partition the topology (a "cut-edge").

**Scope for Ze:** This is a procedure refinement, not a protocol extension.
It affects the IGP (`ospf`/`isis` plugins) SPF and LSA/LSP origination logic
and the LDP plugin's "LDP operational" signalling, not any wire codec. It is
relevant to an `ldp` + IGP sync feature: the IGP must consult LDP operational
state and a per-interface "cut-edge" flag before reflecting a newly-up
broadcast adjacency into its Router-LSA (OSPF) or Link State PDU (IS-IS).

## Concepts

### Cut-edge (§4, Appendix A)

A directly connected network's interface is a **"cut-edge"** for a router when
there is no alternate path to that network in the topology:

> "If a router has a directly connected network that does not have an alternate
> path to reach it, then the interface to that network is a "cut-edge" in the
> topology for that router. When a "cut-edge" goes down, the network is
> partitioned into two disjoint sub-graphs." (§4)

The cut-edge property decides whether withholding the link is safe. If the
interface is *not* a cut-edge, traffic can reach the network another way while
LDP converges, so the link may be withheld. If it *is* a cut-edge, withholding
it would disconnect the network, so the link must be advertised immediately
regardless of LDP state.

### Pseudonode / broadcast cost model (§3, §4)

> "On broadcast networks, a router's Link State Advertisement (LSA) contains a
> single cost to the broadcast network rather than a separate cost to each peer
> on the broadcast network." (§3)

> "A broadcast network is advertised as a pseudonode containing a list of
> routers to which the broadcast network is connected, and the cost of all
> these links from the pseudonode to each router is zero when computing SPF
> (Shortest Path First)." (§4)

This single-cost model is exactly why per-peer max-metric (RFC 5443) cannot
express "stay away from peer B while keeping peers C and E usable." The fix is
to remove the whole link from the LSDB temporarily instead of raising its cost.

## Procedure (Encoding / Origination Rules)

The behavioural rule replaces "raise the metric" with "withhold the
link-to-pseudonode advertisement." It applies only at the router whose link is
coming up; no other router on the segment participates.

Origination sequence (§4):

1. During intra-area SPF, additionally compute whether each directly connected
   network has an alternate path; mark interfaces with no alternate path as
   "cut-edge" (see Appendix A).
2. During IGP procedures, when the router's **first** adjacency to the
   broadcast network is coming up and the LSA is about to be updated with a
   link to the pseudonode of the broadcast interface, check whether that
   interface is a "cut-edge". The check must be done "just before the adjacency
   is about to be reflected in the LSA."
3. If it is **not** a cut-edge: postpone updating the LSA with that link to the
   pseudonode until LDP is operational with all LDP peers on that broadcast
   interface.
4. After LDP is operational: update the LSA with the link to the pseudonode and
   flood it.
5. If it **is** a cut-edge: the LSA update MUST NOT be delayed by LDP's
   operational state (advertise immediately).

Per-IGP realisation (§4):

| IGP | Withheld until LDP operational | Verbatim |
|-----|-------------------------------|----------|
| OSPF | Router-LSA "Link Type 2" (link to transit network) for that subnet | "the Router-LSA is not updated with a "Link Type 2" (link to transit network) for that subnet until LDP is operational with all neighboring routers on that subnet." |
| IS-IS | "IS Reachability TLV" (or "Extended IS Reachability TLV") to the pseudonode | "the "Link State PDU" is updated with an "IS Reachability TLV" (or an "Extended IS Reachability TLV") to the pseudonode after LDP is operational with all neighboring routers on that subnet." |

## Decoding / Receiver Rules

There is no receiver-side parsing change. Other routers on the broadcast
network observe only that the new router's link-to-pseudonode advertisement
appears later (after LDP convergence) than it otherwise would. The mechanism is
unilateral at the originator:

> "Only the router whose link is coming up plays a role in ensuring this. The
> other routers on the broadcast network are not involved." (§4)

> "Note that this solution can be introduced in a gradual manner in a network
> without any backward compatibility issues." (§4)

## Cut-Edge Computation Algorithm (Appendix A)

Two equivalent methods are given:

1. **During SPF:** An interface is a cut-edge if, during intra-area SPF (using
   Dijkstra's algorithm per Section 16.1 of OSPF), there is no alternate path
   for the directly connected network.
2. **From last SPF:** A cut-edge can be detected from the last SPF run if there
   is a lack of connectivity to the router-id of a directly connected peer via
   an alternate path. The peer's router-id can be learned during adjacency
   bring-up.

Timing constraint:

> "If an SPF run was scheduled but is pending execution, that SPF MUST be
> executed immediately before any procedure checks whether an interface is a
> "cut-edge"." (Appendix A)

Cost guidance (non-normative, lowercase "should"):

> "A "cut-edge" computation should not require any extra SPF runs. It should
> not increase the algorithmic complexity of SPF." (Appendix A)

### Sync without support at one end (Appendix B, informational)

- **P2P (or broadcast in P2P mode):** The supporting end does not advertise the
  link to the other router in its LSA unless the edge is a cut-edge or until
  LDP becomes operational; so neither router selects the other as IGP next-hop
  prematurely. This works even if the far end implements neither RFC 6138 nor
  RFC 5443.
- **Broadcast:** Not straightforward, "a topic for future study." One suggested
  approach: the designated router (DR) stops advertising the link in the
  pseudonode to the router whose link is coming up until LDP is operational.

Only two normative RFC 2119 keyword requirements appear in the document body

- [ ] [RFC6138-4-1] [MUST NOT] If the interface is a "cut-edge", updating of the LSA MUST NOT be delayed by LDP's operational state (the link is advertised immediately, regardless of LDP) (§4)
- [ ] [RFC6138-x-1] [MUST] If an SPF run was scheduled but is pending execution, that SPF must be executed immediately before any procedure checks whether an interface is a "cut-edge" (Appendix A)

### Non-normative guidance (not RFC 2119, but implementation-relevant)

- [ ] If the interface is not a "cut-edge", postpone updating the LSA with the link to the pseudonode until LDP is operational with all LDP peers on that broadcast interface; update and flood after LDP is operational (§4)
- [ ] The cut-edge check must be done just before the adjacency is about to be reflected in the LSA (§4)
- [ ] The check applies when the router's first adjacency to the broadcast network is coming up (§4)
- [ ] (OSPF) Do not add the Router-LSA "Link Type 2" for the subnet until LDP is operational with all neighboring routers on that subnet (§4)
- [ ] (IS-IS) Add the IS Reachability TLV / Extended IS Reachability TLV to the pseudonode only after LDP is operational with all neighboring routers on that subnet (§4)
- [ ] Cut-edge computation should not require extra SPF runs and should not increase SPF algorithmic complexity (Appendix A)

|-------------------------------------------------|-----------|---------------------------------|--------|

| First adjacency coming up | No | No | Postpone the link-to-pseudonode advertisement (§4) |
| First adjacency coming up | No | Yes | Update LSA with link to pseudonode and flood (§4) |

## Pitfalls

- **Edge cases:**
  - *Cut-edge override is mandatory.* The single normative MUST NOT (§4) means a
    naive "always wait for LDP" implementation is non-conformant: a cut-edge
    link must be advertised immediately or the network partitions.
  - *Pending SPF.* Reading a stale cut-edge result is unsafe; a scheduled-but-
    pending SPF MUST run first (Appendix A). Do not cache cut-edge across a
    topology change without re-running SPF.
  - *First adjacency only.* The withholding decision is tied to the router's
    first adjacency to the broadcast network coming up, evaluated just before
    the LSA reflects it (§4); later adjacencies on an already-advertised
    pseudonode link are a different case.
  - *"All peers".* LDP must be operational with **all** neighboring routers on
    the subnet before the link is advertised (§4), not just one.

- **Interop:**
  - No protocol changes means no negotiation and no compatibility flag; the
    feature is invisible on the wire and deploys incrementally (§4, §8).
  - Coexists with RFC 5443: an implementation may use RFC 5443 for P2P and RFC
    6138 for broadcast (§6).
  - Detection of "LDP operational" is implementation-defined and out of this
    RFC's scope; RFC 5919 End-of-LIB is the noted preferred signal (§5). A
    mismatch in how each end declares LDP operational is an interop hazard the
    RFC does not resolve.

- **Security (§7):**
  - Introduces no new security considerations beyond RFC 5443.
  - Carry-over risk from RFC 5443: advertising a link with a high metric can
    push the end-to-end path beyond 255 hops, causing TTL-based
    unreachability; exploitable if an attacker controls metrics.
  - This is not unique to LDP-IGP-sync: a plain link-state IGP can also pick a
    >255-hop alternate path over a higher-metric directly connected path and
    conclude the neighbor is reachable when it is not. Operators must apply
    policy/security to metric determination and distribution.

## Compatibility

- **Non-supporting peers:** Fully backward compatible. Because nothing changes
  on the wire, a router running RFC 6138 interoperates with routers that run
  RFC 5443 or no sync method at all; the only observable effect is delayed
  appearance of the originator's broadcast link in the LSDB (§4, §8).
- **Negotiation/fallback:** None required (no protocol negotiation exists). RFC
  6138, RFC 5443, and plain max-metric can coexist on different links in the
  same network (§6, §8).
