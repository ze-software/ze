# RFC 5176 - Dynamic Authorization Extensions to RADIUS

## Meta

| Field | Value |
|-------|-------|
| RFC | 5176 |
| Title | Dynamic Authorization Extensions to Remote Authentication Dial In User Service (RADIUS) |
| Status | Informational |
| Date | January 2008 |
| Author | M. Chiba, G. Dommety, M. Eklund, D. Mitton, B. Aboba |
| Obsoletes | RFC 3576 |
| Updates | - |
| Updated by | - |

**Purpose:** Extends RADIUS to allow a RADIUS server to initiate
changes to active sessions on the NAS. Two new message types:
Change-of-Authorization (CoA) for modifying session parameters, and
Disconnect-Message (DM) for terminating sessions.

**Scope:** The NAS listens on UDP port 3799 for incoming requests from
the RADIUS server. This reverses the normal client-server direction:
the RADIUS server sends requests, and the NAS responds. The same
shared secret, authenticator computation, and TLV attribute encoding
from RFC 2865 apply.

## Packet Codes (Section 3)

| Code | Name | Direction |
|------|------|-----------|
| 40 | Disconnect-Request | Server -> NAS |
| 41 | Disconnect-ACK | NAS -> Server |
| 42 | Disconnect-NAK | NAS -> Server |
| 43 | CoA-Request | Server -> NAS |
| 44 | CoA-ACK | NAS -> Server |
| 45 | CoA-NAK | NAS -> Server |

## Request Authenticator (Section 2.3)

The Request Authenticator in CoA-Request and Disconnect-Request is
computed the same way as Accounting-Request (RFC 2866 Section 3):

```
MD5(Code + Identifier + Length + 16-zero-octets + Attributes + Secret)
```

RFC 5176 states no receive-side rule for this field: Section 2.3 says only
that the Authenticator "MUST be calculated in the same way as is specified for
an Accounting-Request in [RFC2866]". Ze verifies it before it reads any
attribute, and discards a packet whose value does not match without answering,
because a sender that cannot compute the value holds no shared secret and
Section 6.1 makes such a source untrusted.

## Response Authenticator (Section 2.3)

Response packets (ACK/NAK) use the standard Response Authenticator
from RFC 2865 Section 3:

```
MD5(Code + Identifier + Length + Request-Authenticator + Attributes + Secret)
```

## Session Identification (Section 3)

The RADIUS server identifies the target session using one or more of:

| Attribute | Type | Purpose |
|-----------|------|---------|
| Acct-Session-Id (44) | String | Unique session identifier from Accounting-Start |
| User-Name (1) | String | PPP authenticated identity |
| NAS-Port (5) | Integer | Port number on the NAS |
| Calling-Station-Id (31) | String | Subscriber phone/MAC |
| NAS-IP-Address (4) | IPv4 | NAS identification |
| NAS-Identifier (32) | String | NAS identification |

Multiple identification attributes narrow the match. Section 3 says the
combination "MUST match at least one session in order for a Request to be
successful; otherwise a Disconnect-NAK or CoA-NAK MUST be sent". The presence
of User-Name or Chargeable-User-Identity is a SHOULD, not a MUST.

## CoA Use Cases (Section 2)

- **Bandwidth change:** Update Filter-Id or vendor-specific rate
  attributes on an active session. The NAS applies new TC/QoS rules
  without disconnecting the subscriber.

- **Session disconnect:** Force-terminate a session (e.g., prepaid
  credit exhausted, administrative action).

- **Authorization change:** Modify any RADIUS-provisioned session
  attribute (VLAN, ACL, idle timeout).

## Message-Authenticator (Section 3.4)

Optional in the RFC, and optional in ze by default. The
`require-message-authenticator` leaf turns an absent attribute into a discard.
The HMAC-MD5 is computed with the Request Authenticator field AND the
Message-Authenticator value each taken as sixteen octets of zero, and the
attribute is inserted before the Request Authenticator is computed. Both fields matter: hashing the Request
Authenticator would make each of the two authenticators depend on the other,
and RFC 3579 Section 3.2's Access-Request rule does not apply here.

## Ze Implementation Notes

- The NAS listens on a configurable UDP port. Unset keeps the listener off, and
  a listener with no resolved server address does not start (RFC 5176 §6.1).
- The shared secret is chosen by the source address, and the RADIUS auth/acct
  server config supplies it.
- The identification attributes ze evaluates are Acct-Session-Id, User-Name and
  NAS-Port, and they narrow the match together rather than each opening its own
  route to a session.
- A match of more than one session is answered with Error-Cause 508, because ze
  does not apply one request to several sessions (RFC 5176 §2.3).
- CoA with a Filter-Id carrying a rate string ("10mbit") or a MikroTik VSA emits
  the SessionRateChange event; a Filter-Id naming a CoS profile emits
  SessionCoSChange. A CoA-ACK is sent only after the event was emitted.
- Disconnect-Request calls TeardownSession on the L2TP subsystem.
- Event-Timestamp is required, which is stricter than the RFC and is the answer
  to a port that takes unsolicited teardowns. Message-Authenticator is optional
  by default, and the `require-message-authenticator` leaf makes its absence a
  discard.
- Proxy-State and State are echoed unmodified and are never read.

**Known deviation, owner decision owed.** Five ids are anchored to sections
their obligations do not live in: `RFC5176-3.5-1`, `-3.5-2`, `-3.5-3` and
`-3.5-4` state Section 2.3 obligations, and `RFC5176-3.3-1` states a Section 3
one. An id is anchored to the section its line cites and `checkRetiredRequirements`
refuses a vanishing id, so correcting an anchor means retiring five ids and that
is not a walk's decision to take. Each of the three lines whose TEXT was also
wrong now names its true section: `-3.5-1` and `-3.5-2` quoted sentences that
appear nowhere in RFC 5176, and `-3.3-1` stated a Section 3 SHOULD as a MUST.

## Compliance Checklist

- [ ] [RFC5176-3.5-1] [MUST] A CoA-Request or Disconnect-Request MUST have its Request Authenticator verified before any attribute of it is acted on (anchored §3.5; the sentence it enforces is at §2.3, "The Authenticator field MUST be calculated in the same way as is specified for an Accounting-Request in [RFC2866]", and a value nobody checks authenticates nothing)
- [ ] [RFC5176-3.5-2] [MUST] A CoA-Request or Disconnect-Request whose Request Authenticator does not match MUST be discarded with no response emitted (anchored §3.5; a sender that cannot compute the Authenticator holds no shared secret, so §6.1, "A Dynamic Authorization Server MUST silently discard Disconnect-Request or CoA-Request packets from untrusted sources", covers it)
- [ ] [RFC5176-3.3-1] [MUST] The combination of NAS and session identification attributes in a CoA-Request or Disconnect-Request MUST match at least one session for the request to succeed, and a request matching none MUST be answered with a CoA-NAK or a Disconnect-NAK (anchored §3.3; stated at §3)
- [ ] [RFC5176-3.5-3] [MUST] Response Authenticator MUST be computed per RFC 2865 Section 3 (§3.5) {single-polarity: positive; the NAS only emits CoA/Disconnect responses and never receives one, so there is no inbound Response Authenticator to reject; correctness is proven by verifying the emitted authenticator against radius.ResponseAuthenticator (internal/component/radius/packet.go:145)}
- [ ] [RFC5176-3.5-4] [MUST] Request Authenticator MUST be computed as MD5(Code + Identifier + Length + 16-zero-octets + Attributes + Secret) (§3.5)
- [ ] [RFC5176-2.3-1] [MUST] A packet received with an invalid Code field MUST be silently discarded (§2.3)
- [ ] [RFC5176-2.3-2] [MUST] A Dynamic Authorization Server MUST detect a duplicate request carrying the same source address, Identifier and Request Authenticator within a short span of time, and MUST answer it with the response the first copy earned (§2.3)
- [ ] [RFC5176-2.3-3] [MUST] Octets outside the range of the Length field MUST be treated as padding and ignored on reception, and a packet shorter than its Length field indicates MUST be silently discarded (§2.3)
- [ ] [RFC5176-2.3-4] [MUST] The Dynamic Authorization Server MUST use the source IP address of the RADIUS UDP packet to decide which shared secret to use (§2.3)
- [ ] [RFC5176-2.3-5] [MUST] Every attribute of a CoA-Request or Disconnect-Request MUST be treated as mandatory, so a request carrying an attribute the NAS does not support MUST be answered with a CoA-NAK or a Disconnect-NAK; a Disconnect-Request MUST carry only NAS and session identification attributes (§2.3, restated at §3)
- [ ] [RFC5176-2.3-6] [MUST] A CoA-Request whose authorization changes cannot all be carried out MUST be answered with a CoA-NAK and MUST leave the matching session unchanged, and a Disconnect-Request that cannot terminate the matching session MUST be answered with a Disconnect-NAK (§2.3)
- [ ] [RFC5176-2.3-7] [MUST] When the identification attributes match more than one session, a NAS that supports multi-session requests MUST apply the request to all of them, and a NAS that does not MUST answer with a CoA-NAK or a Disconnect-NAK (§2.3, with the apply-to-all branch stated at §3)
- [ ] [RFC5176-3.1-1] [MUST] The Dynamic Authorization Server MUST include the request's Proxy-State attributes in its response, unmodified, in the order they arrived, and treated as opaque data (§3.1)
- [ ] [RFC5176-3.2-1] [MUST] A NAS MUST answer a CoA-Request carrying a Service-Type Attribute whose value it does not support, "Authorize Only" included, with a CoA-NAK, and MUST NOT answer it with a CoA-ACK (§3.2, with the unsupported-value branch stated at §2.2)
- [ ] [RFC5176-3.3-2] [MUST] The Dynamic Authorization Server MUST NOT interpret the State Attribute locally, and MUST send it unmodified in the ACK or NAK it returns (§3.3)
- [ ] [RFC5176-3.4-1] [MUST] When the HMAC-MD5 message integrity check of a CoA-Request or Disconnect-Request is calculated, the Request Authenticator field and the Message-Authenticator Attribute MUST each be considered to be sixteen octets of zero (§3.4)
- [ ] [RFC5176-3.4-2] [MUST] The Message-Authenticator Attribute is calculated and inserted in the packet before the Request Authenticator is calculated, so the Request Authenticator MUST cover the Message-Authenticator value as sent (§3.4)
- [ ] [RFC5176-3.4-3] [MUST] A Dynamic Authorization Server receiving a CoA-Request or Disconnect-Request with a Message-Authenticator Attribute present MUST calculate the correct value of the Message-Authenticator and silently discard the packet if it does not match the value sent (§3.4)
- [ ] [RFC5176-3.4-4] [MAY] The Message-Authenticator Attribute MAY be used to authenticate and integrity-protect CoA-Request, CoA-ACK, CoA-NAK, Disconnect-Request, Disconnect-ACK and Disconnect-NAK packets in order to prevent spoofing, so a request that carries none is answered rather than discarded; the `require-message-authenticator` leaf turns its absence into a discard for an operator who wants the Blast-RADIUS mitigation (§3.4)
- [ ] [RFC5176-3.5-5] [MUST] An Error-Cause value in the 200-299 range MUST NOT be sent within a CoA-NAK or Disconnect-NAK, a value in the 400-599 range MUST NOT be sent within a CoA-ACK or Disconnect-ACK, 202 MUST NOT be sent by an implementation of this specification, 502 MUST NOT be sent by a NAS, 201 MUST NOT leave a packet other than a Disconnect-ACK and 504 MUST NOT leave a packet other than a Disconnect-NAK (§3.5)
- [ ] [RFC5176-3.6-1] [MUST] NAS and session identification attributes MUST NOT be used for a purpose other than identification, and the same Vendor-Specific Attribute MUST NOT serve identification and authorization change at the same time (§3.6)
- [ ] [RFC5176-6.1-1] [MUST] A Dynamic Authorization Server MUST silently discard Disconnect-Request or CoA-Request packets from untrusted sources, so a source that is not a configured Dynamic Authorization Client is refused; an EMPTY allow list means no configured server resolved and refuses every source rather than accepting all of them (§6.1)
- [ ] [RFC5176-6.3-1] [MUST] When an Event-Timestamp Attribute is present the Dynamic Authorization Server MUST check that it is current within an acceptable time window, and MUST silently discard the packet when it is not; that window MUST be the one used for duplicate detection (§6.3)
