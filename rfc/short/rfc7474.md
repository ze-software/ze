# RFC 7474 - Security Extensions for OSPFv2 when Using Manual Key Management

## Meta

| Field | Value |
|-------|-------|
| RFC | 7474 |
| Title | Security Extensions for OSPFv2 when Using Manual Key Management |
| Status | Proposed Standard |
| Date | April 2015 |
| Authors | M. Bhatia (Ionos Networks), S. Hartman (Painless Security), D. Zhang (Huawei), A. Lindem, Ed. (Cisco) |
| Updates | RFC 2328, RFC 5709 |
| Updated-by | None |

**Purpose:** Hardens the OSPFv2 cryptographic authentication mechanism (RFC 2328 Appendix D, extended by RFC 5709) against replay attacks when manual keying is used. It replaces the 32-bit per-packet sequence number with an extended 64-bit cryptographic sequence number so that replays cannot succeed across router reboots, adjacency resets, or sequence-number wrap, and it folds the IP source address into the digest so a spoofed source address is detected. It defines a new authentication type, AuType 3 ("Cryptographic Authentication with Extended Sequence Numbers").

**Scope:** Only the manual key management case is in scope (Phase 1 of the KARP working group, §8). Automatic key management is explicitly out of scope. Aside from changing the value of `Apad`, RFC 7474 introduces no other changes to the digest/HMAC machinery of RFC 5709 (§5); it reuses RFC 5709's algorithms, key database lifetimes (via RFC 7210), and First-Hash/Second-Hash construction. The checksum-zero rule for cryptographic auth is inherited unchanged from RFC 2328 Appendix D.3 / RFC 5709 (see Inherited Constraints below).

## Problem Being Solved (§1)

The RFC 2328 mechanism uses per-packet sequence numbers that "increase monotonically so that attempts to replay stale packets can be thwarted." (§1) Three gaps make this exploitable ([RFC6039] catalogues the attacks):

| Gap | Why it is exploitable (§1) |
|-----|-----------------------------|
| Sequence number is per-adjacency soft state | "if an adjacency is taken down, the associated sequence numbers get reinitialized and neighbor adjacency formation starts over again" -- enables **inter-session** (cross-reboot / cross-reset) replay |
| 32-bit space wraps | "the cryptographic authentication mechanism does not specify how to deal with the rollover of a sequence number when its value wraps" -- enables **intra-session** replay after wrap |
| IP header not covered by the digest | "The cryptographic authentication as described in [RFC2328] and later updated in [RFC5709] does not include the IP header... the source address in the IP header is not protected" -- enables source-address spoofing / reflection attacks |

Abstract framing: the mechanism "is vulnerable to both inter-session and intra-session replay attacks when using manual keying," and RFC 7474 "defines changes to the authentication sequence number mechanism that will protect OSPFv2 from both inter-session and intra-session replay attacks when using manual keys."

## Extended 64-bit Cryptographic Sequence Number (§2)

The 32-bit sequence number is expanded to 64 bits: "the OSPFv2 sequence number is expanded to 64 bits with the least significant 32-bit value containing a strictly increasing sequence number and the most significant 32-bit value containing the boot count." (§2)

### Sequence-number layout

| Word | Bits | Contents | Source / Rule (§2) |
|------|------|----------|--------------------|
| High-order | 63..32 (MSB) | Boot count | Retained in non-volatile storage; incremented each time the router loses prior sequence-number state (cold restart) and may be incremented on low-word wrap |
| Low-order | 31..0 (LSB) | Strictly increasing per-packet counter | MUST be incremented for every OSPF packet sent; reinitialized after a cold restart (the boot count increment preserves the aggregate strictly-increasing property) |

Wire placement: there is no room in the OSPFv2 packet for the 64-bit value, so "it will occupy the 8 octets following the OSPFv2 packet and MUST be included when calculating the OSPFv2 packet digest." (§2) These 8 octets are carried after the OSPF protocol packet (high-order word first, then low-order word) and before the authentication data; they are counted in the IP header length and the Authentication Data length but not in the OSPF packet header length (§3).

### Sender rules (§2)

| Rule | Normative text (§2) |
|------|----------------------|
| Per-packet increment | "The lower-order 32-bit sequence number MUST be incremented for every OSPF packet sent by the OSPF router." |
| Preserve strictly-increasing across cold restart | "OSPF routers implementing this specification MUST use available mechanisms to preserve the sequence number's strictly increasing property for the deployed life of the OSPFv2 router (including cold restarts)." |
| Boot count persistence | "OSPFv2 implementations are required to retain the boot count in non-volatile storage for the deployment life of the OSPF router." -- "This is achieved by maintaining a boot count in non-volatile storage and incrementing it each time the OSPF router loses its prior sequence number state." |
| Low-word wrap handling | "in the rare event that the lower-order 32-bit sequence number wraps, the boot count can be incremented to preserve the strictly increasing property of the aggregate sequence number." |
| Separate OSPF boot count | "a separate OSPF boot count is RECOMMENDED" (decouples SNMP reinitialization from OSPF reinitialization). |

### Receiver acceptance rules (§2)

Core replay check: "Upon reception, the sequence number MUST be greater than the sequence number in the last OSPF packet of that type accepted from the sending OSPF neighbor. Otherwise, the OSPF packet is considered a replayed packet and dropped." (§2) The comparison is over the full 64-bit value, so a boot-count bump after reboot/wrap always sorts ahead of any pre-reboot sequence number, defeating cross-reboot replay.

| Condition on received 64-bit seq | Action | Rationale (§2) |
|----------------------------------|--------|----------------|
| `recv > last_accepted[neighbor][packet_type]` | Accept; update stored high-water mark for that (neighbor, type) | "MUST be greater than the sequence number in the last OSPF packet of that type accepted" |
| `recv <= last_accepted[neighbor][packet_type]` | Drop as replay | "considered a replayed packet and dropped" |
| New (neighbor, packet type) with no prior state | NOT SPECIFIED by RFC 7474 (initialization of first-packet state is left to the implementation) | -- |

Per-type, per-neighbor state: the high-water mark is tracked **per OSPF packet type** because "OSPF packets of different types may arrive out of order if they are prioritized as recommended in [RFC4222]." A single per-neighbor counter would otherwise drop legitimately reordered packets of a different type.

## OSPF Header / Authentication Field Changes (§3)

RFC 7474 defines **Authentication type 3** (§3). The 64-bit Authentication field of the OSPF header (RFC 2328 Appendix D.3) is restructured: "The sequence number is removed and the Key ID is extended to 32 bits and moved to the former position of the sequence number." (§3) The leading reserved field grows: "The 0 field at the start of the OSPFv2 header authentication is extended from 16 bits to 24 bits." (§3)

| OSPF auth-field component (AuType 3, §3) | Width | Note |
|------------------------------------------|-------|------|
| Reserved `0` field | 24 bits | Extended from 16 bits |
| Auth Data Len | 8 bits | Length of trailing authentication data (includes the 8 sequence-number octets) |
| Key ID | 32 bits | Extended from 8 bits; occupies the former sequence-number position |

Layout on the wire: OSPF header (with AuType=3 auth field above) -> OSPF protocol packet -> 64-bit sequence number (8 octets) -> Authentication Data (the cryptographic hash).

## Key Selection and Rollover (§4)

Key selection reuses the RFC 7210-style key database with directional lifetimes; RFC 7474 does not define separate generate/accept state machines.

| Direction | Field set on packet / matched (§4) | Lifetime / direction constraints |
|-----------|-------------------------------------|----------------------------------|
| Send (unicast §4.1, multicast §4.2) | "The Key ID field in the OSPFv2 header... will be set to the selected key's LocalKeyName." | SendLifetime interval covers now; Direction "out" or "both"; matching interface; on multiple matches "the key with the most recent SendLifetimeStart will be selected" -- "This will facilitate graceful key rollover." |
| Receive (§4.3) | "The Key ID obtained from the OSPFv2 packet header corresponds to the neighbor's PeerKeyName." | AcceptLifetime interval covers now; Direction "in" or "both" |

Rollover model: a router may **send** under one Key ID while still **accepting** multiple Key IDs whose accept lifetimes overlap, allowing keys to be rotated without dropping in-flight adjacencies.

## IP-Header Protection and Digest Coverage (§5, §6)

RFC 7474 changes only the `Apad` value relative to RFC 5709: "Besides changing the value of Apad, this document does not introduce any other changes to the authentication mechanism described in [RFC5709]." (§5)

| Element | Text (§5 / §6) |
|---------|-----------------|
| Digest input | "RFC 5709, Section 3.3 describes how the cryptographic authentication must be computed. In RFC 5709, the First-Hash includes the OSPF packet and Authentication Trailer. With this specification, the 64-bit sequence number will be included in the First-Hash along with the Authentication Trailer and OSPF packet." (§5) |
| Apad base value | "Apad is a hexadecimal constant with the value 0x878FE1F3 repeated (L/4) times, where L is the length of the hash being used and is measured in octets rather than bits." (§5) |
| Apad first 4 octets (send) | "OSPF routers sending OSPF packets must initialize the first 4 octets of Apad to the value of the IP source address that would be used when sending the OSPFv2 packet." (§5) -- binds the IP source address into the digest |
| Apad first 4 octets (receive) | Receivers initialize the first 4 octets of `Apad` to the IP source address of the incoming packet; a spoofed source thus yields a digest mismatch (§5) |
| Cross-protocol defense | "In order to prevent cross-protocol replay attacks for protocols sharing common keys, the two-octet OSPFv2 Cryptographic Protocol ID is appended to the authentication key prior to use." (§6) |

## Inherited Constraints (from RFC 2328 / RFC 5709)

These are not redefined by RFC 7474 but apply whenever cryptographic authentication is in effect; RFC 7474 builds directly on them.

| Constraint | Origin | Note |
|------------|--------|------|
| OSPF packet **Checksum field MUST be 0** under cryptographic authentication | RFC 2328 Appendix D.3 (carried by RFC 5709) | The packet integrity is provided by the keyed digest, not the OSPF checksum; RFC 7474 itself does not restate this (the word "checksum" does not appear in RFC 7474), but AuType 3 is a cryptographic-auth type and inherits the rule |
| Authentication data / digest algorithms (HMAC-SHA family), First-Hash / Second-Hash construction | RFC 5709 §3.3 | Unchanged by RFC 7474 except for the `Apad` value (§5) |
| Key database with directional Send/Accept lifetimes | RFC 7210-style model referenced by §4 | Drives key selection and rollover |

## Security Considerations (§8)

Scope and residual risk:

| Point | Text (§8) |
|-------|-----------|
| KARP phase | "This document rectifies the manual key management procedure that currently exists within OSPFv2, as part of Phase 1 of the KARP Working Group." |
| Manual keys only | "Therefore, only the OSPFv2 manual key management mechanism is considered." -- "Any solution that takes advantage of the automatic key management mechanism is beyond the scope of this document." |
| Operational dependency | Replay protection across restarts depends on the boot count surviving in non-volatile storage; a router taken out of service and later reintroduced is the residual concern the boot count addresses. |

## Compliance Checklist

- [ ] [RFC7474-2-1] [MUST] Carry the 64-bit sequence number in the 8 octets following the OSPFv2 packet and include it when computing the digest (§2)
- [ ] [RFC7474-2-2] [MUST] Compose the 64-bit value as high-order boot count + low-order strictly increasing counter (§2) {single-polarity: positive; the 64-bit composition (boot count in the high word, per-packet counter in the low word) is a numeric construction property with no violating input to feed a negative test}
- [ ] [RFC7474-2-3] [MUST] Increment the lower-order 32-bit sequence number for every OSPF packet sent (§2) {single-polarity: positive; a monotonic send-side counter increment has no observable violating case, since every sent crypto packet advances it (and bumps the boot word on wrap)}
- [ ] [RFC7474-2-4] [MUST] Preserve the strictly increasing property of the aggregate sequence number for the deployed life of the router, including cold restarts (§2) {single-polarity: positive; strict-increase preservation across restarts is a durability property with no violating input to feed; it is asserted positively across a simulated restart via the persisted boot count}
- [ ] [RFC7474-2-5] [MUST] On receive, accept only when the sequence number is greater than the last accepted packet **of that type** from that neighbor; otherwise drop as a replay (§2)
- [ ] [RFC7474-2-6] [MUST] Track the accepted-sequence high-water mark per neighbor and per OSPF packet type (allows out-of-order arrival across types, §2)
- [ ] [RFC7474-3-1] [MUST] Set the OSPF Authentication field per AuType 3: 24-bit reserved `0`, 8-bit Auth Data Len, 32-bit Key ID in the former sequence-number position (§3)
- [ ] [RFC7474-5-1] [MUST] Include the 64-bit sequence number in the First-Hash along with the Authentication Trailer and OSPF packet (§5)
- [ ] [RFC7474-5-2] [MUST] Initialize the first 4 octets of `Apad` to the packet's IP source address (send and receive), remainder 0x878FE1F3 (§5)
- [ ] [RFC7474-6-1] [MUST] Append the two-octet OSPFv2 Cryptographic Protocol ID to the authentication key prior to use, to block cross-protocol replay (§6)
- [ ] [MUST (inherited)] Set the OSPF packet Checksum field to 0 when cryptographic authentication is in use (RFC 2328 App. D.3 / RFC 5709)
- [ ] [RFC7474-4.1-1] [SHOULD] On send, when multiple keys match, select the key with the most recent SendLifetimeStart to enable graceful rollover (§4.1)
- [ ] [RFC7474-2-7] [RECOMMENDED] Maintain a separate OSPF boot count in non-volatile storage (decouples SNMP and OSPF reinitialization) (§2)
- [ ] [RFC7474-2-8] [RECOMMENDED] Increment the boot count on cold restart and, if the low-order word wraps, to keep the aggregate sequence number strictly increasing (§2)
- [ ] [IMPL] Define behavior for the first packet from a new (neighbor, packet-type): RFC 7474 leaves initialization of received sequence-number state unspecified (§2)
