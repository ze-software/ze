## Purpose

Defines the SRV resource record, which lets a client discover the host(s) and
port offering a given service in a domain, with priority/weight load balancing.

## Owner name

`_Service._Proto.Name` (e.g. `_kerberos._tcp.example.`). `_Service` is the
symbolic service name, `_Proto` is usually `_tcp` or `_udp`, `Name` is the
domain the record refers to.

## RDATA format

```
Priority  Weight  Port  Target
```

- **Priority** — unsigned 16-bit (0..65535). Lower priority is tried first.
- **Weight** — unsigned 16-bit (0..65535). Relative weight among records of the
  same priority (load balancing). Weight 0 means no special weighting.
- **Port** — unsigned 16-bit (0..65535). The port the service runs on.
- **Target** — the canonical hostname of the machine providing the service. A
  domain name; MUST NOT be a name alias (no CNAME). A Target of `.` means the
  service is decidedly not available at this domain.

## How geodns applies this

- A host record of `type SRV` carries a `srv { priority; weight; port; target }`
  block. `priority`, `weight`, `port` are parsed as uint16 (0..65535); `target`
  is FQDN-normalised. All four are required — a missing field rejects the record
  (`parseSRV` in `internal/plugins/geodns/config.go`).
- geodns serves SRV answers verbatim; it does not perform the client-side
  priority/weight selection (that is the resolver/client's job).

## Compliance Checklist

RFC 2782 has named sections rather than numbered ones, so each requirement is
anchored to a single-word token drawn from its section/field heading
(`Applicability`, `Priority`, `Weight`, `Target`, `Usage`, `Notes`). The RFC
2119 definitions paragraph ("The key words MUST, MUST NOT, ...") is boilerplate,
not an obligation, and is not listed.

- [ ] [RFC2782-Applicability-1] [MUST] A protocol specification indicating SRV use MUST define the symbolic name to be used in the Service field of the SRV record (§Applicability) {not-applicable: this MUST binds the author of a protocol specification that adopts SRV to define the Service token; ze authors no such specification -- the _Service._Proto owner name is operator config data served verbatim (internal/plugins/geodns/config.go:319, server.go:111), not a name ze defines}
- [ ] [RFC2782-Applicability-2] [MUST] Such a specification MUST also include security considerations (§Applicability) {not-applicable: this is a security-considerations obligation on the author of an SRV-adopting protocol specification; ze publishes no such specification}
- [ ] [RFC2782-Priority-1] [MUST] A client MUST attempt to contact the target host with the lowest-numbered priority it can reach (§Priority) {not-applicable: ze implements no SRV-cognizant connecting client; geodns is authoritative and serves SRV verbatim without selection (internal/plugins/geodns/server.go:111), and internal/component/resolve/dns returns target:port strings without contacting or ordering by priority (resolver.go:321) -- no production code resolves TypeSRV}
- [ ] [RFC2782-Target-1] [MUST] There MUST be one or more address records for the Target name (§Target) {not-applicable: an SRV Target is an arbitrary FQDN that commonly lives outside any zone geodns is authoritative for, so geodns cannot require in-zone address records for it (internal/plugins/geodns/config.go:319); the address-record obligation belongs to the target's own authoritative zone}
- [ ] [RFC2782-Target-2] [MUST NOT] The Target name MUST NOT be an alias, in the sense of RFC 1034 or RFC 2181 (§Target) {not-applicable: geodns serves no CNAME record type (internal/plugins/geodns/record.go:10-14), so a geodns SRV Target can never resolve to a geodns-served alias; whether an external target name is a CNAME is outside geodns's authority}
- [ ] [RFC2782-Notes-2] [MUST] A client MUST parse all of the RRs in the reply (§Notes) {not-applicable: this parse-all-RRs MUST governs the SRV-cognizant client that locates and connects to servers; ze has no such client. internal/component/resolve/dns iterates every answer RR (resolver.go:299) but is a generic stub resolver surfacing data, not a connecting SRV client, and no production code drives it with TypeSRV}
- [ ] [RFC2782-Notes-3] [MUST] If the Additional Data section lacks address records for all the SRV RRs, the client MUST look up the missing address records before connecting (§Notes) {not-applicable: Additional-section address follow-up before connecting is a connecting-SRV-client obligation ze does not implement; internal/component/resolve/dns never reads the Additional section and never connects (resolver.go:299), and geodns as a server emits no target address glue for SRV answers (server.go:182-188)}
- [ ] [RFC2782-Applicability-3] [SHOULD NOT] Service SRV records SHOULD NOT be used in the absence of such a protocol specification (§Applicability)
- [ ] [RFC2782-Priority-2] [SHOULD] Target hosts with the same priority SHOULD be tried in an order defined by the weight field (§Priority)
- [ ] [RFC2782-Weight-1] [SHOULD] Larger weights SHOULD be given a proportionately higher probability of being selected (§Weight)
- [ ] [RFC2782-Weight-2] [SHOULD] Domain administrators SHOULD use Weight 0 when there is no server selection to do (§Weight)
- [ ] [RFC2782-Weight-3] [SHOULD] The specified ordering algorithm SHOULD be used to order the SRV RRs of the same priority (§Weight)
- [ ] [RFC2782-Usage-1] [SHOULD] A SRV-cognizant client SHOULD use the specified procedure to locate servers and connect to the preferred one (§Usage)
- [ ] [RFC2782-Notes-1] [SHOULD NOT] Port numbers SHOULD NOT be used in place of the symbolic service or protocol names (§Notes)
