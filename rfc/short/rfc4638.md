**Authors:** P. Arberg, D. Kourkouzelis, M. Duckett, T. Anschutz, J. Moisand
**Related:** RFC 2516 (PPPoE), RFC 1661 (PPP LCP MRU)

## Purpose

Lets a PPPoE client and server that sit on an Ethernet path carrying
baby-giant or jumbo frames negotiate a PPP MRU above the 1492 octets RFC 2516
imposes, by exchanging a PPP-Max-Payload tag during discovery.

## Wire Format

#### PPP-Max-Payload Tag

```
Tag-name:   PPP-Max-Payload
Tag-value:  0x0120
Tag-length: 2 octets
Tag-value:  binary encoded value (max PPP payload in octets)
```

| Field | Offset | Size | Type | Constraints |
|-------|--------|------|------|-------------|
| TAG_TYPE | 0 | 2 | uint16 | 0x0120 |
| TAG_LENGTH | 2 | 2 | uint16 | 2 |
| TAG_VALUE | 4 | 2 | uint16 | maximum PPP payload, comparable with the LCP MRU |

Carried by the client in PADI and PADR, echoed by a capable server in PADO
and PADS (§4).

## MRU selection (§5.1)

```
If PPPoE {
PPP_MRU_Max = 1492
If (PPP-Max-Payload-Tag) AND (PPP-Max-Payload-Tag > 1492)
Then PPP_MRU_Max = min (PPP-Max-Payload-Tag, Interface MTU-8)
}
"Normal" PPP_MRU_Negotiation (PPP_MRU_Max)
```

## Pitfalls

- **Interop**: echoing the tag in PADO tells the client the server supports a
  larger MRU. Ze echoes it while its LCP still caps the MRU at 1492, so a
  client that trusts the echo and asks for more in LCP is Nak'd back to 1492.
