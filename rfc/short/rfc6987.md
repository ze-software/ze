**Purpose:** Describes a technique by which an OSPF router advertises its
unavailability (or lowered preference) to forward *transit* traffic, while
remaining present in the topology so that its own directly attached IP
prefixes stay reachable. The router achieves this by setting the cost of all
non-stub links in its Router-LSA to a maximum value (`MaxLinkMetric`,
0xFFFF), so neighbours route *around* it during the SPF (Dijkstra)
calculation rather than *through* it (Abstract, §1, §2).

**Scope:** This is an Informational document; it defines no new protocol
messages, no new LSA types, and no new TLVs. It defines one architectural
constant, `MaxLinkMetric` (§3), and describes the operational behaviour and
deployment caveats of using it in OSPFv2 (RFC 2328). It also notes the
OSPFv3 R-bit (RFC 5340) as the analogous mechanism for OSPFv3 (§2.1). Vendors
expose this feature under the name "max-metric router-lsa" (Cisco/FRR) and as
"stub" in BIRD's OSPF protocol.

## Problem and Mechanism (§2)

A router that wants to stop carrying transit traffic faces two problems that
must be solved together (§2):

1. Make other routers prefer routes *around* this router during their
   Dijkstra calculation.
2. Still allow other routers to reach the IP prefixes directly connected to
   this router.

The mechanism: the router (call it X) originates its Router-LSA with the cost
of **all non-stub links** (Router-LSA link types *other than* type 3) set to
`MaxLinkMetric`. Stub links (type 3) are deliberately *not* raised: keeping
them at their real metric is what preserves reachability to X's own
directly-attached networks while transit drains away (§2). Because the
transit links carry the near-infinite cost but X remains a node in the graph,
any redundant path is preferred and traffic to X's stub prefixes still
resolves through X.

The technique only yields a benefit where the network has redundancy, so that
transit traffic actually has somewhere else to go (§1).

## Router-LSA Link-Metric Handling

Router-LSA link types are those defined in RFC 2328 §A.4.2. The table below
summarises how each is treated when advertising stub-router status (§2).

| Link Type | RFC 2328 meaning | Stub-router treatment | Effect |
|-----------|------------------|------------------------|--------|
| Type 1 | Point-to-point to another router | Cost set to `MaxLinkMetric` (0xFFFF) | Neighbour avoids transit over this link |
| Type 2 | Connection to a transit network (DR) | Cost set to `MaxLinkMetric` (0xFFFF) | Neighbour avoids transit through the segment via X |
| Type 3 | Connection to a stub network | **Left at real cost** (not raised) | X's own attached prefixes stay reachable |
| Type 4 | Virtual link | Cost set to `MaxLinkMetric` (0xFFFF) | Virtual-link transit avoided |

Per §2 the rule is literally "all non-stub links (links of the types other
than 3) being set to MaxLinkMetric"; type 3 stub-network links are the sole
excluded category and retain their configured cost. The RFC itself does *not*
prescribe `LSInfinity - 1` for stub prefixes; that is an implementation
convention some vendors (FRR `max-metric router-lsa ... on-startup`, when
configured to also raise summary/stub costs) offer as an extra knob, but the
baseline RFC 6987 behaviour is to keep type-3 links at their actual cost.

## MaxLinkMetric Constant (§3)

| Name | Value | Width | Definition |
|------|-------|-------|------------|
| `MaxLinkMetric` | 0xFFFF (65535) | 16 bits | Metric value indicating a Router-LSA link should not be used for transit traffic; defined as the 16-bit binary value of all ones (§3) |

This is the single normative-style definition the document adds. RFC 3137
described the same idea using the term `LSInfinity`, which created confusion
about whether a maxed-out link meant "infinite / unreachable" or merely "very
expensive." RFC 6987 replaces that with the explicit architectural constant
`MaxLinkMetric = 0xFFFF` to remove the ambiguity (§3, Appendix A).

## SPF Behaviour on Receiving Routers (§2, §4)

Receiving routers run their normal intra-area Dijkstra calculation. Because
X's transit links now carry `MaxLinkMetric`, any alternate path of normal cost
is cheaper, so routers converge on routes that bypass X for transit. X is *not*
removed from the link-state database, so its type-3 stub prefixes remain
reachable through it.

A subtle interoperability point (§4): older implementations following
RFC 1247 *discard* Router-LSA link records whose cost equals `MaxLinkMetric`
(treating them as unreachable), whereas RFC 1583 and later implementations
keep such links in the graph at the high cost (not treated as unreachable).
RFC 6987 notes this inconsistency does **not** cause routing loops: when any
alternate path exists, both kinds of router agree on using it rather than the
path through the stub router. The two flavours only differ in the corner case
where the stub-router path is the *only* path.

## OSPFv3 R-bit (§2.1)

OSPFv3 (RFC 5340) provides an additional, cleaner control: the R-bit in the
Router-LSA Options indicates whether a router is active and should be used for
transit. Clearing the R-bit signals "do not use me for transit" without
relying on metric manipulation. RFC 6987 records this as the OSPFv3-native
equivalent; the `MaxLinkMetric` technique remains the OSPFv2 approach.

## Canonical Use Cases (§1)

| Use case | Trigger | Behaviour |
|----------|---------|-----------|
| Startup convergence | Router reboots; IGP up but BGP/RIB not yet converged | Advertise stub-router until BGP/edge protocols converge, so traffic is not blackholed through a router with an incomplete RIB; then revert to real metrics |
| Planned maintenance / graceful shutdown | Operator removing a router from service | Advertise stub-router first so transit drains away gracefully before the router is taken down |
| Critical condition | High CPU / low memory | Shed transit load while staying reachable |
| Administrative / traffic engineering | Operator policy | Lower preference for paths through this router |

The startup case is the headline operational driver: a freshly booted transit
router that participates in OSPF before its BGP sessions are established would
otherwise attract transit traffic it cannot forward. Advertising stub-router
status on startup (commonly with a timer or until BGP signals convergence)
prevents that blackhole.

## Differences from RFC 3137 (Appendix A)

| Aspect | RFC 3137 | RFC 6987 |
|--------|----------|----------|
| Max value naming | `LSInfinity` (ambiguous: infinite vs expensive) | `MaxLinkMetric` = 0xFFFF, explicit constant (§3) |
| Stub-link handling | Underspecified | Explicit: only non-stub (non-type-3) links raised (§2) |
| OSPFv3 | Not covered | R-bit documented as OSPFv3 equivalent (§2.1) |
| Status | Informational | Informational; obsoletes RFC 3137 |

Both RFCs use the same 0xFFFF value on transit links; RFC 6987 is primarily a
clarification and re-specification, not a behaviour change.

## Compliance Checklist

- [ ] [BEHAVIOUR] When advertising stub-router status, set the cost of all non-stub Router-LSA links (types 1, 2, 4) to `MaxLinkMetric` 0xFFFF (§2, §3)
- [ ] [BEHAVIOUR] Leave type-3 stub-network links at their real configured cost so directly-attached prefixes stay reachable (§2)
- [ ] [CONSTANT] Use `MaxLinkMetric` = 0xFFFF (65535) as the transit-link cost, not an `LSInfinity`-derived value (§3)
- [ ] [BEHAVIOUR] Keep the router in the LSDB; do not withdraw the Router-LSA (the router stays in the topology) (§1, §2)
- [ ] [USE] Support advertising stub-router on startup until BGP/edge convergence, then revert to real link costs (§1)
- [ ] [USE] Support advertising stub-router for planned maintenance / graceful shutdown to drain transit (§1)
- [ ] [INTEROP] Do not treat `MaxLinkMetric` links as unreachable on receipt; follow RFC 1583+ Dijkstra (keep the link at high cost) (§4)
- [ ] [INTEROP] Confirm no routing loops arise from mixed RFC 1247 / RFC 1583 receivers; rely on alternate paths being agreed by both (§4)
- [ ] [OSPFv3] For OSPFv3, prefer the R-bit (RFC 5340) to signal transit unavailability rather than metric manipulation (§2.1)
