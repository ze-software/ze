# RFC 2181 — Clarifications to the DNS Specification

Implementation-relevant summary. Full text: https://www.rfc-editor.org/rfc/rfc2181

## Scope

Corrects and clarifies parts of RFC 1034/1035 that implementations interpreted
inconsistently. The points geodns relies on are TTL handling (section 8) and
RRSet TTL consistency (section 5.2).

## Section 5.2 — TTLs of RRs in an RRSet

All resource records in an RRSet (same name, class, type) **should** have the
same TTL. If they differ (e.g. loaded from different sources), a receiver must
treat the set as if all TTLs were the lowest of the set. geodns assigns one TTL
per host record line, so an A/AAAA set it emits already shares a TTL.

## Section 8 — Time to Live (TTL)

- The TTL field is an unsigned number.
- "The maximum value is 2147483647, that is, the largest number that can be
  represented in an unsigned 31-bit integer." (2^31 − 1)
- Although RFC 1035 §3.2.1 defines the TTL field as 32 bits, the top (sign) bit
  must be zero on the wire, narrowing the valid range to **0 .. 2147483647**.
- A resolver that receives a TTL with the top bit set should treat it as zero.
  As an authoritative server reading a config file, geodns instead **rejects** a
  configured TTL outside 0..2147483647 rather than silently zeroing it, so a
  typo is surfaced rather than served.

## How geodns applies this

- `default-ttl` and each host `ttl` leaf are bounded to `0..2147483647`
  (`parseTTL` in `internal/plugins/geodns/config.go`); out-of-range values abort
  the commit.
- The YANG leaves use `type uint32 { range "0..2147483647"; }` so native
  validation also enforces the bound.
