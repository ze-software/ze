# RFC 7858 — DNS over TLS (DoT)

**Status:** Proposed Standard
**Date:** May 2016
**Authors:** Z. Hu, L. Zhu, J. Heidemann, A. Mankin, D. Wessels, P. Hoffman

## Purpose

Specifies how to run DNS message exchange over a TLS-encrypted TCP
connection, so on-path observers cannot read or tamper with queries and
answers. Only the transport is new: the DNS messages inside are exactly the
DNS-over-TCP framing of RFC 1035 / RFC 7766.

## Transport (§3.1, §3.2)

| Property | Value |
|----------|-------|
| Well-known port | **853** (TCP), IANA-assigned "domain-s" |
| Transport | TLS 1.2+ over TCP |
| Message framing | RFC 1035 §4.2.2 / RFC 7766: a 2-octet big-endian length prefix, then the DNS message |
| Session reuse | Connections are long-lived and reused (RFC 7766); pipelining and out-of-order responses are permitted |

A DoT client connects to TCP port 853, completes the TLS handshake, then
sends length-prefixed DNS messages. A server offering DoT MUST NOT use port
53 for TLS; port 53 stays cleartext DNS.

## Requirements (RFC 2119 keywords)

- **MUST** use the well-known port 853 unless both parties have mutually
  agreed to another port (§3.1).
- Clients and servers **MUST** implement the length-prefixed framing of
  RFC 7766 (§3.3).
- Servers **SHOULD** support connection reuse and idle-connection timeouts to
  amortize the TLS handshake cost (§3.4).
- A client that keys on the response ID **MUST** be able to match out-of-order
  responses on a shared connection (§3.3).

## Authentication profiles (§4, refined by RFC 8310)

RFC 7858 defines two usage profiles; the authentication policy is the
client's choice, not the server's:

| Profile | Meaning |
|---------|---------|
| Opportunistic privacy | Encrypt when possible; do not fail if the server cannot be authenticated. Protects against passive observation only. |
| Out-of-band key-pinned | The client pins the server's SPKI (SubjectPublicKeyInfo) hash and refuses a mismatch. |

RFC 8310 later adds strict authentication by an Authentication Domain Name
(the server certificate must validate for a configured hostname).

## How ze applies this

- The authoritative DNS harness (`internal/core/dnsserver`) binds an optional
  DoT listener: a TCP listener wrapped with `crypto/tls` (`tls.NewListener`)
  handed to the miekg/dns `Server{Listener}`, which already speaks the RFC 7766
  length-prefixed framing. The same `dns.Handler` serves cleartext DNS, DoT,
  and DoH, so answer policy is identical across transports.
- The DoT port defaults to **853** and is operator-configurable per listener
  (`tls { listen-port }`). Cleartext UDP/TCP on port 53 (as112) or the geodns
  listener ports is unaffected when DoT is enabled.
- ze is the DoT **server**. Certificate material is operator-provided PEM
  (`tls { cert-file / key-file }`) or, absent that, a self-signed certificate
  from `internal/core/selfcert` (the same helper the web UI uses). A
  `ze doctor` check reports certificate validity and near-expiry.
- Client authentication policy (opportunistic vs pinned vs strict) is the
  querying resolver's concern; ze presents a normal server certificate and
  does not require client certificates.

## Notes

- DoT is TCP-only. There is no UDP variant; the harness binds only a TCP+TLS
  listener for DoT (no UDP counterpart), unlike cleartext DNS which binds both.
- Because self-signed material cannot be validated by a strict client, the
  operator either supplies a CA-issued cert or the client uses opportunistic /
  pinned mode.
