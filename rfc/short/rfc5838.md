# RFC 5838 - Support of Address Families in OSPFv3

## Meta

| Field | Value |
|-------|-------|
| RFC | 5838 |
| Title | Support of Address Families in OSPFv3 |
| Status | Standards Track |
| Date | April 2010 |
| Authors | A. Lindem, S. Mirtorabi, A. Roy, M. Barnes, R. Aggarwal |
| Obsoletes | None |
| Updates | None |
| Updated by | RFC 6969, RFC 7949, RFC 8362, RFC 9454 |

**Purpose:** Extends OSPFv3 so multiple address families can be carried by
separate OSPFv3 instances. The mapping is based on the Instance ID field in
the OSPFv3 packet header.

**Scope for Ze:** This is an out-of-scope marker for the first `ospfv3`
follow-up. Initial OSPFv3 support should implement IPv6 unicast only. Keep
Instance ID plumbing clean so IPv4 unicast over OSPFv3 can be added later
without redesigning the LSDB or config model.

## Mechanism

RFC 5340 already includes an Instance ID field with link-local significance.
RFC 5838 assigns Instance ID ranges and rules so different address families
can use separate OSPFv3 instances on the same link. Each address family has a
separate link-state database, which simplifies operation and debugging.

| Concept | Rule |
|---------|------|
| Instance mapping | Address family maps to an OSPFv3 Instance ID |
| LSDB | Separate LSDB per address family instance |
| Base IPv6 unicast | Remains the default OSPFv3 address family |
| Other AFs | IPv4 unicast, IPv6 multicast, and IPv4 multicast are extensions |
| Configuration | Existing instance, area, and interface model is reused with AF-specific instance selection |

## Processing Consequences

| Area | Consequence |
|------|-------------|
| Packet receive | Instance ID validation must happen before packet-specific processing |
| Neighbor state | Neighbor state is per instance, not just per link |
| LSDB | LSDB keying must include instance or an owning protocol context |
| Route install | Address family determines Loc-RIB family and next-hop handling |
| Debugging | Show commands must identify the address-family instance if multi-AF is enabled later |

## Out-of-Scope Decision for First Ze OSPFv3

The first Ze OSPFv3 implementation should not carry IPv4 routes in OSPFv3.
Reasons:

- It is not required for IPv6 OSPFv3 interoperability with FRR `ospf6d`.
- It expands next-hop calculation and redistribution semantics before the base
  protocol is proven.
- It risks coupling IPv4 OSPFv2 and OSPFv3 route policy too early.

Implementation guardrail: define Instance ID as a validated field from day
one, but restrict accepted configured address family to IPv6 unicast until a
separate RFC 5838 spec is opened.

## Compliance Checklist (implemented by spec-ospf-ext-15)

- [x] [CONFIG] Add address-family-specific OSPFv3 instance configuration
      (`ospf { address-family { ipv6-unicast | ipv6-multicast | ipv4-unicast | ipv4-multicast { instance-id N; ... } } }`)
- [x] [INSTANCE] Enforce the RFC 5838 Instance ID ranges for each address family
      (§2.1 ranges 0-31/32-63/64-95/96-127; native YANG range + `validateConfig` `ErrInstanceIDRange`)
- [x] [LSDB] Keep a separate LSDB per address family instance
      (one v6-codec engine per AF; each owns a private LSDB/neighbors/SPF)
- [x] [NEIGHBOR] Keep neighbor adjacency state per address family instance
      (per-instance neighbor table; the AF-bit gates Full for non-default AFs, §2.5/§2.6)
- [x] [ROUTES] Install routes into the correct Loc-RIB family with correct next-hop semantics
      (`NewInstallerFamily`; IPv4-over-OSPFv3 next-hop from the adjacency, §2.7)
- [x] [CLI] Display address family and Instance ID in OSPFv3 show commands (`show ospf ipv6`)
- [x] [INTEROP] Add FRR `ospf6d` multi-AF interop scenarios (`ospf-multiaf-frr`,
      `ospf-multiaf-v4-frr`; the IPv4-AF leg falls back to Ze<->Ze per the assumption that
      FRR ospf6d lacks the IPv4 AF)

The AF-bit (§2.4) lives at `internal/plugins/ospf/v3/types/options.go` (`OptAF = 0x000100`),
is emitted in Hello/DD by `encoder_v6.go`, and gated on receive by `multiaf.go`
(`afHelloAccepted`). The Instance-ID-range to AF mapping is `afFromInstanceID` in `multiaf.go`.
