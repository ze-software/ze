**Purpose:** RFC 1195 ("Integrated" or "Dual" IS-IS) extends the OSI
Intermediate System to Intermediate System (IS-IS) routing protocol (ISO
10589) so that a single intra-domain routing protocol can carry IP routing
information alongside OSI (CLNP) routing information. It adds IP-specific
variable-length fields to the existing IS-IS PDUs without changing the base
PDU formats (Abstract, Section 1.3).

**Scope:** This summary covers the IP-specific fields RFC 1195 adds to IS-IS
PDUs: the new code points (128 IP Internal Reachability, 129 Protocols
Supported, 130 IP External Reachability, 131 Inter-Domain Routing Protocol
Information, 132 IP Interface Address, 133 Authentication Information), their
wire layouts, the metric fields (default / delay / expense / error), and the
rules for pure-IP, pure-OSI, and dual operation. The OSI base protocol
itself is specified in ISO 10589 and is out of scope here.

## Encoding of Variable-Length Fields

All IP-specific information is carried in IS-IS PDUs as variable-length
fields using a Code, Length, Value triplet (Section 3.1, Section 5.2,
Figure 3):

```
                                  No. of Octets
+---------------------------+
|           CODE            |      1
+---------------------------+
|          LENGTH           |      1
+---------------------------+
|           VALUE           |    LENGTH
+---------------------------+
```

| Field | Size | Meaning |
|-------|------|---------|
| Code | 1 octet | Identifies the field type |
| Length | 1 octet | Length of the Value field, 0 to 254 octets (Section 3.1) |
| Value | Length octets | Field contents |

Rules (Section 3.1, Section 5.2):

- "Any codes in a received PDU that are not recognised shall be ignored
  and, for those packets which are forwarded (specifically Link State
  Packets), passed on unchanged." This applies to OSI-only, IP-only, and
  dual routers alike, and is what lets IP and OSI information coexist in
  the same PDU.
- Except where explicitly stated otherwise, the variable-length fields may
  occur in any order.
- Bit/octet numbering (Section 5.3): octets are numbered from 1 in
  increasing order. Within an octet, bits are numbered 1 to 8 where bit 1
  is the least significant (pictured on the right). For multi-octet
  numbers, the lower-numbered octet is the most significant.

## IP-Specific Code Points

| Code | Field | Appears in |
|------|-------|------------|
| 128 | IP Internal Reachability Information | LSPs (Level 1 and Level 2), not pseudonode LSPs |
| 129 | Protocols Supported | Hellos and LSP number 0; ISO 9542 ISHs over point-to-point links |
| 130 | IP External Reachability Information | Level 2 LSPs only, not pseudonode LSPs |
| 131 | Inter-Domain Routing Protocol Information | Level 2 LSPs only, not pseudonode LSPs |
| 132 | IP Interface Address | Hellos (once) and LSPs |
| 133 | Authentication Information | All IS-IS PDUs (optional) |

(Section 5.2, Section 5.3.1 through Section 5.3.5.)

## Protocols Supported (Code 129)

Identifies the set of Network Layer protocols the IS is capable of relaying,
using one-octet NLPID (Network Layer Protocol Identifier) values assigned by
ISO/TR 9577 (Section 3.1, Section 5.3.x).

```
                                  No. of Octets
+----------------------------+
|           NLPID            |      1
+----------------------------+
:                            :
+----------------------------+
|           NLPID            |      1
+----------------------------+
```

| Field | Size | Meaning |
|-------|------|---------|
| Code | 1 octet | 129 |
| Length | 1 octet | Total length of the value field (one octet per protocol supported) |
| NLPID | 1 octet each | ISO/TR 9577 registered Network Layer Protocol Identifier, one per supported data protocol |

Rules (Section 3.1, Section 5.2):

- NLPID is a one-octet value assigned by ISO to identify network-level
  protocols. NLPID values have been assigned to ISO 8473 (CLNP) and to IP.
  (The RFC text states that values are assigned but does not list the
  numeric NLPID values in the body covered here.)
- The Protocols Supported field MUST be included in all IS-IS Hello packets
  and all LSPs with LSP number 0 transmitted by IP-capable routers. It MUST
  also be included in ISO 9542 ISHs sent by IP-capable routers over
  point-to-point links to other IS-IS routers.
- If this field is not present in a Hello or in an LSP with LSP number 0,
  the packet may be assumed to come from an OSI-only router.

## IP Interface Address (Code 132)

Carries the IP address(es) of the router's interfaces (Section 5.2,
Section 5.3.1, Section 5.3.4).

```
                                  No. of Octets
+----------------------------+
|         IP ADDRESS         |      4
+----------------------------+
:                            :
+----------------------------+
|         IP ADDRESS         |      4
+----------------------------+
```

| Field | Size | Meaning |
|-------|------|---------|
| Code | 1 octet | 132 |
| Length | 1 octet | Total length of the value field (four octets per address) |
| IP ADDRESS | 4 octets each | 4-octet IP address |

Rules (Section 5.2, Section 4.2):

- In Hello packets the field occurs once only and contains the IP
  address(es) of the interface over which the Hello is sent, up to a maximum
  of 63 IP addresses per interface.
- If a Hello is sent over an interface with no IP address assigned, the
  field MAY be omitted or included with zero entries.
- In LSPs the field contains one or more IP addresses of interfaces of the
  originating router. Each IP-capable router MUST include this field in its
  LSPs; it may occur multiple times and in an LSP with any LSP number.
- A router that is both a Level 1 and a Level 2 router MUST include the same
  IP address(es) in its Level 1 and Level 2 LSPs.

## IP Internal Reachability Information (Code 128)

Lists [IP address, subnet mask, metrics] entries within the routing domain
reachable by the originating router (Section 5.3.4, Section 5.3.5). Each
entry is 12 octets, so the field Length is a multiple of 12.

```
                                  No. of Octets
+----------------------------+
| 0 |I/E|   DEFAULT METRIC   |      1
+----------------------------+
| S | R |    DELAY METRIC    |      1
+----------------------------+
| S | R |   EXPENSE METRIC   |      1
+----------------------------+
| S | R |    ERROR METRIC    |      1
+----------------------------+
|         IP ADDRESS         |      4
+----------------------------+
|        SUBNET MASK         |      4
+----------------------------+
   (entry repeats)
```

| Field | Size | Meaning |
|-------|------|---------|
| Code | 1 octet | 128 |
| Length | 1 octet | A multiple of 12 |
| DEFAULT METRIC | 1 octet | Bit 8 reserved (set to 0 on transmission, ignored on reception); bit 7 (I/E) is the metric type for all four TOS metrics and MUST be set to 0 (internal); remaining 6 bits hold the metric value |
| DELAY METRIC | 1 octet | Bit "S" = 1 if metric unsupported; bit 7 reserved (0 on transmission, ignored on reception); 6-bit value |
| EXPENSE METRIC | 1 octet | Bit "S" = 1 if metric unsupported; bit 7 reserved; 6-bit value |
| ERROR METRIC | 1 octet | Bit "S" = 1 if metric unsupported; bit 7 reserved; 6-bit value |
| IP ADDRESS | 4 octets | 4-octet Internet address |
| SUBNET MASK | 4 octets | 4-octet IP subnet mask |

Rules (Section 5.3.4, Section 5.2):

- For IP Internal Reachability the I/E bit MUST be set to 0 (internal
  metrics only).
- This field MUST NOT appear in pseudonode LSPs. It may appear multiple
  times and in an LSP with any LSP number.
- Each entry MUST contain a default metric and MAY contain delay, expense,
  and error metrics.
- In Level 1 LSPs this field includes only entries directly reachable by
  the originator via one of its interfaces. In Level 2 LSPs it includes
  entries reachable either directly or indirectly via Level 1 routing.

## IP External Reachability Information (Code 130)

Lists [IP address, subnet mask, metrics] entries reachable outside the
routing domain (Section 5.3.5). The entry layout is identical to Code 128
(12 octets per entry, Length a multiple of 12).

| Field | Size | Meaning |
|-------|------|---------|
| Code | 1 octet | 130 |
| Length | 1 octet | A multiple of 12 |
| DEFAULT METRIC | 1 octet | Bit 8 reserved; bit 7 (I/E) is the metric type for all four TOS metrics and MAY be 0 (internal) or 1 (external); 6-bit value |
| DELAY / EXPENSE / ERROR METRIC | 1 octet each | Same encoding as Code 128 (bit "S" = unsupported, bit 7 reserved, 6-bit value) |
| IP ADDRESS | 4 octets | 4-octet Internet address |
| SUBNET MASK | 4 octets | 4-octet IP subnet mask |

Rules (Section 5.3.5, Section 5.2, Section 3.4):

- The I/E bit MAY indicate internal or external metrics for the default
  metric. This is the key difference from Code 128, where I/E MUST be 0.
- This field may be present in Level 2 LSPs transmitted by Level 2
  IP-capable routers. It MUST NOT appear in pseudonode LSPs. It may appear
  multiple times and in an LSP with any LSP number.
- A route defined solely using internal metrics is always preferred to any
  route defined using external metrics. When external metrics are used, the
  lowest external metric is preferred regardless of the internal cost to
  reach the exit point (Section 3.4).

## Inter-Domain Routing Protocol Information (Code 131)

Carries inter-domain routing protocol information transparently through
Level 2 for the convenience of a border (inter-domain) protocol; it is not
used by IS-IS itself (Section 5.3.5, Section 3.4, Annex A).

```
                                     No. of Octets
+-------------------------------+
| Inter-Domain Information Type |      1
+-------------------------------+
|     External Information      |   VARIABLE
+-------------------------------+
```

| Field | Size | Meaning |
|-------|------|---------|
| Code | 1 octet | 131 |
| Length | 1 octet | Total length of the value field |
| Inter-Domain Information Type | 1 octet | Type of the external information encoded in the field |
| External Information | variable | Inter-domain routing protocol information, passed transparently by IS-IS |

Rules (Section 3.4, Section 5.3.5):

- Carried in Level 2 LSPs, stored by all Level 2 routers, but used only by
  those Level 2 routers directly involved in external routing.
- MUST NOT be included in pseudonode LSPs.
- Initial values for the Inter-Domain Information Type field are specified
  in Annex A.

## Authentication Information (Code 133)

```
+---------------------------+
|           CODE = 133      |
+---------------------------+
|          LENGTH           |
+---------------------------+
|           VALUE           |
+---------------------------+
```

| Field | Size | Meaning |
|-------|------|---------|
| Code | 1 octet | 133 |
| Length | 1 octet | Total length of the value field |
| Value | variable | Authentication data (TBD in the base text; a proposed use is in Annex D) |

Rules (Section 3.9):

- The authentication field is optional in all IS-IS PDUs (including ISO 9542
  IS Hellos).
- The authentication information in each packet authenticates the entire
  packet, including both OSI and IP parts.
- If a packet with invalid authentication information is received, the
  entire packet MUST be discarded.
- If an LSP or SNP is split into multiple packets, each is authenticated
  independently.
- Routers are not required to interpret authentication information; a router
  that does not implement it ignores any authentication field present.

## Metric Fields and Type of Service

RFC 1195 carries four metrics per reachability entry (Section 3.5):

| Metric | Role |
|--------|------|
| Default | Throughput; the commonly used metric. Every entry MUST carry it |
| Delay | Delay TOS metric (optional) |
| Expense | Expense TOS metric (optional) |
| Error | Residual error probability TOS metric (optional) |

- Each metric occupies one octet. The low 6 bits hold the value; for the
  default metric, bit 8 is reserved and bit 7 is the I/E (internal/external)
  type. For delay, expense, and error metrics, bit "S" marks the metric as
  unsupported and bit 7 is reserved.
- The maximum metric value reportable is 63. When summing metrics for Level
  2 advertisement would exceed 63, the value 63 MUST be used (Section 3.2).
- TOS support is optional. If no path of routers all supporting the
  requested TOS exists, packets are forwarded using the default metric
  instead (Section 3.5).
- IP has no cost TOS, so there is no IP TOS mapping to a minimum-cost metric
  (Section 3.5). The IP TOS field maps as: low delay -> delay metric, high
  reliability -> reliability (error) metric, all other combinations ->
  default metric (Section 3.5).

## Dual (IP + CLNP) Operation

RFC 1195 defines three routing-domain types (Section 1.4):

| Domain | Rule |
|--------|------|
| Pure IP | All routers MUST be IP-capable. IP-only and dual routers may be freely mixed. Only IP traffic is routed; OSI traffic may be discarded (except IS-IS PDUs) |
| Pure OSI | All routers MUST be OSI-capable. OSI-only and dual routers may be freely mixed. Only OSI traffic is routed; IP traffic may be discarded |
| Dual | IP-only, OSI-only, and dual routers may be mixed on a per-area basis. Each area may itself be pure IP, pure OSI, or dual |

Additional dual-environment rules (Section 1.4, Section 3.7):

- In a dual area within a dual routing domain, only dual routers may be
  used.
- Within a dual domain, if both IP and OSI traffic are to be routed between
  areas, then all Level 2 routers MUST be dual.
- IP-only routers leave the IS-IS PDU formats unchanged but may omit some
  OSI-specific variable-length fields. Specifically, in LSPs the "End
  Systems Neighbours" and "Prefix Neighbours" entries are omitted; Hellos
  and Sequence Number Packets are unchanged (Section 3.7).
- The Dijkstra computation does not distinguish IP-only, OSI-only, or dual
  routers; each IP reachability entry [IP address, subnet mask] is treated
  much like an OSI end system, using a 64-bit equality test instead of the
  48-bit test used for OSI end systems (Section 3.10).

## Reachability Preference (Dijkstra)

- An "IP reachability entry" is the combination [IP address, subnet mask]
  (Section 3.10). Two entries are the same if and only if the subnet masks
  are identical and the address bits selected by the mask are identical.
- Order of preference within an area considers route specificity and TOS:
  routes on which the requested TOS is supported are preferred to routes on
  which it is not; when the requested TOS is unsupported on a route, the
  default metric is used (Section 3.10.1, Section 3.10.2).
- Routes learned via Level 1 routing are preferred to routes learned via
  Level 2 routing for destinations reachable both ways within the area
  (Section 3.10.1).
- Internal-metric routes are always preferred over external-metric routes
  (Section 3.4, Section 3.10.2).

## MUST / MUST NOT Summary

- Protocols Supported (Code 129) MUST be included in all IS-IS Hellos, all
  LSPs with LSP number 0, and ISO 9542 ISHs over point-to-point links sent
  by IP-capable routers (Section 5.2).
- IP Interface Address (Code 132) MUST be included by every IP-capable
  router in its LSPs; a Level 1 + Level 2 router MUST advertise the same IP
  address(es) at both levels (Section 5.2).
- IP Internal Reachability (Code 128): the I/E bit MUST be 0; the field MUST
  NOT appear in pseudonode LSPs (Section 5.3.4).
- IP External Reachability (Code 130) and Inter-Domain Routing Protocol
  Information (Code 131) MUST NOT appear in pseudonode LSPs (Section 5.3.5,
  Section 3.4).
- Each reachability entry MUST contain a default metric (Section 5.2).
- A Level 2 metric sum that exceeds 63 MUST be reported as 63 (Section 3.2).
- A packet with invalid authentication information MUST be discarded
  (Section 3.9).
- Unrecognised codes MUST be ignored and, in forwarded LSPs, passed on
  unchanged (Section 3.1).


## Current implementation scope

On 2026-09-21 the owner selected "Keep specific prefixes" and "Do not originate
IDRPI". RFC 1195 section 3.2 says, "Each level 2 router may be configured with
one or more [IP address, subnet mask, metric] entries". Ze has no manual-summary
configuration or producer; `spf.LeakPrefixes` selects specific reachable
prefixes and `lsdb.Originator.fragmentTLVs` emits them. Duplicate specific
prefixes still require one minimum-metric L2 entry.

Section 5.2 says the IDRPI field "may be present" and "is not used by the IS-IS".
Ze has no IDRPI producer or consumer. `packet.DecodeTLVs` retains an unknown
TLV 131 for unchanged flooding, while `spf.addTLVs` ignores it. This is the
selected absence of an optional IDRPI role, rather than a claim that its AS
association semantics have been implemented.

The narrow-metric wire rules are read with RFC 2966: bit 8 of the default
metric is the up/down bit, and a TLV 128 entry with external metric type is
ignored. Bit 7 of each optional metric remains reserved.
