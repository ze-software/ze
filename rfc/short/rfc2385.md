**Purpose:** Defines TCP option Kind 19, which carries an MD5 digest computed over
the TCP pseudo-header, the TCP header, the segment data and a shared key. A receiver
that holds the same key recomputes the digest and drops a segment that does not match,
which keeps a spoofed segment, and in particular a spoofed RST, out of a BGP session.

**Register:** the document predates RFC 2119 and writes every obligation in lowercase
(`must`, `must not`, `strongly recommended`). It cites RFC 2119 nowhere and carries no
capitalized MUST-level keyword, so the extraction sign-off derives register `prose`.
The rows below are gated at the level the sentence states, not at the level its
capitalization suggests.

## Wire Format

The option is fixed length. It appears in every segment of a protected connection.

```
             +---------+---------+-------------------+
             | Kind=19 |Length=18|   MD5 digest...   |
             +---------+---------+-------------------+
             |                                       |
             +---------------------------------------+
             |                                       |
             +---------------------------------------+
             |                                       |
             +-------------------+-------------------+
             |                   |
             +-------------------+
```

| Field | Offset | Size | Type | Constraints |
|-------|--------|------|------|-------------|
| Kind | 0 | 1 | uint8 | 19 |
| Length | 1 | 1 | uint8 | 18, the whole option including Kind and Length |
| MD5 digest | 2 | 16 | opaque | always 16 octets |

## Digest Computation

MD5 is applied to these items, in this order, with the header and pseudo-header in
network byte order:

1. the TCP pseudo-header: source IP address, destination IP address, zero-padded
   protocol number, segment length
2. the TCP header excluding options, with the checksum field taken as zero
3. the TCP segment data, if any
4. the key, known to both TCPs and presumably connection-specific

## Validation

| Check | Valid | Invalid Action |
|-------|-------|----------------|
| Digest in a received segment | equals the digest the receiver computes with its own key | drop the segment, send nothing back |
| Option absent from the peer's SYN,ACK | does not change the local decision to sign | never disable signing |
| Key length | whatever the local TCP accepts; 80 printable ASCII octets is the recommended floor | reject the configuration |

## Some Implications

- A connectionless reset carries no valid digest, so it is ignored. A connect attempt
  to a port with no listener times out rather than being refused, and a stale-connection
  RST no longer clears the session quickly.
- The option costs 18 octets in every segment, so the MSS offered at connection setup
  must leave room for it, and the whole option list still has to fit in the 40 octets
  the TCP data-offset field leaves.
- MD5 is weak against collision search. The option carries no algorithm-type field, so
  no upgrade path exists inside Kind 19.

## How Ze Implements It

Ze does not compute or verify a digest. It installs the key on the socket and the
kernel signs and validates every segment, which is the same route Ze takes for TCP
itself. The whole stack is what conformance is judged on
(`ai/rules/rfc-compliance.md`), so the rows below are met through the kernel and the
tests assert the thing Ze produces: the key Ze installs, on the sockets Ze opens,
before the handshake.

| Surface | Producer |
|---------|----------|
| Config `connection { md5 { password; ip; } }` to `PeerSettings.MD5Key` / `MD5IP` | `parsePeer`, internal/component/bgp/reactor/config.go |
| Outbound connection | `NewSession` and `mergedRealDialer` fill `network.RealDialer.MD5Key` and `PeerAddr`, internal/component/bgp/reactor/session.go |
| Inbound connection | `Reactor.md5PeersForListener` fills `network.RealListenerFactory.MD5Peers`, internal/component/bgp/reactor/reactor.go; `Reactor.addPeer` restarts an existing listener when a new MD5 peer appears, internal/component/bgp/reactor/reactor_peers.go |
| Socket option, before connect | `RealDialer.DialContext` `Control` callback, internal/core/network/network.go |
| Socket option, before bind | `RealListenerFactory.Listen` `Control` callback, internal/core/network/network.go |
| Linux setsockopt | `setTCPMD5Sig`, internal/core/network/md5_linux.go: `unix.SetsockoptTCPMD5Sig(fd, IPPROTO_TCP, TCP_MD5SIG, &sig)` with the key, its length and the peer sockaddr |
| FreeBSD | `setTCPMD5Sig`, internal/core/network/md5_freebsd.go: enables the boolean flag; the key itself comes from the SAD via `setkey(8)` |
| macOS and every other platform | `setTCPMD5Sig`, internal/core/network/md5_darwin.go and md5_other.go: returns an error, so the dial or the listen fails and no unsigned session is established in place of a signed one |
| Operator warning | `checkBGPMD5`, internal/component/doctor/checks_config.go, and the `parsePeer` warning on a platform with no support |

## Pitfalls

- The Linux `TCP_MD5SIG` key is keyed by PEER ADDRESS and cannot be read back, so a
  test proves the install by making a connection rather than by a `getsockopt`.
- `net.ListenConfig.Control` fires once, at socket creation. A peer added later needs
  the listener restarted or its inbound connection is dropped by the kernel, which is
  what `Reactor.addPeer` does.
- A peer configured with `md5 { ip; }` and no password is a configuration error, not a
  silently unsigned session (`parsePeer`).
- Linux caps the key at 80 octets (`TCP_MD5SIG_MAXKEYLEN`), which is exactly the floor
  Section 4.5 recommends, so a longer operator key is refused rather than truncated.

## Compliance Checklist

- [ ] [RFC2385-2.0-1] [MUST] The key must be known by both ends of the connection, so the same configured key is installed for the peer on the outbound socket and on the listening socket (§2.0)
- [ ] [RFC2385-2.0-2] [MUST] Upon receiving a signed segment, the receiver must validate it by calculating its own digest from the same data using its own key and comparing the two digests (§2.0)
- [ ] [RFC2385-2.0-3] [MUST] A failing comparison must result in the segment being dropped, and must not produce any response back to the sender (§2.0)
- [ ] [RFC2385-2.0-4] [MUST NOT] The absence of the option in the SYN,ACK segment must not cause the sender to disable its sending of signatures (§2.0) {single-polarity: positive; ze holds no code path that stops signing: the key is installed from the peer's settings on every dial attempt and is never cleared by anything the remote host does or fails to do, so there is no rejecting branch a negative test could reach}
- [ ] [RFC2385-2.0-5] [MUST] The sending of signatures must be under the complete control of the application, not at the mercy of the remote host not understanding the option (§2.0)
- [ ] [RFC2385-2.0-6] [MUST] Every segment sent on a protected connection carries the 16-byte MD5 digest of the TCP pseudo-header, the TCP header with a zero checksum, the segment data and the key, in that order (§2.0)
- [ ] [RFC2385-3.0-1] [MUST] The option is Kind 19, Length 18, carrying a 16-byte digest, and it appears in every segment of the connection (§3.0)
- [ ] [RFC2385-4.3-1] [MUST] The size of the MD5 option must be factored into the MSS offered to the other side during connection negotiation (§4.3) {single-polarity: positive; the MSS is chosen by the kernel that signs the segments, and ze holds no code that lowers, rejects or recomputes an MSS, so there is no rejecting branch a negative test could reach}
- [ ] [RFC2385-4.3-2] [MUST] The total size of the TCP header plus its options must be less than or equal to 60 bytes, leaving 40 bytes for options (§4.3) {single-polarity: positive; the option list is assembled by the kernel and ze contributes no TCP option of its own, so there is no rejecting branch a negative test could reach}
- [ ] [RFC2385-4.5-1] [SHOULD] It is strongly recommended that an implementation support at minimum a key composed of a string of printable ASCII of 80 bytes or less (§4.5)
