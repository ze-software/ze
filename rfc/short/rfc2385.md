**Purpose:** Defines TCP option Kind 19, which carries an MD5 digest computed over
the TCP pseudo-header, the TCP header, the segment data and a shared key. A receiver
that holds the same key recomputes the digest and drops a segment that does not match,
which keeps a spoofed segment, and in particular a spoofed RST, out of a BGP session.

**Register:** the document predates RFC 2119 and writes every obligation in lowercase
(`must`, `must not`, `strongly recommended`). It cites RFC 2119 nowhere and carries no
capitalized MUST-level keyword, so the extraction sign-off derives register `prose`.
The rows below are gated at the level the sentence states, not at the level its
capitalization suggests.

## Wire Format

The option is fixed length. It appears in every segment of a protected connection.

```
             +---------+---------+-------------------+
             | Kind=19 |Length=18|   MD5 digest...   |
             +---------+---------+-------------------+
             |                                       |
             +---------------------------------------+
             |                                       |
             +---------------------------------------+
             |                                       |
             +-------------------+-------------------+
             |                   |
             +-------------------+
```

| Field | Offset | Size | Type | Constraints |
|-------|--------|------|------|-------------|
| Kind | 0 | 1 | uint8 | 19 |
| Length | 1 | 1 | uint8 | 18, the whole option including Kind and Length |
| MD5 digest | 2 | 16 | opaque | always 16 octets |

## Digest Computation

MD5 is applied to these items, in this order, with the header and pseudo-header in
network byte order:

1. the TCP pseudo-header: source IP address, destination IP address, zero-padded
   protocol number, segment length
2. the TCP header excluding options, with the checksum field taken as zero
3. the TCP segment data, if any
4. the key, known to both TCPs and presumably connection-specific

## Validation

| Check | Valid | Invalid Action |
|-------|-------|----------------|
| Digest in a received segment | equals the digest the receiver computes with its own key | drop the segment, send nothing back |
| Option absent from the peer's SYN,ACK | does not change the local decision to sign | never disable signing |
| Key length | whatever the local TCP accepts; 80 printable ASCII octets is the recommended floor | reject the configuration |

## Some Implications

- A connectionless reset carries no valid digest, so it is ignored. A connect attempt
  to a port with no listener times out rather than being refused, and a stale-connection
  RST no longer clears the session quickly.
- The option costs 18 octets in every segment and the complete TCP option list
  must fit in 40 octets. RFC 6691 Section 3.2 explicitly corrects this RFC's
  Section 4.3 MSS advice; RFC 9293 Section 3.7.1 retains that correction.
  The advertised MSS subtracts only fixed headers (1460 for IPv4 on MTU 1500).
  The sender reduces the actual data length for options instead. The packet
  test reads the SYN MSS bytes and checks that signed data packets fit the MTU;
  a successful loopback transfer alone proves neither.
- MD5 is weak against collision search. The option carries no algorithm-type field, so
  no upgrade path exists inside Kind 19.

## How Ze Implements It

Ze does not compute or verify a digest. It installs the key on the socket and the
kernel signs and validates every segment, which is the same route Ze takes for TCP
itself. The whole stack is what conformance is judged on
(`ai/rules/rfc-compliance.md`), so the rows below are met through the kernel and the
tests assert the thing Ze produces: the key Ze installs, on the sockets Ze opens,
before the handshake.

The packet carrier uses `RealDialer` and `RealListenerFactory` over a configured
MTU-1500 veth between two network namespaces. AF_PACKET observes the peer link,
not local delivery. Its digest oracle hashes the captured pseudo-header, fixed
TCP header with zero checksum, payload and key without calling Linux's verifier.
Malformed SYN cases change only the MD5 option and recompute the ordinary IP/TCP
checksums; each has a correctly signed control against the same listener.
RFC2385-2.0-3 belongs to that direct packet observation, not to a failed dial:
a dial timeout cannot distinguish peer silence from an unusable reply. The
silence window is 300ms, followed by the signed control. Unrelated UDP traffic
exercises the capture deadline; filtering a non-TCP frame must not start another
blocking receive outside that deadline.
An unsigned SYNACK acknowledging the actual SYN is injected on the peer link,
then the same connection's retransmitted SYN must still carry a valid signature.

## Pitfalls

- The Linux `TCP_MD5SIG` key is keyed by PEER ADDRESS and cannot be read back, so a
  test proves the install by making a connection rather than by a `getsockopt`.
- `net.ListenConfig.Control` fires once, at socket creation. A peer added later needs
  the listener restarted or its inbound connection is dropped by the kernel, which is
  what `Reactor.addPeer` does.
- A peer configured with `md5 { ip; }` and no password is a configuration error, not a
  silently unsigned session (`parsePeer`).
- Linux caps the key at 80 octets (`TCP_MD5SIG_MAXKEYLEN`), which is exactly the floor
  Section 4.5 recommends, so a longer operator key is refused rather than truncated.

## Compliance Checklist

- [ ] [RFC2385-2.0-1] [MUST] The nature of the key is deliberately left unspecified, but it must be known by both ends of the connection. (§2.0)
- [ ] [RFC2385-2.0-2] [MUST] Upon receiving a signed segment, the receiver must validate it by calculating its own digest from the same data (using its own key) and comparing the two digest. (§2.0)
- [ ] [RFC2385-2.0-3] [MUST] A failing comparison must result in the segment being dropped and must not produce any response back to the sender. (§2.0)
- [ ] [RFC2385-2.0-4] [MUST NOT] Unlike other TCP extensions (e.g., the Window Scale option [RFC1323]), the absence of the option in the SYN,ACK segment must not cause the sender to disable its sending of signatures. (§2.0) {single-polarity: positive; ze holds no code path that stops signing: the key is installed from the peer's settings on every dial attempt and is never cleared by anything the remote host does or fails to do, so there is no rejecting branch a negative test could reach}
- [ ] [RFC2385-2.0-5] [MUST] More importantly, the sending of signatures must be under the complete control of the application, not at the mercy of the remote host not understanding the option. (§2.0)
- [ ] [RFC2385-2.0-6] [MUST] Every segment sent on a TCP connection to be protected against spoofing will contain the 16-byte MD5 digest produced by applying the MD5 algorithm to these items in the following order: 1. the TCP pseudo-header (in the order: source IP address, destination IP address, zero-padded protocol number, and segment length) 2. the TCP header, excluding options, and assuming a checksum of zero 3. the TCP segment data (if any) 4. an independently-specified key or password, known to both TCPs and presumably connection-specific (§2.0)
- [ ] [RFC2385-3.0-1] [MUST] The proposed option has the following format: +---------+---------+-------------------+ | Kind=19 |Length=18| MD5 digest... | +---------+---------+-------------------+ | | +---------------------------------------+ | | +---------------------------------------+ | | +-------------------+-------------------+ | | +-------------------+ The MD5 digest is always 16 bytes in length, and the option would appear in every segment of a connection. (§3.0)
- [ ] [RFC2385-4.3-2] [MUST] This means that the total size of the header plus option must be less than or equal to 60 bytes -- this leaves 40 bytes for options. (§4.3) {single-polarity: positive; the option list is assembled by the kernel and ze contributes no TCP option of its own, so there is no rejecting branch a negative test could reach}
