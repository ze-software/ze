# RFC 9494: Long-Lived Graceful Restart for BGP

**Status:** Standards Track
**Updates:** RFC 6368
**Date:** November 2023

## Overview

Extends BGP Graceful Restart (RFC 4724) to allow stale routes to be retained for much longer periods (hours/days vs minutes). Introduces the LLGR Capability and two well-known communities.

## Key Concepts

| Term | Meaning |
|------|---------|
| LLGR | Long-Lived Graceful Restart |
| LLST | Long-Lived Stale Time (24-bit, seconds) |
| Helper | Router that detects session failure and retains routes |
| Depreference | Reduce route preference to "least preferred" |

## LLGR Capability (Code 71)

**Wire Format:**

```
+--------------------------------------------------+
| Address Family Identifier (16 bits)              |
+--------------------------------------------------+
| Subsequent Address Family Identifier (8 bits)    |
+--------------------------------------------------+
| Flags for Address Family (8 bits)                |
+--------------------------------------------------+
| Long-Lived Stale Time (24 bits)                  |
+--------------------------------------------------+
| ... (repeated for each AFI/SAFI)                 |
+--------------------------------------------------+
```

**Flags:**

| Bit | Name | Description |
|-----|------|-------------|
| 0 | F | Forwarding state preserved during restart |
| 1-7 | Reserved | MUST be zero |

**Requirements:**
- MUST also advertise GR Capability (RFC 4724)
- If GR not present, LLGR MUST be ignored
- LLST can be up to 16,777,215 seconds (~194 days)

## Well-Known Communities

| Community | Value | Purpose |
|-----------|-------|---------|
| LLGR_STALE | 0xFFFF0006 | Marks routes retained beyond GR timer |
| NO_LLGR | 0xFFFF0007 | Routes should NOT be retained if stale |

## Operation Timeline

```
Session fails
    │
    ▼
┌─────────────────────────┐
│   GR Restart Time       │  Routes retained, preference unchanged
│   (0-4095 seconds)      │
└─────────────────────────┘
    │
    ▼
┌─────────────────────────┐
│   LLGR Period           │  Routes get LLGR_STALE, become least-preferred
│   (0-16,777,215 sec)    │  Routes withdrawn from non-LLGR peers
└─────────────────────────┘
    │
    ▼
Routes deleted (if session not re-established)
```

## Key Behaviors

### When LLGR Period Begins

1. **Start LLST timer** for each AFI/SAFI with nonzero LLST
2. **Attach LLGR_STALE** community to stale routes (requires readvertisement)
3. **Delete NO_LLGR routes** immediately
4. **Depreference** routes (treat as least preferred)

### LLGR_STALE Route Processing

- Treat as **least preferred** in route selection
- **SHOULD NOT advertise** to peers without LLGR capability
- **MUST NOT remove** LLGR_STALE when readvertising
- Only used as last resort (no better route available)

### Session Re-establishment

- RFC 4724 procedures apply for stale routes
- LLST timer continues running until EoR received
- If F bit clear or AFI/SAFI missing in new LLGR cap → delete stale routes
- If both GR and LLGR caps missing → delete all stale routes

## Partial Deployment (Section 4.6)

When advertising to IBGP peers without LLGR:

1. MUST be internal (IBGP/Confederation) neighbors
2. MUST attach NO_EXPORT community
3. MUST set LOCAL_PREF to zero

## VPN Considerations (Section 4.7)

### EBGP PE-CE

- MAY advertise stale routes to CE without LLGR (explicit config required)
- SHOULD attach NO_EXPORT by default
- All other LLGR rules still apply

### IBGP PE-CE (RFC 6368 Update)

When using ATTR_SET:
- LLGR_STALE from imported VPN route MUST be included in CE advertisement
- Even if not in ATTR_SET attribute

## Deployment Guidance

**MUST NOT enable by default** - requires explicit per-AFI/SAFI configuration.

### Safe to Use

- MPLS/tunneled forwarding networks
- Non-forwarding data (VPLS auto-discovery, FlowSpec)
- Route reflectors (control-plane only)

### Use with Caution

- Hop-by-hop forwarded networks (risk of forwarding loops)
- Conventional reachability information

### Security: Label Reuse

For MPLS VPNs, ensure:
- **Label reuse lower bound** > **LLST upper bound**
- Prevents VPN traffic isolation breach

## Implementation Notes

### Timer Interaction

| GR Restart Time | LLST | Behavior |
|-----------------|------|----------|
| 0 | nonzero | Skip GR, go straight to LLGR |
| nonzero | 0 | GR only, no LLGR |
| 0 | 0 | Neither GR nor LLGR (base BGP only) |
| nonzero | nonzero | GR then LLGR (serial) |

### F Bit Coordination

- If LLGR F bit set → GR F bit should also be set
- Otherwise GR will clear state before LLGR kicks in

### Route Selection

```
Normal routes (any preference)
    ↓ more preferred than
LLGR_STALE routes (least preferred)
```

Between two LLGR_STALE routes: normal tiebreaking applies.

## ZeBGP Implementation Considerations

### Capability

- Code: 71
- Variable length (7 bytes per AFI/SAFI tuple)
- Requires GR capability (code 64) or ignore

### Communities

```go
const (
    CommunityLLGRStale = 0xFFFF0006
    CommunityNoLLGR    = 0xFFFF0007
)
```

### State Machine Impact

- Add LLST timer per AFI/SAFI
- Track LLGR state separately from GR state
- Handle F bit in both GR and LLGR capabilities

## Compliance Checklist

- [ ] [MUST] If the LLGR Capability is advertised, the Graceful Restart capability MUST also be advertised (§3.1, §4.1)
- [ ] [MUST] If GR capability is not advertised alongside LLGR, the LLGR Capability MUST be disregarded (§4.1)
- [ ] [MUST] Reserved bits in the Flags field MUST be set to zero by the sender and MUST be ignored by the receiver (§3.1)
- [ ] [MUST] If configured to support LLGR procedures, a BGP speaker MUST use BGP Capabilities Advertisement to advertise the LLGR Capability (§4)
- [ ] [MUST] After session goes down, stale routes for an AFI/SAFI MUST be retained for the sum of Restart Time and Long-Lived Stale Time (§4.2)
- [ ] [MUST] Once the LLGR period begins, for each AFI/SAFI with nonzero LLST, the helper router MUST start a timer for that Long-Lived Stale Time (§4.2)
- [ ] [MUST] If the LLST timer expires before session re-establishment, the helper MUST delete all stale routes of that AFI/SAFI from the neighbor (§4.2)
- [ ] [MUST] The helper router MUST attach the LLGR_STALE community to stale routes being retained (§4.2)
- [ ] [MUST NOT] Routes marked with NO_LLGR community MUST NOT be retained and MUST be removed per normal RFC 4271 operation (§4.2)
- [ ] [MUST] The helper router MUST perform the LLGR_STALE route processing procedures (§4.2, §4.3)
- [ ] [MUST NOT] In case of consecutive restarts, previously marked stale routes MUST NOT be deleted before the LLST timer expires (§4.2)
- [ ] [MUST] Once LLGR period begins, helper MUST immediately remove all stale routes if F bit is not set, AFI/SAFI is not listed, or LLGR+GR capabilities are not received in re-established session (§4.2)
- [ ] [MUST NOT] A running LLST timer MUST NOT be updated (other than by manual intervention) until the peer has established and synchronized a new session (§4.2)
- [ ] [MUST] A BGP speaker that advertised LLGR Capability MUST treat LLGR_STALE routes as least preferred in route selection (§4.3, §4.4)
- [ ] [MUST NOT] The LLGR_STALE community MUST NOT be removed when the route is further advertised (§4.3)
- [ ] [MUST] A least preferred route MUST be treated as less preferred than any route that is not also least preferred (§4.4)
- [ ] [MUST] If LLGR Capability is received without accompanying GR Capability, the LLGR Capability MUST be ignored (§4.5)
- [ ] [MUST] For partial deployment, neighbors receiving stale routes MUST be internal (IBGP or Confederation) neighbors (§4.6)
- [ ] [MUST] For partial deployment, the NO_EXPORT community MUST be attached to the stale routes (§4.6)
- [ ] [MUST] For partial deployment, stale routes MUST have their LOCAL_PREF set to zero (§4.6)
- [ ] [MUST] When using ATTR_SET (IBGP PE-CE), PE MUST include LLGR_STALE community in CE advertisement if present in imported VPN route, even if not in ATTR_SET (§4.7.2)
- [ ] [MUST] When exporting CE route to VPN address family, PE MUST include LLGR_STALE community in VPN route if present in path attributes received from CE (§4.7.2)
- [ ] [MUST NOT] Implementations MUST NOT enable LLGR procedures by default (§5)
- [ ] [MUST] Implementations MUST require affirmative configuration per AFI/SAFI to enable LLGR (§5)
- [ ] [MUST] If LLST timer expires during synchronization and session subsequently resets, remaining routes for that AFI/SAFI MUST be removed immediately (§4.2)
- [ ] [SHOULD] The LLST timers received SHOULD be modifiable by local configuration (§4.2)
- [ ] [SHOULD NOT] LLGR_STALE routes SHOULD NOT be advertised to any neighbor from which the LLGR Capability has not been received (§4.3)
- [ ] [SHOULD] When advertising stale routes over PE-CE EBGP session, implementation SHOULD by default attach NO_EXPORT community (§4.7.1)
- [ ] [MAY] An implementation MAY allow users to configure policies for LLGR_STALE community (§3.2)
- [ ] [MAY] An implementation MAY allow users to configure policies for NO_LLGR community (§3.3)
- [ ] [MAY] The value of LLST received from a neighbor MAY be reduced by local configuration (§4.2)
- [ ] [MAY] For partial deployment, stale routes MAY be advertised to IBGP neighbors without LLGR Capability (§4.6)
- [ ] [MAY] An implementation MAY advertise stale routes over a PE-CE session when explicitly configured (§4.7.1)
- [ ] [MAY] The second rule of Section 4.3 MAY be disregarded for PE-CE VPN sessions (§4.7.1)
- [ ] [MAY] Attachment of NO_EXPORT community MAY be disabled by explicit configuration for PE-CE (§4.7.1)
- [ ] [MAY] For IBGP PE-CE when CE does not support LLGR, optional procedures of Section 4.6 MAY be followed, overriding LOCAL_PREF from ATTR_SET (§4.7.2)
