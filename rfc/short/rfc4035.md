## Purpose

Defines how DNS resolvers and servers use the DNSSEC resource records (RFC 4034)
to authenticate DNS data: signing zones, serving signatures, and validating the
chain of trust so a resolver can tell whether an answer is Secure, Insecure
(unsigned), Bogus (signatures do not verify), or Indeterminate.

## EDNS0 header bits used by a resolver (§3.2, §4.9)

| Bit | Set by | Meaning |
|-----|--------|---------|
| **DO** (DNSSEC OK, EDNS0 flags) | client query | "Send me DNSSEC RRs (RRSIG/NSEC/DS)." A server only includes DNSSEC data when DO=1 (§3.2.1). |
| **CD** (Checking Disabled, message header) | client query | CD=1 tells a validating resolver "do NOT validate, give me the raw data even if Bogus." CD=0 (default) asks the upstream validating resolver to validate (§3.2.2, §4.9.2). |
| **AD** (Authenticated Data, message header) | validating server | The server sets AD=1 in a response when the answer (and authority) RRsets it returns were validated as Secure (§3.2.3). A stub MUST NOT trust AD unless the channel to the validating resolver is trusted. |

## Validation outcomes (§5, RFC 4033 §5)

| State | Meaning | Response |
|-------|---------|----------|
| Secure | Chain of trust verifies to a trust anchor | NOERROR, AD=1 (from a validating resolver) |
| Insecure | Provably unsigned delegation (no DS) | NOERROR, AD=0 -- a legitimate answer, not a failure |
| **Bogus** | Signatures present but do not verify, or missing where required | A validating resolver **MUST return RCODE 2 (SERVFAIL)** to a CD=0 query (§5.5) |
| Indeterminate | No trust anchor covers the name | Treated as Insecure by most resolvers |

## Requirements relevant to a stub / forwarding resolver

- A security-aware **non-validating** stub relies on a trusted validating
  resolver: it sends CD=0 and DO=1, and reads the AD bit / SERVFAIL result
  (§4.9.1-§4.9.3). It MUST NOT set CD=1 if it wants the upstream to validate.
- A validating resolver **MUST** set RCODE=SERVFAIL for data it determines is
  Bogus when the querier did not set CD (§5.5). SERVFAIL under DO=1/CD=0 is the
  wire signal of a broken chain.
- A resolver **MUST NOT** treat an Insecure (AD=0, unsigned) NOERROR answer as a
  failure -- unsigned zones are legitimate.

## How ze applies this

- `internal/component/resolve/dns` is a stub/forwarding resolver, not a full
  local validator. Its `dnssec-validation` mode (`system { dns {
  dnssec-validation } }`, default `off`) follows the stub model:
  - `off` -- DO bit clear, behavior unchanged.
  - `permissive` / `strict` -- set the EDNS0 DO bit (CD stays 0), so a validating
    upstream signs/validates and returns SERVFAIL on a Bogus chain.
  - `strict` rejects a SERVFAIL-under-validation answer as an error (fail-closed);
    `permissive` logs a warning and returns the empty result (fail-open).
  - A NOERROR answer is accepted whether AD=1 (Secure) or AD=0
    (Insecure/unsigned), per the MUST above.
- Full local chain validation (building trust from the root DNSKEY and verifying
  RRSIGs in-process) is intentionally not implemented: ze delegates validation to
  the configured upstream, which is the standard security-aware stub deployment.
- ze's authoritative side (`internal/plugins/geodns`, `internal/plugins/as112`,
  on the shared `internal/core/dnsserver` harness) serves synthesized, unsigned
  zones: it holds no DNSKEY, RRSIG, NSEC, or DS record, so the RFC's
  zone-signing, signed-response, zone-transfer, and recursive-server rules govern
  nothing ze produces. The header-bit rules it does meet are the CD bit copied
  from the query into the reply (`msg.SetReply`,
  `internal/core/dnsserver/handler.go:56`), the query's AD bit ignored and never
  asserted in a reply, and a DS query inside a served zone answered as
  authoritative no-data (`internal/plugins/geodns/server.go:205`).
- Two name-server EDNS0 obligations are unmet and tracked as gaps in
  `docs/features/rfc-status.md`: the server emits no OPT pseudo-RR and honors no
  requestor payload size (RFC4035-3-1), and its UDP listener reads at most 512
  octets because `dns.Server.UDPSize` stays zero
  (`internal/core/dnsserver/manager.go:165`, RFC4035-3-2).
