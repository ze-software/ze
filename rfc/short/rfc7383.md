**Purpose:** Lets IKEv2 peers split a large encrypted message (typically IKE_AUTH carrying certificates) into separately protected IKE Fragment messages, so it is never fragmented at the IP layer.

**Ze context:** Ze sends IKE_AUTH as a single UDP datagram. Large certificate chains therefore rely on IP fragmentation reaching the peer.

## Negotiation (Section 2.3)

IKEV2_FRAGMENTATION_SUPPORTED status notify in IKE_SA_INIT, both directions.

## Encrypted Fragment Payload (Section 2.5)

Payload type 53. Replaces the Encrypted payload (46) in each IKE Fragment message.

| Field | Size | Constraints |
|-------|------|-------------|
| Next Payload | 1 | first inner payload type in fragment 1, zero in every later fragment |
| C, RESERVED | 1 | as the generic payload header |
| Payload Length | 2 | |
| Fragment Number | 2 | 1-based, non-zero, at most Total Fragments |
| Total Fragments | 2 | non-zero |
| IV, encrypted content, padding, ICV | variable | as the Encrypted payload, each fragment protected on its own |

## Pitfalls

- Each fragment is protected on its own, so a forged fragment is discarded before reassembly instead of poisoning the whole message (Section 2.6).
- RFC7383-2.5-5 is the Fragment Number field and RFC7383-2.5-6 the Total Fragments field; the RFC words both identically.
