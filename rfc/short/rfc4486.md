**Purpose:** Defines subcodes for the BGP Cease NOTIFICATION message (Error Code 6) to provide more specific reasons for session teardown.

## Subcodes

| Subcode | Name | Description |
|---------|------|-------------|
| 1 | Maximum Number of Prefixes Reached | Peer exceeded configured prefix limit |
| 2 | Administrative Shutdown | Operator-initiated shutdown (RFC 9003 adds message) |
| 3 | Peer De-configured | Peer removed from configuration |
| 4 | Administrative Reset | Operator-initiated reset (RFC 9003 adds message) |
| 5 | Connection Rejected | Inbound connection refused |
| 6 | Other Configuration Change | Non-specific config change |
| 7 | Connection Collision Resolution | RFC 4271 Section 6.8 |
| 8 | Out of Resources | System resource exhaustion |

## Ze Implementation

### Subcode 1: Maximum Number of Prefixes Reached

Ze enforces per-peer per-family prefix maximums. When a peer exceeds the configured maximum for any family:

- NOTIFICATION sent with Error Code 6 (Cease), Subcode 1
- Data field: AFI (2 bytes big-endian) + SAFI (1 byte) + prefix upper bound (4 bytes
  big-endian). Figure 1 names the last four octets the upper bound, so they carry the
  configured maximum. The count that crossed it is a different number and is not sent
- Session torn down (when `teardown true`, the default)
- With `teardown false`: session stays up, excess NLRIs dropped silently

Prefix counting: wire-level counting of NLRI entries per UPDATE. Withdrawals processed before announces in the same UPDATE to prevent false triggers from prefix replacement.

### Subcodes 2, 4: Administrative Shutdown/Reset

Ze supports RFC 9003 shutdown communication messages (up to 128 bytes sent, up to 255 bytes accepted).

### MAY Decisions

| Section | Decision | Rationale |
|---------|----------|-----------|
| Subcode 1 data field | Include AFI+SAFI+upper bound | Tells the remote operator which family exceeded and what the bound is. **Correction 2026-08-23:** this row read "Include AFI+SAFI+count" and the code sent the count that crossed the maximum. Figure 1 labels the field "Prefix upper bound", so a peer read that count as the bound |

### Backoff on receipt (§4)

RFC 4486 §4 closes with a retry-damping recommendation: treat `DampPeerOscillations`
as true when re-trying after a Cease with subcode Administrative Shutdown, Peer
De-configured, Connection Rejected, or Out of Resources, and bound the number of
consecutive automatic retries. Both are advisory (RECOMMENDED / SHOULD), captured
below as `RFC4486-4-9` and `RFC4486-4-8`.

### Not an RFC 4486 obligation

The shutdown *communication message* carried with subcodes 2 and 4 is defined by
RFC 9003, not by this document; RFC 4486 §4 says nothing about it. Ze's support for
it (up to 128 bytes sent, up to 255 accepted) is noted above as implementation
context, and its obligations belong in `rfc/short/rfc9003.md`.

## Compliance Checklist

All normative statements in RFC 4486 are in §4 (Subcode Usage); §2 is the RFC 2119
boilerplate and §3 is the subcode registry table.

- [ ] [RFC4486-4-1] [MUST] If a BGP speaker decides to terminate its peering with a neighbor because the number of address prefixes received from the neighbor exceeds a locally configured upper bound (as described in [BGP-4]), then the speaker MUST send to the neighbor a NOTIFICATION message with the Error Code Cease and the Error Subcode "Maximum Number of Prefixes Reached" (§4)
- [ ] [RFC4486-4-2] [SHOULD] If a BGP speaker decides to administratively shut down its peering with a neighbor, then the speaker SHOULD send a NOTIFICATION message with the Error Code Cease and the Error Subcode "Administrative Shutdown" (§4)
- [ ] [RFC4486-4-3] [SHOULD] If a BGP speaker decides to de-configure a peer, then the speaker SHOULD send a NOTIFICATION message with the Error Code Cease and the Error Subcode "Peer De-configured" (§4)
- [ ] [RFC4486-4-4] [SHOULD] If a BGP speaker decides to administratively reset the peering with a neighbor, then the speaker SHOULD send a NOTIFICATION message with the Error Code Cease and the Error Subcode "Administrative Reset" (§4)
- [ ] [RFC4486-4-5] [SHOULD] If a BGP speaker decides to disallow a BGP connection (e.g., the peer is not configured locally) after the speaker accepts a transport protocol connection, then the BGP speaker SHOULD send a NOTIFICATION message with the Error Code Cease and the Error Subcode "Connection Rejected" (§4)
- [ ] [RFC4486-4-6] [SHOULD] If a BGP speaker decides to administratively reset the peering with a neighbor due to a configuration change other than the ones described above, then the speaker SHOULD send a NOTIFICATION message with the Error Code Cease and the Error Subcode "Other Configuration Change" (§4)
- [ ] [RFC4486-4-7] [SHOULD] If a BGP speaker decides to send a NOTIFICATION message with the Error Code Cease as a result of the collision resolution procedure (as described in [BGP-4]), then the subcode SHOULD be set to "Connection Collision Resolution" (§4)
- [ ] [RFC4486-4-8] [SHOULD] An implementation SHOULD impose an upper bound on the number of consecutive automatic retries (§4)
- [ ] [RFC4486-4-9] [RECOMMENDED] It is RECOMMENDED that a BGP speaker behave as though the DampPeerOscillations attribute [BGP-4] were true for this peer when re-trying a BGP connection after the speaker receives a Cease NOTIFICATION message with a subcode of "Administrative Shutdown", "Peer De-configured", "Connection Rejected", or "Out of Resources" (§4)
- [ ] [RFC4486-4-10] [MAY] The message MAY optionally include the Address Family information [BGP-MP] and the upper bound in the "Data" field, as shown in Figure 1 (§4)
- [ ] [RFC4486-4-11] [MAY] If a BGP speaker runs out of resources (e.g., memory) and decides to reset a session, then the speaker MAY send a NOTIFICATION message with the Error Code Cease and the Error Subcode "Out of Resources" (§4)
