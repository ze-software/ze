**Purpose:** Defines the signed ROA object through which an IP address holder
authorizes an AS to originate routes. RFC 9582 obsoletes RFC 6482.

**Scope:** The CMS content type, ASN.1 payload and ROA-specific validation
checks performed by a relying party. Section 7 registers content types, the
`.roa` file extension and `application/rpki-roa`.

## Content and Encoding

Section 3 assigns `id-ct-routeOriginAuthz` the OID
`1.2.840.113549.1.9.16.1.24`:

> This OID MUST appear within both the eContentType in the encapContentInfo
> object and the content-type signed attribute in the signerInfo object
> (see [RFC6488]).

Section 4 defines a `RouteOriginAttestation` containing version 0, one `asID`
and one or two `ROAIPAddressFamily` entries. Each family contains prefixes and
optional `maxLength` values.

| Element | Constraint |
|---------|------------|
| `addressFamily` | `0001` for IPv4 or `0002` for IPv6; one entry per AFI |
| IPv4 prefix | Must not use an IPv4-mapped IPv6 address |
| `maxLength`, when present | At least the prefix length and at most 32 for IPv4 or 128 for IPv6 |
| `maxLength`, when absent | Authorization covers the exact prefix |

Section 4.3.3 defines canonical ordering by AFI, first address, prefix length
and maximum length. Equal tuples are duplicates. The RFC recommends this
canonical form and omission of a `maxLength` equal to the prefix length.

## ROA Validation

Section 5 states:

> Before a Relying Party can use a ROA to validate a routing announcement,
> the Relying Party MUST first validate the ROA.

Validation includes RFC 6488's checks, the presence of the EE certificate's
IP address delegation extension, containment of every ROA prefix within that
extension, absence of `inherit` elements, absence of the AS identifier
delegation extension, and conformity with Sections 3 and 4. Failure makes the
whole ROA invalid and should be logged.

Section 6 also requires signature verification using the RPKI X.509
certificate and checking that the ROA prefixes are contained within the
certificate's IP address delegation extension.

## Compliance Checklist

- [ ] [RFC9582-3-1] [MUST] The content-type for a ROA is defined as id-ct-routeOriginAuthz and has the numerical value 1.2.840.113549.1.9.16.1.24. This OID MUST appear within both the eContentType in the encapContentInfo object and the content-type signed attribute in the signerInfo object (see [RFC6488]). (§3)
- [ ] [RFC9582-4.1-1] [MUST] The version number of the RouteOriginAttestation entry MUST be 0 (§4.1)
- [ ] [RFC9582-4.3.1-1] [MUST] addressFamily MUST be either 0001 or 0002 (§4.3.1)
- [ ] [RFC9582-4.3.1-2] [MUST NOT] IPv4 prefixes MUST NOT appear as IPv4-mapped IPv6 addresses (§4.3.1)
- [ ] [RFC9582-4.3.1-3] [MUST] There MUST be only one instance of ROAIPAddressFamily per unique AFI in the ROA (§4.3.1)
- [ ] [RFC9582-4.3.1-4] [MUST NOT] Thus, the ROAIPAddressFamily structure MUST NOT appear more than twice. (§4.3.1)
- [ ] [RFC9582-4.3.2.2-1] [MUST] If present, the maxLength element MUST be: * an integer greater than or equal to the length of the accompanying prefix, and * less than or equal to the maximum length (in bits) of an IP address in the applicable address family: 32 in the case of IPv4 and 128 in the case of IPv6. (§4.3.2.2)
- [ ] [RFC9582-5-1] [MUST] Before a Relying Party can use a ROA to validate a routing announcement, the Relying Party MUST first validate the ROA (§5)
- [ ] [RFC9582-5-2] [MUST] To validate a ROA, the Relying Party MUST perform all the validation checks specified in [RFC6488] as well as the following additional ROA-specific validation steps: (§5)
- [ ] [RFC9582-5-3] [MUST NOT] * The EE certificate's IP address delegation extension MUST NOT contain "inherit" elements as described in [RFC3779]. (§5)
- [ ] [RFC9582-5-4] [MUST NOT] * The Autonomous System identifier delegation extension described in [RFC3779] is not used in ROAs and MUST NOT be present in the EE certificate. (§5)
- [ ] [RFC9582-5-5] [MUST] If any of the above checks fail, the ROA in its entirety MUST be considered invalid (§5)
- [ ] [RFC9582-5-6] [MUST] * The IP address delegation extension [RFC3779] is present in the end-entity (EE) certificate (contained within the ROA), and every IP address prefix in the ROA payload is contained within the set of IP addresses specified by the EE certificate's IP address delegation extension. (§5)
- [ ] [RFC9582-5-7] [MUST] The ROA content fully conforms with all requirements specified in Sections 3 and 4 (§5)
- [ ] [RFC9582-6-1] [MUST] Thus, the integrity of a ROA MUST be established. (§6)
- [ ] [RFC9582-6-2] [MUST] Specifically, one MUST verify the signature on the ROA using an X.509 certificate issued under this PKI and check that the prefix or prefixes in the ROA are contained within those in the certificate's IP address delegation extension. (§6)
- [ ] [RFC9582-4.3.2.2-2] [SHOULD NOT] The maxLength element SHOULD NOT be encoded if the maximum length is equal to the prefix length (§4.3.2.2)
- [ ] [RFC9582-4.3.2.2-3] [SHOULD] Certification Authorities SHOULD anticipate that future Relying Parties will become increasingly stringent in considering the presence of superfluous maxLength elements an encoding error (§4.3.2.2)
- [ ] [RFC9582-4.3.3-1] [SHOULD] In order to produce and verify this canonical form, the process described in this section SHOULD be used to ensure that information elements are unique with respect to one another and sorted in ascending order. (§4.3.3)
- [ ] [RFC9582-4.3.3-2] [SHOULD] Certification Authorities SHOULD anticipate that future Relying Parties will impose a strict requirement for the ipAddrBlocks field to be in this canonical form. (§4.3.3)
- [ ] [RFC9582-5-8] [SHOULD] If any of the above checks fail, the ROA in its entirety MUST be considered invalid and an error SHOULD be logged. (§5)
- [ ] [RFC9582-4.3.2.3-1] [NOT RECOMMENDED] Additionally, a ROA MAY contain two ROAIPAddress elements, where the IP address prefix is identical in both cases. However, this is NOT RECOMMENDED, because in such a case, the ROAIPAddress element with the shorter maxLength grants no additional privileges to the indicated AS and thus can be omitted without changing the meaning of the ROA. (§4.3.2.3)

`draft-ietf-sidrops-8210bis.md` has no row stating their subject. Their text is
the old ledger's claim, not a statement of RFC 9582. This RFC has no Section
5.12; its Section 7 is IANA Considerations. The nine other historical rows were
retired on 2026-09-26, each naming its destination row in
`rfc/corrections/rfc9582.md`; their tags had already moved to those rows.

The source audit and exact candidate mappings are in
`draft-ietf-sidrops-8210bis.md`. Some old rows have no current obligation to
map: the AFI claims are absent from revision 27, and its Section 5.12 does not
