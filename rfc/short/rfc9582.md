**Purpose:** Defines version 2 of the RPKI-to-Router protocol (RTR), adding support for ASPA (Autonomous System Provider Authorization) objects alongside existing ROA prefix and Router Key distribution.

**Scope:** Cache-to-router communication. Extends RTR v1 (RFC 8210) with new PDU types for ASPA records. Same transport, timing, and session management model.

## Changes from RFC 8210 (Version 1)

| Change | Section | Impact |

| Protocol version incremented from 1 to 2 | 5.1 | All PDUs carry version field = 2 |

| New error code for ASPA | 12 | Handling of unknown PDU type in older implementations |

## Wire Formats

### ASPA PDU (Type 11) -- NEW in Version 2

```
 0          8          16         24        31
.-------------------------------------------.
| Version  | Type=11  |        zero         |
+-------------------------------------------+
|                  Length                    |
+-------------------------------------------+
|  Flags   |   AFI    |       zero          |
+-------------------------------------------+
|            Customer AS Number             |
+-------------------------------------------+
|           Provider AS Number 1            |
+-------------------------------------------+
|           Provider AS Number 2            |
+-------------------------------------------+
|                   ...                     |
+-------------------------------------------+
|           Provider AS Number N            |
`-------------------------------------------'
```

| Field | Offset | Size | Type | Constraints |
|-------|--------|------|------|-------------|
| Version | 0 | 1 | uint8 | 2 |
| PDU Type | 1 | 1 | uint8 | 11 |
| zero | 2 | 2 | uint16 | Must be 0 |
| Length | 4 | 4 | uint32 | 16 + 4*N (N = provider count) |
| Flags | 8 | 1 | uint8 | Bit 0: 1=announce, 0=withdraw |
| AFI Flags | 9 | 1 | uint8 | 0=IPv4+IPv6, 1=IPv4-only, 2=IPv6-only |
| zero | 10 | 2 | uint16 | Must be 0 |
| Customer AS | 12 | 4 | uint32 | Customer ASN (1 to 2^32-2) |
| Provider ASNs | 16 | 4*N | []uint32 | Set of authorized provider ASNs |

**Fixed portion:** 16 bytes (header + flags + customer AS).
**Variable portion:** 4 bytes per provider ASN.
**Minimum length:** 20 bytes (one provider).

### AFI Flags Semantics

| Value | Meaning |
|-------|---------|
| 0 | ASPA applies to both IPv4 and IPv6 |
| 1 | ASPA applies to IPv4 unicast only |
| 2 | ASPA applies to IPv6 unicast only |

**Note:** Early drafts used per-AFI ASPA records. RFC 9582 simplified to a single provider set with AFI flags indicating applicability. Most deployments use AFI=0 (both).

| Type | Name | Length | Direction | New in v2 |

| 0 | Serial Notify | 12 | Cache->Router | No |

| 2 | Reset Query | 8 | Router->Cache | No |

| 11 | ASPA | variable | Cache->Router | Yes |

Type 5 remains unassigned.

## Protocol Version Negotiation (Extended for v2)

```
1. Router sends Reset Query or Serial Query with version = 2
2. If cache supports version 2: responds with version 2 PDUs (may include ASPA)
3. If cache only supports version 1:
   a. Cache sends Error Report with code 4 (Unsupported Protocol Version),
      max supported version in the version field of the error PDU
   b. Router downgrades: re-sends query with version = 1
   c. ASPA data unavailable at v1 (no Type 11 PDU)
4. If cache only supports version 0: same downgrade as v1->v0
5. Once negotiated, version is stable for session lifetime
```

**Key constraint:** ASPA PDUs are ONLY sent when the negotiated version is 2. A v1 session never contains ASPA data.

## ASPA Cache Management

### Storage Model

For each (Customer-AS, AFI) tuple, store the complete set of authorized provider ASNs.

| Operation | Semantics |
|-----------|-----------|
| Announce (flags bit 0 = 1) | Replace entire provider set for (Customer-AS, AFI) |
| Withdraw (flags bit 0 = 0) | Remove ASPA record for (Customer-AS, AFI) |

**Important:** ASPA announce replaces the full provider set, not a delta. If Customer AS 64500 changes from providers {1, 2, 3} to {1, 2, 4}, the cache sends a single announce PDU with {1, 2, 4}.

### Delta Handling

Within a Cache Response / End of Data exchange:
- Multiple ASPA PDUs for same (Customer-AS, AFI): last one wins
- Withdraw followed by announce: net effect is the announce
- Announce followed by withdraw: net effect is removal

## Algorithms

### Router ASPA Cache Update (on End of Data)

```
1. Accumulate ASPA PDUs between Cache Response and End of Data
2. For withdrawals: mark (Customer-AS, AFI) for removal
3. For announces: store complete provider set for (Customer-AS, AFI)
4. At End of Data: apply all changes atomically
5. Trigger re-validation of affected routes (routes with Customer-AS in AS_PATH)
```

## Pitfalls

### Edge Cases

- **Empty provider set:** PDU with Length=16 (no providers) is malformed; MUST have at least one provider
- **AFI=0 vs per-AFI:** If both AFI=0 and AFI=1 records exist for same customer, behavior is implementation-defined; caches SHOULD only emit one form
- **Provider ordering:** Providers MUST be sorted ascending in the PDU; unsorted PDUs are malformed
- **Large provider sets:** A customer with many providers (100+) produces a single large PDU; implementations must handle variable-length reads
- **Customer AS 0:** Reserved, MUST NOT appear; ignore if received

### Interop

- **v1 caches:** Will never send ASPA PDUs; router gets ROA-only validation
- **Mixed v1/v2 caches:** Different caches may provide different RPKI data subsets; track per-cache
- **PDU Type 11 in v1 session:** If received, this is a protocol violation; send Error Report code 5 (Unsupported PDU Type)

### Security

- **ASPA data integrity:** Same trust model as ROA; relies on transport security to cache
- **Provider set completeness:** An incomplete ASPA (missing a legitimate provider) causes false Invalid results for routes through that provider
- **Transition period:** During ASPA deployment, many ASes lack ASPA records; Unknown (not Invalid) is the expected result

## Compatibility

### With Version 1 (RFC 8210)

- All v1 PDU types valid in v2 (same type codes, same formats)
- ASPA PDU (Type 11) only in v2 sessions
- End of Data unchanged (24 bytes, same timing parameters)
- Error codes unchanged (0-8)
- Session ID and serial semantics unchanged

### Feature Availability by Version
