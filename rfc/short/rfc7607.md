# RFC 7607 - Codification of AS 0 Processing

## Meta

| Field | Value |
|-------|-------|
| RFC | 7607 |
| Title | Codification of AS 0 Processing |
| Status | Proposed Standard |
| Date | August 2015 |
| Obsoletes | - |
| Updates | RFC 4271 |
| Obsoleted by | - |

**Purpose:** Proscribes AS 0 in the BGP OPEN message and in the AS_PATH, AS4_PATH,
AGGREGATOR and AS4_AGGREGATOR attributes of the UPDATE message, and names the error
handling for each.

## Why AS 0 is proscribed

RFC 6491 lets a resource holder publish a ROA naming AS 0 as the only origin for a
prefix, which says the prefix must not be routed. That signal only works if no BGP
speaker accepts or propagates a route carrying AS 0. RFC 7607 Section 1 states the
consequence: "To respond to this signal requires that BGP implementations not accept
or propagate routes containing AS 0."

Before this document no BGP specification said AS 0 was proscribed. RFC 7607 updates
the error handling of RFC 4271 Sections 6.2 and 6.3 to say it.

## The five normative statements

All of them are in Section 2. Section 1 is the introduction, Section 3 is an IANA
registry change, Section 4 is security considerations, and Section 5 is references.

| # | Statement | Error handling |
|---|-----------|----------------|
| 1 | Never originate or propagate AS 0 in AS_PATH, AS4_PATH, AGGREGATOR or AS4_AGGREGATOR | - |
| 2 | AS 0 in AS_PATH or AGGREGATOR makes the UPDATE malformed | RFC 7606 |
| 3 | AS 0 in AS4_PATH or AS4_AGGREGATOR makes the UPDATE malformed | RFC 6793 |
| 4 | AS 0 as the peer AS in an OPEN aborts the connection | NOTIFICATION 2/2 |
| 5 | Never initiate a connection claiming to be AS 0 | - |

The two referenced documents name the action, and RFC 7607 does not restate it.

- RFC 7606 Section 7.2: "An UPDATE message with a malformed AS_PATH attribute SHALL be
  handled using the approach of 'treat-as-withdraw'."
- RFC 7606 Section 7.7: "An UPDATE message with a malformed AGGREGATOR attribute SHALL
  be handled using the approach of 'attribute discard'."
- RFC 6793 Section 6: "the 'attribute discard' approach is chosen to handle a malformed
  AS4_PATH attribute", and the same paragraph chooses it for AS4_AGGREGATOR.

So the four attributes do not share one action. AS_PATH is treat-as-withdraw and the
other three are attribute discard.

## Ze Implementation

### The wire, not the sentinel

Ze uses AS 0 internally to mean "no AS is known yet", and RFC 7607 governs the wire.
Keeping the two apart is the constraint every check below is written against.

| Internal use | Where | Why the RFC 7607 checks do not touch it |
|--------------|-------|------------------------------------------|
| A dynamic peer carries `PeerAS` 0 until establishment | `buildDynamicPeerSettings` (`reactor_dynamic.go`), filled by `resolveDynamicPeerSettings` (`peer_run.go`) | `validateOpenPeerAS` reads the OPEN's own My AS field and the peer's Four-octet AS capability, never `s.settings.PeerAS` |
| `collisionPeerAS` and `validateOpenIdentifier` read `PeerAS` 0 as absence | `session.go`, `session_open_validation.go` | Both keep their fallback. `validateOpenPeerAS` runs BEFORE them on each rail, so neither can be handed a peer that really claimed AS 0 |
| Observation and traffic features group by AS 0 as "unknown" | `internal/core/observation/observation.go`, `internal/component/trafficfeature/service.go` | Neither reads a BGP message. They label a flow, and no check was added there |
| BGP-LS node descriptors take AS 0 as a safe zero value | `internal/component/bgp/plugins/nlri/ls/types_descriptor.go` | An NLRI descriptor is not one of the four attributes RFC 7607 names |
| `globalLocalAS` returns 0 when the config declares no AS | `internal/component/bgp/config/loader_create.go` | That 0 means "not declared". `sendOpen` refuses to put it on the wire |

### Receiving an UPDATE

`Session.enforceRFC7606` (`internal/component/bgp/reactor/session_validation.go`) calls
`ValidateUpdateRFC7606AddPath`, which walks the path attributes and dispatches through
`attrValidators`. The four checks live at that dispatch:

| Attribute | Code | Producer | Action |
|-----------|------|----------|--------|
| AS_PATH | 2 | `validateASPath` (`message/rfc7606.go`) | treat-as-withdraw |
| AGGREGATOR | 7 | `validateAggregatorAttr` (`message/rfc7606.go`) | attribute discard |
| AS4_PATH | 17 | `validateAS4PathAttr` (`message/rfc7607.go`) | attribute discard |
| AS4_AGGREGATOR | 18 | `validateAS4AggregatorAttr` (`message/rfc7607.go`) | attribute discard |

AS_PATH and AGGREGATOR already had a validator, so the AS 0 test was added inside it
beside the structural tests of the same attribute. Codes 17 and 18 had no validator at
all, and `message/rfc7607.go` registers theirs.

One scanner answers the AS 0 question for both path attributes.
`asPathHoldsASZero` (`message/rfc7607.go`) walks AS_PATH-shaped segment data at a
caller-chosen AS width, so the two-octet and four-octet paths cannot disagree.

The scanner reports no zero when the segment structure is inconsistent. That is
deliberate and is not a fail-open: a structural fault is a different malformation with a
different owner, RFC 7606 Section 7.2 for AS_PATH and RFC 6793 Section 6 for AS4_PATH.
For AS_PATH the structural walk runs first and rejects such an attribute anyway.

### Receiving an OPEN

`Session.validateOpenPeerAS` (`internal/component/bgp/reactor/session_open_as.go`)
aborts the connection with NOTIFICATION OPEN Message Error (2) / Bad Peer AS (2). Both
OPEN rails call it: `handleOpen` (`session_handlers.go`), which every non-colliding
connection takes, and `processOpen` (`session_connection.go`), which a connection takes
after winning collision resolution. A check on one rail alone is bypassed by arriving as
the second connection.

`openClaimsASZero` reads two fields, because a peer AS can hide in either. The two-octet
My Autonomous System field of RFC 4271 Section 4.2 is the first. A speaker with a
four-octet AS puts AS_TRANS there and its real AS in the Four-octet AS capability
instead (RFC 6793 Section 3), so a capability carrying 0 is the second.

### Sending an OPEN

`Session.sendOpen` (`internal/component/bgp/reactor/session_negotiate.go`) refuses to
send when the local AS is 0. This is the second half of a pair: the YANG type refuses
AS 0 at config load, because `zt:asn` is `range "1..4294967295"` in
`internal/component/config/yang/modules/ze-types.yang`, so an operator cannot configure
it, and a local AS that arrived from anywhere else still cannot reach a socket.

### Never propagating AS 0

Ze needs no separate egress check for the propagate half of statement 1, and this is why.
A received AS_PATH holding AS 0 is treat-as-withdrawn, so the route never enters the RIB
and nothing can relay it. A received AGGREGATOR, AS4_PATH or AS4_AGGREGATOR holding AS 0
is discarded at receive, so the attribute is gone before any egress path reads it. The
only AS Ze adds on egress is its own, which `sendOpen` and the YANG range keep non-zero.

### Not an RFC 7607 obligation

RFC 6793 Section 6 gives AS4_PATH and AS4_AGGREGATOR malformed conditions of their own:
a length that is not 8 for AS4_AGGREGATOR, and a length, segment length or segment type
fault for AS4_PATH. Those belong to `rfc/short/rfc6793.md`, which records the receive-path
gap under RFC6793-6-5. The validators above do not police them, so that record stays true.

## Compliance Checklist

- [ ] [RFC7607-2-1] [MUST NOT] A BGP speaker MUST NOT originate or propagate a route with an AS number of zero in the AS_PATH, AS4_PATH, AGGREGATOR, or AS4_AGGREGATOR attributes (§2)
- [ ] [RFC7607-2-2] [MUST] An UPDATE message that contains the AS number of zero in the AS_PATH or AGGREGATOR attribute MUST be considered as malformed and be handled by the procedures specified in [RFC7606] (§2)
- [ ] [RFC7607-2-3] [MUST] An UPDATE message that contains the AS number of zero in the AS4_PATH or AS4_AGGREGATOR attribute MUST be considered as malformed and be handled by the procedures specified in [RFC6793] (§2)
- [ ] [RFC7607-2-4] [MUST] If a BGP speaker receives zero as the peer AS in an OPEN message, it MUST abort the connection and send a NOTIFICATION with Error Code "OPEN Message Error" and subcode "Bad Peer AS" (§2)
- [ ] [RFC7607-2-5] [MUST NOT] A router MUST NOT initiate a connection claiming to be AS 0 (§2)
