**Purpose:** Extend the IS-IS protocol so a routing domain running both
level 1 (L1) and level 2 (L2) Intermediate Systems can distribute IP
prefixes between L1 and L2 and vice versa, with restrictions that insure
persistent forwarding loops do not form. The goal is to increase the
granularity of routing information within the domain (Abstract).

**Scope:** RFC 1195 defines the TLV tuples that transport IPv4 routing
information in IS-IS, and the semantics for interactions between levels.
RFC 1195 defines that L1L2 routers advertise L1-learned IP routes into
L2 (L1->L2 inter-area routes), carried in L2 LSPs in the "IP Internal
Reachability Information" TLV (TLV 128), and does not define L2->L1
inter-area routes (Section 2). This document extends RFC 1195 to allow
L2->L1 inter-area routes and external prefixes in L1 LSPs.

## Background (Sections 1, 2)

- An IS-IS routing domain can be partitioned into multiple L1 areas and
  an L2 connected subset that interconnects all the L1 areas (Section 1).
- Per RFC 1195, for IP destinations not found in the L1 database, an L1
  router forwards packets to the nearest router that is in both L1 and
  L2 (an L1L2 router) with the "attached bit" set in its L1 LSP
  (Section 1).
- RFC 1195 defines that L1->L2 inter-area routes must be advertised in
  L2 LSPs in the "IP Internal Reachability Information" TLV (TLV 128).
  Intra-area L2 routes are also advertised in L2 LSPs in an "IP Internal
  Reachability Information" TLV, so L1->L2 inter-area routes are
  indistinguishable from L2 intra-area routes (Section 2).

## The up/down bit (Section 2)

To allow L2->L1 inter-area routes while preventing routing loops, a way
is needed to distinguish L2->L1 inter-area routes from L1 intra-area
routes.

- RFC 1195 defines TLVs 128 and 130 to contain IP routes. TLVs 128 and
  130 have a metric field that consists of 4 TOS metrics. The first
  metric, the so-called "default metric", has the high-order bit
  reserved (bit 8). Routers must set this bit to zero on transmission,
  and ignore it on receipt (per RFC 1195).
- This document redefines this high-order bit (bit 8) in the default
  metric field in TLVs 128 and 130 to be the up/down bit (Section 2).

Semantics (Section 2):

- L1L2 routers MUST set this bit to one for prefixes that are derived
  from L2 routing and are advertised into L1 LSPs.
- The bit MUST be set to zero for all other IP prefixes in L1 or L2 LSPs.
- Prefixes with the up/down bit set that are learned via L1 routing MUST
  NEVER be advertised by L1L2 routers back into L2.

## Loop-prevention rules (Sections 2, 2.2, 3.3, 4)

- L1L2 routers MUST never advertise L2->L1 inter-area routes that they
  learn via L1 routing, back into L2 (Section 2). Distinguishing such
  routes is the reason the up/down bit is defined.
- When an L1L2 router advertises a L1 route into L2, where that L1 route
  was learned via a prefix advertised in an "IP External Reachability
  Information" TLV, that L1L2 router should advertise that prefix in its
  L2 LSP within an "IP External Reachability Information" TLV. L1 routes
  learned via an "IP Internal Reachability Information" TLV should still
  be advertised within an "IP Internal Reachability Information" TLV.
  These rules also apply when advertising IP routes derived from L2
  routing into L1, and in that case the up/down bit must be set
  (Section 2.2).
- The up/down bit is never set in L2 LSPs (Section 3.1). Because IS-IS
  is currently defined with two levels of hierarchy, there should never
  be a need to set the up/down bit in L2 LSPs. It is recommended that
  implementations ignore the up/down bit in L2 LSPs and accept the
  prefixes regardless of whether the bit is set, to allow simpler
  migration once more than two levels of hierarchy are defined
  (Section 3.3).

## Which routes may be leaked (Sections 2.2, 3.3, 4)

- This document loosens the RFC 1195 restriction and allows inclusion of
  the "IP External Reachability Information" TLV (TLV 130) in L1 LSPs
  (Section 2.2). TLV 128 is "IP Internal Reachability Information" (for
  prefixes directly connected to IS-IS routers); TLV 130 is "IP External
  Reachability Information" (for routes learned from outside the IS-IS
  domain) (Section 2.1).
- L1L2 routers should only advertise into their L2 LSP those L1 routes
  that they use for forwarding themselves. They should not
  unconditionally advertise into L2 all prefixes from LSPs in the L1
  database (Section 3.3).
- Not all prefixes need to be advertised up or down the hierarchy.
  Implementations might allow additional manual filtering or
  summarization. It is recommended that the default configuration of
  L1L2 routers is to not advertise any L2 routes into L1 (Section 3.3).
- Implementations should force the network administrator to manually
  configure L1L2 routers to advertise any L2 routes into L1 (Section 4).

## Metric-type bit and route-type (Sections 2.1, 3)

There are four variables involved in advertising an IP route (Section 3):

1. The level of the LSP (level 1 or level 2).
2. The route-type, derived from the TLV: internal routes in TLV 128, and
   external routes in TLV 130.
3. The metric-type (internal or external), derived from the
   Internal/External metric-type bit in the metric field (bit 7).
4. Whether the route is leaked down in the hierarchy (and thus cannot be
   advertised back up), derived from the up/down bit in the default
   metric field.

- The combination "IP Internal Reachability Information" and external
  metric-type is not allowed; on receipt of an IP prefix with this
  combination, routers must ignore the prefix (Sections 3.1, 3.3).
- External metric-type can only be used for external IP prefixes; metrics
  of external metric-type should never be seen in TLV 128 (Section 2.1).
- Internal routes and external routes using internal metrics are treated
  identically for the purpose of order of preference of routes and the
  Dijkstra calculation. IP routes advertised in "IP External
  Reachability Information" with external metric-type must be given less
  preference than the same routes advertised with internal-metric type,
  regardless of metric values (Section 2.1).

## Bit positions in the default metric field (TLVs 128 and 130)

| Bit | Name | Meaning |
|-----|------|---------|
| 8 (high-order) | up/down bit | Set to one for prefixes derived from L2 routing advertised into L1 LSPs; zero otherwise (Section 2). Originally reserved by RFC 1195. |
| 7 | Internal/External metric-type bit | Internal or external metric-type (Section 3) |

## Inter-operability with older implementations (Section 4)

- The solution is not fully compatible with RFC 1195; it is an extension.
  If routers do not use external L1 routes nor L2->L1 inter-area routes,
  older RFC 1195 implementations are compatible with newer ones.
- Implementations that follow RFC 1195 should ignore bit 8 in the
  default metric field when computing routes. Even older implementations
  that do not know of the up/down bit should be able to accept the new
  L2->L1 inter-area routes; they will install them as L1 intra-area
  routes, which by itself does not cause routing loops among L1-only
  routers.
- It is vital that the up/down bit is recognized by L1L2 routers. If L2
  routes are advertised down into an L1 area, it is required that all
  L1L2 routers in that area run software that understands the up/down
  bit. Older implementations that do not understand it will treat
  L2->L1 inter-area routes as L1 intra-area routes and advertise them
  back into L2, which can cause routing loops, sub-optimal routing, or
  routing instability. For this reason it is recommended that
  implementations by default do not advertise any L2 routes into L1.

## MUST / SHOULD Notes

- Section 2: L1L2 routers MUST set the up/down bit to one for prefixes
  derived from L2 routing advertised into L1 LSPs; MUST set it to zero
  for all other IP prefixes in L1 or L2 LSPs.
- Section 2: Prefixes with the up/down bit set that are learned via L1
  routing MUST NEVER be advertised by L1L2 routers back into L2.
- Section 2: L1L2 routers MUST never advertise L2->L1 inter-area routes
  learned via L1 routing back into L2.
- Sections 3.1, 3.3: The combination "IP Internal Reachability
  Information" with external metric-type must never be built; routers
  must ignore such a prefix on receipt.
- Section 3.3: It is recommended that the default configuration of L1L2
  routers does not advertise any L2 routes into L1.
