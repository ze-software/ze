**Purpose:** Turns the BCP 172 advice into a standards requirement: a BGP speaker does
not advertise an UPDATE whose AS_PATH holds an AS_SET (segment type 1) or an
AS_CONFED_SET (segment type 4), and handles a received one by treat-as-withdraw.

## Wire Format

No new format. The segment types are those of RFC 4271 Section 4.3 and RFC 5065
Section 3:

```
AS_PATH / AS4_PATH segment:
+-----------------+-------------------+------------------------------+
| Type (1 octet)  | Length (1 octet)  | ASNs (Length x 2 or 4 octets) |
+-----------------+-------------------+------------------------------+
Type 1 AS_SET            deprecated by RFC 9774
Type 2 AS_SEQUENCE
Type 3 AS_CONFED_SEQUENCE
Type 4 AS_CONFED_SET     deprecated by RFC 9774
```

## Ze Implementation

### Receiving

`Session.enforceRFC7606` reaches the attribute validators through
`ValidateUpdateRFC7606Peer`. `validateASPathAttr` (code 2) runs its structure walk first,
so a structurally malformed AS_PATH keeps its RFC 7606 Section 7.2 description, then
asks `ASPathSetSegment`. `validateAS4PathAttr` (code 17) asks `ASPathSetSegment` before
its AS 0 check, because treat-as-withdraw outranks the attribute discard RFC 6793
Section 6 chooses (RFC 7606 Section 3(h): "the approach with the strongest action MUST
be used"). The verdict applies on every session, whatever the negotiated AS width.
`ASPathSetSegment` judges a fully framed path only, so a misframed AS4_PATH draws no
set verdict.

### Sending

`Session.writeUpdateBody` is the writer every UPDATE producer reaches: relay, API batch,
static routes, RIB replay. Before the AIGP guard it asks `transmittedPathHoldsSet`, which
judges every AS_PATH and AS4_PATH occurrence in the body. When one holds a set,
`writeUpdateAsWithdrawal` writes the withdrawal form instead, counts the routes in
`ze_bgp_as_set_withdrawn_total`, and logs a rate-limited warning naming the peer, the
cause and the fix. The `raw` write of `send bgp <peer> raw` is exempt (owner decision
2026-10-18, Q-4 (b)): it is a test instrument for operator-chosen bytes.

### Owner-approved deviation: received AS_SET on a peer migrated from ExaBGP

Section 3: "Unless explicitly configured by a network operator to do otherwise (e.g.,
during a transition phase), BGP speakers:" ... "MUST use the "treat-as-withdraw" error
handling behavior per [RFC7606] upon reception of BGP UPDATE messages containing AS_SETs
or AS_CONFED_SETs in the AS_PATH or AS4_PATH [RFC6793]."

The owner decided (`ai/META-DECISIONS.md`, "ExaBGP compatibility") that a received
AS_SET is accepted on a peer whose `session as-set accept` (`ze-bgp-conf.yang`) the
operator set. The leaf is an ordinary operator leaf that any config may carry; ExaBGP 6.0
(f9bfb853b) has the neighbor leaf `as-set accept`, and `ze exabgp migrate` writes the ze
leaf for it. On such a peer `ValidateUpdateRFC7606Peer`, given `acceptASSet` by
`Session.validateRFC7606Attrs`, hands the policy to every registered attribute validator
(`receivePolicy`, `message/rfc9774.go`), and the AS_PATH and AS4_PATH validators skip the
set scan and keep every other check (structure, AS 0). The default, `withdraw`, is the
RFC's behavior and is what RFC9774-3-2 counts.

|-------|-------|

| Scope | Peers whose config carries `session as-set accept`, set by the operator; `ze exabgp migrate` writes it for an ExaBGP `as-set accept` neighbor |
| Counted | No. The deviation is not counted as conformant; RFC9774-3-2 is counted on the default behavior only |
| Proof | `TestRFC9774ReceiveASSetAcceptedByOperator` (reactor), `TestValidateUpdateAcceptASSetKeepsSetsOnly` (message) |

The send half (RFC9774-3-1) has no deviation in the code yet. The owner decision lets a
route from an ExaBGP script through the bridge carry a set, while Ze's own API and
plugins never originate one; until that exemption exists, a bridge route with a set is
written as its withdrawal like every other.

### Aggregation: not implemented

Ze has no route aggregation, and RFC 4271 Section 9.1 makes it optional: "Route
aggregation and information reduction can optionally be performed within this phase."
The obligations of Sections 5.2, 6.1 and 6.2 are conditional on aggregation, so they
are excluded from the conformance count as `feature-out-of-scope` in
`rfc/extraction/rfc9774.json`. The SHOULD of Section 5 is a quotation of RFC 4271
Section 5.1.6 and belongs to that document.

### Section 4

Section 4 restates RPKI behavior and binds nothing new. Ze's ROV
(`internal/component/bgp/plugins/rpki/validate.go`) and ASPA
(`internal/component/bgp/plugins/rpki/aspa_verify.go`) set handling stays as written.
