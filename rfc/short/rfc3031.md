**Purpose:** Defines the architecture for Multiprotocol Label Switching (MPLS), a forwarding mechanism that assigns short fixed-length labels to packets at ingress and uses them for forwarding decisions at each hop, replacing network-layer header analysis.

## Core Concepts

### Label Switching Router (LSR)

An LSR forwards packets based on labels rather than network-layer headers. It maintains a Label Information Base (LIB) mapping incoming labels to outgoing labels and next hops.

| Role | Description |
|------|-------------|
| Ingress LSR | Classifies packet into FEC, pushes label(s), forwards into MPLS domain |
| Transit LSR | Swaps incoming label for outgoing label, forwards to next hop |
| Egress LSR | Pops label, forwards based on network-layer header |

### Forwarding Equivalence Class (FEC)

A group of packets forwarded the same way (same path, same treatment). A packet is assigned to a FEC once, at ingress. The FEC determines the label.

Common FEC types:
- **Prefix FEC:** destination IP prefix (most common)
- **Host FEC:** specific host address
- **Application FEC:** identified by port, protocol, or other criteria

### Label

A short, fixed-length, locally significant identifier. Labels have meaning only on the link between two adjacent LSRs.

| Property | Value |
|----------|-------|
| Length | 20 bits (in shim header, per RFC 3032) |
| Scope | Local to the link between label assigner and receiver |
| Assignment | By downstream LSR (in downstream modes) |
| Lifetime | Until withdrawn or session ends |

### Label Stack

Packets carry an ordered set of labels (a stack). The top label is used for forwarding at each hop. Label stacking enables hierarchical LSPs (tunnels within tunnels).

Operations:
- **Push:** add label to top of stack (ingress or tunnel entry)
- **Pop:** remove top label (egress or penultimate hop)
- **Swap:** replace top label with new label (transit)

## Label Distribution

### Modes

| Mode | Description |
|------|-------------|
| Downstream Unsolicited | LSR distributes labels for its FECs to peers without being asked |
| Downstream On-Demand | LSR distributes labels only when a peer requests them |

### Retention Modes

| Mode | Description |
|------|-------------|
| Liberal | Keep all received labels, even for FECs not currently using that peer as next hop |
| Conservative | Keep only labels from the current next hop for each FEC |

### Label Distribution Protocols

Labels can be distributed by:
- **LDP (RFC 5036):** dedicated label distribution protocol
- **RSVP-TE (RFC 3209):** RSVP with traffic engineering extensions
- **BGP (RFC 8277):** BGP labeled unicast, L3VPN (RFC 4364)
- **IS-IS/OSPF extensions:** segment routing

### Label Spaces

| Type | Description |
|------|-------------|
| Per-platform | One label space for entire LSR (common for LDP) |
| Per-interface | Separate label space per interface (used with ATM/FR) |

## Label Switched Path (LSP)

A path through the MPLS network for a given FEC. Established by label distribution between adjacent LSRs.

### LSP Types

| Type | How Established | Routing |
|------|-----------------|---------|
| Hop-by-hop | LDP, follows IGP shortest path | Dynamic |
| Explicitly routed | RSVP-TE, operator-specified path | Constrained |

### Penultimate Hop Popping (PHP)

The second-to-last LSR pops the label stack so the egress LSR does not need to do both a label lookup and a network-layer lookup. Signaled by the egress LSR assigning Implicit NULL (label 3) to the FEC.

## MUST Requirements

### Label Assignment
- "the label value is used to look up the NHLFE" (Section 3.8) -- label forwarding MUST use the Next Hop Label Forwarding Entry
- "label merging...upstream labels...MUST all map into the same LER" (Section 3.14) -- merged labels must share the same egress point

### Forwarding
- "If the packet's label stack is empty...forward it based on its network layer header" (Section 3.10) -- unlabeled packets use conventional forwarding
- Label stack processing: top label only determines forwarding; lower labels are opaque to transit LSRs

### Loop Prevention
- "TTL field...MUST be decremented" (Section 3.24) -- each LSR must decrement the TTL in the label stack entry to prevent loops
- If TTL reaches 0, packet MUST be discarded

## SHOULD/MAY Requirements

- [SHOULD] "an LSR SHOULD be able to support both liberal and conservative label retention" (Section 3.15)
- [SHOULD] LSR SHOULD support penultimate hop popping (Section 3.16)
- [MAY] LSR may support label merging to reduce label consumption (Section 3.14)
- [MAY] Explicitly routed LSPs may be used for traffic engineering (Section 2.1)

## Validation

| Check | Valid | Invalid Action |
|-------|-------|----------------|
| Unknown label in lookup | No | Discard packet |
| Empty label stack at transit | No | Forward as unlabeled if IP, else discard |
| TTL reaches 0 | No | Discard, send ICMP Time Exceeded if possible |
| Label outside valid range | No | Implementation-dependent |

## Next Hop Label Forwarding Entry (NHLFE)

Each NHLFE specifies:
1. The next hop
2. The operation on the label stack (swap, push, pop)
3. The outgoing label (for swap/push)
4. The outgoing interface
5. Any additional information (QoS, encapsulation)

## Incoming Label Map (ILM)

Maps incoming labels to NHLFEs. When a labeled packet arrives, the top label is looked up in the ILM to find the corresponding NHLFE.

## FEC-to-NHLFE Map (FTN)

Maps FECs to NHLFEs. Used at ingress to assign labels to unlabeled packets entering the MPLS domain.

## Algorithms

### Forwarding Algorithm

```
if packet.has_label_stack:
    nhlfe = ILM_lookup(packet.top_label)
    if nhlfe is None:
        discard(packet)
        return
    ttl = packet.top_label.TTL - 1
    if ttl == 0:
        discard(packet)
        send_icmp_time_exceeded()
        return
    execute(nhlfe.operation, packet)  // swap, push, or pop
    forward(packet, nhlfe.next_hop, nhlfe.interface)
else:
    fec = classify(packet)
    nhlfe = FTN_lookup(fec)
    if nhlfe is None:
        ip_forward(packet)  // conventional routing
        return
    push_label(packet, nhlfe.label)
    forward(packet, nhlfe.next_hop, nhlfe.interface)
```

## Pitfalls

### Edge Cases
- **Label merging with different QoS:** merged streams lose per-flow QoS distinction
- **PHP with multiple FECs:** if egress uses same label for multiple FECs, PHP exposes ambiguity
- **Liberal retention memory:** keeping all labels can consume significant memory in large networks

### Interop
- **Per-platform vs per-interface label space:** LSRs must agree on label space type for each link
- **Label distribution protocol mismatch:** both ends of a link must use the same protocol (LDP, RSVP-TE, or BGP)
- **Unsolicited vs on-demand:** mismatch can cause label distribution failure

### Security
- **Label spoofing:** no built-in authentication of label assignments
- **MPLS domain trust:** LSRs must be trusted; compromised LSR can redirect traffic
- **TTL manipulation:** attacker can set high TTL to create forwarding loops

## ZeBGP Implementation Notes

RFC 3031 is the architectural foundation for MPLS in Ze:
- Ze implements label switching via the kernel FIB backend (netlink) and VPP backend
- Labels arrive via BGP labeled unicast (RFC 8277) and optionally LDP (RFC 5036)
- The sysrib carries labels in `BestChangeEntry.Labels`
- Kernel MPLS requires `sysctl net.mpls.platform_labels` and per-interface `net.mpls.conf.<iface>.input`
- Ze supports push (imposition), swap (transit), and pop (disposition) via netlink `RTA_ENCAP` and `AF_MPLS`
