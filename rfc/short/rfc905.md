# RFC 905 - ISO Transport Protocol Specification (ISO DP 8073)

## Meta

| Field | Value |
|-------|-------|
| RFC | 905 |
| Title | ISO Transport Protocol Specification (ISO DP 8073) |
| Status | Unknown (republication of ISO DP 8073 as an RFC) |
| Date | April 1984 |
| Authors | International Organization for Standardization (ISO TC97/SC16) |
| Obsoletes | RFC 892 |
| Updated by | - (not stated in the document text) |

**Purpose:** RFC 905 republishes the ISO Transport Protocol (ISO DP 8073).
For the Ze OSPFv2 work only ONE part of it matters: the Fletcher checksum
algorithm specified for Class 4 transport in Section 6.17 and Annex B. This
same algorithm (sometimes cited via its ISO 8473 / CLNP appearance) is the
"Fletcher-16" checksum reused by OSPFv2 (RFC 2328 Section 12.1.7) for the LSA
LS Checksum and by IS-IS (ISO/IEC 10589 clause 7.3.11) for the LSP checksum.

**Scope:** This summary covers only the checksum: the two running-sum
formulas (Section 6.17.3), the modulo-255 arithmetic conventions
(Annex B.2), the two-pass generation procedure that derives the two checksum
octets X and Y so the sums fall to zero at the placement position
(Annex B.3), the verification procedure (Annex B.4), and the checksum
parameter wire encoding (Section 13.2.3.1). Everything else in the transport
protocol (connection establishment, classes, TPDU formats) is out of scope.

## Why Ze Cares (OSPF / IS-IS Reuse)

The Fletcher-16 algorithm RFC 905 specifies is the algorithm OSPFv2 and
IS-IS use for their link-state checksums. The algorithm is identical; only
the COVERED BYTE RANGE differs per protocol.

| Protocol | Spec | Covered region | Checksum field position |
|----------|------|----------------|-------------------------|
| ISO 8073 transport | RFC 905 Section 6.17, Annex B | whole TPDU, octets 1..L | the 2 checksum-parameter octets, at position n |
| IS-IS LSP | ISO/IEC 10589 clause 7.3.11 | from the octet after Remaining Lifetime to end | offset 12 in that region (after LSPID + Sequence Number) |
| OSPFv2 LSA | RFC 2328 Section 12.1.7 | LSA from the Options field to end, EXCLUDING the 2-byte LS Age | the 2-byte LS Checksum field |

For OSPF specifically: the Fletcher-16 covers the LSA starting at the
Options field (byte 2 of the 20-byte LSA header), i.e. it EXCLUDES LS Age
(bytes 0-1) because LS Age changes hop by hop. The LS Checksum field is
treated as zero during the forward (step-1) computation, then the two-octet
result is placed by the Annex B.3 adjustment. The in-tree IS-IS
implementation is `internal/plugins/isis/packet/checksum.go`; OSPF has its
own copy at `internal/plugins/ospf/types/checksum.go` with the OSPF covered
range (the two are kept separate because the ranges differ).

## Checksum Formulas (Section 6.17.3)

Section 6.17.3 states the two conditions a correctly checksummed TPDU
satisfies. Using the RFC's notation (`i` = octet position 1..L, `a[i]` =
octet value, `L` = TPDU length, arithmetic "module 255" [sic, modulo 255]):

| # | Condition (verbatim form) | Meaning |
|---|---------------------------|---------|
| 1 | SUM (i=1..L) of a[i] EQUALS 0 (mod 255) | the plain octet sum is zero |
| 2 | SUM (i=1..L) of i*a[i] EQUALS 0 (mod 255) | the position-weighted octet sum is zero |

A receiver whose received TPDU does not satisfy both formulas (and for which
checksum use was agreed) shall discard the TPDU (Section 6.17.3). The
efficient running-sum realisation of these two conditions is given in Annex
B; condition 1 corresponds to the C0 sum and condition 2 to the C1 sum.

Note 3 (Section 6.17.3): the checksum is cheap to compute but "will not
detect insertion or loss of leading or trailing zeros and will not detect
some octets misordering." This is the known Fletcher limitation.

## Arithmetic Conventions (Annex B.2)

Addition is performed in one of two equivalent modes:

| Mode | Rule |
|------|------|
| Modulo 255 | all additions reduced mod 255 |
| One's complement | if any variable reaches minus zero (255) it is treated as plus zero (0) |

The modulus is 255 (NOT 256): the all-zero 16-bit checksum field value is
reserved to mean "checksum not computed", so the arithmetic is over the
255-residue field. A computed octet value of 0 may therefore be emitted as
255 (which is congruent to 0 mod 255) to keep the field from colliding with
the reserved all-zero value.

## Symbols (Annex B.1)

| Symbol | Meaning |
|--------|---------|
| C0, C1 | the two running-sum variables |
| i | position of an octet within the TPDU (1-based) |
| n | position of the FIRST octet of the checksum parameter |
| L | length of the complete TPDU (octets) |
| X | value of the first checksum octet (stored at octet n) |
| Y | value of the second checksum octet (stored at octet n+1) |

## Generation Procedure (Annex B.3) - Two-Pass

The "two-pass" name reflects: first run the sums over the message with the
checksum field zeroed (pass 1), then solve a closed-form adjustment for X and
Y (pass 2) so re-running the sums over the message WITH X, Y in place yields
both sums zero. The RFC presents it as five steps:

| Step | Action (verbatim intent) |
|------|--------------------------|
| B.3.1 | Set up the complete TPDU with the checksum parameter field set to zero. |
| B.3.2 | Initialize C0 and C1 to zero. |
| B.3.3 | Process each octet sequentially from i = 1 to L by: (a) add the octet value to C0; then (b) add C0 to C1. |
| B.3.4 | Calculate X and Y such that: X = -C1 + (L-n)*C0 ; Y = C1 - (L-n+1)*C0 |
| B.3.5 | Place X and Y in octets n and (n+1) respectively. |

The two B.3.4 equations are evaluated modulo 255 (Annex B.2). They are the
exact text of the RFC. An algebraically equivalent form used by the in-tree
IS-IS implementation is, with a 0-based offset `k = n-1` and `m = L - k`:
X = (m-1)*C0 - C1 and Y = C1 - m*C0 (mod 255); both forms produce the same
two octets. A computed octet of 0 is stored as 255 (see Annex B.2 / the
modulus note).

## Verification Procedure (Annex B.4)

| Step | Action |
|------|--------|
| B.4.1 | Initialize C0 and C1 to zero. |
| B.4.2 | Process each octet of the TPDU from i = 1 to L by: (a) add the octet value to C0; then (b) add C0 to C1. The checksum octets X, Y are INCLUDED this time. |
| B.4.3 | After all octets processed, if either C0 or C1 is non-zero, the formulas in 6.17 are not satisfied (the checksum is wrong). |

Annex B.4 Note: because of how the algorithm is constructed, it is NOT
necessary to compare the stored checksum bytes explicitly. Running the sums
over the whole region (checksum field included) and checking C0 == 0 and
C1 == 0 is sufficient. This is exactly what the in-tree `VerifyChecksum`
does.

## Checksum Parameter Encoding (Section 13.2.3.1)

All TPDU types may carry a 16-bit checksum parameter in their variable part.
It MUST be present in the CR TPDU and in all other TPDUs unless non-use of
the checksum was selected. (Class 4 only.)

| Field | Value |
|-------|-------|
| Parameter Code | 1100 0011 (0xC3) |
| Parameter Length | 2 |
| Parameter Value | result of the checksum algorithm (the two octets X, Y from Section 6.17 / Annex B) |

## Constants

| Constant | Value | Source |
|----------|-------|--------|
| Modulus | 255 (mod-255 / one's-complement, NOT 256) | Annex B.2 |
| Checksum field width | 2 octets (16 bits) | Section 13.2.3.1 |
| Placement offset (transport) | octet n (B.3.5), where n is the first checksum-parameter octet | Annex B.1, B.3.5 |
| Placement offset (IS-IS LSP) | offset 12 within the checksummed region | ISO/IEC 10589 7.3.11 (in-tree) |
| Placement offset (OSPF LSA) | the LS Checksum field, with the covered region starting at the Options field (excluding the 2-byte LS Age) | RFC 2328 Section 12.1.7 |
| Reserved field value | all-zero 16-bit checksum means "checksum not computed" | Annex B.2 (modulus note) |
