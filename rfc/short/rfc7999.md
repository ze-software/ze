## Scope

Registers one well-known BGP community, BLACKHOLE, and states how networks use it
for destination-based blackholing. The community is advisory: its presence asks
the receiving network to discard any traffic sent toward the tagged prefix (§2).
Accepting and honoring it, or ignoring it, is a choice each operator makes (§3.1).

The document defines no message, attribute, capability, or NLRI of its own, and
places no restriction on AFI or SAFI.

## Requirements Language (§1.1)

The RFC 2119 key words are normative "only when they appear in all upper case".
The same words in lower case or mixed case are English words with no normative
meaning. RFC 7999 uses both forms. §3.2, §3.3, and §6 each carry a lower-case
"should" that gives guidance and creates no obligation. "Guidance Without an
RFC 2119 Keyword" below collects those statements so they are not read as
requirements.

## Encoding

RFC 7999 defines no wire format of its own. BLACKHOLE is one 4-octet element of
the RFC 1997 COMMUNITIES path attribute. That attribute is optional transitive,
is of variable length, carries Type Code 8, and holds a set of 4-octet values
(RFC 1997, "COMMUNITIES attribute").

| Octet | Value | Meaning |
|-------|-------|---------|
| 0-1 | 0xFFFF | High-order two octets. RFC 1997 reserves the range 0xFFFF0000 to 0xFFFFFFFF |
| 2-3 | 0x029A | Low-order two octets. 666 in decimal (§5) |

Network byte order applies, with no exception.

## Constants

| Name | Value | Usage |
|------|-------|-------|
| BLACKHOLE | 0xFFFF029A | Well-known transitive community. IANA registered it in the "BGP Well-known Communities" registry (§5) |

The 32-bit value is 4294902426 in decimal. Operators write it as 65535:666, which
follows from the octet split above. RFC 7999 states the hexadecimal value and the
low-order decimal only, and uses neither of these two forms.

## Operation

### Sender (§3.1)

1. The network under DDoS duress selects a prefix that covers the victim
   addresses.
2. It announces that prefix with the BLACKHOLE community attached.
3. On a bilateral peering relationship, it advertises the community only after
   the two networks agree to use it.

### Receiver (§3.1, §3.2, §3.3)

1. The receiver decides by local routing policy whether to honor or ignore the
   community. Both are conforming.
2. A receiver that honors it discards traffic sent toward the tagged prefix.
3. A receiver that does not use the community ignores it.
4. The receiver limits the scope of the prefix with NO_ADVERTISE, NO_EXPORT, or
   a similar community.

## Validation

| Check | Valid | Invalid action |
|-------|-------|----------------|
| Prefix coverage, bilateral session | The announced prefix is covered by an equal or shorter prefix the neighboring network is authorized to advertise | Do not accept the announcement and do not honor it (§3.3) |
| Session agreement, bilateral session | The receiving party agreed to honor BLACKHOLE on that BGP session | Do not accept the announcement and do not honor it (§3.3) |
| Peer authorization | The peer announcing the prefix is authorized to announce it | Filter the announcement (§6) |
| COMMUNITIES attribute form | Well-formed attribute | Treat the route as withdrawn, by the RFC 7606 process (§3.3) |

## MUST Requirements

| Group | Requirement | Section |
|-------|-------------|---------|
| Tx | On a bilateral peering relationship, the two networks agree on use of BLACKHOLE before it is advertised | §3.1 |
| Rx | On a bilateral session, accept and honor a BLACKHOLE announcement only when the announced prefix is covered by an equal or shorter prefix the neighbor is authorized to advertise | §3.3 |
| Rx | On a bilateral session, accept and honor a BLACKHOLE announcement only when the receiving party agreed to honor BLACKHOLE on that session | §3.3 |
| Operator | Origin validation, such as RFC 6811, does not inadvertently block legitimate BLACKHOLE announcements | §3.3 |

The two Rx rows are the two bullet conditions of one sentence in §3.3. Both hold,
or the announcement is neither accepted nor honored.

The Operator row binds the operator rather than the BGP speaker. RFC 7999 names no
mechanism for it.

RFC 7999 states no MUST NOT, SHALL, SHALL NOT, or REQUIRED outside the §1.1 key
words list.

## SHOULD and MAY

- [SHOULD] A network that does not use BLACKHOLE ignores it on receipt (§3.1): a network that neither honors nor ignores it acts on a signal it never agreed to.
- [SHOULD] A network that announces a covering prefix under DDoS duress attaches BLACKHOLE (§3.1): without the community the neighbor reads an ordinary announcement and discards nothing.
- [SHOULD] The receiver adds NO_ADVERTISE, NO_EXPORT, or a similar community (§3.2): without one, the blackhole prefix can leak outside the local AS and drop traffic in networks that agreed to nothing.
- [SHOULD] The choice of the community that prevents propagation follows the operator's routing policy (§3.2).
- [SHOULD] A route server or other multilateral speaker applies the same two conditions as a bilateral speaker (§3.3).
- [SHOULD NOT] Absent an explicit configuration directive from the operator, a network element does not discard traffic toward a BLACKHOLE-tagged prefix (§4): a device that honors the community by default lets any peer drop traffic for a prefix.
- [SHOULD] The receiving speaker applies strict filtering to confirm the announcing peer is authorized for the prefix (§6): §6 names unauthorized addition of BLACKHOLE as a denial-of-reachability vector.
- [RECOMMENDED] Operators apply best common practices to protect their BGP sessions, RFC 7454 among them (§6).
- [MAY] BLACKHOLE is used in all bilateral and multilateral BGP deployment scenarios (§3.1).
- [MAY] A network under DDoS duress announces a prefix covering the victim addresses (§3.1).
- [MAY] BLACKHOLE is one of the trigger communities of a destination-based RTBH configuration, RFC 5635 (§3.1).
- [MAY] A vendor provides a configuration shorthand for the value. The suggested string is "blackhole" (§4).

## Guidance Without an RFC 2119 Keyword

These statements shape deployments and impose nothing. §1.1 puts the lower-case
forms outside the normative set.

| Statement | Section |
|-----------|---------|
| Announcements longer than /24 for IPv4 and /48 for IPv6 are usually not accepted on the Internet (RFC 7454 Section 6.1.3) | §3.3 |
| Blackhole prefix length should be as long as possible, and is typically /32 for IPv4 or /128 for IPv6, to limit the impact on adjacent address space that is not under duress | §3.3 |
| Extreme caution should be used when propagating a BLACKHOLE-tagged prefix outside the local routing domain, unless policy aims at that | §3.2 |
| BLACKHOLE is not intended for use with flow specification NLRI (RFC 5575) | §3.3 |
| Operators are encouraged to store BGP updates carrying BLACKHOLE, for long-term analysis or internal audit | §3.3 |
| BGP announcements carrying BLACKHOLE should only be accepted and honored if the neighboring network is authorized to advertise the prefix. The validation method follows the operator's routing policy | §6 |
| In a multilateral peering relationship, the decision to honor or ignore BLACKHOLE follows the operator's routing policy | §3.1 |

## Security

| Vector | Mitigation the RFC names | Section |
|--------|--------------------------|---------|
| An adversary adds BLACKHOLE to a prefix and causes a denial-of-service attack based on denial of reachability | Strict filtering that confirms the announcing peer is authorized for the prefix | §6 |
| A forwarding agent alters, adds, or removes communities. Recipients cannot detect the change, and BGPsec does not resolve it | None. §6 records the exposure | §6 |
| A blackhole prefix leaks outside the local AS | NO_ADVERTISE, NO_EXPORT, or a similar community | §3.2 |

## Compatibility

| Peer behavior | Result |
|---------------|--------|
| Peer does not use BLACKHOLE | It ignores the community (§3.1). The prefix stays an ordinary announcement and is routed normally |
| Peer uses a per-network blackhole community instead | BLACKHOLE is a value inside an existing attribute, so there is no capability to negotiate and no fallback to signal. The two mechanisms coexist on the same session |
| Peer strips or rewrites communities | The signal is lost or forged. §6 states BGP has no mechanism against this |

## Errata

No errata are recorded for RFC 7999. Checked at
https://www.rfc-editor.org/errata/rfc7999 on 2026-08-08 .

One typographic defect in the published text carries no erratum: §3.1 reads "a
network that it not using it", where the sense is "that is not using it". It
changes no obligation.
