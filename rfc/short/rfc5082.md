# RFC 5082: The Generalized TTL Security Mechanism (GTSM)

## Meta

| Field | Value |
|-------|-------|
| RFC | 5082 |
| Title | The Generalized TTL Security Mechanism (GTSM) |
| Status | Standards Track |
| Date | October 2007 |
| Obsoletes | RFC 3682 |
| Obsoleted-by | - |
| Updates | - |

**Purpose:** Protects a router's control plane from off-link CPU-exhaustion
attacks. A GTSM-enabled session sends every packet with IP TTL (IPv4) or Hop
Limit (IPv6) 255, and the receiver refuses a packet from that session whose
inbound TTL is below the expected value. A packet that crossed a router arrives
with a lower TTL, so 255 cannot be forged from off-link.

RFC 5082 defines no wire format and no protocol messages. It adds two steps to
the IP send and receive paths of a protocol that adopts it. Ze applies GTSM to
BGP (`connection { ttl { max; set; min } }`), to BFD single-hop and multi-hop,
and to VRRP.

## TTL Semantics

| Term | Meaning |
|------|---------|
| TTL | RFC 5082 Section 1 uses "TTL" for both the IPv4 Time to Live field and the IPv6 Hop Limit field. From GTSM's point of view they have identical semantics |
| 255 | The maximum value of both fields, and the value a GTSM sender sets |
| Trusted | A received packet that belongs to a GTSM-enabled session and whose TTL is inside the expected range |
| Dangerous | A received packet that belongs to a GTSM-enabled session and whose TTL is outside the expected range |
| Unknown | A received packet that no GTSM-enabled session claims. GTSM makes no judgment about it |

## Encoding Rules

1. **Transmit:** every IP packet of a GTSM-enabled session leaves with TTL 255.
   Related ICMP error messages of that session leave with TTL 255 too.
2. **No decrement:** an architecture that decrements the TTL of control-plane
   originated traffic in the forwarding plane must not do so for a GTSM-enabled
   session.
3. **Single hop only:** RFC 5082 Section 6 limits GTSM to directly connected
   peers. The multi-hop form, where the receiver accepts a TTL inside a
   configured number of hops from 255, is Appendix A and is non-normative.

## Decoding Rules

1. Classify each received control-plane packet as Trusted, Dangerous, or
   Unknown.
2. Deliver Trusted and Unknown packets. GTSM processing never drops them.
3. A Dangerous packet may be dropped, and should not compete for resources with
   the other two classes.

## Validation

| Check | Valid | Invalid Action |
|-------|-------|----------------|
| Inbound TTL, single-hop GTSM session | 255 | Classify Dangerous; MAY drop |
| Inbound TTL, session with a configured hop count N | 255-N+1 through 255 | Classify Dangerous; MAY drop |
| Inbound TTL, no GTSM-enabled session claims the packet | any | Classify Unknown; MUST NOT drop as part of GTSM processing |
| Outbound TTL, GTSM-enabled session | 255 | The peer's receive check rejects the packet |

## MUST Requirements

### Tx (Sender)
- "The TTL field in all IP packets used for transmission of messages associated
  with GTSM-enabled protocol sessions MUST be set to 255" (Section 3)
- "This also applies to the related ICMP error handling messages" (Section 3),
  restated in Section 6.1 as "This specification mandates setting and verifying
  TTL=255 of those as well as the main protocol packets"
- "The TTL of GTSM-enabled sessions MUST NOT be decremented" (Section 3)

### Rx (Receiver)
- "MUST NOT drop (as part of GTSM processing) packets classified as Trusted or
  Unknown" (Section 3)

### Negotiation
- "protocol messages used for such negotiation MUST be authenticated using other
  security mechanisms to prevent DoS attacks" (Section 2.1), and the sentence is
  conditional on dynamic GTSM negotiation, which RFC 5082 neither assumes nor
  defines

## SHOULD/MAY

### SHOULD
- "[SHOULD NOT] be enabled by default in order to remain backward-compatible
  with the unmodified protocol" (Section 3) - GTSM added to an existing protocol
  such as BGP, LDP, or MSDP; consequence: a peer that does not send TTL 255 is
  locked out
- "[SHOULD] ensure that packets classified as Dangerous do not compete for
  resources with packets classified as Trusted or Unknown" (Section 3) -
  consequence: a flood of Dangerous packets consumes the CPU the mechanism
  exists to protect

### MAY
- "[MAY] drop packets classified as Dangerous" (Section 3) - when to use: the
  session is single-hop and the operator wants the strongest filter
- "[MAY] suggest the use of GTSM provided that GTSM would only be enabled if
  both peers agree to use it" (Section 3) - when to use: the protocol defines a
  built-in dynamic capability negotiation for GTSM

### OPTIONAL
- "[OPTIONAL] Use of GTSM is OPTIONAL, and can be configured on a per-peer
  (group) basis" (Section 2)

### RECOMMENDED
- "[RECOMMENDED] it is highly RECOMMENDED for GTSM-protected protocols to avoid
  fragmentation and reassembly by manual MTU tuning, using adaptive measures
  such as Path MTU Discovery (PMTUD), or any other available method"
  (Section 5.4) - a non-initial fragment carries no Layer 4 information, so it
  classifies as Unknown and the reassembled packet inherits that

## Error Handling

| Condition | Detect How | Response |
|-----------|------------|----------|
| Packet of a GTSM session arrives with TTL below the floor | Kernel `IP_MINTTL` / `IPV6_MINHOPCOUNT` for TCP, `IP_RECVTTL` / `IPV6_RECVHOPLIMIT` plus an application check for UDP | Discard before the protocol sees it |
| Packet arrives with TTL 255 on a session that expects it | Same | Deliver |
| Packet matches no GTSM session | No socket carries a TTL floor | Deliver |

## Constants

| Name | Value | Usage |
|------|-------|-------|
| GTSM TTL | 255 | Transmit value, and the single-hop receive floor |
| Multi-hop receive floor | 255 - N + 1 | N is the configured hop count. Appendix A, non-normative |

## Algorithms

### Sending

```
For each packet of a GTSM-enabled session:
    Set IPv4 TTL, or IPv6 Hop Limit, to 255
    Do not let the forwarding plane decrement it
```

### Receiving

```
For each packet addressed to the control plane:
    If no GTSM-enabled session claims it:
        Classify Unknown; deliver
    Else if its TTL is inside the session's expected range:
        Classify Trusted; deliver
    Else:
        Classify Dangerous; drop or rate-limit
```

## Pitfalls

### Edge Cases
- **The listen socket.** A GTSM peer that initiates the TCP connection gates the
  SYN-ACK too. A listen socket left at the default TTL emits a SYN-ACK the peer
  drops, and the session never opens even though the per-connection option is
  correct.
- **Related ICMP errors.** RFC 5082 extends the TTL 255 rule to the ICMP errors
  of the session. Linux generates those from the IP stack with the system
  default TTL, not with the socket's `IP_TTL`, so a socket option alone does not
  reach them.
- **Fragments.** A non-initial fragment carries no Layer 4 header, so it cannot
  be tied to a session and classifies as Unknown.

### Interop
- **RFC 3682 peers.** RFC 5082 Section 6.1 says setting TTL 255 on related
  messages does not disturb an RFC 3682 implementation, but requiring it can:
  some RFC 3682 senders emit related messages with TTL 64.
- **Uniform-model MPLS.** RFC 5082 Section 5.2.2 shows the GTSM check fails over
  a Uniform Model LSP of more than one hop, because the exposed TTL is the popped
  label's.

### Security
- **On-link attackers.** Section 5.3: an attacker on a directly connected
  interface can still spoof a peer address unless ingress filtering is applied.
- **Not authentication.** Section 1: GTSM does not secure against on-the-wire
  attacks such as packet spoofing or replay.
