# RFC 6286: Autonomous-System-Wide Unique BGP Identifier for BGP-4

## Meta

| Field | Value |
|-------|-------|
| RFC | 6286 |
| Title | Autonomous-System-Wide Unique BGP Identifier for BGP-4 |
| Status | Standards Track |
| Date | June 2011 |
| Updates | RFC 4271 |
| Errata | None |

**Purpose:** Relaxes RFC 4271's definition of the BGP Identifier. RFC 4271 required it to be a
valid unicast IPv4 host address assigned to the speaker and globally unique; that is impossible in
an IPv6-only network. RFC 6286 redefines it as a 4-octet, unsigned, non-zero integer that need only
be unique within an AS, and adjusts the two places where the old definition was load-bearing: OPEN
error handling and connection collision resolution.

## Definition (Section 2.1)

> "The BGP Identifier is a 4-octet, unsigned, non-zero integer that should be unique within an AS.
> The value of the BGP Identifier for a BGP speaker is determined on startup and is the same for
> every local interface and every BGP peer."

Three separable properties:

| Property | Level | Ze |
|----------|-------|-----|
| 4-octet unsigned | structural | the wire field is `uint32` (`internal/component/bgp/message/open.go:55`) |
| non-zero | enforced on RECEPTION by Section 2.2 (the RFC's own rail) | `ValidateBGPIdentifier` rejects a received zero with Bad BGP Identifier; `parseRouterID` additionally refuses to configure ze's own identifier as 0.0.0.0 |
| AS-wide unique | lowercase "should" | enforced by default via the reactor's claim registry; `bgp/session/allow-shared-router-id` opts out |

RFC 4271 Section 6.2 already made a zero identifier invalid by requiring "a valid unicast IP host
address"; RFC 6286 drops the IP-address requirement and states the zero case explicitly instead of
leaving it implied. Either way the check belongs on the receiving speaker.

**"should" is lowercase in the RFC text**, not the RFC 2119 SHOULD keyword. Uniqueness is therefore
advisory: a deployment that shares one identifier between two peers of the same AS (one anycast
speaker peering over IPv4 and IPv6) is conformant, which is why ze offers the opt-out.

## Error Handling (Section 2.2)

> "If the BGP Identifier field of the OPEN message is zero, or if it is the same as the BGP
> Identifier of the local BGP speaker and the message is from an internal peer, then the Error
> Subcode is set to 'Bad BGP Identifier'."

This replaces RFC 4271 Section 6.2's "syntactically incorrect" test (which meant "a valid unicast IP
host address"). Two rejection conditions, and the second is gated on the peer being INTERNAL:

| Received BGP Identifier | Peer | Outcome |
|-------------------------|------|---------|
| zero | any | NOTIFICATION OPEN Message Error (2) / Bad BGP Identifier (3) |
| equal to the local identifier | internal (same AS) | NOTIFICATION 2/3 |
| equal to the local identifier | external | ACCEPTED -- Section 2.3 resolves any resulting collision |
| anything else non-zero | any | accepted |

The NOTIFICATION Data field is empty: RFC 4271 Section 6.2 defines data only for Unsupported Version
and Unacceptable Hold Time.

## Connection Collision Resolution (Section 2.3)

> "If the BGP Identifiers of the peers involved in the connection collision are identical, then the
> connection initiated by the BGP speaker with the larger AS number is preserved."

Extends RFC 4271 Section 6.8, which compares identifiers as 4-octet unsigned integers and has no
tie-break because under RFC 4271 identifiers could not collide. Applicable to external peers only
(an internal peer presenting the local identifier is already rejected by Section 2.2). Covers 4-byte
AS numbers (RFC 4893, now RFC 6793).

## Remarks (Section 3)

- A BGP Identifier allocated per RFC 4271 satisfies the revised definition (no migration needed).
- In a confederation the whole confederation counts as one AS for uniqueness.
- A speaker supporting this cannot share an identifier with an EXTERNAL neighbour until that
  neighbour is upgraded (an un-upgraded peer applies RFC 4271's stricter test).
- The identifier is also used in AGGREGATOR, in route-reflection attributes (ORIGINATOR_ID /
  CLUSTER_LIST, where only an internal neighbour's identifier is propagated), and in tie-breaking
  during route selection -- which is why an AS-wide duplicate is still a misconfiguration worth
  flagging even though the RFC only says "should".

## Implementation Notes

1. **Enforcement point:** both OPEN rails run `Session.validateOpenIdentifier`
   (`internal/component/bgp/reactor/session_open_validation.go`): `handleOpen` (normal receive) and
   `processOpen` (the connection that won collision resolution and replays its pre-read OPEN).
2. **Internal-peer test:** `s.settings.LocalAS == s.settings.PeerAS`, the same test RFC 7606
   enforcement uses for iBGP. It is taken from the configured session rather than the OPEN's My AS
   field, because My AS carries AS_TRANS for a 4-byte AS.
3. **AS-wide uniqueness** is a claim taken during OPEN validation, keyed `(peer AS, identifier)` and
   released on session teardown (`internal/component/bgp/reactor/routerid_unique.go`). Claiming at
   validation rather than testing for an already-ESTABLISHED holder is what makes the outcome
   independent of scheduling when two peers present one identifier at the same instant.
4. **Opt-out:** `bgp/session/allow-shared-router-id true` skips the claim entirely. It does NOT relax
   Section 2.2, which is about this speaker's own identifier and about zero.
5. **Local identifier:** `parseRouterID` (`internal/component/bgp/reactor/config.go`) rejects a
   configured `router-id 0.0.0.0` on the global leaf and on a per-peer override, so ze never
   originates the identifier its own Section 2.2 rail would reject.
