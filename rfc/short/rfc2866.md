**Purpose:** Defines the RADIUS Accounting protocol for carrying
accounting information between a NAS and a shared accounting server.
Uses the same packet format as RADIUS Authentication (RFC 2865) on
UDP port 1813.

**Scope:** Accounting is fire-and-forget from the session's perspective:
accounting failures MUST NOT tear down user sessions. The NAS sends
Accounting-Request packets; the server responds with Accounting-Response.

## Packet Format (Section 3)

Same as RFC 2865 with these codes:
- **Code 4:** Accounting-Request
- **Code 5:** Accounting-Response

## Request Authenticator (Section 3)

Unlike authentication, the Accounting-Request authenticator is computed,
not random:

```
RequestAuth = MD5(Code + ID + Length + 16_zero_octets + Attributes + Secret)
```

The 16 zero octets replace where the authenticator will be placed.

## Length field (Section 3)

Section 3 states the packet format in its own voice, so its Length rules are
RFC 2866's own. The Length field bounds the packet: octets after it are padding
and are ignored on reception, and a datagram shorter than the Length claims is
silently discarded. The minimum length is 20 and the maximum is 4095.

## Identifier and NAS identity (Section 4.1)

The Identifier changes whenever the content of the Attributes field changes, and
whenever a valid reply arrives for a previous request. A retransmission of
identical content keeps it.

An Accounting-Request names the NAS that sent it: either NAS-IP-Address or
NAS-Identifier is present, and Section 5.13 Note 1 states the same rule over the
Table of Attributes. Four attributes are forbidden in an Accounting-Request:
User-Password, CHAP-Password, Reply-Message and State.

## Accounting-Response (Section 4.2)

The client matches the Identifier of an Accounting-Response with a pending
Accounting-Request. The Response Authenticator holds the correct response for
that request. An invalid packet is silently discarded.

## Attribute values (Section 5)

An attribute value is bounded by its Length field and never by a null, so a
sender and a receiver both carry embedded nulls without loss. Text of length
zero is not sent: the whole attribute is omitted instead.

## Accounting Lifecycle

1. **Start (Status-Type=1):** Sent when user session begins (NCP completes).
   Includes User-Name, NAS-IP-Address, Acct-Session-Id, Service-Type.

2. **Interim-Update (Status-Type=3):** Sent periodically during active session.
   Includes cumulative counters (octets, packets, session time).

3. **Stop (Status-Type=2):** Sent when session ends.
   Includes final duration, byte/packet counters, termination cause.

## Framed-IP-Address in an Accounting-Request (Section 4.1)

An Accounting-Request MAY carry any attribute a RADIUS Access-Request or
Access-Accept may carry, except User-Password, CHAP-Password, Reply-Message
and State. Framed-IP-Address is one of them, and including it constrains its
value: it MUST be the address of the user, and when the Access-Accept used one
of the two special values that tell the NAS to assign or negotiate an address,
the Accounting-Request MUST report the address actually assigned or negotiated,
not the special value.

The Table of Attributes (Section 5.13) allows 0-1 instances of
Framed-IP-Address in an Accounting-Request.

## Acct-Session-Id (Section 5.5)

MUST be unique across all active sessions on the NAS. The NAS generates
it; the server uses it to correlate Start/Interim/Stop records for the
same session.

## Implementation Constraints

- Accounting failures must not affect session state.
- Interim-Update interval is locally configured (typically 300s).
- Acct-Session-Id must be unique per NAS per session.
- Same retransmit and failover rules as RFC 2865.
