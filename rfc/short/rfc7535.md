# RFC 7535 — AS112 Redirection Using DNAME

**Status:** Informational
**Date:** May 2015
**Authors:** J. Abley, B. Dickson, W. Kumari, G. Michaelson

## Purpose

Extends the AS112 project (RFC 7534) with a second, lighter-weight
service mode: instead of delegating each private-use reverse zone
directly to AS112 nameservers (which requires AS112-operator
coordination per zone), any zone administrator can install a DNAME
(RFC 6672) record redirecting their zone to a single shared sink zone,
EMPTY.AS112.ARPA, hosted by AS112 infrastructure. Adding or removing a
redirected zone requires no change on the AS112 node itself.

## Design (§2)

- A new zone, **EMPTY.AS112.ARPA**, is delegated to a single nameserver
  **BLACKHOLE.AS112.ARPA** at IPv4 192.31.196.1 and IPv6 2001:4:112::1.
- These two addresses are chosen so each is uniquely coverable by a
  single anycast prefix with no other address in use within it: IPv4
  192.31.196.0/24, IPv6 2001:4:112::/48 (both IANA-assigned, §8.1).
- Any AS112 node may optionally extend itself to also serve
  EMPTY.AS112.ARPA at these two addresses; this is independent of (and
  additive to) the existing Direct Delegation service described in
  RFC 7534.
- A zone administrator redirects part of their namespace by adding a
  DNAME record pointing at EMPTY.AS112.ARPA — e.g. for
  TEST-NET-1 (192.0.2.0/24):
  ```
  $ORIGIN 192.IN-ADDR.ARPA.
  2.0     IN      DNAME   EMPTY.AS112.ARPA.
  ```

## Operational Notes (§3, §4)

- It takes only one AS112 operator implementing the extension for the
  mechanism to function; more operators adopting it improves capacity
  and distribution, but adoption is not coordinated or mandatory.
- An IPv4-only AS112 node configures only 192.31.196.1; an IPv6-only
  node configures only 2001:4:112::1.
- Existing Direct Delegation service (PRISONER.IANA.ORG,
  BLACKHOLE-1.IANA.ORG, BLACKHOLE-2.IANA.ORG, and the zones delegated to
  them per RFC 7534) continues unchanged — this document does not retire
  or replace it.
- DNAME deployment is reviewed for compatibility (§6): authoritative
  servers must support DNAME, but resolvers/stub resolvers that do not
  understand DNAME still work via the synthesized CNAME RRset that
  accompanies a DNAME answer (RFC 6672 fallback). DNSSEC-validating
  resolvers are required to implement DNAME itself. **DNAME support on
  the AS112 node is never required** — the node only needs to answer
  authoritatively for EMPTY.AS112.ARPA; the DNAME records live in the
  redirecting zones, not on the AS112 node.

## Candidate Redirected Zones (§5)

All zones listed in RFC 6303 (Locally Served DNS Zones) are candidates
for redirection to EMPTY.AS112.ARPA — this document does not mandate
that any specific redirection be deployed, only that the mechanism
exists.

## AS112.ARPA Zone Content (§8.2, IANA-hosted, informative)

```
$ORIGIN AS112.ARPA.
$TTL 3600
@        SOA   BLACKHOLE.AS112.ARPA. NOC.DNS.ICANN.ORG. (
                       1          ; serial
                       10800      ; refresh
                       3600       ; retry
                       1209600    ; expire
                       3600 )     ; negative cache TTL
         NS    A.IANA-SERVERS.NET.
         NS    B.IANA-SERVERS.NET.
         NS    C.IANA-SERVERS.NET.
BLACKHOLE  A     192.31.196.1
           AAAA  2001:4:112::1
HOSTNAME   NS    BLACKHOLE
EMPTY      NS    BLACKHOLE
```

This top-level AS112.ARPA zone is hosted and signed by IANA, not by
individual AS112 node operators (§8.2–8.3). Node operators are only
responsible for answering authoritatively for the delegated
EMPTY.AS112.ARPA zone itself.
