**Purpose:** Describes a local mechanism to avoid black-holing labeled MPLS
traffic on a link whose IGP (OSPF or IS-IS) adjacency is up but whose LDP is
not yet fully operational. While LDP is not fully operational on a link, the
IGP advertises that link at maximum cost so transit traffic prefers other
paths; once LDP synchronizes the normal cost is restored.

**Scope:** No protocol changes. The mechanism is "a local implementation
issue" (§2). It reuses pre-existing IGP cost encodings (OSPF LSInfinity,
IS-IS maximum metric) rather than defining any new wire format, message, TLV,
or capability. There is no new packet to parse or emit.

## No New Wire Formats

RFC 5443 defines **no** message, attribute, capability, TLV, or NLRI. The
required structure's "Wire Formats" section is therefore expressed as the
constraints on the *existing* IGP metric fields the mechanism manipulates.
The document states (§2): "The mechanism described in this document does not
entail any protocol changes and is a local implementation issue."

### IGP Link Cost Values Used by the Mechanism

The mechanism's only externally observable effect is the value written into
the link-cost field of the IGP's existing link advertisement. The RFC pins
the exact "near-infinity" values for each IGP (§2).

| IGP | Field manipulated | Max-cost value | Constraints |
|-----|-------------------|----------------|-------------|
| OSPF (RFC 2328) | metric / cost of the router link in the Router-LSA | LSInfinity = `0xFFFF` (16-bit) | Same value proposed by RFC 3137 (OSPF Stub Router Advertisement). Per-link, not per-router. |
| IS-IS (ISO 10589 / RFC 5305) | link metric | `2^24 - 2` = `0xFFFFFE` (24-bit wide metric) | MUST NOT use `2^24 - 1` (`0xFFFFFF`): per RFC 5305 the maximum link metric `2^24 - 1` removes the link from the topology. The mechanism uses one less so the link stays advertised. |

**Why one below maximum for IS-IS** (§2, verbatim): "Indeed, if a link is
configured with 2^24-1 (the maximum link metric per [RFC5305]), then this
link is not advertised in the topology.  It is important to keep the link in
the topology to allow IP traffic to use the link as a last resort in case of
massive failure."

**Difference from RFC 3137** (§2, verbatim): "One difference is that
[RFC3137] raises the link costs on all (stub) router links, while the
mechanism described here applies on a per-link basis."

## Mechanism

The black-hole condition (§1): LDP establishes MPLS LSPs along the IP
shortest path. If a link on that shortest path has an IGP adjacency but no
operational LDP session (or has not yet exchanged all label bindings), the
link is usable for IP forwarding but not for MPLS forwarding, so MPLS-only
services (L2/L3 VPNs, BGP-free cores) black-hole. "LDP is not a routing
protocol; it cannot re-direct traffic to an alternate IGP path" (§1).

The solution (§2, verbatim): "the solution described by this document is to
discourage a link from being used for IP forwarding as long as LDP is not
fully operational." And: "when LDP is not 'fully operational' (see below) on
a given link, the IGP will advertise the link with maximum cost to avoid any
transit traffic over it."

### Definition of "LDP Fully Operational" (§2)

A link is considered LDP fully operational when **all three** conditions
hold (verbatim): "LDP is considered fully operational on a link when an LDP
hello adjacency exists on it, a suitable associated LDP session (matching the
LDP Identifier of the hello adjacency) is established to the peer at the other
end of the link, and all label bindings have been exchanged over the
session."

| # | Condition | Verifiable directly? |
|---|-----------|----------------------|
| 1 | LDP hello adjacency exists on the link | Yes |
| 2 | A suitable associated LDP session (matching the LDP Identifier of the hello adjacency) is established to the peer at the other end of the link | Yes |
| 3 | All label bindings have been exchanged over the session | No, in general. "the latter condition cannot generally be verified by a router and some estimation may have to be used" (§2) |

### Determining Condition 3 (all bindings exchanged)

Two strategies are given (§2):

1. **Hold-down timer (estimation):** "A simple implementation strategy is to
   use a configurable hold-down timer to allow LDP session establishment
   before declaring LDP fully operational." The timer runs after session
   establishment; on expiry LDP is declared fully operational and the IGP
   restores normal cost.
2. **LDP End-of-LIB (deterministic):** When the LDP End-of-LIB signal is
   implemented, "the configurable hold-down timer is no longer needed. The
   neighbor LDP session is considered fully operational when the End-of-LIB
   notification message is received."

The default hold-down value is deliberately **not defined** (§2, verbatim):
"The default timer is not defined in this document due to concerns of the
large variations of the Label Information Base (LIB) table size and equipment
capabilities."

## Synchronization State Model

The RFC does not name an explicit FSM, but the prose defines a two-state
condition per link (plus the transient hold-down sub-state). This table
distills it for implementers.

| State | Entry condition | IGP advertises | Exit condition |
|-------|-----------------|----------------|----------------|
| Not synchronized | Link's IGP adjacency is up but LDP is not fully operational (any of the three conditions §2 unmet), including the period a link "has just come up and has an IGP adjacency but LDP has either not yet established an adjacency or session, or has not yet distributed all the label bindings" (§1) | Maximum cost (OSPF `0xFFFF`; IS-IS `0xFFFFFE`) so transit traffic avoids the link (§2) | LDP becomes fully operational (all three conditions §2 met), determined by hold-down timer expiry or End-of-LIB receipt |
| Hold-down (transient sub-state of Not synchronized) | LDP hello adjacency and session established, awaiting estimate that all bindings exchanged | Maximum cost (still not synchronized) | Hold-down timer expires, or End-of-LIB notification received |
| Synchronized | All three §2 conditions met | Normal (configured) link cost | LDP ceases to be fully operational on the link |

## State Machine

| State | Event | Guard | Action | Next |
|-------|-------|-------|--------|------|
| (any) | IGP adjacency comes up, LDP not yet operational | - | Advertise link at max cost | Not synchronized |
| Not synchronized | LDP hello adjacency + session established | - | Start hold-down timer (if End-of-LIB not used) | Hold-down |
| Hold-down | Hold-down timer expires | End-of-LIB not implemented | Declare LDP fully operational; restore normal IGP cost | Synchronized |
| Hold-down / Not synchronized | End-of-LIB notification received | End-of-LIB implemented | Declare LDP fully operational; restore normal IGP cost | Synchronized |
| Synchronized | LDP session/adjacency lost on link | - | Re-advertise link at max cost; issue network management alert | Not synchronized |

## Timers

| Name | Default | Range | Behavior |
|------|---------|-------|----------|
| Hold-down timer | Not defined by the RFC (§2) | Configurable | Runs after LDP session establishment to allow label-binding exchange before declaring LDP fully operational. Not needed when LDP End-of-LIB is implemented (§2). |

## Constants

| Name | Value | Usage |
|------|-------|-------|
| OSPF LSInfinity | `0xFFFF` (65535, 16-bit) | Max cost advertised for an OSPF link while LDP not synchronized (§2; per RFC 3137) |
| IS-IS max advertised cost | `0xFFFFFE` (`2^24 - 2`, 16777214) | Max cost advertised for an IS-IS link while LDP not synchronized (§2) |
| IS-IS maximum link metric | `0xFFFFFF` (`2^24 - 1`, 16777215) | Per RFC 5305 this value removes the link from the topology; the mechanism MUST avoid it (§2) |

## Applicability (§3)

- Applicable where "the availability of LDP-signaled MPLS LSPs and avoidance
  of blackholes for MPLS traffic are more important than always choosing an
  optimal path for IP-forwarded traffic" (§3).
- Non-optimal IP forwarding "only occurs for a short time after a link comes
  up or when there is a genuine problem on a link" (§3).
- Example beneficiaries: MPLS VPNs and BGP-free core network designs (§3).
- Usefulness "depends on the availability of alternate paths with sufficient
  bandwidth" so the cost-out does not itself congest the network (§3).

## Broadcast Links (§3)

Verbatim (§3): "On broadcast links with more than one IGP/LDP peer, the
cost-out procedure can only be applied to the link as a whole and not to an
individual peer.  So a policy decision has to be made whether the
unavailability of LDP service to one peer should result in the traffic being
diverted away from all the peers on the link."

| Aspect | Rule |
|--------|------|
| Granularity | Cost-out applies to the whole link, never a single peer (§3) |
| Policy | Operator must decide whether one peer's LDP failure cost-outs the entire link (§3) |

(RFC 6138 later refines broadcast-link behavior; it updates RFC 5443.)

## Interaction with TE Tunnels (§4)

- The mechanism "should only be applied to the IP link cost to prevent
  unnecessary TE tunnel reroutes" (§4). It MUST NOT alter the TE link cost
  flooded by the IGP, otherwise CSPF would needlessly reroute TE tunnels.
- LDP LSPs across a TE tunnel need a targeted LDP session between tunnel
  endpoints. The same black-hole reasoning applies: "Again, raising the IP
  cost of the tunnel while there is no operational LDP session will solve the
  problem" (§4).
- When there is no IGP adjacency over the tunnel and the tunnel is not
  advertised into the IGP, this is "a local issue of the tunnel headend
  router" (§4).

## Validation

| Check | Valid | Invalid Action |
|-------|-------|----------------|
| IS-IS max-cost value | `0xFFFFFE` (`2^24 - 2`) | Using `0xFFFFFF` removes link from topology (loses last-resort IP path) (§2) |
| Which cost is raised | IP link cost only | Raising the TE link cost triggers unnecessary TE tunnel reroutes (§4) |
| Cost-out trigger | Link's IGP up AND LDP not fully operational | Costing out a synchronized link needlessly diverts traffic |
| Cost restoration trigger | All three §2 conditions met (timer expiry or End-of-LIB) | Restoring cost before bindings exchanged re-introduces the black hole |

## Compliance Checklist

**Note on RFC 2119 keywords:** RFC 5443 declares the RFC 2119 conventions in
§1.1 but its normative body contains **no uppercase RFC 2119 keywords**. All
obligations are stated in lowercase prose (this is permitted for an
Informational document with no protocol changes). The checklist below
captures each distinct normative statement, tagging it with the RFC 2119
level its lowercase wording most closely maps to, and quotes the source text.
Grouped requirement-strength first, then by section.

- [ ] [RFC5443-2-1] [MUST] While LDP is not fully operational on a link, the IGP advertises that link with maximum cost to avoid transit traffic ("when LDP is not 'fully operational' ... on a given link, the IGP will advertise the link with maximum cost to avoid any transit traffic over it") (§2)
- [ ] [RFC5443-2-2] [MUST] In OSPF, the maximum cost advertised is LSInfinity, the 16-bit value `0xFFFF` ("In the case of OSPF, this cost is LSInfinity (16-bit value 0xFFFF), as proposed in [RFC3137]") (§2)
- [ ] [RFC5443-2-3] [MUST] In IS-IS, the maximum metric advertised is `2^24-2` (`0xFFFFFE`) ("In the case of ISIS, the maximum metric value is 2^24-2 (0xFFFFFE)") (§2) {gap: ze implements RFC 5443 LDP-IGP sync only in OSPF (internal/plugins/ospf/ldp_sync.go); IS-IS has no LDP-IGP sync state machine, so there is no IS-IS 2^24-2 max-metric cost-out producer (internal/plugins/isis defines only the generic MaxMetric topology-removal value)}
- [ ] [RFC5443-2-4] [MUST NOT] Do not advertise the IS-IS link at `2^24-1` (the per-RFC-5305 maximum link metric), because that removes the link from the topology and loses the last-resort IP path ("if a link is configured with 2^24-1 ... then this link is not advertised in the topology. It is important to keep the link in the topology to allow IP traffic to use the link as a last resort") (§2) {not-applicable: ze runs no IS-IS LDP-IGP sync (internal/plugins/isis has no sync state machine), so it never originates an LDP-sync-driven IS-IS metric and cannot misuse the 2^24-1 value}
- [ ] [RFC5443-2-5] [MUST] Treat LDP as fully operational on a link only when all three conditions hold: an LDP hello adjacency exists, a suitable associated LDP session matching the hello adjacency's LDP Identifier is established to the peer at the other end of the link, and all label bindings have been exchanged over the session ("LDP is considered fully operational on a link when an LDP hello adjacency exists on it, a suitable associated LDP session ... is established ... and all label bindings have been exchanged over the session") (§2)
- [ ] [RFC5443-2-6] [MUST] When LDP End-of-LIB is implemented, consider the neighbor LDP session fully operational only upon receipt of the End-of-LIB notification message ("The neighbor LDP session is considered fully operational when the End-of-LIB notification message is received") (§2) {not-applicable: the precondition is unmet -- ze's LDP (internal/plugins/ldp) implements no End-of-LIB notification, so ze uses the RFC 5443 hold-down-estimate alternative instead}
- [ ] [RFC5443-3-1] [MUST] On broadcast links with more than one IGP/LDP peer, apply the cost-out procedure to the link as a whole, not to an individual peer ("the cost-out procedure can only be applied to the link as a whole and not to an individual peer") (§3)
- [ ] [RFC5443-4-1] [MUST] Apply the cost-raising mechanism only to the IP link cost, not the TE link cost ("The mechanism described in this document should only be applied to the IP link cost to prevent unnecessary TE tunnel reroutes") (§4)

- [ ] [RFC5443-5-1] [SHOULD] Follow current best security practice for MPLS/GMPLS networks ("implementors should follow the current best security practice [MPLS-GMPLS-Sec]") (§5)

## Pitfalls

### Edge Cases

- **IS-IS off-by-one:** Use `0xFFFFFE`, never `0xFFFFFF`. The maximum value
  `2^24-1` deletes the link from the topology; the mechanism deliberately
  uses one less so IP still has a last-resort path during massive failure
  (§2).
- **Estimating "all bindings exchanged":** Condition 3 of full-operational
  "cannot generally be verified by a router" (§2). A hold-down timer that is
  too short restores cost before bindings are present, re-creating the black
  hole; too long needlessly prolongs sub-optimal IP routing. Prefer
  End-of-LIB where available.
- **No default hold-down:** The RFC deliberately leaves the hold-down default
  undefined because LIB size and equipment capability vary widely (§2). Make
  it configurable; do not hardcode a universal default.
- **TE cost vs IP cost:** Manipulating the TE metric (not just the IP metric)
  causes CSPF to reroute TE tunnels unnecessarily (§4).
- **Transient vs persistent:** Cost-out at link bring-up is transient and
  expected; persistent cost-out signals a genuine fault (config error,
  implementation bug, DoS) and should raise an operator alert (§1, §3, §5).

### Interop

- **Per-link, not per-router (vs RFC 3137):** RFC 3137 raises cost on all
  stub-router links; this mechanism is strictly per-link (§2). Do not conflate
  the two.
- **Broadcast links:** Granularity is the whole link, not the peer; behavior
  with multiple LDP peers on a LAN is a policy choice and was later refined by
  RFC 6138.
- **Targeted LDP over TE tunnels:** The same sync logic must cover targeted
  LDP sessions between TE tunnel endpoints (§4).

### Security (§5)

- A DoS attack that brings down or prevents LDP service on a link can itself
  cause LDP-related black-holing; this document does not address preventing
  LDP session failure (§5).
- Assigning maximum IGP cost to a link "should not introduce new security
  threats" because the operation is internal to the router (§5).
- However, making many LDP links unavailable is a security threat: it can
  cause dropped traffic due to limited remaining capacity, triggered by
  operational or implementation error (§5).

## Compatibility

- **No protocol changes:** Interoperates with any IGP/LDP peer; the cost-out
  is purely local. Peers see only a normal (high) IGP cost and react with
  standard SPF (§2).
- **Fallback:** Where End-of-LIB is unsupported, the hold-down timer provides
  the estimation path; both yield the same externally visible behavior (§2).
- **Last-resort IP path preserved:** Because the link stays in the topology
  (IS-IS `0xFFFFFE`, OSPF `0xFFFF` rather than withdrawal), IP traffic can
  still traverse it under massive failure (§2).
