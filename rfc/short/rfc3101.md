# RFC 3101 - The OSPF Not-So-Stubby Area (NSSA) Option

## Meta

| Field | Value |
|-------|-------|
| RFC | 3101 |
| Title | The OSPF Not-So-Stubby Area (NSSA) Option |
| Status | Proposed Standard (Standards Track) |
| Date | January 2003 |
| Author | P. Murphy |
| Obsoletes | RFC 1587 |
| Relates to | RFC 2328 (OSPF Version 2) -- NSSA is an optional area type layered on OSPFv2 |

**Purpose:** RFC 3101 defines the Not-So-Stubby Area (NSSA), an optional OSPF
area type that can import AS-external routes in a limited fashion. Like a stub
area, an NSSA does not carry Type-5 AS-External-LSAs; unlike a stub area, it
permits external routes to be injected locally and advertised throughout the
NSSA as Type-7 NSSA-LSAs. NSSA border routers may then translate selected
Type-7 LSAs into Type-5 LSAs for AS-wide distribution. The document supersedes
RFC 1587 and makes the NSSA specification consistent with OSPFv2 (RFC 2328)
while preserving backward compatibility with RFC 1587 implementations.

**Scope:** This summary covers the NSSA concept and how it differs from a stub
area; the N-bit (Hello/Database-Description negotiation) and the P-bit
(Type-7 propagation); the Type-7 NSSA-LSA wire format and its differences from
the Type-5 AS-External-LSA; the forwarding-address requirement; NSSA
translator election (Section 3.1, the Nt bit, the translator stability
interval); Type-7 to Type-5 translation at the elected translator
(Section 3.2); Type-7 flooding scope; default-route handling into an NSSA
(including the no-summary / totally-NSSA case); and Type-7 address ranges /
aggregation. The base OSPFv2 protocol (RFC 2328) is out of scope here.

## NSSA Concept vs. Stub Area

An NSSA is an optional area type "which has the capability of importing
external routes in a limited fashion" (Section 1). The distinguishing rule is
that an NSSA blocks Type-5 transit, like a stub, but allows local external
import via Type-7:

| Property | Stub Area | NSSA |
|----------|-----------|------|
| Type-5 AS-External-LSA flooded in | No | No |
| Type-7 NSSA-LSA originated/flooded in | N/A | Yes |
| External routes importable locally | No | Yes, as Type-7 |
| Border-router translation to Type-5 | N/A | Yes (elected translator) |
| Options bit that gates the area | E-bit clear | N-bit set, E-bit clear |

The NSSA solves the problem that a stub area cannot host an AS Boundary Router
(ASBR): a leaf or transit site can run RIP or another protocol and inject its
routes into OSPF as Type-7 LSAs, which an NSSA border router can later
aggregate and translate into Type-5 LSAs for the backbone (Section 1).

## The N-bit (Options field, Hello / Database-Description negotiation)

The N-bit lives in the OSPF **Options field** carried in Hello and
Database-Description packets. "The N-bit describes the router's NSSA
capability. The N-bit is used only in Hello packets and ensures that all
members of an NSSA agree on that area's configuration" (Appendix A). When the
N-bit is set in the Hello sent out an interface, "it means that the router
will send and receive Type-7 LSAs on that interface."

Negotiation rules:

- "Two routers will not form an adjacency unless they agree on the state of
  the N-bit" (Section 2.1) -- the Hello's N-bit and E-bit must match the area
  type, the same agreement check stub areas perform on the E-bit.
- "If the N-bit is set in the options field, the E-bit must be clear"
  (Appendix A) -- N and E are mutually exclusive, so an NSSA never floods
  Type-5 LSAs.

## Type-7 NSSA-LSA Wire Format

The NSSA-LSA uses LS Type value **7** ("The Type field in the LSA header is
7", Section 2.3). Format figure (Appendix C, reproduced verbatim):

    0                                 32
    ------------------------------------
    |                | Options |   7   |
    |                -------------------
    |        Link-State Header         |
    |                                  |
    ------------------------------------
    | Network Mask                     |
    ------------------------------------  ______
    |E| TOS  |        metric           |  .
    ------------------------------------  .  repeated for each TOS
    | Forwarding Address               |  .
    ------------------------------------  .
    | External Route Tag               |  ______
    ------------------------------------

| Field | Size | Meaning |
|-------|------|---------|
| LS Type | (in header) | 7 (NSSA-LSA) |
| Options | 1 octet (in header) | Includes the P-bit (see below) |
| Network Mask | 4 octets | IP address mask of the advertised network |
| E (bit) | high bit of metric octet | External metric type: 0 = Type-1, 1 = Type-2 |
| TOS | 7 bits | Type of Service to which this metric applies |
| metric | 3 octets | Cost of this route |
| Forwarding Address | 4 octets | Where data traffic is forwarded; 0.0.0.0 means forward to the LSA's originator |
| External Route Tag | 4 octets | 32-bit tag, not used by OSPF itself |

The Network Mask, metric, E-bit, TOS, and External Route Tag fields are
defined identically to the Type-5 AS-External-LSA. Differences from Type-5
(Section 2.3):

- Type-7 LSAs are flooded only within the originating NSSA (see Flooding
  Scope below), not AS-wide.
- Type-7 LSAs are listed only in the OSPF area data structures of their
  respective NSSAs.
- NSSA border routers select which Type-7 LSAs are translated into Type-5.
- Type-7 LSAs carry a propagate (P) bit in their Options field; Type-5 LSAs
  do not.

## The P-bit (Propagate, in the Type-7 Options field)

The Options field of a Type-7 LSA (Appendix A) is laid out as:

    --------------------------------------
    | * | O | DC | EA | N/P | MC | E | * |
    --------------------------------------

        The Type-7 LSA options field

"The P-bit is used only in the Type-7 LSA header. It flags the NSSA border
router to translate the Type-7 LSA into a Type-5 LSA" (Appendix A). (The same
Options bit position is labelled N/P: it is the N-bit in Hello packets and the
P-bit in Type-7 LSA headers.)

P-bit rules:

- Default setting is clear.
- "An NSSA internal AS boundary router must set the P-bit in the LSA header's
  option field of any Type-7 LSA whose network it wants advertised into the
  OSPF domain's full transit topology" (Section 2.4).
- "When an NSSA border router originates both a Type-5 LSA and a Type-7 LSA
  for the same network, then the P-bit must be clear in the Type-7 LSA"
  (Section 2.4) -- prevents a double translation of the same network.
- If the P-bit is set, the forwarding address must be non-zero (see below).

## Forwarding Address Requirement for Type-7 LSAs

- "If the P-bit is set, the forwarding address must be non-zero; otherwise it
  may be 0.0.0.0" (Section 2.4). A non-zero forwarding address is what lets a
  translated Type-5 LSA point external traffic at the correct exit even though
  the Type-7 originator's router ID changes on translation.
- "If the P-bit is set and a non-zero forwarding address is unavailable, then
  the route's Type-7 LSA is not originated into this NSSA" (Section 2.4).
- A forwarding address of 0.0.0.0 means "data traffic will be forwarded to the
  LSA's originator" (the ASBR itself) (Section 2.3).
- Selection preference when a router must pick a forwarding address: first the
  router's internal addresses (if internal addressing is supported), otherwise
  the router's active OSPF stub-network addresses (Section 2.4).

## NSSA Translator Election (Section 3.1)

Only an elected NSSA border router translates Type-7 LSAs into Type-5 LSAs.
Election uses the Nt bit advertised in the Router-LSA. The Router-LSA bit row
(Appendix B) prints the NSSA bit as:

    |  0  Nt|W|V|E|B|        0      |            # links            |

"bit Nt -- When set, the router is an NSSA border router that is
unconditionally translating Type-7 LSAs into Type-5 LSAs (Nt stands for NSSA
translation)" (Appendix B).

Election algorithm (Section 3.1):

- Each NSSA border router has an `NSSATranslatorRole`: **Always** (always
  translates regardless of other routers) or **Candidate** (participates in
  the election). Default is **Candidate** (Appendix D).
- "If there exists another border router in this list whose router-LSA has bit
  Nt set or who has a higher router ID, then its NSSATranslatorState is
  disabled. Otherwise its NSSATranslatorState is elected." That is, the
  reachable NSSA border router with the highest Router ID (or any router with
  Nt set / role Always) becomes the translator.
- "An elected translator will continue to perform translation duties until
  supplanted by a reachable NSSA border router whose Nt bit is set or whose
  router ID is greater."

Stability / hysteresis: the `TranslatorStabilityInterval` "defines the length
of time an elected Type-7 translator will continue to perform its translator
duties once it has determined that its translator status has been deposed by
another NSSA border router translator... The default setting is 40 seconds"
(Appendix D). This prevents translator thrashing during topology change. "It
is normally sufficient to have only one NSSA border router perform the
translation" (Section 3.1).

## Type-7 to Type-5 Translation (Section 3.2)

Performed only by the elected translator. "Only installed Type-7 LSAs and
those non-default Type-7 LSAs originated by the router itself should be
examined. Locally sourced Type-7 LSAs should be processed first" (Section 3.2).

Translation construction (Section 3.2):

- The new Type-5 LSA "will describe the same network and have the same network
  mask, path type, metric, forwarding address and external route tag as the
  Type-7 LSA." The forwarding address is preserved from the Type-7 LSA.
- "The advertising router field will be the router ID of this NSSA border
  router" (the translator), not the original Type-7 originator.
- The P-bit is cleared in the Type-5 result (the Type-5 LSA has no P-bit; the
  Type-7's P-bit is what authorized translation in the first place).
- Forwarding address must be non-zero for a direct (non-aggregated)
  translation; "only those Type-5 LSAs that are aggregations of Type-7 LSAs
  may have 0.0.0.0 as a forwarding address" (Section 2.3 / Section 3.2).
- AS-wide flooding: the translated Type-5 LSA is flooded throughout the OSPF
  AS like any other AS-External-LSA.

Duplicate avoidance (Section 3.2): a Type-5 LSA is generated only "if... the
calculating router has the highest router ID amongst NSSA translators that
have originated a functionally equivalent Type-5 LSA (i.e. same destination,
cost and non-zero forwarding address) and that are reachable over area 0 and
the NSSA." Translation can also supplant a locally sourced Type-5 LSA: "Future
reoriginations of the locally sourced Type-5 LSA should be suppressed until the
Type-5 LSA generated by translation is flushed."

## Type-7 Flooding Scope

"Type-7 LSAs are only flooded within the originating NSSA. The flooding of
Type-7 LSAs follows the same rules as the flooding of Type-1 and Type-2 LSAs"
(Section 2.3). Type-7 LSAs never reach the backbone or other areas as Type-7;
only their translated Type-5 versions cross area boundaries.

## Default Route into an NSSA (Section 2.4, 2.7)

- "A Type-7 default LSA for the network 0.0.0.0/0 may be originated into the
  NSSA by any NSSA router" (Section 2.4).
- "NSSA border routers must originate an LSA for the default destination into
  all their directly attached NSSAs in order to support intra-AS routing and
  inter-AS routing" (Section 2.4).
- "The Type-7 default LSA originated by an NSSA border router must have the
  P-bit clear"; "an NSSA ASBR that is not an NSSA border router may originate a
  Type-7 default LSA with the P-bit set" (Section 2.4).
- "A Type-7 default LSA may be installed by NSSA border routers if and only if
  its P-bit is set" (Section 2.4).
- No-summary / totally-NSSA case (`ImportSummaries` disabled): "When summary
  routes are not imported, the default LSA originated by an NSSA border router
  into the NSSA should be a Type-3 summary-LSA" (Section 2.7). The default
  behavior is to import summary routes (Section 2.7). NSSA border routers
  should not originate Type-4 summary-LSAs into their NSSAs (Section 2.4).

## Type-7 Address Ranges / Aggregation (Section 2.2)

An NSSA Type-7 address range is configured as (Section 2.2):

| Item | Value |
|------|-------|
| Address / Mask | An [address, mask] pair defining the range |
| Status | Advertise or DoNotAdvertise |
| External Route Tag | 32-bit tag applied to the aggregate Type-5 LSA |

"NSSA border routers may aggregate Type-7 routes by advertising a single
Type-5 LSA for each Type-7 address range" (Section 2.2). Aggregation metric
rules (Section 3.2): if any contributing Type-7 LSA has path type 2, the
aggregate is type 2; a Type-1 aggregate takes the highest contributing cost; a
Type-2 aggregate takes the highest Type-2 cost plus 1 so the aggregate does
not appear closer than a non-aggregated route. An aggregated Type-5 LSA may
use forwarding address 0.0.0.0.

## MUST / MUST NOT / SHOULD Summary

- (Section 2.1) An NSSA router MUST verify that both the N-bit and the E-bit in
  a received Hello's Options field match the area type before forming an
  adjacency.
- (Appendix A) If the N-bit is set, the E-bit MUST be clear.
- (Section 2.4) An NSSA internal ASBR MUST set the P-bit on any Type-7 LSA it
  wants advertised into the full transit topology.
- (Section 2.4) If P-bit set, the forwarding address MUST be non-zero; if no
  non-zero forwarding address is available, the Type-7 LSA MUST NOT be
  originated.
- (Section 2.4) When an NSSA border router originates both a Type-5 and a
  Type-7 LSA for the same network, the Type-7's P-bit MUST be clear.
- (Section 2.4) A Type-7 default LSA from an NSSA border router MUST have the
  P-bit clear; it MAY be installed only if its P-bit is set.
- (Section 2.4) NSSA border routers MUST originate a default-destination LSA
  into all directly attached NSSAs.
- (Section 3.1) All NSSA border routers MUST set the E-bit in the Type-1
  router-LSAs of their directly attached non-stub areas.
- (Section 2.7) All NSSA border router implementations MUST support the
  optional import of summary routes into NSSAs as Type-3 summary-LSAs.
- (Section 2.4) NSSA border routers SHOULD NOT originate Type-4 summary-LSAs
  into their NSSAs.
- (Section 3.1) It SHOULD normally be sufficient for only one NSSA border
  router to perform translation; default `NSSATranslatorRole` is Candidate.
