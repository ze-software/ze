# RFC 7166 - Supporting Authentication Trailer for OSPFv3

## Meta

| Field | Value |
|-------|-------|
| RFC | 7166 |
| Title | Supporting Authentication Trailer for OSPFv3 |
| Status | Standards Track |
| Date | March 2014 |
| Authors | M. Bhatia, V. Manral, A. Lindem |
| Obsoletes | RFC 6506 |
| Updates | None |

**Purpose:** Defines a non-IPsec authentication trailer for OSPFv3 so
OSPFv3 can authenticate protocol packets without depending only on AH/ESP.
It reuses HMAC-SHA algorithms and key rollover concepts familiar from
OSPFv2 cryptographic authentication, but the wire framing is an OSPFv3
trailer, not an OSPF header field.

**Scope for Ze:** Use this for the first OSPFv3 authentication follow-up.
Do not add OSPFv2 AuType fields to the OSPFv3 header. IPsec from RFC 4552
is a later optional path.

## Authentication Trailer Placement (§2)

The Authentication Trailer is appended after the OSPFv3 packet and optional
LLS data block. Its length is not included in the OSPFv3 packet header
length, but is included in the IPv6 payload length. The digest calculation
covers the OSPFv3 packet, any LLS data block, selected trailer fields, and
the IPv6 source address protection input from §2.3 and §4.5.

| Length | Includes |
|--------|----------|
| OSPFv3 packet length | OSPFv3 header and OSPFv3 packet body only |
| LLS data block length | Optional LLS data block when the L-bit is set |
| Authentication length | Fixed 16-byte trailer plus digest |
| IPv6 payload length | OSPFv3 packet, optional LLS data, and Authentication Trailer |

## AT-Bit (§2.1)

The AT-bit in the OSPFv3 Options field indicates Authentication Trailer
use. Routers using the trailer must set the AT-bit in Hello and Database
Description packets. For packet types without an Options field, the neighbor
state learned from Hello/DD determines whether a trailer is expected.

Implementation rule: once a neighbor is operating with the AT-bit, every
OSPFv3 packet from that neighbor is expected to include a valid trailer.
Missing, expired, or invalid Security Association state is a drop.

## Trailer Format (§4.1)

| Field | Width | Rule |
|-------|-------|------|
| Authentication Type | 16 bits | 0 reserved, 1 HMAC Cryptographic Authentication |
| Auth Data Len | 16 bits | Length in octets of the whole Authentication Trailer, including the fixed 16-byte header and digest |
| Reserved | 16 bits | Send zero, ignore on receive |
| Security Association ID | 16 bits | Selects the configured algorithm and key |
| Cryptographic Sequence Number | 64 bits | Strictly increasing anti-replay value |
| Authentication Data | variable | HMAC digest |

Sequence numbers must be strictly greater than the last accepted sequence
number for the same neighbor and OSPFv3 packet type. Packet-type separation
is required because OSPF packet prioritization can reorder different packet
types. The 64-bit value should preserve monotonicity across restarts, for
example by using high-order 32 bits as a persistent boot or wrap counter.

## Security Association (§3)

An OSPFv3 Security Association contains:

| SA item | Requirement |
|---------|-------------|
| SA ID | 16-bit configured identifier carried in the trailer |
| Authentication algorithm | HMAC-SHA-1, HMAC-SHA-256, HMAC-SHA-384, or HMAC-SHA-512 |
| Authentication key | Secret key for the SA |
| Accept/generate lifetimes | KeyStartAccept, KeyStartGenerate, KeyStopGenerate, KeyStopAccept |

A receiver chooses the active SA from the SA ID in the packet. The algorithm
is not carried on the wire and must not be inferred only from digest length,
because future algorithms can share the same output length.

For smooth rollover, accept lifetime should start before generate lifetime,
and generate lifetime should stop before accept lifetime. If no valid key
exists for an interface, the router must not transmit unauthenticated OSPFv3
packets.

## Checksum Handling (§2.2, §4.2)

When the Authentication Trailer is used, OSPFv3 header checksum calculation
and LLS data block checksum calculation are omitted. The LLS data block, if
present, is included in the authentication digest instead. This is a key
difference from unauthenticated RFC 5340 packets.

## IPv6 Source Address Protection (§2.3, §4.5)

OSPFv3 identifies neighbors by Router ID, but learns the neighbor IPv6 source
address from Hellos. The IPv6 source address is included in the digest
calculation to prevent an attacker from changing the source address while
leaving the Router ID unchanged.

## Cryptographic Procedure (§4.3 through §4.6)

The supported algorithms are HMAC-SHA-1, HMAC-SHA-256, HMAC-SHA-384, and
HMAC-SHA-512. The implementation must use the protocol-specific key derivation
from §4.5, include the source address protection input, include the LLS block
when present, and compare digests in constant time.

Received packets are dropped if the trailer is absent when expected, if the
SA is unknown or expired, if the sequence number is not strictly greater than
the last accepted value for that neighbor and packet type, or if digest
verification fails.

## Compliance Checklist

- [ ] [OPTIONS] Set the AT-bit in Hello and Database Description packets when all packets on the link include an Authentication Trailer (§2.1)
- [ ] [LENGTH] Keep the trailer out of the OSPFv3 packet length while including it in IPv6 payload length (§2)
- [ ] [TRAILER] Encode and decode the fixed trailer fields exactly: Authentication Type, Auth Data Len, Reserved, SA ID, 64-bit sequence number, digest (§4.1)
- [ ] [SA] Select the Security Association by SA ID, not by digest length (§3)
- [ ] [SEQUENCE] Require sequence numbers to be strictly greater than the last accepted value for the same neighbor and packet type (§4.1)
- [ ] [CHECKSUM] Omit OSPFv3 header checksum and LLS checksum when the trailer is used (§2.2, §4.2)
- [ ] [DIGEST] Include OSPFv3 packet, optional LLS data, trailer fields, and protected IPv6 source-address input in HMAC calculation (§2.3, §4.5)
- [ ] [DROP] Drop packets with missing trailer, unknown/expired SA, replayed sequence, or failed digest (§4.6)
- [ ] [KEYS] Support HMAC-SHA-1/256/384/512 and key rollover lifetimes (§3, §4.5)
