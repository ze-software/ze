# RFC 4552 - Authentication/Confidentiality for OSPFv3

## Meta

| Field | Value |
|-------|-------|
| RFC | 4552 |
| Title | Authentication/Confidentiality for OSPFv3 |
| Status | Standards Track |
| Date | June 2006 |
| Authors | M. Gupta, N. Melam |
| Obsoletes | None |
| Updates | None |

**Purpose:** Specifies how OSPFv3 can use IPv6 IPsec AH and ESP for
authentication and confidentiality. OSPFv3 removed the OSPFv2 AuType and
Authentication header fields, so this RFC originally supplied the security
mechanism for OSPFv3.

**Scope for Ze:** This is an out-of-scope marker for the first `ospfv3`
follow-up. Use RFC 7166 authentication trailer first. IPsec support requires
kernel policy, Security Association management, multicast key handling, and
operator workflow that are larger than base OSPFv3.

## Required Capabilities

| Area | RFC 4552 requirement |
|------|----------------------|
| Mode | Transport mode Security Associations must be supported; tunnel mode may also be supported (§2) |
| Authentication | Implementations must support OSPFv3 authentication; ESP must be supported and AH may be supported (§3) |
| Confidentiality | Implementations should support confidentiality; if confidentiality is provided, ESP must be used (§4) |
| Packet drops | When auth or confidentiality is enabled, unprotected packets and failed checks are silently discarded (§3, §4) |
| OSPF version | OSPFv2 and OSPFv3 both use protocol 89, but IP version distinguishes them for IPsec selectors (§5) |
| SPD | Multiple Security Policy Databases with interface-based selection are required (§6) |
| Selectors | Source, destination, protocol, direction, and interface tagging are required (§6) |
| Manual keys | Manual keying must be available for the specified traffic (§6, §7) |

## Key Management Constraint (§7)

OSPFv3 uses multicast and unicast. For broadcast links, authentication is a
one-to-many problem. IKE is not suitable for the multicast group case in this
RFC, so manual keying is required. The RFC explains why per-peer inbound and
outbound SAs do not scale on broadcast links, then uses shared SA parameters
for inbound and outbound group traffic.

This is the main reason Ze should not treat RFC 4552 as the first auth path:
base OSPFv3 should not require users to configure kernel IPsec policy and
manual multicast group keys before an adjacency can form.

## SA Granularity and Selectors

The implementation should let operators choose whether one SA is shared among
multiple interfaces or each interface has a unique SA. Selectors must be able
to distinguish direction, source, destination, protocol, and interface. Virtual
links have additional dynamic policy needs.

## Out-of-Scope Decision for First Ze OSPFv3

Initial Ze OSPFv3 should implement RFC 7166 trailer authentication instead of
RFC 4552 IPsec. Reasons:

- RFC 7166 is carried in OSPFv3 packet processing and can share Ze key-chain
  patterns.
- RFC 4552 needs OS IPsec policy management, manual group keys, and SPD
  interface selection.
- FRR interoperability for base OSPFv3 can be proven without implementing
  kernel IPsec control first.

## Compliance Checklist

boilerplate and the §6 quoted keyword-name interpretation sentence are the only
occurrences excluded). Grouped MUST/MUST NOT, then SHOULD/SHOULD NOT, then MAY;
ordered by section within each group. IDs anchor to the first section cited.
