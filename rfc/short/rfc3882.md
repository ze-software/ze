**Purpose:** Describes an enhanced BGP-triggered blackholing technique in which per-router BGP communities select the border routers that rewrite an attacked prefix's next hop to a null interface, and a sinkhole-tunnel variant that diverts attack traffic for analysis and then back to its destination.

**Scope:** Operational, Informational. iBGP only. No wire format.

**Errata:** None affecting implementation.

## Technique (§2)

| Step | Configuration on each border router |
|------|------------------------------------|
| 1 | Static route from an RFC 1918 address to the null interface |
| 2 | AS-path list matching locally originated advertisements |
| 3 | Community list matching this router's community (65001:1 for R1) |
| 4 | Community list matching the all-routers community (65001:666) |
| 5 | iBGP import policy: on a match of 3 or 4 and of 2, set the next hop to the RFC 1918 address and replace the communities with NO_ADVERTISE |

The trigger announces the attacked /32 into iBGP with the router community and NO_EXPORT. Routers without the matching policy keep the legitimate next hop. Matching only locally originated routes stops an eBGP peer from using the community.

## Sinkhole Tunnels (§3)

The same community selection rewrites the next hop to an RFC 1918 address statically routed into a tunnel (MPLS TE in the example) towards a sinkhole router. The sinkhole may rate-limit, apply QoS or filter, and a default route returns the remaining traffic to the network.
