# RFC 4576 - Using an LSA Options Bit to Prevent Looping in BGP/MPLS IP VPNs

## Meta

| Status | Standards Track |

**Purpose:** Defines the **DN bit**, the high-order bit of the OSPFv2 LSA
Options field, used by a PE router to mark an LSA whose route was learned
from BGP (the VPN backbone). A PE that receives a type 3, 5, or 7 LSA with
the DN bit set MUST NOT use it in the OSPF route calculation, which prevents
a route learned via BGP from being redistributed back into BGP and thereby
prevents routing loops in BGP/MPLS IP VPNs (RFC 4577 / RFC 4364 OSPF PE-CE).

**Scope for Ze:** Affects the OSPFv2 LSA codec and the OSPFv2 SPF / route
calculation path, but only in the context of an OSPF PE-CE deployment for
BGP/MPLS IP VPNs. It is a single options bit plus set/clear/ignore rules on
summary (type 3), AS-external (type 5), and NSSA-external (type 7) LSAs.
There is no new LSA, no new packet, and no negotiation.

## Wire Format

### LSA Options Field with DN Bit (§4)

RFC 4576 does not define a new structure. It reuses the existing 8-bit
(one octet) OSPFv2 LSA Options field defined in RFC 2328, Section A.2, and
assigns a name to its previously unused high-order bit.

Verbatim diagram from §4:

```
                  +-------------------------------------+
                  | DN | * | DC | EA | N/P | MC | E | * |
                  +-------------------------------------+

                         Options Field with DN Bit
                          (RFC 2328, Section A.2)
```

The diagram is drawn most-significant bit on the left. In RFC 2328 the
Options bits are numbered 0..7 from the least-significant (rightmost) bit,
so the **DN bit is the high-order bit, bit 7** of the one-octet Options
field (the leftmost position, mask `0x80`). It is described verbatim as
"The high-order bit of the LSA Options field (a previously unused bit)"
(§4). The remaining named bits (DC, EA, N/P, MC, E) are the pre-existing
RFC 2328 / RFC 1793 / RFC 1587 options and are unchanged by this RFC; the
two `*` positions are unused/reserved bits.

| Field | Offset | Size | Type | Constraints |
|-------|--------|------|------|-------------|
| DN | bit 7 (high-order, mask `0x80`) of the Options octet | 1 bit | flag | Set on type 3, 5, 7 LSA sent PE->CE; MUST be clear in all other LSA types (§4). On receive: causes the LSA information to be excluded from the route calculation for type 3, 5, 7; MUST be ignored in all other LSA types (§4) |
| * | bit 6 (mask `0x40`) | 1 bit | reserved | Unused; not defined by this RFC |
| DC | bit 5 (mask `0x20`) | 1 bit | flag | RFC 1793 Demand Circuits; unchanged |
| EA | bit 4 (mask `0x10`) | 1 bit | flag | External Attributes; unchanged |
| N/P | bit 3 (mask `0x08`) | 1 bit | flag | NSSA; unchanged |
| MC | bit 2 (mask `0x04`) | 1 bit | flag | Multicast (MOSPF); unchanged |
| E | bit 1 (mask `0x02`) | 1 bit | flag | External routing capability; unchanged |
| * | bit 0 (mask `0x01`) | 1 bit | reserved | Unused; not defined by this RFC |

**Byte order / placement:** The Options field is a single octet; no
multi-byte ordering applies. Where the Options field appears within an LSA
is governed by RFC 2328 (e.g., the LSA header Options byte and the per-LSA
Options usage), not by this RFC. RFC 4576 adds no field, no length, and no
new option semantics beyond bit 7.

## Encoding Rules (Transmit)

The DN bit applies only to LSAs a PE originates from BGP-learned VPN routes
and sends toward a CE:

- "When a type 3, 5, or 7 LSA is sent from a PE to a CE, the DN bit MUST be
  set." (§4)
- "The DN bit MUST be clear in all other LSA types." (§4)

In practice a PE sets DN when it originates:

- a **Type 3 (Summary) LSA** from a route learned via BGP/VPN-IPv4, and
- a **Type 5 (AS-external) LSA** from a route learned via BGP/VPN-IPv4, and
- a **Type 7 (NSSA-external) LSA** from a route learned via BGP/VPN-IPv4.

For every other LSA type (e.g., Router type 1, Network type 2,
Type 4 ASBR-summary, opaque types) the bit is left clear.

The DN bit "has no other effect on LSA handling" (§4): an LSA with DN set is
placed in the topological (link-state) database, aged, and flooded exactly
as if DN were not set. Encoding the bit does not change checksum, length, or
flooding behaviour.

## Decoding Rules (Receive)

When a PE receives an LSA from a CE router:

- "When the PE receives, from a CE router, a type 3, 5, or 7 LSA with the DN
  bit set, the information from that LSA MUST NOT be used during the OSPF
  route calculation. As a result, the LSA is not translated into a BGP
  route." (§4)
- "The DN bit MUST be ignored in all other LSA types." (§4)

Decoding the bit is a single mask test (`Options & 0x80`) against the
high-order Options bit. The bit only gates the SPF / route-calculation
input for type 3, 5, and 7 LSAs; for all other LSA types its value is not
inspected. The LSA is still installed, aged, and flooded normally (§4); only
the route-calculation contribution is suppressed.

## Validation

| Check | Valid | Invalid Action |
|-------|-------|----------------|
| LSA type when setting DN on transmit | DN set only on type 3, 5, 7 PE->CE | DN on any other type violates §4 (MUST be clear); do not set |
| LSA type when honouring DN on receive | DN honoured only on received type 3, 5, 7 | For other types DN MUST be ignored (§4); do not gate route calc on it |
| Received type 3/5/7 LSA with DN set | Exclude from OSPF route calculation; do not translate to a BGP route | Including it risks redistributing a BGP-learned route back into BGP (loop) |

## MUST Requirements

**Tx (PE -> CE):**

- When a type 3, 5, or 7 LSA is sent from a PE to a CE, the DN bit MUST be
  set. (§4)
- The DN bit MUST be clear in all other LSA types. (§4)

**Rx (PE <- CE):**

- When the PE receives, from a CE router, a type 3, 5, or 7 LSA with the DN
  bit set, the information from that LSA MUST NOT be used during the OSPF
  route calculation. (§4)
- The DN bit MUST be ignored in all other LSA types. (§4)

There are no SHOULD or MAY requirements in this RFC. (§2 normatively imports
the full RFC 2119 keyword set, but only MUST / MUST NOT keywords are used in
the body, all in §4.)

## Algorithms

The complete behaviour, expressed as pseudocode over the single options bit:

```
# PE originating an LSA toward a CE (Tx, §4)
on originate(lsa):
    if lsa.type in {3, 5, 7} and route_learned_from_BGP_VPN(lsa):
        lsa.options |= DN          # DN = high-order bit, mask 0x80
    else:
        lsa.options &= ~DN         # MUST be clear in all other types

# PE receiving an LSA from a CE (Rx, §4)
on receive(lsa from CE):
    install_in_lsdb(lsa)           # aged, flooded as normal -- DN has no
                                   # other effect on LSA handling
    if lsa.type in {3, 5, 7} and (lsa.options & DN):
        exclude_from_route_calculation(lsa)   # not translated into a BGP route
    # for all other LSA types: DN is ignored (do not test it)
```

## Pitfalls

- **Edge cases:**
  - The DN bit is the **high-order** (most significant) bit of the Options
    octet, mask `0x80` (bit 7). Do not confuse it with any low-order or
    middle option bit. Picking the wrong bit silently corrupts an unrelated
    option (DC/EA/N-P/MC/E) or fails to suppress loops.
  - DN is meaningful for routing only on type 3, 5, and 7 LSAs. On any other
    LSA type it MUST be ignored on receive and MUST be clear on transmit;
    do not let it leak into route-calc gating for type 1/2/4 LSAs.
  - DN has **no other effect** on LSA handling: an LSA with DN set is still
    stored in the topological database, aged, and flooded just as if DN were
    not set (§4). A common mistake is to drop or refuse to flood a DN LSA.
  - The DN bit prevents *route translation back into BGP*; it does not
    delete the prefix from the LSDB. The suppression is at SPF / route
    calculation only.

- **Interop:** This RFC is the standardized replacement for vendor-specific
  loop-prevention tags. RFC 4577 §4.2.5/§4.2.6 also defines a VPN Route Tag
  mechanism for AS-external LSAs; the DN bit is the general mechanism that
  also covers Summary (type 3) LSAs, which a tag cannot (§3). An implementer
  must honour DN even if it also uses route tags.

- **Security (§5):** An attacker who **sets** DN in a CE->PE LSA when it
  should be clear can make the affected prefixes unreachable from other VPN
  sites. An attacker who **clears** DN (in either direction) when it should
  be set can create routing loops for traffic to those prefixes. Mitigation:
  use OSPFv2 cryptographic authentication as specified in Section D of
  RFC 2328 (§5).

## Compatibility

- **Behaviour with non-supporting peers:** A router that does not understand
  the DN bit treats the Options octet per RFC 2328 and simply ignores the
  previously-unused high-order bit, so a DN-marked LSA is still flooded and
  aged normally. The loop-prevention guarantee only holds when the receiving
  **PE** honours DN; a PE that ignores DN can re-leak a BGP-learned route
  back into BGP and form a loop. There is no capability negotiation; correct
  behaviour relies on all PEs implementing §4.
- **Feature negotiation fallback:** None. The bit is always present in the
  one-octet Options field; there is nothing to negotiate.
