# RFC 7440 - TFTP Windowsize Option

## Meta

| Field | Value |
|-------|-------|
| RFC | 7440 |
| Title | TFTP Windowsize Option |
| Status | Standards Track |
| Date | January 2015 |
| Author | P. Masotta (Serva) |
| Enrolment | enrolled |
| Enrolment reason | TFTP Windowsize Option: nine MUST-level requirements. 3-1 (all RRQ/WRQ fields except the opcode are NUL-terminated ASCII strings) is met with positive+negative tags on the RRQ parser (internal/plugins/tftpserver/handler.go:61 parseRRQ rejects a field lacking its NUL). The eight windowsize-option MUSTs (3-2 value range, 3-3 acknowledged windowsize, 3-4 client uses the OACK windowsize, 4-1 windowed send, 4-2 windowed ACK, 4-3 windowsize-1 equivalence, 4-4 timeout window-start, 4-5 sequence-error rollback) are {not-applicable}: ze's TFTP server implements base RFC 1350 with the RFC 2347/2348/2349 blksize and tsize options only; it records the windowsize option name but discards the value and never negotiates it, falling back to lockstep. |
| Support | - |

**Purpose:** Defines the "windowsize" option for TFTP option negotiation (RFC 2347),
allowing client and server to negotiate a window of consecutive data blocks
to be sent before waiting for an ACK, replacing the single-block lockstep
of RFC 1350.

**Scope:** Single option definition. Uses the OACK mechanism from RFC 2347.
Composable with blksize (RFC 2348).

## Option Specification (Section 3)

| Field | Value |
|-------|-------|
| Option name | `windowsize` (case-insensitive) |
| Option value | ASCII decimal, number of consecutive blocks per window |
| Valid range | 1 to 65535, inclusive |
| Default (no negotiation) | 1 (equivalent to RFC 1350 lockstep) |

### Wire Format in RRQ/WRQ

```
    2B     string   1B   string   1B     string     1B   string   1B
   +-------+---~~---+----+---~~---+----+-----~~-----+----+---~~---+----+
   |  opc  |filename|  0 |  mode  |  0 | windowsize |  0 | #blocks|  0 |
   +-------+---~~---+----+---~~---+----+-----~~-----+----+---~~---+----+
```

## Negotiation (Section 3)

- Server's acknowledged value MUST be less than or equal to client's value.
- Client MUST use the OACK value or send ERROR code 8 to terminate.

## Traffic Flow (Section 4)

- Data sender sends `windowsize` consecutive data blocks, then stops and
  waits for an ACK of the last block in the window.
- Data receiver sends ACK of the last data block of the window.
- On timeout (no ACK received), the last received ACK sets the start of
  the next window.
- On sequence error, receiver sends ACK of the last correctly received
  block; sender restarts from that point.

## MUST Requirements

- "Traffic with windowsize = 1 MUST be equivalent to traffic specified
  by [RFC1350]." (Section 4)
- "The DSND MUST cyclically send to the DRCV the agreed windowsize
  consecutive data blocks before normally stopping and waiting for the
  ACK of the transferred window." (Section 4)
- "The DRCV MUST send to the DSND the ACK of the last data block of the
  window in order to confirm a successful data block window reception."
  (Section 4)
- Server's acknowledged windowsize MUST be <= client's requested value.
  (Section 3)

## SHOULD/MAY

- [SHOULD] "Operators SHOULD test various values and SHOULD be
  conservative when selecting a windowsize value" (Section 5)
- [SHOULD] "Implementations SHOULD always set a maximum number of
  retries for datagram retransmissions" (Section 6)
- [SHOULD] Data receiver SHOULD notify sender of sequence errors by
  ACKing the last correctly received block. (Section 4)

## Constants

| Name | Value | Usage |
|------|-------|-------|
| WINDOWSIZE_MIN | 1 | Minimum (equivalent to RFC 1350) |
| WINDOWSIZE_MAX | 65535 | Maximum |
| WINDOWSIZE_DEFAULT | 1 | Used when option not negotiated |

## Pitfalls

- **windowsize=1 is RFC 1350:** A server that does not want to implement
  windowed transfers can acknowledge windowsize=1 in the OACK and
  proceed with standard lockstep.

- **Final window:** A window with fewer blocks than the negotiated
  windowsize is the final window. Same end-of-transfer rule as
  RFC 1350/2348 (short data block = last block).

- **Error recovery rewinds:** On sequence error or timeout, the sender
  must go back to the block after the last ACKed block and resend a
  full window from there.

- **Congestion:** Recommended implementation example for Ethernet
  (1 Gbit/s, MTU=1500): windowsize=8, blksize=1456, max retransmit=6,
  timeout=1s, inter-packet delay=80us. (Section 6)

## Compliance Checklist

- [ ] [RFC7440-3-1] [MUST] All fields in RRQ/WRQ except "opc" MUST be ASCII strings followed by a single-byte NULL character (§3)
- [ ] [RFC7440-3-2] [MUST] Valid windowsize values MUST be between 1 and 65535 blocks, inclusive (§3) {not-applicable: ze does not implement the RFC 7440 windowsize option; parseRRQ records the option name as a bool and discards the value (internal/plugins/tftpserver/handler.go:129-130) without range-validating it, and the option is never negotiated}
- [ ] [RFC7440-3-3] [MUST] Server's acknowledged windowsize MUST be less than or equal to the client's requested value (§3) {not-applicable: ze never acknowledges the windowsize option -- sendOACKAndWait (internal/plugins/tftpserver/handler.go:312-343) builds the OACK from blksize/tsize only, so there is no acknowledged windowsize to constrain}
- [ ] [RFC7440-3-4] [MUST] Client MUST use the windowsize specified in the OACK or send ERROR code 8 to terminate (§3) {not-applicable: this is a TFTP client obligation (use the OACK windowsize or send ERROR 8); ze is a TFTP server and does not implement the windowsize option}
- [ ] [RFC7440-4-1] [MUST] The data sender MUST cyclically send the agreed windowsize consecutive data blocks before stopping and waiting for ACK (§4) {not-applicable: ze's TFTP server transfers in RFC 1350 lockstep -- one DATA block per ACK (serveFile/sendAndWaitACK internal/plugins/tftpserver/handler.go:346-413) -- and implements no windowed send; it logs a fallback to lockstep when a client requests windowsize (handler.go:276-277)}
- [ ] [RFC7440-4-2] [MUST] The data receiver MUST send ACK of the last data block of the window to confirm successful reception (§4) {not-applicable: ze acknowledges each single DATA block, not a window -- serveFile/sendAndWaitACK wait for the ACK of the one block just sent (internal/plugins/tftpserver/handler.go:346-413); with no negotiated windowsize there is no last-block-of-window ACK to send}
- [ ] [RFC7440-4-3] [MUST] Traffic with windowsize=1 MUST be equivalent to traffic specified by RFC 1350 (§4) {not-applicable: ze's default RFC 1350 lockstep is windowsize-1-equivalent by construction, but the windowsize option itself is unimplemented -- parseRRQ discards the requested value (internal/plugins/tftpserver/handler.go:129-130) and the OACK never carries windowsize (handler.go:312-343), so there is no negotiated windowsize=1 to equate}
- [ ] [RFC7440-4-4] [MUST] On timeout, the beginning of the next window MUST be set based on the last received ACK (§4) {not-applicable: ze retransmits the single unacknowledged block on timeout (sendAndWaitACK internal/plugins/tftpserver/handler.go:386-413) and computes no window start; with no windowed send there is no next-window beginning to derive from the last ACK}
- [ ] [RFC7440-4-5] [MUST] On sequence error, the sender's new window beginning MUST be set based on the ACK received out of sequence (§4) {not-applicable: ze has no windowed transfer, so no out-of-sequence window recomputation exists -- sendAndWaitACK only accepts the ACK matching the block just sent and otherwise retransmits that one block (internal/plugins/tftpserver/handler.go:404-411)}
- [ ] [RFC7440-5-1] [SHOULD] Operators SHOULD test various windowsize values and SHOULD be conservative when selecting (§5)
- [ ] [RFC7440-6-1] [SHOULD] Implementations SHOULD always set a maximum number of retries for datagram retransmissions (§6)
- [ ] [RFC7440-6-2] [SHOULD] After max retries exceeded, a transfer SHOULD always be aborted (§6)
- [ ] [RFC7440-4-6] [SHOULD] The data receiver SHOULD notify the sender of sequence errors by ACKing the last correctly received block (§4)
- [ ] [RFC7440-6-3] [SHOULD] The rate of TFTP UDP datagrams SHOULD follow the congestion control guidelines in RFC 5405 Section 3.1 (§6)
- [ ] [RFC7440-7-1] [NOT RECOMMENDED] TFTP file transfers are NOT RECOMMENDED where the inherent protocol limitations could raise insurmountable liability concerns (§7)
