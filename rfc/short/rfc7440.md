# RFC 7440 - TFTP Windowsize Option

## Meta

| Field | Value |
|-------|-------|
| RFC | 7440 |
| Title | TFTP Windowsize Option |
| Status | Standards Track |
| Date | January 2015 |
| Author | P. Masotta (Serva) |

**Purpose:** Defines the "windowsize" option for TFTP option negotiation (RFC 2347),
allowing client and server to negotiate a window of consecutive data blocks
to be sent before waiting for an ACK, replacing the single-block lockstep
of RFC 1350.

**Scope:** Single option definition. Uses the OACK mechanism from RFC 2347.
Composable with blksize (RFC 2348).

## Option Specification (Section 3)

| Field | Value |
|-------|-------|
| Option name | `windowsize` (case-insensitive) |
| Option value | ASCII decimal, number of consecutive blocks per window |
| Valid range | 1 to 65535, inclusive |
| Default (no negotiation) | 1 (equivalent to RFC 1350 lockstep) |

### Wire Format in RRQ/WRQ

```
    2B     string   1B   string   1B     string     1B   string   1B
   +-------+---~~---+----+---~~---+----+-----~~-----+----+---~~---+----+
   |  opc  |filename|  0 |  mode  |  0 | windowsize |  0 | #blocks|  0 |
   +-------+---~~---+----+---~~---+----+-----~~-----+----+---~~---+----+
```

## Negotiation (Section 3)

- Server's acknowledged value MUST be less than or equal to client's value.
- Client MUST use the OACK value or send ERROR code 8 to terminate.

## Traffic Flow (Section 4)

- Data sender sends `windowsize` consecutive data blocks, then stops and
  waits for an ACK of the last block in the window.
- Data receiver sends ACK of the last data block of the window.
- On timeout (no ACK received), the last received ACK sets the start of
  the next window.
- On sequence error, receiver sends ACK of the last correctly received
  block; sender restarts from that point.

## MUST Requirements

- "Traffic with windowsize = 1 MUST be equivalent to traffic specified
  by [RFC1350]." (Section 4)
- "The DSND MUST cyclically send to the DRCV the agreed windowsize
  consecutive data blocks before normally stopping and waiting for the
  ACK of the transferred window." (Section 4)
- "The DRCV MUST send to the DSND the ACK of the last data block of the
  window in order to confirm a successful data block window reception."
  (Section 4)
- Server's acknowledged windowsize MUST be <= client's requested value.
  (Section 3)

## SHOULD/MAY

- [SHOULD] "Operators SHOULD test various values and SHOULD be
  conservative when selecting a windowsize value" (Section 5)
- [SHOULD] "Implementations SHOULD always set a maximum number of
  retries for datagram retransmissions" (Section 6)
- [SHOULD] Data receiver SHOULD notify sender of sequence errors by
  ACKing the last correctly received block. (Section 4)

## Constants

| Name | Value | Usage |
|------|-------|-------|
| WINDOWSIZE_MIN | 1 | Minimum (equivalent to RFC 1350) |
| WINDOWSIZE_MAX | 65535 | Maximum |
| WINDOWSIZE_DEFAULT | 1 | Used when option not negotiated |

## Pitfalls

- **windowsize=1 is RFC 1350:** A server that does not want to implement
  windowed transfers can acknowledge windowsize=1 in the OACK and
  proceed with standard lockstep.

- **Final window:** A window with fewer blocks than the negotiated
  windowsize is the final window. Same end-of-transfer rule as
  RFC 1350/2348 (short data block = last block).

- **Error recovery rewinds:** On sequence error or timeout, the sender
  must go back to the block after the last ACKed block and resend a
  full window from there.

- **Congestion:** Recommended implementation example for Ethernet
  (1 Gbit/s, MTU=1500): windowsize=8, blksize=1456, max retransmit=6,
  timeout=1s, inter-packet delay=80us. (Section 6)

## Compliance Checklist

- [ ] [MUST] All fields in RRQ/WRQ except "opc" MUST be ASCII strings followed by a single-byte NULL character (§3)
- [ ] [MUST] Valid windowsize values MUST be between 1 and 65535 blocks, inclusive (§3)
- [ ] [MUST] Server's acknowledged windowsize MUST be less than or equal to the client's requested value (§3)
- [ ] [MUST] Client MUST use the windowsize specified in the OACK or send ERROR code 8 to terminate (§3)
- [ ] [MUST] The data sender MUST cyclically send the agreed windowsize consecutive data blocks before stopping and waiting for ACK (§4)
- [ ] [MUST] The data receiver MUST send ACK of the last data block of the window to confirm successful reception (§4)
- [ ] [MUST] Traffic with windowsize=1 MUST be equivalent to traffic specified by RFC 1350 (§4)
- [ ] [MUST] On timeout, the beginning of the next window MUST be set based on the last received ACK (§4)
- [ ] [MUST] On sequence error, the sender's new window beginning MUST be set based on the ACK received out of sequence (§4)
- [ ] [SHOULD] Operators SHOULD test various windowsize values and SHOULD be conservative when selecting (§5)
- [ ] [SHOULD] Implementations SHOULD always set a maximum number of retries for datagram retransmissions (§6)
- [ ] [SHOULD] After max retries exceeded, a transfer SHOULD always be aborted (§6)
- [ ] [SHOULD] The data receiver SHOULD notify the sender of sequence errors by ACKing the last correctly received block (§4)
- [ ] [SHOULD] The rate of TFTP UDP datagrams SHOULD follow the congestion control guidelines in RFC 5405 Section 3.1 (§6)
- [ ] [NOT RECOMMENDED] TFTP file transfers are NOT RECOMMENDED where the inherent protocol limitations could raise insurmountable liability concerns (§7)
