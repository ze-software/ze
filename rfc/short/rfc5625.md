**Purpose:** Guidance for DNS proxies in residential gateways: be
transparent, proxy what you do not understand, carry large answers (TC,
TCP, EDNS0), keep TSIG working, let LAN hosts reach upstream resolvers
directly, and do not hand out a default domain name.

**Scope:** Section 4 binds the DNS proxy; Section 5 binds the gateway's
DHCP server; Section 6 is the security guidance. Ze's LAN resolver is not
a packet-level proxy: it answers from its cache or asks the upstream with
a query of its own (docs/architecture/dns/lan-resolver.md, "The upstream
query"). Each Section 4 row is judged on what reaches the client and the
upstream through that resolver.

## Compliance Checklist

- [ ] [RFC5625-4.1-1] [MUST] Therefore, proxies MUST ignore any unknown DNS flags and proxy those packets as usual. (§4.1)
- [ ] [RFC5625-4.2-1] [MUST] Proxies MUST forward packets regardless of the presence or absence of compressed labels therein. (§4.2)
- [ ] [RFC5625-4.3-1] [MUST] All requests and responses MUST be proxied regardless of the values of the QTYPE and QCLASS fields. (§4.3)
- [ ] [RFC5625-4.3-2] [MUST] Similarly, all responses MUST be proxied regardless of the values of the TYPE and CLASS fields of any Resource Record therein. (§4.3)
- [ ] [RFC5625-4.4-1] [MUST] Where the required portions of a response would not fit inside that limit, the DNS server MUST set the "TrunCation" (TC) bit in the DNS response header to indicate that truncation has occurred. (§4.4)
- [ ] [RFC5625-4.4-2] [MUST] If a proxy must unilaterally truncate a response, then the proxy MUST set the TC bit. (§4.4)
- [ ] [RFC5625-4.4-3] [MUST NOT] Similarly, proxies MUST NOT remove the TC bit from responses. (§4.4)
- [ ] [RFC5625-4.4.1-1] [MUST] DNS proxies MUST therefore be prepared to receive and forward queries over TCP. (§4.4.1)
- [ ] [RFC5625-4.4.2-1] [MUST NOT] As per Section 4.1, proxies MUST NOT refuse to proxy such packets. (§4.4.2)
- [ ] [RFC5625-4.5-1] [MUST] DNS proxies MUST implement Section 4.7 of [RFC2845] and either forward packets unchanged (as recommended above) or fully implement TSIG. (§4.5) {gap: the LAN resolver re-originates every query and answers from its cache, so a TSIG-signed query is neither forwarded unchanged nor verified, and its reply carries no TSIG; internal/plugins/dnsresolver/forward.go upstreamQuery}
- [ ] [RFC5625-4.5-2] [MUST] As per Section 4.3, DNS proxies MUST be capable of proxying packets containing TKEY [RFC2930] Resource Records. (§4.5) {gap: the TKEY record of a query's additional section is not carried into the upstream query the LAN resolver builds; internal/plugins/dnsresolver/forward.go upstreamQuery}
- [ ] [RFC5625-5.2-1] [MUST NOT] this option MUST NOT be sent to clients when no value is configured. (§5.2)
- [ ] [RFC5625-3-1] [RECOMMENDED] It is RECOMMENDED that proxies should be as transparent as possible, such that any "hop-by-hop" mechanisms or newly introduced protocol extensions operate as if the proxy were not there. (§3)
- [ ] [RFC5625-3-2] [SHOULD] Except when required to enforce an active security or network policy (such as maintaining a pre-authentication "walled garden"), end-users SHOULD be able to send their DNS queries to specified upstream resolvers, thereby bypassing the proxy altogether. (§3)
- [ ] [RFC5625-3-3] [SHOULD NOT] In this case, the gateway SHOULD NOT modify the DNS request or response packets in any way. (§3)
- [ ] [RFC5625-4.4-4] [SHOULD NOT] Since UDP packets larger than 512 octets are now expected in normal operation, proxies SHOULD NOT truncate UDP packets that exceed that size. (§4.4)
- [ ] [RFC5625-4.4.1-2] [SHOULD] Therefore, whenever a proxy receives a request over TCP, the proxy SHOULD forward the query over TCP (§4.4.1)
- [ ] [RFC5625-4.4.1-3] [SHOULD NOT] and SHOULD NOT attempt the same query over UDP first. (§4.4.1)
- [ ] [RFC5625-4.4.3-1] [SHOULD] Therefore (irrespective of which of the above methods is in use), proxies SHOULD be capable of forwarding UDP packets up to a payload size of at least 4096 octets. (§4.4.3)
- [ ] [RFC5625-5.1-1] [SHOULD] As per Section 3, end-users SHOULD be able to send their DNS queries directly to specified upstream resolvers, ideally without hard-coding those settings in their stub resolver. (§5.1)
- [ ] [RFC5625-5.1-2] [RECOMMENDED] It is therefore RECOMMENDED that gateways SHOULD support device- administrator configuration of values for the "Domain Name Server" DHCP option. (§5.1)
- [ ] [RFC5625-5.2-2] [RECOMMENDED] Since no standard exists for a "local" scoped domain name suffix, it is RECOMMENDED that the default value for this option SHOULD be empty (§5.2)
- [ ] [RFC5625-6.1-1] [RECOMMENDED] It is strongly RECOMMENDED that DNS proxies follow the relevant recommendations in [RFC5452], particularly those in Section 9.2 relating to randomisation of Query IDs and source ports. (§6.1)
- [ ] [RFC5625-6.1-2] [SHOULD] If a DNS proxy is running on a broadband gateway with NAT that is compliant with [RFC4787], then it SHOULD also follow the recommendations in Section 10 of [RFC5452] concerning how long DNS state is kept. (§6.1)
- [ ] [RFC5625-6.2-1] [SHOULD NOT] The DNS proxy in a gateway SHOULD NOT, by default, be accessible from the WAN interfaces of the device. (§6.2)
- [ ] [RFC5625-6.3-2] [SHOULD] In these circumstances, proxies SHOULD synthesise a suitable DNS error response to the client (i.e., SERVFAIL) instead of dropping the packet completely. (§6.3)
