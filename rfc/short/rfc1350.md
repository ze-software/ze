**Purpose:** TFTP is a simple protocol to transfer files over UDP. It is
designed to be small and easy to implement, lacking directory listing,
user authentication, and most features of FTP.

**Scope:** File transfer over UDP. Server listens on port 69. Each transfer
uses a new pair of ephemeral ports (Transfer IDs). Supports two modes:
"octet" (raw 8-bit bytes) and "netascii" (NVT ASCII). The "mail" mode is
obsolete (Section 1).

**Errata:**
- 7167 (Verified, Section 6): "Datagram length < 516" should account for
  UDP header; does not affect implementation (we check data length < 512).
- 4971 (Verified, Section 6): Conflicting correction to same text.
  Neither affects implementation.
- 1712 (Held, Section 3): Spelling fix only.

## Wire Formats

### Opcodes (Section 5)

```
   opcode  operation
     1     Read request (RRQ)
     2     Write request (WRQ)
     3     Data (DATA)
     4     Acknowledgment (ACK)
     5     Error (ERROR)
```

### RRQ/WRQ Packet (Section 5, Figure 5-1)

```
    2 bytes    string   1 byte     string   1 byte
    -----------------------------------------------
   | 01/02 |  Filename  |   0  |    Mode    |   0  |
    -----------------------------------------------
```

| Field | Offset | Size | Type | Constraints |
|-------|--------|------|------|-------------|
| Opcode | 0 | 2 | uint16 | 1 (RRQ) or 2 (WRQ), big-endian |
| Filename | 2 | variable | string | NUL-terminated, netascii |
| Mode | variable | variable | string | NUL-terminated, case-insensitive: "octet" or "netascii" |

### DATA Packet (Section 5, Figure 5-2)

```
    2 bytes    2 bytes       n bytes
    ---------------------------------
   | 03    |   Block #  |    Data    |
    ---------------------------------
```

| Field | Offset | Size | Type | Constraints |
|-------|--------|------|------|-------------|
| Opcode | 0 | 2 | uint16 | 3 (DATA), big-endian |
| Block# | 2 | 2 | uint16 | Starts at 1, consecutive, big-endian |
| Data | 4 | 0-512 | bytes | 512 for non-final blocks; 0-511 for final block |

"The data field is from zero to 512 bytes long. If it is 512 bytes
long, the block is not the last block of data; if it is from zero to
511 bytes long, it signals the end of the transfer." (Section 5)

### ACK Packet (Section 5, Figure 5-3)

```
    2 bytes    2 bytes
    -------------------
   | 04    |   Block #  |
    --------------------
```

| Field | Offset | Size | Type | Constraints |
|-------|--------|------|------|-------------|
| Opcode | 0 | 2 | uint16 | 4 (ACK), big-endian |
| Block# | 2 | 2 | uint16 | Block number being acknowledged; 0 for WRQ ACK |

"A WRQ is acknowledged with an ACK packet having a block number of
zero." (Section 5)

### ERROR Packet (Section 5, Figure 5-4)

```
    2 bytes  2 bytes        string    1 byte
    ----------------------------------------
   | 05    |  ErrorCode |   ErrMsg   |   0  |
    ----------------------------------------
```

| Field | Offset | Size | Type | Constraints |
|-------|--------|------|------|-------------|
| Opcode | 0 | 2 | uint16 | 5 (ERROR), big-endian |
| ErrorCode | 2 | 2 | uint16 | Error code (see table), big-endian |
| ErrMsg | 4 | variable | string | Human-readable, netascii, NUL-terminated |

## Encoding Rules

- All multi-byte fields are big-endian (network byte order).
- Strings in RRQ/WRQ are NUL-terminated (zero byte delimiter).
- Mode string is case-insensitive: "any combination of upper and lower
  case, such as 'NETASCII', 'NetAscii', etc." (Section 5)
- Data blocks are fixed 512 bytes except the final block (0-511 bytes).

## Decoding Rules

- First 2 bytes determine packet type (opcode).
- RRQ/WRQ: scan for NUL bytes to find filename and mode boundaries.
- DATA: block number at offset 2, data starts at offset 4.
- ACK: block number at offset 2, no payload.
- ERROR: error code at offset 2, scan for NUL-terminated message at offset 4.

## Validation

| Check | Valid | Invalid Action |
|-------|-------|----------------|
| Opcode | 1-5 | Ignore packet |
| RRQ/WRQ mode | "octet" or "netascii" (case-insensitive) | ERROR code 4 |
| Source TID | Matches established TID | ERROR code 5 to unexpected source; do not disturb current transfer |
| DATA block# | Expected next block | Duplicate: ignore (Sorcerer's Apprentice fix) |
| Data length | 0-512 bytes | Malformed packet |

## MUST Requirements

### Tx
- "the file is sent in fixed length blocks of 512 bytes" (Section 2)
- "Each data packet contains one block of data, and must be acknowledged
  by an acknowledgment packet before the next packet can be sent." (Section 2)
- "The host sending the last DATA must retransmit it until the packet is
  acknowledged or the sending host times out." (Section 6)

### Rx
- "A host which receives netascii mode data must translate the data to
  its own format." (Section 5)
- "If a host receives a octet file and then returns it, the returned
  file must be identical to the original." (Section 5)

### State
- "block numbers are consecutive and begin with one" (Section 4)
- "the positive response to a write request is an acknowledgment packet,
  in this special case the block number will be zero" (Section 4)
- "each end of the connection chooses a TID for itself, to be used for
  the duration of that connection" (Section 4)

### Errors
- "Timeouts must also be used to detect errors." (Section 7)
- "If a source TID does not match, the packet should be discarded as
  erroneously sent from somewhere else. An error packet should be sent
  to the source of the incorrect packet, while not disturbing the
  transfer." (Section 4)

## SHOULD/MAY

- [SHOULD] "dallying is encouraged" for the host sending the final ACK:
  "the host sending the final ACK will wait for a while before
  terminating in order to retransmit the final ACK if it has been
  lost" (Section 6)
- [SHOULD] "The TID's chosen for a connection should be randomly chosen,
  so that the probability that the same number is chosen twice in
  immediate succession is very low." (Section 4)

## Error Handling

| Condition | Detect How | Response | Code |
|-----------|------------|----------|------|
| File not found | os.Open fails | ERROR packet | 1 |
| Access violation | Permission denied | ERROR packet | 2 |
| Disk full | Write fails mid-transfer | ERROR packet | 3 |
| Illegal operation | Unknown opcode, bad mode | ERROR packet | 4 |
| Unknown transfer ID | Source TID mismatch | ERROR to incorrect source; continue transfer | 5 |
| File already exists | File exists on write | ERROR packet | 6 |
| No such user | Mail mode recipient invalid | ERROR packet | 7 |
| Not defined | Any other error | ERROR packet with message | 0 |

"Most errors cause termination of the connection. An error is
signalled by sending an error packet. This packet is not acknowledged,
and not retransmitted" (Section 2)

"TFTP recognizes only one error condition that does not cause
termination, the source port of a received packet being incorrect."
(Section 2)

## State Machine

### Read Transfer

| State | Event | Guard | Action | Next |
|-------|-------|-------|--------|------|
| IDLE | RRQ received | File exists, accessible | Send DATA block 1 from new TID | SEND_DATA |
| IDLE | RRQ received | File missing or denied | Send ERROR | IDLE |
| SEND_DATA | ACK received | Block# matches, data was 512 bytes | Send next DATA block | SEND_DATA |
| SEND_DATA | ACK received | Block# matches, data was < 512 bytes | Transfer complete | DONE |
| SEND_DATA | Timeout | Retries remaining | Retransmit last DATA | SEND_DATA |
| SEND_DATA | Timeout | No retries left | Abort | DONE |
| SEND_DATA | Duplicate ACK | Block# < current | Ignore (Sorcerer's Apprentice fix) | SEND_DATA |
| SEND_DATA | Wrong TID | Source port mismatch | Send ERROR code 5 to wrong source | SEND_DATA |

### Write Transfer

| State | Event | Guard | Action | Next |
|-------|-------|-------|--------|------|
| IDLE | WRQ received | File writable | Send ACK block 0 from new TID | RECV_DATA |
| IDLE | WRQ received | Cannot write | Send ERROR | IDLE |
| RECV_DATA | DATA received | Block# matches | Write data, send ACK | RECV_DATA or DONE |
| RECV_DATA | Timeout | Retries remaining | Retransmit last ACK | RECV_DATA |
| RECV_DATA | DATA received | Data < 512 bytes | Write data, send ACK, transfer complete | DONE |

## Algorithms

### Sorcerer's Apprentice Fix (Section 2, per RFC 1123 Section 4.2)

The original TFTP (RFC 783) had a protocol flaw where duplicate ACKs
caused escalating duplicate DATA packets:

1. Sender sends DATA block N.
2. Receiver sends ACK N.
3. ACK N delayed; sender times out, retransmits DATA N.
4. Original ACK N arrives; sender sends DATA N+1.
5. Retransmitted DATA N arrives; receiver sends duplicate ACK N.
6. Duplicate ACK N arrives; sender re-sends DATA N+1 (BUG).

Fix: when the sender receives a duplicate ACK (block number it has
already advanced past), it MUST ignore the duplicate and NOT resend the
next DATA block. Only a timeout triggers retransmission.

### Connection Establishment (Section 4)

Read:
1. Host A sends RRQ to host B, source = A's TID, destination = port 69.
2. Host B sends DATA (block 1) to host A, source = B's TID, destination = A's TID.

Write:
1. Host A sends WRQ to host B, source = A's TID, destination = port 69.
2. Host B sends ACK (block 0) to host A, source = B's TID, destination = A's TID.

### Normal Termination (Section 6)

"The end of a transfer is marked by a DATA packet that contains
between 0 and 511 bytes of data." The final DATA is acknowledged
normally. The sender retransmits until acknowledged or timed out.
The acknowledger SHOULD "dally" (wait before closing) to retransmit the
final ACK if lost.

## Pitfalls

- **Zero-length final block:** When file size is an exact multiple of 512,
  the sender must send a final DATA packet with zero bytes of data.
  Omitting this causes the receiver to wait indefinitely for more data.

- **Sorcerer's Apprentice:** Duplicate ACKs must be silently ignored.
  Retransmitting on duplicate ACKs creates an escalating flood.

- **TID validation:** Each transfer uses unique ephemeral ports. Packets
  from unexpected source ports must be rejected with ERROR code 5, not
  processed as part of the current transfer.

- **Port 69 vs transfer port:** Initial request goes to port 69, but
  server responds from a different ephemeral port. Clients must accept
  responses from the server's new TID, not expect port 69.

- **Block number wrap:** Block numbers are uint16 (1-65535). Files larger
  than 65535 * 512 = ~32 MB cause block number wrap. RFC 1350 does not
  define wrap behavior.

## Security Considerations (Section "Security Considerations")

"Since TFTP includes no login or access control mechanisms, care must
be taken in the rights granted to a TFTP server process so as not to
violate the security of the server hosts file system. TFTP is often
installed with controls such that only files that have public read
access are available via TFTP and writing files via TFTP is
disallowed."

| Concern | Mitigation |
|---------|------------|
| No authentication | Restrict server to read-only, serve only from designated directory |
| No encryption | Use on isolated/provisioning networks only |
| Path traversal | Server must validate filenames against serving directory |
| Write abuse | Disable write support (WRQ) unless explicitly needed |
