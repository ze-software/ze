**Purpose:** Defines the MS-CHAPv2 authentication protocol: a challenge/response
mechanism with mutual authentication built on MD4, SHA-1, and DES. The peer proves
it knows the password; the authenticator proves it too knows the password hash.
Both sides derive keying material usable for session encryption (MPPE) or, in the
EAP context, for the Master Session Key (MSK).

**Ze context:** Ze implements native IKEv2. For road warrior VPN clients using
password-based authentication (Windows built-in IKEv2 client defaults to this),
Ze runs EAP-MSCHAPv2 (EAP type 26) inside IKE_AUTH. Ze acts as the EAP
authenticator: it generates the Authenticator Challenge, validates the
NT-Response, computes the Authenticator Response for mutual auth, and derives
the MSK from the MS-CHAPv2 master key. Passwords are stored in Ze config with
`$9$` reversible encoding so Ze can compute the NT password hash at runtime.
Ze runs the peer side too, when it dials an EAP-capable responder as the IKEv2
initiator (`startEAPExchange`, `internal/component/ike/engine/fsm.go`).

## Protocol Flow

MS-CHAPv2 is a three-message mutual authentication exchange. When carried inside
EAP (type 26), each MS-CHAPv2 message is wrapped in an EAP-MSCHAPv2 TLV inside
an EAP Request or Response, which in turn sits inside an IKE_AUTH exchange.

```
Initiator (peer/client)              Responder (authenticator/Ze)
                                     Generate 16-octet AuthenticatorChallenge
                          <--        Challenge (Code 1)
Generate 16-octet PeerChallenge
Compute NT-Response
Response (Code 2)         -->
                                     Verify NT-Response
                                     Compute AuthenticatorResponse
                          <--        Success (Code 3) with S=<40-hex>
Verify S= value
Authentication complete
```

| Step | Direction | Payload | Key fields |
|------|-----------|---------|------------|
| 1 | Authenticator -> Peer | Challenge (Code 1) | 16-octet Authenticator Challenge, authenticator Name |
| 2 | Peer -> Authenticator | Response (Code 2) | 16-octet Peer-Challenge, 8 zero Reserved, 24-octet NT-Response, 1 zero Flags, peer Name |
| 3a | Authenticator -> Peer | Success (Code 3) | `S=<40-hex-uppercase> M=<message>` (mutual auth proof) |
| 3b | Authenticator -> Peer | Failure (Code 4) | `E=<error> R=<retry> C=<32-hex> V=<version> M=<message>` |
| 4 | Peer | (local check) | Verify S= matches expected Authenticator Response; disconnect if wrong |

## Wire Formats

### Challenge Packet (Code 1)

| Field | Size | Value |
|-------|------|-------|
| Code | 1 octet | 1 |
| Identifier | 1 octet | Fresh per challenge; retransmissions reuse same value |
| Length | 2 octets | Total packet length |
| Value-Size | 1 octet | 16 (fixed) |
| Authenticator Challenge | 16 octets | Cryptographic random |
| Name | variable | Authenticator identity (to end of packet) |

### Response Packet (Code 2)

| Field | Size | Value |
|-------|------|-------|
| Code | 1 octet | 2 |
| Identifier | 1 octet | Copied from Challenge |
| Length | 2 octets | Total packet length |
| Value-Size | 1 octet | 49 (fixed: 16+8+24+1) |
| Peer-Challenge | 16 octets | Cryptographic random generated by peer |
| Reserved | 8 octets | MUST be zero |
| NT-Response | 24 octets | Three DES blocks (see Crypto Operations) |
| Flags | 1 octet | MUST be zero |
| Name | variable | Peer identity; bare username or `DOMAIN\user` |

### Success Packet (Code 3)

| Field | Size | Value |
|-------|------|-------|
| Code | 1 octet | 3 |
| Identifier | 1 octet | Copied from Response |
| Length | 2 octets | Total packet length |
| Message | variable | `S=<40-hex-uppercase> M=<human-readable>` |

The `S=` field carries the 20-octet Authenticator Response encoded as 40 uppercase hex digits.

### Failure Packet (Code 4)

| Field | Size | Value |
|-------|------|-------|
| Code | 1 octet | 4 |
| Identifier | 1 octet | Copied from Response |
| Length | 2 octets | Total packet length |
| Message | variable | `E=<error> R=<0|1> C=<32-hex-uppercase> V=<version> M=<text>` |

| Element | Meaning |
|---------|---------|
| `E=` | Decimal error code (see Error Codes) |
| `R=` | `1` = retry allowed, `0` = no retry |
| `C=` | Fresh 16-octet challenge as 32 uppercase hex digits (MUST be present) |
| `V=` | Version; SHOULD be `3` for MS-CHAPv2 |
| `M=` | Human-readable text; informational only |

## Crypto Operations

All operations use three primitives: MD4 (16-octet digest), SHA-1 (20-octet
digest), and DES in ECB mode (8-octet block, 7-octet key expanded to 8 with
parity bits).

### NtPasswordHash: password to 16-octet hash

| Input | Transform | Output |
|-------|-----------|--------|
| Password (Unicode, up to 256 chars) | UTF-16LE encode (no null terminator), then MD4 | 16-octet PasswordHash |

This is the standard NT password hash. Ze computes it from the plaintext password
stored in config (under `$9$` reversible encoding).

### HashNtPasswordHash: hash of hash

| Input | Transform | Output |
|-------|-----------|--------|
| 16-octet PasswordHash | MD4 | 16-octet PasswordHashHash |

Used for Authenticator Response generation and MPPE master key derivation.

### ChallengeHash: combine challenges and username into 8-octet value

| Input | Transform | Output |
|-------|-----------|--------|
| 16-octet PeerChallenge, 16-octet AuthenticatorChallenge, UserName (bare, no domain prefix) | SHA-1(PeerChallenge &#124;&#124; AuthenticatorChallenge &#124;&#124; UserName), take first 8 octets | 8-octet Challenge |

The UserName fed to SHA-1 MUST exclude any `DOMAIN\` prefix.

### ChallengeResponse: DES encrypt challenge with password hash

| Input | Transform | Output |
|-------|-----------|--------|
| 8-octet Challenge, 16-octet PasswordHash | Pad PasswordHash to 21 octets with 5 zero bytes. Split into three 7-octet keys. DES-ECB encrypt Challenge with each key. Concatenate three 8-octet ciphertexts. | 24-octet Response |

Each 7-octet key is expanded to 8 octets by inserting a parity bit after every 7 bits.

### GenerateNTResponse: full peer computation

```
ChallengeHash(PeerChallenge, AuthenticatorChallenge, UserName) -> Challenge (8 octets)
NtPasswordHash(Password)                                       -> PasswordHash (16 octets)
ChallengeResponse(Challenge, PasswordHash)                     -> NT-Response (24 octets)
```

### GenerateAuthenticatorResponse: mutual auth proof

```
NtPasswordHash(Password)       -> PasswordHash (16 octets)
HashNtPasswordHash(PasswordHash) -> PasswordHashHash (16 octets)

SHA-1(PasswordHashHash || NT-Response || Magic1) -> Digest (20 octets)
ChallengeHash(PeerChallenge, AuthenticatorChallenge, UserName) -> Challenge (8 octets)
SHA-1(Digest || Challenge || Magic2) -> AuthenticatorResponse (20 octets)
```

| Constant | Size | ASCII |
|----------|------|-------|
| Magic1 | 39 octets | `Magic server to client signing constant\0` (includes null) |
| Magic2 | 41 octets | `Pad to make it do more than one iteration\0` (includes null) |

The 20-octet binary result is hex-encoded to the 40-character `S=` string.

### CheckAuthenticatorResponse: peer verifies server

The peer recomputes GenerateAuthenticatorResponse using its own inputs and compares
the result to the value decoded from the `S=` field. Mismatch means the server does
not know the password hash, and the peer MUST disconnect.

## Mutual Authentication

MS-CHAPv2 provides mutual authentication, unlike plain CHAP:

1. **Peer proves identity:** NT-Response can only be computed by someone who knows the password (or its NT hash).
2. **Authenticator proves identity:** The Authenticator Response in the `S=` field can only be computed by someone who knows the NT password hash. It binds PasswordHashHash, the NT-Response, both challenges, and the username through SHA-1.

Without verifying the `S=` field, a rogue authenticator could accept any Response and the peer would not detect the impersonation.

## MPPE Key Derivation (RFC 3079 Section 3)

When MS-CHAPv2 is used inside EAP, the key derivation produces the EAP Master
Session Key (MSK). Ze needs this to complete the IKEv2 EAP exchange, because
RFC 5765 / RFC 3748 Section 7.10 require the MSK to be fed into the IKEv2
AUTH payload computation after EAP success.

### GetMasterKey

```
SHA-1(PasswordHashHash || NTResponse || Magic1) -> take first 16 octets = MasterKey
```

| Constant | Size | ASCII |
|----------|------|-------|
| Magic1 | 27 octets | `This is the MPPE Master Key` |

### GetAsymmetricStartKey

```
SHA-1(MasterKey || SHSpad1 || Magic || SHSpad2) -> take first SessionKeyLength octets
```

| Constant | Size | Value |
|----------|------|-------|
| SHSpad1 | 40 octets | 40 bytes of `0x00` |
| SHSpad2 | 40 octets | 40 bytes of `0xf2` |

The Magic constant selects direction:

| Magic constant | Size | ASCII | Used when |
|----------------|------|-------|-----------|
| Magic2 | 84 octets | `On the client side, this is the send key; on the server side, it is the receive key.` | IsSend=true (client) or IsSend=false (server) |
| Magic3 | 84 octets | `On the client side, this is the receive key; on the server side, it is the send key.` | IsSend=false (client) or IsSend=true (server) |

### MSK Construction for EAP

The EAP MSK (64 octets) is constructed by concatenating:

| Offset | Size | Content |
|--------|------|---------|
| 0 | 16 octets | Server receive key = GetAsymmetricStartKey(MasterKey, 16, IsSend=true, IsServer=true) |
| 16 | 16 octets | Server send key = GetAsymmetricStartKey(MasterKey, 16, IsSend=false, IsServer=true) |
| 32 | 16 octets | SHSpad1 (padding to 64 octets) |
| 48 | 16 octets | SHSpad2 (padding to 64 octets) |

Ze derives this MSK after successful MS-CHAPv2 and uses it in the IKEv2 AUTH
payload computation per RFC 7296 Section 2.16.

## Ze Integration: EAP-MSCHAPv2 inside IKEv2

### Protocol Stack

```
IKE_AUTH exchange
  +-- EAP payload (RFC 7296 Section 3.16)
       +-- EAP-MSCHAPv2 (EAP type 26, RFC 2759 + draft-kamath-pppext-eap-mschapv2)
            +-- MS-CHAPv2 Challenge / Response / Success / Failure
```

### Ze as EAP Authenticator

| Responsibility | Detail |
|----------------|--------|
| Generate Authenticator Challenge | 16 cryptographic random octets |
| Validate NT-Response | Compute expected NT-Response from stored password hash; compare to received |
| Compute Authenticator Response | GenerateAuthenticatorResponse for the `S=` field |
| Derive MSK | GetMasterKey then GetAsymmetricStartKey, construct 64-octet MSK |
| Complete IKE_AUTH | Use MSK as the shared secret for the final AUTH payload |

### Password Storage

Ze stores passwords in config with `$9$` reversible encoding. At authentication
time, Ze decodes the password, computes `NtPasswordHash(UTF-16LE(password))`, and
uses the 16-octet hash for all subsequent operations. The plaintext password is
discarded after hashing.

### Username Handling

The peer's IKEv2 IDi payload provides the username. For ChallengeHash, only the
bare username is used (strip any `DOMAIN\` prefix). Feeding the full
`DOMAIN\user` string to SHA-1 produces a wrong Challenge and authentication fails.

## Pitfalls

| Pitfall | Consequence |
|---------|-------------|
| Value-Size in Response is fixed at 49 | Any other value is a protocol violation; MUST reject |
| Reserved (8 octets) and Flags (1 octet) in Response MUST be zero | Non-zero MUST be rejected |
| NT password hash uses UTF-16LE, not UTF-8 | Common interop break between Windows and Linux |
| ChallengeHash uses bare username without `DOMAIN\` prefix | Full `DOMAIN\user` in SHA-1 never matches |
| `S=` hex digits MUST be uppercase A-F | Lowercase comparison fails against compliant peers |
| Success/Failure Message has no length prefix | Runs from byte 5 to end of packet (no Msg-Length octet) |
| MD4 has no salt | NT hash is vulnerable to precomputation; MS-CHAPv2 security relies on challenge freshness |

## Validation

| Check | Action on failure |
|-------|-------------------|
| Response Value-Size != 49 | Reject as malformed |
| Response Reserved octets non-zero | Reject as malformed |
| Response Flags octet non-zero | Reject |
| NT-Response mismatch | Send Failure with `E=691`; terminate |
| Authenticator Response (`S=`) mismatch at peer | Peer MUST disconnect |
| Authenticator Challenge not cryptographic random | Security violation |

## Security Considerations

| Concern | Detail |
|---------|--------|
| No session confidentiality | MS-CHAPv2 alone provides no encryption; IKEv2 ESP provides it |
| Offline dictionary attack | An observer of Challenge/Response can brute-force the password offline |
| MD4 weakness | NT hash has no salt; precomputed tables apply |
| Brute-force | Authenticator SHOULD limit retry count |
| Mitigation in Ze | MS-CHAPv2 runs inside IKE_AUTH (encrypted by IKE SA keys from IKE_SA_INIT DH exchange), so the challenge/response is not visible to passive observers |

## Change-Password (Section 6)

Change-Password (Code 7) allows a peer to change an expired password when the
authenticator returns `E=648`. Ze does not implement Change-Password. The packet
is 586 octets total, carrying an RC4-encrypted new password block, the old hash
encrypted with the new hash, a fresh Peer-Challenge, and an NT-Response computed
on the new password. Ze ignores Code 7 packets.
