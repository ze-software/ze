# RFC 9190 - EAP-TLS 1.3: Using the Extensible Authentication Protocol with TLS 1.3

**Purpose:** Specifies how to run EAP-TLS over TLS 1.3. TLS 1.3 changes the message flow, the handshake messages, the key schedule, the cipher suites, the resumption mechanism, and the privacy protection. Large parts of the normative text in RFC 5216 therefore do not apply. This document replaces the parts that do not apply, and it adds guidance on authentication, authorization, and resumption that applies to EAP-TLS with any TLS version.

## Applicability: which document governs

| Negotiated TLS version | Governing text |
|------------------------|----------------|
| TLS 1.3 | RFC 9190, plus RFC 5216 text that RFC 9190 does not replace |
| TLS 1.2 | RFC 5216 |
| Any version | RFC 9190 Sections 2.2 and 5.7 only |

An EAP-TLS implementation must know which TLS version was negotiated. The version selects the applicable specification.

**Terminology.** EAP-TLS peer is the entity that acts as EAP peer and TLS client. EAP-TLS server is the entity that acts as EAP server and TLS server. The document follows TLS-bis terminology: `master_secret` is renamed the main secret, and `exporter_master_secret` is renamed the exporter secret.

## New TLS 1.3 Handshake Messages in EAP-TLS

| Message | Treatment in EAP-TLS |
|---------|----------------------|
| HelloRetryRequest | The server rejects the offered parameters and proposes new ones. It adds one round trip. See Section 2.1.6 |
| NewSessionTicket | Carries resumption material. See Sections 2.1.2 and 2.1.3 |
| KeyUpdate | Not needed. EAP-TLS does not encrypt a significant amount of data. Implementations SHOULD NOT send it, but some TLS libraries generate and process it automatically |
| Early data | MUST NOT be used. Servers MUST NOT send an `early_data` extension, and clients MUST NOT send an `EndOfEarlyData` message |
| Post-handshake authentication | MUST NOT be used. Clients MUST NOT send a `post_handshake_auth` extension, and servers MUST NOT request post-handshake client authentication |

SessionID is deprecated in TLS 1.3. Resumption uses the PSK mechanism instead.

## Message Flows

### Full handshake with mutual authentication (Figure 1, §2.1.1)

```
 EAP-TLS Peer                                      EAP-TLS Server

                                                      EAP-Request/
                             <--------                   Identity
 EAP-Response/
 Identity (Privacy-Friendly) -------->
                                                      EAP-Request/
                                                 EAP-Type=EAP-TLS
                             <--------                 (TLS Start)
 EAP-Response/
 EAP-Type=EAP-TLS
(TLS ClientHello)            -------->
                                                      EAP-Request/
                                                 EAP-Type=EAP-TLS
                                                 (TLS ServerHello,
                                          TLS EncryptedExtensions,
                                           TLS CertificateRequest,
                                                  TLS Certificate,
                                            TLS CertificateVerify,
                             <--------               TLS Finished)
 EAP-Response/
 EAP-Type=EAP-TLS
(TLS Certificate,
 TLS CertificateVerify,
 TLS Finished)               -------->
                                                      EAP-Request/
                                                 EAP-Type=EAP-TLS
                             <-------- (TLS Application Data 0x00)
 EAP-Response/
 EAP-Type=EAP-TLS            -------->
                             <--------                EAP-Success
```

The full handshake always provides forward secrecy, because the ClientHello and the ServerHello exchange ephemeral `key_share` extensions.

### Ticket establishment (Figure 2, §2.1.2)

The same flow, with `TLS NewSessionTicket` sent in the same EAP-Request as the application data 0x00, or in an earlier one.

### Resumption (Figure 3, §2.1.3)

```
 EAP-TLS Peer                                      EAP-TLS Server

                                                      EAP-Request/
                             <--------                   Identity
 EAP-Response/
 Identity (Privacy-Friendly) -------->
                                                      EAP-Request/
                                                 EAP-Type=EAP-TLS
                             <--------                 (TLS Start)
 EAP-Response/
 EAP-Type=EAP-TLS
(TLS ClientHello
 + pre_shared_key)           -------->
                                                      EAP-Request/
                                                 EAP-Type=EAP-TLS
                                                 (TLS ServerHello,
                                          TLS EncryptedExtensions,
                             <--------            TLS Finished,
                                             TLS NewSessionTicket)
 EAP-Response/
 EAP-Type=EAP-TLS
(TLS Finished)               -------->
                                                      EAP-Request/
                                                 EAP-Type=EAP-TLS
                             <-------- (TLS Application Data 0x00)
 EAP-Response/
 EAP-Type=EAP-TLS            -------->
                             <--------                EAP-Success
```

### Failure flows (Figures 4, 5, 6, §2.1.4)

| Figure | Case | Flow |
|--------|------|------|
| 4 | Server rejects the ClientHello | Server sends a TLS Error alert, the peer answers with an EAP-Response, the server sends EAP-Failure |
| 5 | Server authentication fails at the peer | The peer sends a TLS Error alert, the server sends EAP-Failure |
| 6 | Peer authentication fails at the server | The server sends a TLS Error alert, the peer answers with an EAP-Response, the server sends EAP-Failure |

In TLS 1.3 error alerts are always fatal. The only alerts at warning level are `close_notify` and `user_canceled`, and both mean the connection does not continue normally. TLS 1.3 does not make an alert mandatory after a fatal error. EAP-TLS 1.3 strengthens that: an implementation that meets a fatal error condition MUST send an appropriate TLS Error alert.

### No peer authentication (Figure 7, §2.1.5)

The server omits the CertificateRequest, and the peer sends only TLS Finished. This case is for deployments such as emergency services.

### Hello retry request (Figure 8, §2.1.6)

The server answers the first ClientHello with a HelloRetryRequest, and the peer sends a second ClientHello. One use case is a server that supports no group in the `key_share` extension, or receives no `key_share` extension, but does support a group in `supported_groups`.

## Key Hierarchy (§2.3)

TLS 1.3 replaces the TLS PRF with HKDF and changes the key schedule. The key hierarchy in RFC 5216 Section 2.3 is therefore not correct for TLS 1.3. Key material comes from the TLS exporter interface, defined in RFC 5705 and in RFC 8446 Section 7.5.

```
Type = 0x0D
Key_Material = TLS-Exporter("EXPORTER_EAP_TLS_Key_Material",
                            Type, 128)
Method-Id    = TLS-Exporter("EXPORTER_EAP_TLS_Method-Id",
                            Type, 64)
Session-Id   = Type || Method-Id
```

```
MSK          = Key_Material(0, 63)
EMSK         = Key_Material(64, 127)
```

| Value | Exporter label | Context | Length |
|-------|----------------|---------|--------|
| Key_Material | `EXPORTER_EAP_TLS_Key_Material` | `Type` = 0x0D, one octet | 128 octets |
| Method-Id | `EXPORTER_EAP_TLS_Method-Id` | `Type` = 0x0D, one octet | 64 octets |
| MSK | first half of Key_Material | | 64 octets |
| EMSK | second half of Key_Material | | 64 octets |
| Session-Id | `Type` concatenated with Method-Id | | 65 octets |

`Type` is the value of the EAP Type field defined in RFC 3748 Section 2. For EAP-TLS the value is 0x0D.

**Length rule.** The key derivation MUST use the lengths above. TLS 1.2 and earlier permitted truncation by a request for less data from the exporter. TLS 1.3 does not. An implementation that intends to use only a part of the exporter output MUST request the full output, then use the desired part. A shorter request produces different, incorrect values.

**Initialization vectors.** RFC 5247 deprecates the IV. RECV-IV and SEND-IV are not exported in EAP-TLS with TLS 1.3.

**Cross-version note.** The EAP-TLS exporter used with TLS 1.2 generates the same key material as RFC 5216.

## Protected Success and Failure Indication (§2.5)

TLS 1.3 post-handshake messages use the handshake content type and can arrive after the main handshake. After the server sends TLS Finished, it can send any number of post-handshake messages in one or more EAP-Requests. The peer therefore cannot tell from the handshake alone that the exchange succeeded. The following procedure removes that uncertainty and MUST be followed.

| Step | Actor | Action |
|------|-------|--------|
| 1 | Server | Process the TLS client Finished successfully, and send the last handshake message, either Finished or a post-handshake message |
| 2 | Server | Send an encrypted TLS record with application data 0x00. This record is the protected success result indication defined in RFC 3748 |
| 3 | Server | After the EAP-Request that carries the indication, send no more EAP-Requests. Only EAP-Success may follow |
| 4 | Peer | Answer with an EAP-Response of EAP-Type=EAP-TLS and no data |
| 5 | Server | Send EAP-Success |

The server MUST NOT send an encrypted TLS record with application data 0x00 before it has processed the client Finished successfully and sent its last handshake message.

**Ordering caveat.** A TLS implementation MAY not let the EAP-TLS layer control the send order, so the application data MAY be sent before a NewSessionTicket. The application data 0x00 is therefore read as success after the EAP-Request that contains it, not by its position among the post-handshake messages.

**Failure indication.** TLS Error alerts SHOULD be treated as a failure result indication as defined in RFC 3748. An implementation that follows RFC 4137 sets `altReject` after it sends or receives an error alert. After a TLS Error alert is sent or received, the server may only send EAP-Failure. A protected TLS Error alert is a protected failure result indication. An unprotected one is not.

**State machine variables (RFC 4137).**

| Variable | When it can be set |
|----------|--------------------|
| `eapKeyData`, `aaaEapKeyData` | After the TLS server Finished has been sent or received |
| `eapKeyAvailable`, `aaaEapKeyAvailable` | After the authenticated success result indication has been sent or received |
| `altReject` | After a TLS Error alert is sent or received |

## Authentication (§2.1.1)

| Rule | Detail |
|------|--------|
| Server credential | The server MUST authenticate with a certificate |
| Peer credential | The server SHOULD require the peer to authenticate with a certificate |
| Certificate types | Any type that TLS supports, including raw public keys |
| PSK | PSK authentication SHALL NOT be used except for resumption |
| Forward secrecy | Always present in the full handshake, through ephemeral `key_share` extensions |
| Early application data | Not used in EAP-TLS |

## Ticket Establishment and Resumption

### Ticket establishment (§2.1.2)

| Rule | Detail |
|------|--------|
| Issuing tickets | To enable resumption, the server MUST send one or more post-handshake NewSessionTicket messages during the initial authentication |
| Timing | The NewSessionTicket is sent after the server has received the client Finished. It can go in the same flight as the server Finished, or later |
| Precomputation | With client authentication the PSK depends on the client Finished, so it cannot be precomputed for the server Finished flight |
| Lifetime | TLS 1.3 caps the ticket lifetime at 604800 seconds, which is 7 days. Servers MUST respect that limit |
| Early data | The NewSessionTicket MUST NOT include an `early_data` extension. A received `early_data` extension MUST be ignored |
| Quantity | Fewer tickets are needed than in a normal HTTPS scenario. One ticket is usually enough |

### Resumption (§2.1.3)

| Rule | Detail |
|------|--------|
| Mechanism | With TLS 1.3, EAP-TLS SHALL use a resumption mechanism compatible with TLS 1.3, which is the PSK exchange of RFC 8446 Section 2.2 |
| Peer choice | It is RECOMMENDED that the peer use resumption when it holds a valid, unused ticket |
| Server choice | It is RECOMMENDED that the server accept resumption while the issued ticket is valid. The server MAY require a full handshake instead |
| Full handshake fallback | When a full handshake is required, the resumption attempt is ignored and Sections 2.1.1 and 2.1.2 apply in full |
| Key exchange mode | The `psk_dh_ke` key exchange mode MUST be used for resumption, unless the deployment has a local requirement to allow other mechanisms |
| Key share | The peer SHOULD supply a `key_share` extension when it attempts resumption, so the server can decline and fall back to a full handshake without an extra HelloRetryRequest round trip |
| Ticket reuse | Reuse of a ticket lets a passive observer correlate connections. Peers and servers SHOULD follow the client tracking preventions in RFC 8446 Appendix C.4 |
| NAI realm | It is RECOMMENDED to use NAIs with the same realm in the resumption and in the original full handshake, so EAP packets route to the same destination. Resumption is likely impossible otherwise |
| NAI reuse | When reuse carries no privacy implication, it is RECOMMENDED to use the same NAI. `@realm` is safe to reuse. A unique username is not, because it lets an on-path attacker link the resumption to the original handshake |
| PSK identity as NAI | The TLS PSK identity is typically an opaque blob with no routable realm, so it is unsuitable as an NAI in the Identity Response |

## Identity and Privacy (§2.1.7, §2.1.8)

| Rule | Detail |
|------|--------|
| Anonymous NAI support | Peer and server implementations that support TLS 1.3 MUST support anonymous NAIs, defined in RFC 7542 Section 2.4 |
| Cleartext username | A client that supports TLS 1.3 MUST NOT send its username, or any other permanent identifier, in cleartext in the Identity Response or in any message used instead of it |
| Preferred form | It is RECOMMENDED to omit the username, which makes the NAI `@realm` |
| Other allowed forms | A fixed username such as `anonymous@realm`, or an encrypted username |
| Encoding | The NAI MUST be a UTF-8 string per the grammar in RFC 7542 Section 2.2 |
| Identity Response content | Anonymous NAIs are RECOMMENDED because they are routable and privacy-friendly. Opaque blobs are NOT RECOMMENDED, because they are not routable |
| Derived anonymous NAI | When the client certificate holds an NAI as subject name or alternative subject name, an anonymous NAI SHOULD be derived from it |
| Privacy handshake | The HelloRequest message used for privacy in EAP-TLS 1.2 does not exist in TLS 1.3. Certificate messages are encrypted, so no empty `certificate_list` and no second handshake are needed |
| Empty certificate_list | Peer and server SHALL follow TLS 1.3 processing: the peer sends an empty `certificate_list` only when it has no appropriate certificate, and the server MAY treat an empty `certificate_list` as a terminal condition |
| Round trips | EAP-TLS with TLS 1.3 is always used with privacy, and privacy adds no round trip |

Cipher suites without confidentiality are forbidden, so TLS 1.3 always encrypts large parts of the handshake, including the certificate messages.

## Identity Verification (§2.2)

This guidance applies to EAP-TLS with any TLS version.

| Rule | Detail |
|------|--------|
| Trust in the Identity Response | The EAP peer identity in EAP-Response/Identity is not authenticated by EAP-TLS. Unauthenticated information MUST NOT be used for accounting or to give authorization |
| Permitted use | The authenticator and the server MAY examine that identity for purposes such as routing and EAP method selection, and servers MAY reject conversations when the identity does not match policy |
| Server identity | The server identity in the TLS server certificate is typically an FQDN in the SubjectAltName extension |
| Peer configuration | Peer implementations SHOULD allow configuration of one or more trusted root certificates and one or more server names to match against the SAN extension |
| Name match rule | The name check passes when any configured name matches any name in the SAN extension |
| Consequence of no name matching | Confidence that the server is authoritative for the network degrades. With a public root CA, any server can obtain a certificate the peer will trust |
| Provisioning | The process of configuring a root CA certificate and a server name is not trivial, so automated provisioning methods are RECOMMENDED |
| TOFU | With no trusted root CA certificate, peers MAY implement trust on first use, storing the server certificate at the first connection and requiring the same certificate later |
| TOFU limits | TOFU does not allow the server certificate to change without out-of-band validation, so it does not suit deployments with several servers for high availability, and it raises exposure to traffic interception |

## Fragmentation (§2.1.9)

A single TLS record can be up to 16645 octets, which includes the ContentType of 1 octet, the ProtocolVersion of 2 octets, and the length of 2 octets. Fragmentation uses the flags octet and the conditional TLS Message Length field of 4 octets, as in RFC 5216.

| Rule | Detail |
|------|--------|
| L bit on send | Implementations MUST NOT set the L bit in unfragmented messages |
| L bit on receive | Implementations MUST accept unfragmented messages with the L bit set and without it |
| Avoidance | Some EAP implementations and access networks limit the number of EAP packet exchanges. It is RECOMMENDED to keep peer, server, and trust anchor certificates small, and certificate chains short |
| Message size reduction | It is RECOMMENDED to use mechanisms that reduce the size of Certificate messages. RFC 9191 discusses this in detail |

## Parameter Negotiation (§2.4)

| Rule | Detail |
|------|--------|
| Cipher suite definitions | TLS 1.3 defines cipher suites differently, so the cipher suites in RFC 5216 Section 2.4 cannot be used with TLS 1.3 |
| Compliance | Peers and servers MUST comply with the compliance requirements in RFC 8446 Section 9, which cover mandatory-to-implement cipher suites, signature algorithms, key exchange algorithms, and extensions |
| Confidentiality | Only cipher suites with confidentiality SHALL be supported |
| Data protection | EAP-TLS protects no application data except the 0x00 byte that carries the success indication. The negotiated cipher suites and algorithms MAY be used to secure data, as other TLS-based EAP methods do |

## Certificate Revocation (§5.4)

Revocation of the server certificate is complicated, because the peer may have no Internet connectivity until authentication completes.

| Rule | Detail |
|------|--------|
| Chain checking | With TLS 1.3, the revocation status of every certificate in the certificate chains MUST be checked, except the trust anchor |
| Permitted methods | CRL, OCSP, or other standardized or proprietary methods, including non-standard revocation list formats and certificates with a very short lifetime |
| Server obligation | Servers that support TLS 1.3 MUST implement Certificate Status Requests, that is OCSP stapling, per RFC 6066 and RFC 8446 Section 4.4.2.1 |
| Recommended use | It is RECOMMENDED that peers and servers use OCSP stapling to verify the status of the server certificate chain |
| Peer obligation on stapling | A peer that uses Certificate Status Requests MUST treat a CertificateEntry without a valid CertificateStatus extension as invalid, and MUST abort the handshake with an appropriate alert. The trust anchor is excluded |
| TLS 1.3 carriage | OCSP information is carried in the CertificateEntry of the associated certificate, not in a separate CertificateStatus message as in RFC 6066. This lets a server send OCSP information for every certificate in the chain except the trust anchor |
| Post-authentication check | Peer implementations MUST also support revocation checking after authentication completes and network connectivity is available |
| Trust before checking | A peer implementation SHOULD NOT trust the network, or any service on it, until it has verified the revocation status of the server certificate after it receives connectivity |
| Transport for the check | A peer MUST use a secure transport to verify the revocation status of the server certificate |
| Traffic before the check | A peer SHOULD NOT send any other traffic before revocation checking for the server certificate is complete |

## Authorization (§5.6)

This guidance applies to EAP-TLS with any TLS version.

| Rule | Detail |
|------|--------|
| Unauthenticated peers | When peer authentication is not used, server implementations MUST limit network access appropriately, for example with a walled garden or a quarantine network |
| Resumption privilege | Implementations MUST use resumption with caution, so a resumed session is not granted more privilege than the original session was intended to have |
| Basis for decisions | Authorization and accounting MUST be based on authenticated information, such as information in the certificate, or the PSK identity and cached data provisioned for resumption |
| NAI requirements | The NAI requirements in RFC 7542 Section 4 still apply and MUST be followed |
| Non-EAP information | Encapsulating protocols such as PPP, RADIUS, Diameter, and PANA can supply non-EAP information, for example MAC addresses, IP addresses, port numbers, and SSIDs. Servers can make policy decisions on a combination of EAP-TLS and non-EAP information, and MAY reject conversations on that basis |
| SAN to CA binding | Peer implementations MAY bind the configured acceptable SAN to a specific CA that should have issued the server certificate, which prevents attacks from rogue or compromised CAs |

## Resumption Security (§5.7)

This guidance applies to EAP-TLS with any TLS version. "Cached data" means the authorization information from the initial full handshake, such as certificate chains.

| Rule | Detail |
|------|--------|
| Authorization source | Authorization during resumption MUST be based on cached data |
| Policy continuity | Any security policy for authorization MUST be followed for resumption as well |
| Fresh checks | Peer and server MAY perform fresh revocation checks on the cached certificate data, and MAY force a full handshake when cached revocation data is not current enough |
| Caching obligation | The server or the client MUST cache data during the initial full handshake sufficient to allow authorization decisions during resumption |
| Retrieval failure | When cached data cannot be retrieved securely, resumption MUST NOT be done |
| Accounting | Accounting must be tied to an authenticated identity, and resumption supplies none. Systems that expect to perform accounting SHOULD cache an identifier for later accounting |
| Storage limit | Peers MUST NOT store resumption PSKs or tickets, and the associated cached data, for longer than 604800 seconds, which is 7 days, whatever the PSK or ticket lifetime says |
| Early deletion | The peer MAY delete them earlier by local policy. Cached data MAY also be removed by peer or server when a certificate in the chain is revoked or expired. Resumption then falls back to a full handshake |
| TOCTOU risk | EAP and non-EAP information can change between the initial handshake and resumption. A malicious user can supply one set of data at initial authentication and a different set at resumption, which can yield access they should not have |
| Reevaluation | Decisions made with information that has changed MUST be reevaluated when the change may lead to a different decision. It is RECOMMENDED to reevaluate authorization, accounting, and policy decisions on the resumption information |
| Mismatch handling | Servers MAY reject resumption when the resumption information does not match the original authentication. When a safe decision is not possible, servers SHOULD reject the resumption and continue with a full handshake |

### Two ways to retrieve cached data

| Method | Where state lives | Identifier |
|--------|-------------------|------------|
| Local cache | Server and client each cache the information | Session ID before TLS 1.3, PSK identity in TLS 1.3 |
| Ticket (RFC 5077, RFC 8446) | The server encapsulates the information in a ticket held by the client, encrypted with a key only the server knows | The ticket itself |

The client caches the original handshake information locally in both methods, because it needs that information while it selects the session ID or PSK identity for resumption.

## Packet Modification Attacks (§5.5)

Only the parts of the TLS Data that TLS protects are integrity and replay protected. Everything else can be modified, spoofed, or replayed: EAP-Request and EAP-Response headers, the identity in the Identity Response, the EAP-TLS packet header fields, Type, Flags, EAP-Success, and EAP-Failure.

Protected TLS Error alerts are protected failure result indications, and they let peer and server tell that a failure was not spoofed. They provide integrity and replay protection, but they MAY be unauthenticated. They do not improve availability much, because TLS 1.3 treats most malformed data as a fatal error.

## Privacy Considerations (§5.8)

| Topic | Detail |
|-------|--------|
| Certificate encryption | All certificates are encrypted. The server identity is protected against a passive attacker only. The client identity is protected against passive and active attackers |
| Realm visibility | The realm in the NAI stays visible. The information it leaks depends on how many users share that realm in the access network |
| Size leakage | Without padding, the EAP-TLS packet sizes leak the size of the client certificate, which can track or identify a user. Peers SHOULD use record padding, per RFC 8446 Section 5.4 |
| Identifier generation | When anonymous NAIs are not used, identities MUST be generated in a cryptographically secure way, so that an attacker cannot tell two identities of one user from two identities of different users in the same realm. Random or pseudo-random usernames used once achieve this |
| Identifier construction | Privacy-friendly usernames MUST NOT include substrings that relate the identity to a specific user, and MUST NOT be formed by a fixed mapping that stays the same across authentications |
| TLS 1.2 downgrade risk | A peer that allows TLS 1.2 without privacy and with a static RSA key exchange can disclose its username. An active attacker impersonates the server, negotiates TLS 1.2 with static RSA, and sends a TLS alert when the peer tries privacy with an empty certificate message. The attacker proves no possession of the private key until Finished, so the peer can disclose its identity first |
| Mitigation | It is RECOMMENDED that peers do not use EAP-TLS with TLS 1.2 and static RSA-based cipher suites without privacy. A peer SHOULD NOT continue the authentication attempt when a TLS 1.2 server answers an empty certificate message with a TLS alert |

## Security Claims Strengthened by TLS 1.3 (§5.1)

| Claim | How TLS 1.3 strengthens it |
|-------|----------------------------|
| Mutual authentication | Revocation checking is mandatory, so authentication with a revoked certificate always fails |
| Confidentiality | Cipher suites that ensure confidentiality are mandatory, certificates and some extensions are encrypted, and privacy is mandatory at no extra round trip |
| Cryptographic strength | TLS 1.3 defines only strong algorithms and always provides forward secrecy. 3DES, CBC mode, RC4, SHA-1, MD5, P-192, and RSA-1024 are not registered for TLS 1.3 |
| Cryptographic negotiation | EAP-TLS inherits TLS 1.3 negotiation of the AEAD algorithm, the HKDF hash algorithm, the key exchange groups, and the signature algorithm |

Forward secrecy note: TLS 1.3 gives forward secrecy for traffic secrets through the post-handshake key update. EAP-TLS 1.3 has no equivalent mechanism for MSK and EMSK. An implementation that uses the exported MSK and EMSK can achieve forward secrecy by frequent derivation of new keys, as in RFC 8446 Section 7.2.

## Cross-Protocol Attacks (§5.11)

Use of the same certificate in several protocols can let an attacker authenticate over one protocol and resume that session in another. The FQDNs in the SAN extension are for EAP validation only, and they do not mean the certificate suits HTTPS or another protocol on the named host. Section 2.1.3 suggests that authorization rules be reapplied on resumption, but it does not mandate it, so cross-protocol resumption can bypass authorization policy. Different certificates and different resumption caches for different protocols are RECOMMENDED.

## Discovered Vulnerabilities (§5.10)

Many attacks on earlier TLS versions are less serious for EAP-TLS, because EAP-TLS uses only the TLS handshake and protects no application data. RFC 7457 summarizes the known attacks, and BCP 195 gives recommendations. EAP-TLS implementations MUST mitigate known attacks, and need to follow new EAP and TLS security guidance such as RFC 8447 and RFC 9155.

| 8094 | 2.1.1 | Technical | Reported | Proposes to reword "Certificates can be of any type supported by TLS including raw public keys" to "Certificates can be of any type supported by TLS. Raw public keys may also be used", because a raw public key is not a certificate |

## Pitfalls

- **Exporter truncation.** A request for fewer than 128 octets from the TLS exporter yields different bytes, not a prefix of the 128-octet output. The MSK computed that way is wrong, and the failure appears only at the lower layer that consumes the MSK.
- **Exporter context.** The context is the single octet 0x0D, and it is a real context value, not an empty context. An empty context produces a different output from a TLS 1.3 exporter.
- **Success indication timing.** The 0x00 application data record can arrive before or after a NewSessionTicket, because a TLS library may control the send order. The indication is defined by the EAP-Request that carries it, never by its position in the post-handshake sequence.
- **A missing success indication.** A server that omits the 0x00 record leaves the peer without a protected success result indication. See errata 7577 for the reported gap in peer-side behavior.
- **Key exchange mode name.** Section 2.1.3 requires the `psk_dh_ke` mode for resumption. RFC 8446 defines the modes `psk_ke` and `psk_dhe_ke`, and the surrounding prose in Section 2.1.3 discusses `psk_dhe_ke`. No erratum is filed for the difference in spelling.
- **Version split.** RFC 5216 governs a TLS 1.2 session and RFC 9190 governs a TLS 1.3 session, but Sections 2.2 and 5.7 of RFC 9190 apply to both. An implementation that selects behavior by document rather than by negotiated version will apply the wrong rules to one of the two.
- **Ticket lifetime is capped twice.** The server caps the lifetime it issues at 604800 seconds, and the peer caps its own storage at 604800 seconds whatever the ticket says. Both caps are needed.
- **Resumption without a key_share.** A peer that omits `key_share` when it attempts resumption forces a HelloRetryRequest when the server declines, which costs an extra round trip.
