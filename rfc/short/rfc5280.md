**Purpose:** Profiles X.509 v3 certificates and v2 CRLs for the Internet: the fields and extensions a CA writes, what a certificate user must accept and recognise, the path validation algorithm (Section 6) and the CRL validation algorithm (Section 6.3).

**Ze context:** Ze fills three roles. As a CA for its own services, `internal/component/pki/ca.go` builds the certificate templates, so the field values are Ze's and Go encodes them. As a certificate user, Ze hands peer chains to `x509.Certificate.Verify` with a trust anchor and the key usages it installs. As a CRL user, EAP-TLS reads the CRLs an operator configures. Ze issues no CRL and runs no OCSP responder.

## Certificate Structure (Section 4.1)

```
Certificate  ::=  SEQUENCE  {
     tbsCertificate       TBSCertificate,
     signatureAlgorithm   AlgorithmIdentifier,
     signatureValue       BIT STRING  }
```

| Field | Section | Ze's CA writes |
|-------|---------|----------------|
| version | 4.1.2.1 | v3 (Go always) |
| serialNumber | 4.1.2.2 | random in [1, 2^128 - 1], at most 17 DER octets |
| signature | 4.1.2.3 | ECDSA with SHA-256, chosen by Go from the P-256 key |
| issuer | 4.1.2.4 | CN=Ze Local CA (empty for the self-signed web certificate) |
| validity | 4.1.2.5 | NotBefore backdated 5 minutes; root 10 years, leaf 24 hours by default |
| subject | 4.1.2.6 | CN=<component name>; empty for the self-signed web certificate |
| unique identifiers | 4.1.2.8 | never |

## Extensions Ze's CA Writes (Section 4.2)

| Extension | Root | Leaf | Critical |
|-----------|------|------|----------|
| basicConstraints | cA TRUE, pathLenConstraint 0 | cA FALSE | yes (Go) |
| keyUsage | keyCertSign, cRLSign, digitalSignature | digitalSignature | yes (Go) |
| subjectKeyIdentifier | generated by Go for a CA | - | no |
| authorityKeyIdentifier | omitted (self-signed) | root's key identifier | no |
| extKeyUsage | - | id-kp-serverAuth | no |
| subjectAltName | - | dNSName and iPAddress per host | critical only with an empty subject |

## Error Handling

| Condition | Detect How | Response |
|-----------|------------|----------|
| Unrecognised critical certificate extension | ParseCertificate records it in UnhandledCriticalExtensions | Verify rejects the certificate |
| Issuer not a CA, or keyUsage without keyCertSign | CheckSignatureFrom | Verify rejects the chain |
| Path longer than pathLenConstraint | Verify | TooManyIntermediates |
| CRL not signed by the certificate's issuer, or past nextUpdate | currentListFrom | EAP-TLS refuses the chain for want of a current CRL |
| Certificate listed on the CRL | revocationEntry | EAP-TLS refuses the session |

## Pitfalls

- **Encoding is Go's, content is Ze's**: CreateCertificate decides the version, the time encoding, the key identifiers and every criticality bit, while the template values (serial, subject, key usage, basic constraints, SANs) are Ze's and owe tests at the template boundary.
- **Critical CRL extensions**: x509.ParseRevocationList keeps unknown critical extensions in Extensions without refusing the list, so the caller must look at them before trusting a delta, partitioned or indirect CRL.
- **ExtKeyUsageAny**: chosen so IKE peers whose certificates carry no extended key usage or strongSwan's id-kp-ipsecIKE verify; it also accepts a certificate restricted to an unrelated purpose.
- **Name chaining**: Go matches issuer to subject by DER bytes, so a CA that re-encodes its name between its own certificate and what it issues breaks the chain.
