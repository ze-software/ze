# RFC 5303 - Three-Way Handshake for IS-IS Point-to-Point Adjacencies

## Meta

| Title | Three-Way Handshake for IS-IS Point-to-Point Adjacencies |
| Status | Standards Track |
| Date | October 2008 |
| Obsoletes | RFC 3373 |
| Updates | - |
| Updated by | - |

**Purpose:** IS-IS (ISO 10589) assumes reliable link-layer protocols on
point-to-point links and therefore uses only a two-way handshake when
establishing adjacencies on point-to-point media. RFC 5303 defines a
backward-compatible extension that adds a three-way handshake, so a system
declares an adjacency Up only when it knows the neighbour is receiving its
IS-IS Hello (IIH) packets. It is fully interoperable with systems that do
not support the extension. The extension also removes the implicit
255-interface limit for point-to-point links.

**Scope:** The extension adds one new IS-IS Option, the Point-to-Point
Three-Way Adjacency TLV (type 0xF0, decimal 240), carried in Point-to-Point
IIH PDUs, plus the procedures that consume it. It does not change LAN
behaviour or any PDU other than the point-to-point IIH. It defines a separate
"three-way state" that is distinct from the ISO 10589 adjacency state
(Section 2.1).

## Problem Solved (Section 1)

The base two-way handshake has three known failure modes:

1. If the link bounces or a system restarts and the triggering CSNP is lost,
   and the link is a cut set of one, the two link-state databases will not
   resynchronise until a full LSP refresh period (up to 18 hours).
2. If the link fails in one direction only, just one system detects the
   failure. With two parallel links, SPF may still compute a path and the
   undetecting system sends traffic down the failed direction.
3. On some physical layers, interconnectivity can change without a
   link-layer-down event, so a system can believe it is adjacent to a remote
   system that is in fact adjacent to a third system.

## Adjacency Three-Way State (Section 2.1)

The adjacency three-way state can be one of three values:

| State | Meaning |
|-------|---------|
| Down | Initial state. The system has not received any IIH containing the three-way handshake option on this circuit. |
| Initializing | The system has received an IIH containing the three-way handshake option from a neighbour but does not yet know whether the neighbour is receiving its own IIH packets. |
| Up | The system knows the neighbour is receiving its IIH packets. |

The three-way state is not equal or equivalent to the ISO 10589 adjacency
state. When this mechanism is supported, an adjacency has both states.
Receipt of an Intermediate System Hello (ISH) moves the ISO 10589 adjacency
to Initializing but has no effect on the three-way state, which remains
firmly Down until an IIH containing the three-way handshaking option is
received from a neighbour.

The neighbour's system ID and (newly defined) extended circuit ID are
reported in order to detect the case where the same stream is being received
by multiple systems, only one of which can talk back.

The new mechanism only comes into play when the remote system includes the
new option in its IIH packet. If the option is not present, the system is
assumed not to support the mechanism and the old procedures are used
(Section 2.1).

## Wire Format

### Point-to-Point Three-Way Adjacency Option (Section 3.1)

- Type: 0xF0 (decimal 240)
- Length: total length of the value field (1 to 17 octets)

```
                                            No. of Octets
+-----------------------------------+
| Adjacency Three-Way State         |      1
+-----------------------------------+
| Extended Local Circuit ID         |      4
+-----------------------------------+
| Neighbor System ID                |  ID Length
+-----------------------------------+
| Neighbor Extended Local Circuit ID|      4
+-----------------------------------+
```

| Field | Size | Meaning |
|-------|------|---------|
| Adjacency Three-Way State | 1 octet | The three-way state of the point-to-point adjacency. Values: 0 = Up, 1 = Initializing, 2 = Down. |
| Extended Local Circuit ID | 4 octets | Unique ID assigned to this circuit when it is created by this Intermediate system. |
| Neighbor System ID | ID Length octets | System ID of the neighbouring Intermediate system if known. The length equals the "ID Length" of the IIH PDU (ISO 10589 section 9.7). |
| Neighbor Extended Local Circuit ID | 4 octets | Extended Local Circuit ID of the other end of the adjacency if known. |

The value field length therefore ranges from 1 octet (state only) to 17
octets (state + 4 + ID Length of 8 + 4, with ID Length 8 being the common
case making the full TLV 1 + 4 + 8 + 4 = 17 octets).

## More Than 256 Interfaces (Section 2.2)

The IS-IS specification has an implicit limit of 256 interfaces because of
the eight-bit Circuit ID field. The only true constraint is 256 LAN
interfaces for which a system is the Designated IS, because the circuit ID is
advertised in LSPs only in the pseudo-node LSP ID. Because the four-octet
Extended Local Circuit ID is an integral part of the new handshaking
mechanism, it provides a backward-compatible way to expand the
point-to-point circuit ID number space. The Extended Local Circuit ID is not
necessarily related to the value carried in the Local Circuit ID field of the
IIH PDU (Section 3.2).

## MUST / SHALL / SHOULD (Section 3.1)

- "Any system that supports this mechanism SHALL include this option in its
  Point-to-Point IIH packets."
- "Any system that does not understand this option SHALL ignore it, and (of
  course) SHALL NOT include it in its own IIH packets."
- "Any system that supports this mechanism MUST include the Adjacency
  Three-Way State field in this option. The other fields in this option
  SHOULD be included as explained below in section 3.2."
- "Any system that is able to process this option SHALL follow the procedures
  below."

## Elements of Procedure (Section 3.2)

The handshake procedure is added to the point-to-point IIH state machine
after the PDU acceptance tests have been performed.

Sending (added as clause e to ISO 10589 section 8.2.3):

- The IS SHALL include the Point-to-Point Three-Way Adjacency option in the
  transmitted Point-to-Point IIH PDU, reporting the current three-way state
  in the Adjacency Three-Way State field. If no adjacency exists, the state
  SHALL be reported as Down.
- The Extended Local Circuit ID field SHALL contain a value assigned by this
  IS when the circuit is created. This value SHALL be unique among all the
  circuits of this Intermediate System.
- If the neighbour's system ID and Extended Local Circuit ID are known (state
  Initializing or Up), they SHALL be reported in the Neighbor System ID and
  Neighbor Extended Local Circuit ID fields.

Receiving (added as ISO 10589 section 8.2.4.1.1):

- If a received Point-to-Point IIH does not contain the option, the link is
  assumed functional in both directions and the section 8.2.4.2 procedures
  are followed.
- If the option is present but the Adjacency Three-Way State is invalid, the
  PDU SHALL be discarded and no further action is taken.
- If the option has a valid state, the Neighbor System ID and Neighbor
  Extended Local Circuit ID fields, if present, SHALL be examined. If present
  and the Neighbor System ID does not match the local system's ID, or the
  Neighbor Extended Local Circuit ID does not match the local extended
  circuit ID, the PDU SHALL be discarded and no further action is taken.
- If those fields match the local system, or are not present, the section
  8.2.4.2 procedures are followed with the changes below.

## Adjacency Three-Way State Table (Section 3.2)

When the action from section 8.2.4.2 a or b is "Up" or "Accept", the IS
performs the action from this table, based on the current three-way state and
the received Adjacency Three-Way State:

```
                          Received Adjacency Three-Way State
                             Down       Initializing    Up
                       --------------------------------------
          Down         |  Initialize        Up         Down
                       |
  Adj.    Initializing |  Initialize        Up         Up
  Three-               |
  Way     Up           |  Initialize        Accept     Accept
  State                |
```

Resulting actions:

- "Down": generate adjacencyStateChange(Down) with reason "Neighbor
  restarted" and delete the adjacency.
- "Initialize": no event; set the three-way state to "Initializing".
- "Up": generate adjacencyStateChange(Up).

Additional rules:

- In section 8.2.4.2 a and b, the "Up" action from state tables 5, 6, 7, 8
  may create a new adjacency, but the three-way state of that adjacency SHALL
  be Down.
- Skip section 8.2.4.2 c and d.
- If the new action is "Initialize", "Up", or "Accept", follow section
  8.2.4.2 e.

The procedure works correctly even if the Neighbor System ID / Neighbor
Extended Local Circuit ID fields are never included, providing backward
compatibility with an earlier version of the option.

## Backward Compatibility

The extension is interoperable with systems that do not support it. A
non-supporting neighbour never sends the option, so the receiver falls back
to the ISO 10589 two-way procedures (Section 2.1). A non-supporting system
ignores the option if it receives one and never emits it (Section 3.1).

## IANA Considerations (Section 4)

The option uses IS-IS Option type 240 (0xF0), which was already allocated
(per RFC 3359).

## Security Considerations (Section 5)

The document raises no new security issues for IS-IS. IS-IS security (RFC
5304) may be used to secure these messages.
