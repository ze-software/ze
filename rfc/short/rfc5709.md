**Purpose:** RFC 5709 extends the OSPFv2 Cryptographic Authentication mechanism
of RFC 2328 Appendix D (Authentication Type 2, AuType = 2) so that the NIST
Secure Hash Standard (SHS) algorithms can be used in HMAC mode in addition to
the original Keyed-MD5. It adds HMAC-SHA-1, HMAC-SHA-256, HMAC-SHA-384, and
HMAC-SHA-512 as authentication algorithms (Section 3). It explicitly does not
change the OSPFv2 packet structure: the same 8-byte authentication header in the
OSPF packet header is used, and a variable-length message digest is appended to
the packet. The document "does not deprecate or supercede RFC 2328" (Section 1):
Keyed-MD5 remains valid for backwards compatibility.

**Scope:** This summary covers the algorithm-agility model (Section 3), the
algorithm implementation requirements (Section 3), the Authentication Type 2
header field layout inherited from RFC 2328 Appendix D (Key ID, Auth Data
Length, Cryptographic Sequence Number), the appended Authentication
Data / Authentication Trailer, the Apad constant, and the HMAC computation
procedure (Section 3.3). The base OSPFv2 protocol and the original Keyed-MD5
digest procedure are specified in RFC 2328 Appendix D and are referenced rather
than reproduced here.

## Relationship to RFC 2328 Authentication Type 2

OSPFv2 (RFC 2328) defines three authentication types in the OSPF packet header:
AuType 0 (Null), AuType 1 (Simple Password), and AuType 2 (Cryptographic
Authentication). RFC 5709 operates entirely within AuType 2: it reuses the same
8-byte authentication field and the same "append the digest after the packet"
mechanism defined in RFC 2328 Appendix D, and only changes which cryptographic
algorithm computes the digest. The algorithm is selected implicitly by the
Key ID of the OSPFv2 Security Association in use (Section 3.4): "the
cryptographic algorithm/mode in use is indicated implicitly by the KeyID of the
received OSPFv2 packet."

## Algorithm Implementation Requirements (Section 3)

The set of valid algorithms for AuType 2 after this document is: Keyed-MD5 (from
RFC 2328), HMAC-SHA-1, HMAC-SHA-256, HMAC-SHA-384, HMAC-SHA-512.

| Algorithm | Requirement (Section 3) |
|-----------|-------------------------|
| HMAC-SHA-256 | MUST include support |
| HMAC-SHA-1 | SHOULD include support |
| Keyed-MD5 | SHOULD include support (backwards compatibility with existing deployments) |
| HMAC-SHA-384 | MAY include support |
| HMAC-SHA-512 | MAY include support |

In addition (Section 3): an implementation "MUST allow network operators to
configure ANY authentication algorithm supported by that implementation for use
with ANY given KeyID value." This is the algorithm-agility requirement: the
Key ID -> (key, algorithm) binding is operator-configurable rather than fixed.

## Authentication Type 2 Header Field Layout (RFC 2328 Appendix D, used as-is)

The OSPF packet header carries an 8-byte authentication field. For AuType = 2 it
is interpreted as the following (offsets are within the 8-byte authentication
field of the OSPF header):

| Field | Offset (bytes) | Size | Meaning |
|-------|----------------|------|---------|
| Reserved (0) | 0 | 2 bytes | Set to 0 |
| Key ID | 2 | 1 byte | 8-bit unsigned value uniquely identifying the OSPFv2 Security Association; selects the key and algorithm (Section 3.2) |
| Auth Data Length | 3 | 1 byte | Length, in bytes (not bits), of the appended cryptographic digest (Section 3.1) |
| Cryptographic Sequence Number | 4 | 4 bytes | 32-bit anti-replay sequence number, set per RFC 2328 Appendix D (Section 3.1) |

The actual message digest is NOT stored in these 8 bytes. The 8-byte field only
carries Key ID, Auth Data Length, and the Cryptographic Sequence Number; the
variable-length digest is appended after the OSPF packet body (see below).

## Appended Authentication Data / Authentication Trailer

The variable-length message digest is appended to the OSPF packet rather than
placed inside the 8-byte authentication field (Section 3.1, Section 3.3):

- The Authentication Data Length field is set "to the length (measured in bytes,
  not bits) of the cryptographic hash that will be used" (Section 3.1). "When any
  NIST SHS algorithm is used in HMAC mode ... the Authentication Data Length is
  equal to the normal hash output length (measured in bytes)." Example: with
  SHA-256 the Authentication Data Length is 32 bytes (Section 3.1).
- "the message digest is then calculated and appended to the OSPF packet"
  (Section 3.1, step four).
- The appended region is the "Authentication Trailer ... described in RFC 2328,
  Section D.4.3, Page 233, items (6)(a) and (6)(d)" (Section 3.3). The length of
  the Authentication Trailer always equals the message digest size.

Note (RFC 2328 Appendix D, referenced by Section 3.3): the appended
Authentication Data is not counted in the OSPF packet's own Length field, but is
included in the IP datagram's total length.

## Apad and HMAC Constants

The Apad constant fills the appended Authentication Data area before the hash is
computed, so the digest covers a known placeholder rather than uninitialized
bytes. It is also used for consistency with the RIPv2-SHA (RFC 4822) and IS-IS
SHA (RFC 5310) HMAC specifications (Section 4).

Verbatim definitions (Section 3.3):

- "H is the specific hashing algorithm (e.g., SHA-256)."
- "K is the Authentication Key for the OSPFv2 security association."
- "Ko is the cryptographic key used with the hash algorithm."
- "B is the block size of H, measured in octets rather than bits. Note well that
  B is the internal block size, not the hash size."
- "L is the length of the hash, measured in octets rather than bits."
- "Ipad is the hexadecimal value 0x36 repeated B times."
- "Opad is the hexadecimal value 0x5c repeated B times."
- "Apad is the hexadecimal value 0x878FE1F3 repeated (L/4) times."

Because Apad is 0x878FE1F3 (4 octets) repeated L/4 times, Apad is always exactly
L octets long, i.e. the same length as the hash output and the same length as the
appended Authentication Trailer.

| Algorithm (H) | Hash output L (octets) | Block size B (octets) | Apad = 0x878FE1F3 repeated | Auth Data Length |
|---------------|------------------------|-----------------------|----------------------------|------------------|
| HMAC-SHA-1 | 20 | 64 | 5 times | 20 bytes |
| HMAC-SHA-256 | 32 | 64 | 8 times | 32 bytes |
| HMAC-SHA-384 | 48 | 128 | 12 times | 48 bytes |
| HMAC-SHA-512 | 64 | 128 | 16 times | 64 bytes |

| Constant | Value | Length |
|----------|-------|--------|
| Ipad | 0x36 repeated B times | B octets |
| Opad | 0x5c repeated B times | B octets |
| Apad | 0x878FE1F3 repeated (L/4) times | L octets |

## Generating Cryptographic Authentication (Section 3.1)

The sender performs the following (Section 3.1; quoted/paraphrased):

1. Following RFC 2328 Appendix D, select the appropriate OSPFv2 Security
   Association for this packet and set the Key ID field to the Key ID value of
   that Security Association.
2. Set the Authentication Type to Cryptographic Authentication (AuType = 2) and
   set the Authentication Data Length field to the length, in bytes, of the
   cryptographic hash that will be used.
3. Set the 32-bit Cryptographic Sequence Number "in accordance with the
   procedures in RFC 2328, Appendix D that are applicable to the Cryptographic
   Authentication type."
4. Calculate the message digest and append it to the OSPF packet, as described in
   Section 3.3.

## HMAC Computation Procedure (Section 3.3)

The digest is a standard HMAC (two nested hashes) over the OSPF packet, with the
appended Authentication Trailer first filled with Apad. Procedure (Section 3.3,
quoted formulas):

1. Derive the working key Ko from K so that Ko is exactly L octets: if K is L
   octets, Ko = K; if K is longer than L, Ko = H(K); if K is shorter than L, Ko =
   K padded on the right with zero octets to length L.
2. Fill the appended Authentication Trailer with Apad and set the Authentication
   Type field to 2: "the OSPFv2 packet's Authentication Trailer ... is filled with
   the value Apad, and the Authentication Type field is set to 2."
3. Compute the inner hash over the keyed, Ipad-masked block concatenated with the
   whole OSPFv2 packet (which now includes the Apad-filled trailer):
   First-Hash = H(Ko XOR Ipad || (OSPFv2 Packet)).
4. Compute the outer hash:
   Second-Hash = H(Ko XOR Opad || First-Hash).
5. The resulting Second-Hash becomes the Authentication Data; copy it into the
   appended Authentication Trailer (replacing the Apad placeholder). Its length
   equals the hash output length L and matches the Auth Data Length field.

The First-Hash covers the Authentication Trailer that contains the Apad value as
well as the OSPF packet body, per RFC 2328 Section D.4.3.

## OSPF Packet Checksum Handling

RFC 5709 does not restate the checksum-zeroing rule in its own text; it inherits
it from RFC 2328 Appendix D, Section D.4.3, which it references explicitly in
Section 3.3 (items (6)(a) and (6)(d)). Under RFC 2328 AuType 2 the OSPF packet
header Checksum field is set to 0 for packets using Cryptographic Authentication
(the appended digest provides integrity instead of the OSPF checksum). The HMAC
in RFC 5709 is therefore computed over an OSPF packet whose Checksum field is 0
and whose appended trailer holds Apad.

## Message Verification (Section 3.4)

Verification follows RFC 2328 except that the digest is computed using the
Section 3.3 procedure whenever a NIST SHS algorithm in HMAC mode is in use. The
algorithm/mode is indicated implicitly by the Key ID of the received OSPFv2
packet (Section 3.4). Implementation note (Section 3.4): the receiver must save
the received digest value before computing the expected digest value (the
on-the-wire trailer must be replaced with Apad before recomputation).

## OSPFv2 Security Association and Key Rollover (Section 3.2, Section 3.5)

A Key ID identifies an OSPFv2 Security Association (SA), which binds together the
Key ID, the Authentication Algorithm (and HMAC mode), the Authentication Key, and
time windows for key use (Key Start/Stop Accept, Key Start/Stop Generate)
(Section 3.2). Rollover rules (Section 3.2, Section 3.5):

- When the active SA changes, the sender uses the Key ID of the newly active SA;
  the receiver uses that Key ID to select the matching SA for verification
  (Section 3.5).
- When a new key replaces an old key, the new key's KeyStartGenerate time MUST be
  less than or equal to the old key's KeyStopGenerate time (Section 3.2), so there
  is no gap with no usable generate key.
- KeyStartAccept SHOULD be less than KeyStartGenerate, and KeyStopGenerate SHOULD
  be less than KeyStopAccept (Section 3.2), so receivers accept a key before
  senders start using it and continue accepting after senders stop.
- When the last key expires it is unacceptable to revert to an unauthenticated
  condition (Section 3.2).
- The Authentication Key and Authentication Algorithm SHOULD never be sent over
  the wire in cleartext; key storage SHOULD persist across system restart
  (Section 3.2).

## Backward Compatibility

AuType 2 packets, the 8-byte authentication field, the append-the-digest
mechanism, and the Cryptographic Sequence Number anti-replay model are all
unchanged from RFC 2328. Keyed-MD5 remains a valid AuType 2 algorithm and SHOULD
be supported for backwards compatibility (Section 3). Because the algorithm is
selected by Key ID, a deployment can run Keyed-MD5 and HMAC-SHA under different
Key IDs and migrate by rolling Key IDs (Section 3.4, Section 3.5).

## Security Considerations (Section 4)

- HMAC-SHA provides stronger digests than Keyed-MD5 in response to published
  cryptanalysis of MD5/SHA-1; HMAC-SHA-256 is mandatory to implement (Section 3,
  Section 4).
- Apad is used "primarily for consistency with IETF specifications for HMAC-SHA
  authentication of RIPv2 [RFC4822] and IS-IS [RFC5310]" (Section 4).
- The mechanism remains vulnerable to a replay attack by an on-link node via
  sequence-number reuse; an automated key-management mechanism for OSPF is
  desirable (Section 4).
- Because all specified algorithms use symmetric keys, one cannot authenticate
  precisely which OSPF router sent a packet; digital signatures (RFC 2154) are a
  stronger but heavier alternative (Section 4).
- Good cryptographic randomness for keys per RFC 4086 is recommended (Section 4).
