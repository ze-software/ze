**Purpose:** Defines the overall security architecture for IPsec: the Security Policy Database (SPD), Security Association Database (SAD), and the inbound/outbound packet processing model. Ze delegates IKEv2 negotiation to strongSwan/charon and dataplane encryption to the Linux XFRM subsystem; this RFC is the conceptual model behind both. RFC 4303 (ESP wire format) and RFC 7296 (IKEv2) implement the pieces; this RFC defines how they fit together.

## Architecture Overview (Section 3)

IPsec protects IP traffic using two protocols:

| Protocol | IP Proto | Service |
|----------|----------|---------|
| AH (Authentication Header) | 51 | Integrity, data-origin authentication |
| ESP (Encapsulating Security Payload) | 50 | Confidentiality, integrity, data-origin authentication, anti-replay |

Ze uses ESP only (protocol 50). AH is not used in the strongSwan VTI deployment.

Three databases govern processing:

| Database | Purpose |
|----------|---------|
| SPD (Security Policy Database) | Ordered policy rules: which traffic to PROTECT, BYPASS, or DISCARD |
| SAD (Security Association Database) | Per-SA parameters: keys, SPI, algorithms, lifetimes, tunnel endpoints |
| PAD (Peer Authorization Database) | Links IKE peer identity to SPD entries for SA authorization |

On Linux, SPD maps to XFRM policies (`ip xfrm policy`), SAD maps to XFRM states (`ip xfrm state`), and PAD is managed by strongSwan's credential subsystem.

## Tunnel Mode vs Transport Mode (Section 4.1)

| Mode | Description | When required |
|------|-------------|---------------|
| Tunnel | Outer IP header (IPsec endpoints) encapsulates entire inner IP packet (original src/dst). Security protocol header sits between outer and inner headers. | MUST be used whenever either SA endpoint is a security gateway (two exceptions below). |
| Transport | Security protocol header inserted between IP header and next-layer protocol. Protects payload only (ESP) or payload plus selected IP header fields (AH). | Host-to-host only. Security gateways MAY use transport mode only when acting as a host (e.g. SNMP management traffic). |

**Ze uses tunnel mode exclusively** for site-to-site VPN via VTI.

### Tunnel Mode Packet Layout

```
+---------------------------------------------+
| Outer IP Header (src/dst = IPsec endpoints) |
+---------------------------------------------+
| ESP Header (SPI + Sequence Number)          |
+---------------------------------------------+
| Inner IP Header (src/dst = original hosts)  |
+---------------------------------------------+
| Original Payload (TCP, UDP, etc.)           |
+---------------------------------------------+
| ESP Trailer (Padding + Pad Length + NH)      |
+---------------------------------------------+
| ICV (Integrity Check Value)                 |
+---------------------------------------------+
```

Outer header Protocol/Next Header = 50 (ESP). Inner header is the complete original packet carried unchanged. Mixed IP versions permitted (IPv4-in-IPv6, IPv6-in-IPv4).

### Requirements (Section 4.1)

| Requirement | Detail |
|-------------|--------|
| Host MUST support both modes | Transport and tunnel |
| Security gateway MUST support tunnel mode | MAY support transport mode (host-acting-as-host only) |
| SA pairs MUST use same mode | IKE creates paired SAs; both transport or both tunnel |
| Multicast-capable MUST support multicast SAD lookup | Three-step algorithm: SPI+dst+src, then SPI+dst, then SPI alone |

## Security Policy Database (Section 4.4.1)

### Three Processing Actions

| Action | Meaning |
|--------|---------|
| PROTECT | Afford IPsec protection using specified protocols, modes, algorithms |
| BYPASS | Allow traffic to cross IPsec boundary without protection |
| DISCARD | Drop traffic; not allowed to traverse IPsec boundary |

### SPD Subdivisions

| Partition | Contains | Direction |
|-----------|----------|-----------|
| SPD-S | Entries for traffic subject to IPsec protection | Both (creates SAs) |
| SPD-O | Entries for outbound BYPASS or DISCARD traffic | Outbound |
| SPD-I | Entries for inbound BYPASS or DISCARD traffic | Inbound |

The SPD is an ordered database (like ACLs). Entries may overlap; first match wins. Every implementation MUST have at least one SPD. A final default entry SHOULD discard unmatched traffic.

The order is the OPERATOR'S. `policy-priority` under an IPsec peer ranks that peer's entries, lower first, and it defaults to `dataplane.PriorityChildSA` (2000) so an unordered configuration installs what it installed before the leaf existed. `dataplane.PriorityIKEBypass` (100) holds the IKE control-plane bypass, and `ValidatePolicyOrder` refuses a peer rank at or above it, because such an entry captures the IKE exchange that builds and rekeys the SA it protects.

### Selectors (Section 4.4.1.1)

All implementations MUST support:

| Selector | Source | Notes |
|----------|--------|-------|
| Remote IP Address | Dst (outbound) / Src (inbound) | Single, range, or list of ranges |
| Local IP Address | Src (outbound) / Dst (inbound) | Single, range, or list of ranges |
| Next Layer Protocol | IPv4 Protocol / IPv6 Next Header | Specific value, ANY, or OPAQUE |
| Local Port | TCP/UDP/SCTP src port | List of ranges; OPAQUE for fragments |
| Remote Port | TCP/UDP/SCTP dst port | List of ranges; OPAQUE for fragments |
| ICMP Type/Code | 16-bit (type in high 8, code in low 8) | If Next Layer Protocol is ICMP |

Special values: **ANY** (wildcard, encompasses OPAQUE) and **OPAQUE** (field not available due to fragmentation or prior encryption).

### SPD Entry Structure (Section 4.4.1.2)

Each PROTECT entry contains:

| Field | Description |
|-------|-------------|
| Selector sets (1..N) | Traffic matching criteria per selector above |
| PFP flags | Per-selector: derive SA value from packet (true) or from SPD entry (false) |
| IPsec mode | Tunnel or transport |
| Tunnel addresses | Local and remote (tunnel mode only) |
| IPsec protocol | AH or ESP |
| Algorithms | Ordered list by priority |
| Extended Sequence Number flag | Enable 64-bit sequence numbers |
| Stateful fragment checking flag | Maintain reassembly state |
| DF bit bypass | Tunnel mode: copy/set/clear DF from inner header |
| DSCP bypass/mapping | Tunnel mode: how to handle DSCP in outer header |

### XFRM Mapping

| SPD concept | XFRM equivalent |
|-------------|-----------------|
| SPD entry (PROTECT) | `ip xfrm policy` with `dir out` or `dir in`, action `allow`, template referencing SA |
| SPD entry (BYPASS) | `ip xfrm policy` with `dir out/in`, action `allow`, no template |
| SPD entry (DISCARD) | `ip xfrm policy` with `dir out/in`, action `block` |
| Selector (remote addr + port) | Policy selector `src`/`dst` + `proto` + `sport`/`dport` |
| SPD-S/SPD-O/SPD-I | Policy direction (`dir out`, `dir in`, `dir fwd`) |
| PFP flags | Implicit in how strongSwan negotiates traffic selectors |

## Security Association Database (Section 4.4.2)

### SA Definition (Section 4.1)

An SA is a simplex (one-way) connection providing security services via AH or ESP (not both). Bidirectional communication requires a pair of SAs. IKE creates SA pairs explicitly.

### SA Identification

| Traffic type | Lookup key |
|--------------|------------|
| Unicast (inbound) | SPI alone (or SPI + protocol as local matter) |
| Multicast (inbound) | Step 1: SPI + dst + src. Step 2: SPI + dst. Step 3: SPI alone. |
| Outbound | SPD-S cache entry points to SAD entry |

### SAD Data Items (Section 4.4.2.1)

| Field | Size/Type | Description |
|-------|-----------|-------------|
| SPI | 32-bit | Selected by receiver to identify the SA. Outbound: placed in AH/ESP header. Inbound: maps packet to SA. |
| Sequence Number Counter | 64-bit | Generates Sequence Number field. First packet uses value 1. 32-bit also supported if negotiated. |
| Sequence Counter Overflow | flag | If set, overflow generates auditable event and prevents further transmission. If clear, rollover permitted. |
| Anti-Replay Window | 64-bit counter + bitmap | Detects replayed inbound packets. Ignored if anti-replay disabled (e.g. manual keying). |
| AH Auth Algorithm | algorithm + keys | If AH SA (not used by Ze). |
| ESP Encryption Algorithm | algorithm + keys | Cipher, key material, IV requirements. |
| ESP Auth Algorithm | algorithm + keys | Integrity algorithm and key. For AEAD (e.g. AES-GCM): combined mode. |
| IPsec Protocol | AH or ESP | Which protocol this SA uses. |
| IPsec Mode | tunnel or transport | Encapsulation mode. |
| SA Lifetime | time + bytes | Soft limit (rekey trigger), hard limit (SA deletion), idle timeout. |
| Tunnel Header (tunnel mode) | IP addresses | Local tunnel address (outer src), remote tunnel address (outer dst). |
| Traffic Selectors | per selector | Negotiated values for verifying inbound packets match policy. |
| Path MTU | integer | Current PMTU for this SA's path. |
| Stateful Fragment Checking | flag | Maintain fragment reassembly state. |
| Extended Sequence Numbers | flag | 64-bit ESN enabled. |

### SA Lifetime (Section 4.4.2.1)

| Lifetime | Trigger | Action |
|----------|---------|--------|
| Soft (time or bytes) | Threshold reached | Initiate rekeying via IKE. SA remains usable during rekey. |
| Hard (time or bytes) | Threshold reached | Delete SA. No further traffic permitted. |
| Idle (time) | No traffic for duration | Delete SA to reclaim resources. |

### XFRM Mapping

| SAD concept | XFRM equivalent |
|-------------|-----------------|
| SAD entry | `ip xfrm state` |
| SPI | `spi` field in xfrm state |
| ESP encryption algorithm + key | `enc` attribute |
| ESP auth algorithm + key | `auth` attribute (or `aead` for combined mode) |
| Tunnel addresses | `src`/`dst` in xfrm state |
| SA lifetime (soft/hard) | `limit` attributes: `time-soft`, `time-hard`, `byte-soft`, `byte-hard` |
| Anti-replay window | `replay-window` attribute |
| Mode | `mode tunnel` or `mode transport` |
| XFRM mark | Binds SA to VTI interface (not in RFC, Linux extension) |

## Packet Processing Model (Section 5)

### Outbound Processing (Section 5.1)

Direction: protected side to unprotected side.

```
Outbound Packet
     |
     v
[SPD Lookup] -- match selectors against SPD-S and SPD-O
     |
     +---> DISCARD: drop packet
     |
     +---> BYPASS: forward without IPsec
     |
     +---> PROTECT:
              |
              v
         [SAD Lookup] -- find existing SA via SPD-S cache
              |
              +---> No SA exists: trigger IKE negotiation, queue packet
              |
              +---> SA found:
                       |
                       v
                  [Apply ESP/AH] -- encrypt, authenticate per SA parameters
                       |
                       v
                  [Tunnel Header] -- construct outer IP header (tunnel mode)
                       |
                       v
                  [Fragment Check] -- PMTU handling per Section 8
                       |
                       v
                  Forward to network
```

### Inbound Processing (Section 5.2)

Direction: unprotected side to protected side.

```
Inbound Packet
     |
     v
[IPsec Header?] -- check for AH (51) or ESP (50) protocol
     |
     +---> No IPsec header:
     |        |
     |        v
     |   [SPD-I Lookup] -- check BYPASS or DISCARD policy
     |        |
     |        +---> BYPASS: forward to protected side
     |        +---> DISCARD: drop
     |        +---> No match: drop (MUST discard)
     |
     +---> IPsec header present:
              |
              v
         [SAD Lookup] -- SPI (+ dst addr for multicast)
              |
              +---> No SA: discard (auditable event)
              |
              +---> SA found:
                       |
                       v
                  [Anti-Replay Check] -- sequence number in window?
                       |
                       v
                  [Verify Integrity] -- ICV check
                       |
                       v
                  [Decrypt] -- if ESP with encryption
                       |
                       v
                  [Strip Tunnel Header] -- extract inner packet (tunnel mode)
                       |
                       v
                  [Verify Selectors] -- inner header fields match SAD traffic selectors
                       |
                       v
                  Forward to protected side
```

### SPD Consultation Requirement

All traffic crossing the IPsec boundary MUST be checked against SPD/SAD, including IPsec management traffic (IKE). No exception.

## SA and Key Management (Section 4.5)

| Method | Requirement | Notes |
|--------|-------------|-------|
| Manual | MUST support | Administrator configures SA parameters and keys directly into SAD. No rekeying, no anti-replay (window ignored). |
| Automated (IKEv2) | MUST support | IKEv2 (RFC 7296, originally RFC 4306) negotiates SAs, manages rekeying, handles DPD. |

Ze delegates all SA negotiation to strongSwan/charon via its VICI control interface. The kernel XFRM subsystem receives SA/SP installations from charon. Ze manages the lifecycle (start, monitor, restart on DPD failure) but never touches keys or negotiation directly.

### IKE Responsibilities

| Function | Owner |
|----------|-------|
| SA parameter negotiation | IKE (strongSwan) |
| Key generation and exchange | IKE (strongSwan) |
| SA installation into kernel | IKE -> XFRM netlink |
| Rekeying on soft lifetime | IKE (strongSwan) |
| Dead Peer Detection (DPD) | IKE (strongSwan) |
| SA deletion on hard lifetime | IKE (strongSwan) |
| Policy (SPD) installation | IKE -> XFRM netlink (or Ze via `ip xfrm policy`) |

## SA Bundles (Section 4.3)

RFC 4301 removes the "SA bundle" concept from RFC 2401. Nested SAs (e.g. ESP inside AH) are no longer a first-class construct. They can still be achieved through SPD configuration and forwarding table entries, but this is outside the IPsec module proper.

Ze does not use nested SAs. A single ESP tunnel SA per peer is the deployment model.

## Peer Authorization Database (Section 4.4.3)

The PAD links IKE peer identity to SPD entries:

| PAD component | Purpose |
|---------------|---------|
| Entry IDs and matching rules (4.4.3.1) | Map peer identity (DN, FQDN, IP) to PAD entry |
| IKE peer authentication data (4.4.3.2) | Credentials: certificates, PSK, EAP |
| Child SA authorization data (4.4.3.3) | Which traffic selectors this peer may negotiate |

Ze's native IKEv2 engine holds the PAD. One `remote-id` leaf per peer is the entry ID, `remote-id-type` pins the one ID type the peer can assert, and `ca-certificate` plus `certificate` carry the authentication data. `remoteIDMatches` (`internal/component/ike/engine/remote_id.go`) is the matching rule and `certificateCarriesIdentity` is the binding against the credential.

### Entry ID Matching (Section 4.4.3.1)

An entry names one peer or a sub-tree of peers. A sub-tree is written with the hierarchy separator in front, and it admits the identities BELOW it and never its own text.

| Entry form | Example | Admits |
|------------|---------|--------|
| Exact domain name | `vpn.example.com` | that name alone |
| Domain sub-tree | `.example.com` | `vpn.example.com`, `gw.branch.example.com` |
| Exact mail address | `gateway@example.com` | that address alone |
| Mail sub-tree | `@example.com` | `gateway@example.com` |
| Exact distinguished name | `CN=hq,O=Example` | that DN alone |
| DN sub-tree | `,ST=MA,C=US` | every DN whose top RDNs are `ST=MA,C=US` |
| Address | `10.0.0.1` | that address alone |
| Address range | `10.0.0.0/24`, `2001:db8::/32` | every address in the prefix |
| Key ID | `branch-42` | exact match only (§4.4.3.1 requires no other) |

RFC 4514 renders the most significant RDN last, so a DN sub-tree is a suffix of every member and the leading comma is what makes the comparison land on an RDN boundary. The address range syntax is the `zt:ip-prefix` the SPD traffic-selector leaves use, which is what "the same address range syntax used for SPD entries" binds Ze to.

The certificate binding stays per peer whichever form the entry takes: a peer admitted by a sub-tree must still assert an identity its own certificate carries.

## Fragment Handling (Section 7)

| Rule | Detail |
|------|--------|
| Transport mode: no fragments | AH/ESP MUST NOT be applied in transport mode to IPv4 fragments. Use tunnel mode. |
| Tunnel mode: fragments OK | Tunnel mode may encapsulate fragments. The inner packet may be a fragment. |
| PMTU | Encapsulator SHOULD perform Path MTU Discovery and adjust tunnel MTU. |
| BYPASS/DISCARD fragments | Plaintext fragments on protected side are discarded if policy requires port matching beyond ANY/OPAQUE. |
