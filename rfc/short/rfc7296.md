# RFC 7296 - Internet Key Exchange Protocol Version 2 (IKEv2)

## Meta

| Field | Value |
|-------|-------|
| RFC | 7296 |
| Title | Internet Key Exchange Protocol Version 2 (IKEv2) |
| Status | Standards Track (Internet Standard, STD 79) |
| Date | October 2014 |
| Authors | C. Kaufman, P. Hoffman, Y. Nir, P. Eronen, T. Kivinen |
| Obsoletes | RFC 5996 |
| Updated by | RFC 7427, RFC 7670, RFC 8247, RFC 8784 |

**Purpose:** Defines the protocol for mutual authentication between two IPsec peers and the establishment of IKE Security Associations (SAs) containing shared keying material used to set up Child SAs for ESP and AH. IKEv2 replaces IKEv1 (RFC 2409) with a simpler, more robust design: four messages to establish the first Child SA, a single CREATE_CHILD_SA exchange for rekeying, and built-in NAT traversal and dead peer detection.

**Ze context:** Ze implements IKEv2 natively in Go at `internal/component/ike/`, as both **initiator and responder** (`connection-type initiate`/`respond`). The engine handles IKE negotiation, authentication (X.509, PSK, EAP — as EAP peer when initiating and as EAP authenticator/server when responding), IKE-SA and Child-SA rekey in both directions, and XFRM SA/policy installation via netlink (or VPP API). Message direction (SK keys, key-derivation nonce order, AUTH octets, ESP key roles) is selected by the SA's role. This summary is the primary reference for the wire format, state machine, key derivation, and exchange semantics.

## Exchange Overview (Sections 1.2, 1.3, 1.4)

### Initial Exchanges (4 messages, 2 request/response pairs)

```
Initiator                          Responder
-----------                        -----------
HDR, SAi1, KEi, Ni        -->                     IKE_SA_INIT (exchange 34)
                           <--  HDR, SAr1, KEr, Nr, [CERTREQ]

HDR, SK {IDi, [CERT,]
  [CERTREQ,] [IDr,]
  AUTH, SAi2, TSi, TSr}    -->                     IKE_AUTH (exchange 35)
                           <--  HDR, SK {IDr, [CERT,]
                                  AUTH, SAr2, TSi, TSr}
```

| Exchange | Type | Purpose |
|----------|------|---------|
| IKE_SA_INIT | 34 | Negotiate IKE crypto, exchange nonces and DH, detect NAT |
| IKE_AUTH | 35 | Authenticate peers, establish first Child SA with traffic selectors |

After these four messages: one IKE SA (for control) and one Child SA (for data) exist.

### CREATE_CHILD_SA Exchange (Section 1.3)

Used after the initial exchanges for three purposes:

| Purpose | Payloads | Section |
|---------|----------|---------|
| New Child SA | SA, Ni, [KEi], TSi, TSr | 1.3.1 |
| Rekey Child SA | N(REKEY_SA), SA, Ni, [KEi], TSi, TSr | 1.3.2 |
| Rekey IKE SA | SA, Ni, KEi (KE mandatory) | 1.3.3 |

```
Initiator                          Responder
-----------                        -----------
HDR, SK {[N,] SA, Ni,
  [KEi,] [TSi, TSr]}      -->                     CREATE_CHILD_SA (exchange 36)
                           <--  HDR, SK {SA, Nr,
                                  [KEr,] [TSi, TSr]}
```

### INFORMATIONAL Exchange (Section 1.4)

```
Initiator                          Responder
-----------                        -----------
HDR, SK {[N,] [D,]
  [CP,] ...}               -->                    INFORMATIONAL (exchange 37)
                           <--  HDR, SK {[N,] [D,]
                                  [CP,] ...}
```

| Use | Payloads | Notes |
|-----|----------|-------|
| Dead Peer Detection (DPD) | Empty (no payloads inside SK) | Liveness check; response confirms peer is alive |
| Delete Child SA | D (Delete, protocol ESP/AH, SPI) | Peer deletes matching SA and responds with its own Delete |
| Delete IKE SA | D (Delete, protocol IKE) | Both sides tear down the IKE SA and all Child SAs |
| Error notification | N (Notify) | Reports errors outside of other exchanges |

## Authentication Methods (Section 3.8)

| ID | Method | Notes |
|----|--------|-------|
| 1 | RSA Digital Signature | X.509 certificate with RSA key |
| 2 | Shared Key (PSK) | Pre-shared key, MAC-based proof |
| 3 | DSS Digital Signature | X.509 certificate with DSA key |
| 9 | ECDSA with SHA-256 on P-256 | RFC 4754 |
| 10 | ECDSA with SHA-384 on P-384 | RFC 4754 |
| 11 | ECDSA with SHA-512 on P-521 | RFC 4754 |
| 13 | NULL Authentication | RFC 7619 |
| 14 | Digital Signature | RFC 7427 generic, replaces method 1/3/9/10/11 |

The AUTH payload proves the sender knows the private key (certificates) or shared secret (PSK) corresponding to its identity. For PSK, AUTH is a MAC over the first-exchange messages using a key derived from the shared secret and negotiated PRF. For certificates, AUTH is a digital signature over the same data.

## Proposal and Transform Negotiation (Sections 2.7, 3.3)

The SA payload contains a list of proposals. Each proposal specifies one protocol and a set of transforms. The responder picks exactly one proposal or rejects all with NO_PROPOSAL_CHOSEN.

### SA Payload Structure

```
SA Payload
  +-- Proposal 1 (Protocol: IKE/ESP/AH, SPI)
  |     +-- Transform (Type: ENCR, ID: AES_CBC, Attr: keylen=256)
  |     +-- Transform (Type: ENCR, ID: AES_GCM_16, Attr: keylen=256)
  |     +-- Transform (Type: PRF, ID: HMAC_SHA2_256)
  |     +-- Transform (Type: INTEG, ID: HMAC_SHA2_256_128)
  |     +-- Transform (Type: DH, ID: 14)
  +-- Proposal 2 ...
```

### Protocol IDs

| ID | Protocol |
|----|----------|
| 1 | IKE |
| 2 | AH |
| 3 | ESP |

### Transform Types

| Type | Name | Used by |
|------|------|---------|
| 1 | ENCR (Encryption) | IKE, ESP |
| 2 | PRF (Pseudorandom Function) | IKE only |
| 3 | INTEG (Integrity) | IKE, ESP, AH |
| 4 | DH (Diffie-Hellman Group) | IKE, ESP (optional PFS), AH (optional PFS) |
| 5 | ESN (Extended Sequence Numbers) | ESP, AH |

### Required Transforms by Protocol

| Protocol | Required | Optional |
|----------|----------|----------|
| IKE | ENCR, PRF, INTEG, DH | - |
| ESP | ENCR | INTEG (not with AEAD), ESN, DH (PFS) |
| AH | INTEG | ESN, DH (PFS) |

Note: AEAD ciphers (GCM, CCM, CHACHA20_POLY1305) provide both encryption and integrity. When proposing AEAD for ESP, INTEG must be NONE (0). A proposal mixing AEAD encryption with a separate integrity algorithm is invalid. This requires separate proposals for AEAD and non-AEAD suites.

## Traffic Selectors (Sections 2.9, 3.13)

Traffic Selectors define which IP traffic a Child SA protects. The initiator proposes TSi (initiator traffic) and TSr (responder traffic); the responder may narrow them but never widen.

### TS Types

| Type | Name | Address size |
|------|------|-------------|
| 7 | TS_IPV4_ADDR_RANGE | 4 bytes |
| 8 | TS_IPV6_ADDR_RANGE | 16 bytes |

### TS Selector Fields

| Field | Size | Description |
|-------|------|-------------|
| TS Type | 1 byte | 7 (IPv4) or 8 (IPv6) |
| IP Protocol | 1 byte | 0 = any, 6 = TCP, 17 = UDP, etc. |
| Selector Length | 2 bytes | Total length of this TS item |
| Start Port | 2 bytes | 0 = any |
| End Port | 2 bytes | 65535 = any upper bound |
| Start Address | 4 or 16 bytes | Lower bound of IP range |
| End Address | 4 or 16 bytes | Upper bound of IP range |

### TS to XFRM Policy Mapping

| IKEv2 TS concept | Linux XFRM equivalent |
|-------------------|----------------------|
| TSi (initiator traffic) | src selector in XFRM policy |
| TSr (responder traffic) | dst selector in XFRM policy |
| IP Protocol field | proto in XFRM selector |
| Port range | sport/dport in XFRM selector |
| Address range | saddr/daddr + prefix length in XFRM selector |
| Child SA direction | XFRM_POLICY_OUT (initiator sends), XFRM_POLICY_IN (initiator receives) |

Narrowing: the responder can select a subset of the proposed address ranges, port ranges, or protocols. strongSwan communicates the final narrowed selectors back, and Ze validates they fall within the configured policy.

## NAT Traversal (Section 2.23)

### Detection

Both peers include two Notify payloads in IKE_SA_INIT:

| Notify | ID | Content |
|--------|----|---------|
| NAT_DETECTION_SOURCE_IP | 16388 | SHA-1(SPIi, SPIr, source IP, source port) |
| NAT_DETECTION_DESTINATION_IP | 16389 | SHA-1(SPIi, SPIr, dest IP, dest port) |

If the hash does not match, a NAT exists on that side. Detection is automatic and requires no configuration.

### UDP Encapsulation

| Condition | Port | Encapsulation |
|-----------|------|---------------|
| No NAT detected | 500 | None (raw IKE over UDP) |
| NAT detected | 4500 | IKE: 4 zero bytes prefix before IKE header |
| NAT detected | 4500 | ESP: UDP-encapsulated ESP (RFC 3948), Non-ESP marker absent |

When NAT is detected, both IKE and ESP traffic float to port 4500. IKE packets on port 4500 are prefixed with 4 zero bytes (Non-ESP marker) to distinguish them from UDP-encapsulated ESP packets (which start with a non-zero SPI).

### Keepalives

Peers behind NAT send keepalive packets (a single 0xFF byte over UDP) to maintain NAT mappings. The interval is implementation-defined; strongSwan defaults to 20 seconds.

## SA Lifetime and Rekeying (Section 2.8)

| Aspect | Rule |
|--------|------|
| Negotiation | Lifetimes are NOT negotiated in IKEv2. Each peer enforces its own policy independently |
| Soft lifetime | Implementation-defined threshold before hard lifetime; triggers rekeying |
| Hard lifetime | SA expires; traffic must use a new SA |
| Rekey method | CREATE_CHILD_SA creates replacement SA, then old SA is deleted via INFORMATIONAL |
| IKE SA rekey | New IKE SA inherits all Child SAs from old IKE SA |
| Jitter | Implementations should add random jitter to rekey time to avoid synchronized rekeying storms |
| Simultaneous rekey | Both peers may initiate rekey at the same time; tie-breaking uses lowest nonce (Section 2.8.1) |

strongSwan configuration exposes `ikelifetime` (IKE SA), `lifetime` (Child SA), `margintime` (soft lifetime offset), and `rekeyfuzz` (jitter percentage). Ze validates these values and passes them to strongSwan.

## Dead Peer Detection (Section 2.4)

DPD in IKEv2 uses empty INFORMATIONAL exchanges, not a separate protocol:

| Aspect | Detail |
|--------|--------|
| Mechanism | Empty INFORMATIONAL request (no payloads inside SK{}) |
| Response | Peer replies with empty INFORMATIONAL response |
| Failure | No response after retransmissions means peer is dead; tear down IKE SA and Child SAs |
| Initiation | Only sent when there is traffic to protect and no recent proof of liveness |
| Not periodic | Unlike IKEv1 DPD (RFC 3706), IKEv2 does not mandate periodic keepalives; implementations decide when to check |

strongSwan exposes `dpddelay` (how long to wait before checking) and `dpdtimeout` (when to declare peer dead). Ze validates these in config.

### State Synchronization and re-initiation (Section 2.4)

Two normative requirements govern how a responder that already holds an established SA reacts to a peer that re-initiates (after a crash/reboot, or after an operator clear on the far side):

- **Unauthenticated messages MUST NOT trigger teardown.** "An endpoint MUST NOT conclude that the other endpoint has failed based on any routing information (e.g., ICMP messages) or IKE messages that arrive without cryptographic protection (e.g., Notify messages complaining about unknown IKE SPIs)." A fresh `IKE_SA_INIT` (new initiator SPI, zero responder SPI) is unauthenticated, so the responder MUST accept it in PARALLEL and MUST NOT delete the established SA on its arrival. Superseding the old SA is legal only once the new SA is authenticated (IKE_AUTH). Deleting on the bare init would be an unauthenticated remote-teardown primitive.
- **INITIAL_CONTACT is the authenticated supersede signal.** "The INITIAL_CONTACT notification asserts that this IKE SA is the only IKE SA currently active between the authenticated identities. It MAY be sent when an IKE SA is established after a crash, and the recipient MAY use this information to delete any other IKE SAs it has to the same authenticated identity without waiting for a timeout." Placement is fixed: "The INITIAL_CONTACT notification, if sent, MUST be in the first IKE_AUTH request or response, not as a separate exchange afterwards."

Ze enforcement: the responder accepts a re-initiation in parallel (`tryResponderSAInit`, never touching the established SA) and supersedes only on the authenticated IKE_AUTH (`finishResponderEstablish`); the initiator emits INITIAL_CONTACT on every first IKE_AUTH request (one-SA-per-configured-peer model, so the assertion is always truthful). An operator `clear` additionally sends an authenticated INFORMATIONAL Delete (Section 1.4) so the peer tears down at once instead of waiting for the DPD timeout.

## Key Behavior

| Section | Requirement |
|---------|-------------|
| 1.2 | Initial exchange is exactly 4 messages (2 round trips). First pair (IKE_SA_INIT) is unencrypted. Second pair (IKE_AUTH) is encrypted under the IKE SA keys derived from the first pair. |
| 2.1 | IKE uses UDP. Messages that are too large for the path MTU should use IKEv2 fragmentation (RFC 7383). Minimum reassembly size is 1280 bytes; implementations should handle up to 3000 bytes. |
| 2.4 | Liveness checks are demand-driven, not periodic. Only check when there is traffic to send and no recent inbound traffic proves the peer is alive. |
| 2.6 | IKE SA is identified by the pair (SPIi, SPIr), each 8 bytes, chosen by each peer. The SPI pair is carried in every IKE header. |
| 2.7 | The responder picks exactly one transform of each type from the proposal. If no acceptable combination exists, it responds with NO_PROPOSAL_CHOSEN. |
| 2.8 | Lifetimes are local policy; not negotiated. Each peer rekeys independently. Simultaneous rekey collisions are resolved by comparing nonces (lower nonce wins). |
| 2.9 | Responder may narrow traffic selectors but never widen. If the narrowed result is empty, respond with TS_UNACCEPTABLE. |
| 2.23 | NAT detection is automatic via hash comparison in IKE_SA_INIT. When NAT is present, all traffic (IKE + ESP) floats to UDP 4500. |
| 3.3 | AEAD ciphers (GCM, CCM, CHACHA20_POLY1305) and non-AEAD ciphers cannot be in the same proposal. Use separate proposals for each class. |
| 3.8 | RFC 7427 Digital Signature (method 14) is the modern replacement for methods 1, 3, 9-11. It allows algorithm agility via the SIGNATURE_HASH_ALGORITHMS notify. |
