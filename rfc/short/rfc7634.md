**Purpose:** Defines the ChaCha20-Poly1305 AEAD (RFC 7539) for ESP and for the IKEv2 Encrypted payload, with Transform ID 28.

**Ze context:** `chacha20poly1305` sits in ze's ESP-only encryption registry; the IKE SA cannot negotiate it.

## ESP Usage (Section 2)

| Item | Value |
|------|-------|
| Key | 256 bits |
| KEYMAT per key | 36 octets: 32 key, 4 salt |
| IV | 64 bits, explicit in each packet, unique per SA |
| Nonce | 32-bit salt followed by the 64-bit IV |
| Tag (ICV) | 16 octets, all included in the packet |
| AAD | SPI and sequence number (ESN: SPI, high 32 bits, low 32 bits) |

## Compliance Checklist

- [ ] [RFC7634-2-1] [MUST] The IV MUST be unique for each invocation for a particular security association (SA) but does not need to be unpredictable. (§2) {lower-layer: Linux XFRM rfc7539esp(chacha20,poly1305) and its IV generator; internal/component/ike/dataplane/xfrm_linux.go::xfrmStateFromParams installs only the key and salt, and the kernel chooses every IV}
- [ ] [RFC7634-4-1] [MUST NOT] As with other AEAD algorithms, INTEG (type 3) transform substructures MUST NOT be specified, or just one INTEG transform MAY be included with value NONE (0). (§4)
- [ ] [RFC7634-2-2] [RECOMMENDED] The use of a counter or a linear feedback shift register (LFSR) is RECOMMENDED. (§2)
- [ ] [RFC7634-3-1] [SHOULD] The sender SHOULD include no padding and set the Pad Length field to zero. (§3)
- [ ] [RFC7634-5-1] [MAY] Thus, implementations that keep keys and other secret material within some security boundary MAY export the Salt from the security boundary. (§5)

## Pitfalls

- The salt is never transmitted; both peers take it from the last four octets of the KEYMAT slice.
- An AEAD proposal that also lists a real INTEG transform is malformed (Section 4).
