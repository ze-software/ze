**This document is obsolete.** RFC 9846, "The Transport Layer Security (TLS)
Protocol Version 1.3" (July 2026), obsoletes RFC 5077, RFC 5246, RFC 6961,
RFC 7627, RFC 8422 and RFC 8446. RFC 9846 Appendix D renames the extension to
"Extended Main Secret" and the code point to `extended_main_secret`, and states
that "The label parameter to the PRF function in Section 4 of [RFC7627] is left
unchanged for compatibility". RFC 9846 Appendix E adds one recommendation of its
own: "implementations which support both TLS 1.3 and earlier versions SHOULD
indicate the use of the Extended Main Secret extension in their APIs whenever TLS
1.3 is used". Read RFC 9846 for the current obligations. This summary records
what RFC 7627 itself states, because TLS 1.2 stacks and their configuration
surfaces name the extension by this number.

## Purpose

The TLS master secret defined in RFC 5246 is derived from the pre-master secret
and the two hello randoms only. It is not bound to the rest of the handshake, so
two different sessions can end up with the same master secret. This document
defines a TLS extension that recomputes the master secret over a hash of the
handshake log, which makes the master secret unique per session (Section 1,
Section 4).

## Scope

The document defines one TLS extension, one alternative master secret
derivation, and the negotiation rules for both. It defines no new message, no
new cipher suite and no new alert. It applies to TLS and, by Section 5.1, to
DTLS (RFC 6347). It cannot apply to SSL 3.0, which carries no extension
mechanism (Section 6.4).

## Requirements Notation (Section 2)

The document uses the RFC 2119 key words with their RFC 2119 meanings. It states
no case rule of its own, and every normative keyword in the body is capitalised.

## Terms

| Term | Definition |
|------|------------|
| `session_hash` | `Hash(handshake_messages)`, over every handshake message from ClientHello up to and including ClientKeyExchange, type and length fields included (Section 3) |
| `handshake_messages` | The concatenation of the exchanged Handshake structures of RFC 5246 Section 7.4 |
| extended master secret | The master secret computed by the Section 4 formula |
| legacy master secret | The master secret computed by the RFC 5246 formula |
| abort the handshake | Terminate the handshake by sending a fatal `handshake_failure` alert (Section 5.2) |
| full handshake | A handshake that creates a new session |
| abbreviated handshake | A handshake that resumes an existing session; it computes no new master secret |

## Wire Format

### extended_master_secret extension

Extension type: 23 (0x0017), registered by IANA in the "ExtensionType Values"
registry of RFC 5246 (Section 5.1, Section 7).

The `extension_data` field is empty, so the extension carries no payload and has
one encoding only.

| Offset | Size | Value | Field |
|--------|------|-------|-------|
| 0-1 | 2 | 0x0017 | `extension_type` |
| 2-3 | 2 | 0x0000 | `extension_data` length |

Total length: 4 octets. The RFC gives the whole encoding as the four hexadecimal
octets `00 17 00 00` (Section 5.1). Network byte order applies.

The extension appears in ClientHello and in ServerHello. Its presence in both is
what selects the Section 4 derivation.

## Algorithms

### Session hash (Section 3)

```
session_hash = Hash(handshake_messages)
```

`handshake_messages` runs from the ClientHello up to and including the
ClientKeyExchange message, and includes the type and length fields of each
handshake message.

| TLS version | Hash function |
|-------------|---------------|
| TLS 1.2 | The hash defined in RFC 5246 Section 7.4.9 for the Finished message computation |
| All earlier versions | The concatenation of MD5 and SHA1 |

A resumed handshake has no `session_hash`, because it creates no new session
(Section 3).

### Extended master secret (Section 4)

```
master_secret = PRF(pre_master_secret, "extended master secret",
                    session_hash)
                    [0..47];
```

Two changes from RFC 5246:

- The label is `"extended master secret"` instead of `"master secret"`.
- The input is `session_hash` instead of `ClientHello.random + ServerHello.random`.

The output length is unchanged at 48 octets. All other cryptographic
computations are unchanged (Section 5.1).

The session hash covers the hello randoms, the cipher suite, the key exchange
messages and the certificates of both ends, so the extended master secret
depends on all of them (Section 4).

## Negotiation: Full Handshake (Section 5.2)

| Client offers extension | Server includes extension | Outcome |
|-------------------------|---------------------------|---------|
| yes | yes | The new session uses the extended master secret computation |
| yes | no | The client SHOULD abort. If it continues, the new session uses the legacy computation and Section 5.4 applies |
| no | no | The server SHOULD abort if it does not wish to interoperate with legacy clients. If it continues, it MUST NOT include the extension, and Section 5.4 applies |
| no | yes | Not permitted: a server MUST NOT include the extension when the ClientHello did not carry it |

A client implementing this document sends the extension in every ClientHello,
including the ClientHello of an abbreviated handshake (Section 5.2,
Section 5.3).

## Negotiation: Abbreviated Handshake (Section 5.3)

The client sends the extension in every ClientHello that offers resumption. The
two ends then compare the offered extension against the flag stored with the
original session.

Server behavior on a ClientHello that offers to resume a known session:

| Original session used the extension | New ClientHello carries it | Server action |
|-------------------------------------|----------------------------|---------------|
| no | yes | MUST NOT perform the abbreviated handshake; SHOULD continue with a full handshake to negotiate a new session |
| yes | no | MUST abort the abbreviated handshake |
| no | no | SHOULD abort the handshake. If it continues for legacy resumption, Section 5.4 applies |
| yes | yes | Continue. The server MUST include the extension in its ServerHello |

Client behavior on a ServerHello that accepts an abbreviated handshake:

| Original session used the extension | New ServerHello carries it | Client action |
|-------------------------------------|----------------------------|---------------|
| no | yes | MUST abort the handshake |
| yes | no | MUST abort the handshake |
| yes | yes | Continue |

When the abbreviated handshake continues, both ends derive the connection keys
for the new session from the master secret of the original session, as usual
(Section 5.3).

## Session State

A peer that accepts legacy full handshakes has to tell the two kinds of session
apart, so it adds a flag to the session state that records whether the session
uses the extended or the legacy master secret (Section 5.4). Every rule in the
abbreviated-handshake tables above reads that flag.

## Interoperability Considerations (Section 5.4)

Two degraded cases exist, and each disables a different set of features.

| Case | What is unsafe | Required response |
|------|----------------|-------------------|
| A full handshake continued without the extension | The new master secret can be synchronized across two sessions | MUST NOT export key material based on the new master secret for any subsequent application-level authentication. In particular MUST disable RFC 5705 exporters and any EAP method relying on compound authentication |
| An abbreviated handshake continued to resume a session that does not use the extended master secret | The handshake log, and with it `verify_data`, can be synchronized | MUST NOT use the current handshake's `verify_data` for application-level authentication. In particular the client MUST disable renegotiation and any use of the `tls-unique` channel binding of RFC 5929 |

A third case is stated twice in the same paragraph and the two statements pull
in opposite directions. Where the original session uses an extended master
secret but the ClientHello or ServerHello of the abbreviated handshake omits the
extension, the paragraph opens with "it MAY be safe to continue the abbreviated
handshake since it is protected by the extended master secret of the original
session", and closes with "this document recommends that the client and server
MUST abort such handshakes". The document gives its own reason for the closing
sentence: such a state is unusual and is likely to come from a transient or
inadvertent misconfiguration. The two sentences are recorded below as two
requirements, at the levels the text gives them.

## Validation

| Check | Valid | Invalid action |
|-------|-------|----------------|
| ServerHello carries the extension while the ClientHello did not | never | The server side is prohibited from producing this; the specification states no client-side detection for a full handshake |
| Abbreviated handshake, original session without the extension, ServerHello with it | never | Client aborts the handshake |
| Abbreviated handshake, original session with the extension, ServerHello without it | never | Client aborts the handshake |
| Abbreviated handshake, original session with the extension, ClientHello without it | never | Server aborts the abbreviated handshake |
| Abbreviated handshake, original session without the extension, ClientHello with it | never as an abbreviated handshake | Server does not resume; it continues with a full handshake |
| `extension_data` length | 0 | The document defines no other length and states no error handling for one |

## MUST Requirements

### Tx

- A client sends the `extended_master_secret` extension in every ClientHello, in a full handshake and in an abbreviated one (Section 5.2, Section 5.3).
- A server that receives the extension includes it in its ServerHello (Section 5.2).
- A server that continues a full handshake after a ClientHello without the extension does not include the extension in its ServerHello (Section 5.2).
- A server that continues an abbreviated handshake whose ClientHello carries the extension includes the extension in its ServerHello (Section 5.3).

### Key derivation

- When both hellos carry the extension and a full handshake takes place, both ends use the Section 4 derivation (Section 5.1).
- When a full handshake continues without the extension, both ends use the RFC 5246 derivation (Section 5.2).
- When SSL 3.0 is supported and used, the resulting session uses the legacy derivation (Section 6.4).

### Errors

- A server aborts the abbreviated handshake when the original session used the extension and the new ClientHello does not carry it (Section 5.3).
- A server does not perform the abbreviated handshake when the original session did not use the extension and the new ClientHello carries it (Section 5.3).
- A client aborts the handshake when the extension state of the original session and of the new ServerHello disagree, in either direction (Section 5.3).
- Both ends abort an abbreviated handshake where the original session uses the extended master secret and a hello omits the extension (Section 5.4).

### Downgrade containment

- After a full handshake without the extension: no key material derived from the new master secret is exported for application-level authentication, and RFC 5705 exporters and compound-authentication EAP methods are disabled (Section 5.4).
- After an abbreviated handshake resuming a session without the extended master secret: `verify_data` is not used for application-level authentication, and renegotiation and the `tls-unique` channel binding are disabled (Section 5.4).

## SHOULD / MAY

- [SHOULD NOT] Accept a handshake that does not use the extended master secret, especially when relying on compound authentication (Section 4). Consequence: the session falls into one of the Section 6.1 vulnerable cases.
- [SHOULD] Abort a full handshake when the peer omits the extension and interoperation with legacy peers is not wanted (Section 5.2). Consequence of continuing: Section 5.4 restrictions apply for the life of the session.
- [SHOULD NOT] Offer an abbreviated handshake to resume a session that does not use an extended master secret; offer a full handshake instead (Section 5.3). Consequence: renegotiation on that connection is not secure even when RFC 5746 is in use.
- [SHOULD] Continue with a full handshake instead of resuming when the original session lacks the extension and the new ClientHello carries it (Section 5.3).
- [SHOULD] Abort when neither the original session nor the new ClientHello uses the extension (Section 5.3).
- [NOT RECOMMENDED] MD5 or SHA1 as the session hash function (Section 6.2). Reason: the session hashes of two sessions have to be distinct, so the hash has to be collision resistant.
- [SHOULD] Refuse SSL 3.0 handshakes (Section 6.4).
- [MAY] Continue an abbreviated handshake where the original session uses an extended master secret and a hello omits the extension (Section 5.4). See the note above: the same paragraph also states a MUST to abort.

## Pitfalls

- **The triple handshake attack** (Section 1, Section 6.1). An attacker who can make two sessions share a pre-master secret makes them share a master secret, and everything that relies on master secret uniqueness then fails: resumption authenticates the wrong peer, RFC 5705 exporters no longer bind to one session, and the synchronized `verify_data` defeats RFC 5746 renegotiation indication and the RFC 5929 `tls-unique` channel binding.
- **Vulnerable key exchanges** (Section 1, Section 6.1). RSA and DHE make pre-master secret synchronization easy. ECDHE is vulnerable when arbitrary explicit curves are allowed or when curves with small subgroups are used. SRP and PSK are vulnerable against a stronger adversary.
- **An attacker can force the key exchange.** Offering only RSA or only DHE in the hello messages makes both ends use it, whatever they would have preferred (Section 1).
- **Session tickets are outside the session hash** (Section 6.3). The hash stops at the ClientKeyExchange, so an RFC 5077 NewSessionTicket sent afterwards is not covered, and a man in the middle can make a client store a ticket that was not meant for the current session. No attack on this vector is known, and the RFC asks for careful analysis of applications that put extra state in tickets.
- **CertificateVerify is outside the session hash too** (Section 6.3). This is deliberate: for existing cipher suites CertificateVerify adds no session content, and ending the hash at ClientKeyExchange lets the pre-master secret be erased from memory as early as possible. A future cipher suite or extension that adds meaningful messages between ClientKeyExchange and Finished would fall outside the guarantee.
- **The mitigation is only as good as the hash** (Section 6.2). The session hash function follows the TLS version, so a TLS 1.2 session uses SHA256 or better, while an earlier version uses MD5 concatenated with SHA1.

## Compatibility

- With a peer that does not implement the extension, the handshake completes with the legacy master secret computation whenever both ends choose to continue. Section 5.4 then governs the whole session.
- A server that supports the extension can still resume a session it created before it did, because the extension state is a per-session flag rather than a per-peer property (Section 5.4).
- Resumption at a different server that lacks the extension is called out as a real deployment case and is nevertheless to be aborted, because it is more likely to be a misconfiguration than a topology (Section 5.4).
- SSL 3.0 cannot carry the extension, so the mechanism is unavailable there (Section 6.4). SSL 3.0 is deprecated by RFC 7568.
- The extension applies unchanged to DTLS (Section 5.1).
