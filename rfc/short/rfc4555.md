# RFC 4555 - IKEv2 Mobility and Multihoming Protocol (MOBIKE)

## Meta

| Field | Value |
|-------|-------|
| RFC | 4555 |
| Title | IKEv2 Mobility and Multihoming Protocol (MOBIKE) |
| Status | Standards Track |
| Date | June 2006 |
| Authors | P. Eronen (editor) |
| Depends on | RFC 4306 (IKEv2, now RFC 7296) |

**Purpose:** Extends IKEv2 to allow the IP addresses associated with IKE SAs and tunnel-mode IPsec SAs to change after establishment. A mobile VPN client can move between networks (Ethernet to Wi-Fi to cellular) without tearing down and re-establishing SAs. A multihomed host can fail over to a different interface when the current one breaks. Only tunnel mode is supported; transport mode is out of scope.

**Ze context:** Ze does not implement MOBIKE. The IKE engine at `internal/component/ike/` does not define the MOBIKE notify types and does not handle UPDATE_SA_ADDRESSES. As a CPE headend, Ze would need at minimum the responder role: announce MOBIKE_SUPPORTED, accept UPDATE_SA_ADDRESSES from mobile initiators, update XFRM SA endpoints via netlink, and optionally perform return routability checks.

## Protocol Overview (Section 2)

### Roles

The IKE SA **initiator** (typically the mobile client) decides which address pair to use and sends UPDATE_SA_ADDRESSES to request the change. The **responder** (typically the VPN gateway) does not update IPsec SAs without an explicit UPDATE_SA_ADDRESSES from the initiator, except when its own source address becomes unavailable.

### Constraints

- Only one address pair is active per SA at any time (no load balancing).
- At least one endpoint should have a relatively stable, discoverable address.
- Responses are always sent to the address/port the request came from.
- If NATs are present, the initiator is assumed to be behind the NAT.

## Capability Negotiation (Sections 3.1-3.2)

Both peers signal MOBIKE support by including `N(MOBIKE_SUPPORTED)` in the IKE_AUTH exchange (the message containing the SA payload). Both peers MUST include it to enable MOBIKE for that IKE SA.

Implementations supporting both MOBIKE and NAT Traversal MUST switch to port 4500 during IKE_AUTH even if no NAT is detected. This avoids a port change later if a NAT appears on a new path.

## Additional Addresses (Sections 3.4, 3.6)

Both peers MAY advertise extra addresses in IKE_AUTH and later in INFORMATIONAL requests:

```
Initiator                          Responder
-----------                        -----------
HDR, SK { [N(ADDITIONAL_*_ADDRESS)+],
          [N(NO_ADDITIONAL_ADDRESSES)],
          [N(NO_NATS_ALLOWED)],
          [N(COOKIE2)] }  -->

                          <--  HDR, SK { [N(COOKIE2)] }
```

- Each update replaces the entire previous address set (no incremental add/delete).
- The initiator uses the responder's address set for path selection and failover.
- The responder stores the initiator's addresses but only uses them when its own address changes and the current path stops working.

## Changing Addresses (Section 3.5)

When the initiator decides to change addresses (due to link-down, retransmission failure, or address set update from the responder):

### Initiator procedure

1. Update the IKE SA with new addresses, set `pending_update` flag.
2. Update IPsec SAs with new addresses (unless policy requires return routability check first).
3. Enable NAT Traversal (UDP encapsulation) if a NAT is suspected on the new path.
4. Send INFORMATIONAL with UPDATE_SA_ADDRESSES from the new address:

```
Initiator                          Responder
-----------                        -----------
HDR, SK { N(UPDATE_SA_ADDRESSES),
          [N(NAT_DETECTION_SOURCE_IP),
           N(NAT_DETECTION_DESTINATION_IP)],
          [N(NO_NATS_ALLOWED)],
          [N(COOKIE2)] }  -->

                          <--  HDR, SK { [N(NAT_DETECTION_SOURCE_IP),
                                    N(NAT_DETECTION_DESTINATION_IP)],
                                    [N(COOKIE2)] }
```

5. If a newer address change occurs while waiting for the response, restart from step 1 and ignore the pending response.

### Responder procedure (on receiving UPDATE_SA_ADDRESSES)

1. Check ordering (if window size > 1, discard if a newer request was already processed).
2. Process NO_NATS_ALLOWED if present.
3. Verify the (source IP, destination IP) pair is acceptable per local policy; if not, reply with `N(UNACCEPTABLE_ADDRESSES)`.
4. Update the IKE SA addresses from the IP header.
5. Reply with INFORMATIONAL response (with NAT detection and COOKIE2 if requested).
6. Optionally perform return routability check.
7. Update IPsec SA addresses (tunnel header outer addresses and XFRM state).
8. Enable or disable NAT Traversal based on NAT detection results.

### Initiator on receiving the response

- If UNACCEPTABLE_ADDRESSES: select different addresses, retry, or disconnect.
- If UNEXPECTED_NAT_DETECTED: process per Section 3.9.
- Update IPsec SAs if not done before sending the request.
- Enable or disable NAT Traversal based on NAT detection results.

## Return Routability Check (Section 3.7)

Verifies the peer can actually receive packets at its claimed address. SHOULD be performed by default; MAY be omitted in trusted environments.

Uses the COOKIE2 notification: the exchange initiator includes 8-64 bytes of unpredictable data in any INFORMATIONAL request. The exchange responder MUST copy it verbatim into the response. The original sender verifies the value matches; mismatch closes the IKE SA.

The check can run before updating IPsec SAs (default, safer), immediately after, or continuously.

**Exception:** if the same request was retransmitted to multiple addresses (destination changed mid-flight), the response does not prove which address works. A fresh INFORMATIONAL is needed.

## NAT Mapping Changes (Section 3.8)

When MOBIKE and NAT Traversal are both enabled, NAT_DETECTION_SOURCE_IP and NAT_DETECTION_DESTINATION_IP MAY be included in any INFORMATIONAL request (the responder MUST echo them if present).

The initiator behind a NAT SHOULD include these in DPD messages and compare the received NAT_DETECTION_DESTINATION_IP with the value from the previous UPDATE_SA_ADDRESSES response. If they differ, the NAT mapping changed and UPDATE_SA_ADDRESSES should be sent.

**MOBIKE override:** when MOBIKE is active, the host not behind a NAT MUST NOT use dynamic IKEv2 address updates (Section 2.23 of RFC 7296) for IKE packets, but MAY use them for ESP packets. This prevents a path-test INFORMATIONAL from accidentally changing the IKE SA addresses.

## NAT Prohibition (Section 3.9)

When NAT Traversal is NOT enabled, address-updating messages MUST include NO_NATS_ALLOWED containing the actual source/destination IP and ports. The responder verifies these match the IP header. Mismatch triggers an UNEXPECTED_NAT_DETECTED response.

Intended for IPv6 and site-to-site VPN where NATs should never exist. The initiator SHOULD retry several times on UNEXPECTED_NAT_DETECTED (a single attacker-modified packet should not permanently block a path).

## Path Testing (Section 3.10)

The initiator can probe whether alternative paths work using normal INFORMATIONAL request/response exchanges sent to different address pairs. This can run even when the current path is working, to detect when a better path becomes available.

## Failure Recovery (Section 3.11)

The initiator is responsible for detecting and recovering from failures. The responder SHOULD use long timeout intervals (at least 5 minutes for retransmission) to give the initiator time to detect problems and switch paths.

## Dead Peer Detection (Section 3.12)

Same as base IKEv2, but MOBIKE nodes SHOULD verify that incoming IPsec packets use the expected addresses. Packets from stale addresses SHOULD NOT count as evidence that the peer is alive and synchronized.

## Notify Message Types (Sections 4, 6)

### Error Types

| ID | Name | Data | Description |
|----|------|------|-------------|
| 40 | UNACCEPTABLE_ADDRESSES | none | Responder rejected the address change |
| 41 | UNEXPECTED_NAT_DETECTED | none | NO_NATS_ALLOWED check failed (IP header differs from notification) |

### Status Types

| ID | Name | Data | Description |
|----|------|------|-------------|
| 16396 | MOBIKE_SUPPORTED | empty (zero-length) | Peer supports MOBIKE; included in IKE_AUTH |
| 16397 | ADDITIONAL_IP4_ADDRESS | 4-octet IPv4 address | Additional initiator/responder address |
| 16398 | ADDITIONAL_IP6_ADDRESS | 16-octet IPv6 address | Additional initiator/responder address |
| 16399 | NO_ADDITIONAL_ADDRESSES | none | Sender has only the address in the IP header |
| 16400 | UPDATE_SA_ADDRESSES | none | Request to update IKE SA and IPsec SA addresses |
| 16401 | COOKIE2 | 8-64 octets (unpredictable) | Return routability token; responder MUST echo verbatim |
| 16402 | NO_NATS_ALLOWED | see below | NAT prohibition: sender's view of source/dest IP and ports |

All notify types use Protocol ID = 0 and SPI Size = 0.

## Example: Mobile Client Address Change

```
Initiator (mobile)                 Responder (gateway)
-------------------                -------------------
1) (IP_I1:500 -> IP_R1:500)
   HDR, SAi1, KEi, Ni,
        N(NAT_DETECTION_SOURCE_IP),
        N(NAT_DETECTION_DESTINATION_IP)  -->

                                   <--  HDR, SAr1, KEr, Nr,
                                             N(NAT_DETECTION_SOURCE_IP),
                                             N(NAT_DETECTION_DESTINATION_IP)

2) (IP_I1:4500 -> IP_R1:4500)
   HDR, SK { IDi, CERT, AUTH,
             CP(CFG_REQUEST),
             SAi2, TSi, TSr,
             N(MOBIKE_SUPPORTED) }  -->

                                   <--  HDR, SK { IDr, CERT, AUTH,
                                                  CP(CFG_REPLY),
                                                  SAr2, TSi, TSr,
                                                  N(MOBIKE_SUPPORTED) }

   (Initiator moves to new network, gets new IP address IP_I2)

3) (IP_I2:4500 -> IP_R1:4500)
   HDR, SK { N(UPDATE_SA_ADDRESSES),
             N(NAT_DETECTION_SOURCE_IP),
             N(NAT_DETECTION_DESTINATION_IP) }  -->

                                   <--  HDR, SK { N(NAT_DETECTION_SOURCE_IP),
                                                  N(NAT_DETECTION_DESTINATION_IP) }

   (Responder performs return routability check)

4)                                 <--  HDR, SK { N(COOKIE2) }

   HDR, SK { N(COOKIE2) }  -->
```

## Example: Multihomed Responder Failover

```
Initiator                          Responder (2 addresses)
-----------                        -----------
1-2) Normal IKE_SA_INIT + IKE_AUTH with N(MOBIKE_SUPPORTED)
     Responder sends N(ADDITIONAL_IP4_ADDRESS) with IP_R2

     (Initiator suspects path to IP_R1 is broken, probes liveness)

3) (IP_I1:4500 -> IP_R1:4500)
   HDR, SK { N(NAT_DETECTION_*) }  -->   (no response after retries)

   (Initiator tries the other responder address)

4) (IP_I1:4500 -> IP_R2:4500)
   HDR, SK { N(NAT_DETECTION_*) }  -->

                                   <--  HDR, SK { N(NAT_DETECTION_*) }

   (Path to IP_R2 works; initiator requests address switch)

5) (IP_I1:4500 -> IP_R2:4500)
   HDR, SK { N(UPDATE_SA_ADDRESSES),
             N(NAT_DETECTION_*),
             N(COOKIE2) }  -->

                                   <--  HDR, SK { N(NAT_DETECTION_*),
                                                  N(COOKIE2) }
```

## Security Considerations (Section 5)

| Threat | Mitigation |
|--------|------------|
| Traffic redirection by on-path attacker modifying IP headers | MOBIKE payloads are encrypted + integrity-protected inside SK. NO_NATS_ALLOWED detects header modification when NAT-T is off. On-path attacker can only cause DoS, not decrypt traffic. |
| Third-party DoS via traffic redirection | Return routability check (COOKIE2) limits duration. INVALID_SPI from victim triggers liveness check. Ingress filtering at attacker's network largely prevents this. |
| Spoofed link-layer or network indications | MOBIKE does not protect lower layers. Use SEND, link-layer security, ICMP validation. Final path decision uses authenticated IKEv2 messages. |
| Address and topology disclosure | ADDITIONAL_*_ADDRESS notifications are encrypted. Peers may omit addresses they do not want to use. Responder with a single fixed address need not process initiator's additional addresses. |
| Stale IPsec SAs after address change | PAD authorization for traffic selectors must account for address mobility. Closing SAs for abandoned addresses may be needed. |

## Implementation Considerations (Appendix A)

- SPD cache links to SAD entries should NOT use (remote IP, remote SPI) as the key, because the IP changes with MOBIKE and two hosts behind the same NAT can choose the same SPI. Use the IKE SA identity or an internal SA index instead.
- When creating outbound SAs, identify the right peer by authenticated identity rather than current IP address, since the address may have changed.
