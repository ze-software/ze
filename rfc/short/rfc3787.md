**Purpose:** Discuss a number of differences between the IS-IS protocol
used to route IP traffic as described in RFC 1195 and the protocol as it
is deployed today, as a service to those implementing, testing, and
deploying IS-IS to route IP traffic (Abstract). A companion document
(RFC 3719) describes the differences between the protocol described in
ISO 10589 and current practice.

**Scope:** The document describes interoperability recommendations and
clarifications. It does not change the underlying protocol described in
ISO 10589 and RFC 1195 (Section 11).

## Unused features (Section 3)

- Inter-Domain Routing Protocol Information TLV, code 131: not used, and
  MUST be ignored if received (Section 3.1).
- Authentication TLV, code 133: replaced by TLV 10 ("IS-IS Cryptographic
  Authentication"); TLV 133 is not used and MUST be ignored (Section
  3.2, Section 11).

## Overload (OL) Bit (Section 4)

- ISO 10589 defines an LSP Database Overload condition (section 7.3.19).
  When an IS is in Database Overload condition it sets the Overload Bit
  in the non-pseudonode LSP number Zero that it generates.
- ISO 10589 section 7.2.8.1 instructs other systems not to use the
  overloaded IS as a transit router, because the overloaded IS does not
  have complete information and routing loops could develop. An
  overloaded router may still be used to reach End Systems directly
  attached to it.
- The meaning of the flag has been overloaded: when a router running BGP
  and IS-IS reboots, BGP may take more time to converge than IS-IS, so
  it is convenient to set the Overload Bit until BGP has converged (see
  RFC 3277, Transient Blackhole Avoidance).
- An implementation SHOULD use the Overload Bit to signal that it is not
  ready to accept transit traffic.
- An implementation SHOULD not set the Overload bit in PseudoNode LSPs it
  generates, and Overload bits seen in PseudoNode LSPs SHOULD be ignored.
- RFC 1195 (section C.1.4) makes clear that directly connected IP
  subnetworks are reachable when an IS is overloaded. When processing
  LSPs from a router that has the Overload bit set in LSP number Zero,
  the receiving router SHOULD treat all IP reachability advertisements as
  directly connected and use them in its SPF computation.
- Since the IP prefixes an overloaded router announces will be treated as
  directly attached, an overloaded router SHOULD take care in selecting
  which routes to advertise in the LSPs it generates.

## Narrow vs Wide Metrics (Section 5)

- The IS-Neighbors TLV (TLV 2, ISO 10589) and the IP Reachability TLV
  (TLV 128 / TLV 130, RFC 1195) provide a 6-bit metric for the default
  link metric to the listed neighbor. This metric has proved too limited.
- The Extended IS-Neighbors TLV (TLV 22) and the Extended IP Reachability
  TLV (TLV 135), defined in "IS-IS extensions for Traffic Engineering"
  (RFC 3784), provide wider metrics: TLV 22 defines a 24-bit metric, and
  TLV 135 defines a 32-bit metric for IP Networks and Hosts.
- If not all devices in the IS-IS domain support wide metrics, narrow
  metrics MUST continue to be used. Once all devices can support the new
  wide-metric TLVs, the network can migrate, with care to avoid routing
  loops.

### Up/down bit handling during metric comparison (Section 5)

- RFC 1195 section 3.10.2 item 2c states that IP prefixes in "IP External
  Reachability" with internal-metric and IP prefixes in "IP Internal
  Reachability" with internal-metric have the same preference.
- As defined in "Domain-wide Prefix Distribution with Two-Level IS-IS"
  (RFC 2966), the Most Significant Bit on an L1 metric tells whether the
  route has been leaked down, but does not change the distance; thus the
  MSBit is ignored when comparing metrics.
- The default metric is interpreted as a 7-bit quantity. Metrics with the
  external bit set are interpreted as metrics in the range [64..127];
  metrics with the external bit clear are interpreted as metrics in the
  range [0..63] (Section 5).

### Transition algorithm (Section 5.1)

Steps must be taken in this order:

1. All routers advertise Narrow Metrics (ISO 10589) and consider narrow
   metrics only in SPF.
2. Each system is configured in turn to send wide metrics as well as
   narrow metrics. The two metrics for the same link or IP prefix SHOULD
   agree.
3. When all systems advertise wide metrics, make the changes needed on
   each system to consider Wide Metrics during SPF, and change
   MaxPathMetric to 0xFE000000.
4. Each system is configured in turn to stop advertising narrow metrics.
5. When the network is using only wide metrics, metrics on individual
   links may be rescaled to take advantage of the larger metric.

### Dealing with non-equal metrics (Section 5.2)

- When both Narrow and Wide metric styles are considered, the SPF
  algorithm resolves multiple descriptions of the same link by selecting
  the minimum metric for each link. This may give a path with some links
  chosen due to a wide metric and some due to a narrow metric.
- MaxPathMetric and MaxLinkMetric SHOULD retain the values defined in
  Table 2 of section 8 of ISO 10589.
- In the SPF algorithm (ISO 10589 C.2.5 Step 0 sections b and i, and
  C.2.6 Step 1 section a), if multiple styles of metric for the link or
  neighbor are defined, the cost is the minimum available cost for the
  circuit.

## Intermediate System Hello (ISH) PDU (Section 6)

- RFC 1195 section 5.1 requires all routers implementing IS-IS (IP-only,
  OSI-only, or dual) with point-to-point interfaces to be able to
  transmit ISO 9542 ISHs on those links. In an IP-only environment the
  original need for the ISH PDU is not present.
- A multi-protocol IS supporting attachment of CLNS ESs over
  point-to-point circuits must act in accordance with ISO 10589 section
  8.2.2 when CLNS functionality is enabled.
- An IP-only implementation SHOULD issue an ISH PDU as described in ISO
  10589 section 8.2.3, to interoperate with implementations that require
  an ISH to initiate adjacency formation.
- An IP-only implementation may issue an IIH PDU when a point-to-point
  circuit transitions to "Up" to initiate adjacency formation without
  sending an ISH PDU, but this may not interoperate with implementations
  requiring an ISH.
- An IS may issue an IIH PDU in response to receipt of an IIH PDU (ISO
  10589 section 8.2.5.2) even if it has not received an ISH PDU.

## Attached Bit (Section 7)

ISO 10589 section 7.2.9.2 describes an algorithm for determining when the
attachedFlag should be set on an IS. Some implementations also allow the
attachedFlag to be set on ISs routing IP traffic when there is a default
route in the local routing table, or when some other state implies a
connection to the rest of the network.

## Default Route (Section 8)

RFC 1195 section 1.3 states that default routes are permitted only at
level 2 as external routes (in the "IP External Reachability Information"
field) and are not permitted at level 1. Because of the utility of the
default route and the ability to influence the exit point from an area,
an implementation MAY generate default routes in Level 1.

## Non-homogeneous Protocol Networks (Section 9)

- RFC 1195 assumes every deployment supports a homogeneous protocol set
  (OSI-only, IP-only, or dual). The behavior of mixed networks that do
  not follow its guidelines is not well defined.
- RFC 1195 requires the Protocol Supported TLV (code 129) in IIH and ISH
  PDUs and in LSP number Zero. IP-capable routers MUST generate a
  Protocol Supported TLV and MUST include the IP protocol as a supported
  protocol. A router that does not include the Protocols Supported TLV
  may be assumed to be a pure OSI router.
- ITU-T requires that SONET/SDH equipment running IS-IS must not form an
  adjacency with a neighbour unless they share at least one network-layer
  protocol in common. Implementors MAY include this feature to ensure
  interoperability with SONET and SDH DCN networks.

## Adjacency Creation and IP Interface Addressing (Section 10)

- RFC 1195 states adjacencies are formed without regard to IP interface
  addressing, but many implementations refuse adjacencies based on
  interface addresses.
- RFC 1195 section 4.2 requires routers with IP interface addresses to
  advertise them in an IP Interface Address TLV (132) carried in IIH
  PDUs. Some implementations will not interoperate with a neighbor that
  omits the IP Interface Address TLV; some will not form an adjacency on
  broadcast interfaces with a peer not sharing an interface address in a
  common IP subnetwork.
- For an implementation to interoperate in a mixed environment, it MUST
  include an IP Interface address (TLV 132) in its IIH PDUs. The network
  administrator should ensure a common IP subnet is assigned to links
  with numbered interfaces, and that all routers on each link have IP
  Interface Addresses belonging to the assigned subnet.

## MUST / SHOULD / MAY Notes

- Section 3.1: TLV code 131 MUST be ignored if received.
- Section 3.2: TLV code 133 is not used and MUST be ignored.
- Section 4: An implementation SHOULD use the Overload Bit to signal it
  is not ready to accept transit traffic; SHOULD not set the OL bit in
  PseudoNode LSPs and SHOULD ignore it there; on receiving an OL-set
  LSP number Zero, SHOULD treat all IP reachability as directly connected.
- Section 5: If not all devices support wide metrics, narrow metrics
  MUST continue to be used.
- Section 8: An implementation MAY generate default routes in Level 1.
- Section 9: IP-capable routers MUST generate a Protocol Supported TLV
  (code 129) and MUST include IP as a supported protocol.
- Section 10: To interoperate in a mixed environment, an implementation
  MUST include an IP Interface address (TLV 132) in its IIH PDUs.
