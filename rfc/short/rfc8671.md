# RFC 8671 -- Support for Adj-RIB-Out in BGP Monitoring Protocol (BMP)

## Purpose

Extends BMP (RFC 7854) to support monitoring of Adj-RIB-Out (routes
advertised to peers) in addition to the original Adj-RIB-In (routes
received from peers). Enables collectors to see both directions of
a BGP session.

### Bouncing a Changed Session

Section 7.2 binds a configuration change that alters the behavior of an existing
BMP session. The collector must not keep state that the new configuration makes
wrong. Ze answers with the Peer Down and Peer Up pair the section names: the BMP
session stays up, and every established BGP peer reported on it gets a Peer Down
followed by a Peer Up, so the collector re-learns each peer under the new
configuration without losing the session. The Peer Down reason is 5, "Information
for this peer will no longer be sent to the monitoring station for configuration
reasons" (RFC 7854 Section 4.9), which is the one defined reason that reports a
local configuration decision and does not claim the peer went down.

Ze acts on a change and not on a delivery. The plugin is handed the whole `bgp`
root, so it is told about every neighbor and policy the operator edits. It
compares the parsed sender configuration against the one in force and bounces the
peers only when a leaf that decides what a session carries has moved:
`route-monitoring-policy`, `route-mirroring`, `loc-rib` or `statistics-timeout`.
A change to the collector set is a different act: a collector that is removed, or
that now points at another address, has its session ENDED with a Termination,
because that session does not continue and Section 7.2 does not govern it. A
collector the change did not touch keeps its session and everything learned on
it.

The reload reaches the sender over the plugin config-apply callback, which the
bmp plugin registers beside the startup configure callback. Both end in
`applySenderConfig`. The startup callback is served once for each plugin
process, so a plugin that registered only that callback would never re-apply a
sender configuration and would never bounce a peer.

### Reserved Per-Peer Header Flag Bits

Section 4 reserves bits 3 to 0 of the Flags field for future use. A sender
transmits them as 0. A receiver ignores their values, so a header that carries
them set decodes with the same meaning as one that does not.

### Post-policy Fidelity

Section 5.1 binds the post-policy Adj-RIB-Out feed to what the router puts on
the wire. Ze wraps the transmitted BGP UPDATE body byte for byte and does not
re-encode it, so an attribute Ze does not recognise reaches the collector
unchanged.

### Admin Label

Section 6.3.1 defines Peer Up Information TLV type 4, Admin Label: a free-form
UTF-8 string with no null terminator. A Peer Up message can carry more than one.
A receiver keeps them in the order the wire gives.

## Changes to RFC 7854

### O Flag (Per-Peer Header, bit 4)

| Value | Meaning |
|-------|---------|
| 0 | Adj-RIB-In (received routes, original BMP behavior) |
| 1 | Adj-RIB-Out (sent routes, post-policy) |

When O=1, the L flag (bit 6, post-policy) is also set because
Adj-RIB-Out represents routes after export policy.

### Affected Message Types

- **Route Monitoring (type 0)**: carries Adj-RIB-Out UPDATEs when O=1
- **Peer Up (type 3)**: same OPENs for both Adj-RIB-In and Adj-RIB-Out
- **Peer Down (type 2)**: signals loss of Adj-RIB-Out monitoring
- **Statistics Report (type 1)**: not specific to either RIB, so the O flag is zero

### Peer Up Behavior

A single BGP session may produce two Peer Up messages: one for
Adj-RIB-In (O=0) and one for Adj-RIB-Out (O=1). Both carry the
same sent and received OPEN messages.

## Key Constraints

- O flag uses bit 4 of the Flags field (bits numbered 7 to 0)
- Pre-policy Adj-RIB-Out (L=0, O=1) is valid but uncommon
- Peer Down for Adj-RIB-Out does not imply BGP session loss

## Ze Implementation

- O flag constant: `PeerFlagO` in `internal/component/bgp/plugins/bmp/header.go`
- Sender sets O=1 and L=1 for `direction=sent` events, on Route Monitoring and on
  Route Mirroring alike: both build their header with `peerHeaderFromEvent`
- `senderSession.writeStatisticsReport` clears the O flag, so a Statistics Report
  for an Adj-RIB-Out peer still carries zero
- Receiver decodes O flag in all per-peer header messages, and keeps Peer Up
  Information TLVs, Admin Label among them, in wire order
- Ze exports no pre-policy Adj-RIB-Out: `peerHeaderFromEvent` sets the O flag and
  the L flag together, so no message carries O=1 with L=0
