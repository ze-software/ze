# RFC 5301 - Dynamic Hostname Exchange Mechanism for IS-IS

## Meta

| Field | Value |
|-------|-------|
| RFC | 5301 |
| Title | Dynamic Hostname Exchange Mechanism for IS-IS |
| Status | Standards Track |
| Date | October 2008 |
| Obsoletes | RFC 2763 |
| Updates | - |
| Authors | D. McPherson (Arbor Networks), N. Shen (Cisco Systems) |

**Purpose:** Define a dynamic mechanism for routers running IS-IS to
learn symbolic hostnames. The document defines a TLV that lets IS-IS
routers flood their name-to-systemID mapping information across the
IS-IS network (Abstract). It obsoletes RFC 2763 and moves the
capability to the Standards Track.

**Scope:** IS-IS uses a variable 1-8 byte system ID (normally 6 bytes)
to represent a node (Section 1). Hexadecimal representations of system
IDs and LSP identifiers are less clear than symbolic names when looking
at diagnostics information. Rather than static mapping tables or DNS
lookups, this document uses the transport mechanism of the routing
protocol itself to advertise symbolic names in IS-IS link-state PDUs
(Section 2).

## Background (Section 1, Section 2)

A name-to-systemID mapping can be used bidirectionally: to find symbolic
names for system IDs and to find system IDs for symbolic names (Section
1). Three ways to build such a table are discussed (Section 2):

- Static configuration: every router must maintain a statically
  configured table with mappings between router names and system IDs,
  for every router in the network. The drawback is scalability and
  maintainability; changing the name or system ID of one router, or
  adding a new router, affects the configurations of all other routers.
- DNS lookups: a drawback is that during network problems DNS response
  time may not be satisfactory or DNS may be unavailable; some DNS
  implementations might not support A and PTR records for CLNS NSAPs.
- Advertising symbolic names in IS-IS link-state PDUs (the solution
  defined here), which has proven easier and more manageable in
  wide-scale deployment than static mapping or DNS schemes.

## Wire Format

### Dynamic Hostname TLV (Section 3)

The Dynamic Hostname TLV is defined as TLV type 137.

| Field | Size | Meaning |
|-------|------|---------|
| Type | 1 octet | 137 |
| Length | 1 octet | Total length of the value field |
| Value | 1 to 255 bytes | A string identifying the symbolic name of the router originating the LSP |

- The Length is the total length of the value field (Section 3).
- The Value is a string of 1 to 255 bytes (Section 3).

## Carriage and Semantics (Section 3)

- The Dynamic Hostname TLV is optional.
- This TLV may be present in any fragment of a non-pseudonode LSP.
- The value field identifies the symbolic name of the router
  originating the LSP. This symbolic name can be the FQDN for the
  router, a subset of the FQDN, or any string operators want to use for
  the router. The use of FQDN or a subset of it is strongly recommended.
- The content of this value is a domain name (see RFC 2181). The string
  is not null-terminated.
- The system ID of this router can be derived from the LSP identifier.
- If this TLV is present in a pseudonode LSP, then it SHOULD NOT be
  interpreted as the DNS hostname of the router.

## Character Encoding (Section 3)

- The Value field is encoded in 7-bit ASCII.
- If a user-interface for configuring or displaying this field permits
  Unicode characters, that user-interface is responsible for applying
  the ToASCII and/or ToUnicode algorithm as described in RFC 3490 to
  achieve the correct format for transmission or display.

## Implementation (Section 4)

- The Dynamic Hostname TLV is optional. When originating an LSP, a
  router may decide to include this TLV in its LSP.
- Upon receipt of an LSP with the Dynamic Hostname TLV, a router may
  decide to ignore this TLV, or to install the symbolic name and system
  ID in its hostname mapping table for the IS-IS network.
- A router may also optionally insert this TLV in its pseudonode LSP for
  the association of a symbolic name to a local LAN.
- If a system receives a mapping for a name or system ID that is
  different from the mapping in the local cache, an implementation
  SHOULD replace the existing mapping with the latest information.

## Security Considerations (Section 5)

Since the name-to-systemID mapping relies on information provided by the
routers themselves, a misconfigured or compromised router can inject
false mapping information. This information needs to be treated with
suspicion when, for example, doing diagnostics about a suspected
security incident. The document raises no other new security issues for
IS-IS.

## IANA Considerations (Section 7)

This document specifies TLV 137, "Dynamic Name". This TLV had already
been allocated and reserved by RFC 2763, so no new actions are required
on the part of IANA.

## Normative reading of the wire format

RFC 5301 carries an RFC 2119 boilerplate (Section 1.1) but uses a capitalised
keyword only twice, both advisory: `SHOULD NOT` at Section 3 (pseudonode LSP) and
`SHOULD` at Section 4 (cache replacement). There is **no capitalised MUST, MUST NOT,
SHALL or REQUIRED anywhere in the document.**

Its wire format is nevertheless stated in indicative declaratives -- the TLV type,
the meaning of Length, the 1-to-255-byte Value, the 7-bit ASCII encoding, and the
absence of a NUL terminator. Those are format constraints, not choices: an
implementation that emits type 138, a 0- or 256-byte value, 8-bit octets, or a
NUL-terminated string does not interoperate and is not implementing this TLV. They
are therefore extracted at MUST level below. Previously they sat behind bare
`[FORMAT]` bracket tags, which the parser classifies as an implementation-task line
rather than a compliance requirement -- so they were invisible to the gate.

Nothing in this file promotes a *recommendation* to a MUST: the FQDN preference
(`RFC5301-3-1`), the pseudonode reading (`RFC5301-3-3`) and the cache replacement
(`RFC5301-4-1`) all keep the advisory level the RFC gives them.

## Reading of the conditional IDNA sentence (Section 3)

`RFC5301-3-10` is the only obligation in this document whose text carries an
antecedent. Section 3 says:

> If a user-interface for configuring or displaying this field permits Unicode
> characters, that user-interface is responsible for applying the ToASCII and/or
> ToUnicode algorithm as described in [RFC3490] to achieve the correct format for
> transmission or display.

Two readings are available, and they differ on what a user-interface that REFUSES
Unicode owes.

| Reading | Statement | Consequence |
|---------|-----------|-------------|
| A | The antecedent is "permits Unicode characters". An interface that refuses Unicode never enters the conditional, so no ToASCII conversion is owed. The refusal itself satisfies the sentence | An implementation may bound its configuration surface to 7-bit ASCII and owe no IDNA code |
| B | The sentence assigns the interface responsibility for producing the correct transmission format. Refusing pushes the conversion onto the operator | An implementation owes ToASCII so an operator can configure a Unicode name |

Reading A is the reading this checklist is graded against. The two readings agree
on the wire: under either one, the octets that leave the implementation are 7-bit
ASCII, which is what `RFC5301-3-7` already requires. They differ only on whether a
Unicode name must be accepted and converted, or refused.

Neither reading lowers the obligation. Reading A is discharged by the refusal
being observable, not by the requirement being annotated away.
