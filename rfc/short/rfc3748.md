# RFC 3748 - Extensible Authentication Protocol (EAP)

## Meta

| Field | Value |
|-------|-------|
| RFC | 3748 |
| Title | Extensible Authentication Protocol (EAP) |
| Status | Standards Track |
| Date | June 2004 |
| Authors | B. Aboba, L. Blunk, J. Vollbrecht, J. Carlson, H. Levkowetz (Ed.) |
| Obsoletes | RFC 2284 |
| Updated by | RFC 5247, RFC 7057 |

**Purpose:** Defines a flexible authentication framework that supports multiple authentication mechanisms (methods) over various link layers. EAP provides a standard exchange of authentication credentials between a peer and an authenticator, with method negotiation via type codes. It does not select a specific mechanism at the link layer; instead, authentication is deferred to a type-specific exchange.

**Ze context:** Ze implements EAP as part of its native IKEv2 engine for authenticating road warrior clients. EAP runs inside IKE_AUTH exchanges (RFC 7296 Section 2.16): the responder authenticates first with a certificate, then the initiator authenticates via EAP. Ze supports EAP-TLS (Type 13, RFC 5216) and EAP-MSCHAPv2 (Type 26) for Windows client compatibility.

## EAP Packet Format (Section 4)

| Field | Size | Description |
|-------|------|-------------|
| Code | 1 octet | Packet type: 1=Request, 2=Response, 3=Success, 4=Failure |
| Identifier | 1 octet | Matches Responses to Requests; unchanged on retransmission |
| Length | 2 octets | Total packet length including Code, Identifier, Length, and Data |
| Type | 1 octet | Authentication method (present only in Request/Response, Codes 1-2) |
| Type-Data | Variable | Method-specific data (present only in Request/Response) |

Success (Code 3) and Failure (Code 4) packets contain only Code, Identifier, and Length (4 octets total, no Type field).

Minimum Length: 4 octets. Packets shorter than Length are silently discarded. Octets beyond Length are ignored.

## Code Values (Section 4)

| Code | Name | Direction | Contains Type |
|------|------|-----------|---------------|
| 1 | Request | Authenticator to Peer | Yes |
| 2 | Response | Peer to Authenticator | Yes |
| 3 | Success | Authenticator to Peer | No |
| 4 | Failure | Authenticator to Peer | No |

## EAP Exchange Model (Sections 1.3, 2, 2.1)

### Roles

| Role | Description |
|------|-------------|
| Peer | End system being authenticated (supplicant). Sends Responses. |
| Authenticator | System requesting authentication. Sends Requests, Success, Failure. |
| EAP Server | Back-end entity terminating the EAP method. May be co-located with the authenticator or accessed via AAA (RADIUS). |

### Exchange Flow

```
Peer                              Authenticator
----                              -------------
                           <--    Request/Identity
Response/Identity          -->
                           <--    Request/Method
Response/Method            -->
                           ...    (method-specific exchanges)
                           <--    Success or Failure
```

### Key Rules

| Rule | Section | Detail |
|------|---------|--------|
| Lock-step | 2 | One outstanding Request at a time. Authenticator must receive a valid Response before sending a new Request. |
| Retransmission | 4.1 | Authenticator only. Peer never retransmits on timer; it re-sends its last Response if a duplicate Request arrives. |
| One method | 2.1 | Only one authentication method (Type >= 4) per conversation. After the method completes, authenticator sends Success or Failure. |
| Success/Failure | 4.2 | Not retransmitted, not acknowledged. Peer must handle loss (e.g., treat lower-layer success as implicit EAP Success). |
| NAK rejects | 2.1 | Peer sends NAK (Type 3) to reject a proposed method and suggest alternatives. Not permitted after first non-NAK Response. |

### Pass-Through Model (Section 2.3)

The authenticator may act as a pass-through, forwarding EAP packets between the peer and a back-end EAP server via AAA (RADIUS/Diameter). The authenticator examines only Code, Identifier, and Length for routing. It must forward packets of any Type without interpreting method-specific data.

## Method Types (Sections 5, 6.2)

### Initial Types (defined in RFC 3748)

| Type | Name | Section | Notes |
|------|------|---------|-------|
| 1 | Identity | 5.1 | Query/declare peer identity. Sent in cleartext. |
| 2 | Notification | 5.2 | Display message to user. Advisory only. |
| 3 | NAK (Legacy) | 5.3 | Response only. Rejects proposed type, lists alternatives. |
| 4 | MD5-Challenge | 5.4 | CHAP-like challenge-response. No mutual auth, no key derivation. |
| 5 | OTP | 5.5 | One-Time Password (RFC 2289). |
| 6 | GTC | 5.6 | Generic Token Card. |
| 254 | Expanded Types | 5.7 | Vendor-specific or extended IETF namespace. |
| 255 | Experimental | 5.8 | Local testing only. |

### Types Relevant to Ze

| Type | Name | Defined in | Notes |
|------|------|------------|-------|
| 13 | EAP-TLS | RFC 5216 | Certificate-based mutual authentication. Derives MSK/EMSK. |
| 26 | EAP-MSCHAPv2 | RFC 2759 + vendor | Password-based. Microsoft extension, widely deployed for Windows VPN clients. |

### Expanded Type Format (Section 5.7)

When Type = 254, the packet carries additional fields for a larger namespace:

| Field | Size | Description |
|-------|------|-------------|
| Type | 1 octet | Set to 254 |
| Vendor-Id | 3 octets | 0 = IETF, other = SMI Network Management Private Enterprise Code |
| Vendor-Type | 4 octets | Method within vendor namespace |
| Vendor-Data | Variable | Method-specific |

## EAP over IKEv2 (RFC 7296 Section 2.16)

EAP within IKEv2 modifies the standard IKE_AUTH exchange:

```
Initiator                          Responder
-----------                        -----------
HDR, SK {IDi, [CERTREQ]}  -->                        IKE_AUTH request 1
                           <--  HDR, SK {IDr, [CERT],
                                  AUTH, EAP}          Responder authenticates with cert,
                                                      starts EAP
HDR, SK {EAP}              -->                        EAP Response
                           <--  HDR, SK {EAP}         EAP Request (method-specific)
                           ...                        (repeat as needed)
HDR, SK {EAP}              -->                        Final EAP Response
                           <--  HDR, SK {EAP(Success)} EAP Success
HDR, SK {AUTH}             -->                        Initiator AUTH (derived from EAP MSK)
                           <--  HDR, SK {AUTH, SAr2,
                                  TSi, TSr}           Responder final AUTH + Child SA
```

| Aspect | Detail |
|--------|--------|
| Responder authenticates first | Certificate-based AUTH before EAP begins |
| Initiator defers AUTH | No AUTH payload in first IKE_AUTH request; AUTH sent after EAP Success |
| AUTH from EAP keys | Initiator's AUTH payload uses key material derived from EAP MSK |
| EAP method must derive keys | Methods that do not generate MSK (e.g., MD5-Challenge) cannot be used with IKEv2 |
| One method per IKE_AUTH | Consistent with EAP's one-method-per-conversation rule |

## Key Derivation (Section 7.10)

| Key | Minimum size | Purpose | Visibility |
|-----|-------------|---------|------------|
| MSK (Master Session Key) | 64 octets | Exported to authenticator for link/SA protection | Shared with authenticator |
| EMSK (Extended MSK) | 64 octets | Reserved for future use, method-specific extensions | Not shared with authenticator |

For IKEv2, the MSK is used to derive the AUTH payload that completes initiator authentication after EAP Success.

Methods that do not derive keys (Identity, Notification, MD5-Challenge, OTP, GTC) are unsuitable for IKEv2.

## Lower Layer Transport (Section 3)

| Lower Layer | Encapsulation | Section |
|-------------|---------------|---------|
| PPP | Protocol 0xC227 | 3.2 |
| IEEE 802.1X | EAPOL frames | 3.3 |
| IKEv2 | EAP payload inside SK{} | RFC 7296 2.16 |
| RADIUS | EAP-Message attribute | RFC 3579 |

### Lower Layer Requirements (Section 3.1)

| Requirement | Detail |
|-------------|--------|
| Unreliable transport | Acceptable; EAP handles retransmission |
| Ordering | Required; EAP depends on in-order delivery |
| Error detection | Required (CRC, checksum, MIC) |
| Minimum MTU | 1020 octets for EAP packets |
| Duplicate detection | Required to avoid method confusion |

## Security Considerations (Section 7)

### Threat Model (Section 7.1)

| Threat | Description |
|--------|-------------|
| Identity exposure | Identity (Type 1) is sent in cleartext; vulnerable to eavesdropping |
| Spoofing | Success/Failure packets are unauthenticated; lower layer or method must protect |
| Dictionary attacks | Methods using passwords without per-packet integrity are vulnerable |
| Man-in-the-middle | Sequential method negotiation is vulnerable; tunneled methods must include MITM protection |
| Downgrade | Attacker may force weaker method via NAK manipulation |
| Replay | Methods must include replay protection |

### Method Security Properties (Section 7.2)

| Property | Methods providing it |
|----------|---------------------|
| Mutual authentication | EAP-TLS; not MD5-Challenge, OTP, GTC |
| Key derivation (MSK/EMSK) | EAP-TLS, EAP-MSCHAPv2; not MD5-Challenge, OTP, GTC |
| Protected identity | EAP-TLS (inside TLS tunnel); not Identity type |
| Integrity protection | EAP-TLS; not base types |
| Replay protection | EAP-TLS (TLS nonces); not MD5-Challenge alone |
| Dictionary attack resistance | EAP-TLS (no password); EAP-MSCHAPv2 (limited) |

### Implementation Guidance for Ze

| Concern | Guidance |
|---------|----------|
| Method selection | Only use methods that derive MSK (required for IKEv2 AUTH) |
| Identity privacy | Use EAP-TLS or tunnel the identity inside the method; avoid sending real identity in initial Identity Response |
| Certificate validation | EAP-TLS requires full chain validation, CRL/OCSP checking |
| Fragmentation | EAP-TLS messages can exceed MTU; fragment at the EAP method layer (RFC 5216 Section 2.1.5) |
| Result indication | Peer should not grant access until both EAP Success and IKEv2 AUTH are verified |
