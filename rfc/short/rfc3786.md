# RFC 3786 - Extending the Number of IS-IS LSP Fragments Beyond the 256 Limit

## Meta

| Field | Value |
|-------|-------|
| RFC | 3786 |
| Title | Extending the Number of Intermediate System to Intermediate System (IS-IS) Link State PDU (LSP) Fragments Beyond the 256 Limit |
| Status | Informational |
| Date | May 2004 |
| Obsoletes | - |
| Updates | - |
| Authors | A. Hermelin (Montilio Inc.), S. Previdi (Cisco Systems), M. Shand (Cisco Systems) |

**Purpose:** Describe a mechanism that allows a system to originate more
than 256 Link State PDU (LSP) fragments, a limit set by the original
IS-IS routing protocol as described in ISO/IEC 10589. The mechanism can
be used in IP-only, OSI-only, and dual routers (Abstract).

**Scope:** In IS-IS a system floods its link-state information in LSP
Data Units. These logical LSPs can become large, so the protocol
fragments the information into multiple LSP fragments. ISO/IEC 10589
limits the number of fragments a system can generate to 256, where each
fragment's size is also limited; hence there is a limit on the amount of
link-state information a system can generate (Section 1).

## The 256-fragment model and drivers (Section 1)

Factors that can contribute to exceeding the limit (Section 1): new TLVs
and sub-TLVs in LSPs; use of LSPs to propagate various types of
information (such as traffic-engineering information); the increasing
number of destinations and AS topologies; finer-granularity routing and
injection of external routes into areas (RFC 2966); and other emerging
technologies (optical, IPv6, etc.).

## Terms (Section 1.2)

| Term | Meaning |
|------|---------|
| Originating System | A router physically running IS-IS; the single "physical" IS-IS process |
| Normal system-id | The system-id of an Originating System |
| Additional system-id | A system-id assigned by the network administrator; each one allows generation of 256 additional (extended) LSP fragments and must be unique throughout the routing domain |
| Virtual System | The system, identified by an Additional system-id, advertised as originating the extended LSP fragments; those fragments specify the Additional system-id in their LSP IDs |
| Original LSP | An LSP using the Normal system-id in its LSP ID |
| Extended LSP | An LSP using an Additional system-id in its LSP ID |
| LSP set | Logical LSP (resolves the ambiguity between a logical LSP and an LSP fragment) |
| Extended LSP set | A group of LSP fragments using an Additional system-id, originated by the Originating System |
| Extension-capable IS | An IS implementing the mechanisms in this document |

## The extension approach (Section 1.4)

Using Additional system-ids assigned by the administrator, the
Originating System advertises excess link-state information in extended
LSPs under these Additional system-ids, as if other routers ("Virtual
Systems") were advertising it. Each extended LSP set still has the
256-fragment limit, but the Originating System may generate extended
LSPs under numerous Virtual Systems (Section 1.4).

For both modes, each LSP set created by a node contains in its fragment-0
a new TLV (IS Alias ID TLV) that contains the Normal system-id and PN
Number of the Original LSP created by the router. Extension-capable ISs
use this information to store the original and extended LSPs as one
logical LSP (Section 1.4).

## Operation Modes (Section 1.3)

- Operation Mode 1: allows implementations that do not support this
  extension to correctly process the extended fragment information
  without modification. This mode restricts what may be advertised in
  extended LSP fragments: only leaf information may be advertised.
- Operation Mode 2: relaxes Mode 1 advertisement restrictions; any
  link-state information may be advertised in extended LSPs. It mandates
  a change to how LSPs are considered during the SPF algorithm, in a way
  not compatible with previous implementations.

Modes are configured on a per-level and area basis: all LSPs considered
in the same SPF instance MUST use the same Mode. An L1/L2 IS need not use
the same mode for its L1 and L2 instances. Routers should operate in
Mode 1 only if backwards compatibility is desired; otherwise Mode 2 is
recommended. Routers MAY implement Mode 2 without supporting Mode 1, and
will still interoperate correctly with routers that support both modes.

## Wire Format

### IS Alias ID TLV (IS-A), type 24 (Section 2)

| Field | Size | Meaning |
|-------|------|---------|
| CODE | 1 octet | 24 |
| LENGTH | 1 octet | Total length of the value field |
| Normal system-id | 6 octets | The Normal system-id of the LSP set |
| Pseudonode number | 1 octet | The Pseudonode number of the LSP set |
| Sub-TLVs length | 1 octet | Total length of all sub-TLVs |
| Sub-TLVs | 0-247 octets | A series of sub-TLV tuples |

Sub-TLV tuple format (Section 2):

| Field | Size | Meaning |
|-------|------|---------|
| Sub-type | 1 octet | Type of the sub-TLV |
| Length | 1 octet | Total length of the value field |
| Value | 0-245 octets | Type-specific payload |

- LSPs with the same Normal system-id and Pseudonode number are
  considered in SPF as one logical LSP (Section 2).
- Without sub-TLVs, the structure consumes 8 octets per LSP set. This TLV
  MUST be included in fragment 0 of every LSP set belonging to an
  Originating System running in either Mode 1 or Mode 2. Currently there
  are no sub-TLVs defined (Section 2).

## Fragment-0 validity and binding (Sections 3.1, 5)

- Under both modes, the Originating System MUST include information
  binding the Original LSP and the Extended ones. This binding is
  advertised via the IS Alias ID TLV in all fragment 0 of Original and
  Extended LSPs (Section 3.1).
- Extended LSP fragment zero should be regarded in the same special
  manner specified in ISO/IEC 10589 for LSPs with number zero, and
  should include the same type of extra information specified in ISO/IEC
  10589 and RFC 1195. An extended LSP fragment zero MUST be generated for
  every extended LSP set, to allow a router's SPF calculation to consider
  those fragments (Section 3.1).
- The restriction in ISO/IEC 10589 section 7.2.5 holds: if an LSP Number
  zero of the Originating System is not present, none of that system's
  neighbor entries are processed during SPF, hence none of its extended
  LSPs are processed either (Section 3.2).

## SPF handling (Section 5)

- When considering LSPs of an extension-capable IS (identified by the
  IS Alias ID TLV), the original and extended LSPs are combined into one
  large logical LSP.
- If LSP fragment 0 of the Original LSP set is missing or its
  RemainingLifetime is zero, all LSPs generated by that Originating
  System (Extended as well) MUST NOT be considered in the SPF. Original
  LSP fragments are identified when the is-alias-id value equals the
  system-id of those LSPs.
- If an LSP fragment 0 of an extended LSP set is missing or its
  RemainingLifetime is zero, only that LSP set MUST NOT be considered in
  the SPF.

## Bits on extended LSPs (Sections 3.1.1 to 3.1.4)

- Attached (ATT) bits: SHOULD be set to zero for all four metric types on
  all Extended LSPs. If a Virtual System is reachable, so is its
  Originating System; an L1 IS should choose the Originating System, not
  the Virtual System, as its nearest L2 exit point (Section 3.1.1).
- Partition Repair (P) bit: SHOULD be set to zero on all extended LSPs,
  for the same reasons as the Attached bits (Section 3.1.2).
- Overload bit: should be set consistently across all LSPs, original and
  extended, belonging to an Originating System, and should reflect the
  Originating System's overload state (Section 3.1.4).

## Operation Mode 1 additions (Section 3.2)

- Adjacencies from the Originating System to its Virtual Systems are
  advertised using the standard neighbor TLVs. The metric for these
  connections MUST be zero, since the cost of reaching a Virtual System
  is the same as the cost of reaching its Originating System.
- Only "leaf" information (information that serves only as leaves in a
  shortest path tree) can be advertised in extended LSPs under Mode 1.
- When an Extended LSP belonging to Additional system-id S' is first
  created, the Original LSP MUST specify S' as a neighbor with metric set
  to zero, and the Extended LSP MUST specify the Normal system-id as a
  neighbor with metric SHOULD set to MaxLinkMetric - 1 (any metric
  greater than zero is acceptable), to satisfy the two-way connectivity
  check on other routers. Where relevant this adjacency SHOULD be
  considered point-to-point (Section 3.2).
- An Extended LSP must specify only the Originating System as a neighbor;
  other neighbors MUST NOT be specified in an Extended LSP, because they
  would only specify the Originating System and not the Virtual System,
  and so would not satisfy the bi-directionality check in SPF
  (Section 3.2.1).
- If the Originating System is in the overload state, information in the
  extended LSPs will not be processed by other routers in their SPF
  computation, because in Mode 1 extended LSPs are reachable only through
  adjacencies from the Original LSP, and an OL-set Original LSP has its
  adjacencies excluded from SPF (Section 3.2.2).
- Routers configured in Mode 2 SHOULD NOT apply the Mode 1 additions
  (Section 3.2).

## Purging extended LSP fragments (Section 4)

- An extended LSP fragment zero should not be purged until all fragments
  in its set (belonging to a particular Additional system-id) are empty
  as well, to ensure implementations consider the fragments in their SPF
  computations (ISO/IEC 10589 section 7.2.5).
- In Mode 1, when all extended LSP fragments of a particular Additional
  system-id S' have been purged, the Originating System SHOULD remove the
  neighbor information to S' from its original LSPs.

## Forming adjacencies (Section 6)

An IS MUST use the system-id of the LSP that will include a neighbor when
forming an adjacency with that neighbor. If a neighbor is to be included
in extended LSP S', then S' should be used as the system-id in IS Hellos
and IS-IS Hellos when forming the adjacency, regardless of the
Operational Mode. In Mode 1 this means only the Normal system-id is used
when sending hellos.

## Interoperation (Section 7)

- Under Operation Mode 2, all ISs in an area must be extension-capable.
  It is possible to not upgrade every router if the extended information
  is not routing information but data useful only to a subset of routers.
- Incremental transition: upgrade routers one-by-one to run in Mode 1
  (non-capable routers interoperate correctly); when all routers are
  extension-capable, configure them one-by-one to run in Mode 2.
- Implementations SHOULD support a configuration parameter controlling
  the LSP origination behavior. The default value SHOULD correspond to
  the behavior described in ISO/IEC 10589, i.e., neither mode should be
  enabled without explicit configuration when the software is upgraded.

## MUST / SHOULD Notes

- Section 2: The IS Alias ID TLV (type 24) MUST be included in fragment 0
  of every LSP set running in either Mode 1 or Mode 2.
- Section 3.1: An extended LSP fragment zero MUST be generated for every
  extended LSP set.
- Section 5: If Original LSP fragment 0 is missing or RemainingLifetime
  is zero, all that system's LSPs (Extended too) MUST NOT be considered
  in SPF; if an extended set's fragment 0 is missing or expired, only
  that set MUST NOT be considered.
- Section 3.2: Mode 1 metric for Originating-to-Virtual adjacencies MUST
  be zero; other neighbors MUST NOT be specified in an Extended LSP.
- Sections 3.1.1, 3.1.2: ATT bits and the P bit SHOULD be set to zero on
  all extended LSPs.
