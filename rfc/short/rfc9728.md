**Purpose:** Defines a discovery document the resource server publishes at a well-known URL so OAuth 2.1 clients can learn which authorization servers issue tokens for that resource, what scopes are recognised, and how Bearer tokens must be presented. The MCP 2025-06-18 authorization profile makes this document a MUST for MCP resource servers.

## Well-Known Endpoint (Section 3.1)

| Item | Value |
|------|-------|
| Path | `/.well-known/oauth-protected-resource` inserted between the host and the path of the resource identifier (§3): `https://mcp.example/mcp` publishes at `/.well-known/oauth-protected-resource/mcp` |
| Method | GET (other methods answer 405) |
| Auth | Ze serves it without authentication; RFC 9728 states no obligation either way |
| Content-Type | `application/json` |

## Metadata Document (Section 2)

| Field | Requirement | Ze implementation |
|-------|-------------|-------------------|
| `resource` | MUST; canonical URL identifying this resource | Operator-configured via `environment.mcp.oauth.audience` (or `metadata-resource` override); NEVER derived from request Host |
| `authorization_servers` | OPTIONAL; JSON array of AS issuer URLs | Single entry built from `environment.mcp.oauth.authorization-server` |
| `scopes_supported` | MAY; JSON array of scope names | Mirrors `environment.mcp.oauth.required-scopes` |
| `bearer_methods_supported` | MAY; array of delivery methods | Always `["header"]` -- MCP only accepts `Authorization: Bearer` |
| `resource_documentation` | MAY; URL | Not emitted |
| `resource_signing_alg_values_supported` | MAY | Not emitted; ze validates RS256/RS384/RS512/ES256/ES384 |

## 401 Challenge (Section 5.1)

A resource server MAY name the metadata URL in the WWW-Authenticate header so a client can discover the AS without out-of-band configuration (§5: "A protected resource MAY use the WWW-Authenticate HTTP response header field ... to return a URL to its protected resource metadata to the client"). Ze always sends it:

```
WWW-Authenticate: Bearer realm="ze-mcp",
                  error="invalid_token",
                  error_description="...",
                  resource_metadata="https://mcp.example/.well-known/oauth-protected-resource"
```

| Section | Requirement |
|---------|-------------|
| 5.1 | §5.1 defines the `resource_metadata` parameter, "The URL of the protected resource metadata". RFC 9728 states no obligation to send it and no obligation that the URL be absolute. |
| 5.2 | The `error` / `error_description` parameters use RFC 6750 vocabulary: `invalid_request`, `invalid_token`, `insufficient_scope`. |

## Key Behavior

| Section | Requirement |
|---------|-------------|
| 7.10 | Normal HTTP caching behaviors apply to the metadata GET. Implementations should utilize caching directives such as `Cache-Control: max-age=N`; the RFC names no value. |
| 3.2 | Metadata parameters that are not understood MUST be ignored by the consumer of the response. |
| 7.1 | Implementations MUST support TLS and MUST follow the guidance in BCP 195. |

## Ze Implementation

- Handler: `internal/component/mcp/oauth.go` `writeResourceMetadata`
- Location: `internal/component/mcp/streamable_auth.go` `resourceMetadataURL` and `resourceMetadataPath` insert the well-known suffix between the host and the resource identifier's path (§3, §3.1); the same URL is advertised in the 401 `resource_metadata` parameter.
- Serving: `internal/component/mcp/streamable.go` ServeHTTP dispatches GET at that path to the handler only when `AuthMode=OAuth`; other modes return 404, and the bare suffix or the suffix appended after the path is not served.
- TLS (§7.1): the MCP listener's `tls.Config` is built by `cmd/ze/hub/service_mcp.go` `loadMCPTLSConfig` with `MinVersion` TLS 1.2; `cmd/ze/hub/service_mcp_rfc9728_test.go` proves it and cannot carry tags, because the tag scanner walks `internal/`, `pkg/` and `test/` only.
- Resource field: `cfg.OAuth.MetadataResource` with fallback to `cfg.OAuth.Audience`. Never derived from `r.Host` -- a reverse proxy cannot change the resource's advertised identity.

## Compliance Checklist

- [ ] [RFC9728-2-1] [MUST] The `resource` field MUST be present in the metadata document and contain the canonical URL identifying the resource (§2) {single-polarity: positive; the resource field is emitted unconditionally by writeResourceMetadata (internal/component/mcp/oauth.go:170-171,184-192), so no input can make it absent and there is no negative to assert}
- [ ] [RFC9728-2-6] [MUST] The `jwks_uri` URL MUST use the https scheme (§2)
- [ ] [RFC9728-2-7] [MUST] When both signing and encryption keys are made available in the referenced JWK Set, a `use` (public key use) parameter value is REQUIRED for all keys to indicate each key's intended usage (§2)
- [ ] [RFC9728-2-8] [MUST NOT] The value `none` MUST NOT be used in `resource_signing_alg_values_supported` (§2)
- [ ] [RFC9728-2.1-1] [MUST NOT] If any human-readable field is sent without a language tag, parties using it MUST NOT make any assumptions about the language, character set, or script of the string value (§2.1)
- [ ] [RFC9728-2.1-2] [MUST] A human-readable string value sent without a language tag MUST be used as is wherever it is presented in a user interface (§2.1)
- [ ] [RFC9728-2.2-1] [MUST] Signed metadata MUST be digitally signed or MACed using a JWS and MUST contain an `iss` (issuer) claim denoting the party attesting to the claims in the signed metadata (§2.2)
- [ ] [RFC9728-2.2-2] [MUST] If the consumer of the metadata supports signed metadata, metadata values conveyed in the signed metadata MUST take precedence over the corresponding values conveyed using plain JSON elements (§2.2)
- [ ] [RFC9728-3-2] [MUST] Protected resources supporting metadata MUST make a JSON document containing the Section 2 metadata available at a URL formed by inserting a well-known URI string into the resource identifier between the host component and the path and/or query components (§3)
- [ ] [RFC9728-3-3] [MUST] The well-known URI path suffix used MUST be registered in the "Well-Known URIs" registry (§3)
- [ ] [RFC9728-3-4] [MUST] An OAuth 2.0 application using this specification MUST specify what well-known URI suffix it will use for this purpose (§3)
- [ ] [RFC9728-3.1-2] [MUST] A protected resource metadata document MUST be queried using an HTTP GET request at the specified URL (§3.1)
- [ ] [RFC9728-3.1-3] [MUST] If the resource identifier value contains a path or query component, any terminating slash following the host component MUST be removed before inserting /.well-known/ and the well-known URI path suffix (§3.1)
- [ ] [RFC9728-3.2-3] [MUST] A successful response MUST use the 200 OK HTTP status code and return a JSON object using the application/json content type whose members are a subset of the metadata parameters defined in Section 2 (§3.2)
- [ ] [RFC9728-3.2-4] [MUST] Parameters with zero values MUST be omitted from the response (§3.2)
- [ ] [RFC9728-3.3-1] [MUST] The `resource` value returned MUST be identical to the protected resource's resource identifier value into which the well-known URI path suffix was inserted to create the URL used to retrieve the metadata (§3.3)
- [ ] [RFC9728-3.3-2] [MUST NOT] If the `resource` value and the resource identifier are not identical, the data contained in the response MUST NOT be used (§3.3)
- [ ] [RFC9728-3.3-3] [MUST] If the metadata was retrieved from a URL returned by the protected resource via the WWW-Authenticate `resource_metadata` parameter, the `resource` value returned MUST be identical to the URL that the client used to make the request to the resource server (§3.3)
- [ ] [RFC9728-3.3-4] [MUST] The recipient MUST validate that any signed metadata was signed by a key belonging to the issuer and that the signature is valid (§3.3)
- [ ] [RFC9728-6-1] [MUST NOT] Unicode Normalization MUST NOT be applied at any point to either the JSON string or the string it is to be compared against (§6)
- [ ] [RFC9728-6-2] [MUST] Comparisons between two strings MUST be performed as a Unicode code-point-to-code-point equality comparison (§6)
- [ ] [RFC9728-7.1-1] [MUST] Implementations MUST support TLS (§7.1)
- [ ] [RFC9728-7.1-2] [MUST] Implementations MUST follow the guidance in BCP 195 (§7.1)
- [ ] [RFC9728-7.3-1] [MUST] TLS certificate checking MUST be performed by the client as described in RFC 9525 when making a protected resource metadata request (§7.3)
- [ ] [RFC9728-7.3-2] [MUST] The client MUST ensure that the resource identifier URL it is using as the prefix for the metadata request exactly matches the value of the `resource` metadata parameter in the protected resource metadata document received (§7.3)
- [ ] [RFC9728-2-2] [MAY] The `authorization_servers` field MAY be included as a JSON array of AS issuer URLs (§2; the RFC marks the parameter OPTIONAL: "authorization_servers OPTIONAL. JSON array containing a list of OAuth authorization server issuer identifiers")
