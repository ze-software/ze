# RFC 9728 - OAuth 2.0 Protected Resource Metadata

|-------|-------|
| RFC | 9728 |
| Title | OAuth 2.0 Protected Resource Metadata |
| Status | Proposed Standard |

| Authors | A. Parecki, M. Jones |

**Purpose:** Defines a discovery document the resource server publishes at a well-known URL so OAuth 2.1 clients can learn which authorization servers issue tokens for that resource, what scopes are recognised, and how Bearer tokens must be presented. The MCP 2025-06-18 authorization profile makes this document a MUST for MCP resource servers.

**Scope:** Partial implementation covers plain JSON metadata publication,
escaped resource path/query identity, bearer challenges and the MCP TLS
listener. Verification is carried by the tagged tests and their recorded
discrimination results, not by these scope decisions.

Features not offered under the 2026-09-21 decision are response-signing keys
and algorithms, signed metadata, protected-resource discovery/validation
clients, and metadata-consuming user interfaces. These absent optional
features and roles remain implementation limitations, not conformance gaps
in Ze's selected publisher role.

RFC9728-6-3 records the JSON-unescaping step omitted from the earlier
checklist. Ze compares a JSON string with its resource identifier when it
checks a bearer token's `aud` claim, and decodes the claim before it compares.

## Well-Known Endpoint (Section 3.1)

| Item | Value |
|------|-------|
| Path | `/.well-known/oauth-protected-resource` inserted between the host and the resource path or query (§3). Escaped path segments and queries keep their identity. |
| Method | GET (other methods answer 405) |
| Auth | Ze serves it without authentication; RFC 9728 states no obligation either way |
| Content-Type | `application/json` |

## Metadata Document (Section 2)

| Field | Requirement | Ze implementation |
|-------|-------------|-------------------|
| `resource` | REQUIRED HTTPS resource identifier, without a fragment | Configured `environment.mcp.oauth.audience` (or the Go API's `OAuthConfig.MetadataResource` override), never the request Host |
| `authorization_servers` | OPTIONAL; JSON array of AS issuer URLs | Single entry built from `environment.mcp.oauth.authorization-server` |
| `scopes_supported` | RECOMMENDED; JSON array of scope names | Mirrors `environment.mcp.oauth.required-scopes` |
| `bearer_methods_supported` | MAY; array of delivery methods | Always `["header"]` -- MCP only accepts `Authorization: Bearer` |
| `resource_documentation` | MAY; URL | Not emitted |
| `resource_signing_alg_values_supported` | OPTIONAL response-signing algorithms | Not emitted. Token-verification algorithms do not describe resource response signing. |

## 401 Challenge (Section 5.1)

A resource server MAY name the metadata URL in the WWW-Authenticate header so a client can discover the AS without out-of-band configuration (§5: "A protected resource MAY use the WWW-Authenticate HTTP response header field ... to return a URL to its protected resource metadata to the client"). Ze always sends it:

```
WWW-Authenticate: Bearer realm="ze-mcp",
                  error="invalid_token",
                  error_description="...",
                  resource_metadata="https://mcp.example/.well-known/oauth-protected-resource"
```

| Section | Requirement |
|---------|-------------|
| 5.1 | §5.1 defines the `resource_metadata` parameter, "The URL of the protected resource metadata". RFC 9728 states no obligation to send it and no obligation that the URL be absolute. |
| 5.2 | The `error` / `error_description` parameters use RFC 6750 vocabulary: `invalid_request`, `invalid_token`, `insufficient_scope`. |

## Key Behavior

| Section | Requirement |
|---------|-------------|
| 7.10 | Normal HTTP caching behaviors apply to the metadata GET. Implementations should utilize caching directives such as `Cache-Control: max-age=N`; the RFC names no value. |
| 3.2 | Metadata parameters that are not understood MUST be ignored by the consumer of the response. |
| 7.1 | Implementations MUST support TLS and MUST follow the guidance in BCP 195. |

## Ze Implementation

- Handler: `internal/component/mcp/oauth.go` `writeResourceMetadata`
- Location: `internal/component/mcp/streamable_auth.go` `resourceMetadataURL` and `resourceMetadataPath` insert the well-known suffix before the resource identifier's escaped path and query (§3, §3.1). The same URL appears in the 401 `resource_metadata` parameter.
- Serving: `internal/component/mcp/streamable.go` ServeHTTP dispatches GET at that path to the handler only when `AuthMode=OAuth`; other modes return 404, and the bare suffix or the suffix appended after the path is not served.
- TLS (§7.1): `cmd/ze/hub/service_mcp.go` `loadMCPTLSConfig` sets the MCP listener's minimum version to TLS 1.2. `cmd/ze/hub/service_mcp_rfc9728_test.go` exercises that configuration and the actual serving listener. RFC scanner coverage and discrimination must include that actual boundary; a fixture authorization server cannot prove Ze's resource-server TLS.
- Resource field: `cfg.OAuth.MetadataResource` with fallback to `cfg.OAuth.Audience`. Never derived from `r.Host` -- a reverse proxy cannot change the resource's advertised identity.
