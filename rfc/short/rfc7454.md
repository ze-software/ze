**Purpose:** Collects the operational practices that protect a BGP speaker, its
sessions, and the routing information it exchanges. It covers control-plane
filtering, TCP session protection, GTSM, prefix filtering, route flap dampening,
maximum-prefix limits, AS path filtering, next-hop filtering, and community
scrubbing.

**Scope:** No wire format, message, attribute, capability, or NLRI is defined.
The document adds no state machine, no timer, and no error code. It states
policy for generic Internet BGP peerings.

**Audience:** The document addresses network administrators and operators. Its
subject in almost every normative sentence is the person who configures the
network, not the code that implements BGP. Section 12 states the limit
directly: "This document does not aim to describe existing BGP implementations,
their potential vulnerabilities, or ways they handle errors."

**Errata:** None reported. The RFC Editor errata search for RFC 7454 returned no
records on 2026-08-08.

## Protection of the BGP Speaker (Section 4)

| Control | Recommendation | Note |
|---------|----------------|------|
| ACL on TCP port 179 | SHOULD discard packets to port 179 from an address not known or permitted to become a BGP neighbor | TCP alone is not sufficient protection, because TCP is sometimes run in control-plane software |
| Control-plane ACL | SHOULD be used if supported: receive-ACL, control-plane policing | Avoids data-plane filters for transit packets. If the hardware cannot do it, interface ACLs can block packets addressed to the local router |
| Rate limit | MAY be configured for accepted BGP traffic | Bits or packets per second to the control plane. Protects the control plane when BGP traffic goes above platform capability |

RFC 6192 holds the wider control-plane protection recommendation.

## Protection of BGP Sessions (Section 5)

### TCP Session Protection (Section 5.1)

| Mechanism | Reference | Status in this document |
|-----------|-----------|-------------------------|
| TCP MD5 | RFC 2385 | The first mechanism. Obsoleted by TCP-AO. Still the most deployed |
| TCP-AO | RFC 5925 | SHOULD be preferred when implemented. Stronger protection |
| IPsec | | Not enough deployment experience at publication time. No guideline given |

The document states that TCP session protection is "NOT REQUIRED even when
peerings are established over shared networks where spoofing can be done (like
IXPs)". It pairs that with a RECOMMENDED action: consider the trade-offs, and
apply TCP session protection where appropriate. The named drawback is the
configuration and management overhead of the authentication information.

Anti-spoofing at the network edge (RFC 2827, RFC 3704) is a separate
recommendation. It protects IBGP sessions from attackers outside the AS.

### GTSM (Section 5.2)

RFC 5082. The sender sends TCP packets with TTL 255 instead of TTL 1, and the
receiver checks that the TTL equals 255. An IP packet with TTL 255 cannot reach
a host that is not directly connected, so the check stops spoofing from third
parties that are not on the same subnet.

| Property | Value |
|----------|-------|
| TTL value sent | 255 |
| TTL value checked on receipt | 255 |
| Directly connected peerings | SHOULD implement TTL security |
| Multi-hop peerings | GTSM can be applied. TTL is set from the distance between the speakers. Less effective, because anyone inside the TTL diameter can spoof the TTL |
| Configuration | Must be configured on both ends, the same as MD5 |

## Prefix Filtering (Section 6)

### Filter Classes (Section 6.1)

| Class | Section | Rule |
|-------|---------|------|
| Special-purpose IPv4 | 6.1.1.1 | Use the IANA IPv4 Special-Purpose Address Registry. Discard prefixes whose "Global" column is "False" on Internet BGP peerings |
| Special-purpose IPv6 | 6.1.1.2 | Use the IANA IPv6 Special-Purpose Address Registry. Discard only prefixes whose "Global" column is "False" |
| Unallocated IPv4 | 6.1.2.1 | No filter needed. IANA has allocated all the IPv4 space |
| Unallocated IPv6 | 6.1.2.1 | Build the list from the IANA-allocated IPv6 space. Update all IPv6 prefix filters within one month of any change |
| IRR-derived | 6.1.2.2.1 | Build the accepted prefix list from the peer AS and its AS-SET, by recursion. Refresh daily |
| RPKI-derived | 6.1.2.2.2 | Route origin validation per RFC 6811, operated per RFC 7115 |
| Too specific | 6.1.3 | Set per peering. The RIPE community documented IPv4 longer than /24 and IPv6 longer than /48 as neither announced nor accepted |
| Local AS and downstreams | 6.1.4 | Filter your own prefixes inbound on all peerings. Do not apply it where multihoming needs the route |
| IXP LAN | 6.1.5 | Reject more specifics of the IXP LAN prefix. Accept the exact match only from the ASes the IXP authorizes |
| Default route | 6.1.6 | Filter 0.0.0.0/0 and ::/0 outside specific customer or provider configurations |

Section 6.1.2 states the precondition for the whole unallocated-prefix approach:
filtering unallocated prefixes needs constant updates, so a network that cannot
maintain updated prefix filters is told not to use these solutions at all. The
IPv4 de-bogonizing experience is the cited evidence.

### Route Origin Validation Outcomes (Section 6.1.2.2.2)

| RPKI lookup result | Action on the prefix |
|--------------------|----------------------|
| ROA found and valid | Accept |
| ROA found and INVALID | Discard |
| ROA not found | Accept, and give the route a low preference |

SIDR complements the practices in this document. It does not replace them.
Origin validation (RFC 6811) was operational at publication time. Path
validation (BGPsec) was still work in progress and could not be implemented.
Network administrators are told to sign their own routing objects as well, so
other networks can validate their routes.

### IXP LAN Prefix and PMTUD (Section 6.1.5.2)

Loose uRPF drops an ICMP "packet too big" message that an IXP member router
sources from an IXP LAN address, if the receiver has no route covering the IXP
LAN prefix. Every network that can source traffic through the IXP therefore
needs such a route.

The recommended arrangement: each IXP member holds a route for the IXP LAN
prefix or a less specific prefix on all its routers, and announces that route to
its downstreams. Those announcements have to pass the IRR-generated filters and
the too-specific filters. Appendix A gives the worked example: the IXP holds a
/22, uses a /23 of it for the LAN, originates the /22 from its route servers,
and the members accept the /22 through their IRR filters and re-announce it
downstream.

### Filtering Policy by Peer Type (Sections 6.2, 6.3)

Full-routing networks (Section 6.2). "It is RECOMMENDED that each Autonomous
System configures rules for advertised and received routes at all its borders."

| Peer type | Direction | Filters |
|-----------|-----------|---------|
| Internet peer, loose option (6.2.1.1.1) | In | Not globally routable, not IANA-allocated (IPv6), too specific, local AS, IXP LAN, default route |
| Internet peer, strict option (6.2.1.1.2) | In | Announcements must match the routing registries. Optionally the loose list first, when the registry source is not fully trusted |
| Internet peer (6.2.1.2) | Out | Send only appropriate prefixes, selected by community or AS path. Add: not globally routable, too specific, IXP LAN, default route |
| Customer (6.2.2.1) | In | Accept only customer prefixes. Discard all others. A customer that connects other customers and filters strictly can be treated as a peer instead |
| Customer (6.2.2.2) | Out | Default route only, or the full table with: not globally routable, too specific, default route |
| Upstream (6.2.3.1) | In | Same as an Internet peer, with the exception of the default route |
| Upstream (6.2.3.2) | Out | Close to the Internet peer outbound set |
| Leaf network (6.3.1) | In | The default route only, or the full table with: not routable, too specific, local AS, default route as requested |
| Leaf network (6.3.2) | Out | Announce local routes only. The Section 6.2.1.2 filters can be added |

The strict option carries a warning: registries are not always accurate, and
this varies across registries and regions. On script failure, the administrator
decides whether all routes are accepted or rejected, and both choices carry a
cost.

## Route Flap Dampening (Section 7)

Dampening gives a penalty to a route each time it changes. Studies showed the
early implementations caused more harm than benefit, and the RIPE community
recommended against dampening. RFC 7196 later proposed new thresholds that make
it usable, and RIPE reviewed its recommendation. RFC 7454 recommends following
the IETF and RIPE recommendations and using dampening with the adjusted
thresholds.

## Maximum Prefixes on a Peering (Section 8)

| Peer type | Limit relative to the size of the Internet table | Effect |
|-----------|--------------------------------------------------|--------|
| Peer | Lower | Shuts the peering down if the peer sends the full table. A per-peer limit can be set from the expected route count plus headroom |
| Upstream providing full routing | Higher | Protects router memory if the upstream sends too many routes. Choose from what the routers can handle |

The limits need a regular review, because the Internet table grows. Some vendors
give two thresholds: the higher one shuts the peering down, and the lower one
only logs, which lets an operator adjust the limit from observation.

## AS Path Filtering (Section 9)

| Rule | Direction | Exception |
|------|-----------|-----------|
| Accept from a customer only AS paths whose ASNs belong to the customer or are authorized to transit through it | In | If the filter expressions cannot be built: accept only path lengths relevant to the customer type, and discourage excessive prepending |
| Do not accept prefixes with private AS numbers in the AS path | In | Prefixes from customers. An upstream service such as black-hole origination based on a private AS number, where the prefixes are accepted |
| Do not accept prefixes whose first AS number in the path is not the peer's | In | A peering toward a BGP route server with transparent AS path handling. The check has to be deactivated there, because the first AS is an IXP member and the peer AS is the route server |
| Do not advertise prefixes with a nonempty AS path | Out | The network intends to provide transit for them |
| Do not advertise prefixes with upstream AS numbers in the path to a peering AS | Out | The network intends to provide transit for them |
| Do not use private AS numbers in advertisements to peers outside the private arrangement, and strip them when received from such peers | Both | Peers that are party to the private arrangement |
| Do not override the BGP default that rejects an update carrying the local AS number in the AS path | In | An exception needs a careful study of the routing impact |

ASN renumbering is the named case where these rules are adjusted. The usual
migration technique modifies the AS path so the peer still sees the previous
ASN, which lets one router change its ASN without reconfiguring every EBGP peer
at the same time.

## Next-Hop Filtering (Section 10)

On a shared network such as an IXP, BGP can carry a third-party next hop. That
sends packets somewhere other than the announcing peer.

| Peering type | Policy |
|--------------|--------|
| Direct peering on an IXP | Apply an inbound policy that sets the next hop of accepted prefixes to the peer IP address on the IXP LAN that sent the prefix. This is what "next-hop-self" enforces on the sending side |
| Route-server peering | Do not apply that policy. The route server relays the originating member's next hop on purpose, and it has neither the capacity nor the desire to receive the data packets |
| Peering where third-party next hops are intentionally permitted | Do not apply that policy |
| RTBH is implemented (RFC 6666) | Adjust the policy. A well-known next hop is statically routed to a null interface, and a unicast RPF check then discards traffic from and toward the prefix. A community can carry the black-hole signal between peers |

Without the policy, a peer can direct traffic into a black hole (an unreachable
next hop) or onto an unsuspecting third party. Black-holing of this kind is hard
to see without an inspection of the BGP prefixes at the receiving router.

## BGP Community Scrubbing (Section 11)

Section 11 opens with "Optionally, we can consider the following rules".

| Community set | Action |
|---------------|--------|
| Inbound communities carrying the local AS number in the high-order bits | Scrub them, and allow only the ones customers and peers can use as a signaling mechanism |
| All other communities on received routes | Keep them. Customers can need them to signal to upstream providers |
| Communities already present when the local network applies its own | Keep the originals |
| NO_EXPORT | Do not remove it, generally. A peer announces it for a purpose |

## Pitfalls

- **A prefix filter that is not maintained is worse than no filter.** Section
  6.1.2 states this for unallocated-prefix filters, and the IPv4 de-bogonizing
  work is the evidence. A stale IANA-derived filter blocks a newly allocated
  prefix.
- **A strict IRR policy inherits every registry error.** Prefixes are missing
  and information is wrong, and the accuracy varies by registry and by region.
  Section 6.2.1.1.2 asks for an impact check before the policy goes live.
- **An IRR-derived filter is large.** Section 6.1.2.2.1 records tens of
  thousands of configuration lines for an important peer.
- **The first-AS check breaks a route-server peering.** Section 9 requires that
  check to be deactivated there, because the first AS is the announcing member
  and the peer AS is the route server. RFC 7947 makes the same point from the
  route server side.
- **A next-hop-self inbound policy breaks a route-server peering.** Section 10
  states the same exception for the next-hop rule.
- **An exact-match IXP LAN route learned over EBGP can misdirect IXP traffic.**
  Section 6.1.5.1 asks for IGP routes to be preferred over EBGP, or for
  "next-hop-self" on every route learned at that IXP, so a recursive lookup does
  not point the wrong way.
- **Filtering a customer prefix from peers breaks the customer's redundancy.**
  Section 6.1.4 keeps the multihomed customer's prefix accepted from peers and
  upstreams, so the customer can still reach the operator network through the
  Internet when its own peering is down.
- **RPKI concentrates trust.** Section 6.1.2.2.2 cites the analysis of what a
  misbehaving RPKI authority can do to the Internet.
