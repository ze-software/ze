**Status:** Standards Track
**Date:** August 2015
**Authors:** J. Uttaro, P. Mohapatra, D. Smith, R. Raszuk, J. Scudder

## Overview

Defines the ACCEPT_OWN well-known community (0xFFFF0001). Allows a BGP
speaker to accept UPDATE messages that carry its own AS number in the
AS_PATH, provided the route also carries this community. Normally such
routes are rejected as loop prevention (RFC 4271 Section 9).

Primary use case: L3VPN environments where a PE needs to re-import a
route it originated into a different VRF on the same PE, via a route
reflector.

| Community | Value | Hex |
|-----------|-------|-----|

## Operation

### Normal BGP behavior (without ACCEPT_OWN)

A route carrying the receiver's own AS in AS_PATH is rejected as a loop.

### With ACCEPT_OWN

1. Originating PE exports a VPN route with ACCEPT_OWN attached
2. Route reflector reflects the route back to the same PE
3. PE recognizes ACCEPT_OWN and suppresses the AS_PATH loop check
4. PE imports the route into a different VRF (matched by Route Target)
5. When propagating routes into a VRF the community "SHOULD NOT be propagated", and it "SHOULD NOT be attached to any routes that cannot be associated with a source VRF" (§2.2). RFC 7611 states no rule about removing it before re-advertising to an eBGP peer

### Conditions for acceptance

§2.1: "A router MAY accept a route whose ORIGINATOR_ID or NEXT_HOP value matches that
of the receiving speaker if all of the following are true". The acceptance is a MAY, and
each condition below is quoted from that list. RFC 7611 states no iBGP-only restriction
and no AS_PATH condition.

| Condition | Requirement |
|-----------|-------------|
| Configuration | "Processing of the ACCEPT_OWN community is enabled by configuration" |
| Community | "The route in question carries the ACCEPT_OWN community" |
| Source VRF | "The route in question originated from a source VRF on the router", the VRF whose configured Route Distinguisher equals the route's |
| Destination VRF | "The route in question is targeted to one or more destination VRFs on the router (as determined by inspecting the Route Target(s))" |
| Different VRF | "At least one destination VRF is different from the source VRF" |

A route "MUST NOT ever be accepted back into its source VRF, even if it carries one or
more RTs that match that VRF" (§2.1).

## Key Requirements

- MUST NOT accept a route back into its source VRF, "even if it carries one or more RTs
  that match that VRF" (§2.1)
- MUST discard the community when the route arrives "in an address family that does not
  allow the source VRF to be looked up" (§2.2)
- SHOULD control processing by configuration, and it "MUST default to being disabled"
  where configuration controls it (§2.3)
- MUST NOT apply the §2.1 acceptance rules while ACCEPT_OWN is disabled (§2.3)
- MUST invoke the extra decision-process step only for VPN-IP best path selection, and
  not for imported IP routes in a VRF (§3)

The four bullets this section used to carry (honor only on iBGP, never accept from eBGP,
remove before advertising to eBGP, route reflectors propagate unchanged) are in no
sentence of RFC 7611 and were deleted on 2026-09-21.

## Security Considerations

- Misconfiguration can create forwarding loops between VRFs
- Should only be enabled where the PE/RR topology is well understood
- eBGP guard (reject ACCEPT_OWN from external peers) is critical

## Implementation Notes (Ze context)

- Constant to be added as `CommunityAcceptOwn` (0xFFFF0001) in
  `attribute/community.go`
- Parse/display as `accept-own` in text format
- Ze's VPN support would need explicit opt-in to honor this community;
  default behavior remains: reject own-AS routes
