## Overview

Defines the ACCEPT_OWN well-known community (0xFFFF0001). Allows a BGP
speaker to accept UPDATE messages that carry its own AS number in the
AS_PATH, provided the route also carries this community. Normally such
routes are rejected as loop prevention (RFC 4271 Section 9).

Primary use case: L3VPN environments where a PE needs to re-import a
route it originated into a different VRF on the same PE, via a route
reflector.

## Well-Known Community

| Community | Value | Hex |
|-----------|-------|-----|
| ACCEPT_OWN | 65535:1 | 0xFFFF0001 |

## Operation

### Normal BGP behavior (without ACCEPT_OWN)

A route carrying the receiver's own AS in AS_PATH is rejected as a loop.

### With ACCEPT_OWN

1. Originating PE exports a VPN route with ACCEPT_OWN attached
2. Route reflector reflects the route back to the same PE
3. PE recognizes ACCEPT_OWN and suppresses the AS_PATH loop check
4. PE imports the route into a different VRF (matched by Route Target)
5. ACCEPT_OWN community MUST be removed before re-advertising externally

### Conditions for acceptance

All of the following MUST hold:

| Condition | Requirement |
|-----------|-------------|
| Community | ACCEPT_OWN present |
| Received from | iBGP peer (MUST NOT accept from eBGP) |
| AS_PATH | Contains receiver's own AS |
| Route type | VPN route (VRF import/export context) |
| Different VRF | Route must target a different VRF than originated |

## Key Requirements

- MUST only be honored on routes received from iBGP peers
- MUST NOT accept from eBGP peers (loop prevention still applies)
- MUST remove ACCEPT_OWN before advertising to eBGP peers
- SHOULD be used with explicit configuration (not enabled by default)
- Route reflectors MUST propagate the community unchanged

## Security Considerations

- Misconfiguration can create forwarding loops between VRFs
- Should only be enabled where the PE/RR topology is well understood
- eBGP guard (reject ACCEPT_OWN from external peers) is critical

## Implementation Notes (Ze context)

- Constant to be added as `CommunityAcceptOwn` (0xFFFF0001) in
  `attribute/community.go`
- Parse/display as `accept-own` in text format
- Ze's VPN support would need explicit opt-in to honor this community;
  default behavior remains: reject own-AS routes

## Compliance Checklist

- [ ] [RFC7611-3-2] [MUST] ACCEPT_OWN MUST only be honored on routes received from iBGP peers (§3) {not-applicable: The "honored only on iBGP routes" restriction governs a router that honors ACCEPT_OWN via VRF import, which Ze does not implement (community.go:59-61 defines the value for display only; there is no VRF-import honoring path).}
- [ ] [RFC7611-3-3] [MUST NOT] ACCEPT_OWN MUST NOT be accepted from eBGP peers (§3) {not-applicable: Ze never honors ACCEPT_OWN from any peer (it has no VRF-import mechanism), so the "MUST NOT accept from eBGP" restriction has no applicable honoring code path -- the community is recognized only as a named value for display (community.go:112).}
- [ ] [RFC7611-3-4] [MUST] ACCEPT_OWN community MUST be removed before re-advertising to eBGP peers (§3) {not-applicable: Ze does not participate in the ACCEPT_OWN VPN mechanism -- it neither sets ACCEPT_OWN on VRF export nor honors it on import (community.go:59-61 is display-only) -- so the "remove before re-advertising to eBGP" obligation, which prevents a participating router from leaking the VPN-internal ACCEPT_OWN signal, has no applicable code path.}
- [ ] [RFC7611-3-5] [MUST] Route reflectors MUST propagate the ACCEPT_OWN community unchanged (§3) {not-applicable: Ze's route reflector forwards route communities verbatim and does not special-case ACCEPT_OWN, so a received ACCEPT_OWN would be reflected unchanged as a side effect of the generic community-transparent forwarding already gated under RFC 4456 / RFC 7947; Ze implements no ACCEPT_OWN VPN mechanism (community.go:59-61 is display-only), so this RR requirement has no ACCEPT_OWN-specific code path.}
- [ ] [RFC7611-5-1] [SHOULD] ACCEPT_OWN SHOULD be used with explicit configuration, not enabled by default (§5)
