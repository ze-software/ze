## Purpose

Replaces RFC 1034 Section 4.3.4. A negative answer (the name does not exist,
or holds no data of the type asked for) carries its own time to live in the
SOA record of the authority section, and a resolver caches it and hands it to
its own clients like a positive answer. RFC 2308 also redefines the SOA
MINIMUM field of RFC 1035 Section 3.3.13 (Section 4).

## Negative responses (Section 2)

| Response | RCODE | Answer | Authority | Meaning |
|----------|-------|--------|-----------|---------|
| NXDOMAIN type 1 | NXDOMAIN | CNAMEs, if any | SOA and NS | name (QNAME, the last CNAME target) does not exist; implicit referral |
| NXDOMAIN type 2 | NXDOMAIN | CNAMEs, if any | SOA | the form an authoritative server should send (Section 2.1.1) |
| NXDOMAIN type 3 | NXDOMAIN | CNAMEs, if any | empty | not cacheable (no SOA) |
| NXDOMAIN type 4 | NXDOMAIN | CNAMEs, if any | NS | not cacheable (no SOA) |
| NODATA type 1 | NOERROR | empty | SOA and NS | name exists, no RRset of the type; implicit referral |
| NODATA type 2 | NOERROR | empty | SOA | the form an authoritative server should send (Section 2.2.1) |
| NODATA type 3 | NOERROR | empty | empty | not cacheable (no SOA) |
| Referral | NOERROR | empty or CNAMEs | NS, no SOA | not a negative answer |

A NODATA is told from a referral by an SOA in the authority section, or by
the absence of NS records there (Section 2.2).

## SOA MINIMUM (Section 4)

| Earlier meaning (RFC 1035 Section 3.3.13) | RFC 2308 |
|-------------------------------------------|----------|
| Minimum TTL of every RR in the zone | Deprecated: "has never in practice been used and is hereby deprecated" |
| Default TTL of an RR with no TTL in the master file | Replaced by the `$TTL <TTL> [comment]` master file directive |
| TTL of negative responses | The one remaining meaning |

Ze reads no master file, so the `$TTL` directive has no consumer in Ze.

## Negative answer TTL (Sections 3 and 5)

| Who | Rule |
|-----|------|
| Authoritative server | SOA TTL in the authority section = min(SOA.MINIMUM, SOA TTL) |
| Caching resolver | the entry's TTL decrements like a positive entry; at zero it is never used again |
| Caching resolver | NXDOMAIN keyed on `<QNAME, QCLASS>`, NODATA on `<QNAME, QTYPE, QCLASS>` |
| Caching resolver | a negative answer without an SOA SHOULD NOT be cached |
| Caching resolver | a configured cap, not above the positive cap; 1 to 3 hours is a sensible default, above a day is problematic |

How Ze applies it: `storeNegative` caches the bailiwick SOA (`findSOA`) for
min(SOA TTL, SOA.MINIMUM), each first bounded by `cache max-negative-ttl`
(default 3600 seconds, `ze-dns-resolver-conf.yang`). NXDOMAIN is stored under
type 0 (`typeNameError`), so one entry answers every type of the name.
GeoDNS writes the configured `soa minimum` as both the SOA TTL and MINIMUM;
AS112 writes 604800 for both (`zoneTTL`, `soaMinTTL`).

## Pitfalls

- **Lowercase words.** RFC 2308 is post-RFC 2119 and capitalises its
  keywords, so lowercase "must" and "should" (Section 2.2.1 "the resolver must
  query again using the QNAME", and the Section 8 summary of changes) are not
  requirement rows. Section 8 restates Sections 5 and 6 in lowercase; its one
  capitalised MUST is row 8-1.
- **NXT and SIG.** The NXT and SIG records of RFC 2065 were replaced by NSEC
  and RRSIG (RFC 4034, RFC 4035, which update this RFC). Ze's resolver sends
  its upstream queries with DO clear (`forward.go::upstreamQuery`), and caches
  only the SOA of a negative answer.
- **CNAME then NXDOMAIN.** The negative answer is about the last CNAME target,
  never the query name. `absorb` stores it under the chain's last name
  (`current`), and `lookup` follows cached CNAMEs before it reads the
  negative cache.
- **Forwarding loops (Section 5).** A cached negative answer handed on with a
  TTL that is not counted down can circulate between two servers for ever;
  hence the decrement of Section 6 and the SHOULD NOT for an SOA-less answer.
- **Security (Section 11).** A forged NXDOMAIN with a very high TTL denies a
  name for as long as it is cached: the `cache max-negative-ttl` cap bounds it.

- [ ] [RFC2308-3-2] [MUST] If the containing zone is signed [RFC2065] the SOA and appropriate NXT and SIG records MUST be added. - [ ] [RFC2308-5-1] [MUST NOT] This TTL decrements in a similar manner to a normal cached answer and upon reaching zero (0) indicates the cached negative answer MUST NOT be used again. (§5)
- [ ] [RFC2308-5-2] [MUST] The NXT record, if it exists in the authority section of a negative answer received, MUST be stored such that it can be be located and returned with SOA record in the authority section (§5) {gap: storeNegative caches the SOA alone, so an NXT (or NSEC) record in a received negative answer is dropped and never returned; internal/plugins/dnsresolver/resolve.go::storeNegative}
- [ ] [RFC2308-5-3] [MUST] The NXT record MUST have the same owner name as the query name for NODATA responses. (§5) {gap: no part of Ze produces a NODATA response carrying an NXT (or NSEC) record, because the answering plugins serve unsigned zones and the resolver caches none; internal/plugins/geodns/server.go::answerQuestions, internal/plugins/dnsresolver/resolve.go::storeNegative}
- [ ] [RFC2308-6-1] [MUST] When a server, in answering a query, encounters a cached negative response it MUST add the cached SOA record to the authority section of the response with the TTL decremented by the amount of time it was stored in the cache. (§6)
- [ ] [RFC2308-6-2] [MUST] If a NXT record was cached along with SOA record it MUST be added to the authority section. (§6) {gap: the negative cache holds the SOA alone, so no NXT (or NSEC) record is cached with it or added from it; internal/plugins/dnsresolver/resolve.go::storeNegative, internal/plugins/dnsresolver/cache.go::lookup}
- [ ] [RFC2308-7.1-1] [MUST NOT] If it does so it MUST NOT cache it for longer than five (5) minutes (§7.1) {single-polarity: negative; the resolver caches no server failure at all (internal/plugins/dnsresolver/resolve.go::servfail is never stored), so the only observable is that a later identical query is forwarded again rather than answered from a cache}
- [ ] [RFC2308-7.1-2] [MUST] it MUST be cached against the specific query tuple <query name, type, class, server IP address>. (§7.1) {single-polarity: negative; the resolver caches no server failure, so no cached failure can reach a query outside its tuple, and the observable is a later query for the same or another tuple being forwarded again}
- [ ] [RFC2308-7.2-1] [MUST NOT] If it does so it MUST NOT be deemed dead for longer than five (5) minutes. (§7.2) {single-polarity: negative; the resolver keeps no dead-server indication (internal/plugins/dnsresolver/resolve.go::forward asks every configured upstream again on each query), so the observable is a silent upstream being asked again on the next query}
- [ ] [RFC2308-7.2-2] [MUST] The indication MUST be stored against query tuple <query name, type, class, server IP address> unless there was a transport layer indication that the server does not exist, in which case it applies to all queries to that specific IP address. (§7.2) {single-polarity: negative; the resolver stores no dead-server indication, so none can be applied beyond its tuple, and the observable is an upstream that failed one query being asked for the next}

- [ ] [RFC2308-5-4] [SHOULD NOT] Negative responses without SOA records SHOULD NOT be cached as there is no way to prevent the negative responses looping forever between a pair of servers even with a short TTL. (§5)
