# RFC Compliance (every protocol, not just BGP)

**When:** writing, changing, reviewing, or testing any protocol-implementing code, for any RFC Ze implements
**Severity:** blocking
**Related:** rfc-conformance, testing, interop-and-goal-validation

## Directives

**An RFC MUST be treated as the required baseline behavior, not a ceiling on explicit operator control. Implemented protocol capabilities MUST follow the applicable requirements of their own RFCs and standards on the default configuration path. Explicit configuration options for more specific behavior or extensions MUST remain supported, and their existence MUST NOT make the compliant default path fail conformance.** An operator's ability to configure custom policy, raw octets, or explicit overrides in a way that violates an RFC is not a software failure and MUST NOT turn a compliant default path into a `{gap}` or `{partial}` requirement. RFC work MUST NOT remove existing features to improve a conformance figure. Specs MUST name the default configuration being assessed, the options to preserve, and tests of both. Claims and evidence MUST identify the configuration they cover; an explicitly selected extension that differs from an RFC MUST be described as such. This applies to every protocol Ze speaks, including BGP, IS-IS, OSPF, BFD, LDP, RSVP-TE, IKE and IPsec, L2TP, PPPoE, DHCP, NTP, RADIUS, TACACS+, gNMI, BMP, RPKI and VRRP. Coverage follows the full-coverage directive below.
**Every MUST and MUST NOT enforced in code MUST carry a comment directly above it naming the RFC section and quoting the requirement (`// RFC NNNN Section X.Y: "quoted requirement"`), covering whichever of the validation rules, error conditions, state transitions, timer constraints and message ordering the code enforces.** Protocol code MUST NOT be changed without documenting the wire format: an ASCII diagram with field offsets, byte offset annotations, and the RFC section reference. Before editing protocol code, RFC summaries under `rfc/short/`, or RFC-tagged tests, you MUST also read `ai/rules/rfc-conformance.md` in full (quotes, whole-stack accounting, implementer kinds, extraction walks, and verbatim requirement rows).

**A tag you add, and a tagged unit whose behavior or claim you change, MUST carry a discrimination record in the same change.** A tag's prose states what its test demonstrates, and no gate can read a sentence, so the proof is a recorded break of the producing code under which that tagged unit itself goes red. `./le rfc discriminate stem <stem> report <path>` proposes the candidate breaks, `./le rfc record` observes one and writes the record, and `./le rfc check` refuses a tagged unit the commit under test added against `HEAD^` and that carries none. The main thread runs these three commands, and an agent lists them as owed commands.
**A commit that changes a tagged test or its claim MUST carry the record `./le rfc record` re-took, or remove the tag with the judge's approval.** The proof belongs to the test, so it goes stale only when the tagged unit or its claim changes: a change to the code the test checks, the producer or paired producer the record broke included, changed, renamed or removed, leaves it standing, because the unchanged test still catches what it caught. `./le commit create` refuses a commit that stales a record the parent held fresh, or deletes one while its tag stays, and its refusal prints the `./le rfc record` line that re-takes each one on its recorded route; a record already stale at the parent refuses nothing. The two proof routes, the closed escape vocabulary and the refusals are in `docs/contributing/rfc-conformance-gates.md`.
**The claim MUST state what the test body checks, and MUST NOT state more.** A claim wider than the assertion converts an unproven MUST into a proven one on the public ledger, which is the violation with a green bar on top. Rewording a claim stales its record and owes a fresh one, because a proof of the old sentence is not a proof of the new one.

## Full RFC Coverage

**Ze MUST implement every applicable requirement of every RFC it implements, fully and correctly (`ai/META-DECISIONS.md`). Full RFC coverage MUST NOT be treated as a first-release prerequisite: shipped code MUST comply with the RFC requirements of the capabilities it implements, while a missing RFC feature MAY wait until after the first release.** A missing Linux primitive claimed as an implementation limit MUST be named with evidence, not assumed. Verification MUST exercise real entry points and include interoperability with another implementation where applicable. Helpers, isolated encoders and unfinished code alone do not prove a capability works.

**An absent requirement of an RFC Ze implements is owed work, never a gap awaiting permission: it MUST be recorded in the RFC summary and implemented, and whether to implement it MUST NOT be put to the owner.** Release scheduling MUST follow the owner's release timing (`ai/META-DECISIONS.md`): a missing RFC feature MAY wait until after the first release. Touching a capability MUST NOT automatically pull every absent feature of its RFC into first-release scope; requirements needed for that capability's correct behavior remain inside the work.
**A question the RFC text answers MUST NOT be put to the owner.** Where the RFC is silent or unclear, the goal is interoperability: Ze MUST work with BIRD and FRR, so read their source, choose what lets Ze interoperate with both, and report the quoted evidence. Ask only when claiming a Linux implementation limit, when proposing a scope exception beyond that release timing, or when the RFC is silent and FRR and BIRD disagree.
**Prior owner decisions MUST remain in force until the owner changes them, and existing unfinished code MUST be preserved.**

**A false public support claim MUST be corrected immediately on the surface that carries it to the status the evidence supports.** Reports MUST distinguish implemented-and-tested, implemented-but-unverified and unimplemented capabilities, and name the behavior exercised and any missing proof. Correcting the claim MUST NOT wait for the new tests or the missing implementation that will later make it true.
