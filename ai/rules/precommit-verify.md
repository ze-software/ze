# Pre-Commit Verification

**When:** before running tests to judge a change, before any `./le verify` command, or before committing Go
**Severity:** blocking

## Directives

**An agent MUST NOT run any `./le verify` command, `./le verify changed` included: GitHub CI/CD verifies a pushed commit, and the evidence for a change is the scoped test runs of what it reaches (the named tests, the packages, the functional tests), which the main thread runs in the main checkout from the agent's owed commands.** A rule, skill, hook or tool message that tells an agent to run `./le verify` is wrong: correct it, never follow it. The full verification (`./le verify current`, `./le verify worktree`) is the release check, which CI runs and Thomas starts himself when he chooses; its exact command is the only form an agent gives him.
**Code MUST be developed and tested in the main checkout, never in a worktree, a `git archive` export or any other copy of the tree.** When another session's in-progress edit breaks the build there, report what broke and whose it is, and wait for it to clear; MUST NOT move to a copy to dodge it.

**Only `./le repo compiles check` compiles what git holds: `go build`, every other verify stage and every native test action read your working tree, uncommitted and untracked files included.** So a consumer MUST NOT be committed while the file that defines a symbol it newly uses stays uncommitted. That compile is a repo-wide compile, which is full testing: it runs in the release check GitHub CI runs on a pushed commit, and a session MUST NOT start it on its own initiative, after a commit that carried Go included. A commit that carried Go owes the scoped tests of the packages it reaches and nothing wider; the committed-tree compile is CI's. A red it reports is cleared by committing the producer, never by reverting the consumer. It compiles no `_test.go`, so a test file committed without its fixture producer stays invisible to it. The design is `docs/architecture/testing/tracked-build-gate.md`.

**The main thread MUST land a code change through `./le commit create` and its script as soon as the change's owed commands pass: those scoped runs of what the change reaches are the whole evidence the commit owes, and the committed-tree compile is CI's. An agent MUST NOT build its own export, archive or copy of HEAD to test a commit set, before or after it lands, and a brief MUST NOT ask for one.** CI's verify run already compiles what git holds on a pushed commit, so a hand-built export repeats it at the cost of tens of tool calls. The main thread makes the commit, so no successor agent is spent on it. A red that compile reports is fixed forward in a new commit. A red that the change's own diff did not cause MUST NOT be investigated on the way to landing: the commit names it in its body.
