**Deferral versus parking, settled by one question: does the goal this work exists to achieve still hold if I leave this?** If no, it is parking with a polite name: MUST fix it now (`completion.md`). If yes, it is separable future work, and its home depends on what it is.
**A small defect you walked into MUST be fixed in the work in hand, its spec's scope widened to carry it (`completion.md`). One too big for that MUST get one row in `plan/journal/<class>.md`, listed in the owned journal rows table of the spec that will fix it, an existing spec amended before a new one is written, then the work in hand closes and you stop: no row anywhere else, no question to Thomas. A distinct, larger, separable feature MUST be homed in a spec per `planning.md`, an existing one amended where its scope can take it, and Thomas MUST be asked whether that spec runs, unless an RFC Ze implements, an agreed design or a correctness defect already decides it: then the spec is written and runs without asking.**
**Automatic admission of RFC work MUST respect the owner's release timing (`ai/META-DECISIONS.md`): a missing RFC feature MAY wait until after the first release.** Owed post-release coverage MUST NOT become immediate implementation solely because its RFC is partially implemented.
