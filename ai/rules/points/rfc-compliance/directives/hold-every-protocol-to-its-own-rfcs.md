**An RFC MUST be treated as the required baseline behavior, not a ceiling on explicit operator control. Implemented protocol capabilities MUST follow the applicable requirements of their own RFCs and standards on the default configuration path. Explicit configuration options for more specific behavior or extensions MUST remain supported, and their existence MUST NOT make the compliant default path fail conformance.** RFC work MUST NOT remove existing features to improve a conformance figure. Specs MUST name the default configuration being assessed, the options to preserve, and tests of both. Claims and evidence MUST identify the configuration they cover; an explicitly selected extension that differs from an RFC MUST be described as such. This applies to every protocol Ze speaks, including BGP, IS-IS, OSPF, BFD, LDP, RSVP-TE, IKE and IPsec, L2TP, PPPoE, DHCP, NTP, RADIUS, TACACS+, gNMI, BMP, RPKI and VRRP. Coverage follows the full-coverage directive below.
**Every MUST and MUST NOT enforced in code MUST carry a comment directly above it naming the RFC section and quoting the requirement (`// RFC NNNN Section X.Y: "quoted requirement"`), covering whichever of the validation rules, error conditions, state transitions, timer constraints and message ordering the code enforces.** Protocol code MUST NOT be changed without documenting the wire format: an ASCII diagram with field offsets, byte offset annotations, and the RFC section reference. Before editing protocol code, RFC summaries under `rfc/short/`, or RFC-tagged tests, you MUST also read `ai/rules/rfc-conformance.md` in full (quotes, whole-stack accounting, implementer kinds, extraction walks, and verbatim requirement rows).
