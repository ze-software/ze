**Conformance MUST be judged on the behavior the whole stack produces, and the component that enforces a requirement MUST NOT decide the verdict.** A requirement Ze meets by configuring the kernel correctly is MET when the evidence proves it. Delegation to XFRM, netlink or another layer implements an obligation only when that layer performs it. `{not-applicable}` and `excluded-kind: binds-another-role` MUST NOT be used for a requirement whose role Ze fills, including through a layer acting on Ze's behalf.
**A requirement met through a lower layer MUST still carry a test, and that test MUST assert the thing Ze actually produces: the selector, the state, or the option Ze installs for the layer below.** The stack-level answer is what conformance counts, so the proof runs at the boundary Ze owns, and it MUST NOT claim a rejecting branch Ze does not hold. An integration test that reads the installed kernel state proves more than a unit test over the builder and is preferred where one is reachable (`ai/rules/platform-linux.md`).
**A requirement that NO layer performs MUST NOT be recorded as met.** A correct encoder with no non-test caller emits nothing, so no behavior reaches the wire and there is no stack answer to count. The reachability question is what the ruling above turns on: whether the packet is handled somewhere, not whether Ze's own code handles it (`ai/rules/principles.md`).
**A gap and an exclusion MUST remain distinct, with the RFC's actual obligation level and applicability preserved.** An applicable requirement that the stack does not meet is a conformance gap even when its implementation is outside the agreed session scope. An exclusion requires evidence that the obligation does not bind Ze; absence of code alone is insufficient.
**`binds-another-role` MUST identify the role and show that neither Ze nor a layer acting on its behalf fills it.** The reason MUST cite the relevant implementation and RFC condition. Unfinished or unreachable code alone proves neither implementation nor role applicability.
**An OPTIONAL feature outside the owner's agreed scope MUST be recorded as an implementation gap, and obligations conditional on that absent feature MUST be excluded from the conformance count.** Use `excluded-kind: feature-out-of-scope`; the reason MUST quote the RFC condition and optionality and name the scope decision. An unconditional MUST MUST NOT be relabeled optional or inapplicable because its feature is absent.
