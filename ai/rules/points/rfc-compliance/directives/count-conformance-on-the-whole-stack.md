**Conformance MUST be judged on the behavior the whole stack produces, and the identity of the component that enforces a requirement MUST NOT decide the verdict (owner directive, 2026-08-31).** Ze is TCP conformant because Linux is. A requirement Ze meets by configuring the kernel correctly is MET, and delegation to XFRM, to netlink or to any other layer under Ze is an implementation of the obligation rather than an exemption from it. `{not-applicable}` and an `excluded-kind` of `binds-another-role` MUST NOT be written for a requirement whose role Ze fills, and both are wrong wherever the packet is really handled on Ze's behalf.
**A requirement met through a lower layer MUST still carry a test, and that test MUST assert the thing Ze actually produces: the selector, the state, or the option Ze installs for the layer below.** The stack-level answer is what conformance counts, so the proof runs at the boundary Ze owns, and it MUST NOT claim a rejecting branch Ze does not hold. An integration test that reads the installed kernel state proves more than a unit test over the builder and is preferred where one is reachable (`ai/rules/platform-linux.md`).
**A requirement that NO layer performs MUST NOT be recorded as met.** A correct encoder with no non-test caller emits nothing, so no behavior reaches the wire and there is no stack answer to count. The reachability question is what the ruling above turns on: whether the packet is handled somewhere, not whether Ze's own code handles it (`ai/rules/principles.md`).
**A gap and an exclusion MUST NOT be confused, because a gap is an ISSUE and an exclusion is a DECISION (owner directive, 2026-08-31).** A `{gap}` says Ze owes the behavior and does not produce it, so it is work outstanding and it stays on the ledger until the behavior exists. An `excluded` site says the obligation never bound Ze in the first place, and the reason names which decision put it out of reach.
**`binds-another-role` is PRESUMED WRONG and MUST be justified before it is written (owner directive, 2026-08-31).** Ze rarely implements one side of a protocol: it speaks client and server, sender and receiver, initiator and responder, and a split role is the exception. So an obligation addressed to "the sender", "the receiver" or "the gateway" almost always binds Ze, and the label reads on the public ledger as "not our problem" where the truth is usually "our problem, unbuilt". Writing it MUST name the role, show Ze never acts as it, and cite the producer that would act as it if Ze did. "Ze does not implement it" is the claim, never the showing, and a role Ze fills with unreached code is a gap rather than another role.
**An OPTIONAL feature Ze decided not to offer MUST exclude the obligations conditional on it, and those MUST NOT be recorded as gaps (owner directive, 2026-08-31).** Conformance is not owed for an optional feature that is out of scope: a MUST written as "if you do X, do it this way" does not bind an implementation that never does X. The exclusion carries `excluded-kind: feature-out-of-scope`, and its reason MUST quote the sentence that makes the feature optional and name the scope decision. The absent FEATURE is still recorded, as an implementation gap a later scope decision can revisit, and never as a conformance gap.
