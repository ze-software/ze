How to read the colors

A color names what the measure MEANS, not how well Ze scores on it. Green is a good outcome at any value, red is a bad one, and neither a population nor a scope count is an outcome, so both take no color. The number under the label is what says how far Ze has got. An outlined card with no colored edge, under Totals, is a total the other cards are counted against, not a measure.

Automatic checks

Included in automatic checks: Generic Routing Encapsulation (GRE) base header. Ze fills the tunnel endpoint and encapsulator roles by programming gre and gretap tunnels: on Linux through internal/plugins/iface/netlink/tunnel_linux.go::buildGretun and buildGretap (linux:CONFIG_NET_IPGRE), and on the VPP interface backend (iface-vpp, ze_vpp feature gate) through internal/plugins/iface/vpp/tunnel.go::createGRETunnel. The kernel ip_gre module and VPP build and parse every GRE header. All eleven MUSTs are gaps, because the VPP datapath is a shipped path no test verifies. Two are also unmet on Linux: the kernel processes a packet with the Strict Source Route bit or a recursion bit set (2.3-1, 5.2-1). The other nine hold on Linux, from the flags ze writes (GRE_KEY only, no checksum, version 0), and owe tests

The MUST bar shows mandatory requirements (MUST, MUST NOT, REQUIRED, SHALL and SHALL NOT) that Ze and its operating system must meet. It includes only RFCs whose requirement lists have been checked against the original text. Ze verified means a test has been shown to fail when the required behavior is deliberately broken. Behavior provided by the operating system or a library is OS verified when a test checks it using the settings Ze installs and has also been shown to detect a deliberate fault; until then, it is an OS testing gap. Tests awaiting verification counts requirements a tagged test covers that no deliberate fault has yet been shown to break and that nothing records as unmet. Exclusion unchecked counts requirements claimed not to apply to Ze whose evidence is still to be checked. Not assessed counts requirements no tagged test covers and that nothing records as unmet, so nothing yet says whether Ze meets them. Not built counts requirements the RFC summary or a test review says Ze does not meet, in full or in part. The overview bar adds optional requirements (MAY, NOT RECOMMENDED, OPTIONAL, RECOMMENDED, SHOULD and SHOULD NOT) and requirements that do not apply to Ze. An RFC marked requirements not reviewed is excluded from these figures because its requirement list has not been checked against the original text. Counts are loaded from the RFC data files.

{gap}: unmet on Linux and unverified on VPP. The kernel's gre_parse_header (net/ipv4/gre_demux.c, linux:CONFIG_NET_IPGRE_DEMUX) refuses only the Routing bit (bit 1) and a non-zero version; it accepts the Key and Sequence bits (bits 2 and 3, RFC 2890) and never checks the Strict Source Route bit (bit 4) or the recursion bits, so a packet with bit 4 or bit 5 set is processed, and Linux implements no other part of RFC 1701. The Linux path is the verified half: after the kernel's ip_tunnel_rcv (net/ipv4/ip_tunnel.c, linux:CONFIG_NET_IPGRE) decapsulates, ip_forward routes the payload on its destination and decrements its TTL, on the link internal/plugins/iface/netlink/tunnel_linux.go::buildGretun creates; no test covers it. The VPP half is unverified: iface-vpp (internal/plugins/iface/vpp/register.go, ze_vpp feature gate) installs the tunnel through internal/plugins/iface/vpp/tunnel.go::createGRETunnel, and no test shows VPP decrements the payload TTL
RFC2784-3.1-3 Care should be taken when forwarding such a packet, since if the destination address of the payload packet is the encapsulator of the packet (i.e., the other end of the tunnel), looping can occur. In this case, the packet MUST be discarded. (§3.1) {gap}, no test a gap in proof on one of the two interface backends. The Linux path is the verified half: when the payload's route leads back into the tunnel it came from, the kernel's ip_tunnel_xmit (net/ipv4/ip_tunnel.c, linux:CONFIG_NET_IPGRE) finds the route's device is the tunnel itself, counts a collision and drops the packet, on the link internal/plugins/iface/netlink/tunnel_linux.go::buildGretun creates; no test covers it. The VPP half is unverified: iface-vpp (internal/plugins/iface/vpp/register.go, ze_vpp feature gate) installs the tunnel through internal/plugins/iface/vpp/tunnel.go::createGRETunnel, and no test shows VPP discards a looping payload
RFC2784-5.2-1 As stated in Section 5.3, a packet with non-zero bits in any of bits 1-5 MUST be discarded unless the receiver implements RFC 1701. (§5.2) {gap}, no test unmet on Linux and unverified on VPP, as RFC2784-2.3-1. The kernel's gre_parse_header (net/ipv4/gre_demux.c, linux:CONFIG_NET_IPGRE_DEMUX) refuses only the Routing bit and a non-zero version, so a packet with the Strict Source Route bit or a recursion bit set is processed. On VPP, iface-vpp (internal/plugins/iface/vpp/register.go, ze_vpp feature gate) installs the tunnel through internal/plugins/iface/vpp/tunnel.go::createGRETunnel, and no test shows VPP discards it
