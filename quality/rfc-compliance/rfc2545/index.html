Enrolment

Enrolled: Section 3 specifies the address order, length and shared-subnet conditions for the MP_REACH_NLRI next-hop field. Section 2 scope definitions and Section 4 BGP Identifier references are classified in rfc/extraction/rfc2545.json. Enrolled 2026-08-07.

What the public ledger says

Status: Partial

What the ledger says is covered
  • Ze emits and parses the 16-octet global-only and 32-octet global-plus-link-local forms. Tagged socket, functional and replay tests check exact address order and lengths. Independently rejudged RFC2545-3-2 retains that wire-length proof. The earlier Supported claim counted tagged coverage as proof of every address and subnet condition
  • the 2026-10-06 source review does not support that claim.
What the ledger says remains

RFC2545-3-1 and RFC2545-3-3 have weak audit verdicts. nextHopGlobalOctets in internal/component/bgp/reactor/reactor_wire.go rejects unset and IPv4 addresses but admits IPv6 unspecified and multicast addresses through ValidateGlobalNextHop; the tagged refusal cases do not cover these inputs. egressNextHopGlobalHalf in internal/component/bgp/reactor/forward_next_hop.go preserves a received pair for an on-link destination without checking the received global next hop's subnet. These source findings still need wire-level reproduction.

The existing RFC2545-3-6 gap remains: on locally constructed routes, linkScope.linkLocalNextHop has no source for another router's link-local address and sends its global address alone. Capability code 77 is draft-based, not an RFC2545 capability.

Audit verdict: unimplemented (no code path enforces the requirement), fresh. Independently rejudged against rfc/full/rfc2545.txt Section 3: 'The link-local address shall be included in the Next Hop field if and only if the BGP speaker shares a common subnet with the entity identified by the global IPv6 address carried in the Network Address of Next Hop field and the peer the route is being advertised to.'
