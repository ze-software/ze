Enrolment

Enrolled: VRRP Version 3 for IPv4 and IPv6 (RFC 5798, obsoleted by RFC 9568): the VRRPv3 document ze speaks on the IPv4 wire only in a group configured `checksum rfc5798-compatible`; a default group speaks RFC 9568. Every one of its 59 gated requirements carries a {superseded} marker naming where the obligation lives in RFC 9568, and 55 of them are restated there unchanged, so ze implements them through the same producers rfc/short/rfc9568.md gates: internal/plugins/vrrp/packet (advert encode/decode, checksum), internal/plugins/vrrp/fsm (Initialize/Backup/Master), internal/plugins/vrrp/transport (proto 112, GTSM, GARP/NA). The row that is NOT a restatement is RFC5798-5.2.8-1: Section 5.2.8 puts a pseudo-header under the checksum for both families, RFC 9568 Section 5.2.8 removes it for IPv4, and ze transmits this document form only in a group configured `checksum rfc5798-compatible`, because keepalived and the pre-RFC-9568 base require it (pseudoSumV4 and FillChecksum, internal/plugins/vrrp/packet/checksum.go). Tagged under RFC5798 ids: 43 of the 59 gated MUSTs carry a positive and a negative test, 4 carry a positive test and a `{single-polarity}` annotation because the producer writes a constant no input changes, 3 are met below ze by the Linux forwarding and SLAAC paths, 2 are conditional on an optional feature ze declined, and 7 are `{gap}` rows ze owes.

What the public ledger says

Status: Partial

What the ledger says is covered
  • For IPv4, ze transmits the RFC 5798 pseudo-header checksum form only with checksum rfc5798-compatible, because that is what keepalived (proven on the wire: its own adverts use it) and the rest of the deployed base compute and require
  • a message-only advert is rejected by them as "Invalid VRRPv3 checksum". On receive, a group so configured accepts only this form, and a default group sends and accepts only the RFC 9568 message-only form.
What the ledger says remains

RFC 9568 Section 5.2.8 clarifies the IPv4 checksum as message-only (no pseudo-header), and that is what a ze VRRPv3 IPv4 group sends and accepts by default. A group configured checksum rfc5798-compatible sends and accepts only the RFC 5798 pseudo-header form instead, which keepalived and the pre-RFC 9568 deployed base require.

Enrolled 2026-09-01: rfc/short/rfc5798.md declares 85 requirements, 59 of them MUST-level, and every one carries a {superseded} marker naming where RFC 9568 states it. 45 of those 59 are proven under RFC5798 ids in both polarities. 4 carry a positive test and a {single-polarity} annotation, because the producer writes a constant no input changes: RFC5798-5.1.1.3-1, RFC5798-5.1.2.3-1, RFC5798-7.2-2 and RFC5798-7.2-4. RFC5798-5.1.2.3-1 is the weakest of those four, because its only evidence is an integration-gated test the privileged QEMU suite runs and ./le rfc record cannot reach. 3 are met below ze and carry a {lower-layer} annotation: RFC5798-5.1.1.2-1 and RFC5798-5.1.2.2-1, where Linux consumes a link-local scope multicast datagram rather than forwarding it, and RFC5798-7.4-1, where Linux derives each device's Interface Identifier. 2 are conditional on an optional feature ze declined and carry a {feature-declined} annotation: RFC5798-8.4.2-1, the VRRPv2/VRRPv3 dual-send flag RFC 5798 Section 8.4.2 makes a MAY, and RFC5798-A.2-1, the Token Ring functional-address mode. 4 are {gap} rows ze owes: RFC5798-6.4.3-4 and RFC5798-8.2.3-1 (no ND Router Advertisement is sent for a virtual router, so there is no option set to configure either), and RFC5798-8.2.2-2 and RFC5798-8.2.2-3 (ze authors no Neighbor Solicitation for a host and installs nothing that sources one from the virtual MAC). RFC5798-8.1.3-1 is met by refusal: ze config verify refuses proxy ARP on any interface an IPv4 VRRP group uses (validateNoProxyARP, internal/plugins/vrrp/proxyarp.go), because the kernel would answer with the device MAC. 1 carries a {partial} annotation: RFC5798-7.1-3, the Section 7.1 discard of an advertisement the IPvX address owner receives, is met and tested only in an IPv4 group configured checksum rfc5798-compatible, whose owner discards it (onPacket, internal/plugins/vrrp/instance.go).

The discard is IPv4-only: an IPv6 owner, and an IPv4 owner in a group in the default RFC 9568 mode, follow RFC 9568 erratum 8298 instead, which logs the advertisement and processes it, so that part of the RFC 5798 obligation stays unmet for them. One RFC 5798 obligation is NOT a restatement: RFC5798-5.2.8-1 puts a pseudo-header under the checksum for both address families, which ze computes for IPv4 only in a group configured checksum rfc5798-compatible. RFC 5798 Section 5.2.8 cites the pseudo-header "as defined in Section 8.1 of [RFC2460]", an IPv6-only shape, so what ze and the deployed base compute for IPv4 is the classic IPv4 pseudo-header (pseudoSumV4, internal/plugins/vrrp/packet/checksum.go) rather than the shape that sentence names.
