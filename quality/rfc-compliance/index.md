# RFC Compliance Report

How far Ze meets each RFC it implements, and the tests that check it. Source: `internal/le/rfc`, `rfc/short/*.md`, and `rfc/audit/*/*.json`.

## How to read this page

This page shows how far Ze meets the standards (RFCs) it implements, and how that is tested. For each RFC, Ze keeps a summary of the requirements identified so far and links them to their tests. Automatic checks read those summaries and tests, and the figures on this page are computed from the same summaries and tests.

If you are evaluating Ze for one role, start with Coverage by profile. To check one RFC, find it in the RFCs included in automatic checks table and open its own page, which lists each requirement and the tests behind it. The glossary below explains the results and notes the corresponding terms in Ze's source.

- **Summary**: Ze's file for one RFC: it lists the RFC's requirements, the tests behind each one, and the support status Ze publishes for the RFC.
- **Requirement**: one obligation an RFC states, kept in the summary with an identifier such as RFC4271-8.2.2-12 that names the RFC and its section.
- **MUST-level (mandatory)**: a requirement stated with MUST, MUST NOT, REQUIRED, SHALL, SHALL NOT. The optional levels are MAY, NOT RECOMMENDED, OPTIONAL, RECOMMENDED, SHOULD, SHOULD NOT.
- **Included in automatic checks**: an RFC whose mandatory requirements are checked against its summary and tests. Other RFC summaries are listed at the end of the page with the reason they are excluded. The repository calls this enrollment.
- **Automatic compliance check**: the check reads RFC requirement summaries and tests to find missing evidence or unsupported claims. The repository calls it a gate.
- **Positive and negative test (polarity)**: a positive test checks that Ze does what the requirement demands; a negative test checks that Ze refuses what the requirement forbids. Tested both ways means both exist.
- **Test linked to a requirement**: one test that names the requirement it checks in a source annotation. One requirement can have several tests.
- **Recorded fault test**: evidence that a test can detect a fault: the code under the test was broken once on purpose, the test was seen to fail, and a record stores what the test, its claim and the code looked like. The break is not run again. Ze's source calls this a discrimination record.
- **No fault test recorded**: a test record states that no deliberate code change could demonstrate the test failing. The source calls this escaped, and it does not verify that the test can detect a fault.
- **Outdated fault test**: a test, its stated claim, or the code it checks has changed since the fault test was recorded. The source calls this lapsed, and the fault-detection check is no longer current.
- **Gap**: a requirement the summary openly declares Ze does not meet yet. Every gap is work Ze owes.
- **Annotation**: a note on a requirement, written in braces, that says why it needs no ordinary pair of tests. {single-polarity}: the requirement admits no counter-case, so one direction plus a recorded reason is the complete test coverage required. {not-applicable}: the obligation does not bind Ze. {feature-declined}: the obligation applies only to a feature the RFC makes optional and Ze does not offer. {lower-layer}: a layer under Ze performs the behavior, on state Ze installs into that layer. {gap}: a declared gap. A partial requirement has tests for part of it; the rest is unmet or unverified and earns no credit.
- **Linux cannot do this**: a verified kernel limitation prevents the required primitive. The annotation names the Linux Limitations Register entry. The row is OS blocked: a limit of the kernel, never counted against Ze, so it sits with the rows not owed and in no section of the MUST bar.
- **Requirements reviewed**: a reviewer read the original RFC sentence by sentence and checked the requirement list against it. The review record documents that check. Requirements not reviewed means that this check has not been completed, so the RFC is excluded from the coverage figures.
- **Excluded sentence**: a sentence of the RFC that the review decided not to turn into a requirement, with a kind and a reason.
- **Test review**: a reviewer's recorded judgment of whether the tests check what the requirement says. Fresh means still current. Shifted means the test is unchanged and only the surrounding file moved. Stale means the reviewed code or requirement changed.
- **Ze verified, Ze MUST verified (bar segment)**: a MUST row Ze's own code performs, with a tagged test whose recorded break was seen to fail.
- **OS verified (bar segment)**: a row a layer under Ze performs (the Linux kernel Ze ships, or a Go library Ze links), with a tagged test that checks that layer's behavior on the state Ze installs, and a recorded break.
- **Tests awaiting verification (bar segment)**: a row with a tagged test and no recorded break checking fault detection, that neither the summary nor a test review says Ze does not meet.
- **OS testing gap (bar segment)**: a row a layer under Ze performs, with no verified test of that behavior yet. It is a gap in testing, not in correctness.
- **Exclusion unchecked (bar segment)**: a row claimed not to bind Ze whose evidence is still to be checked. Until it is, the row stays among the rows Ze owes.
- **Not assessed (bar segment)**: a row no tagged test covers and that neither the summary nor a test review says Ze does not meet, so nothing yet says whether Ze meets it.
- **Not built (bar segment)**: a row the summary or a test review says Ze does not meet, including a row built only in part.
- **SHOULD verified (bar segment)**: a SHOULD or MAY row Ze's code performs, with a tagged test whose recorded break was seen to fail.
- **Not owed (bar segment)**: a row that does not bind Ze, shown by checked evidence: it binds a role Ze does not fill, it applies only to an optional feature Ze does not offer, or Linux cannot provide its primitive (OS blocked). It is left out of the MUST bar.

## Exclusion disclosure

Not every sentence of an RFC becomes a requirement. This section counts the sentences a review left out, by the reason given, so you can check what was left out and why.

A reviewer reads the original RFC sentence by sentence and decides which sentences become requirements. A sentence left out is recorded with a category and a reason, and is absent from the requirement list. This differs from the Out of scope card above, which counts requirements that exist and carry a {not-applicable} annotation. Across the sign-offs done so far, 4,908 sentences were mapped to a requirement and 2,236 were declined. 2 of those declines are not scope at all: they are obligations Ze OWES, relocated to a named spec, and they are stated apart below.

- `backlog`: the requirements have not been extracted from the document yet; this is work owed rather than a decision
- `blocked`: something outside the summary stops the extraction, and it is named in the reason
- `foundation`: the document defines, registers or describes, and obliges no implementer, so there is no implementation anywhere for a gate to hold
- `non-normative`: the document imposes no MUST-level obligation on an implementation, so there is nothing to gate
- `out-of-scope`: the requirements ARE extracted and the owner decided not to offer the feature for now, so the absence is a scope decision rather than a conformance gap
- `third-party`: a layer under or beside Ze performs the document and Ze holds no Go code for it, so the reason beside this kind names the component that does
