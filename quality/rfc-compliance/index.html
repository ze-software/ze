RFC Compliance Gate Report

How far Ze meets each RFC it implements, and the tests that prove it. Source: internal/le/rfc, rfc/short/*.md, and rfc/audit/*/*.json.

How to read this page

This page shows how far Ze meets the standards (RFCs) it implements, and how that is proven. For each RFC, Ze keeps a summary that lists every requirement the RFC states and links each requirement to the tests that prove Ze meets it. An automatic check, the gate, reads those summaries and the tests, and the figures on this page are computed from the same summaries and tests.

If you are evaluating Ze for one role, start with Coverage by profile. To check one RFC, find it in the Enrolled RFCs table and open its own page, which lists each requirement and the tests behind it. The terms below are used throughout this page; the per-RFC pages and Ze's source use the same terms.

Glossary of the terms this page uses
Summary
Ze's file for one RFC: it lists the RFC's requirements, the tests behind each one, and the support status Ze publishes for the RFC.
Requirement
one obligation an RFC states, kept in the summary with an identifier such as RFC4271-8.2.2-12 that names the RFC and its section.
MUST-level (mandatory)
a requirement stated with MUST, MUST NOT, REQUIRED, SHALL, SHALL NOT. The optional levels are MAY, NOT RECOMMENDED, OPTIONAL, RECOMMENDED, SHOULD, SHOULD NOT.
Enrolled
an RFC whose summary the gate holds Ze to. Summaries that are not enrolled are listed at the end of the page, each with its reason.
Gate, gated
the gate is the automatic check that reads every summary and the tests. A gated requirement is a MUST-level requirement of an enrolled RFC, one the gate holds Ze to.
Positive and negative test (polarity)
a positive test proves Ze does what the requirement demands; a negative test proves Ze refuses what the requirement forbids. Tested both ways means both exist.
Tagged unit
one test that names, in a tag, the requirement it proves. One requirement can have several.
Recorded break
the proof that a test can fail: the code under the test was broken once on purpose, the test was seen to fail, and a record stores what the test, its claim and the code looked like. The break is not run again. Ze's source calls this a discrimination record.
Escaped
a tagged unit whose record claims that no break of the code exists. It is not counted as a proof.
Lapsed
a recorded break whose test, claim or code has changed since it was recorded. It is not counted as a proof.
Gap
a requirement the summary openly declares Ze does not meet yet. Every gap is work Ze owes.
Annotation
a note on a requirement, written in braces, that says why it needs no ordinary pair of tests. {single-polarity}: the requirement admits no counter-case, so one direction plus a recorded reason is the whole proof. {not-applicable}: the obligation does not bind Ze. {feature-declined}: the obligation applies only to a feature the RFC makes optional and Ze does not offer. {lower-layer}: a layer under Ze performs the behavior, on state Ze installs into that layer. {gap}: a declared gap. A partial requirement has tests for part of it; the rest is unmet or unproven and earns no credit.
Linux cannot do this
a verified kernel limitation prevents the required primitive. The annotation names the Linux Limitations Register entry. The row is OS blocked: a limit of the kernel, never counted against Ze, so it sits with the rows not owed and in no section of the MUST bar.
Walked, sign-off
a reviewer read the RFC's own text sentence by sentence and checked the requirement list against it; the sign-off records that review. Not walked means the review has not been done, so no figure is counted.
Excluded sentence
a sentence of the RFC that the review decided not to turn into a requirement, with a kind and a reason.
Semantic verdict
a reviewer's recorded judgement that a requirement's tests enforce what the requirement says. Fresh: still current. Shifted: the test is unchanged and only the file around it moved. Stale: what it judged has changed.
Ze proven, Ze MUST proven (bar segment)
a MUST row Ze's own code performs, with a tagged test whose recorded break was seen to fail.
OS verified (bar segment)
a row a layer under Ze performs (the Linux kernel Ze ships, or a Go library Ze links), with a tagged test that checks that layer's behavior on the state Ze installs, and a recorded break.
OS testing gap (bar segment)
a row a layer under Ze performs, with no verified test of that behavior yet. It is a gap in testing, not in correctness.
Ze correctness gap (bar segment)
a MUST row Ze's own code owes that no recorded break proves yet: a declared gap, a partial row, a row with no proof, or an exclusion whose evidence does not hold. Every one is work Ze owes.
SHOULD proven (bar segment)
a SHOULD or MAY row Ze's code performs, with a tagged test whose recorded break was seen to fail.
Not owed (bar segment)
a row that does not bind Ze, shown by checked evidence: it binds a role Ze does not fill, it applies only to an optional feature Ze does not offer, or Linux cannot provide its primitive (OS blocked). It is left out of the MUST bar.
SHOULD not ever (bar segment)
a SHOULD or MAY row Ze will never support. Only the project owner sets it.
SHOULD not yet (bar segment)
a SHOULD or MAY row Ze intends to support and does not support yet.
SHOULD not decided (bar segment)
a SHOULD or MAY row nobody has decided on yet: every unproven optional row starts here.

The gate holds Ze to every MUST-level requirement of the RFCs it implements. The cards after them say how many tagged tests carry a recorded break and whether the gate passes.

How to read the colors

A color names what the measure MEANS, not how well Ze scores on it. Green is a good outcome at any value, red is a bad one, and neither a population nor a scope count is an outcome, so both take no color. The number under the label is what says how far Ze has got.

Exclusion disclosure

Not every sentence of an RFC becomes a requirement. This section counts the sentences a review left out, by the reason given, so you can check what was left out and why.

A reviewer walks an RFC's own text sentence by sentence and decides which sentences become requirements. One that does not is EXCLUDED, with a kind and a reason, and it never reaches the gated ledger at all. That is a different mechanism from the Out of scope card above, which counts requirements that exist and carry a {not-applicable} annotation. Check results

The gate runs several groups of checks. Each line below says what one group verifies and whether it passed, and for a group that failed, what that means for the figures. The raw findings, written for Ze's contributors, are in the collapsed block after the list.

  • Requirement lists: Passed. Each RFC's requirement list is readable and consistent: requirement identifiers are not reused or lost, each requirement quotes the RFC text it cites, and the links it declares between RFCs and profiles agree with the RFC texts.
  • Test evidence: Passed. Every gated MUST-level requirement has its tests, or an annotation that says why not, test evidence already recorded is not lost, and every test that claims a requirement compiles and is named for what it covers.
  • Requirement annotations: Passed. Every annotation that excuses a requirement from Ze's own tests still names code that exists, quotes the RFC sentence it relies on, or names a verified blocking kernel entry in the Linux limitations register with evidence for that exact requirement at the shipped kernel version.
  • Published ledger rows: Passed. Every enrolled RFC with an unmet requirement renders a public row that discloses it, a public row never disappears while its summary remains, and each summary's enrolment disposition gives a reason a reviewer can check.
  • Reviewer verdicts: Failed, 24 problems. Each reviewer verdict recorded on a requirement is well formed and still describes the code and tests it judged. What this means: A reviewer verdict is malformed or out of date, and that requirement must be reviewed again before the verdict counts.
  • Recorded breaks: Failed, 21 problems. Each recorded break still matches the test, the claim and the code it was recorded against, and no recorded proof is lost. What this means: A test's proof is missing or no longer matches what it rests on, so it is not counted as proven by a recorded break.
  • Reviews of RFC text: Passed. Each sign-off of a sentence-by-sentence review of an RFC's text is valid and current.

Summaries that are not enrolled

RFCs Ze keeps a summary for that the gate does not hold Ze to, each with the kind of reason and the reason itself.

  • backlog: the requirements have not been extracted from the document yet; this is work owed rather than a decision
  • blocked: something outside the summary stops the extraction, and it is named in the reason
  • foundation: the document defines, registers or describes, and obliges no implementer, so there is no implementation anywhere for a gate to hold
  • non-normative: the document imposes no MUST-level obligation on an implementation, so there is nothing to gate
  • out-of-scope: the requirements ARE extracted and the owner decided not to offer the feature for now, so the absence is a scope decision rather than a conformance gap
  • third-party: a layer under or beside Ze performs the document and Ze holds no Go code for it, so the reason beside this kind names the component that does
