Both page-size directives use unformat_log2_page_size: Ze's 2M setting emits default-hugepage, 1G emits 1G, and explicit default emits native base pages. The default remains 2M; no failed allocation changes the requested mode. default-hugepage-size is a separate key in the memory section, not a page-size value. Ze does not emit that key or set the main heap's page size. VPP's main heap therefore retains the upstream OS-page default.

The buffer directive has a space in default data-size; default-data-size is rejected. The Linux netlink directive requires the nl- prefix; rx-buffer-size is rejected. Unit contracts pin the corrected sections, but source matching does not establish native startup. A native run must still prove the installed plugin set, memory allocation, CPU affinity, device access, namespace access and API connection on the deployment host.

startup.conf Syntax

Forwarding features register their additional startup requirements with RegisterStartupFeature. Each declaration supplies its plugin, section flags and the config roots its predicate reads. The registration extends the VPP plugin's ConfigReads; the SDK delivery list derives from the same declarations. ParseConfigSections selects immutable requirements from the delivered candidate, and GenerateStartupConf renders only the selected requirements. The VPP component does not enumerate the forwarding features that consume it.

A feature can also declare StartupRuntime with its generated binary API messages and its own diagnostic code. Registration copies each message's name, CRC and type. The compatibility check reads the message table supplied by the VPP instance on the configured API socket. It therefore tests the loaded plugin's API, including patched layouts, rather than a library on disk.

Each runtime declaration registers a doctor check with the same requirements. An answered API mismatch is an error. A connection that cannot be queried is a warning, because it does not prove a plugin is absent. The check opens and closes its own API client and never starts or stops the VPP process.

When vpp.startup-cli-file is configured for managed VPP, the manager first compares the retained API Unix peer with the supervised child's atomic process descriptor, then executes that exact file once through a synchronous CLI request on the same connector generation. The native reply, stream close, caller context and generation must all succeed before statistics and readiness. Generated startup.conf omits asynchronous unix exec for this setting. Native failure kills and reaps the original child before runOnce returns. The independent retained pidfd observer alone proves physical death; notification may precede reap. External supervision owns its own bootstrap.

The manager checks selected runtime requirements after publishing statistics and before announcing readiness. A refusal closes the statistics owner and the candidate API connection. The plugin's startup callback waits for this answer, so a dependent plugin cannot start against an unchecked connection. Each ready lifetime emits one disconnected event when it ends, including a configuration replacement. A candidate that fails before readiness emits no disconnected event.

Configuration applies use the SDK's existing transaction. The lifecycle cancels and joins the previous manager before starting a replacement, then waits for the replacement's readiness. If the candidate fails after confirmed cleanup, it reinstalls the previous settings before answering the failed apply. Unresolved native cleanup retains the joined original manager and its exact binder receipt instead. The failed apply leaves the transaction broken and starts neither a candidate nor restoration. Each later configuration operation or stop makes at most one retry against that same receipt before admitting a replacement. Confirmed driver restoration clears that custody; an unresolved child-cleanup result remains a separate barrier. If restoration also fails, the transaction retains the original settings for a later retry. Selected startup settings contain immutable requirements; registry predicates are used during selection and do not make equal settings compare unequal.

VPP's startup.conf uses a custom format (not INI, not YAML):

section-name {
  key value
  key value value
  flag-without-value
  nested-section {
    key value
  }
}

String values are unquoted. Multi-word keys such as default data-size and default netns use spaces. The emitted boolean directives are bare flags (present = true); this is not a rule for every VPP option. Dev entries use PCI address as the key with a nested block for per-device options.

Runtime statistics

The VPP manager connects the statistics segment after the binary API handshake and the configured managed bootstrap's successful completion, even when no metrics exporter is configured. It reads interface statistics before publishing the connection and emitting connected or reconnected. Subscriber accounting therefore has the same counter source with or without telemetry. A failed connection or read remains explicitly unavailable; it is never interpreted as zero traffic or idle time. The runtime doctor and health row retain doctor-vpp-stats, with the underlying failure in show warnings. An unavailable statistics segment does not restart an otherwise usable VPP API.

A session retains its binary API connector and connection generation. InterfaceCountersForGeneration accepts only the statistics connection published for that pair and checks the generation again after reading. A replaced VPP process cannot answer an older session's counter request. Statistics reads are serialized because GoVPP updates cached statistics directories. When telemetry is configured, its one poller uses that same owner. Shutdown cancels and joins the poller, withdraws the statistics publication and disconnects it before closing the binary API connection. A success clears only the same live owner's statistics category, and a confirmed new statistics connection clears its own connection failure.

Per-session counters come from one shared snapshot, not one dump per session. InterfaceCountersForGeneration answers one interface index from the statistics owner's latest dump, indexed by interface, and takes a new dump only when that one started before the caller's freshness bound. Reading every subscriber within one interval therefore costs one dump and one lookup per session. A fresh read (the bound set to the call time) still shares the one dump that starts after it, with every other fresh read waiting behind it. The snapshot belongs to the statistics owner of one API generation, and every answer re-checks that generation, so a replaced VPP process never answers from it. A request with no bound is refused, a failed dump discards the snapshot so the failure reaches the next caller, and a missing or duplicated interface row is an error.

DPDK Bind Sequence (vfio-pci)

Ze loads vfio, vfio_pci and vfio_iommu_type1, then handles only the configured PCI addresses:

  1. Read the current driver symlink. An already-vfio device remains borrowed; Ze does not acquire custody of its existing attachment or override.
  2. Read the exact original override from driver_override_raw when available, otherwise an unambiguous legacy driver_override, and retain both original values in the binder's process-local receipt. An empty original driver is meaningful state.
  3. Unbind the original driver when present, select vfio-pci in that device's driver_override, then write that exact PCI address to /sys/bus/pci/drivers/vfio-pci/bind. Verify the resulting driver.
  4. On teardown, detach only the owned VFIO attachment. If an original driver existed, temporarily select it in driver_override and bind the exact address to it. Restore the original override after the driver is restored. An originally driverless device remains driverless.

Every retry reads the same device's actual driver and override. A completed detach, driver bind or override write is not repeated. The receipt is removed only after complete restoration; failed native calls remain wrapped causes. A failed later input preserves both its primary error and any failed rollback. No on-disk recovery journal or native hardware restoration proof is implied by the portable operation-table tests.

Only absence of driver_override_raw allows legacy fallback. A failed raw read keeps its original cause, while a legacy (null) is refused before device mutation because it does not identify the original override. The reader removes only one final newline; spaces, tabs and carriage returns remain policy bytes. Restoration writes a nonempty value without an added newline and clears an unset override with exactly one newline. An ambiguous legacy host needs a kernel that provides the raw getter before Ze can bind the NIC.

The configured-device doctor check uses the binder's same read-only original state capture. It skips missing devices and borrowed VFIO attachments, reports capture failure with its original path and cause, and changes no device state. Portable file and operation-table controls do not establish raw-getter kernel support or physical NIC restoration.

The earlier vendor/device-wide new_id path could attach an unconfigured matching driverless NIC: Linux v7.3 do_pci_add_dynid calls driver_attach, which walks every bus device and attempts matching probes. Removing that ID does not detach those devices. Ze therefore uses per-device override and exact bind, with no new_id, remove_id or bus rescan. The pinned consumers are PCI dynamic IDs and override matching, driver attachment, exact-address bind and override attribute, and the PCI sysfs ABI.

The manager classifies an expected kill from the original command's actual reaped ProcessState, never from an error string or cancellation alone. A separate failed native cleanup remains a typed cause and stops child restart. Deferred DPDK restoration errors are joined into the terminal manager result. The independent retained-pidfd observer still supplies physical process-exit proof; neither cancellation nor that proof alone confirms NIC restoration.

Mellanox RDMA Exception

mlx5 NICs use bifurcated driver mode. The kernel mlx5_core driver stays loaded. VPP creates the interface via create interface rdma host-if <pci-addr> instead of a DPDK dev entry.

This means:

  • No vfio binding step
  • No driver save/restore
  • DPDK section in startup.conf does NOT include mlx5 devices
  • Interface creation uses GoVPP RdmaCreate API instead of DPDK auto-discovery
  • Performance is equivalent to DPDK for mlx5

This describes VPP's general Mellanox handling. Ze's own VPP integration does not yet implement RDMA/mlx5 interface creation (there is no RdmaCreate call in the codebase); this section is background for a future deployment path.

TAP Interface Naming

LCP creates TAPs with VPP's interface name, truncated to Linux's 15-char limit. TenGigabitEthernet3/0/0 becomes a truncated name. vppcfg uses short names. Ze's naming module (vpp-4 spec) handles bidirectional mapping.

Network Namespace

All LCP TAPs are created in the dataplane netns. This isolates the forwarding plane from the management plane. Ze's BGP reactor, SSH, web UI all run in this netns.

Ze's interface backend exposes actual pair readback through iface.LCPPairReader.GetLCPPair. The caller MUST first resolve the device through that backend's link read. Exact VPP link readback records the native name and index without replacing the configured logical name used by interface events. Pair lookup reads this existing native identity directly, then uses an owned context-bound stream; it never starts the shared channel's lazy interface dump. An unresolved name is a failed lookup, not proof that a pair is absent. The targeted lcp_itf_pair_get_v2 exchange must contain one details message and its explicit final reply, with matching identity and the configured global namespace.

GoVPP Connection

Resource owners capture Connector.ConnectionGeneration when they acquire VPP state and use NewStreamForGeneration for later operations. The epoch changes on successful connection publication and every close. Checking it and selecting the connection share the connector mutex, so a retained session or LCP-map lease cannot send its cleanup to a replacement connection through the same connector object. Each returned stream remains the caller's resource and must be closed.

Socket Transport

GoVPP connects via Unix socket at /run/vpp/api.sock. Pure Go, no CGo.

Ze uses synchronous core.Connect, with at most ten attempts separated by one second when the manager starts a connection. Each successful connection owns one health worker. A failed bounded control-ping probe invalidates the published generation before notifying the manager. Closing the connector cancels and joins that worker. GoVPP's AsyncConnect is deliberately avoided: its internal redial could otherwise replace the underlying socket while Ze still held an older generation. Existing streams must remain tied to their original Unix connection.

A stream context does not interrupt GoVPP's native Unix socket write. Bounded shutdown also requires the retained govpp-socket-bounded-close.patch. Its separate deadline mutex prevents an ordinary writer from extending or clearing the shutdown deadline, while the client-delete handshake remains allowed. A failed partial write closes that connection before another request can use it. Apply the diff to the vendored module through ./le setup install before claiming this native shutdown bound. The public-adapter tests in govpp_socket_transport_test.go exercise a real Unix peer that withholds reads, concurrent sends during disconnect, and the healthy client-delete request.

On API loss, the manager kills and waits for the exact VPP child it supervised before returning or restarting. Managed startup obtains an owned process descriptor atomically with child creation (SysProcAttr.PidFD) and compares its pidfs identity with the actual API socket peer before the startup CLI barrier, statistics and readiness. Other process attributes remain intact. A claimed PID has no authority, including across PID namespaces.

Statistics capture the actual Unix socket that transfers the mapped segment, disable automatic socket replacement, and retain that peer. API and statistics must name the same live pidfs device and 64-bit inode before any initial read, before atomic provider installation under the original connector lock, and before and after subsequent reads. A different statistics process refuses readiness. Unsupported or unknown physical identity refuses with a diagnostic; neither a pathname, integer PID nor boot timestamp repairs it.

The manager disconnects statistics before closing its original API transport. A late old child wait cannot close a newer generation. A completed wait alone never publishes ProcessExit: the retained physical witness is the sole notifier and requires kernel-confirmed whole-process exit. Notification may precede the original child's reap; the manager still joins that child before runOnce returns. Retained ProcessLease owners validate the sealed exact physical proof before releasing obligations. Covers checks the logical epoch only and cannot replace that validation.

One bounded worker covers each retained API lifetime, including after its manager disconnects. Owners retain a lease before their first native mutation and keep it through unresolved cleanup. Ordinary Close releases its mutex before joining final descriptor cleanup; a notification uses nonjoining Retire. A proof also covers other retained epochs of the same physical process, but cannot retire a live foreign peer. Observation failure remains unknown. At most 1,024 physical API lifetimes and 131,072 references per lifetime are retained; no reconnect history accumulates. ze doctor probes the actual socketpair/pidfs capability, and doctor-vpp-process retains observation and descriptor-close failures. The server must create its own listeners: inheriting another process's listener does not change its original kernel peer owner.

External mode also observes API loss and retries its connection through the manager's backoff loop. Its supervisor is external: Ze neither kills that process nor treats an API failure as proof of process death. Owners must retain unresolved native state until its own ownership or absence is confirmed. The owner decisions of 2026-11-23 ("Design decisions" below) replace this behavior: Ze refuses to run VPP unmanaged. A failed alive test declares the loss; when the reconnect-and-verify limit that follows expires with no same-process VPP answering with its configured data, Ze kills the VPP through the retained pidfd, waits for the exit proof, and restarts and reconfigures it. That is not built yet; its implementation is owed by plan/post-release/features/spec-vpp-failure-lifecycle.md.

What VPP Does NOT Provide

  • No routing protocols (BGP, OSPF, IS-IS). Ze's job.
  • No firewall (nftables/iptables bypassed). VPP ACLs are basic match/action.
  • No hierarchical QoS. VPP policers are flat token buckets, not HTB/HFSC.
  • No kernel features on fast path (tc, XDP, conntrack, eBPF).
  • DPDK/RDMA NIC drivers only (not all hardware supported).
  • Minimum 4 physical CPU cores, 8 GB RAM.
