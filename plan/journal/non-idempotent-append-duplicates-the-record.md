# Non-Idempotent Append Duplicates The Record

A writer appends a row without testing whether the file already holds it, so a
second run of the same step records the same fact twice.

| Date | Spec | Surface | Symptom | Fix |
|------|------|---------|---------|-----|
| 2026-08-19 | - | commit_helper.py, verification-debt shard | `record_debt` (the retired `scripts/dev/commit_helper.py` (current producer: `internal/le/commit/prepare.go`)) appends one row per owed gate and never tests whether the shard already carries that row, so a second `create` for the same session, subject and gate writes it again. Measured on commit `d0ddef174`: two `create` runs left four rows in `plan/verification-debt/aabf4645.md` where two were owed. The first run was killed at a 2-minute timeout after it had appended, and `--replace` on the same commit would do the same | not fixed. The two duplicate rows were deleted at owner request; the append is still non-idempotent |
| 2026-08-19 | - | commit_helper.py, verification-debt shard | Second occurrence of the row above, the same day, by the route that row predicted. `create --replace` rewrites the script and appends the debt rows a second time. `record_debt` (the retired `scripts/dev/commit_helper.py` (current producer: `internal/le/commit/prepare.go`)) opens the shard with mode `a` and tests nothing. Commit `2f2eb832b` owes 2 gates and `plan/verification-debt/f8bfdd86.md` holds 4 rows. The inflated count reaches the session-start banner. It also refuses `--push` until each duplicate is cleared, which re-runs one gate twice | fixed for the class, both routes. `record_debt` reads the shard under the lock it already takes and skips a row the shard holds OPEN. A cleared row is spent, so a later commit owing the same gate earns a fresh one. The first sizing of this fix was wrong. It called deduplication large because `open_debt_rows` makes the line position a row's identity. That guard is about clearing rows which already exist, not about appending. The two never met. That docstring also claimed one `create` can render two identical rows. `DEBT_FLAGS` and `debt_owed` make it impossible. The false claim made the duplicates look expected. Three tests in the retired `scripts/dev/commit_helper_test.py` (current producer: `internal/le/`), and the duplicate rows already in `plan/verification-debt/f8bfdd86.md` are untouched |
| 2026-08-29 | - | `./le commit create append` and the message file it names (`Create`, `internal/le/commit/prepare.go`) | The message path is derived from the TAG alone, `tmp/commit-msg-<session>-<tag>.txt`, and every block in a script names that one path in its `git commit -F`. `/ze-close` prepares two commits by calling `create replace` and then `create append`, so a closure that gives both blocks the same tag has the SECOND message overwrite the first and makes both commits with the closing text. Nothing looks wrong: the script holds two blocks with two subjects in their comments, and each block's `-F` path is correct for the file that path now holds. Found by reading the generated script before running it. Reading it afterwards would not have shown it either, because commit A would simply carry commit B's message | not fixed here, and worked around by giving the two blocks different tags, `plan` and `plan-close`, so each has a message file of its own. The fix is for the message path to carry the BLOCK rather than the tag, so a second block cannot name the first's file. Until then a two-commit closure script needs two tags, and the generated script must be read before it is run |
