# A counter is placed where it sees a wider population than its name

A counter sits before the test that selects what it is supposed to measure, so
it counts everything that reached the code path rather than everything the path
selected. The value has a producer and it moves, which is what makes it hard to
see: nothing is zero and nothing is a literal. The tell is two counters that
name different populations and always report the same number.

| 2026-09-14 | gtsm-related-icmp-ttl | firewall nft backend | The same `applyChain` prepend, met again while proving RFC5082-3-2. A GTSM drop proof read one term's counter as "this rule matched", and every one of the ten rules ze published reported `Packets:0x1, Bytes:0x38` for a single injected ICMP error, including the four type-4 and type-5 rules the packet could not match. The first draft of the receive proofs therefore passed on a value that would have read the same with no matching rule at all. The tests now read the kernel's own `IcmpMsg InType3` for delivery, and use the counter only for what it truthfully answers: the LAST rule with a non-zero count is the rule that matched, because a verdict ends the evaluation and every rule after it stays at zero | fixed 2026-09-20. `applyChain` now inserts the counter at the term's match/action boundary (`loweredRule.withCounter`, `internal/plugins/firewall/nft/lower_linux.go`), so a rule whose match fails counts nothing and the ten-rule reading above cannot happen again. The receive proofs keep their `IcmpMsg InType3` reads, which answer a question a counter never did. This is the SAME defect as the 2026-09-08 row below, met from an unrelated feature, and one fix closed both |
| 2026-09-08 | policyroute-interface-list-matches-no-packet | firewall nft backend | `applyChain` (`internal/plugins/firewall/nft/backend_linux.go`) prepends `&expr.Counter{}` to the front of a rule's expression list, before the expressions `lowerTerm` produced for the term's matches. nftables evaluates a rule's expressions in order, so the counter increments for every packet the CHAIN sees and not for the packets the term matched. `readRuleCounter` then reads that first counter and `show firewall ruleset` reports it as the term's own packets. Measured in a QEMU guest: a policy naming `lo` and `dummy0` with one `tcp dport 2222` rule, driven by a loopback SSH connection, printed `counter packets 3 bytes 120` on BOTH kernel rules, so the `dummy0` rule reported the 3 packets that only the `lo` rule matched. An operator reading the ruleset to learn which interface carries the traffic gets the same number for every interface | fixed 2026-09-20. `lowerTerm` now returns each rule with the index where the term's actions begin, and `applyChain` inserts the counter there: after every match, ahead of every action, so it never sits behind a verdict or a nat statement that would end the rule before it ran. Proof: `TestNftIntegrationCounterCountsOnlyTheTermsOwnPackets` (`internal/plugins/firewall/nft/counter_integration_linux_test.go`) reproduces this row's measurement against a real kernel, two terms on `lo` and a dummy, traffic on `lo` only, the dummy term asserted at zero with the `lo` term as the positive control; `TestLowerTermCounterSitsBetweenTheMatchesAndTheActions` (`lower_linux_test.go`) pins the expression order. This is the SAME defect as the 2026-09-14 row above, recorded there from the GTSM feature, and one fix closed both |
| 2026-09-15 | gtsm-related-icmp-ttl | `icmpInType`, `tcpMinTTLDrop` (`internal/component/gtsm/gtsm_rfc5082_linux_test.go`) | The tagged receive proofs read `/proc/net/snmp` and `/proc/net/netstat` from a goroutine whose LOCKED thread unshared a network namespace (`newTestbed`). `/proc/net` is `/proc/self/net`, and `/proc/<tgid>/net` answers for the thread-group LEADER's namespace, so the counters are the host's unless the test happens to run on the main thread. On this Linux host under `sudo`, `TestGTSMDeliversAQuotedICMPErrorAtTTL255` read 7133 type-3 messages in a namespace seconds old and failed, `TestGTSMDeliversAnICMPErrorNoSessionClaims` and `TestGTSMMinHopCountDropsALowHopLimitICMPv6Error` failed the same way, and `TestGTSMDropsADangerousQuotedICMPError` passed because a no-change assertion holds against the wrong namespace too. The discrimination records were observed in a container where the read happened to answer | fixed in the closure: both reads go through `/proc/thread-self/net/`, which resolves to the calling thread, and `procNetColumn` says why. The tagged units' fingerprints did not move (the helpers are not part of the unit hash), so `./le rfc discriminate stem rfc5082` lists no stale record |
