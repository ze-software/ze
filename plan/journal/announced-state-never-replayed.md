# A peer is announced to a consumer whose copy of that peer's state is empty

| Date | Spec | Surface | Symptom | Fix |
|------|------|---------|---------|-----|
| 2026-08-31 | rfcgate-6-supported-extraction-signoff | `internal/component/bgp/plugins/bmp` -- `primeSender` and `BMPPlugin.bounceMonitoredPeers` vs `senderSession.writeRouteMonitoring` | A BMP collector is told a peer is up and is never given that peer's routes. The only Route Monitoring producer for an Adj-RIB is the live update path, `handleStructuredEvent` -> `writeRouteMonitoring`; the two other call sites are both Loc-RIB replay in `bmp_locrib.go`. `primeSender` sends a Peer Up and stops. So a collector that attaches to a running ze, or one whose peers were bounced by the RFC 8671 Section 7.2 config-change sequence, holds nothing for each announced peer until that peer sends its next UPDATE, which on a stable session can be hours. RFC 7854 Section 4.9 gives a Peer Down the meaning "withdraw everything you hold for this peer", so the bounce is a withdraw with no matching announce. Found by review round 4, which read the comment on `bounceMonitoredPeers` saying the collector "re-learns each peer under the new configuration" and looked for the producer that would make it true | comment corrected to say what the code does, defect recorded not fixed. It predates the peer bounce and is not that change's regression: the transport drop the bounce replaces ended in the same empty state, because a reconnected collector was primed the same way. It blocks no goal of this spec, whose subject is the extraction sign-off gate. What an operator loses is the Adj-RIB-In half of BMP: Loc-RIB monitoring replays correctly, pre-policy monitoring is silently empty until traffic arrives |
