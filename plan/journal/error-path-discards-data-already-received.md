# Error path discards data already received

A reader that stores a terminal error and a consumer that checks that error
before the queue are two correct halves of a broken whole. The last bytes a peer
sent arrive, get queued, and are then dropped in favour of the EOF that followed
them. The loss looks like a peer that never sent the data, so it is diagnosed on
the wrong side of the connection. Ask, of every error check placed above a
receive: what is already in the queue when this returns?

| 2026-09-05 | commit-end-reports-what-each-peer-took | `answerValue` (`pkg/plugin/sdk/sdk_engine.go`), reached by `(*Plugin).DispatchCommand` for every plugin that drives a command over the socket | It calls `rpc.CollapseAnswer` first, so the answer's records are already rebuilt into a document. It then reads the terminator, and when the terminator carries a message it returns that message as a Go error with a NIL document. So a command that answers with a failure AND a payload loses the payload at this boundary: the plugin sees the sentence and nothing else. The engine side supports the pair, and `quiesceAll` (`internal/component/plugin/server/quiesce.go`) already writes one, answering `StatusError` naming the failed subsystems while `Data` lists every subsystem asked. The in-process bridge loses it the same way for the same reason: `dispatchCommandResult` returns `(out.Status, nil, errors.New(out.Error))` whenever `out.Error` is non-empty, discarding the `out.Data` it holds. So both transports agree, and both agree on dropping half of an answer the engine composed | not fixed. It is one line in the SDK and its blast radius is every plugin that reads an error answer, which is wider than the reporting spec above and is not what that spec exists to change. That spec works around it by stating each refused peer and its reason in the error sentence, so the sentence alone carries the facts |
| 2026-08-19 | streaming-answer-protocol | plugin rpc framing | `readFrame` (`pkg/plugin/rpc/conn.go`) opened with a fast path returning `readerErr` when the persistent reader had stopped. Its `readerDone` branch did the same. The reader stores that error one read AFTER it pushed a frame into the capacity-1 `frameCh`. So a peer that wrote its last line and closed the connection lost that line. Every caller was affected. A `CallRPC` whose peer answered and exited at once got `EOF` instead of its answer. A streamed answer lost its last records and its terminator, which is the failure the spec exists to prevent | fixed: the fast path is gone. The `readerDone` branch calls `queuedFrame`, which takes a queued frame before it reports why the reader stopped. `TestAnswerWithoutTerminatorReportsTruncation` (`pkg/plugin/rpc/mux_test.go`) drives a peer that writes a head and one record and then closes. It asserts the record is delivered and the answer reads as truncated. It fails on the old code with zero records delivered |
| 2026-09-05 | commit-end-reports-what-each-peer-took | `responseToDispatchOutput` (`internal/component/plugin/server/dispatch.go`), reached by EVERY dispatch path, not only the SDK | Correction to the row above, which named `answerValue` as the boundary and is understated by one layer. `responseToDispatchOutput` copies `resp.Status`, then returns early on `if resp.Error != ""` and never reaches the `json.Marshal(resp.Data)` below it. So `DispatchCommandOutput.Data` is nil for every command that answers with an error, before the SDK is involved at all: the engine composes a payload beside its error and the FIRST layer above the handler deletes it. `answerValue` then discards the collapsed document a second time, and `dispatchCommandResult` a third for the in-process bridge. | 2026-09-08 | commit-end-reports-what-each-peer-took | `(*Server).dispatchCommandResponse` (`internal/component/plugin/server/dispatch.go`), one layer ABOVE the two the rows above name | Both rows above conclude that the error SENTENCE is the one field that survives. An error answer therefore loses its Error field as well as its Data, at a FOURTH layer.
