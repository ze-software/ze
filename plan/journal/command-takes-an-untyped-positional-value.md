# command-takes-an-untyped-positional-value

`ai/rules/cli.md` requires a closed keyword before any user-supplied value. A
free-form value therefore never sits in an untyped positional slot, where it can
collide with a keyword. Peer commands are the one stated exception: a peer is
addressed by name or by address with no selector keyword before it, as in
`show bgp peer 192.0.2.1 detail`.

| 2026-08-24 | cli-show-bgp-answer-shapes | bgp plugin command grammar | Five `show bgp` commands take a free-form value in an untyped positional slot, and none is a peer command. The stated exception does not reach them. `handleShow` (`internal/component/bgp/plugins/healthcheck/healthcheck.go`) reads `args[0]` as a probe NAME. `aspaCommand` (`internal/component/bgp/plugins/rpki/rpki.go`) reads `args[0]` as a customer ASN. `roaCommand` reads `args[0]` as a prefix. `rpfLookup` (`internal/component/bgp/plugins/rib/rib_commands.go`) reads `args[0]` and `args[1]` as a family and an address. `showIRRCheck` (`internal/component/bgp/plugins/filter_irr/command.go`) reads `args[1]` as a prefix. The correct spellings carry a selector keyword: `show bgp healthcheck name <name>`, `show bgp rpki aspa customer <asn>`, `show bgp rpki roa prefix <prefix>`, `show bgp rib rpf family <family> address <addr>`. Two of them also make the answer change SHAPE with the argument, which is what surfaced them. `show bgp healthcheck` and `show bgp rpki aspa` answer a row set with no argument and one object with one argument, so no declared shape can describe either. `CheckSiblings` and `CheckRootNamespace` (the retired `scripts/checks/cli_grammar.go` (current producer: `internal/le/cligrammar/cligrammar.go`)) both judge NAMESPACE rather than selector typing, so no gate reads this. Whether a gate deliberately excludes plugin-declared `Args` was NOT checked | not fixed. It blocks no acceptance criterion of the spec that found it. `spec-cli-show-bgp-answer-shapes` and `spec-plugin-declares-answer-shape` make each answer one shape, and a one-shape answer is what a declaration needs whatever the argument spelling. Renaming a shipped command path is a dispatch-key change with backward-compatibility and `.ci` sender obligations of its own (`ai/rules/cli.md`, "Migrating a Built-in Command's Path"). That rename therefore needs its own spec rather than a branch inside one about declarations |
| 2026-08-30 | generated-command-usage | `announce` command grammar | The model declares `announce` as taking one mandatory `selector` leaf (`internal/component/bgp/plugins/cmd/announce/yang/ze-cli-announce-cmd.yang`), so the generated usage line reads `announce <selector>`. `handleAnnounce` (`internal/component/bgp/plugins/cmd/announce/announce.go`) reads `args[0]` as the FAMILY word and switches on `unicast`, `blackhole` and `flowspec`; the peer selector arrives out of band, from `ctx.PeerSelector()`, which `applyExtractedSelectors` fills from `ctx.Selectors[selectorLeaf]`. `docs/guide/configuration.md` documents `announce unicast 192.0.2.1/32 community 65001:666`, with no selector token. The three forms take three different argument grammars, which is why the authored sentence spelled the rest `<args>` | not fixed. `spec-generated-command-usage` declared `announce` its one permitted residue on the reading that the model cannot state a route specification. | 2026-09-04 | fixit-selector-narrows-through-a-pipe | `peer raw`, `peer update` and `request commit` command schemas | The schema declares the selector and nothing else, while the handler reads operator-typed positional arguments the model never states. `container raw` (`internal/component/bgp/plugins/cmd/raw/yang/ze-raw-cmd.yang`) declares `leaf selector` alone; `handleRaw` (`internal/component/bgp/plugins/cmd/raw/raw.go`) reads `[<type>] <encoding> <data>` from `args`, and its own doc comment is where the grammar is written down. `container update` (`ze-update-cmd.yang`) declares `leaf selector` alone; `update_wire.go` and `update_text.go` parse a whole route expression from `args`, keyword by keyword. `container commit` (`ze-cli-commit-cmd.yang`) declares NO leaf at all; `handleCommit` (`commit.go`) reads `<action> <name> [args]`, and the grammar sits in an `ze:help` sentence. So the command model, the completion surface and the generated help text do not know those arguments exist, which is the same shape as the 2026-08-30 `announce` row above and the answer that row records: one `ze:command` per form, each stating its own arguments. Width measured, not assumed: ten non-test files both take a `pluginserver.CommandContext` and index `args` past the first element, and three of them carry the shape. The other seven were not each checked, so three is a floor | not fixed. It blocks no acceptance criterion of the spec that found it: `spec-fixit-selector-narrows-through-a-pipe` moves `raw` and `update` under `request peer`, which changes where the command lives and not what its schema declares. Declaring the arguments is a command-surface change with `.ci` and help-output obligations of its own (`ai/rules/cli.md`), and `announce` shows the shape of the work: `withdraw` was split into three `ze:command` nodes before each could state its arguments |
