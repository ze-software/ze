| 2026-08-22 | - | `TestWriteAnswerUsesPooledBuffer`, `TestWriteAnswerReleasesBufferOnError` (`internal/component/plugin/dispatch_test.go`) | A test proved a pooled buffer's round trip by state. It put a marked buffer into the `sync.Pool`, wrote one answer, then asked the pool again. It passed alone and failed one run in three for the whole package under `-race`, on a different subtest each time, with the returned buffer full of zeros. A `sync.Pool` is per-P and its private slot cannot be stolen. A goroutine the scheduler moves between the release and the next Get therefore reads an empty pool, through no fault of the writer. A pool of its own did not fix it, and neither did `debug.SetGCPercent(-1)`. The scheduler owns which P answers, so no state read of a pool says anything about the code that used it. Found in phase 2 of spec-record-answers-3-zero-alloc | measured the answer's ALLOCATION COUNT instead, with `testing.AllocsPerRun`. It pins GOMAXPROCS for its runs and truncates its average to an integer. A buffer the writer allocates, or fails to return, then reads as exactly one more, and a stray collection reads as nothing. Five of five whole-package runs under `-race` were green after the change. The race detector allocates on its own account, up to two on these answers, so the ceilings are exact on the pass without it and `answerAllocRaceOverhead` gives the changed-group pass that slack |
