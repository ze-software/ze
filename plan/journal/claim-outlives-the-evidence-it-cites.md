# Claim outlives the evidence it cites

The mirror of `ephemeral-record-stored-permanently`. A claim is written where it
survives, and the evidence it rests on is written where it does not. Nothing
breaks at the moment the evidence goes: the claim still reads as authority, still
names a path, and the reader who follows that path finds nothing. The claim is
then worse than no claim, because it costs a reader the time to discover it is
empty and it discourages the work of re-establishing what it asserted.

The general practice is that a claim and its evidence want the same lifetime. Where
that is impossible, the claim carries enough to be re-checked without the artifact,
or it is not recorded until the moment it is preserved.

| 2026-08-22 | - | spec Review Gate section against `tmp/review/` | The Review Gate table records a verdict, the round count, the lenses used and the path of the artifact that pins the reviewed files by hash. The table lives in the spec, which is tracked. The artifact lives under `tmp/`, which is cleaned on a cadence. A spec that records a clean verdict and does NOT close in the same session therefore keeps a citation that expires, and the hashes expire with it, so nothing about the recorded verdict can be re-checked. Two specs met this on one day: each read `clean` or `findings`, each named an artifact that no longer existed, and each cost a full independent re-review to close. The gate itself is sound: `commit_helper.py` requires the artifact at closure-commit time, so a spec that closes in the session that reviewed it is never exposed | not fixed. The narrow repair is to treat a recorded verdict as valid only for the session that recorded it, which is what the two-commit closure rule already assumes: a verdict is written when the closure commit is about to carry it, never in advance of one. The wider repair would give the artifact the lifetime of the claim, and that is a decision about where review evidence belongs rather than a defect in the gate |
| 2026-08-24 | fixit-stored-route-relay-hardening | a spec naming functional tests by their POSITIONAL id in a suite | The spec's Current Behavior, its R-1 early signal and its Completion checklist each required "the four target `.ci` tests (372, 378, 394, 395)" to stay green. One surface did: `plan/deferrals/fixit-load-dependent-functional-failures.md` spells the cluster out, so the mapping survived in exactly one place and by luck, not by design. A checklist item that resolves to the wrong tests reads as one that passed | the spec now names all four (`remove-private-as-replace-peer`, `rfc7606-relay-one-field`, `role-otc-egress-filter`, `role-otc-egress-stamp`) with a then/now id table, and requires the whole suite besides. The general practice this class already states applies exactly: a `.ci` has a stable NAME and an unstable id, so the name is the citation and the id is never one |

| 2026-08-24 | - | commit SHAs cited in prose, after a rebase | A rebase of 50 local commits onto a diverged `origin/main` rewrote every SHA above the divergence point. Prose that cites one still READS as correct in the checkout where the rebase happened, and that is the trap: the old object is unreachable but still present, so `git cat-file -e <sha>` succeeds and `git show` works for everybody here. It is absent from a fresh clone, and it dies locally at the next `git gc`. So the citation is already broken and this checkout is the one place that cannot tell, which is the same shape as the shared working tree answering a question the committed state answers differently. Caught while writing a journal row for a DIFFERENT class: the draft cited five SHAs, three of which the rebase had just hollowed out, so recording one class would have created an instance of this one. Upper bound measured by the session that ran the rebase: 249 hex tokens of 9+ characters across `plan/`, `docs/` and `ai/` markdown, of which 48 already failed to resolve before that night. The newly-hollow ones are NOT in the 48, because they still resolve here | not fixed and not swept, which would be uncommissioned. The method for whoever takes it: resolve a citation by its SUBJECT LINE, never by its SHA, and test reachability with `git merge-base --is-ancestor <sha> main` rather than `git cat-file -e`, because resolvability is what makes the dead ones look alive. The durable repair is to stop citing bare SHAs in prose where a subject line would identify the commit as well and survive a rewrite |
