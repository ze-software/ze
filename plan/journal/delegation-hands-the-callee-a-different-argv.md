# Delegation hands the callee a different argv

A wrapper that runs another program IN PROCESS has to reconstruct what the
program would have received as a subprocess. Getting that wrong is invisible
from the outside: the callee's own argument parser rejects the argv and exits
non-zero, so the wrapper reports a failing gate rather than a failing call, and
the reader goes looking for the drift the gate was checking for.

| Date | Spec | Surface | Symptom | Fix |
|------|------|---------|---------|-----|
| 2026-08-31 | - | `cmd=...:exec=` in every functional suite except `parse`, driven by `runExecCommands` (`internal/test/runner/runner_exec.go`) | The runner has two `.ci` execution paths and they split an exec line differently. `parsing.go` (the `parse` suite) calls `splitCommand`, whose doc comment says it "splits on whitespace, respecting single/double quotes". `runner_exec.go` calls `strings.Fields(execStr)`, which does not. So `exec=ze cli -c "show module list piped through json"` reaches the binary as six arguments, `-c` takes the literal `"show`, no local-data handler matches it, and `ze cli` falls through to the daemon and prints `no credentials for 127.0.0.1:2222 ... hint: is the daemon running?`. It is not a silent failure, and that is what makes it expensive: the message names credentials and a daemon, so a reader debugs the wrong subsystem. Four committed tests in the `ui` suite carry that exact shape and all four are red today for this reason: `cli-config-dump-json-sensitive`, `command-contract-snapshot`, `config-validate-json-diagnostics` and `config-validate-json-related`. Proved by running the suite's own isolated `ze` under `env -i` with no credentials at all: `ze cli -c "show module list piped through json"` exits 0 and answers, because `Run` (`internal/component/cli/client/main.go`) calls `cmd.ServeLocal` before it loads any credential. Found by writing a new offline-command `.ci` into `test/plugin`, then `test/ui`, and meeting the same refusal in both | not fixed. The new `.ci` moved to `test/parse`, which is where `ai/patterns/cli-command.md` puts an offline command's functional test anyway, so the spec's goal is not blocked. The repair is one call site, `strings.Fields` to `splitCommand`, and it is not a one-liner in effect: every `exec=` in every non-parse suite is currently splitting on whitespace, so a line that today relies on a quote being passed through as a literal character would change meaning. The change owes a full run of the affected suites, which is a piece of work of its own |
| 2026-08-25 | port-test-functional-to-le | the retired `scripts/le/devtools/inproc.py` (current producer: `internal/le/`) `_call_args`, the retired `scripts/dev/spec-citation-check.py` (current producer: `internal/le/spec/citation/speccitation.go`) | `./le spec citation anchors` and `./le doc check verify` red with `spec-citation-check.py: error: unrecognized arguments: <its own path>`. Both conventions now run identically through `le` and standalone |
