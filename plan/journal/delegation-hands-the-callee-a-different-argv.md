# Delegation hands the callee a different argv

A wrapper that runs another program IN PROCESS has to reconstruct what the
program would have received as a subprocess. Getting that wrong is invisible
from the outside: the callee's own argument parser rejects the argv and exits
non-zero, so the wrapper reports a failing gate rather than a failing call, and
the reader goes looking for the drift the gate was checking for.

| 2026-09-04 | command-help-and-description | `refuseWrongBuildName` (`cmd/ze/le_build_name.go`), reached by every `.ci` that spawns the shared `bin/le` | `./le --name helpui functional ui` reported 25 failures that have nothing to do with the tree. Each one printed "le: --name asked for 'helpui' and this process is 'le'". The launcher exports `ze.le.build.name` into the process it execs AND into that process's children, which its own file comment states. A `.ci` test that shells out to `bin/le` therefore inherits the name, answers `invokedBuildName` = "le", disagrees, and exits 2 before it runs. The suite reads that as a test failure. The same suite run without `--name` leaves those 25 alone. `ai/rules/commands.md` tells a session reading a result back to use a named build, so the rule and the guard point opposite ways for any suite whose tests spawn `le` | not fixed. The name is a property of the RUN, not of every descendant, so the launcher exporting it to grandchildren is what makes an unrelated test refuse. Two shapes would end it: the guard could ignore the name when the process was not started by the launcher it names, or the runner could clear the key before it spawns a test binary, the way it already isolates the test binaries it builds. Until then, `--name` is safe for a unit or a gate and poisons a functional suite |
| 2026-08-31 | - | `cmd=...:exec=` in every functional suite except `parse`, driven by `runExecCommands` (`internal/test/runner/runner_exec.go`) | The runner has two `.ci` execution paths and they split an exec line differently. `parsing.go` (the `parse` suite) calls `splitCommand`, whose doc comment says it "splits on whitespace, respecting single/double quotes". `runner_exec.go` calls `strings.Fields(execStr)`, which does not. So `exec=ze cli -c "show module list piped through json"` reaches the binary as six arguments, `-c` takes the literal `"show`, no local-data handler matches it, and `ze cli` falls through to the daemon and prints `no credentials for 127.0.0.1:2222 ... hint: is the daemon running?`. It is not a silent failure, and that is what makes it expensive: the message names credentials and a daemon, so a reader debugs the wrong subsystem. Four committed tests in the `ui` suite carry that exact shape and all four are red today for this reason: `cli-config-dump-json-sensitive`, `command-contract-snapshot`, `config-validate-json-diagnostics` and `config-validate-json-related`. Proved by running the suite's own isolated `ze` under `env -i` with no credentials at all: `ze cli -c "show module list piped through json"` exits 0 and answers, because `Run` (`internal/component/cli/client/main.go`) calls `cmd.ServeLocal` before it loads any credential. Found by writing a new offline-command `.ci` into `test/plugin`, then `test/ui`, and meeting the same refusal in both | Fixed 2026-09-02. `runExecCommands` calls `splitCommand`, which moved to `internal/test/runner/runner_exec_util.go` so ONE splitter serves every suite, and `internal/test/fixture/fixture.go` lost the surrounding-quote strip that compensated for the old splitting. A scan of all 2947 `exec=` values found 35 the two splitters disagree on: 21 already ran through `splitCommand` in `parse`, 10 are the `"$ZE_REPO_ROOT"` lines in `install` and `appliance` whose argument `os.ExpandEnv` resolves either way, and 4 are the red `ui` tests, which now pass. `test/runner/exec-quoted-argument.ci` pins the behavior and goes red under `strings.Fields` with `argv has 4 elements`. The rule is now stated in `docs/architecture/testing/ci-format.md`. History: the new `.ci` moved to `test/parse`, which is where `ai/patterns/cli-command.md` puts an offline command's functional test anyway, so the spec's goal is not blocked. The repair is one call site, `strings.Fields` to `splitCommand`, and it is not a one-liner in effect: every `exec=` in every non-parse suite is currently splitting on whitespace, so a line that today relies on a quote being passed through as a literal character would change meaning. The change owes a full run of the affected suites, which is a piece of work of its own |
