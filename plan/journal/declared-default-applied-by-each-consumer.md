| 2026-09-04 | bgp-attribute-defaults | `config.ApplyDefaults` (`internal/component/config/schema_defaults.go`) and every non-peer config container that declares a leaf `default` | A leaf's YANG `default` reaches a config section only where the CONSUMER calls `config.ApplyDefaults` over that container itself. The tree a plugin is delivered carries the operator's keys and nothing else, so a leaf the operator left out is simply absent, and a reader that indexes the map reads the zero value as though the operator had chosen it. Three consumers apply defaults today and each wrote its own lookup: `applyPeerSchemaDefaults` for a peer entry and its template (`internal/component/bgp/config/peers.go`), `parseAdminDistanceConfig` for `rib { distance { } }` (`internal/component/sysrib/sysrib.go`), and now `parseAttributeDefaults` for `bgp { defaults { attribute { } } }` (`internal/component/bgp/plugins/filter_modify/config.go`). A fourth consumer that forgets gets 0 for every unwritten leaf, with no error and no log line, and 0 is a legitimate operator value for both leaves here, so nothing downstream can tell the two apart. Found while wiring the modifier's absent-attribute base to the schema rather than to a Go literal | not fixed, and nothing is broken today: this spec calls `ApplyDefaults` as the two earlier consumers do, and `TestAbsentBaseComesFromConfig` compares the base against `config.SchemaDefaultInt` so a forgotten call would go red. The repair sits one level above all three: whether the config tree applies the schema's defaults once, where every reader sees them, rather than each consumer applying them for its own container. That is a decision about `internal/component/config`, not about any one plugin, so it wants a spec rather than a fourth copy |
