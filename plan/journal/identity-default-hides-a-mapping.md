| 2026-08-19 | fixit-iface-selector-ignored-by-apply | iface config apply, logical-name resolution | An interface entry selects its hardware by `mac/match` or aliases it with `os-name`, and roughly twenty-eight READ consumers reached the right device through `iface.Resolve`. The one WRITER did not: `desiredState` keyed every address, MTU, MAC, sysctl, admin state, mirror and VLAN parent by the logical entry name, and `reconcileOnReadyWithJournal` called the backend on that key. A `mac/match` entry carrying an address was refused outright. Where a device happened to carry the entry's name, everything landed on the wrong physical port with no error. What hid it for the life of the feature is that `ze init` writes `os-name` equal to the kernel name on every entry, so the generated config makes the mapping the IDENTITY and the whole translation layer reads as a no-op. Every test fixture inherited that default, and the integration tests that would have seen it carry the `integration` build tag and do not run on the developer platform | fixed at the writer: `bindDevices` resolves every ethernet entry once per apply from one `ListInterfaces`, `deviceFor` answers every phase, and no path falls back to the logical name. The shape to look for is a mapping whose DEFAULT is the identity. Its readers can all be correct while a writer ignores it, and no fixture built from the default configuration can tell the two apart. The test that finds it is one whose logical name DIFFERS from the kernel name, which is why the four new `.ci` files each make a device under one name and select it under another |
| 2026-08-22 | fixit-iface-selector-ignored-by-apply | iface owned-device and owned-address registries, vrrp | The apply path translates now. The two plugin-facing REGISTRIES beside it do not. `desiredState` (`internal/component/iface/config_apply.go`) merges `ownedAddresses()` under the name a plugin registered. `reconcileOwnedDevices`, in the same file, hands `MacvlanSpec.Parent` to `CreateMacvlanDevice`, which reaches `netlink.LinkByName(spec.Parent)` (`internal/plugins/iface/netlink/macvlan_linux.go`). VRRP fills that parent from `spec.ParentDevice`. `groupsForFamily` (`internal/plugins/vrrp/groups.go`) sets it to the config entry name plus any VLAN suffix. So a VRRP group on a `mac/match`-bound entry builds its virtual-MAC device on whatever wears the LOGICAL name. Today's two producers hide it as `ze init` hid the original: as112 registers on `lo`, and VRRP's VIPs register on the macvlan it just made | NOT fixed. No acceptance criterion of the closing spec depends on it. Recorded because the shape recurs: fixing the WRITER does not fix the registries that feed it. Each registry is a separate entry point holding a name nobody translated. VRRP already resolves the same string for its ifindex and its readiness probe (`iface.Resolve`, `internal/plugins/vrrp/register.go`). The parent is therefore translated on two paths of three and raw on the third |
