Status: source diagnosis and proposed repair; no validation command or runtime executed by this writer.

Symptom supplied by Main: attempt-008 passive pcaps show ordinary PATH refreshes entering label 1000 from H through M to E. The PATH still names strict M (10.11.0.2) first in its ERO, but M does not process that control message.

Root cause: rawTransport.ResolveRoute keeps the native lookup destination in RouteInfo.Lookup and the adjacent gateway in RouteInfo.NextHop. For a loose endpoint, engine.resolveExplicitPath prepends that adjacent next hop to the ERO. engine.sendPath, engine.pathRoute and engine.handlePathTransit preserve both route fields. rawTransport.SendPath nevertheless prefers the remote Lookup for its route query and IP_HDRINCL sockaddr even when TableID is zero. Linux consequently applies the installed endpoint data FEC to that ordinary PATH. Pinning the same output interface does not remove the route's MPLS encapsulation.

Owning layer: Linux RSVP control-packet carriage in internal/plugins/rsvpte/transport_linux.go, rawTransport.SendPath. The producer already selects the adjacent control hop and expands the ERO; the transport must use that hop for the ordinary send.

[workaround] Change the PATH IP destination to the adjacent peer, suppress the initial-subobject rejection at E, or remove the installed endpoint data FEC. These change the protocol identity, bypass required ERO processing, or disable the data path the refresh maintains.
[source] Default the route query and IP_HDRINCL sockaddr to PathRoute.NextHop. Only a nonzero TableID may select PathRoute.Lookup, retaining the established bypass's private MPLS context and its existing missing-table/encapsulation checks. Keep IfIndex, packet mark synchronization, source/destination, RSVP_HOP substitution, Router Alert, TTL and ERO selection unchanged.

Primary requirements read in rfc/full/rfc2205.txt and rfc/full/rfc3209.txt:
RFC 2205 Section 3.1.3: "The IP source address of a Path message must be an address of the sender it describes, while the destination address must be the DestAddress for the session."
RFC 2205 Section 3.1.3: "Each RSVP-capable node along the path(s) captures a Path message and processes it to create path state for the sender defined by the SENDER_TEMPLATE and SESSION objects."
RFC 3209 Section 4.3.4.1 step 6: "Finally, the node replaces the first subobject with any subobject that denotes an abstract node containing the next hop. This is necessary so that when the explicit route is received by the next hop, it will be accepted."
RFC 2205 Section 3.3: "Path, PathTear, and ResvConf messages must be sent with the Router Alert IP option [RFC 2113] in their IP headers."
The quotation whitespace is normalized. Primary URLs: https://www.rfc-editor.org/rfc/rfc2205.html#section-3.1.3 and https://www.rfc-editor.org/rfc/rfc3209.html#section-4.3.4.1 .

The marked exception remains required by RFC 4090 Section 6.4.3: "The PLR sends Path, PathTear, and ResvConf messages via the backup tunnel." Source: rfc/full/rfc4090.txt; https://www.rfc-editor.org/rfc/rfc4090.html#section-6.4.3 .

Linux raw(7), DESCRIPTION, confirms the address separation: "If IP_HDRINCL is specified and the IP header has a nonzero destination address, then the destination address of the socket is used to route the packet." Source read: https://man7.org/linux/man-pages/man7/raw.7.html .
