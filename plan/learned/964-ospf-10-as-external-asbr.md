# 964 - OSPFv2 AS-External routes, redistribution, and default-information

## Context

Completed `plan/spec-ospf-10-as-external-asbr.md`: ASBR Type 5 AS-External-LSA origination (RFC 2328 §12.4.4), the §16.4 external route computation (E1/E2 cost, forwarding-address resolution), bidirectional redistribution (`destination ospf` imports connected/static/BGP as Type 5; `import ospf` exports OSPF routes to BGP via the shared orchestrator), and `default-information originate`. The Router-LSA E-bit and the `ze_ospf_asbr` / `ze_ospf_external_lsas` metrics track ASBR state. Earlier phases (origination, §16.4 compute, consumer/producer) were built across prior sessions; this session implemented Phase 4 (`default-information originate`), the functional test, and the docs, and fixed a real LSDB data race the new concurrency exposed.

## Decisions

- Two distinct route paths, never merged: FIB install is ospf-8 (`locrib.Path` -> sysrib -> fibkernel, AdminDistance 110); redistribution is `redistevents` (out) + the `configredist` consumer (in). `redistevents` never touches the kernel. OSPF resolves intra > inter > E1 > E2 internally and publishes ONE winning `locrib.Path` per prefix; path type is the primary key (trap #7: E1 always beats E2 regardless of cost).
- The redistribution source name AND consumer name are both the single string `ospf`, so the generic loop-prevention evaluator auto-rejects OSPF self-import (origin `ospf` == importing `ospf`) with no OSPF-specific code.
- `default-information originate` lives on the engine, not in the `ospfredistribute` package, because it reads engine + LSDB state. `always` originates unconditionally; the bare form originates only while a NON-OSPF default exists in the Loc-RIB, re-evaluated at config-apply AND live via a Loc-RIB `OnChange` watcher. OSPF runs in-process and shares the `locrib.Default()` singleton, so the engine can read the RIB directly.

## Gotchas

- **A new concurrent reader exposed a latent LSDB data race (fix it at the source, do not serialize the caller).** `installOriginated` mutated the `*Entry` returned by `install()` (`Entry.Header` read + `markPurged` write) AFTER `install` released `d.mu`, while `SelfExternalCount` reads the same fields under `RLock`. Single-threaded origination hid it; the `default-information` Loc-RIB watcher added a second goroutine and `go test -race` caught it immediately. Fix: extract `installLocked` (lock held by caller) so `installOriginated` holds `d.mu` across install + Header + markPurged atomically. `Tick`'s `markPurged` was already locked. This is the "replace sleeps/serialization with real concurrency to surface races" technique paying off.
- **`locrib.RIB.Lookup` returns a SHALLOW `PathGroup` copy whose `Paths` slice shares the stored backing array; ranging it after the shard lock is released races an in-place `upsert` (`g.Paths[i] = p`).** The first review caught `hasNonOSPFDefault` doing exactly this. The canonical safe pattern (sysrib) ranges `Paths` INSIDE `RIB.Iterate`, under the lock. Fix here: added `RIB.Inspect(fam, prefix, fn)` (a single-prefix callback that runs `fn` under the shard `RLock`) and scan inside it. Any concurrent reader of a `Lookup` result's `Paths` is a latent race; inspect under the lock.
- **Two independent intents sharing one LSA key need coordinated lifecycle, not just a self-ownership flag.** `default-information originate` and a redistributed `0.0.0.0/0` share one Type 5 key. A bare `defaultInfoOriginated` "did I originate" flag does NOT stop one intent's withdraw from purging a default the other still wants. Fix: track BOTH intents (`defaultInfoOriginated` + `redistDefaultInjected`) and purge only when neither wants it; serialize ALL default-route mutations (both intents) under one `defaultInfoMu` so the cross-checks are race-free. Presence is always correct; only the LSA params can be briefly stale when both advertise with different metrics (documented).
- **A method called from two goroutines that reads-decides-writes shared state must be serialized end-to-end, not just lock each field access.** `applyDefaultInformation` runs from reconcile (config-apply) AND the watcher worker. Per-field `e.mu` locking left a TOCTOU: a stale worker run could re-originate a default a concurrent config-disable just withdrew. Fix: a dedicated `defaultInfoMu` held across the whole evaluate+act body; cfg/flags re-read fresh inside it, so the last entrant observes the latest config and converges. (Lock order: `defaultInfoMu` > `e.mu` > LSDB `d.mu`, consistent everywhere; LSDB calls happen with `e.mu` released.)
- **A Loc-RIB `OnChange` handler runs UNDER the shard write lock and must not re-enter the RIB.** The watcher handler only does a non-blocking send to a buffered(1, coalesced) channel; a long-lived `wg` worker drains it and calls `applyDefaultInformation` outside the lock. Mirror `sysrib`'s subscriber shape; do not call back into Insert/Remove from the handler.
- **Conditional default-information must exclude OSPF's own default or it self-sustains.** `hasNonOSPFDefault` skips any Loc-RIB path whose `Source == ospf ProtocolID`. Combined with `OriginateExternal`'s body-unchanged short-circuit (returns `changed=false`, no re-flood, no SPF re-trigger), an OSPF-installed default cannot loop the watcher.
- **Spec test-location deviation.** The spec's TDD plan placed `TestOSPFDefaultInformationOriginate` in `redistribute/consumer_test.go`, but `applyDefaultInformation` is an unexported engine method in package `ospf`; the test lives in `internal/plugins/ospf/default_test.go`. AC-12 is fully covered there.
- **Purge must bypass MinLSInterval (R-4, carried from earlier phases).** `flushSelfLSA` uses `nextOwnSequenceForce(area,key,true)` so a withdraw is not delayed up to MinLSInterval (RFC 2328 §14.1 flushing is not rate-limited).
- **Self Type-5 LSAs MUST be refreshed from the AS-wide store too (review BLOCKER).** `LSDB.RefreshSelf` originally iterated only `d.areas`; Type-5 AS-External-LSAs live in the separate AS-wide store `d.asExternal` (where `Tick` DOES purge them at MaxAge). So every redistributed external, the `default-information originate` default, and every NSSA-translated Type 5 aged to MaxAge and `Tick` purged it ~`LSRefreshTime` after the last topology change, blackholing the routes domain-wide while redistribution was still active. Fix: `RefreshSelf` mirrors `Tick`'s dual-iteration, re-stamping self entries in `d.asExternal` under the backbone area key (`TestOSPFLSRefreshExternal`). Lesson: any LSA store that `Tick` ages MUST also be walked by `RefreshSelf` -- the two must iterate the same set, or self-LSAs silently expire.
- **A failed self-LSA install MUST be surfaced, not inferred from a "changed" bool (closure review ISSUE).** `OriginateExternal` returned only `(LSAHeader, bool)` where `bool` conflated three cases: idempotent no-op, MinLSInterval rate-limit, AND a hard install rejection (`installLocked` returns `false` when `len(store.entries) >= MaxASExternalLSAs`, 16384). `InjectExternal` discarded the result and returned `nil`, so a store-full drop was invisible AND the consumer still bumped `ze_ospf_redist_injected_total` -- a route that does not exist counted as injected. Fix at the right altitude: (1) `installOriginated` logs every install-reject uniformly, covering Router/Network/Summary/External/NSSA in one place; (2) `OriginateExternal` returns `(LSAHeader, bool, error)` (`ErrExternalStoreFull`) and `InjectExternal` propagates it, so the consumer's EXISTING `if err != nil { log; return }` path skips the counter for free. Lesson: when one bool encodes "no change" and "failed", a caller cannot distinguish a benign no-op from a dropped write -- give failures their own channel (an `error`), and log store-exhaustion where the install is rejected, not at every caller. Regression: `TestOSPFOriginateExternalStoreFull`.
