# 1156 -- driving a diverged-main rebase through the learned bookkeeping files

Companion to `1155` (which is about *why* learned numbers collide across
branches and the `learned_numbers.py` check/fix). This one is about getting
*through* the rebase that surfaces the collision, and a git message that lies.

## Context

Rebasing 25 local commits onto 65 upstream ones stopped on
`plan/learned/.counter` + `ai/LEARNED-FULL-INDEX.md` at nearly every
learned-touching commit, plus real conflicts (spec deletions from closure
commits, one spec content conflict, `test/.ci-sleep-baseline`). Resolving the
two bookkeeping files by hand ~18 times is pure toil, and both are DERIVABLE.

## The driver

`scripts/dev/rebase_learned.py` drives a rebase the human started: at each stop
it resolves only the two derivable files (`.counter` -> `max(NNNN prefix)+1`,
index regenerated by `learned_index.py`), and HALTS on any other unmerged path.
Judgment is opt-in and logged, never silent:

- `--accept-incoming-delete` -- in a rebase the replayed commit is always one
  of ours, so a modify/delete where the incoming side deletes (no stage-3
  entry) is the intended outcome (e.g. closure commits that `git rm` a spec an
  earlier commit modified).
- `--take-theirs PATH` / `--take-ours PATH` -- resolve a content conflict with
  `git show :3:` / `:2:` wholesale. Using `git show` instead of hand-editing
  also avoids tripping the spec/design edit hook on a mechanical resolution.

The number fix is NOT the driver's job: finish the rebase, then
`make ze-learned-numbers-fix`. Also recompute any derived ratchet the rebase
loosened (taking `test/.ci-sleep-baseline` from a diverged branch can raise it;
the true value is the actual `time.sleep(` count in `test/**/*.ci`).

## The lying message

`git rebase --continue` printed "You must edit all merge conflicts and then
mark them as resolved using git add" while `git ls-files -u` showed ZERO
unmerged entries. The message is misleading: `builtin/rebase.c` ACTION_CONTINUE
guards on `has_unstaged_changes()`, so ANY unstaged tracked change blocks the
continue, not only unmerged entries. The real cause was an unrelated unstaged
doc edit sitting in the tree. Cost ~6 tool calls to diagnose because the error
text points at the wrong thing.

Reproduced and pinned by `TestRebaseContinueMessageIsMisleading` in
`scripts/dev/rebase_learned_test.py`: resolve a conflict, stage it (so
`ls-files -u` is empty), dirty one unrelated tracked file, and `--continue`
exits 1 with exactly that text (verbatim on git 2.55.0). git's source is not
vendored here, so the mechanism above is cited from upstream while the
behaviour itself is now proven by observation. The test asserts the refusal
never names the real file rather than matching git's phrasing, so it pins the
lie without breaking when the wording changes.

## Reusable

- When a git command's error text and `git ls-files -u` disagree, distrust the
  text and read what the command's source actually checks. Rebase's continue
  checks unstaged-changes, not just unmerged, and says "merge conflicts" for
  both.
- Auto-resolve only what is derivable (counters, generated indexes); make every
  judgment call an explicit, logged flag. A driver that silently guessed
  deletions or sides would be worse than stopping.
- Keep the mechanical driver (get through the rebase) separate from the
  semantic fixer (`ze-learned-numbers-fix`, renumber + reference rewrite). One
  tool per concern; see `1155`.
