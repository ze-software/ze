# bare-go-test-drops-feature-tags

Seven tests sat in `plan/known-failures.md` for up to two weeks as "pre-existing
reds" with confident, specific, and entirely wrong root causes. None of them was
ever broken. `go test` without the Makefile's build tags compiles the relevant
features out, so their registrations never happen and unrelated assertions fail.

## What was logged, and what was true

| Entry | Logged cause | Reality |
|---|---|---|
| `internal/component/doctor`, 4 listener tests (2026-07-02, "re-confirmed" 07-03) | "this specific macOS host's socket stack allowing a second bind ... a `SO_REUSEPORT`/dual-stack quirk" | Pass on that same macOS host with tags. Needs `ze_web`/`ze_ssh`/`ze_rest` for the listeners to register |
| `config/cli`, 3 tests (2026-07-03, "re-confirmed" 07-09) | "the `config-listener-conflict` validator produces no diagnostic (hence no repair) **in this build**" | Pass with tags. All three fixtures configure `environment { web { server ... } }`, so they need `ze_web` |

Only `config/schema/cli` `TestCmdMethods` was real: it fails with tags too (a
stale hardcoded `13` after `ze-system:quiesce` was added). Fixed by bumping it.

The proof is one command run twice:

```
go test ./internal/component/config/cli/ -run 'TestConfigFixPlanRepairIDs'          # FAIL
go test -tags "ze_core $(awk '$1 ~ /^ze_/ {print $1}' feature-gates.txt | sort -u | tr '\n' ' ')" \
        ./internal/component/config/cli/ -run 'TestConfigFixPlanRepairIDs'          # PASS
```

## The mechanism

Ze compiles features out per build tag: `all_ze_isis.go`, `all_ze_ospf.go`,
`all_ze_ldp.go`, `all_ze_rsvpte.go` in `internal/component/plugin/all/` are each
guarded by `//go:build ze_<feature>` and generated by
`scripts/codegen/plugin_imports.go`. The Makefile always supplies the set
(`Makefile:51` reads `ZE_FEATURES` from `feature-gates.txt`; `Makefile:65`
`GO_TEST_TAGS = ze_core $(ZE_FEATURES) $(ZE_TAGS)`), so `make ze-unit-test` sees
all of them and a bare `go test` sees none.

The failure that results does not look like a build problem. It looks like a
component is broken: a validator "produces no diagnostic", a listener check
"reports nothing", `TestRegisteredPluginNames` says `missing plugins: "isis"`.
Every one of those is the plugin simply not being in the binary.

## Why it survived so long

**Symptom-matching is not attribution.** Both entries were "re-confirmed" days
later. Re-confirming means running the same command again, and the same wrong
command reproduces the same phantom red forever. `known-failures.md` even carries
a BLOCKING rule that a red "must be attributed, not assumed" -- the attribution
step was performed, and it was performed with the broken tool.

I repeated the mistake myself in this very session, twice:

- I ran bare `go test` on `internal/component/plugin/all/`, saw `missing plugins:
  "isis", "ldp", "ospf", "rsvp-te"`, and told the user **main is red**. It is not.
- I then "proved" it pre-existing with `git archive HEAD` into a scratch tree and
  a bare `go test` there. The technique is sound and is exactly what
  `known-failures.md` prescribes. It confirmed nothing except that I had made the
  same error twice. **A scratch-tree reproduction inherits your invocation.** If
  the invocation is what is wrong, the scratch tree agrees with you enthusiastically.

The tell was available and I walked past it: the logged cause said the validator
produced no diagnostic *"in this build"*. It was literally a different build.

## The rule

`ai/rules/bash-output.md` now leads with it: prefer a `make` target; if you must
scope to packages, pass the tags. Before logging any red in
`plan/known-failures.md`, reproduce it with the Makefile tags.

Heuristic for spotting a tags artifact: **the failure says a thing is missing or
not produced, and the thing is owned by a different feature** (a listener, a
validator, a plugin name, a wire method, a schema provider). A genuinely broken
component usually fails with a wrong value, not an absent one.

## Traps for the next agent

- **`known-failures.md` is scoped to non-deterministic reds.** A deterministic
  failure logged there is either a phantom (fix your invocation) or a real bug
  (fix the code). Two of these four entries were deterministic and were neither.
  A deterministic red in that file is itself a smell worth checking.
- **A wrong known-failure is worse than an unlogged one.** It does not merely
  fail to help; it actively names an innocent component as broken and invites the
  next session to scope around it, or to go hunting a bug that does not exist.
  Both of these entries named a specific producing function.
- **The counts in `config/schema/cli/main_test.go` will break again.** They are
  hardcoded per-module RPC counts, so every new RPC breaks them. Deriving them
  from the registry the test reads would be tautological; a golden snapshot file
  (`plugin/all/testdata/*.snapshot`) is the shape that catches silent removal.
  Left as a note in the test.
