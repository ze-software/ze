# 1002 -- ze_reference MCP tool + aihelp: one assembler for CLI and MCP

## Context

`ze help ai` made the AI reference discoverable from the CLI (see
[[1001-ze-help-ai-subcommand-grammar]]), but only for a CLI-driven agent. An
agent driving ze over MCP enumerates `tools/list` on connect and never runs CLI
commands, so it could not reach the reference at all. The reference-assembly
code (`printAIHelpJSON` and its helpers `cliSubcommands`, `buildAISchemaRegistry`,
`extractServices`) lived in `package main` (cmd/ze), which `internal/component/mcp`
cannot import. So exposing it over MCP meant either duplicating the assembly
(two sources of truth) or extracting it.

## Decisions

- **Extract the assembly into `internal/component/aihelp`, a single source of
  truth.** It exposes `Build() Reference` (the `ze help ai --json` shape) plus
  the building blocks the CLI text renderer reuses (`CLISubcommands`,
  `SchemaRegistry`, `Services`). Every import it needs was already an internal
  package; only `helpfmt` (text rendering) stayed in cmd/ze. `cmd/ze/help_ai.go`
  now renders text but gets its data from `aihelp`, and `printAIHelpJSON` is just
  `json.Encode(aihelp.Build())`. The MCP `ze_reference` tool calls the same
  `aihelp.Build()`, so CLI and MCP cannot diverge.
- **`ze_reference` is a handcrafted MCP tool**, added to both `handcraftedTools`
  (so it appears in `tools/list` on connect) and `toolHandlers` (so `tools/call`
  works), in `internal/component/mcp/handler.go`. Both the legacy and streamable
  transports dispatch via `toolHandlers[name]`, so one registration covers both.
  The handler ignores the server/session and just returns `Build()` as JSON.
- **Discoverability is structural for MCP, not guessed.** Unlike the CLI (where
  the agent must type the right command), an MCP client is handed the tool
  catalog on connect, so a tool in `handcraftedTools` cannot be missed. That is
  why the MCP exposure is the strongest of the discoverability layers.

## Consequences

- Adding a field to the reference is a one-place change in `aihelp`; both
  surfaces pick it up. The JSON shape is locked by `aihelp_test.go`
  (`TestReferenceJSONShape`).
- The MCP tool count test (`TestAllToolsWithCommandLister`) now asserts
  `len(handcraftedTools) + autoGenerated` instead of a magic number, so future
  handcrafted tools do not silently break it.
- `aihelp` is a high-level consumer importing cli/client, command, plugin/server,
  config/yang, etc.; `ze-tier-check` passes (a component depending on
  infrastructure components is allowed).

## Gotchas

- `internal/` cannot import `cmd/ze` (package main). The Explore recon initially
  suggested the MCP handler could "reuse printAIHelpJSON" -- it cannot. Verify
  the import direction before planning a cross-package reuse.
- Editing the cold-path help printers tripped three hooks at once: no-sprintf
  blocks `fmt.Printf` with verbs, errcheck flags an unchecked `fmt.Fprintf`
  return, and the discard hook blocks `_, _ =`. The right resolution is the one
  the no-sprintf hook intends: build the line with `textbuf.Buffer` and print it,
  not wrap `fmt.Fprintf` in a helper to dodge the check. Print with `tb.Slice()`
  (zero-copy) rather than `tb.String()` (1 alloc); the freeze is safe because
  `fmt.Println` consumes the slice before the next `tb.Reset()`.
- The MCP server is behind the `ze_mcp` build tag (in `ZE_FEATURES`). `make ze`
  includes it; `bin/ze-stripped` (ze_core ze_ssh) does not, so the functional MCP
  test must run against `bin/ze`. The plugin suite runs via `ze-test bgp plugin`,
  not `ze-test plugin` (which resolves to the `ze plugin` management command).

## Files

- `internal/component/aihelp/aihelp.go`, `aihelp_test.go` -- the assembler
- `cmd/ze/help_ai.go` -- delegates to aihelp; textbuf-rendered printers
- `internal/component/mcp/handler.go` -- `ze_reference` tool
- `internal/component/mcp/tools_test.go` -- `TestZeReferenceTool`, robust count
- `test/plugin/ze-reference-mcp.ci` -- live tools/list + tools/call
