# 1300 -- mcp2026-2-mrtr

## Context

Phase 2 of the `2026-07-28` cutover. Ze's elicitation blocked a handler
mid-dispatch inside `session.Elicit`, upgraded the POST reply sink to SSE, wrote
an `elicitation/create` JSON-RPC **request** frame to the client, and waited on a
per-elicit channel for a correlated JSON-RPC **response**. The revision forbids
both halves: "The server **MUST NOT** send independent JSON-RPC *requests* on
this stream" and "The client **MUST NOT** send JSON-RPC *responses*."

Multi Round-Trip Requests replace it. The server **returns**
`resultType: "input_required"` with an `inputRequests` map, terminating the
original request; the client gathers the input and retries the original request
carrying `inputResponses`. The server processing the retry needs nothing beyond
what the retry carries.

## Decisions

- **No `requestState` is minted, and the whole integrity design is not built.**
  Research collapsed this phase: there was exactly one reachable elicit call
  site, it asked for a single `command` string, and that string is itself a tool
  argument the retry carries anyway. With no server-side state to carry, the
  "at least one of `inputRequests` or `requestState`" rule is satisfied by
  `inputRequests` alone, which deletes the keyed MAC, principal binding, expiry
  and request-digest design the spec had budgeted at skeleton stage.
- **An arriving `requestState` is rejected, not ignored.** Ze never mints one, so
  no arriving value can be legitimate, and the client's own rule is that it
  "**MUST NOT** include one in the retry" if the result did not carry one.
  Rejecting is what `fail-closed-guards.md` means by "fail closed or say
  something"; silently dropping would be neither.
- **The gate is form-mode support, not the presence of the `elicitation` key.**
  The revision declares the capability as `{form?, url?}`, and an empty object
  means form-mode only. "Servers **MUST NOT** send elicitation requests with
  modes that are not supported by the client", so a bare-presence check would
  emit a form request to a url-only client.
- **The schema validator was RECOVERED from git, not rewritten.** Phase 1 deleted
  `elicit.go` for a compile reason -- `(*session).Elicit` lived in it -- not
  because the flat-primitive `requestedSchema` validator was obsolete.

## Consequences

- `ze_execute` became a pure function of (arguments + `inputResponses`),
  resumable from scratch across two independent HTTP requests with no server-side
  continuation. That is the shape the stateless model requires and it is now the
  only shape the handler has.
- A retry that omits the requested key gets a **new** `InputRequiredResult`
  rather than an error; an explicit `decline` or `cancel` is terminal. Unknown
  `inputResponses` keys are ignored. These are the extension's tolerance rules
  and they keep a slightly-wrong client working instead of failing it.
- URL-mode elicitation is not implemented, and that is correct rather than a gap:
  Ze's one elicitation asks for a `ze` CLI command, which is not a credential,
  and the specification forbids form mode for credentials specifically.

## Gotchas

- **Recovering code is a verifiable claim, and the test is whether its tests
  needed editing.** All 11 recovered validator tests are byte-identical to
  `HEAD:elicit_test.go` -- checked by diffing each function body, not by reading
  the report. If a recovered test had needed a change to pass, the validator had
  been rewritten rather than recovered, which is precisely the failure R-4 was
  written to prevent. One mechanical change was unavoidable: the repo's
  `c_string_concat` hook forbids `+` concatenation, so seven sites became
  `textbuf` chains producing byte-identical strings -- which is exactly why the
  unmodified tests passing is the proof.
- **The feature was reachable in code and unreachable through its own interface.**
  Phase 1 had set `"required": ["command"]` on the `ze_execute` descriptor for
  its AC-15, correct at the time because elicitation had been deleted. Phase 2
  restored the behaviour and never revisited the contract. A schema-validating
  host would never construct the call that triggers MRTR. The fix is structural:
  the descriptor now derives `required` from the same capability the handler
  branches on (`gateExecuteCommandRequired`), copy-on-write so the shared
  package-level descriptor is never mutated, so the two cannot drift again.
- **"No client JSON-RPC response is ever accepted" was true only by accident.**
  A response frame has no `method`, so header validation rejected it for a
  missing `Mcp-Method` -- a correct verdict reached for an unrelated reason, with
  nothing pinning it. It is now an explicit condition at the producer
  (`errBodyCarriesNoMethod`), still answering `-32020` because that is the code
  the specification pins to this class, plus a Go test over 5 frame shapes x 4
  header shapes and a functional test.
- **A `reject=` that cannot fire reads as protection and is not.** The assertion
  guarding "no `elicitation/create` frame is written" could never match, because
  the client prints a frame's `result` member and never the enclosing frame.
  Replaced with a needle that sits inside what is actually printed.
