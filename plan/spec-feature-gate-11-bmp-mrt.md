## Task

Make **BMP** (`ze_bmp`) and **MRT** (`ze_mrt`) compile-out-able features, each
droppable from the `ze` binary at build time for a smaller binary / attack
surface, default-on via `ZE_FEATURES` so the shipped `ze` is unchanged.

**Why one spec.** BMP and MRT both consume BGP message-handling code, and the
correct verification is a **tag matrix** across `{ze_bgp, ze_bmp, ze_mrt}`, not
two independent present/absent pairs. Specifically, the BGP message-type leaf
`internal/core/bgp/msgtype` is imported by the BGP engine, by BMP, and by MRT;
its presence must be proven correct in every combination. Gating the two
separately would verify half the matrix twice and risk leaving the shared-leaf
drop-condition under-specified. The two gates also have opposite dependency
shapes (below), and contrasting them in one design is what makes the shared-leaf
behavior legible.

**The refinement of the "shared BGP header" premise.** The shared BGP-specific
code the two features pull in is `internal/core/bgp/msgtype` (the message-type
codes; a pure library, no `init()`). It is imported directly by both the engine
(`internal/component/bgp/message/*.go`, the reactor) and by MRT
(`internal/plugins/mrt/component.go:11`) and BMP
(`internal/component/bgp/plugins/bmp/bmp.go`). BMP cannot exist without the BGP
engine (it imports `internal/component/bgp/message` and monitors the BGP RIB), so
**`ze_bmp` requires `ze_bgp`**, and BMP's contribution to `msgtype` is subsumed by
the engine. The accurate drop-condition for `msgtype` is therefore
**`ze_bgp || ze_mrt`**, not `ze_bmp || ze_mrt`. Because `msgtype` has no `init()`,
that condition is satisfied by **dead-code elimination** (nothing imports it →
linker drops it); no source build tag is added to it. This spec's job is to make
that drop happen and **prove it with the tag matrix**, not to hand-tag the leaf.

**The two gate shapes differ:**

| Feature | Home | Current linkage | Gate shape | Depends on `ze_bgp`? |
|---------|------|-----------------|------------|----------------------|
| BMP (`bgp-bmp` plugin) | `internal/component/bgp/plugins/bmp` (+ `/yang`) | blank-imported by `all_ze_bgp.go` only; no other importer | **dependent** plugin-compile-out (generated blank import guarded `//go:build ze_bgp && ze_bmp`) | **YES** — imports `bgp/message`, `bgp/types` |
| MRT (`mrt` plugin) | `internal/plugins/mrt` (+ `/yang`) | blank-imported by `all.go` (always-on) **and** directly imported by `cmd/ze/hub/main.go:56` | plugin-compile-out after an **extract-then-gate** (invert one always-on pin) | **NO** — runs inert without BGP |

**Scope:** the two gates, their extract-then-gate work, manifest + codegen +
dep_audit support for a **dependent gate** (the novel piece), and the tag-matrix
verification. **Not changed here:** BMP or MRT runtime behavior; the
`ze_bgp` gate itself (closed, `plan/learned/1249`).

## Data Flow (MANDATORY - see `ai/rules/data-flow-tracing.md`)

### Entry Point
- Build-time: `-tags` selection (default `ZE_FEATURES` includes `ze_bmp ze_mrt`; a hardened build omits either/both).
- Runtime (unchanged): `bgp { … bmp … }` config → BMP plugin; `mrt { … }` config → MRT plugin.

### Transformation Path (the gating)
1. `feature-gates.txt` gains `ze_bmp`/`ze_mrt` lines (+ `/yang` sidecars).
2. `make generate` (`plugin_imports.go`) moves BMP's blank import out of `all_ze_bgp.go` into a new `all_ze_bmp.go` guarded `//go:build ze_bgp && ze_bmp`, and MRT's out of `all.go` into `all_ze_mrt.go` guarded `//go:build ze_mrt`. `feature_tags.go` regenerates the three static tag lists.
3. With a tag off, the plugin's blank import is absent → the plugin package and its now-unreferenced pure-lib dependencies (`msgtype` when also no engine; `internal/mrt`) are dropped by DCE.

### Boundaries Crossed
| Boundary | How | Verified |
|----------|-----|----------|
| always-on `main.go` → MRT | invert direct import to `registry.SetMRTMessageCallback`/`Get…` seam | AC-3, dep_audit |
| reactor-config consumer → MRT bridges | `registry.MessageCallback`/`PeerLifecycleCallback` (unchanged interface) | AC-3 |
| generated composition root → BMP | `all_ze_bmp.go` `//go:build ze_bgp && ze_bmp` | AC-1, AC-4 |
| engine/mrt → `msgtype` leaf | direct import; DCE decides presence | AC-2 (matrix) |

### Integration Points
- `internal/component/plugin/registry` — add `SetMRTMessageCallback`/`SetMRTPeerCallback` + getters (mirror `SetRIBDumpCallback`/`GetRIBDumpCallback`).
- `scripts/codegen/plugin_imports.go` — dependent-gate emission.
- `scripts/dev/dep_audit.py` — treat `ze_bmp` as a sub-feature of `ze_bgp` (a bmp import of a `bgp/*` package is intra-family, not an always-on pin), mirroring how routing-protocol sub-packages are skipped.

### Architectural Verification
- [ ] No bypassed layers (registry seam, not a direct import)
- [ ] No unintended coupling (no always-on type from bmp/mrt in an always-on signature; bridges cross as `registry.MessageCallback`)
- [ ] No duplicated functionality (reuse the existing RIB-dump seam pattern; do not invent a new mechanism)
- [ ] Registration over hardcoding — gates declared once in `feature-gates.txt`; every consumer derives

## Design Insights
<!-- LIVE -->
- The user's "the BGP header becomes conditional to bmp||mrt" is really `msgtype` conditional on **`ze_bgp || ze_mrt`** (BMP ⊂ ze_bgp), satisfied by DCE, not a source tag. The spec's contribution is proving that with a tag matrix, plus the first **dependent** feature gate (`ze_bmp` ⟹ `ze_bgp`).
- **Path-nesting inference beat the explicit `requires=` column (deviation).** The spec recommended a manifest `requires=ze_bgp` third field. In implementation, path-nesting (BMP's package lives under `internal/component/bgp/`, a ze_bgp package) proved strictly less invasive: no manifest-syntax change means all five manifest consumers (Makefile awk, `TestBuildTags`, `feature_tags.go`, `stress-repro.py`, `dep_audit.py`) stay untouched, and `dep_audit`'s existing subtree-prefix same-feature skip ALREADY treats bmp→bgp imports as intra-`ze_bgp`-family — so `dep_audit` needed **zero** changes (R-2 was a non-issue). Only `plugin_imports.go` gained `parentTagOf`/`buildConstraint`. The nesting is a true reflection of the dependency (if BMP moved out of `bgp/`, it could no longer import the engine). Verified byte-stable: `plugin_imports.go --check` passes with no diff to existing gate files.
- **Callback signature-sharing (user question).** Of the three reactor-observer callbacks, `HealthPeerCallback` and `MRTPeerCallback` ALREADY share one signature (`PeerLifecycleCallback`: `OnPeerEstablished`/`OnPeerClosed`). The third, `MRTMessageCallback`, is `MessageCallback` (`OnBGPMessage(any, uint8, bool, []byte)`) — raw wire-message delivery, a genuinely different concern. Merging all three into one interface would force `HealthRevert` (which only observes peer up/down) to implement a dead `OnBGPMessage` stub, violating interface segregation (`ai/rules/design-principles.md`). So the callbacks already share signatures everywhere it is correct to; the message observer is rightly distinct. No code change — the two interfaces stay segregated. (Optional future tidy, not done: MRT could collapse its two zero-field bridge types `messageBridge`/`peerBridge` into ONE type implementing both interfaces, registered into both seams; cosmetic, does not change the seam or the reactor's separate `AddMessageCallback`/`AddPeerLifecycleCallback`.)

## Key Design Decisions
| Decision | Alternatives Considered | Rationale |
|----------|------------------------|-----------|
| One spec for both gates | Two specs (ze_mrt, ze_bmp) | The shared `msgtype` drop-condition spans all three tags; the correct proof is a single tag matrix; the two gates' opposite dependency shapes are clearest contrasted together |
| Express `ze_bmp`⟹`ze_bgp` via an explicit manifest dependency column | Path-nesting inference in the generator; Makefile-only coupling | Explicit is greppable and survives a package move; path-nesting is implicit magic; Makefile-only coupling breaks on a manual `go build -tags ze_bmp` |
| Leave `msgtype`/`internal/mrt` untagged; rely on DCE + verify with `nm` | Add `//go:build ze_bgp || ze_mrt` source tags | They are pure libraries with many importers; a source tag on a whole package imported directly is wrong (would break the engine's use); DCE already gives the exact drop-condition |
| Invert MRT bridges via the existing `registry` seam | A new hub-local seam var; keep the direct import (can't — pins MRT) | The RIB-dump provider already uses this exact seam (`GetRIBDumpCallback`); reuse it, do not invent a mechanism |

## Known Limitations
- `ze_bmp` is the first gate that depends on another; the machinery added here is minimal (one dependency edge). A general N-way gate-dependency graph is not built — only the single `ze_bmp`→`ze_bgp` edge is supported. If a future gate needs a different dependency, extend then.
