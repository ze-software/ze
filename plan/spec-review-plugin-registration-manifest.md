## Task

Address the parts of DESIGN-REVIEW finding 8 that are genuinely still open. The finding's
headline remedy ("generate the multi-site registrations from one manifest per plugin") is, for
the two concrete duplications it names, ALREADY IMPLEMENTED (see "Already done" below). Two real
items remain, verified during the finding review:

1. **No single artifact describes what a plugin actually hooks (finding 8, claim 5).** A plugin
   attaches through many distinct, non-aligned seams: the ~31-field `Registration`
   (`registry.go:39-145`: `Families`, `EventTypes`, `SendTypes`, `FilterTypes`, `RPCHandlers`,
   `ConfigRoots`, `CapabilityCodes`, `DoctorChecks`, `InProcessNLRIDecoder`/`Encoder`,
   `InProcessRouteEncoder`, `InProcessConfigVerifier`/`NLRIBuilder`/`RouteParser`,
   `ConfigureEventBus`/`Metrics`/`PluginServer`) PLUS external seams not in `Registration`
   (filterapi filters, attr-mod handlers, observers, OPEN validation, cross-component EventBus
   subscriptions). Nothing enumerates, per plugin, everything it hooks, so an author cannot see
   the full attach surface and unwired/partial features hide (the documented recurring defect,
   `RECURRING-PATTERNS.md:106`).

2. **A plugin declares its YANG twice (within-plugin redundancy).** The same YANG content is
   registered on two registries: `Registration.YANG` (`hostname/register.go:23`, 84 plugins;
   consumed by the plugin registry, `registry.go` `m[reg.Name] = reg.YANG`) AND
   `configyang.RegisterModule("ze-hostname.yang", ...)` (`hostname/yang/register.go`, part of the
   210 `RegisterModule` calls; consumed by the config YANG loader via `LoadRegistered`). Both
   live inside the plugin folder (delete-the-folder still works), but the same constant is
   declared and kept in sync in two places, an avoidable drift source.

Goal: (1) generate/emit one per-plugin hook manifest that enumerates every seam a plugin
attaches through, aggregated across all the seam registries, plus a completeness gate so a new
seam kind cannot be added without appearing in the manifest; (2) let a plugin declare its YANG
once and have both registries derive from it, deleting the duplicate `RegisterModule` calls for
plugins that also set `Registration.YANG`.

**Already done — DO NOT re-implement (verified during finding review):**
- Central hardcoded YANG module list: GONE. `yang_schema.go:136,148` builds the schema from
  `LoadRegistered()` discovery over per-plugin `RegisterModule` (`yang/register.go:16-18`); no
  central list to edit. The "TWO registrations" note in `plan/learned/DESIGN-HISTORY.md`
  ("Configuration: YANG, parser, editor, reload" -> "Load-bearing invariants") is stale history.
- Plugin-list snapshot duplication: GONE. `learned/999-generated-registry-snapshot.md` +
  `all_test.go:43-47` moved the lists to golden files auto-regenerated from the live registry
  ("can never drift from all.go"); `all/all.go` is generated by
  `scripts/codegen/plugin_imports.go` from `register.go` discovery with a `--check` gate.
- Reuse this codegen/discovery infrastructure; the manifest is a NEW consumer of it, not a
  parallel generator.

## Data Flow (MANDATORY - see `ai/rules/data-flow-tracing.md`)

### Entry Point
- Manifest: an operator or CI runs `ze plugin manifest <name>` (or a generated golden per plugin).
- YANG: a plugin's `init()` registers its `Registration` (with YANG content + module name).

### Transformation Path
1. Plugins register hooks at `init()` across multiple registries: the plugin `Registration`
   (`registry.Register`), the filter registry (filterapi), the event/send-type registries,
   OPEN-validation, attr-mod/observer registries, and EventBus subscriptions.
2. Today those registries are queried independently; no code aggregates them per plugin.
3. The manifest generator queries every seam registry, keyed by plugin name, and emits one
   inventory per plugin; a completeness gate asserts every seam-registry kind is represented.
4. For YANG: today `Registration.YANG` (registry) and `RegisterModule` (yang loader) are set
   separately with the same content.
5. After the collapse: `registry.Register` forwards the plugin's YANG (name + content) to a
   registered YANG sink installed by the config package; the duplicate call is removed.

### Boundaries Crossed
| Boundary | How | Verified |
|----------|-----|----------|
| Plugin ↔ N seam registries | init()-time registration across `Registration` + filterapi + event/send + OPEN + attr-mod + EventBus | [ ] |
| Seam registries ↔ manifest | manifest generator reads each registry keyed by plugin name | [ ] |
| registry (leaf) ↔ config yang loader | registered YANG sink (no direct import), like `ConfigureEventBus` | [ ] |

### Integration Points
- `registry.Registration` and `registry.Register` - the primary seam list + the YANG forward point.
- The external seam registries (filterapi, event/send types, OPEN validation, attr-mod, observers,
  EventBus) - the manifest must enumerate each.
- `config/yang.RegisterModule` / `Modules()` - the YANG sink target.
- `scripts/codegen/plugin_imports.go` discovery - reuse to enumerate plugins for the manifest.
- `cmd/ze` plugin subcommand - where `ze plugin manifest` lands.

### Architectural Verification
- [ ] No bypassed layers (manifest reads registries; does not re-derive by scanning source)
- [ ] No unintended coupling (`registry` gains no `config/yang` import; uses a registered sink)
- [ ] No duplicated functionality (reuses `plugin_imports` discovery + `LoadRegistered`, adds no parallel generator)
- [ ] Zero-copy preserved where applicable (n/a; introspection path)
- [ ] Registration over hardcoding — the manifest enumerates registries by discovery; a new seam
  registry registers itself into the manifest set rather than being hardcoded
  (`ai/rules/plugin-self-containment.md`)

## Design Insights
<!-- LIVE — write IMMEDIATELY when you learn something -->
- Finding 8's "one manifest per plugin" splits cleanly: the registration-generation half is
  already implemented (plugin_imports codegen + LoadRegistered + golden snapshots); the
  hook-inventory half ("what does this plugin actually hook") is the unsolved, valuable part.

## Key Design Decisions
| Decision | Alternatives Considered | Rationale |
|----------|------------------------|-----------|
| Manifest reads live seam registries at runtime (`ze plugin manifest`) | Static source-scan generator | Registries are the source of truth; a source scan re-derives and drifts |
| Collapse YANG via a registered sink installed by config | `registry` imports `config/yang` and forwards | The sink keeps `registry` a leaf (no cycle/tier break); mirrors `ConfigureEventBus` |
| Only collapse plugin-owned duplicates (84), leave non-plugin `RegisterModule` (~126) | Force all 210 through `Registration` | Non-plugin modules (CLI cmd, component conf) have no plugin `Registration`; forcing one would be artificial |

## Known Limitations
- The already-solved registration codegen (yang_schema `LoadRegistered`, `all/all.go` via
  `plugin_imports.go`, golden snapshots) is reused, not replaced.
- The augment attach-mode build dependency on its anchor (`plugin-self-containment.md:132-135`)
  is inherent to YANG `augment` and is NOT removed here; it is already guarded by
  `self_containment_test.go` and mitigated by preferring container-merge.
- The overloaded "plugin" placement-tier naming (finding 8) is a docs/naming concern, not
  addressed by this spec.
