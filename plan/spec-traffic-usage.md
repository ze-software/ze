## Task

Port `git.exa.net.uk/tech/development/lan-bandwidth-exporter` into ze as a native,
self-contained system plugin (`internal/plugins/trafficusage`, plugin name
`traffic-usage`).

The plugin attaches eBPF **TCX** programs (ingress + egress) to operator-configured
network interfaces by ifindex, and counts:
- bytes per `(port, protocol)` (ingress = destination port, egress = source port) --
  ALWAYS collected;
- bytes per source IPv4 (ingress) and per destination IPv4 (egress), via LRU hash
  maps with top-talker eviction -- collected ONLY when the `track-ip` config leaf is
  enabled (off by default, to bound metric cardinality).

A userspace poller goroutine periodically reads the BPF maps and publishes the counts
as Prometheus metrics through ze's existing `internal/core/metrics` registry (served
at the existing `/metrics` endpoint). Stale metric series (IPs/ports not seen within a
timeout) are removed to bound cardinality. A `show traffic-usage` CLI command renders
current counts. Configuration is YANG-modeled. IPv4 only, matching upstream.

**KEY CONSTRAINT (user decision):** the eBPF program is built **in pure Go** using
`github.com/cilium/ebpf`'s `asm.Instructions`, assembled in-process and loaded into
the kernel from memory. There is **NO** C source, **NO** `.o` object file, **NO**
clang/LLVM, **NO** bpf2go, and **NO** committed binary blob -- nothing on the
appliance disk. ze "generates" the program in-process at load time. This deliberately
diverges from `spec-l2tp-12-xdp-policing.md`, which commits bpf2go `.o` files.

## Data Flow (MANDATORY)

### Entry Point
- YANG config `traffic-usage { enable; interface <name>...; interval; stale-timeout; track-ip; max-entries }`
  delivered via `OnConfigure`/`OnConfigApply` (JSON sections).

### Transformation Path
1. Plugin parses config -> resolves each interface name to ifindex via
   `iface.GetBackend().ListInterfaces()`; subscribes to iface up/down topics.
2. For each target interface: build the eBPF program + LRU maps **in Go**
   (`asm.Instructions`, `MapSpec`), `LoadAndAssign`, attach ingress + egress via
   `link.AttachTCX` by ifindex. Maps kept in-process (no bpffs pinning).
3. Data plane: NIC RX/TX -> TCX hook -> BPF program parses eth/IPv4/TCP-UDP ->
   updates maps -> `TC_ACT_OK` (always pass; this plugin never drops).
4. Poller goroutine (every `interval`): iterates each map -> `metrics.Registry`
   `*Vec.With(labels...).Set(bytes)`; records last-seen.
5. Stale sweep: series unseen within `stale-timeout` -> `*Vec.Delete(labels...)`.
6. `/metrics` scrape returns the series; `show traffic-usage` renders a snapshot.

## Design Insights

## Core Insight
Pure-Go eBPF (cilium/ebpf `asm.Instructions`) lets ze introduce kernel code with
nothing on disk and no build-toolchain change -- the program is assembled in-process
and loaded from memory. The cost is that the BPF logic is hand-written assembly with
no compiler, so `BPF_PROG_TEST_RUN` per-path tests become load-bearing.

## Key Design Decisions
| Decision | Alternatives Considered | Rationale |
|----------|------------------------|-----------|
| Pure-Go eBPF (asm.Instructions), no C/.o/clang | bpf2go + committed .o (l2tp-12 style); C->generated-Go bytecode | User decision: nothing on disk; self-contained ze binary; no build toolchain change |
| New standalone plugin `traffic-usage` | Extend flow-export | flow-export = sampled records to external collectors; this = unsampled local Prometheus byte counters. Distinct path/output/consumer |
| Per-interface independent maps | Shared maps keyed by ifindex | Mirrors upstream; clean per-interface isolation + reconcile; eviction does not mix interfaces |
| Absolute totals as GaugeVec `.Set` | CounterVec with delta tracking | ze convention (`rate.go` `ze_interface_rx_bytes_total`); `Counter` has no `Set`; `rate()` works on gauges |
| per-IP family OFF by default (`track-ip`) | per-IP ON (upstream parity) | Cardinality safety out of the box; per-port/proto always on; user decision |
| No bpffs pinning | Pin maps to /sys/fs/bpf like upstream | ze owns full lifecycle in one process; in-proc FDs suffice; avoids read-only-root pin-dir concerns |

## Known Limitations
- IPv4 only (matches upstream); IPv6 not counted.
- Monitoring only: never drops/modifies traffic.
- Per-IP top-talker data requires `track-ip` to be enabled.
- TCX requires Linux >= 6.6 (ze kernel 7.0.11 satisfies this); no-op on non-Linux.
