## Task

spec-daemon-drain-before-stop drains BGP, OSPF and IS-IS only as part of a
daemon stop: the drain RPC runs once, after the config fence, and the daemon
exits after it. An operator who wants traffic moved away for maintenance,
without stopping Ze, has no way to ask for it, and no way to bring the router
back into service afterwards.

Owner, 2026-10-13 (drain spec Q-2): "we want runtime but it need design". The
runtime drain, its cancel ("undrain") and its status are wanted, and are
designed here rather than in the stop drain spec.

Bucket: `plan/` (backlog). By `plan/README.md`'s test the release goes out
without it: an operator on the first release can still drain by stopping the
daemon, and meets no wrong answer, only a missing maintenance verb.

Known starting points, to be confirmed at design:

- The stop drain's RPC carries only kind, restart cause and deadline. Any
  field the runtime form needs (an operator reason, for one) is designed
  here, not inherited. The runtime form also needs the reverse RPC (undrain), which the stop drain
  never sends: the stop drain's state lives until the process exits.
- The stop drain runs the handler on one long-lived drain worker per
  connection (states `running` and `stopping`) and refuses a second stop-kind
  `drain` only in `stopping` (its AC-28, as amended 2026-10-14). A runtime
  drain adds requests and states to that worker, and needs no other goroutine
  (`ai/rules/goroutine-lifecycle.md`).
- Form to choose at design: runtime verbs (`request drain`, `request drain
  cancel`), a config leaf that survives a restart (FRR `bgp graceful-shutdown`,
  EOS maintenance units), or both. `request quiesce` already exists in
  `ze-system-cmd.yang` with an unrelated meaning (an async-work barrier), so
  the name must not collide with it.
- RFC 8326 Section 4.3 asks for "configuration knobs that utilize the
  GRACEFUL_SHUTDOWN community to inform BGP neighbors in preparation for an
  impending neighbor shutdown". A per-neighbour form would close the partial
  Section 4.3 row the stop drain spec records.

Owner context for the design (2026-10-13, carried by the main thread): the runtime form covers bgp, ospf and isis; it reuses the stop drain's mechanism and its one config name `drain-on-shutdown <seconds>` (stop spec Q-6: the same name for every protocol); it steers injected externals and stub networks with the stop spec's headroom values (stop spec Q-8 (b): IS-IS wide 0x7f000000, narrow 63, OSPF type 2 external 0xfffffe, type 1 external 0x7fffff, stub links and OSPFv3 Router-referencing prefixes 0xffff); and the RFC freeze stays lifted for the RFC 8326 sender side only (stop spec Q-4 (a)). No second mechanism is built (`ai/rules/no-layering.md`): every runtime path below is the stop drain's path, with the one-shot parts of it replaced by re-enterable ones.

Design in one paragraph: two daemon-wide verbs, `request drain` and `request undrain`, each with an optional `protocol <name>` filter, and `show drain`. The plugin server fans out the stop drain's `drain` RPC with a new kind, `maintenance`, and a new reverse RPC, `undrain`, to every drain-registered plugin (or the one the filter names). Each plugin enters or leaves the same drain state its stop handler uses, re-advertises, and answers without waiting: the wait belongs to the operator. The stop spec's SDK drain worker gains the `maintenance` and `undrain` requests and the `undrained`/`drained` states. The stop spec's BGP drain scope gains a peer set. The stop spec (amended 2026-10-14) applies the drain at write time as f(U, scope) in `Session.writeUpdateBody`, and bgp-rib's `ribOut` stores U, the undrained egress body, so drain and undrain are one operation, "re-advertise with the current scope", over the existing `ribOut` walk, and the undrain is exact by recomputation (Q-5 (d)) with no record of what the drain changed. The IGPs restore by construction, because the drain never rewrites their stored config or prefix sets. Under Q-7 (a), `request peer <selector> drain` / `undrain` adds the per-neighbour RFC 8326 knob. Every choice below that an owner question governs is written under the option the owner chose and names the question.

**Key insights:**
- The stop drain is implemented nowhere yet: `grep -rn 'OnDrain\|DrainBudget\|drain-on-shutdown'` over Go and YANG finds only an unrelated `parseDrainBudget` in `internal/le/rfc` (2026-10-14). This spec lands after it (Dependencies) and adds to the worker, the scope and the per-epoch walk that it builds.
- Every runtime path is a stop path with the wait removed: the operator, not a timer, decides when the drain ends.
- The BGP undrain is the drain with another scope (redesign 2026-10-14, `challenge-undrain-recompute.md`). The drained body is a pure function f(U, scope) of the undrained egress body U, computed by the writer at every write; `ribOut` stores U, which no scope changes, so a walk over `ribOut` under any scope sends each key in that scope's form, and f(U, undrained) = U. Nothing has to be inverted, so nothing has to be recorded. Rounds 1 to 4 kept finding holes because the replay source was f's output, which f cannot invert (it loses "65535:0 already present" and the LOCAL_PREF it replaced).
- The barrier after each walk is kept for two reasons only: `drained` and `undrained` are answered after the walk's writes are on the wire, and the withhold, which compares f's change under the scope in force with its change under `replaced`, is right only for a replay written before the next scope change. Which form a peer ends with does not depend on it, because every write computes its form under the scope in force at the write.

## Data Flow (MANDATORY - see `ai/rules/architecture.md`)

### Entry Point

| Entry | Handler | Effect |
|-------|---------|--------|
| `request drain` | `ze-plugin:system-drain` (`internal/component/plugin/server/drain_runtime.go`) | fan-out `drain` kind `maintenance` to every drain-registered plugin with a live connection |
| `request drain protocol <name>` | same | fan-out to the one plugin the `redistevents` disposition of `<name>` names (`drained by <plugin>`); a name whose disposition is `no drain: <reason>` is refused quoting the reason; an unknown name is refused with the closest valid name |
| `request undrain [protocol <name>]` | `ze-plugin:system-undrain` | fan-out `undrain` to the same set |
| `show drain [protocol <name>]` | `ze-plugin:show-drain` | the server's drain record (Q-4 (a)); the optional filter resolves as `request drain protocol <name>` does and keeps one row, which is how bgp-rib reads the BGP scope at its start (NOTE-1) |
| `request drain record` (hidden, ISSUE-3) | `ze-plugin:system-drain-record`, a builtin declared in `ze-system-cmd.yang` under `ze:hidden true` (design 5, ISSUE-1) | dispatched only by a drain-registered plugin that changed its own scope (the BGP plugin removing a reloaded peer), with `sdk.DispatchCommand` (the string form): replaces that plugin's row `scope` and `epoch` under the record mutex; refused for any other caller, an operator included (A-13) |
| `request peer <selector> drain` / `undrain` (Q-7 (a)) | `ze-bgp:peer-drain` / `ze-bgp:peer-undrain` in the BGP peer command package, `RequiresSelector: true` | resolves the selector, refuses iBGP, and calls the plugin server's runtime drain entry for the one BGP plugin with the peer set: one `drain` kind `maintenance` (or `undrain`) RPC carrying `peers`, so the request reaches the BGP drain worker by the same RPC and channel as `request drain` (N-5); the scope gains or loses those peers |
| SIGTERM or any stop entry while drained | the stop spec's hub drain | Q-2 (a) remainder wait |
| respawn of a drain-registered plugin while drained | plugin server, on the plugin's ready stage | Q-1 (a) re-drain |

### Transformation Path

1. The dispatcher runs the handler. The handler refuses when the daemon is stopping ("daemon is shutting down; drain refused", and the same for undrain). It sets its deadline at entry, now plus `RuntimeAckBudget`, and acquires the server's runtime drain semaphore, a capacity-1 channel the handler acquires in a select against that deadline (a `sync.Mutex` cannot be taken under a deadline, round 4 N-3), so one transition runs at a time and a second request waits for it; the wait counts against that one deadline, so the command always answers inside `RuntimeAckBudget`. A request that has not acquired the semaphore by its deadline sends nothing and answers every target `refused` with "an earlier drain or undrain is still in progress; run `show drain` to follow it, then run the command again" (round 3, I-1).
2. The handler resolves the target plugins, then updates the drain record (one row per target: state `draining` or `undraining`, `since` now, `requested-by` the command's user, `scope` the row's scope with `router` set or cleared, or for a per-peer request with the peers added or removed, so a whole-router request keeps the row's peers and a per-peer request keeps its `router`; ISSUE-3) before the fan-out, so `show drain` reads the request while it runs.
3. The fan-out is the stop spec's server fan-out, called with the RPC to send (`drain` kind `maintenance`, or `undrain`) and the deadline step 1 set, `RuntimeAckBudget` being one constant declared in `pkg/plugin/rpc` beside the stop ceiling and below `DefaultCommandTimeout` (20 s against 30 s, the inequality held by a test). The handler starts no goroutine per command (round 2, N-2; `ai/rules/goroutine-lifecycle.md`): a goroutine per target would be started per request, because a runtime command can repeat for the life of the process. Calling the targets one after another on the dispatcher goroutine is refused for a reason that forces the calls to overlap: `CallRPC` blocks until the answer or the context ends (`pkg/plugin/rpc/mux.go`, `conn.go`, `internal/component/plugin/ipc/rpc.go`, read 2026-10-14), so a BGP walk over a large table that runs to the shared deadline would leave every later target with an expired deadline and no request sent, and a per-call budget instead would push the command past `DefaultCommandTimeout`. The calls overlap through the permitted shape, a long-lived worker reading a channel: the plugin server's drain callers, one per drain-registered plugin generation, which the stop spec builds (its Data Flow step 4 and its `server/drain.go` row: started by `superviseProcess` for a generation whose registration declared a `DrainBudget`, returning when the generation ends; each takes a request from its channel, makes the blocking call under the generation's context rather than the drain deadline, and posts the answer to the capacity-1 reply channel the request carries). The handler queues one request per target, then reads the reply channels one after another under the one shared deadline; a reply after the deadline still reaches the record (step 5), because the call was not cancelled at the deadline. The runtime fan-out is the stop spec's fan-out function over the same callers, called with a different RPC and deadline, so this spec adds a second user of that function and replaces nothing (as runtime review r1 I-1 did for the SDK worker).

   A stop never waits behind a queued runtime request (round 3, N-2). The stop spec gives each caller one request slot, the stop slot (its Data Flow step 4.2); this spec adds a runtime slot beside it, also capacity 1, and the caller's rule for choosing: before it takes a runtime request it takes a stop request that is waiting, and when it takes a stop request it answers a runtime request still in the runtime slot `refused` with "daemon is shutting down; drain refused" (or "undrain refused") without sending it. A runtime call already in flight is not cancelled: a cancelled mux call drops its answer (stop spec, Key Design Decisions), and the plugin's drain worker would finish that handler before serving the stop in any case, because it serves one request at a time to completion (state machine below). The stop request is sent when that call returns, bounded by the stop deadline, past which the stop names the plugin late, as for any slow plugin. Because a caller makes one call at a time, the plugin's drain worker never holds a queued runtime request in front of a stop. A runtime send to a caller whose runtime slot is still full (an earlier request still waiting there behind a late call) selects on the deadline and the caller's done channel; one not placed by the deadline is answered `refused` with "an earlier drain or undrain of <plugin> is still in progress; run `show drain` to follow it, then run the command again", never `pending`, because a request that was never queued has no answer to wait for.
4. The SDK drain worker serves the request (state machine below). The handler for kind `maintenance` enters the drain state and answers when the state is in force and its effect has been emitted: for BGP when the walk has returned; for OSPF and IS-IS when every LSA or LSP the state changes has been installed in the LSDB with the drained value and queued for flooding, which for OSPF can be after a MinLSInterval deferral (OSPF and IS-IS below, r1 I-6). Scheduling an origination is not emitting it. It never waits a configured time. `undrain` leaves the state the same way and answers on the same rule. An answer that the emission delays past the server's deadline arrives late and resolves the row (step 5, A-4).
5. The server collects the answers. A plugin that answers by the deadline moves to `drained` or `undrained` with `acknowledged`; one that has not stays `draining` or `undraining` with `pending`, and its late answer, which the RPC layer still delivers on the request's own channel (stop spec A-11), updates the row when it arrives. A refusal records `refused` and its reason. A failure after the change was applied (BGP's walk, below) records `failed` and its reason, and the row stays in `draining` or `undraining`, which `show drain` presents as incomplete with that reason (redesign round 1, I-3). The command answers one structured row per target: `plugin`, `result` (`drained`, `undrained`, `unchanged`, `pending`, `refused`, `failed`), `reason` when refused or failed, `elapsed-ms`. A `pending` row carries the reason "still in progress; run `show drain` to follow it", because the plugin's handler runs its walk and barrier to completion whatever the server's deadline (BGP below), so the late answer is certain to come and resolves the row. No client deadline exists to shorten this (A-10, validated round 4): the operator sees the command's answer when the handler returns, which the deadline step 1 set bounds at `RuntimeAckBudget`. That server-side deadline is the only bound on a hung drain: past it the command answers the slow target `pending`, and meanwhile `show drain` shows that target's row in state `draining` (or `undraining`) with result `pending`, its `since` and `requested-by`, until the late answer moves it to `drained` or `undrained`.
6. A target already in the requested state answers `unchanged` and re-advertises nothing (idempotent; not an error), unless its worker is "walk owed", when it runs the walk again (state machine below, ISSUE-2). The plugin's worker decides it, never the server: the server sends every request to its targets whatever their row says.

**Plugin drain state machine** (SDK drain worker, one per connection):

| State | `drain` kind `maintenance` | `undrain` | `drain` kind `stop` / `restart` |
|-------|----------------------------|-----------|---------------------------------|
| `undrained` | handler enters drain; -> `drained` | answer `unchanged` | the stop spec's handler; -> `stopping` |
| `undrained`, walk owed | handler enters drain (the new scope's `replaced` is `unconfirmed`); -> `drained` | handler runs the walk again at the scope in force (Q-9 (a)), never `unchanged`; stays `undrained` | the stop spec's handler (its scope change records `replaced` `unconfirmed`, so nothing is withheld); -> `stopping` |
| `drained` | answer `unchanged` | handler leaves drain; -> `undrained` | the stop spec's handler with Q-2 (a): no new re-advertisement, wait the remainder, or the full `drain-on-shutdown` when a walk owed set during this router drain voided it (ISSUE-2, design 5); -> `stopping` |
| `drained`, walk owed | handler runs the walk again at the scope in force (Q-9 (a)), never `unchanged`; stays `drained` | handler leaves drain (the new scope's `replaced` is `unconfirmed`); -> `undrained` | the stop spec's handler with the owed walk run first at the scope in force, then the full `drain-on-shutdown` wait, never the Q-2 (a) remainder, because the cells re-advertised now have had no convergence time; -> `stopping` |
| `stopping` (terminal) | refused, naming the plugin | refused, naming the plugin | refused, naming the plugin (the stop spec's AC-28) |

"Walk owed" (design review round 4, ISSUE-2) is a qualifier the BGP handler sets on its worker whenever a walk it ran answers `failed` (a failed `DrainEventsApplied`, a refused walk, a walk error), whatever request the walk served: whole-router, per-peer, a retry, or a reload's peer removal (Respawn and reload, below). Only an unfiltered walk that completes, with its barrier, clears it (design 5, ISSUE-2). So every walk the worker serves while a walk is owed runs unfiltered, whatever the request: a per-peer drain or undrain, or a reload's internal peer-undrain, served while walk owed, makes its scope change as asked and then walks the whole table, never the peer-filtered walk, because the owed walk may be the router's and a peer-filtered walk re-advertises only that peer's cells. A peer-filtered walk that completes while no walk is owed clears nothing, because there is nothing to clear; one that fails sets walk owed like any other. Clearing walk owed does not restore the Q-2 (a) remainder: a walk owed set while `router` holds also voids the remainder for that router drain, so a later stop waits the full `drain-on-shutdown` even when a later unfiltered walk has cleared walk owed, because the remainder is counted from the drain's entry and the cells that walk re-advertised were tagged only when it ran (AC-37 (e)). The void is the worker's, like walk owed, and ends when `router` is cleared. A failed walk still moves the state as the request asked: the scope change stays applied (BGP, entering a runtime drain, failed walk), so the state names the scope in force, and only the re-advertisement of what was already sent is missing, which is what "walk owed" records. A repeated request that would answer `unchanged` (the same `router` value, or peers already in or already out of the scope) runs the walk again instead, unfiltered, at the scope in force and the current epoch; a request that changes the scope is served as a change, its `replaced` recorded `unconfirmed`, so its walk withholds nothing and writes every key in the new scope's form. So a failed drain followed by `request undrain` undrains (AC-37), and a stop after a failed drain re-advertises (AC-37 (c)). The OSPF and IS-IS handlers run no walk and answer on emission, so they never set it.

The stop spec's `running` state is `undrained` and `drained` here; `stopping` is the stop spec's. The state is the router scope's: a `drain` kind `maintenance` or an `undrain` whose RPC carries `peers` (a per-peer request, Q-7 (a)) changes only the BGP scope's `peers` and leaves the worker's state as it is, so a plugin with only peers drained is `undrained` with a non-empty peer scope, and `show drain` shows it in `scope` (r1 I-5). A per-peer request in `undrained` or `drained` is served by the BGP handler (the scope change and a peer-filtered walk, or an unfiltered walk when a walk is owed, ISSUE-2) and answers `drained`, `undrained` or `unchanged` for that peer set; in `stopping` it is refused like every other request.

The worker serves requests in arrival order and serves each to completion before it reads the next: for BGP that is the walk and the `barrierPeer` after it, both run under the connection's context, never under the request's deadline (round 3, I-1). So an `undrain` sent while a `drain` re-advertisement runs is served after it, and no scope change is served while an earlier one's walk runs or its replays are still queued behind forwards. The answer to the server can then arrive after the server's deadline, which A-4 and step 5 already carry (the row stays `pending` until it does). It reads a channel the event loop writes, answers each request's own ID, and returns when the connection closes (`ai/rules/goroutine-lifecycle.md`). It is the stop spec's worker: this spec adds the requests and states above to it. The state is the stop spec's one atomic per connection, shared by the event loop and the worker (stop spec, amended for round 2 I-3): the event loop moves it to `stopping` when it queues a stop-kind request and refuses every request that arrives in `stopping` before queuing it, this spec's `maintenance`, `undrain` and peer-scope requests included; the worker moves it between `undrained` and `drained` when a handler has answered, `failed` included (the table above), and never out of `stopping`. "Walk owed" is not part of that shared atomic: only the worker reads and writes it, between requests it serves one at a time, so it needs no lock.

**BGP, entering a runtime drain** (kind `maintenance`). The stop spec's handler steps 1 to 3 run unchanged in meaning, with these differences:
- Before step 2 the handler resolves the drain-replay command's owner, as the stop spec's step 3.1 does. When the command has no owner (bgp-rib not loaded), a runtime drain, whole-router or per-peer, is refused before the scope changes, because without the walk an undrain cannot restore the paths written during the drain, and they would stay tagged and at LOCAL_PREF 0 with no end (r1 I-3; `ai/rules/user-facing-errors.md`). The answer is `refused` with the reason: "bgp drain refused: the bgp-rib plugin is not loaded. Without it Ze cannot restore your routes when you undrain. Load the bgp-rib plugin, then run the command again." The stop drain keeps the stop spec's rule (log and continue), because a Cease follows it.
- A failed walk (redesign round 1, I-3). After the scope change, the walk can fail three ways: `DrainEventsApplied` returns an error (a deadline, a stopped owner, or a delivery failure bgp-rib's process retains for its lifetime: "Success never clears it", `process/delivery.go` `deliveryOwnerError`), bgp-rib refuses the walk (an older epoch), or the walk returns an error. In each case the BGP handler answers its row `failed`, never `drained` or `undrained`: Ze reports a BGP drain or undrain complete only after a completed walk and its barrier. The scope change stays applied, so every live write after it is written under the new scope; only the re-advertisement of what was already sent is missing. The reason names the operation, the error and the next step, for example: "bgp drain incomplete: routes already sent to peers were not re-advertised with GRACEFUL_SHUTDOWN (<returned error>). New routes are sent drained. Run `request drain` again to retry." (`request undrain` and "without GRACEFUL_SHUTDOWN" for an undrain.) The worker moves to the state the request asked for and marks itself "walk owed" (state machine above, ISSUE-2). Under Q-9 (a), a repeated request whose scope is already in force but whose last BGP walk failed runs the ordering sequence and the walk again with the current epoch, and is not answered `unchanged` (AC-3 applies only after a completed walk); the opposite request is served as a scope change whose `replaced` is `unconfirmed`, so its walk withholds nothing (AC-37); bgp-rib accepts a walk of an equal epoch (stop spec, "a walk of an equal or newer epoch replaces the state"). A retained delivery failure makes every retry fail the same way until bgp-rib's process is replaced; the reason then says so: "bgp-rib lost a sent-route event earlier and cannot confirm its table; restart Ze to clear it" (Known Limitations).
- Step 2 replaces the stop spec's drain scope with `router` true. This spec adds one field to the scope; every change of either field increments the epoch, as in the stop spec.

| Field | Type | Description |
|-------|------|-------------|
| `router` | boolean | the stop spec's field: whole-router drain (runtime `request drain`, or the stop drain) |
| `peers` | set of destination peers | added here: per-neighbour drain (Q-7 (a)); empty otherwise |
| `epoch` | unsigned 64-bit counter | the stop spec's field: increments on every change of `router` or `peers`; never reset in the process |
| `replaced` | the scope's own fields (`router`, `peers`), no `epoch`, or `unconfirmed` | the stop spec's field, gaining `peers`: the scope value this change replaced, read only by the withhold of a `drain`-kind or `undrain`-kind replay and by the refresh demotion (a replay is a refresh only when the scope in force equals `replaced`, which only the initial scope does, ISSUE-1). `unconfirmed` (added here, ISSUE-2) is recorded instead of the replaced value when the change is served while the worker is "walk owed": the replaced scope's own walk never completed, so a peer may hold a key in either form, and a replay judged against `unconfirmed` is never withheld and never demoted |

- Step 3's walk is the stop spec's `request bgp rib drain-replay` with the new epoch and the cut M, plus an argument `kind drain` (this spec adds `kind undrain` and, for a per-peer request, the peer filter). bgp-rib's per-epoch snapshot, its refusal of an older epoch and its skip of entries above the cut are the stop spec's, unchanged.
- After the walk returns, and before it answers, the handler runs the forward pool's `barrierPeer` (`forward_pool_barrier.go`) for every destination the walk covered, under the connection's context and never under the request's deadline, so the handler answers `drained` only once every replay write the walk queued behind forwards is on the wire, and the next scope change is served after them (round 2, I-2; round 3, I-1; A-9). The form a peer ends with does not rest on it: every write computes f(U, scope in force) at the write, so a replay written late is written in the current scope's form. The withhold does: it compares f's change under the scope in force with its change under `replaced`, the scope the current change replaced, which is right only for a replay written before the next change. `barrier` returns `ctx.Err()` when its context ends (`forward_pool_barrier.go`), so a barrier bounded by the request's deadline would let the next change be served with this walk's replays still queued; the walk is run under the same context for the same reason. The barrier ends early only when the connection closes, and then no further scope change is served on it. This holds for every walk, `drain` or `undrain`, whole-router or peer-filtered.
- The stop spec's withhold applies unchanged (redesign 2026-10-14). `ribOut` holds U for every path, written live during a drain or not, so a re-drain's walk replays U and the withhold's comparison of f's changes is right after any number of undrains.
- Step 4 does not wait: the handler answers after the walk and the barrier return, with the stop spec's four counts (re-advertised, withheld, receipt replays refused at an owed key, sent untagged (no room)) as deltas over the walk; the server records the last of them on the BGP row as `sent-untagged` (Q-4 (a); redesign round 2, N-1).

**The drain verdict with a scope.** The stop spec's table is the `router` row, unchanged. With `router` false and `peers` non-empty (Q-7 (a)), the verdict reads, per write, whether the destination is in `peers` and whether the path's provenance is "learned from a peer in `peers`":

| Destination | Originated by Ze | Learned from a drained eBGP peer | Learned from another eBGP peer | Learned from an iBGP peer |
|-------------|------------------|----------------------------------|--------------------------------|---------------------------|
| a drained eBGP peer, not a route-server client | tag | tag | tag | tag |
| a drained eBGP route-server client | tag | untouched (RFC 7947 Section 2.2.4) | untouched | untouched |
| another eBGP peer, not a route-server client | untouched | tag (Section 4.2 inbound bullet: the received path carries the community onward) | untouched | untouched |
| another eBGP route-server client | untouched | untouched (RFC 7947 Section 2.2.4) | untouched | untouched |
| iBGP peer | untouched | tag, LOCAL_PREF 0 (stop spec Q-10 substitution) | untouched | untouched: reflection, RFC 4456 Section 10 |

With `router` true the `router` table answers whatever `peers` holds. The send-community mask (stop spec Q-11 (a)) applies to every cell as it does today. The provenance a peer-scope cell needs ("learned from which peer") is the same `*Peer` the writer already reads (stop spec, writer and provenance table): for a forward, the owner path the existing `fwdItem.writePath` yields (`fwdItem.receivedPeer`, or the section span's source), with no new field (redesign round 1, I-2), and for a gated receipt write the adj-out owner's `source`; an origination has owner nil.

**No drain record** (Q-5 (d), redesign 2026-10-14). The undrain needs no inverse, because no write ever loses U: the writer computes f(U, scope) from U at every write, the sent event carries U, and `ribOut` stores it. f adds 65535:0 only when U lacks it, so a GRACEFUL_SHUTDOWN the source or the export policy put in U is in the undrained form too, and f(U, undrained) = U byte for byte keeps it where it was (RFC 8326 Section 4.2 has the initiator apply "an inbound BGP route policy on the EBGP session to be shutdown. This policy tags the paths received over the session with the GRACEFUL_SHUTDOWN community and sets LOCAL_PREF to a low value.", so a path can arrive carrying the tag). The LOCAL_PREF a "tag, LOCAL_PREF 0" cell replaces is U's own, so it needs no record either. Nothing is stored per key while drained, and a session reset needs no rule: the new session's initial table is written under the scope in force (AC-23), and `ribOut` holds U for it as for any write.

**BGP, leaving a runtime drain** (`undrain`):
1. The handler replaces the scope (`router` false, or the peers removed) with one value whose epoch is the next and whose `replaced` is the scope it replaces, as every scope change does in the stop spec. Nothing else is kept: no table of earlier scopes, because a replay is judged only against the change it was walked for, and the barrier (step 4) puts every replay of a walk on the wire before the next change is served.
2. The ordering sequence is the stop spec's step 3, unchanged: per-peer `writeMu` take-and-release, the cut M read after the last release, `DrainEventsApplied` on bgp-rib's process, then the walk `request bgp rib drain-replay` with the new epoch, the cut and `kind undrain`. Its commands carry `replay: undrain`, a fourth value of the existing `replay` key (the stop spec's replay kind gains it: none, refresh, drain, undrain), parsed by `replayFromMeta` and refused when unknown. No other meta key is added.
3. The writer computes f(U, scope in force) for every write, as the stop spec does; for a key the undrain leaves untouched that is U itself. An `undrain`-kind replay is withheld, and counted withheld, by the stop spec's withhold rule read with `undrain` in place of `drain`: when f's change to U under the scope in force equals its change under `replaced` (RFC 4271 Section 9.2). So a key the drain changed is always written, in its undrained form, and a key the drain left untouched is withheld, because the peer already holds U for it. The scope in force is undrained and differs from `replaced`, so the write is never demoted to a refresh: the stop spec's demotion, as amended in design review round 4 (ISSUE-1), applies only to a replay whose scope in force equals its `replaced`, the initial scope, and the same holds for every peer-only `drain`-kind walk, which also runs with `router` clear. When `replaced` is `unconfirmed` (the drain's walk failed, ISSUE-2), nothing is withheld: every key is written as U, the untouched ones included, because the peer may hold either form. A replay older than a live write of the same key is refused by `allow`'s revision check for `adjOutExpected` (`session_ownership.go`), so an undrain walk never overwrites a newer live write, which was itself computed under the scope in force. Replay groups never mix forms: `ribOut` holds U, and two keys whose pre-drain LOCAL_PREF differs have different `AttrHandle`s.
4. After the walk returns the handler runs `barrierPeer` for every walked destination (as on entry, under the connection's context), then answers with re-advertised (undrain kind), withheld and sent-untagged counts, as deltas over the walk.

**No in-flight window, either way** (redesign 2026-10-14). A body queued before a scope change and written after it is computed at its write, under the scope it loads inside `writeMu`, so it goes out in the new scope's form whichever way the change went; nothing is judged on a forward rail, nothing is marked, and bgp-rib answers no event with a further replay. The ordering sequence (step 2) puts every write made before the change in the walk's snapshot, as U; the cut M makes the walk skip every write made after it, which already went out under the new scope. The one duplicate the stop spec accepts (a write between the scope store and the moment M is read, with a message ID at or below M, replayed once more in the same form, its Known Limitations; redesign round 1, N-2) is accepted here for both directions.

**OSPF and IS-IS.** Kind `maintenance` runs the stop spec's `stop` handler body without its wait: OSPF sets the drain state on the v2 engine and every running v3 address-family engine, runs `originateSelfLSAs` and `reconcileExternalImports`, and answers once every self-originated LSA the drain state changes (the Router-LSA, the v3 Router-referencing Intra-Area-Prefix-LSA, every injected external and NSSA LSA) is installed in the LSDB with the drained value and queued for flooding, on every engine. An origination asked for inside MinLSInterval is deferred and published by the engine maintenance worker's ticker (Current Behavior, `startNeighborRetransmitLoop`), so the handler waits for that publication, signalled by the engine when the deferred origination installs, never answering at the call that only scheduled it (r1 I-6). No such signal exists today (round 2, N-1), so the engine gains one, the self-origination installed signal, and the LSDB gains the answer the signal needs (round 3, I-3).

The LSDB answer. Today the origination functions return one boolean that is false both when the body is unchanged and when MinLSInterval deferred a changed body: `OriginateRouter` (`lsdb/origination.go`) returns `false` from the `existingSelfBodyUnchanged` branch and from the `nextOwnSequence` refusal alike, `OriginateExternal` returns `false` with the comments "idempotent: identical body already originated, no change" and "rate-limited by MinLSInterval, not a failure", and `OriginateFromTopology` folds the Router-LSA results into a count that `originateSelfLSAs` (`instance.go`) ignores. A pass that was only deferred is therefore indistinguishable from one that had nothing to change. Each origination function that builds a drain-relevant LSA returns an outcome with three values instead, `originated`, `unchanged` and `deferred` (MinLSInterval refused the sequence for a changed body): `OriginateRouter`, `OriginateExternal` and `OriginateNSSA` (`lsdb/nssa.go`) in the LSDB, which each run the change check, `nextOwnSequence` and `installOriginated` inline and change in place, and the OSPFv3 builders. Every OSPFv3 builder reaches the LSDB through the generic `lsdb.OriginateSelf` (`lsdb/origination.go`), which returns `(h, false)` from its `existingSelfBodyUnchanged` branch and from its `nextOwnSequence` refusal alike (round 4, I-1, read 2026-10-14). `OriginateSelf` has fifteen non-test callers, most of which build LSAs the drain does not change (the v3 Network-LSA, link, summary, Router Information, segment routing, `inject_v3.go`, `lsdb/opaque_as.go`), so it keeps its boolean, and the LSDB gains a three-valued sibling, `OriginateSelfOutcome`, that runs the same sequence and returns the header and the outcome; `OriginateSelf` returns the sibling's `originated` as its true, so the sequence is written once. The drain-relevant v3 builders call the sibling and return the outcome: `v6OriginateRouter` and `v6OriginateIntraAreaPrefix` (`origination_v6.go`), `v6OriginateExternalLSA` (`origination_v6_external.go`), `v6OriginateNSSALSA` (`origination_v6_nssa.go`) and `v6OriginateTranslatedExternal` (`nssa.go`). `v6OriginateNSSALSA` also returns before sequencing: false for a zero router ID or the backbone area, and the result of `PurgeNSSAKey` when the P-bit requires a Forwarding Address it lacks. Those returns are no deferral, so the zero router and the backbone area map to `unchanged`, and `PurgeNSSAKey` maps to `originated` when it flushed and `unchanged` when it did not; nothing on those branches is left deferred. The sibling's own refusals (a nil encoder, a zero advertising router) map to `unchanged` the same way. `OriginateFromTopology` and `v6OriginateSelf` report whether any Router-LSA (and, for v3, any Router-referencing Intra-Area-Prefix-LSA) was left deferred, and `reconcileExternalImports` (`redist_wiring.go`, through `injectExternalLocked`, `applyDefaultInformation` and `applyNSSADefaults`) reports whether any Type 5 or Type 7 LSA was left deferred. Every caller of a changed function reads the outcome where it read the boolean (`default.go`, `redist_wiring.go`, `nssa.go`, `origination_v6.go`, `lsdb/origination.go`), each mapping `originated` to its old true. The LSAs the drain does not change keep their boolean: the v2 Network-LSA (`OriginateNetwork`) and Summary-LSA (`OriginateSummary`) builders are not changed, and every `OriginateSelf` caller not listed above (the v3 Network-LSA, link, summary, Router Information, segment routing, `inject_v3.go`, `lsdb/opaque_as.go`) keeps calling `OriginateSelf` and reading its boolean.

The signal. A drain origination pass is one run of `originateSelfLSAs` followed by `reconcileExternalImports` under one drain state value read at its start. The drain handler runs one; the maintenance worker's ticker in `startNeighborRetransmitLoop` already runs both on every tick, which is the pass that publishes a deferred origination. A pass that leaves no drain-relevant LSA deferred records the drain state value it read and advances a per-engine installed generation, and wakes every waiter by closing the current wait channel and replacing it, under a mutex of its own that guards the generation, the value and the channel. A pass that leaves any drain-relevant LSA deferred advances nothing, and neither does the `originationNotify` case, which runs `originateSelfLSAs` alone and so cannot vouch for the externals. The drain handler reads the generation when it sets the state, and answers once a later generation has installed with the requested drain state value. It waits under the connection's context, like BGP's walk and barrier (round 3, I-1), so the worker serves the next request only after the effect is installed; a deferral lasts at most MinLSInterval plus one tick, and an answer past the server's deadline is the late answer step 5 carries. The OSPFv3 builders' return values were read in round 4 (A-11, validated). IS-IS needs no signal: `originate` installs and arms flooding before it returns. IS-IS sets the drain state and calls `originate`, which installs LSP 0 and arms its flooding synchronously (no generation pacing exists, Current Behavior), and answers after it returns. `undrain` clears the state and runs the same re-origination, answering on the same emission rule, which restores config's costs, the stored external metrics and prefix metrics, and LSP 0's overload bit to `cfg.Overload`. Kind `restart` is not reachable from a runtime command. The OSPF RFC 7770 stub-router capability bit stays derived from config, as the stop spec leaves it.

**Stop while drained (Q-2 (a)).** The stop drain RPC reaches a plugin in state `drained`. BGP: the scope already holds `router`; the handler re-advertises nothing new and waits `drain-on-shutdown` minus the time since the runtime drain's entry, floored at zero, bounded by the deadline as today, or the full `drain-on-shutdown` when a walk owed set during this router drain voided the remainder (state machine, ISSUE-2). The handler makes no scope store: no new scope value, no epoch increment, no `replaced`, so the scope in force stays the runtime drain's. The refresh demotion relies on that (a replay is a refresh only when the scope in force equals `replaced`, ISSUE-1): a store of the same `router` value would record a `replaced` equal to the scope in force, and every replay judged under it would be demoted to a refresh. The walk-owed exception below makes no store either: its walk is a retry at the scope in force and its epoch (Q-9 (a)). OSPF and IS-IS: the state is already in force; same remainder rule. The record, `show drain` and the counts read `stopping` from then on. A BGP worker that is `drained` with a walk owed (its last walk failed, ISSUE-2) is the exception: the stop handler first runs the owed walk at the scope in force, so the routes the failed walk left untagged are re-advertised with GRACEFUL_SHUTDOWN, and then waits the full `drain-on-shutdown`, because those cells have had no convergence time (AC-37 (c)). A walk that fails again is handled by the stop spec's rule (logged, the stop continues).

**Stop after a peer-only drain (r1 I-5).** A BGP plugin whose scope holds only `peers` is in state `undrained`, so the stop drain RPC runs the stop spec's handler unchanged: step 2 sets `router` (a new epoch), the step 3 walk re-advertises every path the verdict now changes and withholds every key whose f change under `router` equals its change under the peer-only scope it replaced (the peer already holds that form), and the handler waits the full `drain-on-shutdown`, because the cells first tagged at stop have had no convergence time. No remainder is computed from the peer drain's age.

**Respawn while drained (Q-1 (a); design review round 4, ISSUE-3).** The server record's `scope` (Q-4 (a)) is what a re-drain replays, never the row's state: a peer-only drain leaves the BGP worker `undrained` with a non-empty peer scope (state machine above), and a row left `draining` by a failed walk still records a drain the operator asked for. When a drain-registered plugin whose record row holds a non-empty scope reconnects after a respawn, the server sends it, once it has delivered its config and before it reports the plugin ready, `drain` kind `maintenance` when the scope holds `router`, then `drain` kind `maintenance` with `peers` when the scope holds peers, in that order, each awaited before the next (while `router` holds it answers every cell, so no write between the two goes out less drained than the record asks), and logs "re-applying runtime drain to <plugin> after respawn". A plugin that refuses or does not answer is logged and its row shows `refused` or `pending`. A plugin removed by commit (`delete ospf`) loses its row, logged "runtime drain of <plugin> ended: plugin removed by commit". A router-plus-peers scope therefore comes back with both, so AC-22's independence of the two survives a respawn (AC-38).

How `peers` is keyed. The record, the RPC's `peers` field and the walk command name each drained peer by its config name, the `bgp peer <name>` / `bgp group <g> peer <name>` list key, and carry its remote address beside it. The name is the identity: `ResolveBGPTree` refuses a peer name used twice anywhere in the config (`internal/component/bgp/config/resolve.go`, read 2026-10-14: "duplicate peer name (already used by %s)", "duplicate peer name %s (already defined in another group or as standalone)"), the name is the CLI selector the operator typed, and it survives a respawn and a reload, which a `*Peer` does not. The address rides beside it because bgp-rib keys `ribOut` by `netip.Addr` (`rib.go`) and reads `SourcePeer` as an address, so the walk filter and the display-time f match on it without a lookup. The reactor's scope holds the resolved `*Peer`s (`peers` in the scope table), so the writer's per-write test stays a pointer comparison; the BGP handler resolves names to `*Peer`s when it builds a scope value.

Reload of a drained peer. The reactor reconciles peers by remote address and port (`reconcilePeersJournaled`, `reactor_api.go`): a peer whose settings changed is swapped in place only when every changed field is hot-swappable (`peerSettingsSwapPlan`, `peer_settings_apply.go`: import and export filters, static routes, process bindings, BFD, a capability set proved to negotiate unchanged), and is otherwise removed and re-added with a session restart; a remote ASN or address change is not hot-swappable. So the rule is one rule: a peer's runtime drain ends when the reactor removes its `*Peer`, and holds across a hot swap.
- Deleted (`delete bgp peer E1`): E1 is dropped from the scope, logged "runtime drain of peer E1 ended: peer removed by commit".
- Re-created (removed and re-added in one commit, by a change that needs a session restart, or deleted and added again later): the new E1 starts undrained, logged "runtime drain of peer E1 ended: peer re-created by commit; run `request peer E1 drain` to drain it again". The hint names the new peer's config name: a rename is a re-creation, because `reconcilePeersJournaled` keys peers by remote address and port (`PeerKey()`, a `netip.AddrPort`) and `hotSwappableSettings` (`peer_settings_apply.go`, read 2026-10-14) does not copy `Name`, so a renamed peer at the same address is removed and re-added, and a rename of E1 to E2 logs "runtime drain of peer E1 ended: peer re-created by commit as E2; run `request peer E2 drain` to drain it again", since `request peer E1 drain` would name no peer (design 5, NOTE-2). The drain was asked for one session about to be shut down (RFC 8326 Section 4.2 has the operator apply the policy "on the EBGP session to be shutdown"); the reload has already shut that session down, the new session is a new negotiation, possibly with another neighbour at a changed address, and carrying the intent forward would tag a session nobody asked to drain. Re-requesting it is one command, and the log names it.
- Re-classified eBGP to iBGP (a remote ASN changed to the local AS, a restart, so a removal): E1 is dropped, logged "runtime drain of peer E1 ended: peer is now iBGP, which a per-peer drain does not cover (RFC 8326 Section 1)", because Q-7 (a) refuses an iBGP peer and the scope must not hold one the command would refuse.
- Hot-swapped (an export filter edited): E1 stays drained, nothing is logged, no walk runs.

The BGP plugin applies the removal itself, from its config apply, by queuing one internal peer-undrain request for the removed peers on its drain worker, served in order like any request: the scope change (new epoch, `replaced`), the ordering sequence, and a peer-filtered `kind undrain` walk (unfiltered when a walk is owed, ISSUE-2), which finds no `ribOut` entry toward the removed destination and re-sends undrained any path still held whose source is the removed peer's address. It then reports the new peer set and the epoch of the scope it applied to the server record through a hidden server command, `request drain record` (`ze-plugin:system-drain-record`), which replaces that row's `scope` and `epoch` and logs nothing more. The command is a builtin, so it is declared in `ze-system-cmd.yang` with `ze:hidden true` on its node (the shape of `internal/test/plugins/fakeas112/yang/ze-fakeas112-cmd.yang`), and the BGP plugin dispatches it with `sdk.DispatchCommand` (`pkg/plugin/sdk/sdk_engine.go`), the string form, never `DispatchCommandArgs` (design 5, ISSUE-1, read 2026-10-14): the args form reaches `Dispatcher.ForwardToPlugin` (`internal/component/plugin/server/command.go`), which resolves through `registry.Lookup`, the plugin-command registry only, so a builtin is never found there; the string form reaches `Dispatcher.Dispatch` (`dispatchCommandResponse`, `dispatch.go`), which finds builtins. A builtin cannot be hidden from Go: `RegisterOptions` has no `Hidden` field, and `loadBuiltinsWithAliases` skips a `WireMethod` that has no YANG path, so a registration kept out of the YANG is never reachable at all. `request bgp rib drain-replay` stays out of the YANG for the opposite reason: it is a bgp-rib plugin command, declared `Hidden: true` in `rib.go`'s `decls`, which `ForwardToPlugin` does find. The command takes only the record's own mutex, never the transition semaphore, because the worker that sends it may be the target of a transition waiting on that semaphore, and it refuses a caller other than the row's plugin (A-13): the dispatch path builds the handler's `CommandContext` with `Process: proc` and `Sender: plugin.ProcessSender(proc.Name())`, so the handler takes `name, ok := cmdCtx.Sender.Process()` (`internal/component/plugin/sender.go`) and accepts only `ok` with `name` equal to the row's plugin: an operator sender (`IsOperator`) and an unset one (`IsSet` false, which `sender.go` says a guard MUST refuse) both answer `ok` false and are refused. A respawn re-drain that names a peer no longer configured, or now iBGP, is answered with the peers the BGP plugin applied, and the record takes that set, with the same log lines (AC-39 (e)). The server never reads BGP config, so it names no protocol.

bgp-rib's start read (design 5, ISSUE-3; restated design 6, ISSUE-B). bgp-rib reads the BGP row once, in its `OnStarted` callback (A-14). The SDK runs `OnStarted` synchronously and enters the event loop only after it returns (`pkg/plugin/sdk/sdk.go`, `Run`), and a walk reaches bgp-rib as an execute-command callback that `DirectBridge.ExecuteCommand` (`pkg/plugin/rpc/bridge.go`) sends to that event loop and waits on, pipe mode likewise through `MuxConn.Requests()`; so no walk is handled before the read returns, and every walk bgp-rib handles comes after its start scope. The record takes a scope only after the plugin's answer, which follows the walk, so the read can return epoch E while the walk at E+1 is already queued on the event loop; without an order bgp-rib could not tell the read was stale, but the queued walk, handled next, replaces it. The epoch orders them. The BGP plugin's `drain` and `undrain` answers (`failed` included, because the scope change stays applied) and `request drain record` each carry the epoch of the scope the plugin applied; the server stores it in the row beside `scope`, and `show drain` presents it as the BGP row's `epoch` (the epoch of the last scope the plugin reported, so while a row is `draining` or `undraining` it can lag the scope the request wrote at step 2). bgp-rib takes the read as its start scope, always, because no walk precedes it. A walk handled after the read replaces the read's scope for the show when its epoch is at least the read's, which every walk it can receive is: the BGP drain worker serializes its walks, and the row's epoch is reported only after the walk that applied it, so no walk below the row's epoch is still in flight when the read returns. The walk's own acceptance stays the stop spec's rule (a walk older than the last walk received is refused), which this changes nothing in.

Epoch lifetime (design 6, NOTE-C). The BGP drain worker's counter is process state, so a respawned BGP plugin would start it from zero while the row keeps the predecessor's higher epoch, and a running bgp-rib's older-walk refusal (the stop spec's rule) would then refuse every walk of the new process until the counter caught up, as would a bgp-rib starting in that window against its start read. The epoch is therefore the pair (generation, counter), compared generation first. The generation is the server's: the record row holds it, starting at 0, and the server increments it when a respawned process takes over the row (Q-1 (a), the respawn path); every `drain` and `undrain` RPC the server sends the plugin carries it, the respawn re-drain included, and the worker stamps each scope it applies with the generation of the request that caused it and a counter it restarts at 0 when the generation changes. The route of the generation (design 7, ISSUE-3): the server sets it, in the row, at respawn; the server passes it in every `drain` and `undrain` RPC to the BGP plugin's drain worker; the worker stores it in the reactor's drain scope, whose `epoch` cell is the pair (the stop spec's scope table, `reactor.go`/`drain.go`), beside the counter; the walk `request bgp rib drain-replay` carries the pair as two arguments, `generation <G>` and `epoch <N>` (`rib_commands.go`), and bgp-rib's "snapshot taken for epoch E" holds the pair. A peer-undrain the BGP plugin starts itself (the reload removal) takes the generation of the last request, and its report to the server, `request drain record` (a server builtin, not a walk), carries the resulting pair; a new process with no request yet has no scoped peer to remove, so it starts none. Resetting the row's epoch on respawn was rejected: it leaves a running bgp-rib holding the higher epoch, so its refusal still rejects the new process's walks. Seeding the new worker from the row's epoch was rejected too: a walk can reach bgp-rib before its answer reaches the row, so bgp-rib can hold an epoch above the row's. A-6 says the BGP plugin is not respawned in practice, so the case is reachable only through the respawn path; the pair holds whether or not A-6 does, at the cost of one field on the RPC and the row.

### Integration Points
- The stop spec's server fan-out (`internal/component/plugin/server/drain.go`): called with the RPC and the deadline instead of always `drain` at stop.
- The stop spec's SDK `OnDrain`: gains kind `maintenance`; `OnUndrain` beside it, registered with it (`startup.go` refuses `OnDrain` without `OnUndrain`, and `OnUndrain` without `OnDrain`, naming the plugin).
- `internal/core/redistevents/registry.go`: a read accessor from protocol name to its disposition, used by the `protocol` filter and its completion.
- The stop spec's BGP verdict and f (`internal/component/bgp/reactor/drain.go`), applied at its one site, `Session.writeUpdateBody` (`session_write.go`), with its withhold; replay kind (`types.go`, `update_text.go`); bgp-rib walk with its cut (`rib.go`, `rib_commands.go`); under Q-8 (b), the Adj-RIB-Out show (`rib_pipeline.go` `outboundSource`).

- `ProcessManager` respawn and the server's plugin-ready stage, for Q-1 (a).

## Design Insights
- A runtime drain is a stop drain whose end is chosen by the operator instead of by a timer, so every element of the stop design had to be re-enterable; the stop spec (amended 2026-10-14) now builds them that way, and this spec adds the way back.
- Undrain by recomputation, not inversion. The drained form is a pure function of the undrained egress body and the scope, so keeping the input (U in `ribOut`) and applying the function at the write makes drain and undrain one operation, "re-advertise with the current scope". An inverse needs a record of what the function lost, and every record then has to survive writes made under another scope; four review rounds found holes in exactly that.
- The IGP drain was designed never to rewrite stored state, which makes its undrain free.

| A long-lived drain worker per connection, built by the stop spec (amended 2026-10-14), to which this spec adds states and requests | a goroutine per request | a goroutine per request is the per-event shape `ai/rules/goroutine-lifecycle.md` forbids; one worker also orders drain before undrain |

## Known Limitations
- No RFC describes the return from a graceful shutdown, a stub router or an overload: the undrain is Ze's design, and no conformance claim is made for it.
- A runtime drain ends at daemon stop under Q-1 (a); a router rebooted mid-maintenance returns to service when it is up.
- A runtime drain of a route-server client or a reflector client leaves the cells the stop spec leaves untouched (RFC 7947 Section 2.2.4, RFC 4456 Section 10); those clients lose the paths only when the session goes down.
- A write made between the scope store and the moment the cut M is read with a message ID at or below M (before its destination's take-and-release, or after that release and before M is read) is replayed once more in the same form: one duplicate UPDATE per such key per scope change, the stop spec's accepted duplicate, in both directions (redesign round 1, N-2).
- A BGP walk that fails leaves the routes already sent in their old form until the operator's next request succeeds (Q-9 (a)); the row says `failed` and the scope still governs live writes. A delivery failure bgp-rib's process retains ("Success never clears it") fails every walk of that process, so only a restart of Ze, which ends the runtime drain (Q-1 (a)), clears it (redesign round 1, I-3).
- A retry after a failed walk (Q-9 (a)) runs at the same epoch, which bgp-rib accepts, and takes a new cut M, so every live write made under the scope since the failed walk's cut is replayed once more in the same form: one duplicate UPDATE per such key per retry, beside the scope-store duplicate above (redesign round 2, N-2).
- The Adj-RIB-Out show while drained: under Q-8 (b) it can lead the wire by a walk's duration, because it renders the scope in force before the walk's writes leave.
- The Adj-RIB-Out show after a failed BGP walk (design review round 4, NOTE-1). bgp-rib learns a scope change from the walk command that carries it, and reads the record only at its own start. When `DrainEventsApplied` fails, the walk command is never dispatched, so the show keeps rendering the scope before the change while the writer already sends under the new one, until the next walk that bgp-rib receives (the operator's retry, Q-9 (a), or the next change); a walk that bgp-rib refuses (an older epoch) leaves it the same way. `show drain` names the BGP row `failed` throughout, with the command to run, and the show agrees with the wire again when that walk is accepted. A walk that bgp-rib accepts and that then fails takes the new scope with it, so it leaves the show right. A start whose read of `show drain protocol bgp` fails renders undrained until the next walk, and says so in its log line. A start read that returns a row whose epoch is not above a walk bgp-rib already received is discarded (bgp-rib's start read, Data Flow; design 5, ISSUE-3), so the read never moves the show back to an older scope.
- A failed walk makes the next scope change replay the whole table (ISSUE-2): its `replaced` is `unconfirmed`, so no key is withheld, and every untouched key is sent again in the form the peer already holds, one duplicate UPDATE per such key, because which form a peer holds after a failed walk is unknown.
- A re-created or re-classified peer is not drained again (ISSUE-3): its drain ends when the reactor removes its `*Peer`, and the log line names the command that drains it again.
