## Task

**The problem.** The published command catalog is built in a reader's own
process, and a plugin's declarations only ever reach a RUNNING daemon. So the
catalog cannot report what a plugin declares. Two deferral rows named the same
gap, one for a plugin's answer shape and column order (2026-08-24,
`spec-plugin-declares-answer-shape`), one for a plugin's registered pipe aliases
(2026-08-22, from the pipe-operations spec). One daemon-backed source answers
both.

**What each reader does today.**

| Reader | Producer | What it reports |
|--------|----------|-----------------|
| `./le command list` | `Collect` and the `Command` struct, `internal/le/command/list/commandlist.go` and `report.go` | verb, path, wire method and source, and nothing else. No shape, no column order, no aliases |
| the published catalog | `Collect` and `operatorsFor`, `internal/le/wikicatalog/catalog.go` | shape, address fields, operators, pipe names, usage and grammar, all read in-process from the compiled registries |
| `ze help command [filter] --json` | `printHelpCommand` and `commandEntry`, `cmd/ze/help_command.go` | path, description, long help, mode, wire method, usage, grammar, args, pipes, `operators`, `answer-shape`, `address-fields`, `pipe-aliases`. NO column order, and nothing a plugin declared |
| `show command help "<name>"` | `commandHelp`, `internal/plugins/meta/cmd/help.go` | description, long help, source, args, `pipe-filters` and `pipe-aliases`. NO shape, NO column order, NO address fields |
| the website catalog | `./le site build` -> `publishCommandCatalog` (`internal/le/site/build.go`) -> `loadLiveCommandCatalog` (`internal/le/docvalid/command_surfaces.go`) | whatever `go run ./cmd/ze help command --json` prints, written to `data/cli-commands.json` |

**Research correction, 2026-09-07: the spec named the wrong surface, and the
gap is wider than it said.** `ze help command` is registered
`commandModeOffline` as a LOCAL command
(`registry.MustRegisterLocalMeta("help command", printHelpCommand, ...)`,
`cmd/ze/ze_core_dispatch.go`), so it runs in a short-lived client process and
never reaches `commandHelp`. `commandHelp` is the handler for
`show command help "<name>"`, a YANG-modeled RPC
(`internal/plugins/meta/yang/ze-command-meta-cmd.yang`) dispatched inside the
daemon, which is why it alone sees a plugin's Stage 1 declarations. So there are
FOUR readers, not three, and the two halves of the answer are split across two
processes: the client publishes the shape, the operators and the address fields
but only for what it compiled in; the daemon sees what a plugin declared but
publishes none of those three. Neither publishes a column order at all, and
`ColumnsForCommand` (`internal/component/command/column_order.go`) has no reader
outside `internal/component/`.

`internal/le/command/list/commandlist.go` blank-imports
`internal/component/plugin/all`, so it sees every IN-TREE registration. It
starts no plugin process, and a plugin declares its shape, its column order and
its pipe aliases in its Stage 1 registration message. Those never happen, so
neither `le` reader can see them.

**What is already true, and must not be rebuilt.** `commandHelp` already
publishes `pipe-filters` and `pipe-aliases` for a command, and its own comment
states the reason: "A running daemon is the only place both lists exist." So the
daemon route exists for the alias half of the second row. What it does NOT
publish is the declared answer shape and the column order, and what `le` cannot
do at all is read either one from a plugin.

**Why it costs the page and not the operator.** The running daemon answers
through completion and `command help`, which is where an operator looks. The gap
costs the PUBLISHED catalog, which is generated by a reader that has no daemon.

**What the work is.** A daemon-backed source for the catalog, so that:

1. `./le command list` reports a plugin's declared shape and column order beside
   the in-tree ones;
2. `ze help command --json` reports the declared shape and column order as well
   as the pipe aliases it already reports;
3. the published catalog page is generated from one source rather than from a
   process that can only see half the registrations.

**The design, ruled 2026-09-07 after auditing all 97 registered runners.** The
spec's three options were re-ruled once, then re-ruled again on evidence. The
final answer needs no daemon and no engine run, so the spec's name is wrong.

| Option | Verdict |
|--------|---------|
| A running daemon queried by the generator | REJECTED. Config, a listener and privileges at documentation-build time, for nothing the option below does not give |
| A collector that drives each plugin's Stage 1 in memory | **REJECTED 2026-09-07, on evidence.** Reading a declaration this way means first running everything the engine does before it declares. Two of 97 runners MUTATE THE HOST there (R-6), seven never reach Stage 1 at all, and eight leave process globals pointing at a dead plugin. `./le command list` must not program nftables |
| A declaration carried on `registry.Registration` | **CHOSEN.** It was called dead because `registry.Registration` has no command field. That is a fact about today's tree, not a constraint |

Each plugin already has ONE `commandDecls()` function. Its `register.go` puts
that slice on the `registry.Registration` it builds in `init()`, and its runner
keeps passing the same slice into `sdk.Registration` at Stage 1. One
declaration, one function, two readers: nothing is copied, so nothing can
disagree.

`le` then blank-imports the composition root, which it already does, and reads
`registry.All()`. No pipe, no bridge, no signal handler, no sequencing rule, no
kernel. The daemon path is untouched, so an EXTERNAL plugin still declares over
Stage 1 and still reaches `show command help` exactly as it does today. The
published catalog is generated from the tree, which is precisely the set
`registry.All()` covers.

One declaration and one reader (`ai/rules/principles.md`): the catalog must not
become a second list beside the registries. It is already a second list today,
which is why `compareWikiCatalogProducer` exists, and this spec collapses the
readers onto the registration rather than adding a fifth. The drift this opens
is a plugin that declares to Stage 1 and not to its registration, so a gate
compares the two.

**Key insights:** (minimal context to resume after compaction)
- `ze help command` is an OFFLINE LOCAL command (`printHelpCommand`, `cmd/ze/help_command.go`), not the daemon RPC. The daemon RPC is `show command help` (`commandHelp`). The spec's original Task table conflated them; see the research correction under Task.
- The two halves of the answer live in two processes. The client publishes shape, operators and address fields for compiled-in commands only; the daemon sees a plugin's declaration and publishes none of those three.
- Column order is published by NO reader. `ColumnsForCommand` (`internal/component/command/column_order.go`) has no caller outside `internal/component/`, so every reader gains a field rather than one gaining a source.
- `le` already execs the product binary: `./le site build` runs `go run ./cmd/ze help command --json` through `loadLiveCommandCatalog` (`internal/le/docvalid/command_surfaces.go`). The chosen design needs neither an exec nor a daemon: it reads `registry.All()`.
- RUNNING a plugin engine to read its declaration was designed, then rejected on an audit of all 97 registered runners. Two mutate the host before Stage 1. The audit table under Risks is the evidence, and it is the answer to any future proposal to run engines for introspection.

## Current Behavior (MANDATORY)

**Source files read:** (must read BEFORE you write this spec)
- [ ] `internal/le/command/list/commandlist.go` - `Collect` reads the builtin RPCs, the YANG command tree and the streaming prefixes after blank-importing the composition root; it starts no plugin, and the `Command` struct it answers (`report.go`) carries verb, path, wire method and source only.
  → Constraint: its header comment carries the sentence "le may link ze to introspect it, ze never links le, and le never RUNS a product command", repeated verbatim in `internal/le/inventory/inventory.go`. Only the FIRST half is written down anywhere else: `docs/architecture/core-design.md` says ze never links `internal/le` and that le must not SERVE a product root, and `TestNormalZeLinksNoInternalLe` measures the ze-to-le direction. No gate enforces the third clause, and `loadLiveCommandCatalog` and `internal/le/terminaldemo/runtime.go` both fork the product binary today, so the clause cannot mean "le must not exec ze". See A-2.
- [ ] `internal/le/wikicatalog/catalog.go` - `Collect` builds one `Entry` for each CLI path and fills shape, address fields, operators, aliases, pipes, usage and grammar from the in-process registries through `operatorsFor` and `command.AddressFieldsForCommand`.
  → Constraint: it publishes NO column order, and it hardcodes four `cmd/ze` main-package commands as literal `Entry` values because `internal` cannot import `package main`.
  → Constraint: it is an INDEPENDENT producer from `ze help command --json`, not a consumer of it. `compareWikiCatalogProducer` (`internal/le/docvalid/command_surfaces.go`) exists to hold the two in agreement, which is the drift R-1 names, already present in the tree.
- [ ] `internal/plugins/meta/cmd/help.go` - `commandHelp` serves `show command help "<name>"`, a YANG-modeled RPC (`internal/plugins/meta/yang/ze-command-meta-cmd.yang`) dispatched INSIDE the daemon. It answers `command`, `description`, `long-help`, `source`, `args`, `pipe-filters` and `pipe-aliases`.
  → Decision: it is the only reader that sees a plugin's declaration, and it publishes none of shape, column order or address fields. Its package already imports `internal/component/command`, so adding the three is a read rather than a new dependency.
- [ ] `cmd/ze/help_command.go` - `printHelpCommand` and `commandEntry` serve `ze help command [filter] --json`, registered `commandModeOffline` as a LOCAL command (`registry.MustRegisterLocalMeta`, `cmd/ze/ze_core_dispatch.go`). It runs in a short-lived client process.
  → Decision: `commandEntry` ALREADY carries `answer-shape`, `address-fields`, `operators` and `pipe-aliases`. What it lacks is a column order and any plugin's values, because its registries hold only what the binary compiled in.
- [ ] `internal/component/command/answer_shape.go`, `internal/component/command/column_order.go` - `RegisterShape`, `ShapeForCommand`, `RegisterAddressFields` and `RegisterPluginShapes` are the registry a plugin's Stage 1 declaration lands in, inside the daemon.
  → Constraint: `shapeRegistry` and `addressFieldRegistry` already have readers under `internal/le/` (`wikicatalog/catalog.go`). `columnRegistry` has NO reader outside `internal/component/`, so the column order is a new field in every reader rather than a source to reconnect.
- [ ] `internal/component/bgp/plugins/adj_rib_in/register.go` and `rib.go` - the plugin's `init()` builds a `registry.Registration` carrying `Name`, `YANG` and `RunEngine`. `registry.Registration` has NO command, shape or column field.
  → Decision: **this is what the whole design turns on.** `commandDecls()` has exactly one non-test caller, `runAdjRIBInPlugin` (`rib.go:356`), which passes it as `sdk.Registration{Commands: commandDecls()}`. So a plugin's declarations exist only after its ENGINE runs and sends Stage 1. Blank-importing `internal/component/plugin/all` registers the plugin and not its commands, and no amount of linking gets `le` the declarations.
- [ ] `internal/component/plugin/inprocess.go`, `internal/component/config/loader.go` - `PluginConfig.Internal` decides in-process against forked, and every auto-load path sets it true.
  → Decision: an internal plugin still runs its full SDK lifecycle. `inprocess.go` calls `reg.RunEngine(conn)` over a `net.Conn`, so Stage 1 travels the same wire in memory as it does over a socket. A collector that speaks the server half of that handshake needs no socket, no config and no privileges. Whether `sdk.Plugin.Run` completes Stage 1 against a minimal peer is A-3, under verification.

**Behavior to preserve:** (unless the user explicitly said to change it)
- `ze help command` keeps answering aliases and filters as it does today.
- `./le command list` keeps answering structured data that `| json`, `| yaml` and `| table` each render.
- `le` may link ze to introspect it; ze never links le, and le never RUNS a product command.

**Behavior to change:** (only what the user asked for)
- The catalog reports a plugin's declared shape and column order, and its registered pipe aliases.

## Data Flow (MANDATORY - see `ai/rules/architecture.md`)

### Entry Point
- An operator or a generator runs `./le command list` or `ze help command <name> | json`.
- A plugin's declarations enter the daemon in its Stage 1 registration message at plugin start.

### Transformation Path
1. A plugin registers its commands, shapes, column orders and pipe aliases at Stage 1.
2. The daemon's command registries hold them.
3. A reader asks for the catalog and renders the answer through the pipe operators.

### Boundaries Crossed
| Boundary | How | Verified |
|----------|-----|----------|
| Plugin ↔ daemon | the Stage 1 registration message | Yes. `runStartupHandshake` / `startupSink`, `internal/component/plugin/server/startup_driver.go` |
| Plugin ↔ collector | REJECTED. See the audit table under Risks |
| le ↔ ze | `le` LINKS the composition root, which `internal/le/command/list/commandlist.go` already blank-imports, and reads `registry.All()`. No daemon, no socket, no exec, no engine run |

### Integration Points
- `command.ShapeForCommand`, `command.ColumnsForCommand`, `command.AliasesForCommand` (`internal/component/command/`) - the three registries the catalog has to read for an IN-TREE command.
- `registry.Registration` and `registry.All()` (`internal/component/plugin/registry/registry.go`) - where the declaration lands and how every reader gets it.
- `rpc.CommandDecl` (`pkg/plugin/rpc/types.go`) - the type the registration carries, already the Stage 1 type, so the two readers share one shape.

| AC ID | Input / Condition | Expected Behavior |
|-------|-------------------|-------------------|
| AC-1 | a plugin declares a shape and a column order | `./le command list` reports both |

1. **Phase: Wiring (MANDATORY FIRST)** -- write the failing test that the catalog reports a plugin's declaration
   - Tests: `TestCommandListReportsAPluginDeclaredShape`
   - Files: `internal/le/command/list/commandlist_test.go`
   - Verify: the test fails because no plugin runs in the reader's process
2. **Phase: The registration carries the declaration** -- `Registration` gains `Commands`, and every plugin that declares commands sets it from the same `commandDecls()` its runner uses
   - Tests: `TestRegistrationCarriesTheDeclaredCommands`, `TestEveryRunnerDeclarationIsOnItsRegistration`
   - Files: `internal/component/plugin/registry/registry.go`, roughly 33 `register.go` files
   - Verify: AC-4, AC-7
3. **Phase: The column order reaches a reader** -- `ColumnsForCommand` gains its first caller outside `internal/component/`
   - Tests: `TestCommandHelpReportsShapeColumnsAndAddressFields`, `TestHelpCommandReportsTheDeclaredColumnOrder`
   - Files: `internal/plugins/meta/cmd/help.go`, `cmd/ze/help_command.go`
   - Verify: AC-5, AC-6
   - → Decision: the JSON key is `column-orders`, plural, and both answers spell it that way. The value is a list of ORDERS, one per record shape the command renders (`ColumnsForCommand` answers `[]ColumnOrder`), so a flat key could state neither of a two-shape command's two orders. `columns` was rejected because `rpc.CommandDecl.Columns` already publishes a FLAT list under that name on the wire, and one name carrying two shapes costs the reader a guess on every page (`docs/contributing/ze-go-style.md`, "Do not overload a name"). Every other array key on these answers is plural: `address-fields`, `pipe-aliases`, `subcommands`.
   - → Decision: `commandHelp` reads the three declaration registries directly and NOT `DeclaredForCommand`. It runs inside the daemon and answers what the daemon holds, so reporting a registered plugin that never started would promise an operator a shape no running command answers with.
4. **Phase: The le readers derive from the registration**
   - Tests: `TestCommandListReportsAPluginDeclaredShape`, `test/plugin/command-catalog-plugin-shape.ci`
   - Files: `internal/le/command/list/`, `internal/le/wikicatalog/catalog.go`, `internal/le/docvalid/command_surfaces.go`
   - Verify: AC-1, AC-2, AC-8
   - → Decision: one reader answers both declaration channels, `command.DeclaredForCommand` (`internal/component/command/declared.go`). It reads the declaration registries first and a plugin's `registry.Registration.Commands` for a field this process declared nowhere, resolving by longest prefix in both, which is what a running daemon answers. `internal/component/command` already imported `internal/component/plugin/registry` (`valuehints.go`), so the join needed no new dependency and no new package. All three catalog readers call it, so AC-8 holds by derivation.
   - → Decision: `compareWikiCatalogProducer` (`internal/le/docvalid/command_surfaces.go`) is KEPT, with its subject restated in its doc comment. Retiring it would have dropped the only guard on the half that still has two producers: an `internal` package cannot import `cmd/ze`'s main package, so `wikicatalog.Collect` carries four main-package commands as literal entries and drops every `le ` path, and nothing derives those. The declaration half no longer needs it and is proven instead by `TestHelpCommandDerivesEveryDeclarationFromOneReader` and `TestWikiCatalogDerivesEveryDeclarationFromOneReader`.
   - → Constraint: `./le command list` gained a fourth `Source` value, `plugin`, because a plugin's command is dispatched through the plugin rather than through a builtin RPC or a streaming prefix and the inventory named none of them. A HIDDEN declaration is listed: the inventory answers what ze registers, and hiding is a completion decision.
6. **Phase: A plugin's pipe aliases reach the compiled tree** -- AC-2
   - Tests: `TestHelpCommandReportsAPluginDeclaredAlias`, `TestWikiCatalogReportsAPluginDeclaredAlias`, `TestCheckNamesAPipeAliasMissingFromTheRegistration`, `TestCheckAcceptsADeclarationFunctionItCannotEvaluate`
   - Files: `internal/component/plugin/registry/registry.go`, `internal/component/bgp/plugins/rpki/`, `internal/component/command/declared.go`, the three readers, `internal/le/plugin/declarations/`
   - Verify: AC-2
   - → Decision: `registry.Registration` gained `Pipes []rpc.PipeDecl`, the exact shape `Commands` already had, and bgp-rpki's inline alias literal moved into `pipeDecls()` so one function serves both readers. `Declared` gained `Aliases`, filled by `aliasesIncludingPlugins`, so the three catalog readers take an alias from the same lookup that already answered the shape.
   - → Decision: `AliasesForCommand` is NOT changed. It is what a running daemon reads, and a daemon has already written each STARTED plugin's aliases into the registry; adding a registration's aliases there would offer an operator a name no running command answers to. This is the same reason `commandHelp` keeps reading the live registries.
   - → Constraint: an alias the registry holds on the resolved path WINS over a plugin's of the same name, because Stage 1 refuses that collision (`RegisterPluginAliases`, through `aliasOnPath`), so keeping the registry's is the answer a daemon reaches. The read side also reproduces `aliasBarriers`: a command the same plugin declares below the alias path inherits nothing.
   - → Constraint: `./le plugin declarations check` gates the pipe channel too. A command is identified by its name and a pipe alias by the pair its registry keys it on. The gate also gained one rule it needed for AC-3's `bgp-rib` derivation: a field both literals write as a call to ONE parameterless function is compared by that function's identity, because one function answers one slice and no syntactic reader can evaluate a loop.

## Known Limitations
- The published sibling artifacts are STALE until they are regenerated, by 52 commands and one new key. `../gh-pages/data/cli-commands.json` holds 411 commands and `wikicatalog.Collect` now answers 463, `column-orders` is a key none of the published entries carries, and `show bgp rpki` now publishes the `summary` alias it did not. `./le site build` regenerates the website file and `./le wiki-catalog update file <catalog.md>` the wiki page; both write a SIBLING checkout, so neither was run here. Until they are, `compareWebsiteCommandCatalog` and `compareWikiCommandCatalog` (`internal/le/docvalid/command_surfaces.go`) both report a disagreement. The wiki MARKDOWN gains its 50 new commands as well, because `wikicatalog.Render` renders every entry; it renders no column order, so that key changes nothing there.
- An EXTERNAL plugin's declarations are still a running daemon's answer alone, and always will be: it registers nothing in the composition root, so neither `Commands` nor `Pipes` exists for it outside Stage 1. R-3 named this for aliases; it is the same boundary for every channel, and it is a property of an external process rather than a gap in this work.
- `command.Usage` answers nil for a node carrying no wire method, so a plugin command the YANG model describes publishes an authored summary, an authored long help and NO grammar. Its `usage` is the invocation form the plugin declares. A machine reader takes an absent `grammar` as "not modeled", which is what the four main-package builtins and every offline local command already publish.
