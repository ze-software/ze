## Task

**The problem.** The published command catalog is built in a reader's own
process, and a plugin's declarations only ever reach a RUNNING daemon. So the
catalog cannot report what a plugin declares. Two deferral rows named the same
gap, one for a plugin's answer shape and column order (2026-08-24,
`spec-plugin-declares-answer-shape`), one for a plugin's registered pipe aliases
(2026-08-22, from the pipe-operations spec). One daemon-backed source answers
both.

**What each reader does today.**

| Reader | Producer | What it reports |
|--------|----------|-----------------|
| `./le command list` | `Collect` and the `Command` struct, `internal/le/command/list/commandlist.go` and `report.go` | verb, path, wire method and source, and nothing else. No shape, no column order, no aliases |
| the published catalog | `Collect` and `operatorsFor`, `internal/le/wikicatalog/catalog.go` | shape, address fields, operators, pipe names, usage and grammar, all read in-process from the compiled registries |
| `ze help command <name>` | `commandHelp`, `internal/plugins/meta/cmd/help.go` | description, long help, source, args, `pipe-filters` and `pipe-aliases` |

`internal/le/command/list/commandlist.go` blank-imports
`internal/component/plugin/all`, so it sees every IN-TREE registration. It
starts no plugin process, and a plugin declares its shape, its column order and
its pipe aliases in its Stage 1 registration message. Those never happen, so
neither `le` reader can see them.

**What is already true, and must not be rebuilt.** `commandHelp` already
publishes `pipe-filters` and `pipe-aliases` for a command, and its own comment
states the reason: "A running daemon is the only place both lists exist." So the
daemon route exists for the alias half of the second row. What it does NOT
publish is the declared answer shape and the column order, and what `le` cannot
do at all is read either one from a plugin.

**Why it costs the page and not the operator.** The running daemon answers
through completion and `command help`, which is where an operator looks. The gap
costs the PUBLISHED catalog, which is generated by a reader that has no daemon.

**What the work is.** A daemon-backed source for the catalog, so that:

1. `./le command list` reports a plugin's declared shape and column order beside
   the in-tree ones;
2. `ze help command --json` reports the declared shape and column order as well
   as the pipe aliases it already reports;
3. the published catalog page is generated from one source rather than from a
   process that can only see half the registrations.

The design decision is where the daemon-backed source lives and how a build-time
generator reaches it: a running daemon queried by the generator, a declaration
exported by each plugin at build time, or the catalog moved behind a command the
daemon answers. Whichever it is, one declaration and one reader
(`ai/rules/principles.md`): the catalog must not become a second list beside the
registries.

## Current Behavior (MANDATORY)

**Source files read:** (must read BEFORE you write this spec)
- [ ] `internal/le/command/list/commandlist.go` - `Collect` reads the builtin RPCs, the YANG command tree and the streaming prefixes after blank-importing the composition root; it starts no plugin, and the `Command` struct it answers (`report.go`) carries verb, path, wire method and source only.
- [ ] `internal/le/wikicatalog/catalog.go` - `Collect` builds one `Entry` for each CLI path and fills shape, address fields, operators, aliases, pipes, usage and grammar from the in-process registries through `operatorsFor` and `command.AddressFieldsForCommand`.
- [ ] `internal/plugins/meta/cmd/help.go` - `commandHelp` answers one command from the running daemon, including `pipe-filters` from `command.PipeFiltersForCommand` and `pipe-aliases` from `command.AliasesForCommand`; it reports neither the declared shape nor the column order.
- [ ] `internal/component/command/answer_shape.go` - `RegisterShape`, `ShapeForCommand`, `RegisterAddressFields` and `RegisterPluginShapes` are the registry a plugin's Stage 1 declaration lands in, inside the daemon.

**Behavior to preserve:** (unless the user explicitly said to change it)
- `ze help command` keeps answering aliases and filters as it does today.
- `./le command list` keeps answering structured data that `| json`, `| yaml` and `| table` each render.
- `le` may link ze to introspect it; ze never links le, and le never RUNS a product command.

**Behavior to change:** (only what the user asked for)
- The catalog reports a plugin's declared shape and column order, and its registered pipe aliases.

## Data Flow (MANDATORY - see `ai/rules/architecture.md`)

### Entry Point
- An operator or a generator runs `./le command list` or `ze help command <name> | json`.
- A plugin's declarations enter the daemon in its Stage 1 registration message at plugin start.

### Transformation Path
1. A plugin registers its commands, shapes, column orders and pipe aliases at Stage 1.
2. The daemon's command registries hold them.
3. A reader asks for the catalog and renders the answer through the pipe operators.

### Boundaries Crossed
| Boundary | How | Verified |
|----------|-----|----------|
| Plugin ↔ daemon | the Stage 1 registration message | No |
| Daemon ↔ le | whatever the design chooses: a command, a query, or an exported declaration | No |

### Integration Points
- `command.ShapeForCommand`, `command.ColumnsForCommand`, `command.AliasesForCommand` (`internal/component/command/`) - the three registries the catalog has to read.
