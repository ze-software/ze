## Task

Owner decision, 2026-10-13: error messages must be user friendly and "propose what
is known is valid from the yang". Direction chosen by the owner, 2026-10-13,
verbatim: "M2 go with (c), friendly errors everywhere". Option (c) is one generic
friendly refusal for every YANG enum, on every path: the setting path, the refused
value, the accepted values with their YANG help, and the closest match where a
helper exists.

Today a value outside a YANG enumeration is refused with
`invalid enum: "redistribute" (expected one of: monitor)`: no setting path, no
meaning for each accepted value, no closest-match hint. Worse, the same refusal has
seven different texts depending on the path the operator took (table in Current
Behavior), and two paths (the SSH editor `set`, the web form) do not list the
accepted values at all, or do not refuse at `set` time.

Goal: ONE generic refusal for every YANG enumeration, built from the schema alone,
reached through every path (config file load, `ze config validate`, offline
`ze config set`, editor `set`, `load` and `commit`, the editor `set cli format`
command, web UI form and web CLI terminal `set`, REST API and gNMI `Set`, reload,
and operational command arguments, which are YANG enums too). It:

| Element | Source |
|---------|--------|
| names the setting by its config path, list keys included | the path the caller already holds |
| quotes the refused value (a placeholder on a sensitive leaf) | the input; one fact, read by two readers: `config.LeafHoldsSecret` where the builder holds a `LeafNode` (parser, set parser, web), and the shared `ze:sensitive` / `ze:bcrypt` extension reader in `config/yang` where it holds a `*gyang.Entry` (`validateEntry` on the tree walk, `ValidateValueAtPath`), which also fills the `LeafNode` fields `LeafHoldsSecret` reads (Data Flow 4) |
| lists every accepted value, in YANG declaration order | the YANG enumeration, never a hand list; order source per producer in Key Design Decisions |
| gives each accepted value its one-line `ze:help` where the YANG declares one | `yang.EnumValueSummaries` (the one reader of an enum value's `ze:help`) |
| offers "did you mean" when one accepted value is close, never on a sensitive leaf | `suggest.Command` (`internal/core/suggest`), the distance the CLI and the unknown-key refusal already use, in the one hint form `(did you mean X?)` that `UnknownKeywordHint` (`retired.go`) writes |
| says why it matters | the surface's frame, never the body: the consequence differs by surface (the file does not load, the value is not set, the commit is refused), so each frame states its own (Text samples below) |
| gives the fix on a line of its own | the frame: `write:` for a file, a `set` line for a set-form surface, `Choose one of the accepted values and submit the form again.` for the web form, `Retry the command with ...` for a command argument (Key Design Decisions, frame table below) |

No per-leaf special case. Known dependant:
`plan/immediate/spec-bmp-route-action-redistribute-acts-as-monitor.md` (owner answer
Q-2 there) removes `enum redistribute` from `route-action` and relies on this
message to refuse it.

### Text samples

The refusal body is the deliverable the owner approves, so its layout is fixed
here. `<help of X>` stands for the one-line `ze:help` of enum value X, read from
the YANG. The body has three parts: the problem line, the heading
`Accepted values:`, and one line per accepted value. The problem line is the
path written as an operator types it, a colon, the quoted value, the words
`is not an accepted value`, and the hint when one exists. A value line is two
spaces, the name, then, when the value declares a `ze:help`, enough spaces to
align every help text two columns after the longest name, and the help. A value
with no `ze:help` is its name alone, with no trailing space (AC-4). The words
`is not an accepted value` are the marker every enum refusal carries, the
command-argument refusal included (R-11).

Body, value close to an accepted one (AC-2):

```text
bgp peer peer1 session capability route-refresh: "requre" is not an accepted value (did you mean require?)
Accepted values:
  enable   <help of enable>
  disable  <help of disable>
  require  <help of require>
  refuse   <help of refuse>
```

The missing-value form (AC-18) replaces the problem line with
`bgp peer peer1 session capability route-refresh: needs a value`. A sensitive
leaf (AC-16) shows `config.SecretDataPlaceholder` in place of the quoted value
and never a hint. A multi-line body keeps its line breaks on every surface. The
body is rendered by one function that takes the continuation indent: the first
line carries the frame's prefix, and every following line of the body (the
heading, the value lines, and the frame's own why and fix lines) starts with the
continuation indent; the value lines keep their own two spaces inside the body.

reader that takes it whole (a walk refusal in `ValidationError.Message`, the body
`formatPeerError` returns alone) holds it in the stored-apart shape of the table

In-entry key-leaf refusal (AC-33 negative case, AC-34). This is a structural
refusal, not an enum refusal: it carries no `Accepted values:` list and no
`is not an accepted value` marker, and it names no secret, because a list key
names an entry and no schema leaf marks it as one. The typed value is not
echoed. Its text is fixed, three lines, the same whatever the value and whether
or not the entry exists, built by the one shared check (`config/schema.go` row,
`Schema.CheckInEntryKeyLeaf`). The check writes every line at the left edge.
The SSH editor viewport prints the text as the check wrote it, through the
multi-line rule (the feedback row holds the first line); the web terminal
writes `error: ` before it and indents each continuation line two spaces. The
last line names the command that changes a key, with the placeholder
`<new-key>` written literally, never a computed value:

```text
<ospf-path> redistribute connected source: source is the key of list redistribute and cannot be set inside an entry; rename changes the key of an existing entry
The value was not set.
rename <ospf-path> redistribute connected to <new-key>
```

**Key insights:**
- Thirteen producers today, one fact (the enumeration): texts 1 to 6 in the table below plus the leaf-list pair (`storeValueOrArray`, `validateValueOrArrayItems`), the `cli format` status line, the command union arm, the parser's missing-value refusal, the editor's bgp-level walk arm in `validateWithYANG`, and the `update text ... origin` argument check (`parseCommonAttributeText`, text 7). Two of them (`ValidateLeafValue` in `schema.go`, `validateInlineListChildValue` in `parser_list.go`) are the ones the operator meets on every file path.
- Two paths do not check an enum value at `set` at all: the web CLI terminal `set` (`executeTerminalSet` in `web/cli_terminal.go` calls `EditorManager.SetValue`, which checks only the secret placeholder) and the REST/gNMI session set.
- `suggest.Command` exists; no new edit-distance helper is needed.
- `yang.EnumValueSummaries(entry)` is the one reader of per-value `ze:help`; `LeafNode` carries `ShortHelp` for the leaf but NO per-value help today, so `yangToLeaf` must store it.
- `config/yang` imports `command`, and `config` imports `config/yang`, so the shared renderer must live in a leaf package all producers can import: `internal/core/suggest` (imports nothing from ze).
- The parser holds no path stack (`Parser` fields: `schema`, `tok`, `warnings`), so the refusal there names only the leaf today.
- The tree walk holds the path only as a string: `validateEntry` takes `path string`, and `walkTree` writes `<child>[<key>]` with no escaping. A list key can hold `/` or `]` (a prefix key), so that string cannot be parsed back into segments. The segments are threaded through the walk instead (Files to Modify, validator.go).
- The secret flag is known where the refusal is built: `validateEntry` holds the `*gyang.Entry`, whose `ze:sensitive` and `ze:bcrypt` extensions are the fact `config.LeafHoldsSecret` reads (`yangToLeaf` fills `LeafNode.Sensitive` and `Bcrypt` from `hasSensitiveExtension` and `hasBcryptExtension`). So every consumer of a walk refusal, not only `SectionValidationError.Message`, receives it already masked.

## Data Flow (MANDATORY - see `ai/rules/architecture.md`)

### Entry Point
- A config value as text: a config file line, a `set` line (editor, offline `ze config set`, REST/gNMI session set), a web form post, or an operational command argument.

### Transformation Path
1. Schema build: `yangToLeaf` reads the enumeration names (declared order) and, new, the per-value `ze:help` (`yang.EnumValueSummaries`) onto `LeafNode`; the leaf-list builder does the same for `ValueOrArrayNode`; the command ArgDef builder does the same for an enum argument.
2. Value check: `ValidateLeafValue` (parser, set parser, meta parser, freeform parser, list keys, `ParseAt` for editor `load`), `validateInlineListChildValue`, `storeValueOrArray`, `validateValueOrArrayItems`, the parser's missing-value arm, the tree walk (`validateEnumeration` gives the verdict; `validateEntry`, the frame that holds the leaf's `*yang.Entry`, attaches the refusal, because the declared-order and help readers take an entry and `validateEnumeration` holds only a `YangType`), `ValidateValueAtPath` (editor `set`, offline `ze config set`), `set cli format` (through `ValidateLeafValue` on its leaf), the web CLI terminal `set` and the web form sites (both new, through `ValidateLeafValue`), the editor bgp walk arms (`validatePeer`, the bgp-level arm), `parseCommonAttributeText`, `validateEnum` and `validateUnion` (command args) each build ONE typed refusal value (path, value, accepted values with help, suggestion, secret flag) when the value is not accepted.
3. Rendering: the typed refusal's `Error()` gives the shared text; each surface adds only its own frame (`line N:` and `write:` for a hierarchical file, `line N:` and the file form of the set-form fix line (the line's verb) for a set-format file, the editor form for a session-mode commit, a `set <path> <value>` fix for the editor, offline set and web terminal, the diagnostic code, `expected`, `actual` and `path` for `ze config validate` JSON, the editor form with no `line N:` and no `write:` for REST and gNMI, and for a tree-walk failure no `<section>: <path>:` prefix, since the body names the path). Every frame wraps the refusal with `%w` (or a typed line error with `Unwrap`), so `errors.As` recovers it through the frame. `SectionValidationError.Message` renders the attached refusal instead of `<section>: <path>: <Err.Message>`. `runValidation` keeps each typed refusal beside its diagnostic (not inside `diagnostic.Diagnostic`, whose fields are the JSON contract), so `ValidateContent` can frame it; today it has only strings.
4. Masking: every refusal is built with its secret flag already set, so no consumer sees a value or a suggestion it would have to mask. On the parser, editor and web paths the builder holds the `LeafNode` and reads `config.LeafHoldsSecret`. On the tree walk, `validateEntry` holds the `*gyang.Entry` and reads its `ze:sensitive` and `ze:bcrypt` extensions through one reader in `config/yang` (moved there from `hasSensitiveExtension` and `hasBcryptExtension` in `yang_schema.go`, which `yangToLeaf` then calls, so `LeafNode.Sensitive`, `LeafNode.Bcrypt` and the walk read one fact). This covers every walk consumer: `SectionValidationError.Message`, the editor's bgp walk (`validatePeer` and the bgp-level arm read `Message`), and the `update text` command (reads `Error()`). With the flag set, the value slot carries `config.SecretDataPlaceholder`, no suggestion is computed, and the accepted values stay. `SectionValidationError.Message` keeps one override: when `Sensitive` is set but the refusal's flag is not, it renders the refusal with the flag forced on. That happens when the schema cannot be built (`ValidateCustomSections` then marks every failure sensitive), and also through `isSensitiveLeaf`'s bare-name match, when a leaf that is not sensitive shares its name with one that is; forcing the flag on in both cases errs toward hiding. One broadening is intended: the walk's flag reads `ze:bcrypt` as well as `ze:sensitive` (the `config.LeafHoldsSecret` fact), while `SensitiveKeys` reads only `LeafNode.Sensitive`, so a walk refusal on a bcrypt leaf is now masked where `Message` did not mask it before. `DisplayMessageAtPath` / `MaskSecretInMessage` stay as the surface's second line of defence, unchanged.
5. Path: the refusal carries its path as segments (a name, plus the key for a list entry). The parser takes them from its path stack, and the set parsers from the tokens their walk has consumed on the line; `ValidateLeafValue` and `ValidateListKey` take them as a parameter; the tree walk threads them from `ValidateTree` (segments split from its root path argument, which holds no key) through `walkTree` and `validateListKey` into `validateEntry`, beside the string path it already builds; `Validate` and `ValidateContainer` split their slash path, which carries no list key from any production caller. The web CLI terminal holds a CLI token path with list keys in place and no `Completer`, so it takes its segments from `Schema.TokenPathSegments` (`schema.go` row), an answer of the one unexported walk `LookupTokenPath` and `ValidateTokenPathKeys` share, so the rule that decides which token is a key stays declared once; the completer's conversion in `ValidateValueAtPath` runs over its own `*gyang.Entry` schema (`completer.go` row). No frame parses the string path back. A frame that knows a better root than the walk re-roots the refusal: one operation on the refusal type replaces its leading segments. `validatePeer` replaces `bgp peer` with `bgp peer <P>`, or `bgp group <G> peer <P>` for a peer under a group whose `peerTree` holds the refused leaf. Whether `peerTree` holds it is decided from the refusal's own segments below the `bgp peer` root, keys included: a container segment descends by name, a list segment descends to the entry its key names, and the last segment is the leaf, which the tree must hold with a value. `hasResolvedValue` is not used for this, because it descends containers only and would call every leaf under a list inherited. When the peer is under a group and `peerTree` does not hold the leaf, the value was inherited from the group, so the refusal is re-rooted to `bgp group <G>` (the path where the value is written) and takes the line of that leaf inside the `group <G>` block (found the way `findFieldInPeer` finds a field in a peer's block, from the `group <G>` header, falling back to that header line), never a peer's line. `validateWithYANG` keeps one set of reported refusals for the whole walk, keyed by the rendered path: a refusal whose key is already in the set is dropped. Every peer of `G` produces the same inherited refusal (same path, same value, same group line), so the one kept does not depend on the order in which the map ranges visit the peers. `parseCommonAttributeText` gains the command words as a parameter (`update text` from `ParseUpdateText`, `update cursor` from `handleUpdateCursor`) and replaces `bgp peer update attribute origin` with those words plus `origin`. Command arguments: `ValidateArgs` gains the command words as a parameter, which its callers hold or are given (the dispatcher passes `matchedCmd.Name`, `ValidateModelArgs` its command path, `leroot.go` its tool words, `commandtest.Args` none, since it passes no definitions; `wrapWithEnsureChain` passes the step's own words from a new `EnsureStep` field, the ancestor command's path, which `buildEnsureChain` fills from the path tokens up to and including the ancestor it is adding), and passes them to `validateEnum` and `validateUnion` as the leading segments, then the argument name, so no re-root is needed there.

## Design Insights

- The parser's enum refusal is reported by `ze config validate` as `config-parse` today, so the diagnostic code that exists for enums (`config-yang-enum`) is reached only when the parser did not refuse first. The typed refusal lets the parser's error carry the same code.
- Three paths do not refuse at `set` (web form: type check only; web CLI terminal: no check; REST/gNMI: no check), so "the same message on every path" also means the same moment for the web terminal, where the operator is looking at the line they typed. REST/gNMI keep the commit-time refusal (A-3).
- `ValidateCustomSections` never checks a `bgp` enum (`bgp` is not in `validatedSections`), so the operator's usual enum refusal at `ze config validate`, daemon start and reload, and AC-11's diagnostic, come from the parser. The editor and web commit run a second walk over `bgp` (`validatePeer` per peer, and the bgp-level arm of `validateWithYANG`), which does check `bgp` enums. It starts at `bgp/peer` with no peer key, so the frame that knows the peer re-roots the refusal (AC-23). The parser refuses a plain enum first, so with Q-2 yes this walk is where a `bgp` union-with-enum leaf is refused.
- The walk's path string cannot be parsed back into segments (a list key may hold `/` or `]`), and several consumers read the walk's refusals (`ze config validate` JSON, `SectionValidationError.Message`, `validatePeer`, `parseCommonAttributeText`). So the walk threads the segments and builds the refusal once in `validateEntry`, with its secret flag already set from the entry's extensions; no consumer re-derives the path or the sensitivity.
- Two renderers sat between the walk and the operator, and both would have undone the shared body: `SectionValidationError.Message` repeats the path and hides the accepted values on a sensitive leaf, and `ValidateContent` flattens every refusal to a string before the REST and gNMI hook sees it.
- The enum value order was not one fact: goyang's `EnumType.Names()` sorts, so the tree walk, the leaf-list builder and `set cli format` listed values alphabetically while the parser listed them as declared.

## Known Limitations

- Option (d), a YANG-declared reason for a removed enum value, is not designed here: the owner chose (c). Possible future work only.
- Pattern refusals (`value "x" does not match pattern "<regex>"`) and range/length refusals are not changed here unless the owner answers Q-5; if Q-5 places them in another spec, that spec is written and named here.
- `retiredKeywords` (keywords, not values) stays a Go map.
- A bad value at `bgp group G ...` in a group with no peer is never walked by the editor and web commit bgp walk, because `validatePeer` runs once per peer (`validateWithYANG`'s group loop ranges over the group's peers). So AC-23's inherited case needs at least one peer in `G`. This predates the spec and is not changed here. A plain enum there is still refused by the parser; a union-with-enum value there is not refused by this walk.
- The group-block line an inherited refusal takes (Data Flow 5) is found the way `findFieldInPeer` finds a field: a `strings.Contains` match on the header needle, then the first line in the block whose text starts with the leaf name and a space. So `group G` also matches a `group G2 {` header that comes first, and a leaf name that occurs twice in the block (`ip` under `connection remote` and under `connection local`, or inside a nested `peer`) takes the first. In schema order the group's own `peer-fields` come before `list peer` (`ze-bgp-conf.yang`, `uses peer-fields` before `list peer`), so AC-23's case finds the right line as long as its `group G` writes no other `ip` leaf of its own, which `TestFormatPeerErrorEnumUsesSharedBody`'s config keeps true (a remote address is per peer). A whole-word header match with a descent by the refusal's segments would remove the limit, but it is a second line finder beside `findFieldInPeer` and `findFieldLine` for a line number only, so it is not built here. On a set-format candidate (session mode) no block exists, so the finder falls back to the first line holding the header words, which is a `set bgp group G ...` line. The verdict and the refusal text are right in every case; only the line number can be another line of the same group.
- The set-form fix line holds the path from the top of the tree, on every surface that writes it: the Set frame (editor `set`) and the Set-format file frame, including a session-mode SSH commit. An operator inside an `edit` context who types the line as written gets the context prepended, because `cmdSet` builds its path from `m.contextPath` plus the arguments (`cli/model_commands_edit.go`), and `cmdRename` builds the path to the old entry the same way, so the `rename` form of a key fix line behaves alike. Typed after `top`, or at the root context, the line is accepted as written. This is the Set frame's existing decision, carried to the commit surface; the fix line is not rewritten relative to the operator's context.
- In a set-format file, the fix line for a refused list key is the entry line alone: the line's verb, the list path and the corrected key (or the alternation). On a line that continues past the key (`set <list> <bad-key> <leaf> <value>`) the rest of the line is not echoed, because those tokens would reach the error text with no secret check, and the refusal's secret flag covers the refused key only. A session-mode surface writes `rename`, which keeps the entry's subtree (Set-format file frame).
- A refused member of a plain leaf-list (`ValueOrArrayNode`) in a session-mode candidate gets the editor form `set <path> <member>`, which adds the accepted member and leaves the refused one, because the editor's `set` appends to a plain leaf-list (`SetValue` → `setLeafListMember`). The operator also deletes the refused member (`delete <path> <refused-member>`, which `deleteLeafListValue` serves); until then the next commit refuses it again. A two-line fix (`delete` then `set`) is not written: it would be a second shape of the one fix line, chosen by the node kind, which the refusal type does not hold.
