## Task

Record and resolve one RFC 4271 Section 9.2 defect in the route-server relay
(`bgp-rs`). When two sources announce the same prefix and one of them
withdraws it, a route-server client that did not negotiate ADD-PATH must be
sent the remaining source's route as its new best path. Today the relay
forwards the withdrawal and nothing else, so the client loses a prefix that is
still reachable.

The route reflector (`bgp-rr`) has the same gap and is in this spec's scope
(owner reading of Q-1, recorded under Q-2; design review round 1, I4): its
per-prefix owner withdrawal is forwarded bare on the same cached rail, and its
source departure is worse, a plain withdrawal sent to every peer whatever
the destination's current owner (Design-time re-check, bgp-rr row).

Found by spec-rfc-verdict-test-fix-pass (child spec-rfc-verdict-fix-bgp,
continuation 19, 2026-10-01). Main-thread ruling R57(b) in
`plan/handover/rfc-verdict-test-fix-pass/RULINGS.md` homes it here because the
fix needs a per-source path store in the relay, which is larger than a verdict
fix.

**Key insights:** (minimal context to resume after compaction)
- Defect open at HEAD only when the withdrawing source is the destination's CURRENT owner (B, A, A-withdraw). Ownership fence `b880c5a9a7` already covers A, B, A-withdraw.
- The survivor election and the fenced writer already exist for source DEPARTURE (`recoverRouteSel` -> `recoverNLRIBatch` -> `request bgp rib recovery`). The fix is to route owner withdrawals through that election, not to build a store.
- Round 2 (I-3): there is no mode field. Each owed key carries an EXCLUDED-SOURCE SET: empty for an owner withdrawal (the withdrawn path is already gone from the RIB after `DrainEventsApplied`) and for a bgp-rib sent-lifecycle removal (the RIB removed the path before it dispatched the removal), the departed source(s) for a departure, unioned on merge. Round 3 (N-6) removed the per-source cut the set used to carry.
- Round 2 (B-1), round 3 (N-6): a departure owes a destination a decision only where the departed source is that destination's CURRENT owner of the key AND that owner's session is no longer current (`forwardSourceCurrent` is false for the source session generation now stored in `adjOutPath`), read under the adj-out table mutex. Elsewhere nothing is written, which keeps forward-all at destinations the departure does not concern and keeps a reconnected source's newer route. No message-ID cut is compared anywhere.
- Two forward rails reach a destination writer: plugin cached forwarding (`reactor_api_forward.go`, shared with bgp-rr) and the reactor RS fast path (`forward_rs.go`, RS only). Both set authority `adjOutForwarded`.
- The original red probe is lost and must be recreated.
- Round 1 (B1): the writer only RECORDS owed keys; a long-lived per-destination recovery worker, separate from the forward worker, does the drains, the lookup and the admission. Neither the destination's forward worker nor a source read goroutine ever waits on recovery.
- Round 1 (B2, I1): the fence is per key (an owed record with an epoch in the destination's adj-out table), not the destination-wide send sequence and not the survivor's whole-source publication cut, which livelock under churn. Round 2 (I-2, I-3): the record also notes which owners' withdrawals for the key reached the writer since the worker's snapshot, and admission retries only when one of them is the chosen candidate; the writer's record is the only authority on "owner moved", so the RIB carries no second owner-moved check.
- Round 2 (I-1): no shared reactor-wide drain. Each recovery worker's round drains for itself; the owed set already coalesces every key owed during a round into the next one.
- Round 1 (I4): bgp-rr is in scope: same per-prefix gap on the cached rail, and a departure that sends plain unowned withdrawals.
- Round 3 (B-1): the owed-key rule is per authority. Only an announcement that installs a NEW owner removes the record. A bgp-rib replay of `ribOut[Destination]` (`adjOutExpected`: ROUTE-REFRESH, `clear bgp rib out`) is refused while the key is owed, because it replays the very route being replaced.
- Round 3 (I-2): a GR-retained source leaves through bgp-rib's sent-lifecycle removals (`sentRemoval`), which are owed exactly like an owner withdrawal. bgp-rr's departure honours `retention.Family` as bgp-rs does (Q-5).
- Round 3 (I-1), round 5 (B-1): a receive-publication failure ends that source's session (Cease, Out of Resources), and the round that meets the failure or the stop EXCLUDES that source from every key it decides, so the election never sees the source's unpublished state; its departure decides the keys it owns.
- Round 3 (I-6): "is a recovery owner registered" is answered by the frozen command registry's lock-free `Lookup`, not by a second atomic.
- Round 3 (I-3): a round's lookup goes out in chunks of at most 500 keys per family; the chunk bounds a request, never the owed set.
- Round 4 (I-1), round 5 (I-1): R-12's sent-projection removal fires only for the sent event of a RECOVERY write (marked in a fresh copy of the item's meta) whose candidate's received path is now gone with no newer revision, and leaves through a long-lived bgp-rib lifecycle dispatcher, never an RPC on the event path. No watermark: the candidate came out of bgp-rib's own lookup, so it was applied by construction.
- Round 4 (I-2), round 5 (I-2): the publication-failure teardown is its own defect-fix phase (2b) and commit. It declares "no retention" through D1's reason producer, a second input beside `notificationExchanged`, because an unsent Cease leaves that flag false. Round 6 (I-2): that input reports a second declared reason, `rpc.ReasonAdjRIBInInvalid` (spelling: Q-6), and GR calls the declared predicate `rpc.ReasonForbidsRetention`, so `gr.go` always changes.
- Round 4 (I-4), round 5 (I-3), round 6 (B-1, option i): drain replays are `adjOutExpected` and are refused for an owed key. The refusal is counted by ONE per-peer monotonic atomic on `Peer`, incremented under `writeMu` by whichever goroutine performs the write (the forward worker for a queued receipt write included), never reset, and read only as a delta. The update-route reply, the SDK and bgp-rib's `resent` / `refused` are unchanged, and no command waits for a queued write: round 5's reply count needed a wait that self-waits through bgp-rib's event delivery (round-6 B-1). This spec deletes `recoverySnapshot`, `sentUpdateSequence` and `noteFilteredOperation`, and the drain keeps only the per-peer `writeMu` take-and-release.
- Round 5 (N-7): a candidate stepped past on `errRelayNoSource` re-owes the key with that source added to its excluded-source set (a merge), so the next round elects over the survivors without it, which keeps AC-12 under the non-transitive MED comparator.
- Round 7 (I-1): `writeUpdateBody` filters a body twice whenever a pass removed an NLRI, so every owed-set effect of `allow` (owe, merge, removal, mover, owed-refused count, wake) is staged on the `adjOutWrite`, reset between the passes, and applied once per write.
- Round 7 (I-2, option b): the down event, and D1's reason producer with it, run in `runOnce` after `<-deliveryDone`, so a late publication failure is in the reason; every plugin now gets a session's buffered UPDATEs before its down. The "Adj-RIB-In invalid" fact is the existing `receivePublication.failed`.
- Round 7 (I-3): one wake rule (every owe, merge and re-owe wakes the worker; an admission that leaves a key owed starts the next round at once), a per-key source fence on the forward worker, and `recoveryAdmission.retry` deleted.
- Round 8 (B-1, I-3): an FSM callback runs on whichever goroutine drains the event, so on a local teardown the leave callback can still be running when `runOnce` passes `<-deliveryDone`. The drain and the down move into a `runOnce` DOWN DEFER: fire `EventTCPConnectionFails` when the FSM still reads Established (no other leave came), close `deliverChan`, `<-deliveryDone`, wait on the leave signal the leave arm closes after `setState(PeerStateConnecting)` when the FSM's sticky entered-Established bit is set, then reason, down, history row and dynamic-peer cleanup. Data Flow 4's departure depends on the down following `setState(PeerStateConnecting)`. Being a defer, it also covers a read-goroutine panic that leaves no lock held (round 9, I-3). Fixes HEAD's "session ends with no down event" here, no journal row.
- Round 9 (B-1): the BFD subscriber goroutine is a drainer too. A non-strict peer's BFD Down in Established runs the leave callback on the subscriber, and the callback's BFD release ended in `<-done`, the channel that same subscriber closes on exit: a self-wait. So the leave arm keeps only the release's non-waiting half (`close(stop)`, `Unsubscribe`, `ReleaseSession`) and hands the subscriber's `done` to the leave record, and the down defer waits on it after step 3, on the `runOnce` goroutine, which is never the subscriber. This also fixes a HEAD defect, the same self-wait, which leaks the subscriber goroutine and loses that session's down (the main thread journals it). Round 9 (I-2), corrected in round 10 (I-2): `Reactor.cleanup` holds `r.mu` for its whole run, Phase 1 (`fwdPool.Stop`, and in standalone mode the owned `r.api.Stop()`, which `cleanup`'s own comment bounds at `pluginStopGrace` 3 s plus a 500 ms group wait), Phase 2's one concurrent 2 s wait for every peer, and Phase 3, so a leave arm that runs after `cleanup` took `r.mu` waits that whole hold out in `markSessionUp`, and the downs this spec newly announces at reactor stop land after it. One drainer is not bounded by it: a forward-pool worker draining a leave blocks in `markSessionUp` while `fwdPool.Stop` joins it with no deadline under the same `r.mu`, a deadlock HEAD already has and this spec neither causes nor widens (Data Flow 5 step 3; `plan/journal/lock-held-across-a-join.md`).
- Round 8 (I-1, I-2): a non-opaque raw write applies its staged record removals (`record` runs for it); the admission's per-key outcomes are written, decided with nothing to write, record already gone, left owed, re-owed, error, and only none of these is `errRecoveryNotWritten`.

## Data Flow (MANDATORY - see `ai/rules/architecture.md`)

### Entry Point
- Wire: an UPDATE from source peer A whose Withdrawn Routes field or MP_UNREACH_NLRI names a prefix A previously announced, received on an Established session.
- Format at entry: raw UPDATE bytes held in the reactor message cache, delivered to bgp-rs as a structured `update-received` event (`item.msg`) or text in fork mode.
- Second entry (round-3 I-2): a bgp-rib sent-lifecycle removal (`sentRemoval` via `dispatchSentLifecycle`) for a source whose GR-retained routes are purged, arriving at the reactor as a withdraw command with `sent-owner-message` meta.

### Transformation Path
1. Reactor receive: the UPDATE is accepted, cached, and either written by the RS fast path (`reactorForwardRS`, bgp-rs only) or handed to the forwarding plugin.
2. bgp-rs worker (`processForward`) or bgp-rr (`forwardUpdate`): forwards the cached UPDATE (`ForwardCached` / `cached <id>`) to selected targets.
3. Session writer (destination forward worker, or the source read goroutine on the fast path): `adjOutWrite.allow` per NLRI. NEW: a withdrawal for a key whose adj-out entry is owned by a source (`entry.owner.source` set), on a destination that did not negotiate ADD-PATH send for the family, while a recovery owner is registered (Key Design Decisions, "No RIB owner"), is not emitted when it is (a) a forwarded withdrawal, received or synthesized, from that owner (`adjOutForwarded`, `adjOutSameOwner`), or (b) a bgp-rib sent-lifecycle removal the writer admits under `adjOutExpected` (`sentRemoval`, sent by `dispatchSentLifecycle`; round-3 I-2). Case (b) is how a GR-retained source's routes leave: bgp-rs, and after this spec bgp-rr (Q-5), skip retained families at departure, and the RIB's eventual purge used to write a bare withdrawal with no election. The writer records the key in the destination's OWED SET and leaves the adj-out entry with the old owner until recovery writes. The owed record holds: a copy of the destination-framed NLRI bytes (taken before `adjOutWrite.release` clears the pooled maps), the family, the destination session it belongs to, an EMPTY excluded-source set, an epoch, and an empty MOVERS set (step 7). The set is empty for (a) because an owner withdrawal excludes nobody (round-2 I-3), and for (b) because the RIB removed those received paths under `peerMu` before it dispatched the removal (A-9), so the purged path is no longer a candidate while the source's other live paths stay eligible. The writer then wakes the destination's recovery worker without blocking: a one-slot wake channel, send-or-skip. The wake carries no data; the owed set is the queue, so a skipped wake loses nothing (round-2 N-7). ONE WAKE RULE (round 7, I-3): every insertion into the owed set and every merge into a record wakes the worker, whoever makes it: the writer's owe or merge here, the departure's owe or merge (step 4), and the admission's re-owe (step 7). The worker also starts its next round at once, without waiting for a wake, whenever an admission completes with any key of its snapshot still owed (left owed on an epoch mismatch or on the mover retry, where a recorded mover is the candidate the admission was about to write, or re-owed; a record of another destination session is never left owed, step 7; round 9, I-1). This cannot hot-loop: every key still owed after an admission is owed because something changed (its epoch moved on a merge, its candidate withdrew, or a source was added to its excluded-source set), and each such change is bounded (step 7, R-9). The writer does no IPC, no drain and no wait. EFFECTS ARE STAGED, never applied inside `allow` (round 7, I-1, read at the producer): `Session.writeUpdateBody` runs `ownership.filter(nil, body)` and, whenever that pass removed an NLRI (`ownership.removed != 0`), clears `removed`, `suppressed`, `owners` and `withdrawn` and runs `ownership.filter(handle.Buf, body)` a second time, and both passes call `section` -> `allow` for every NLRI. Within ONE pass, every MP_UNREACH NLRI goes through `allow` twice (round 8, N-1, read at the producer): `filter`'s "Populate withdrawal admission before announcements" loop calls `section` on every MP_UNREACH attribute, and its second attribute traversal calls it again, so a non-IPv4-unicast withdrawal is evaluated twice per pass and four times in a twice-filtered write. An owed NLRI is always removed, so every write that owes a key and also carries an admitted NLRI evaluates `allow` at least twice for it. So every side effect this spec gives `allow` for an owed key (the new owe record, the merge, the record removal by a new owner, the mover note, the owed-refused count of step 7, and the wake) is staged on the `adjOutWrite` during `filter`, STAGED PER KEY (keyed by `adjOutKey`) and idempotent within a pass, never appended, reset with `owners` and `withdrawn` between the two passes, and applied ONCE, under `writeMu` with the table mutex, after the last pass that ran: on the `length == 0` return (an all-owed body, which never reaches `record`), on the PATHS-LIMIT `n == 0` return, and on the write path before `record`. Both passes therefore read the table as it stood before this write, and the second decides exactly as the first. A pass that returns an error applies nothing, because nothing of that body is written at HEAD either and the error goes back to the caller. A RAW WRITE IS NOT OBSERVE-ONLY (round 8, I-1, read at the producer, correcting round 7): `writeUpdateBody`'s `raw` branch, reached only from `SendRawMessage` under `writeMu` with no `sentForward`, runs `ownership.filter(nil, body)` and, when that returns no error (`opaque` false), `ownership.record(body)`, which installs each announced key with the originated owner and deletes each withdrawn key. Its bytes reach the wire whatever `allow` says, but the table changes. So a raw write whose filter pass returned no error applies its staged record removals, and only those: an announcement of an owed key is an originated write with no sent-owner authority, so it installs a new owner and REMOVES the record (step 7, first bullet, AC-6), and nothing else can be staged, because no NLRI of a raw write is source-bound (no owe, merge, mover or owed-refused count). Its originated withdrawal of an owed key deletes the adj-out entry and leaves the record, as step 7 says for every originated withdrawal, and step 8 reads that. An opaque raw write (filter error) applies nothing and records nothing, as today. A raw write never carries an owner withdrawal that should be owed, because it holds no sent-owner authority. SAME KEY WITHDRAWN AND ANNOUNCED IN ONE BODY (round 8, N-2): RFC 4271 Section 4.3 reads "A BGP speaker SHOULD treat an UPDATE message of this form as though the WITHDRAWN ROUTES do not contain the address prefix.", so an announcement of a key in the same body cancels that key's staged owe: the owner's new route installs, and the key is neither owed nor rewritten by a later round. A key owed before the write began needs no such rule, because the announcement removes its record (step 7, first bullet). The staged effects live in the pooled `adjOutWrite` and are copied into the table before `adjOutWrite.release` clears it. On the fast path, an UPDATE whose only content for this destination is owed keys reports `tryDirectWriteNoFlush` handled AND delivered: the item is finished and the destination's decision is owned by recovery, so the cached rail must not forward it a second time (round-2 N-6). Every forwarded write first checks whether the destination's owed set is empty, and only a non-empty set costs a per-NLRI lookup (round-2 N-9). Every write that installs an owner also records that owner's source session generation in `adjOutPath` (a new field: the forwarded or initial item's `receivedGeneration`, or the survivor's `generation` on a recovery write; an `adjOutExpected` write keeps `entry.owner`, generation included). `adjOutSameOwner` keeps ignoring it, as the `allow` comment requires so that a GR-retained path stays withdrawable by the same source on its new session (round-3 N-6).
4. NEW, departure: the departure command (bgp-rs `recoverRouteSel`, and now bgp-rr `handleStateDown`, both with `recovery-source` meta) no longer runs `recoverNLRIBatch`'s inline per-destination loop. For each selected destination and each key, under that destination's adj-out table mutex, it creates or extends an owed record ONLY when the adj-out entry's owner is the departed source AND that owner's session is no longer current, meaning `forwardSourceCurrent(entry.owner.source, entry.owner.generation)` is false (round-3 N-6). Where another source owns the key, where the departed source's reconnected session owns it (its generation is current, so its newer route stays), or where no entry exists, nothing is owed and nothing is written (round-2 B-1, AC-18). Because `forwardGeneration` moves on every Established transition and on `Peer.Stop`, the rule also owes the keys of every EARLIER session of that source, such as a GR-retained route from before a reconnect that the new session never re-announced. No message-ID cut is compared: the generation is read under the table mutex every write takes, so the test is exact where the round-2 same-source cut was a RIB-side reading after a drain, and `recovery-cut` is deleted end to end (Files to Modify). At an ADD-PATH destination the departure command names received identities, not the destination's identifiers, so the record is owed per prefix there and the per-identifier owner test runs at admission (steps 6 and 7). Creating or extending adds the departed source to the key's excluded-source set; a key already owed (by an owner withdrawal, a lifecycle removal or another departure) keeps one record, its excluded-source set becomes the union, and its epoch moves (round-2 I-3). Each owe or merge wakes the destination's worker under step 3's one wake rule (round 7, I-3), so the departure command never waits on keys no round will start for. A departure that arrives while no recovery owner is registered keeps today's outcome: each selected destination is retired through AutomaticStop/Cease with the cause logged (the registry check at the top of `recoverNLRIBatch` today; AC-11; round-3 N-7), because the plugin asked for an election no process can run. The command then waits for completion of the keys it owed, so its synchronous contract with the plugin holds. Cancelling that wait only stops the waiter; the keys stay owed and the worker still decides them. EVERY removal of a record completes its waiters: a decision at admission (step 8), a removal by an announcement that installs a new owner (step 7, AC-18), and a table reset, which completes them with "session retired" (Integration Points; round-2 I-5, round-3 N-8).
5. NEW, per-destination recovery worker (one long-lived goroutine per destination session, never per event; lifecycle in Integration Points). In ONE table-mutex section it takes a snapshot of the owed set (keys, excluded-source sets, epochs) and clears each snapshotted key's movers set. Only after that section does it capture the source receipts and publication cuts (`recoverySources`) and drain them (`drainRecoverySources`), then `DrainEventsApplied`. This order is a constraint (round-3 N-12): were the cuts captured first, a withdrawal landing between the capture and the movers clear would be neither drained nor recorded. There is no shared reactor-wide drain (round-2 I-1): the owed set already coalesces every key owed while a round runs into the next round, so a burst of withdrawals costs one drain per destination per round, not one per withdrawal. A source X whose publication stopped or failed before reaching its cut (`errReceivePublicationStopped`, `errReceivePublicationFailed` from `receivePublicationCut.wait`) does not fail the round: `drainRecoverySources` waits on every other source and returns the set of such sources instead of the first error, and the round adds each of them to the excluded-source set of EVERY key it asks about (round 5, B-1). The addition is for this round's request only: the owed record is not changed and no epoch moves. For a failure the round's drain observes, X's withdrawals that never reached bgp-rib therefore cannot make X's withdrawn path electable, whoever X is, the chosen survivor included, and correctness does not depend on how fast X's teardown runs: `resolveRelaySource` and `forwardSourceCurrent` still accept X while the FSM keeps it Established after `Session.teardownAutomatic` has sealed it, so the admission's source check alone would not stop the write. The exclusion is exact for what the drain sees: `wait` returns an error only for the source it waited on and checks `failed` before `completed`, so a failure after the cut is excluded too (conservative). A failure after `drainRecoverySources` returns is outside this claim (round-6 N-1): the round may elect X's withdrawn path, and on the cached rail the unpublished withdrawal never reaches C's writer, so no mover is recorded; C then heals through X's teardown and departure (Phase 2b, step 4), the same exposure as any route X forwarded. `failed` is sticky for the session, so every later round of that session excludes X again until X's session ends. A stopped publication belongs to a session that has ENDED: `errReceivePublicationStopped` needs `publication.done` closed, which happens only after a panic (failed) or after `runOnce`'s down defer closes `deliverChan` once `Session.Run` has returned or unwound. X's own departure then decides every key X owns at this destination (step 4). The delivery worker's three failure paths in `peer_run.go` (a recovered panic, a nil reactor, a nil message receiver) call `Session.teardownAutomatic` with Cease / Out of Resources on the session they serve (round-3 I-1, Phase 2b).    - WITHDRAW: no candidate remains.
   The round-2 KEEP outcome is gone (round-3 N-6). It answered "the destination holds the reconnected source's newer route", and that route is now never owed (step 4), so the RIB is never asked about it; A-7 and the per-source cut go with it.
   A departure key at an ADD-PATH destination keeps today's `request.SentAddPath` branch, without its cut: the answer is WITHDRAW for each of the departed source's sent identifiers at the destination for the prefix, and no election runs. The admission writes only those identifiers whose adj-out entry is still owned by a no-longer-current session of the departed source (step 7), so the reconnected session's identifiers are never withdrawn. An owner withdrawal or a lifecycle removal never reaches an ADD-PATH destination's owed set (step 3).
   The RIB no longer answers "nothing" for a key whose sent owner moved: the writer's record is the single authority on ownership (an announcement that installs a new owner removes it, step 7), so the round-1 I1 RIB check is dropped rather than kept as a second declaration (round-2 I-3). A requested key with no outcome in the answer is a lookup error (AC-11), never read as "no survivor".
7. Admission on the destination's forward worker (the existing `recoveryAdmission` item, dispatched with `dispatchOverflow`): under `writeMu`, per key, the owed record must still be present, belong to this destination session, and carry the epoch captured in step 5. A record already gone (removed by a new owner, a decision, or a table reset between snapshot and admission) is that key's outcome "record already gone", and nothing is left owed. A record whose epoch moved is left owed for the next round, that key alone (no destination-wide retry), and the worker starts that round as soon as the admission completes (step 3, one wake rule). A record of another destination session is unreachable (round 8, N-4, read at the producer): every table reset clears the owed set, `beginAdjOut` clears `routes` and the owed set when the table's session changes, and `runOnce` joins a session's recovery worker before the next session exists. Were one ever met, it is removed and its waiters complete with "session retired", never left owed, so it cannot start rounds forever; the admission reports it as RECORD ALREADY GONE (round 9, N-3), so it is one of the six outcomes and never retires C. THE FORWARD WORKER'S SOURCE FENCE BECOMES PER KEY (round 7, I-3, read at the producer): at HEAD the `fwdBatchHandler` recovery branch walks every section of the admission, sets `recovery.retry = true` and `break`s on the first lost source, which skips every sibling key of the admission, and `releaseItem` then sends `recovery.done <- recovery.retry` back to `relayRecovery`'s retry loop, which this spec deletes. After this spec a lost source re-owes only the key its section belongs to, and the sibling keys of the same admission are still written. `recoveryAdmission.retry`, the `bool` that `recoveryAdmission.done` carries, and the `case retry := <-admission.done` return in `relayRecovery` are deleted, not kept beside the re-owe (no-layering): the admission reports per key, and the FULL per-key outcome set is (round 8, I-2, read at the producer): WRITTEN (a survivor, or the owed withdrawal from the record's copy); DECIDED WITH NOTHING TO WRITE (the record is removed and its waiters complete, because the owed withdrawal is due, the outcome being WITHDRAW or SURVIVORS with every candidate egress-denied, and the adj-out entry is already gone, step 8 and case (i), or because no identifier of an ADD-PATH departure key's WITHDRAW answer is still owned by a no-longer-current session of the departed source; round 9, I-1); RECORD ALREADY GONE (removed by a new owner or a table reset between snapshot and admission, cases (b), (c) and (l), or a record of another destination session, removed with "session retired" above; round 9, N-3); LEFT OWED (the epoch moved, or a recorded mover is the candidate the admission was about to write, the MOVER RETRY of fence case (a): the record is untouched and its movers are cleared at the next round's snapshot; round 9, I-1); RE-OWED with a source excluded; or a write ERROR. `releaseItem`'s `errRecoveryNotWritten` check ("not retried and not written") becomes the per-key form: only a key with none of these six outcomes is the error, which `relayRecovery` treats as a hard failure and which retires the destination (AC-11). At HEAD the whole-admission flag is blind to the second and third outcomes only because `fwdBatchHandler` sets `recovery.written` once per batch after the flush; per key, each of them is a decision and MUST NOT retire C. The comment above HEAD's fence loop, "A generation change MUST retry the whole lookup, never relabel selected bytes", is rewritten to say what the code does after this spec: a generation change re-owes that key with its source excluded, and never relabels selected bytes (`ai/rules/stale-comments.md`). The epoch moves only when the record's excluded-source set grows (a merge, step 4), because that changes the question asked of the RIB. Between snapshot and admission the writer applies one rule per authority to an owed key (round-3 B-1):
   - an announcement that installs a NEW owner (`adjOutForwarded`, or an originated write with no sent-owner authority) is written and REMOVES the record, completing its waiters (newer owner wins, AC-6). The withdrawing owner's own later forwarded re-announcement counts as one: it carries a new revision and the owner's current session generation, so the writer MUST NOT compare it with `entry.owner` and refuse it as "the owner being replaced" (round-4 N-5). An `adjOutInitial` write never reaches this rule: `allow` refuses an initial write whenever an entry exists, and an owed key always has one, so it is refused as today (round-4 N-5);
   - an `adjOutExpected` announcement is REFUSED and leaves the record. It is a bgp-rib replay of `ribOut[Destination]`: ROUTE-REFRESH and `clear bgp rib out`, and also the drain spec's drain replay and its `drain-unjudged` one-entry follow-up replay (`plan/immediate/spec-daemon-drain-before-stop.md`), because `sendBatchUpdate` sets `adjOutExpected` whenever `SentOwnerMessage != 0` (round-4 I-4). While A's withdrawal is owed that entry still names A, because the deferred withdrawal produced no sent event, so it replays the very route being replaced (for the drain, tagged with GRACEFUL_SHUTDOWN). Admitted, it would remove the record and leave A's withdrawn route installed for good. The recovery write answers the refresh instead (AC-20). The refusal is COUNTED, never silent, and the count has ONE home: a per-peer monotonic atomic on the destination's `Peer` (round 6, B-1, option i, replacing round 5's update-route reply count). `allow` returns a distinct owed-refused outcome, the write stages one count per NLRI so refused, and the staged count is added to the counter ONCE per write, with the write's other staged effects (step 3, round 7 I-1): an owed-refused NLRI is removed, so a replay that also carries an admitted NLRI is filtered twice, and a count taken inside `allow` would add two for it. It is added under `writeMu`, on whichever goroutine performs the write: the command goroutine for a direct receipt write, and C's forward worker for a receipt write that `queueBehindForwards` diverted ("a nil answer means queued"), so a queued write is counted when it is written and no command waits for it. The counter lives on `Peer`, not on `adjRIBOut`, which resets per session; it is never reset, and every reader reads it as a delta between two loads. The command still succeeds, and the update-route reply, `rpc.UpdateRouteOutput`, the SDK's `UpdateRouteWithMeta` and bgp-rib's `resent` / `refused` keep their HEAD meaning: `resent` is "accepted by the engine", and at HEAD an `adjOutExpected` revision mismatch is already refused with `false, nil` and counted `resent` (journal row, `plan/journal/counter-counts-the-wrong-packets.md`). Round 5's wait for a queued receipt item is not taken: a ROUTE-REFRESH replay runs on bgp-rib's own `Process.deliveryLoop` (DirectBridge, synchronous), and the forward worker writing the queued item blocks in `Process.Deliver` once bgp-rib's 64-slot `eventChan` is full, so the wait would wait on itself (Current Behavior, refresh replay path). The counter counts every `adjOutExpected` refusal at an owed key, whatever replay carried it, so a reader that takes a delta over a window counts a ROUTE-REFRESH or `clear bgp rib out` refusal inside that window too; the drain spec reads its delta as "receipt replays refused at an owed key during the drain" (Blast Radius). Nothing is exported (Integration Checklist, Prometheus row). Under enhanced route refresh (RFC 7313), an End-of-RIB marker that reaches the destination before the recovery write makes it drop the prefix until that write lands; that converges and is accepted;
   - an `adjOutExpected` withdrawal (a lifecycle removal) merges into the record as in step 3: no excluded source is added, the epoch does not move, nothing is written;
   - an originated withdrawal (no sent-owner authority, which `allow` admits today whatever the owner) is written as today and leaves the record, so recovery still decides. Its write deletes the adj-out entry (`adjOutWrite.recordSection`, withdraw branch), which step 8 reads so that C is not sent the withdrawal twice (round-4 N-10);
   - a forwarded withdrawal from any source, admitted or dropped as non-owner, adds its owner identity (source, received path identifier and ADD-PATH flag, the fields `adjOutSameOwner` compares) to the key's movers set and writes nothing else. The rule applies to a key owed BEFORE the write began: the owner withdrawal that creates the record does not also note its own owner as a mover, because the owe is staged and applied after the last filter pass (step 3, round 7 I-1).
   Admission retries the key, leaving it owed with its record untouched (LEFT OWED in the outcome set above; round 9, I-1), only when a recorded mover is the candidate it is about to write, because only that withdrawal can make the chosen route dead (round-2 I-2). Any other mover is irrelevant to the decision: a candidate ranked above the chosen one was already denied by egress, one ranked below was not chosen, and a source with no candidate offered nothing. This still closes the round-1 hole where the survivor's own withdrawal is dropped as non-owner while A's withdrawal is owed, and it bounds retries: each retry needs the chosen candidate's own withdrawal, after which that candidate is gone from the RIB. When `queueRecovery` cannot resolve the chosen survivor, or the survivor's forward generation moved since the round's receipt (`errRelayNoSource`, at queue time), or the same loss is found later on the way to the write (round-6 N-3, read at the producer): `forwardUpdateValidated` refuses with `errForwardNoSource` when its `forwardSourceCurrent` check fails as `queueRecovery` hands the item to `forwardUpdateCore`, and the forward worker's recovery branch (`fwdBatchHandler`) finds `forwardSourceCurrent` false under `writeMu` at write time, where HEAD sets `recovery.retry`; in all three cases the admission writes nothing for the key and RE-OWES it with that survivor's source added to the record's excluded-source set, as a merge: the epoch moves and the next round elects again (round 5, N-7, replacing round 3's step to the next candidate), started by the one wake rule with no further external wake (step 3, round 7 I-3); the admission's other keys are still decided. That survivor's session ended or restarted, or it was not in the round's receipt capture (`queueRecovery` also returns `errRelayNoSource` when the elected source is absent from the round's `sources` map, a peer added to `r.peers` after `recoverySources` captured it; round 7, N-3), so its round-start route is no valid replacement, and a restarted survivor's new route reaches the destination through its own forward (round-3 N-1). Excluding an uncaptured source is safe for the same reason: its own forward to C installs a new owner and removes the record. Stepping to the next candidate of the same list would not do: under the non-transitive MED comparator AC-5 exercises, the list was built by repeated `SelectBest` with the dead source's other paths still in the remainder, so `SelectBest(S \ {D1})` can differ from `SelectBest(S \ {D1, D2})`, and C would end on a route that is not the RIB's best of the survivors (AC-12). The re-owes are bounded: one per source, because an excluded source is never a candidate again for that record. Egress-denied candidates are still stepped past in list order (step 8, AC-5), because a denial removes no path from the RIB. The survivor's receipt is its forward generation only; its whole-source publication cut is no longer compared (round-1 B2). For an ADD-PATH departure key, each identifier in the WITHDRAW answer is written only when its adj-out entry is still owned by a no-longer-current session of the departed source (step 6).
8. Destination writer: on SURVIVORS, the first candidate that passes ordinary egress policy (and bgp-rr's reflection rules) is written with the survivor, and the survivor's session generation, as the new owner; when every candidate is denied by egress, or the outcome is WITHDRAW (a candidate whose source no longer resolves re-owes the key instead, step 7), the owed withdrawal is written from the record's copied destination framing with the old owner (round-1 I2; RFC 4271 Section 9.2 owes the withdrawal when no replacement exists), unless the key's adj-out entry is already gone, in which case nothing is written: an originated withdrawal admitted during the owed window already withdrew the prefix at C, and writing the record's copy again would send C a second withdrawal against AC-2's "exactly once" (round-4 N-10). In every case the record is removed in the same `writeMu` section and its waiters complete.

### Integration Points
- `adjOutWrite.allow` / `adjOutWrite.record` (`reactor/session_ownership.go`) - the single decision point every forward rail shares; gains the "owed to recovery" outcome for an owner's forwarded withdrawal and for a bgp-rib lifecycle removal, the per-authority rule for an owed key (Data Flow 3 and 7), and the owner's source session generation in `adjOutPath`.
- The destination's adj-out table (`adjRIBOut`, `reactor/adj_rib_out.go`) - holds the owed set beside `routes`, under the same table mutex every write already takes. Each record names the destination session it was owed to. EVERY site that resets the table clears the owed set with `routes` and completes each departure waiter with "session retired" (round-2 I-5): `adjRIBOut.reset` (called by `Peer.clearEncodingContexts` on teardown), `Session.retireWrite` (clears `routes` when the table is still its own), and `beginAdjOut` when the table's session changes. So an old session's record, framed for the old session's ADD-PATH negotiation, is never seen by the next session's worker, which also checks the record's session at admission. The departure command and the recovery worker now read the table under its mutex without being final writers, so the type's comment "Its only readers are final writers under writeMu" becomes false and is rewritten in Phase 3 (round-3 N-10, `ai/rules/stale-comments.md`).
- The recovery worker's lifecycle (round-2 I-5, round-3 I-4, N-2, N-3, N-4) - one per destination session. It is STARTED in the FSM Established callback BEFORE `setState(PeerStateEstablished)` publishes Established, and its first round runs on start without waiting for a wake, so a key owed before the worker existed is never stranded (round-3 N-2). STOP is an idempotent cancel plus a closed stop signal and never waits, so any teardown path may call it: `Session.retireWrite` (which runs under `writeMu`, possibly on the forward worker that owes the worker an `admission.done`), `Session.teardownAutomatic` from AC-11 (which runs on the recovery worker itself), and `Reactor.stop` / `StopForRestart`, which seals each live session through `Peer.sealSession` and notifies nobody. The ordinary close paths (a NOTIFICATION from the peer, hold-timer expiry, a TCP read error) reach none of those three, so the `Peer.runOnce` DEFER, the one that runs after `Session.Run` has returned and calls `clearEncodingContexts` (not the FSM leave-Established callback, which also calls it but runs on whichever goroutine fires or drains the FSM event, round-3 N-3, corrected in round 8 B-1), first calls stop and THEN joins. It runs after the down defer (Data Flow 5), which was registered later, so the leave callback has finished and the down has been delivered before the recovery worker is joined. Every exit path is therefore covered by construction (round-3 I-4), and the join holds neither `writeMu` nor the forward worker. A worker woken by stop releases its pending admission with "session retired". The in-process `RecoveryOwner.Lookup` takes no context, so the join is bounded by the lookup in flight; that lookup holds `peerMu` and by its contract never calls the forwarding engine, so it returns, and the IPC transport is already bounded by its command context. A provider that blocks forever (AC-16's test double) would wedge the join, so that test releases its provider before it tears the sessions down (round-3 N-4).
- `recoverNLRIBatch` / `relayRecovery` / `queueRecovery` (`reactor/relay_recovery.go`) - the inline per-destination loop is deleted (no-layering); departure enqueues into the owed set under the owner-and-generation check (Data Flow 4); the lookup transports and the admission item are reused by the recovery worker; `recoveryAdmission.current` and the `receivePublicationCut.current` check in `queueRecovery` give way to the per-key check of Data Flow 7; `errRelayNoSource` re-owes the key with that source excluded (round-3 N-1, round-5 N-7); `drainRecoverySources` returns the set of stopped or failed sources, which the round excludes from every key (round-5 B-1); `relayRecovery` chunks a round's keys at 500 per family (round-3 I-3). The registry lookup `Registry().Lookup("request bgp rib recovery")` at the top of `recoverNLRIBatch` stays the one answer to "is a recovery owner registered": the writer calls the same lookup, which reads the frozen snapshot lock-free, and treats `command == nil` or `command.Process == nil` as "no owner", the same two conditions `recoverNLRIBatch` tests (Key Design Decisions, "No RIB owner"; round-3 I-6, round-4 N-6). With the fence gone, `recoverySnapshot` has no caller and `Peer.sentUpdateSequence` has no reader, so both are deleted with the increment in `notifyMessageReceiver`; `adjOutWrite.noteFilteredOperation`, whose only effect is the other increment, is deleted with its two callers in `session_write.go` (no-layering; round 4, found while applying I-4; round 5, N-3). The recovery admission marks its write for R-12 by setting a `recovery-write` key in a FRESH copy of the item's meta, never in the shared `fwdItem.meta` map, which `session.sentMeta = item.meta` hands to the sent event (round 5, I-1). The drain spec's ordering step needs only the per-peer `writeMu` take-and-release, not the sequence (Blast Radius).
- `ribevents.RecoveryRequest` / `RecoveryRoute` (`internal/core/bgp/ribevents/recovery.go`) - the batch-wide `Source` becomes a per-key excluded-source set and `Cut` is deleted (round-3 N-6); the answer carries one outcome per key (SURVIVORS in election order, WITHDRAW), and each SURVIVORS candidate gains its received path identifier and received ADD-PATH flag (round-3 N-5) and keeps the `MessageID` `RecoveryRoute` already carries, per candidate and in the IPC form, because R-12's check reads it as the recovery write's `SourceMessageID` (round-6 N-4). No mode field (round-2 I-3). `RIBManager.recoveryRouteLocked` reads the per-key set; `recoveryCommand` (`plugins/rib/rib_recovery.go`), which today takes exactly eight positional arguments, takes the new per-key form over IPC, and `relayRecovery`'s argument builder writes it.
- `rr/rr.go` `handleStateDown` - sends its batches with `recovery-source` meta, as bgp-rs does, and first drops every family `retention.Family` keeps, as bgp-rs `handleStateDown` does (round-3 I-2, Q-5).
- The `recovery-cut` plumbing (round-3 N-6) - `routeServer.recoverRouteSel` stops sending the meta, `routeServer.handleStateDown` loses its cut parameter (the `seenMsgID` read in the state handler stays for `handleStateUp` and `ForwardFrom`), `plugins/cmd/update/recovery.go` stops parsing it, and `NLRIBatch.RecoveryCut` (`internal/component/bgp/types/types.go`, set in `update_text.go`) is deleted.
- bgp-rib's sent lifecycle (`rib_sent_lifecycle.go`) is unchanged in what it sends; the reactor's writer now owes its removals at non-ADD-PATH destinations (Data Flow 3). bgp-rib's sent projection gains one check for R-12, run only for a sent event carrying the `recovery-write` meta key, at whichever of the three store sites receives it (`storeSentEntries` from `handleSentStructured`, `storeSentEntries` from `handleSent`'s raw loop, and the inline `FamilyOps` `routeaction.Add` store in `handleSent`), with its removals dispatched off the event path (R-12, round-4 I-1, round-5 I-1).
- The receive delivery worker (`reactor/peer_run.go`) - its three `publication.fail()` sites, which already set `receivePublication.failed` (the "Adj-RIB-In invalid" fact, no new flag; round 7 N-4), call `Session.teardownAutomatic` with Cease / Out of Resources on the session the worker serves, and its stale comment is corrected (round-3 I-1). D1's reason producer moves out of the FSM leave-Established callback into `Peer.runOnce`'s down defer, which fires the leave itself when the FSM is still Established, closes `deliverChan`, waits `<-deliveryDone`, then waits on the session's leave signal when the FSM's sticky entered-Established bit is set (Data Flow 5, steps 1 to 4; round 8 B-1, I-3); it reads `notificationExchanged` and `receivePublication.failed` and reports `rpc.ReasonNotification` when the flag is set, else `rpc.ReasonAdjRIBInInvalid` when the fact is set (round-5 I-2, round-6 I-2), and the down event (`notifyPeerClosed`'s observer loop), `raiseSessionDropped`, the "session closed" log line, the leave-Established history row and `scheduleDynamicPeerCleanup` move with it; the callback keeps the closing mark, `notifyPeerClosed`'s other reactor bookkeeping, `clearEncodingContexts` and `setState(PeerStateConnecting)`, then records its reason and transition in the leave record and closes the leave signal (Data Flow 5, round 7 I-2, round 8 N-3). ## Design Insights
<!-- LIVE: write immediately when you learn something. Route each lesson to its
     governing surface under ai/rules/planning.md. A problem-class journal row
     is appropriate only when no surface governs the lesson yet; closure alone
     requires no lesson artifact. -->
- 2026-10-13: the skeleton's premise ("the fix needs a per-source path store in the relay") is superseded. bgp-rib, a hard dependency of bgp-rs, already holds every source's retained paths and already answers survivor-or-withdrawal for source departure; the store exists, the rail does not reach it for a per-prefix withdrawal.
- 2026-10-13: half the defect was closed by `b880c5a9a7` without anyone recording it: a non-owner withdrawal is already dropped. A test must pin the order B, A, A-withdraw, because A, B, A-withdraw is green at HEAD and would prove nothing.
- 2026-10-13: an untracked red probe named in a ruling was lost. A probe a spec depends on belongs in the spec's Evidence as a shape (done here), not only as a path.
- 2026-10-13 (design review round 1): "reuse the departure rail" was read as reuse of its thread and its fence, and both are wrong for a per-prefix trigger. The rail's admission is dispatched to the destination's own forward worker and awaited, so the writer cannot run it; and its fence retries on any traffic, which is tolerable for a rare session loss and a livelock for a per-prefix withdrawal. The reusable parts are the election, the transports and the admission item; the thread and the fence are replaced, for departure too.
- 2026-10-13 (round 1): the reviewer's per-key fence ("adj-out entry still holds the withdrawn owner and the survivor's path is current") has a hole when taken literally: while A's withdrawal is owed, the entry still names A, so the survivor's own later withdrawal is dropped as non-owner, and the entry check alone would then admit the dead survivor. Round 1 closed it by moving the epoch on EVERY forwarded write for the key, admitted or dropped; round 2 (I-2) showed that lets any peer postpone the replacement forever by repeating withdrawals, so the hole is now closed by noting each withdrawing owner as a mover and retrying only when the mover is the candidate about to be written (Data Flow step 7, `TestOwedKeyFenceInterleavings` cases a and e).
- 2026-10-13 (design review round 2): moving the departure off the destination-wide fence removed a guard nobody had named. The sequence fence was what stopped a departure from rewriting a destination whose route came from another source, and an old DOWN from overwriting a newer advertisement; `recoveryRouteLocked` checks the owner only on its withdrawal branch and the `adjOutRecovery` admission checks none for an announcement. When a fence is replaced, list every outcome the old fence prevented, not only the one it was built for: here the owner check at owe time and the same-source cut carry the two it carried silently (round 3 folded the cut into the owner check by storing the owner's session generation, N-6).
- 2026-10-13 (round 2): "empty answer" meant two different things (no ribOut entry, and owner moved) and the reactor would have had to guess. Every key now gets exactly one named outcome, and a missing one is an error, not a default.
- 2026-10-13 (design review round 3): "any announcement removes the owed record" read every announcement as a new owner, and one authority is not: a bgp-rib replay re-sends `ribOut[Destination]`, which still names the owner whose withdrawal the writer deferred, because a deferred withdrawal produces no sent event. A record rule keyed on "announcement or withdrawal" has to be keyed on authority instead, and every authority the writer admits needs its own row (Data Flow 7).
- 2026-10-13 (round 3): an assumption that "a failed X ends the session" had no producer behind it: the failure was logged and the session read on. Before a design treats a failure as the start of a cleanup, read the code that is supposed to start the cleanup.
- 2026-10-13 (round 3): the cleanest simplification came from data the writer already held. The departure cut existed because `adjOutSameOwner` ignores the source's session generation, but nothing stopped the table from STORING the generation while equality ignores it; one field removed an outcome, an IPC field, a meta key and an assumption.

## Key Design Decisions
<!-- "Chose X over Y because Z." The rejected alternative is the valuable half. -->
| Decision | Alternatives Considered | Rationale |
|----------|------------------------|-----------|
| Recommended: Approach B, the final writer defers an RS owner withdrawal on a non-ADD-PATH destination to the existing recovery election (round 2: as a key with an empty excluded-source set, not a mode) | A: per-source path store inside bgp-rs (the skeleton's wording). C: bgp-rs strips every withdrawal from forwarding and submits it through `recoverRouteSel`; the fast path stops forwarding withdrawals. D: bgp-rs subscribes to bgp-rib best-change events and re-announces the RIB best | B decides at the one point every rail shares and only for the owner case, so non-owner withdrawals keep costing nothing and the fast path needs no new exclusion. A duplicates bgp-rib's Adj-RIB-In and violates "no second route inventory". C puts a RIB round trip on EVERY withdrawal (owner or not) and needs a fast-path change. D races the forward-all writes (best-change and forward are unordered) and turns RS into best-path selection for announcements too |
| Survivor = the RIB's `SelectBest` over retained candidates | "Latest remaining advertisement" | The RIB records no advertisement order across sources; departure recovery already uses `SelectBest` and the guide documents it. Owner confirms in Q-1 |
| One lookup, and each key carries its excluded-source set (empty for an owner withdrawal or a lifecycle removal, the departed sources for a departure, unioned on merge) (round-2 I-3; round 3 removed the per-source cuts, N-6) | A mode field on `RecoveryRequest` (round 1's design); a separate lookup for withdrawals | One producer, one election. A mode had no defined value for a key owed by a withdrawal and then merged with a departure, and several departed sources had no per-key home; the empty set IS the withdrawal case, so the mode was redundant and R-6's misrouting risk disappears with it |
| No config knob | `rs replacement on-withdrawal enable` leaf | A correct-by-default behaviour needs no switch; a knob would leave the RFC 4271 Section 9.2 defect reachable |
| Recovery on a per-destination recovery worker fed by a non-blocking hand-off into a coalescing owed set (round-1 B1) | Run recovery on the destination forward worker after `writeMu` release (the previous design); run it on the source read goroutine; one reactor-wide recovery goroutine | The forward worker would wait on its own admission (`relayRecovery` dispatches to it and blocks on `done`); the read goroutine would wait for its own message's publication (`drainRecoverySources`); one shared goroutine lets a slow destination's admission stall every other destination's recovery |
| Per-key epoch fence, for departure and withdrawal alike (round-1 B2) | Keep the destination-wide send sequence and whole-source publication cut (livelocks under churn); fence owner withdrawals only and leave departure on the old fence (AC-12 covers session loss, and two fences is layering) | A key is retried only on a real change of that key, which is the strongest liveness a lookup outside `writeMu` can have |
| The writer's owed record is the only authority on "the owner moved": an announcement that installs a new owner removes it, and the admission writes nothing for a missing record (round-2 I-3, replacing round 1's RIB-side check); a bgp-rib replay (`adjOutExpected`) installs no new owner and never removes it (round-3 B-1) | `SourceMessageID <= Cut` across sources (round-1 I1: one process-wide counter, so ID order is not writer order); a RIB check of `ribOut[Destination]` owner beside the writer's record (round 1's answer, a second declaration of one fact); "any announcement removes the record" (round 2's rule, which let a ROUTE-REFRESH replay reinstall A's withdrawn route for good) | The writer sees every forwarded write under the table mutex; the RIB sees them only after a drain. A replay re-sends `ribOut[Destination]`, which still names the owner whose withdrawal is owed, so only a write that installs a new owner can mean "the owner moved" |
| The departure's owner test reads the owner's session generation stored in `adjOutPath`: owed only where the departed source owns the key through a session `forwardSourceCurrent` no longer accepts (round-3 N-6) | Round 2's same-source cut with the RIB's KEEP outcome; the reviewer's N-6 wording, "owe only where the entry's owner is the departed SESSION" (generation equality) | Simpler and exact: the generation is read under the table mutex every write takes, where the cut was a RIB-side reading after a drain that needed A-7. It removes the KEEP outcome, the per-source cuts in the excluded-source set and the IPC, `recovery-cut` end to end, A-7 and the Boundary row. "Not current" is used instead of generation equality for two reasons: the departure command names no generation (bgp-rs and bgp-rr learn of the down from a state event), and equality would miss a GR-retained route from an EARLIER session that the reconnected session never re-announced, which must still be decided when the later session departs. `adjOutSameOwner` keeps ignoring the generation, so a retained path stays withdrawable by the same source on its new session |

### Triple challenge

| Challenge | Answer |
|-----------|--------|
| Simplicity | Minimum change that reaches every rail: one writer outcome, one per-key excluded-source set in place of the batch source (no mode field), one election, one worker per destination that both triggers share, each draining for itself (round 2 removed the shared drain and the RIB-side owner check as machinery and a second declaration). Round 3 removed the per-source cut, the KEEP outcome, `recovery-cut` and A-7 by storing the owner's session generation the writer already holds (N-6), and the second recovery-owner atomic by reading the frozen registry (I-6). No route is stored: the owed set holds keys awaiting a decision and empties as they are decided. Simpler C was rejected because it costs every withdrawal a RIB round trip and needs a fast-path change. The worker and the per-key fence are not optional machinery: round 1 showed the simpler "run it after the write on the same worker" deadlocks and the reused fence livelocks |
| Uniformity | Departure and owner withdrawal share one lookup, one per-key fence and one fail-closed policy; the operator gets one rule for "a source stops offering a route" |
| Performance | Announcements and non-owner withdrawals keep the zero-copy write. Every forwarded write gains one check that the destination's owed set is empty, and only while it is non-empty a per-NLRI lookup in it (an announcement may remove a record, a withdrawal may note a mover) (round-2 N-9); the writer's added cost for an owed key is one map insert, one key copy and one non-blocking wake. Owner withdrawals to non-ADD-PATH clients take the cold recovery path off the writer: copies of the survivor's NLRI and attributes (`recoveryCandidate`), one drain per destination per round, one lookup per family per destination per round. This is the R-1 cost the owner accepted (Q-1) |

## Known Limitations
<!-- Deliberate scope boundaries. Anything here that is actually outstanding work

- Steady-state announcements stay forward-all: when A re-announces with worse attributes while B's route is better, the client still gets A's. That is RFC7947-x-5 territory, not claimed here (Q-3).
- The "newly installed routes" half of the 9.2-7 sentence carries no new carrier.
- bgp-rr is in scope (Q-2); its `handleStateDown` starts one goroutine per down event (`go func()` in `routeReflector.handleStateDown`), as bgp-rs does (`go rs.sendPeerDown`, tracked by `routeServer.downWG`). Decided now (round-2 N-8): this is not a permitted shape under `ai/rules/goroutine-lifecycle.md` (it is per event, not a one-time lifecycle step), it predates this spec, and this spec's goal holds without changing it, because the goroutine only sends the departure command and the command's wait is what this spec changes. So it is a defect walked into: Phase 4 writes one row in a new `plan/journal/goroutine-started-per-event.md` (no existing class names it) covering both plugins, and this spec does not change the goroutine.
