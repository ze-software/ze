## Task

Commit `850eb41b66` stopped the VRRP address owner's parent from answering ARP
and ND for the virtual address with its physical MAC. Two halves were recorded
open in `plan/journal/guard-added-to-one-half-of-a-pair.md` on 2026-09-27 (the
`ownerfilter.go` row and the vpp `verifyMatch` row). Both are re-confirmed open
in HEAD `3e2770062b` on 2026-10-13; no commit after `850eb41b66` touches
`ownerfilter.go` or the vpp `verify.go`.

Research on 2026-10-13 changed both rows' shape. Neither repair the journal
names for D1 (drop or rewrite) keeps the owner able to resolve its own LAN
neighbours, and D2 as written ("refused with a generic error") describes a path
the VRRP tables never take: plugin-registered tables skip the vpp verifier, and
the vpp translator silently ignores a match it does not know. Design review r1
(2026-10-14) added the boot and restart window of RFC 9568 Section 8.1.2, which
the 2026-10-13 design proved only in the steady state, and a false
`{not-applicable}` pair in `rfc/short/rfc9568.md`, which commit `bd9fbb5989`
has since corrected to `{gap}` (RFC9568-8.2.2-2 and -3; RFC5798-8.2.2-3
already read `{gap}`). Design review r2 (2026-10-14) settled the boot order at
the producers: iface installs the owned address before VRRP builds, which Q7
put to the owner.

Q3 (owner, yes) brought the IPv6 Neighbor Solicitation defect (D3) into scope.
Design round 5 answered it with a steering route; review r5 broke that design
(gateway routes stayed bound to the macvlan after demotion, RFC 6724 rule 5
moved the router's own source address selection onto the macvlan, and the
owner's NS-source drop starved resolution bound to the parent). The owner
answered "c" on 2026-10-14: Ze sends the parent's Neighbor Solicitations
itself. Design round 6 researched that mechanism at the producers (Design
Review Log row 6), and this body is rewritten for it on 2026-10-15 (row 7): no
steering route, no `rtproto.VRRP`, no on-link `iface.AddRoute` change and no
`ownerNSSourceTerm` remains, so none of the three r5 failure modes has a
producer left. The body also finishes the wording sweep rounds 5 and 6 left
open. Design review r6 (2026-10-15) read the kernel's neighbour code
(`net/core/neighbour.c`, `net/ipv6/ndisc.c`, `net/ipv6/route.c`) and found the
solicitor's count, its PROBE handling and its crash fallback wrong against the
producers; the body answers each finding (Design Review Log row r6), and the
owner decided Q8 (a) and kept the kernel fallback. Owner Questions carry the
decisions this design cannot make.

**Key insights:**
- D1 cannot be fixed by a firewall term alone: drop starves the owner's own resolution, rewrite sends the reply to the macvlan (R-1, R-2)
- The sender protocol address the kernel puts in a request is chosen by `arp_announce`; level 2 picks the primary address of the outgoing interface in the target's subnet
- RFC9568-8.1.2-3 is a boot and restart obligation: the parent holds the owned address before VRRP runs (iface's tier configures first, Q7), so the protection is published in `build`, the earliest point VRRP controls, and a restart is a boot because an orderly stop withdraws it
- D2's real defect is the runtime path: registry tables reach `vpp.Apply` unverified and unknown matches vanish in `applyMatch`
- D3 has no kernel knob that changes the option's MAC on the parent, and every route-based steer moves more than the Solicitations (review r5). The kernel's application-probe interface (`app_solicit`) hands the Solicitation decision to userspace without moving any route or source address, so Ze can send each Solicitation from the device whose MAC the RFC requires
- The kernel does not hand over the whole resolution, only its first `app_solicit` probes: the fifth is its own multicast from the parent (review r6). Ze must finish every resolution, by REACHABLE or FAILED, before the kernel's fifth probe, and the request's `NDA_PROBES` tells it where it stands without a count of its own

## Data Flow (MANDATORY - see `ai/rules/architecture.md`)

### Entry Point
- an interface unit config holding a VRRP group whose virtual address is also a configured address of the unit (owner)
- an interface unit config holding an IPv6 VRRP group, owner or not (D3)

### Transformation Path
1. `groups.go` extracts the group spec with `realAddresses`; `validateGroups` refuses the vpp interface backend (and, under Q4 (c) if A-2 holds, an owner group with the vpp firewall backend)
2. the iface component installs the unit's configured addresses on the parent, the owned one among them, in its own tier's configure, before the VRRP tier's configure runs (A-7; Q7 (b), owner 2026-10-14: iface does not withhold it, and that interval stays open)
3. `engine.build` creates the macvlan; for an IPv6 group it attaches the instance to the parent's solicitor (the first IPv6 group on the parent starts it and opens its neighbour-request subscription) and only then applies the IPv6 parent recipe, so no resolution request finds no reader; it applies the IPv4 parent recipe (`applyDataplaneSysctls`, with `arp_announce=2` under (a)); then it calls `syncOwnerFilter`, which hands `setOwnerFilter` the `ownedVIPs` of the spec's own VIPs, and only then opens the transport, all before the worker starts. `reconfigure` calls `syncOwnerFilter` again after each spec swap; `teardown` and `build`'s `openInstance` unwind call `clearOwnerFilter`, restore the recipe, then detach from the solicitor (the last IPv6 group stops it)
4. the worker waits for `parentReady`, promotes (an owner goes Active at once), and `doInstallVIPs` installs the address on the macvlan. The solicitor reads each instance's state when it handles a request, so promotion and demotion call nothing new
5. with the IPv6 recipe set, the kernel sends no Solicitation of its own for a parent entry during its first four probes: for probe indices 0 to 3 of an INCOMPLETE or PROBE entry, one RetransTimer apart, it multicasts an `RTM_GETNEIGH` request carrying the entry's state, flags, `NDA_PROBES` (the index) and, in PROBE, `NDA_LLADDR` (A-10, A-15). The iface netlink monitor hands it to the subscribers of that device; the solicitor acts on the index: indices 0 to 2 each get one Solicitation and (re)arm the target's deadline, index 3 gets none (step 7). It picks the path (Key Design Decisions row 5: the Active group's macvlan, virtual MAC and source, or the parent with its physical MAC and link-local when none is Active), builds the whole frame (`BuildNS`) and sends it on that device's AF_PACKET socket: to the solicited-node group for INCOMPLETE, to the cached link-layer address for PROBE
6. a host's Advertisement for a macvlan-sent Solicitation arrives on the macvlan (virtual MAC destination, private mode), where the kernel finds no entry and discards it (RFC 4861 Section 7.2.5); the solicitor's ICMPv6 socket on that macvlan reads it, validates it (Section 7.1.2), applies the Section 7.2.5 steps to the parent's entry and writes the result with `iface.SetNeighbor`; the kernel then sends the queued packets (A-11). An Advertisement for a parent-sent Solicitation reaches the parent, and the kernel completes its own entry
7. the request at index 3 (the fourth), for an entry with no Advertisement applied, makes the solicitor write `NUD_FAILED` at once, one RetransTimer after the third Solicitation, and the kernel returns address-unreachable for the queued packets (A-12). The solicitor does not depend on that request arriving: each request it handles arms a per-target deadline at the time index 3 is due plus half a RetransTimer (computed from the request's index and the parent's `retrans_time_ms`), and when the deadline fires with no Advertisement applied it writes `NUD_FAILED` itself. Either way the entry leaves INCOMPLETE or PROBE before the kernel's index 4, its own multicast from the parent, at four RetransTimers. Only a solicitor that saw no request for the target (crashed, or its subscription lost, R-8 and R-16) lets index 4 happen: that is the kernel fallback (owner, 2026-10-15)
8. the firewall registry verifies each owner's tables against the loaded backend's verifier and hands the accepted set to `Apply` (nft lowers the arp family; vpp refuses what it cannot express)
9. the kernel builds the parent's ARP requests: sender protocol address chosen by `arp_announce`, sender hardware address the parent's MAC

| R-11 | An operator, a sysctl profile or another tool overwrites `app_solicit` or `ucast_solicit` on the parent | the kernel's own Solicitations reappear on the wire with the physical MAC | `reassertDataplaneSysctls` rewrites the IPv6 recipe on every config apply, as it does the IPv4 one (AC-21); no Ze producer writes these knobs today (inventory) |
| R-12 | The subscription loses requests (a slow solicitor, the drop-oldest contract of `iface.Subscribe`) | fewer Solicitations than requests; a jump in `NDA_PROBES` between two requests for one target; the lost-request counter rises | each request carries its own index (A-15), so a lost request never shifts a count: a lost request at index 0 to 2 costs that one Solicitation, and the next request (one RetransTimer later) is handled at its true index. A lost request at index 3 is the one the kernel does not follow with another request: the next probe is the kernel's own multicast at four RetransTimers. The deadline armed by the earlier requests (Data Flow step 7) writes `NUD_FAILED` half a RetransTimer before it, so the loss of the fourth request costs nothing. A target whose every request was lost has no deadline and reaches the kernel fallback (A-13), counted by the solicitor only if a later request shows the gap |
| R-15 | `rt6_probe` sends a Solicitation from the parent that never passes through `ndisc_solicit` (Required Reading, Linux kernel source): with `CONFIG_IPV6_ROUTER_PREF` and `net.ipv6.conf.all.forwarding` 0, a route lookup through a gateway whose entry is not `NUD_VALID` makes the kernel multicast a Solicitation for that gateway from the parent with the physical MAC and the parent's link-local, at most once per `rtr_probe_interval`, whatever the recipe says | a physical-MAC Solicitation for a gateway in the AC-14 or interop capture | precondition, not fixed: a VRRP router forwards, and with `all.forwarding` 1 the lookup never carries `RT6_LOOKUP_F_REACHABLE`, so `rt6_probe` is never called. The -2/-3 claims and the dataplane doc state the precondition; AC-14 reads and records `net.ipv6.conf.all.forwarding` in the guest before the capture and refuses to run its negative leg when it is 0; Known Limitations names a router with IPv6 forwarding off |
| R-16 | The solicitor's request subscription dies: the iface monitor's neighbour socket overflows (ENOBUFS), the vendored reader closes the channel, and today `(*monitor).run` returns and stops every monitor stream (pre-existing, `plan/journal/silent-fall-through.md`, 2026-10-15) | requests stop arriving while groups run; the per-parent subscription gauge reads 0; the kernel's own physical-MAC Solicitations reappear on the wire | the kernel fallback (A-13) keeps resolution alive, under the fallback condition of the -2/-3 claims. This spec owes what the solicitor depends on: the monitor sets `ErrorCallback`, logs the error, resubscribes the closed socket and resyncs its state by a dump, and never returns from `run` for a closed channel, so link and address monitoring survive too (AC-19); a closed request subscription is seen by the solicitor, which counts it, sets its per-parent gauge to 0, logs an error naming the parent (problem, why, fix), and subscribes again. The `ze doctor` leg is Q9 (recommendation (a): no doctor rule, because doctor holds no runtime state). The journal row's Fix cell is closed by this spec's D3 phase |
| R-13 | Every IPv6 neighbour on a VRRP parent, not only the LAN hosts VRRP serves, now resolves through Ze (BGP next hops, OSPFv3 neighbours, the default router) | resolution latency or failures on the parent after an IPv6 group is configured | intended and bounded: the solicitor's only added work is one frame per request; the crash fallback (R-8) keeps resolution alive; the QEMU and interop runs resolve through it, and AC-19 keeps router discovery events correct |
| R-14 | The Active router's Solicitations now carry the macvlan link-local (non-owner) as source, so hosts learn that link-local against the virtual MAC | a host unreachable after a failover | the macvlan's link-local derives from the virtual MAC and stays stable across failovers (`vrrp-macvlan-vmac-dataplane.md`, "The macvlan exists in every state"), and a Backup's macvlan drops what it receives (`ze_vrrp_backup`, prerouting), so no host is answered by two routers; the interop scenario asserts the Backup answers no Solicitation for that link-local |

## Design Insights

- The journal row framed D1 as a firewall term; the obligation is on the sender the kernel chooses, which a sysctl governs.
- RFC9568-8.1.2-3 is scoped to restart and boot, and the owned address is on the parent before VRRP exists; a steady-state proof does not reach it.
- The owner filter belongs to the instance's life, not to Active: published wherever the owned set can change (build, reconfigure), withdrawn wherever the instance ends (teardown, build unwind), through one function.
- A route moves everything that follows it: the steering route of round 5 moved gateway routes, source address selection and resolution for traffic that had nothing to do with Solicitations (review r5). Taking over only the Solicitation, through the kernel's application-probe interface, changes the one message the RFC sentence names.

## Key Design Decisions
| Decision | Alternatives Considered | Rationale |
|----------|------------------------|-----------|
| Steer the sender with a per-parent `arp_announce=2` (Q1 (a), owner 2026-10-14) | drop term, sender-MAC rewrite, address move, deviation (Q1 option deltas) | the shape that keeps the owner's resolution, adds no firewall match, and that the address move also needs (A-6); one per-device knob at the `dsr` profile's value. The simpler design that fails: no knob at all, which leaves the request sender at the owned address |
| Publish the owner filter through one function, `syncOwnerFilter`, called in `engine.build` after the parent recipe and before `openInstance`, and in `instance.reconfigure` after every spec swap; withdraw it with `clearOwnerFilter` in `teardown` and in the `build` unwind after an `openInstance` failure; promotion and demotion no longer touch it | keep the promotion call; publish at both | closes the window between build and Active in which the parent answers for the owned address with its physical MAC. `apply` reconfigures a same-netdev instance in place, and a Master whose VIPs change gets `InstallVIPs` (`fsm.masterConfigUpdated`), which today is what republishes the set: with the promotion call gone, `reconfigure` takes that job in every state. `setOwnerFilter` returns early on an unchanged set, so the reconfigure call is free when nothing changed. The simpler design that fails: a build-only publish, which keeps the build-time set after a commit changes the VIPs, and a build with no unwind clear, which leaves a `vrrp-owner` entry silencing an address no instance holds |
| An orderly stop keeps today's behaviour: `flush-on-shutdown` (default true) removes the `vrrp-owner` tables with every other ze table, and `stopAll`, `teardown` and `revertDataplane` restore the parent knobs. A restart is therefore a boot, and its window is Q7's | survive stop and adopt at the next start (r1 proposal) | settled at the producers (A-8). Surviving stop needs a `vrrp-owner` exception to Rule 3 of `table-ownership-and-shutdown-flush.md` and knobs left set by a process that is gone, while iface leaves the address on the parent either way. One window, handled once, by Q7, is the simpler answer |
| Verify each registry owner in `ApplyAll` (Q4 (b), owner 2026-10-14) and refuse an owner group with the vpp firewall backend at commit (Q4 (c), if A-2 holds) | verify the merged set; lower on vpp | one plugin's table cannot stop another's firewall from reconciling, and the operator meets the refusal at commit rather than in a log |
| D3 and RFC9568-8.2.2-2/-3/-5 (owner's "c", 2026-10-14; researched in design round 6): while any IPv6 VRRP instance lives on a parent, Ze is that parent's IPv6 solicitor. The parent's neighbour knobs `app_solicit=4` and `ucast_solicit=0` make the kernel ask userspace for the first four probes of each resolution instead of sending them (A-10); `mcast_solicit` stays at the host value and `mcast_resolicit` is set to 3, so the kernel's own multicast after those four is the crash fallback for new and established entries alike (A-13, owner 2026-10-15). The iface netlink monitor hands each request to the parent's subscribers; Ze sends one Solicitation per request, built whole and sent on an AF_PACKET socket: when a group on the parent is Active, from that group's macvlan (the group whose virtual prefixes hold the target, else the lowest Active VRID), Ethernet source and option the virtual MAC, IPv6 source the owned address in the target's prefix for an owner and the macvlan link-local (`v6SourceLocked`) otherwise; when none is Active, from the parent with its physical MAC and the parent's link-local, never an owned address. INCOMPLETE entries are solicited to the solicited-node group, PROBE entries unicast to the cached address. The Advertisement for a macvlan-sent Solicitation arrives on the macvlan, where the kernel discards it, so Ze reads it there, validates it and writes the parent entry with `iface.SetNeighbor`; a parent-sent Solicitation is answered to the parent and the kernel completes its own entry. Ze reads its place in each resolution from the request's `NDA_PROBES` and ends it, after three Solicitations, by writing `NUD_FAILED` at the index-3 request or at its own deadline, whichever comes first, always before the kernel's own multicast at four RetransTimers (Data Flow step 7), so resolution ends after three Solicitations as RFC 4861 Section 7.2.2 requires | the round-5 steering route (withdrawn: review r5 found gateway routes bound to the macvlan after demotion, RFC 6724 rule 5 moving the router's own source selection onto the macvlan, and the owner NS-source drop starving parent-bound resolution); an IPv6 knob that changes the option's MAC (none exists: `arp_announce` is IPv4 only); an nft rewrite of the option (the Advertisement then reaches the macvlan and the parent's entry never completes, RFC 4861 Section 7.2.5); the drop term alone (starves, R-1); a Ze-built Solicitation alongside the kernel's (the kernel's still leaves with the physical MAC); a policy rule `from <virtual address>` (meets -5, leaves every other Solicitation, so the letter of -2/-3 stays unmet); the Q1 (c) address move (iface withhold) | the only shape that changes the Solicitation alone: no route, no source address selection and no forwarding path moves, so none of the three r5 failure modes has a producer. A Backup never sends the virtual MAC (R-9). The kernel keeps every other part of neighbour discovery: entry state, reachability timers, queuing and the Advertisement on the parent. Expected verdicts: RFC9568-8.2.2-2 and -3 met, tagged on AC-14 with a discrimination record; -5 stays `{gap}` for the pre-build window, in which iface installs the owned address and runs its Duplicate Address Detection on the parent. The simpler design that fails: the drop term alone |
| Q2 (ii) record (owner, 2026-10-14): the owner-approved deviation lives in the RFC9568-8.1.2-3 row's single `{gap: ...}` reason, beside the pre-build window, and `ze doctor` warns per owned address with `doctor-vrrp-owner-address-primary` | a second annotation on the line; `{feature-declined}` | one checklist line carries one disposition (`docs/contributing/rfc-conformance-gates.md`, "The feature-declined annotation"), the register has no deviation kind, and the obligation is not conditional on an optional feature; the row is never counted met and keeps its section and reason (`ai/rules/rfc-compliance.md`) |
| Count from the kernel, finish before it (review r6, 2026-10-15): the solicitor keeps no per-target counter. Each request's `NDA_PROBES` is the probe index; indices 0 to 2 send, index 3 writes `NUD_FAILED`; every handled request arms a per-target deadline at the time index 3 is due plus half a RetransTimer, read from the parent's `retrans_time_ms` at that moment, which writes `NUD_FAILED` if no Advertisement was applied | a per-target counter reset by state events and by a two-RetransTimer gap (the round-7 design, R-12's old heuristic); writing FAILED only at the fourth request; `mcast_solicit=0`, which removes the kernel's fifth probe | the kernel's index survives every lost request, so a counter of Ze's own can only disagree with it. The fourth request is the one whose loss the kernel does not repair, because the next probe is its own multicast from the parent (A-10), so the deadline is the only thing that makes the -2/-3 met claim independent of that request arriving. `mcast_solicit=0` would make the deadline unnecessary and remove the crash fallback with it: rejected by the owner (2026-10-15), who keeps the fallback as design (c)'s answer to a crash. The simpler design that fails: FAILED at the fourth request alone, which lets the kernel's physical-MAC Solicitation out whenever that request is lost |
| PROBE entries keep the crash fallback: the recipe sets `mcast_resolicit=3` (RFC 4861 MAX_MULTICAST_SOLICIT) beside `app_solicit` and `ucast_solicit`, saved and restored with them (review r6, decided in this round under the owner's delegation) | leave `mcast_resolicit` at the host value (0 by default) | with 0, `neigh_max_probes` for PROBE is `0 + 4 + 0`, so a PROBE entry gets four requests, no kernel Solicitation, then FAILED. That is harmless while Ze runs, because Ze ends the entry at index 3 anyway, but after a crash every established neighbour in use (BGP next hops, the default router) fails at each reachability cycle: dropped packets, address unreachable, and a fresh four-RetransTimer resolution, which is the outage the owner's fallback exists to prevent. With 3, the PROBE entry stays usable on its cached address and the kernel re-confirms it by multicast after four RetransTimers. While Ze runs the knob changes nothing on the wire, because the entry has left PROBE before index 4. The cost is one more per-device knob in the save, restore and residue rule |
| RFC 4861 Section 7.2.2 source (Q8 (a), owner 2026-10-15): a recorded deviation, not counted anywhere (RFC 4861 is not enrolled). Parent-sent Solicitations, and an Active non-owner's Solicitations, carry a link-local source whatever address the prompting packet came from; an Active owner's carry the owned address in the target's prefix | (b) the route lookup's preferred source per request; an Active non-owner sourcing from its virtual address in the target's prefix (meets the SHOULD when the virtual address prompted it, and misses it for every other prompt, so a deviation remains); applying the recipe only while a group is Active, so the kernel sources parent-sent Solicitations itself (invalid for an owner in Initialize or Backup: the kernel would source them from the owned address on the parent with the physical MAC, which is what RFC9568-8.2.2-5 forbids) | a resolution request carries no packet, so Ze cannot know the prompting source; the paragraph's second sentence, "Otherwise, any one of the addresses assigned to the interface should be used.", covers the unknown case, and the kernel itself sources from the link-local whenever it holds no prompting packet (`ndisc_solicit` passes NULL, `ndisc_send_ns` picks `ipv6_get_lladdr`). A miss costs the host one resolution of its own, never a wrong binding |
| Build Solicitations as whole Ethernet frames on an AF_PACKET socket, the checksum computed by Ze | a raw ICMPv6 socket like `na_linux.go` | a raw ICMPv6 socket sends through the IP stack, which resolves a unicast destination on the sending device; a PROBE Solicitation from the macvlan would make the kernel resolve the peer on the macvlan, which has no entry and whose own Solicitation Ze does not control. The frame layout is fixed by RFC 4861 Section 4.3, RFC 4291 Section 2.7.1 and RFC 2464 Section 7, and the golden test pins it (AC-20) |

## Known Limitations
- Owners with no non-virtual address in the subnet, or whose owned address is primary: Q2 (ii), the IPv4 deviation recorded in the RFC9568-8.1.2-3 row and reported by `ze doctor`.
- The interval from the iface address install to `engine.build`, at every boot and restart (A-7): Q7 (b). It stays open and is stated in the `{gap}` reasons of RFC9568-8.1.2-3 and RFC9568-8.2.2-5 and in the dataplane doc; for IPv6 it includes the Duplicate Address Detection iface runs on the parent for the owned address.
- RFC 4861 Section 7.2.2 source deviation (Q8 (a), owner 2026-10-15): while no IPv6 group on a parent is Active, Ze's Solicitations from the parent use the parent's link-local as source, and an Active non-owner's use its macvlan link-local, whatever address the prompting packet came from. The SHOULD, "If the source address of the packet prompting the solicitation is the same as one of the addresses assigned to the outgoing interface, that address SHOULD be placed in the IP Source Address of the outgoing solicitation.", is unmet when the prompting packet came from one of the parent's global addresses or the owned address (parent-sent) or from a virtual address (Active non-owner); the next sentence, "Otherwise, any one of the addresses assigned to the interface should be used.", is what Ze does, as the kernel does whenever it holds no prompting packet.
- A crash, or a lost request subscription before Ze resubscribes, hands resolution to the kernel fallback (owner, 2026-10-15): a new neighbour resolves through the kernel's multicast four RetransTimers late, an established one is re-confirmed by multicast with no loss, and every such kernel Solicitation leaves the parent with the physical MAC, sourced from the queued packet's address (the owned address among them) or the parent's link-local. That window is outside the RFC9568-8.2.2-2/-3 met claim and inside the -5 gap. The next start restores residue from `net/ipv6/neigh/default` with a warning (R-8, R-16).
- A router with `net.ipv6.conf.all.forwarding` 0 on a kernel built with `CONFIG_IPV6_ROUTER_PREF` sends router reachability probes from the parent with the physical MAC, outside the recipe (`rt6_probe`, R-15); the -2/-3 claims hold only with IPv6 forwarding on.
- `ze doctor` does not report a lost request subscription: it holds no runtime state (Q9); the counter, the gauge and the log line do.
- Owner heads-up, not a blocker: `net/ipv4/neigh/<parent>/app_solicit` would let the same mechanism send the parent's ARP requests from the macvlan, covering the Q2 configuration; Q1 (a) and Q2 (ii) stand as his answers unless he reopens them.

## Ledger and operator text (design rounds 5 to 7)

RFC9568-8.1.2-3, one disposition: `{gap: ze meets the sentence from instance build on: internal/plugins/vrrp/engine.go::build applies the parent recipe with arp_announce=2 (internal/plugins/vrrp/dataplane_linux.go::parentSysctls) and publishes the owner filter (internal/plugins/vrrp/ownerfilter.go::syncOwnerFilter) before the transport opens. Two parts are unmet and not counted. At every boot and restart the interface component installs the owned address on the parent before VRRP builds the instance, and until then the parent answers and sends ARP for it with its physical MAC. Owner-approved deviation (2026-10-14, RFC 9568 Section 8.1.2): where the owned address is the first of its subnet on the unit, no other sender address exists, so the parent's own ARP requests carry it with the physical MAC; ze doctor reports doctor-vrrp-owner-address-primary}`

RFC9568-8.2.2-5: `{gap: ze meets the sentence from instance build on: the owner filter (internal/plugins/vrrp/ownerfilter.go::syncOwnerFilter) drops the parent's Neighbor Advertisements for the owned address, and the parent's Neighbor Solicitations are ze's own (internal/plugins/vrrp/solicitor.go), sent from the virtual-MAC macvlan while the group is Active and never sourced from the owned address when ze sends them from the parent. Three parts are unmet and not counted. At every boot and restart the interface component installs the owned address on the parent, and runs Duplicate Address Detection for it there, before VRRP builds the instance; until then the parent's ND for it carries the physical MAC. After a crash, or while ze's neighbour-request subscription is lost, the kernel sends its own Solicitations from the parent after four unanswered requests, with the physical MAC and with the prompting packet's source, which can be the owned address. With IPv6 forwarding off, the kernel's router reachability probes (rt6_probe) leave the parent with the physical MAC}`

RFC9568-8.2.2-2 and -3: no annotation once AC-14 is green with its discrimination record; the tag claims name `internal/plugins/vrrp/solicitor.go` as the producer and state the conditions of the met claim in their own words: ze's solicitor is running and subscribed, so every resolution it saw ends before the kernel's own fifth probe (Data Flow step 7), and IPv6 forwarding is on (R-15). Outside those conditions the kernel fallback (owner, 2026-10-15) sends physical-MAC Solicitations, which the claim does not cover; the dataplane doc and `docs/guide/vrrp.md` state the same conditions beside the claim. RFC5798-8.2.2-2 and -3 lose their `{gap}` and keep `{superseded}`.

`doctor-vrrp-owner-address-primary`, severity warning, title "VRRP owner address is the first address of its subnet". Message, per owned IPv4 address (`ai/rules/user-facing-errors.md`: problem, why, fix on its own line):

    interface <unit> vrrp group <vrid>: <owned> is the first address of <prefix> on this unit, so this router's own ARP requests on that subnet pair <owned> with the interface's own MAC instead of the virtual MAC (RFC 9568 Section 8.1.2).
    A LAN host that learns that pairing keeps sending to this router after a failover, until its ARP entry expires.
    Fix: configure a second address in <prefix> on this unit, listed before <owned>.

The fix line assumes iface installs a unit's addresses in config order, so the first listed is the kernel's primary; `applyConfig` (`internal/component/iface/config_apply.go`) is read at implementation to confirm, and the line changes if it does not hold. Pages that state the deviation: `docs/guide/vrrp.md` (doctor table, owner section), `docs/architecture/vrrp/vrrp-first-hop-redundancy.md` (owner section), `docs/architecture/vrrp/vrrp-macvlan-vmac-dataplane.md` (owner filter section).

`doctor-vrrp-parent-neigh-residue`, severity warning, title "IPv6 neighbour discovery on a VRRP parent waits for ze". Message, per parent:

    interface <parent>: net.ipv6.neigh.<parent>.app_solicit is 4 and ucast_solicit is 0, the values ze sets while an IPv6 VRRP group runs on it, but no IPv6 VRRP group is configured on it.
    The kernel asks an application that is not running to resolve each IPv6 neighbour before it solicits it itself, so every new neighbour on this interface resolves four retransmit intervals late (about four seconds by default), and every established one is re-confirmed that late.
    Fix: sysctl -w net.ipv6.neigh.<parent>.app_solicit=<a> net.ipv6.neigh.<parent>.ucast_solicit=<u> net.ipv6.neigh.<parent>.mcast_resolicit=<m>

The fix line's `<a>`, `<u>` and `<m>` are the values doctor reads from `net.ipv6.neigh.default.app_solicit`, `ucast_solicit` and `mcast_resolicit` when it reports, never constants (the host default is the operator's, and the kernel's own defaults are 0, 3 and 0).
