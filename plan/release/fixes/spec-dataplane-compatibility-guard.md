| Field | Value |
|-------|-------|

| Scope | config |
| Priority | P1 |
| Release reason | Ze accepts configurations whose features program a data plane other than the one the interfaces run on. The config commits and the feature then does nothing, or fails when it is applied. Accepted but ineffective configuration is incorrect shipped behavior. |

## Task

Thomas asked (voice-transcribed, read for meaning) for a page that says which
features work on VPP and on the kernel, then for the information to live in the
code "to prevent incompatible configuration combinations", and then: "yes please
make a spec for that work".

Ze has four independent data-plane selections: `interface backend`,
`firewall backend`, `traffic control backend` and the `fib` blocks. Each is
checked against the features under it. Nothing compares them with each other,
and features with no backend leaf (IPsec, L2TP, flow export sampling, policy
routing, GTSM) are never compared with `interface backend`. Ten combinations
are accepted today and then misbehave (table in Current Behavior, rows A to H,
J and K).

The goal: each feature that writes forwarding state declares the data plane it
programs, in its own package. The config component derives one verdict from
those declarations and the selected data plane. A mismatch is refused at
commit, at daemon start, at reload and by `ze config validate`, and reported by
`ze doctor`, with the same words and the line that fixes it: one verdict, the
same at every door (C-5). The hand-written page
`docs/guide/dataplane-features.md` is replaced by a page generated from the same
declarations.

Thomas decided the first product choice, C-1, on 2026-11-23 (voice-transcribed):
"should Ze refuse a kernel-only feature when the interfaces run on VPP: the
commit should fail". Reading taken: refuse outright, with no host-side
exception.

He answered the four other choices on 2026-11-23 (voice-transcribed): "C-2 b /
C-3 a / C-4 a / C-5 we should not refuse to start the deamon if the issue is
that something will not be configured but we should refuse to commit any more
changed until it is fixed". He then replaced his answer to C-5: "You know what.
Refuse invalid configuration at boot", and gave the reason: "simpler".
He then answered the two questions the design judge's refusal raised and the
two pending confirmations, on 2026-11-23 (voice-transcribed): "q1 b - so we can
consider mix setup when we add vrf / q2 I replied elsewhere another agent
should have written it down, it should start the plugin to get the yang / p1 b
atm / p2 delete". "Choices for Thomas" records each answer with the reading
taken (C-1 to C-5, Q-1, Q-2, P-1, P-2). AC-3, AC-5, AC-14 to AC-17 state the
outcome of each, and the three decision rows of
`docs/architecture/core-design.md` carry them.

**Key insights:**
- The per-node fact already has one declaration (`ze:backend`); the per-feature and per-backend data plane has none.
- `registry.ConfigNeed` and `registry.DataPlaneWriter` are the two shapes to copy: a declaration on the registration, evaluated by the config component over the parsed tree, with one judgment shared by boot, reload and doctor.
- `config.RegisterTreeValidator` is the existing whole-tree boundary, and the PPPoE backend gate already uses it to compare a feature with `interface backend`, reading the schema default.
- `kernelcap.Capability` already pairs a requirement with an `InUse(tree)` predicate declared by the owning package.

## Data Flow (MANDATORY - see `ai/rules/architecture.md`)

### Entry Point
- A candidate configuration: at daemon start, at reload or commit, and in `ze config validate`. Format: the parsed config tree.

### Transformation Path
1. Each backend registers with its component and names the data plane it programs. Each component registration names its selector leaf and the config roots the selection governs.
2. Each selector-less feature registration names the data planes its forwarding state lives in and how it is in use. In use is one of two declared forms: a predicate over the candidate tree (the sampling container, a nonzero `ttl` leaf), or, for a plugin that owns no config root, "the candidate selects this plugin". L2TP and GTSM, which have no registration, declare through a registry function they call from `init()`.
3. The interface component registration marks its selector as the one that selects the data plane.
4. In `LoadConfig` and in `verifyTree` (`plugin_verify.go`, the caller of `VerifyPluginConfigMapTransition` that holds the candidate `*Tree`, beside `refuseUnresolvableDependencies`) the config component reads the declarations from the registry, reads each selector leaf (or its schema default), and resolves the selected data plane. It reads the candidate's plugin selection from one function: `ExtractPluginsFromTree`, merged through `MergeCliPlugins` with the command-line plugins of the process and with the command-line plugins its caller holds. The process's are recorded once, by the `ze` dispatcher, where `--plugin` is parsed and before any verb runs (`RecordCommandLinePlugins`, beside `RecordStartedPlugins` in the config component's process record). The caller's are `loadConfig`'s own `cliPlugins` parameter; `verifyTree` holds none and hands none. The selection function is the one reader that decides the verdict's selection; the other readers of the record only display it (the SSH upload receipt) or forward it (`startEphemeralDaemon`), and decide nothing (Q-2). The numbered consequences:
   1. In a daemon the record holds the slice `cmdStart` hands `hub.Run`, which the start and `diskConfigLoaders` hand `LoadConfig`, so in `loadConfig` the parameter and the record are one list and the union is that list. Every commit door of that daemon reaches `verifyTree` (SSH editor, web editor commit and web upload, REST and gRPC sessions, gNMI Set, SSH upload), and the managed push handler reaches `loadConfig` with `nil`, so each judges with the plugin set the daemon runs and none is rewired (A-15). A commit is not accepted that the reload after it refuses.
   2. In `ze config validate`, `ze doctor` and the offline editing sessions the record holds the `--plugin` arguments that command was given, and nothing when it was given none.
   3. In a process the `ze` dispatcher never ran, the `le chaos run` in-process simulation (`internal/chaos/inprocess/runner.go`), the record is empty and the parameter `["ze.bgp-rs"]` is the only holder, and the verdict in `loadConfig` judges with it, because it reads the parameter (R-9).
   4. `ze config edit` with no daemon running starts an ephemeral daemon (`startEphemeralDaemon`), a second process. It passes the recorded list as global `--plugin` arguments before `start`, one `--plugin <name>` pair per entry, in the form the dispatcher parses: `<exe> --plugin <name> ... start [--web <port>] [--insecure-web] <path>`. That daemon's own dispatcher then records the same list, and its SSH editor, the door the session commits through, judges with it.
   5. `verifyTree` merges once, and `refuseUnresolvableDependencies` reads the merged selection too, so a command-line plugin whose dependency this build lacks is refused at validate as `finalizeConfigLoad` refuses it at start. A command-line name `MergeCliPlugins` cannot resolve is refused the same way at both.
   6. The function that judges takes the tree and the selection as arguments and reads no record, so it is tested with no process state; of the verdict's code, only the selection function reads the record.
5. It walks the whole config tree once with the existing walker, judging each annotated node against the selector that governs it. A node outside every declared root (the container networks) is judged against the data-plane selector.
6. It judges each in-use backend and feature: a declared plane other than the selected data plane is a mismatch. One mark exists, the host-side mark: "this declaration acts on the Linux host itself, beside the selected data plane". The mark says nothing about what the declaration does on the host. Two registrations set it, each for its own use as the decision row names it: `fib-kernel` (C-3 (a)), which programs the Linux route table for the router's own traffic, and `sysctl` (Q-1 (b)), which sets the Linux kernel's own tunables. The verdict reports no plane mismatch for a declaration that carries it, without naming its owner. One rule then reads the mark, `ProgramsFIB` and `DataPlane` over the in-use FIB plugins: a marked FIB writer of another plane with no FIB writer of the selected plane beside it is a mismatch, whose fix names the config root of the registration that declares `ProgramsFIB` and the selected plane (P-1 (b)). No declaration says how a door treats it: the verdict is the same at start, reload, commit and validate (C-5).
7. Each mismatch is one `opererr` refusal; all of them are joined. The same function feeds the doctor check.
8. Separately, `ValidateCustomSections` runs the original-tree validators before these steps: in `LoadConfig` at boot and reload, in `ze config validate`, and at editor commit. `validateOriginalTree` hands each validator the whole candidate tree, whichever root changed, and stops at the first validator that refuses. Two validators are added:
   - the firewall's `firewall-producer-tables` resolves the candidate's firewall backend (its leaf, or the schema default), runs every config table builder copp and firewall-irr registered over the tree, and runs that backend's registered verifier over the tables, joining every refusal (AC-8);
   - the VPP interface backend's `iface-vpp-wireguard-plugin` reads three things in the candidate tree: `interface backend`, the `interface wireguard` list and `vpp plugins wireguard`. With the backend `vpp`, one WireGuard interface or more, and the leaf not `true`, it refuses, naming every such interface in one refusal (AC-2). Because it reads the whole tree, a commit or reload that only changes the `vpp` root is judged like one that adds the interface.
9. One verdict, every door (C-5). Daemon start (`runYANGConfig`, and `RecoverConfig` for a rollback it loads), every reload (`diskConfigLoaders`) and a pushed candidate (`judgeConfigBeforeBoot`) call `LoadConfig`, which refuses. `judgeConfigBeforeBoot` hands it the `plugins` it holds, where today it hands `nil`, so the pushed candidate is parsed with the module text of the command-line plugins and resolved with them, as the boot after it is. The SSH editor, the web editor and web upload, the REST and gRPC sessions, gNMI Set, the SSH upload, the offline editing sessions and `ze config validate` reach `verifyTree` and `ValidateCustomSections`, which refuse with the same words; the SSH upload alone answers its fixed receipt in place of the words, as today, because a parser error can carry a secret, and its fix line names the validate command that prints them. Both `LoadConfig` and `verifyTree` take the command-line half of the selection from the one selection function (step 4), which reads the record and, in `loadConfig`, the parameter the start and reload already hand it, so no door can judge with another plugin set than its process runs. The ephemeral daemon of `ze config edit` is a door of its own process, started with the same `--plugin` arguments (step 4, consequence 4). Nothing tells the loader which door it serves, and no door keeps, reports or partly applies a configuration another door refuses.

## Design presentation

### What changes

Each backend and each feature that writes forwarding state says, in its own
package, which data plane it programs. When a configuration puts a feature on a
data plane other than the one `interface backend` selects, Ze refuses it at
commit, at start and in `ze config validate`, and `ze doctor` reports it, with
the line that fixes it. The feature-by-data-plane page is generated from the
same declarations.

## Design Insights

- The firewall YANG annotations are per leaf and the VPP verifier is per value, so the two can disagree by construction (I). The annotation is the gate for operator config; the verifier is the gate for tables other plugins build.
- A table producer's tables reach whichever firewall backend is loaded, and with no `firewall` block that is the OS default: a producer is a firewall user even when the operator wrote no firewall.
- Only copp and the IRR interface bindings build tables whose shape the configuration alone fixes and that can reach `firewall backend vpp` unrefused: the IRR set contents arrive at run time, but the verifier refuses a named set by its shape. Policy routing and GTSM build from config too, but every combination of either with `firewall backend vpp` is already refused by AC-4 or AC-5. A term naming an IRR AS-SET or a domain group is a `MatchInSet` in the firewall's own table, refused at commit today. The others build tables from run-time events and can only be judged when applied.

## Known Limitations
- A VPP router cannot filter its own punted control-plane traffic with kernel nftables (C-1). That is the decided behavior.
- Tables a plugin produces at run time (ddos-local, flowspec-firewall, anomaly shape) are judged when applied (AC-8 survivors).
- The firewall and traffic limit tables stay hand-written (AC-12 survivors).
- `sysctl` stays accepted under `interface backend vpp` (Q-1 (b)), and its keys are applied to the Linux kernel exactly as on any data plane, so a setting about kernel behaviour works unchanged on a VPP box. Only a key about packet forwarding, for example `rp_filter` or `forwarding`, acts on the packets that reach Linux rather than the packets VPP forwards: an `rp_filter` key checks only the packets VPP punts to Linux through the LCP TAP, never the transit traffic VPP forwards (A-1; `plan/journal/silent-fall-through.md`, the `rpf-check` row). The generated page and `docs/guide/vpp.md` say so. That is the decided behavior, kept for mixed setups once VRFs are added.
- A `fib kernel` block with no `fib vpp` block is refused under `interface backend vpp` for now (P-1 (b), "atm"); Thomas may revisit it.
- A box whose stored configuration holds any mismatch this spec refuses, IPsec under `interface backend vpp` included, does not boot after the upgrade that carries this work (C-5 (a), R-8): `ze` exits at start with the refusal and its fix. Before upgrading, the operator runs the new release's `ze config validate` over the stored configuration, as the configuration guide's "Check before you upgrade" shows (`ze config validate /etc/ze/ze.conf`): it gives the refusal start would give, with the same words, and the configuration is fixed before the new daemon starts. The old release's `ze config validate` does not hold the verdict and accepts the file. After the upgrade, `ze doctor` reports the row on the stored file with no daemon running.
- When a running Ze answers `ze config validate` (a file that declares an external plugin is sent to it first, `ai/doors/config-yang.md`), that daemon judges with the `--plugin` list it was started with, not the list on the caller's command line. The answer is then the verdict of the daemon the file would load in. A caller that names other plugins than the running daemon gets no verdict for its own list; the asking route belongs to `spec-explicit-plugin-and-attach-config` (Depends).
- `ze --plugin <name> config edit` with a daemon already running opens a session on that daemon, which judges with the `--plugin` list it was started with, not the editor's command line, as the running Ze that answers `ze config validate` does. Only the ephemeral daemon `ze config edit` starts itself carries the editor's list (AC-18).
- The original-tree validators stop at the first one that refuses, so an operator whose configuration fails both `firewall-producer-tables` and `iface-vpp-wireguard-plugin` sees one, fixes it, and then sees the other. The data-plane verdict joins all of its own refusals.
