## Task

Commit `850eb41b66` stopped the VRRP address owner's parent from answering ARP
and ND for the virtual address with its physical MAC. Two halves were recorded
open in `plan/journal/guard-added-to-one-half-of-a-pair.md` on 2026-09-27 (the
`ownerfilter.go` row and the vpp `verifyMatch` row). Both are re-confirmed open
in HEAD `3e2770062b` on 2026-10-13; no commit after `850eb41b66` touches
`ownerfilter.go` or the vpp `verify.go`.

Research on 2026-10-13 changed both rows' shape. Neither repair the journal
names for D1 (drop or rewrite) keeps the owner able to resolve its own LAN
neighbours, and D2 as written ("refused with a generic error") describes a path
the VRRP tables never take: plugin-registered tables skip the vpp verifier, and
the vpp translator silently ignores a match it does not know. Design review r1
(2026-10-14) added the boot and restart window of RFC 9568 Section 8.1.2, which
the 2026-10-13 design proved only in the steady state, and a false
`{not-applicable}` pair in `rfc/short/rfc9568.md`, which commit `bd9fbb5989`
has since corrected to `{gap}` (RFC9568-8.2.2-2 and -3; RFC5798-8.2.2-3
already read `{gap}`). Design review r2 (2026-10-14) settled the boot order at
the producers: iface installs the owned address before VRRP builds, which Q7
put to the owner.

Q3 (owner, yes) brought the IPv6 Neighbor Solicitation defect (D3) into scope.
Design round 5 answered it with a steering route; review r5 broke that design
(gateway routes stayed bound to the macvlan after demotion, RFC 6724 rule 5
moved the router's own source address selection onto the macvlan, and the
owner's NS-source drop starved resolution bound to the parent). The owner
answered "c" on 2026-10-14: Ze sends the parent's Neighbor Solicitations
itself. Design round 6 researched that mechanism at the producers (Design
Review Log row 6), and this body is rewritten for it on 2026-10-15 (row 7): no
steering route, no `rtproto.VRRP`, no on-link `iface.AddRoute` change and no
`ownerNSSourceTerm` remains, so none of the three r5 failure modes has a
producer left. The body also finishes the wording sweep rounds 5 and 6 left
open. Design review r6 (2026-10-15) read the kernel's neighbour code
(`net/core/neighbour.c`, `net/ipv6/ndisc.c`, `net/ipv6/route.c`) and found the
solicitor's count, its PROBE handling and its crash fallback wrong against the
producers; the body answers each finding (Design Review Log row r6). Design
review r7 (2026-10-15) found the solicitor's FAILED write able to kill a valid
entry, the request contents unreachable through the vendored subscription, the
end of each resolution only a latency bound, and the RFC 4861 Section 7.2.5
router-to-host step missing; the body answers each (Design Review Log row r7).
Design review r8 (2026-10-15) found the end before the kernel's multicast still
a race, a FAILED write possible after fewer than three Solicitations, the raw
exception-route delete unreliable, and ENOBUFS treated as fatal; the body
answers each (Design Review Log row r8). Design review r9 (2026-10-15) found
the exception GC's reach release-dependent, a record expiry that could reset
Ze's count mid-resolution, and the AC timing origin unstated; the body answers
each (Design Review Log row r9). Design review r10 (2026-10-15) found the
release set wrong by sublevel, AC-28's guest leg passable with no flush, and
the AC-22 ping exiting before the last FAILED; the body answers each (Design

Big generator unnamed, its red 1 passable by a stale GC timer and its window
anchored to an unobservable write, and AC-22's ping wait fixed where it must
follow `mcast_solicit`; the body answers each (Design Review Log row r11).
Q8 (a), the retention of the kernel
fallback against `mcast_solicit=0`, and every r6 to r11 disposition are

2026-10-14. The owner answered Q9 (b) on 2026-10-15: a lost neighbour-request

| Q8 | RFC 4861 Section 7.2.2: "If the source address of the packet prompting the solicitation is the same as one of the addresses assigned to the outgoing interface, that address SHOULD be placed in the IP Source Address of the outgoing solicitation.  Otherwise, any one of the addresses assigned to the interface should be used." A kernel resolution request (RTM_GETNEIGH) carries no packet, so Ze never knows the prompting source. Bound, corrected by review r6: Ze's source differs from the one the SHOULD asks for in two cases. (1) Parent-sent: no IPv6 group on the parent is Active, Ze sends from the parent with the parent's link-local, and a prompting packet sourced from one of the parent's global addresses, or from the owned address, gets that link-local instead. **Key insights:**
- D1 cannot be fixed by a firewall term alone: drop starves the owner's own resolution, rewrite sends the reply to the macvlan (R-1, R-2)
- The sender protocol address the kernel puts in a request is chosen by `arp_announce`; level 2 picks the primary address of the outgoing interface in the target's subnet
- RFC9568-8.1.2-3 is a boot and restart obligation: the parent holds the owned address before VRRP runs (iface's tier configures first, Q7), so the protection is published in `build`, the earliest point VRRP controls, and a restart is a boot because an orderly stop withdraws it
- D2's real defect is the runtime path: registry tables reach `vpp.Apply` unverified and unknown matches vanish in `applyMatch`
- D3 has no kernel knob that changes the option's MAC on the parent, and every route-based steer moves more than the Solicitations (review r5). The kernel's application-probe interface (`app_solicit`) hands the Solicitation decision to userspace without moving any route or source address, so Ze can send each Solicitation from the device whose MAC the RFC requires
- The kernel does not hand over the whole resolution, only its first `app_solicit` probes: the next is its own multicast from the parent (review r6). With `app_solicit=8` Ze sends three Solicitations only when all three and its deadline fit before the kernel's ninth probe, and ends the resolution, by REACHABLE or a guarded FAILED, at least one RetransTimer before that probe under the conditions Data Flow step 7 names (reviews r7 and r8); the request's `NDA_PROBES` tells it the kernel's position, and its own count tells it how many Solicitations it sent. It never writes FAILED for a resolution it solicited fewer than three times (RFC 4861 Section 7.2.2)

## Data Flow (MANDATORY - see `ai/rules/architecture.md`)

### Entry Point
- an interface unit config holding a VRRP group whose virtual address is also a configured address of the unit (owner)
- an interface unit config holding an IPv6 VRRP group, owner or not (D3)

### Transformation Path
1. `groups.go` extracts the group spec with `realAddresses`; `validateGroups` refuses the vpp interface backend (and, under Q4 (c) if A-2 holds, an owner group with the vpp firewall backend)
2. the iface component installs the unit's configured addresses on the parent, the owned one among them, in its own tier's configure, before the VRRP tier's configure runs (A-7; Q7 (b), owner 2026-10-14: iface does not withhold it, and that interval stays open)
3. `engine.build` creates the macvlan; for an IPv6 group it attaches the instance to the parent's solicitor (the first IPv6 group on the parent starts it and opens its neighbour-request subscription) and only then applies the IPv6 parent recipe, so no resolution request finds no reader; it applies the IPv4 parent recipe (`applyDataplaneSysctls`, with `arp_announce=2` under (a)); then it calls `syncOwnerFilter`, which hands `setOwnerFilter` the `ownedVIPs` of the spec's own VIPs, and only then opens the transport, all before the worker starts. `reconfigure` calls `syncOwnerFilter` again after each spec swap; `teardown` and `build`'s `openInstance` unwind call `clearOwnerFilter`, restore the recipe, then detach from the solicitor (the last IPv6 group stops it)
4. the worker waits for `parentReady`, promotes (an owner goes Active at once), and `doInstallVIPs` installs the address on the macvlan. The solicitor reads each instance's state when it handles a request, so promotion and demotion call nothing new
5. with the IPv6 recipe set, the kernel sends no Solicitation of its own for a parent entry during its first eight probes: for probe indices 0 to 7 of an INCOMPLETE or PROBE entry, one RetransTimer apart, it multicasts an `RTM_GETNEIGH` request carrying the entry's state, flags, `NDA_PROBES` (the index) and, in PROBE, `NDA_LLADDR` (A-10, A-15). The solicitor reads requests and the parent's `RTM_NEWNEIGH` and `RTM_DELNEIGH` state events through its per-device subscription on the namespace's request socket, an `RTNLGRP_NEIGH` socket the netlink backend opens once per network namespace, decodes from the raw `ndmsg` and attributes (`NDA_DST`, `NDA_LLADDR`, `NDA_PROBES`, `ndm_state`, `ndm_flags`) and demultiplexes by ifindex, separate from the monitor's socket so monitor buffer pressure never costs a request (A-17). An ENOBUFS on that socket reaches the solicitor as a sticky loss flag it reads and clears, not a closed channel and never a droppable channel message (R-16, review r9 N3). A request's position is its `NDA_PROBES` minus the parent's `ucast_solicit`, read when the request is handled. A resolution of a target starts at the first request the solicitor sees for it with none open, or at a request whose position is lower than the last one seen, and the solicitor counts its own Solicitations from zero at that start whatever the position says. Requests are deduplicated on position, never on wall-clock time (review r8, I3): a request whose position equals one already handled in the resolution is ignored and counted, and a request at a distinct higher position is always handled. The fit rule (review r8, I1 and I2): with `n` Solicitations already sent in the resolution, the solicitor sends one for a request at position `q` only while `q + (3 - n) <= 7`, that is, while the Solicitations still owed and the deadline one RetransTimer after the third can all finish by position 7, one position before the kernel's own multicast at position 8. So a resolution's first Solicitation goes out at position 4 at the latest, its third at position 6 at the latest, and its deadline falls at position 7 at the latest. When the rule refuses a send with fewer than three sent, whether the first request seen came too late or requests were lost after the first send, the solicitor sends nothing more for that resolution, never writes FAILED for it, counts it as handed to the kernel fallback, and leaves it to the kernel's own multicast at position 8 (A-13; the fallback condition of the -2/-3 claims). With three sent it sends nothing more (step 7 ends the resolution). It picks the path (Key Design Decisions row 5: the Active group's macvlan, virtual MAC and source, or the parent with its physical MAC and link-local when none is Active), builds the whole frame (`BuildNS`) and sends it on that device's AF_PACKET socket: to the solicited-node group for INCOMPLETE, to the cached link-layer address for PROBE
6. a host's Advertisement for a macvlan-sent Solicitation arrives on the macvlan (virtual MAC destination, private mode), where the kernel finds no entry and discards it (RFC 4861 Section 7.2.5); the solicitor's ICMPv6 socket on that macvlan reads it, validates it (Section 7.1.2), applies the Section 7.2.5 steps to the parent's entry and writes the result with `iface.SetNeighbor`, always carrying the router flag the steps produce (`NTF_ROUTER` set or clear, under `NLM_F_REPLACE`, so `neigh_add` passes `NEIGH_UPDATE_F_OVERRIDE_ISROUTER` and the flag is written either way); the kernel then sends the queued packets (A-11). When the applied Advertisement turns the entry's IsRouter flag from TRUE to FALSE, the solicitor performs the router-to-host step the kernel's `ndisc_recv_na` would have run (`rt6_clean_tohost`), through `iface`: it deletes the parent's Router Advertisement default routes whose gateway is the Advertisement's IPv6 source address, in the parent's table (the VRF's table when the parent is enslaved to one), then, the `SetNeighbor` write having cleared `NTF_ROUTER`, triggers the kernel's exception garbage collector by writing `net/ipv6/route/flush`, which removes every cached exception route whose gateway neighbour lacks `NTF_ROUTER`, and verifies by a re-dump (Key Design Decisions row "Router to host", AC-28). The old IsRouter flag is read from the kernel's current entry (`iface.GetNeighbor`) immediately before the `SetNeighbor` write, never from the request's `NTF_ROUTER`, and the step keys on the Advertisement's IPv6 source address, as `ndisc_recv_na` does (`rt6_clean_tohost(net, saddr)` after reading `old_flags` from the entry; review r8, N-4). An Advertisement for a parent-sent Solicitation reaches the parent, and the kernel completes its own entry and runs that step itself
7. the solicitor ends a resolution in which it has sent three Solicitations at the first of: (a) a request for the target at a position higher than the third Solicitation's (with no request lost, the request one position after it); (b) its own deadline, one RetransTimer after its third Solicitation (the kernel's own wait after its last probe), the RetransTimer read from the parent's `retrans_time_ms` when that Solicitation is sent. A resolution with fewer than three sent is never ended by Ze: it is open only while the fit rule of step 5 can still reach three, and otherwise it is handed to the kernel fallback (review r8, I2). Ending is a `NUD_FAILED` write, after which the kernel returns address-unreachable for the queued packets (A-12), and it is guarded twice (B1): the solicitor disarms the target's deadline and closes the resolution on any state event for the target whose state is outside INCOMPLETE and PROBE (the kernel completing the entry on the parent path, an unsolicited Advertisement on the parent, an operator write, a demotion mid-resolution handing the answer to the parent), and immediately before every `NUD_FAILED` write it re-reads the entry through `iface.GetNeighbor` and writes only if the state is still INCOMPLETE or PROBE, counting the skip otherwise, and only if the re-read's position (its `NDA_PROBES` minus `ucast_solicit`) is not lower than the last position the resolution saw: a lower one means the kernel started a new resolution of the target (an entry that failed or completed and was re-queued), so the write is refused and counted, and the new resolution opens at its own first request (review r8, N-1). Open-resolution records are bounded (review r8, N-2, revised by review r9, I2; main-thread decision 2026-10-15, confirmed by the owner 2026-10-15): a record keeps its last position and its send count until the kernel's resolution can no longer be running, so it expires, and is counted, only after `8 + m - p` RetransTimers with no request, where `p` is the last position it saw and `m` is the kernel's multicast count for that resolution (the parent's `mcast_solicit` for INCOMPLETE, its `mcast_resolicit`, 3, for PROBE), read when the record is updated; a record with a deadline armed lives until that deadline. A request for the target at a position higher than the record's last continues the same resolution with the same count, however long the gap; only a lower position (the kernel's DELAY to PROBE reset or a new resolution, N-1) opens a new record. A shorter expiry would reset the count mid-resolution: with a send at position 0 and the requests at 1 to 3 lost, a three-RetransTimer expiry would let position 4 open a new record at zero and send at 4, 5 and 6, four Solicitations in one resolution. So a resolution handed to the fallback, or one whose entry vanished without a state event Ze saw, frees its record once the kernel's own probes and wait are over. A request at a negative position (`NDA_PROBES` below the parent's `ucast_solicit`, after an operator raised `ucast_solicit` over the recipe and before the reassert) is ignored and counted, and opens no resolution (review r8, N-5). `__neigh_update` writes an administrative FAILED over any state and the kernel offers no compare-and-set, so the remaining window is the interval between that read and the write. Timing (review r8, I1): the kernel's own multicast from the parent waits until position 8, at eight RetransTimers. The fit rule puts the third Solicitation at position 6 at the latest and the deadline at position 7 at the latest, so the end comes at least one RetransTimer before position 8. This is a margin, not a guarantee, and it holds under two conditions, which the -2/-3 claims and the dataplane doc state: (1) Ze's handling latency, from the kernel emitting a request to Ze's send, stays below one RetransTimer, because Ze's deadline runs from its own send while the kernel's probes run from the kernel's timer; (2) the parent's RetransTimer is not lowered mid-resolution by a Router Advertisement after Ze read it for the deadline, because the kernel then reaches position 8 sooner than Ze's deadline assumes. Under (2) end trigger (a) still tracks the kernel's own pace and ends the resolution one kernel probe before position 8, so the margin is lost only when the request after the third Solicitation is lost as well. A resolution Ze handed to the fallback, or one it never saw (crashed, or its subscription lost, R-8 and R-16), reaches position 8: that is the kernel fallback, part of the owner's design (c) of 2026-10-14, and its multicasts carry the physical MAC and add `mcast_solicit` Solicitations to whatever Ze sent
8. the firewall registry verifies each owner's tables against the loaded backend's verifier and hands the accepted set to `Apply` (nft lowers the arp family; vpp refuses what it cannot express)
9. the kernel builds the parent's ARP requests: sender protocol address chosen by `arp_announce`, sender hardware address the parent's MAC

## Design Insights

- The journal row framed D1 as a firewall term; the obligation is on the sender the kernel chooses, which a sysctl governs.
- RFC9568-8.1.2-3 is scoped to restart and boot, and the owned address is on the parent before VRRP exists; a steady-state proof does not reach it.
- The owner filter belongs to the instance's life, not to Active: published wherever the owned set can change (build, reconfigure), withdrawn wherever the instance ends (teardown, build unwind), through one function.
- A route moves everything that follows it: the steering route of round 5 moved gateway routes, source address selection and resolution for traffic that had nothing to do with Solicitations (review r5). Taking over only the Solicitation, through the kernel's application-probe interface, changes the one message the RFC sentence names.

## Known Limitations
- Owners with no non-virtual address in the subnet, or whose owned address is primary: Q2 (ii), the IPv4 deviation recorded in the RFC9568-8.1.2-3 row and reported by `ze doctor`.
- The interval from the iface address install to `engine.build`, at every boot and restart (A-7): Q7 (b). It stays open and is stated in the `{gap}` reasons of RFC9568-8.1.2-3 and RFC9568-8.2.2-5 and in the dataplane doc; for IPv6 it includes the Duplicate Address Detection iface runs on the parent for the owned address.
- RFC 4861 Section 7.2.2 source deviation (Q8 (a), main-thread decision 2026-10-15, confirmed by the owner 2026-10-15): while no IPv6 group on a parent is Active, Ze's Solicitations from the parent use the parent's link-local as source, and an Active non-owner's use its macvlan link-local, whatever address the prompting packet came from. The SHOULD, "If the source address of the packet prompting the solicitation is the same as one of the addresses assigned to the outgoing interface, that address SHOULD be placed in the IP Source Address of the outgoing solicitation.", is unmet when the prompting packet came from one of the parent's global addresses or the owned address (parent-sent) or from a virtual address (Active non-owner); the next sentence, "Otherwise, any one of the addresses assigned to the interface should be used.", is what Ze does, as the kernel does whenever it holds no prompting packet.
- A crash, a lost request subscription before Ze resubscribes, a resolution whose requests reached Ze too late for three Solicitations and the deadline to fit before position 8 (the fit rule, review r8), or a resolution in which Ze's handling latency reached one RetransTimer or a Router Advertisement lowered the RetransTimer while the request after the third Solicitation was lost (Data Flow step 7), hands resolution to the kernel fallback (part of the owner's design (c), 2026-10-14; kept against `mcast_solicit=0` by main-thread decision 2026-10-15, confirmed by the owner 2026-10-15): a new neighbour resolves through the kernel's multicast eight RetransTimers late, a resolution Ze solicited once or twice before handing over gets the kernel's `mcast_solicit` Solicitations on top of Ze's, so more than three in all, an established one is re-confirmed by multicast with no loss, and every such kernel Solicitation leaves the parent with the physical MAC, sourced from the queued packet's address (the owned address among them) or the parent's link-local. That window is outside the RFC9568-8.2.2-2/-3 met claim and inside the -5 gap. The next start restores residue from `net/ipv6/neigh/default` with a warning (R-8, R-16).
- A router with `net.ipv6.conf.all.forwarding` 0 on a kernel built with `CONFIG_IPV6_ROUTER_PREF` sends router reachability probes from the parent with the physical MAC, outside the recipe (`rt6_probe`, R-15); the -2/-3 claims hold only with IPv6 forwarding on.
- Linux v5.3 floor (A-18, review r8 N-6; main-thread decision 2026-10-15, confirmed by the owner 2026-10-15): on a kernel below v5.3 the IPv6 parent recipe is not applied and the solicitor is not started, so the group runs as it does at HEAD, the kernel keeps sending the parent's Solicitations with the physical MAC (RFC9568-8.2.2-2/-3 unmet on that host), and one error line per parent names the running release, the floor, why, and the fix (run a v5.3 or later kernel).
- A lost request subscription is reported by the counter, the gauge, the error log line and `show doctor` (Q9 (b), owner 2026-10-15), and by the offline `ze doctor` through the doctor route (owner, 2026-10-15; AC-31), and only while the daemon runs and answers: with no daemon reachable `ze doctor` says its daemon checks were skipped (`plan/release/fixes/spec-doctor-daemon-route.md`, its AC-2). `show doctor` reports the current state, so a loss the solicitor has already repaired leaves no warning there; its trace is the loss counter and the log line.
- The solicitor's `NUD_FAILED` write is guarded by state events and a re-read (B1), but the kernel has no compare-and-set: an Advertisement the kernel processes between the re-read and the write is overwritten, and the next packet to that neighbour starts a fresh resolution.
- The router-to-host step (AC-28) runs only for Advertisements Ze applies; on the parent path the kernel runs its own `rt6_clean_tohost`. Its exception half goes through the kernel's GC (review r8, I4), so an exception route the GC leaves after the retry (counted and logged) keeps steering traffic through a neighbour that is no longer a router: a gap against the RFC 4861 Section 7.3.3 Destination Cache update that Section 7.2.5 requires. Its bound depends on the kernel release, stated by sublevel (review r9, I1, review r10, I1; main-thread decision 2026-10-15, confirmed by the owner 2026-10-15). The unbounded set is v6.9 through v6.12.24, every 6.13.x, and v6.14 through v6.14.3, plus every 6.10.y and 6.11.y release (neither series received the fix): there `fib6_gc_table` walks only routes that expire and `rt6_insert_exception` does not add the holding route to that list, so an exception held under a route that does not expire (a static or connected default through the neighbour) is never examined, by the flush or by the periodic run, and that residue has no time bound: it lasts until the exception is removed some other way (its route deleted, the exception replaced, the namespace flushed by an operator). On every other release in scope the GC reaches every exception, so a residue lasts until its next periodic run, bounded by `gc_interval`: up to v6.8 and 6.1.y (no GC list, whole-table walk), 6.6.y (the GC list and the fix arrived together at v6.6.120), v6.12.25 and later 6.12.y, v6.14.4 and later 6.14.y, and mainline from v6.15. An exception under a Router Advertisement route is reached on every release in scope. Wiring step 1 checks each target kernel's `uname -r` against this set and probes it.
- Handed-over resolutions and `mcast_solicit` (review r9, N4; main-thread decision 2026-10-15, confirmed by the owner 2026-10-15): the recipe leaves the host's `mcast_solicit` untouched, so the statement that a resolution never reads FAILED after fewer than three Solicitations holds for a resolution handed to the kernel fallback only while the parent's `mcast_solicit` is 3 or more; with a lower value, a resolution in which Ze's Solicitations before the hand-over plus the kernel's `mcast_solicit` fall below three reads FAILED after fewer than three. The recipe reads the parent's `mcast_solicit` when the first IPv6 group applies it and at every reassert, and logs one warning per parent naming the value, the precondition, why, and the fix (`sysctl -w net.ipv6.neigh.<parent>.mcast_solicit=3`).
- Owner heads-up, not a blocker: `net/ipv4/neigh/<parent>/app_solicit` would let the same mechanism send the parent's ARP requests from the macvlan, covering the Q2 configuration; Q1 (a) and Q2 (ii) stand as his answers unless he reopens them.
