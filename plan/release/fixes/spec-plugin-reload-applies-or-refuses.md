## Task

A configuration reload reaches about twenty plugins that answer `config-apply`
with OK and change nothing. The plugin SDK binds `callbackConfigApply` to a
default that accepts the apply when the plugin registered no `OnConfigApply`
handler (`pkg/plugin/sdk/sdk_callbacks.go`, `initCallbackDefaults`,
`configApplyCallback(nil)`). The plugin's `OnConfigure` runs at Stage 2 only, so
the operator's commit reports success while the plugin keeps its startup
configuration. Example: an edit of a prefix-list's entries reaches
`bgp-filter-prefix`, which answers OK and keeps the old lists.

Owner decision, 2026-10-14 ("yes"), two steps in this order:

| Step | What | Rule |
|------|------|------|
| (c) | Every reload-relevant plugin gets its own config verify, apply and rollback handlers, so a reload either takes effect or is refused at verify with a "needs restart" error naming the leaf. Template: `filter_irr` (`irrConfigTx`, `internal/component/bgp/plugins/filter_irr/config_tx.go`) | per-plugin semantics |
| (a) | Then the SDK refuses config for a participant that registered no apply handler, so a new plugin cannot silently ignore a reload again | `ai/rules/no-layering.md`: the silent default is deleted, not kept beside the refusal |

### Boundary with the BGP OPEN spec

spec-bgp-open-session-rfc-defects (closed 2026-10-21), D2, owner Q1 = b
(2026-10-13): a reload that changes, adds or removes a plugin-declared
CAPABILITY is refused at config-verify by the SDK, through the capability
extractor each capability plugin registers (`Plugin.DeclareCapabilitiesFrom`,
final name set there). Its callers: `softver`, `hostname`, `role`, `llnh`, `gr`,
the exabgp bridge, and the external `internal/plugins/exabgp/main_sdk.go`.

| Concern | Owner |
|---------|-------|
| Any leaf whose value reaches a capability declaration (softver encoding, hostname FQDN, role value, llnh capability, GR/LLGR timers and families, bridge route-refresh and add-path) | BGP OPEN spec. This spec adds no verify check for these leaves and never re-declares a capability |
| Every other leaf those plugins read (role `strict`, role `export`, the role name-to-address map, the bridge's non-capability leaves) | This spec |
| The apply handler of a plugin whose only config is capability declarations (`gr`, `hostname`, `llnh`, `softver`, external exabgp) | This spec, Phase 4, and only after the OPEN spec's extractor has landed: before it, a no-op apply would name as handled a change nobody refuses |

The two verify refusals compose in the OPEN spec's order (its "D2 refusal
design" step 3 and Data Flow step 4): the plugin's own verify handler answers
first, then the SDK runs the capability extractor on the candidate and compares.
The OPEN spec fixes that order so the `llnh` and `gr` refusals keep answering
first; nothing in this spec argues for the reverse, so this spec's verify
handlers sit in the "own handler" slot. Neither spec weakens the other's refusal.
(Design review round 1, I3: an earlier draft here said the capability comparison
ran first, which contradicted the OPEN spec.)

## Data Flow (MANDATORY - see `ai/rules/architecture.md`)

### Entry Point
- Operator edits the config file and sends SIGHUP (`cmd/ze/hub/main_reload.go`), or commits from the CLI editor
- Format at entry: config tree, diffed against the running tree

### Transformation Path
1. `server/reload.go` diffs roots, selects participants by `WantsConfigRoots`
2. Transaction orchestrator (`internal/component/config/transaction/orchestrator.go`) sends `config-verify` with full changed-root sections to every participant
3. SDK verify callback: the plugin's verify handler (the same side-effect-free function as its `InProcessConfigVerifier`) parses its subtree into a pending candidate, or refuses with a needs-restart error; then the OPEN spec's capability comparison runs on the same candidate
4. If every participant verified, `config-apply` with diff sections; SDK apply callback calls the plugin's apply handler, which installs the pending candidate (atomic swap or reconcile) and keeps the previous for rollback
5. `config-committed` closes the gate; on failure `config-rollback` reaches plugins that applied, which restore the previous

### Boundaries Crossed
| Boundary | How | Verified |
|----------|-----|----------|
| Engine ↔ Plugin | `config-verify` / `config-apply` / `config-rollback` / `config-committed` RPCs, JSON sections (`rpc.ConfigVerifyInput`, `rpc.ConfigApplyInput`) | Yes, `sdk_callbacks.go` read 2026-10-14 |
| Plugin ↔ consumers of its state | atomic pointers read by filter RPC handlers; `coreCos` registry read by iface; `routingtable` registry read by static | Yes, call sites grepped 2026-10-14 |

### Integration Points
- `Plugin.OnConfigVerify`, `OnConfigApply`, `OnConfigRollback` - each plugin registers all three
- `rib.reselectAIGPRoutes` (`rib_aigp.go`) - the model for the reselect walk rib owes after a selection-rule change
- OPEN spec `DeclareCapabilitiesFrom` - composed after the plugin verify
- `Plugin.OnConfigCommitted` (`sdk_callbacks.go`) - role's prune of learned remote roles moves here (I5)
- Coarse apply order: `participantsWithoutOperations` (`transaction/orchestrator.go`) sorts coarse participants by name, and `placeSectionNodes` (`transaction/solver.go`) places them after the interface operations; no design in this spec depends on cos-before-iface or healthcheck-before-watchdog

| R-8 | healthcheck: a stopped probe leaves its route announced, or the apply stalls or deadlocks. Read 2026-10-14 (design review round 1, I6): `applyConfig` (`healthcheck.go`) holds `m.mu` and blocks on `<-rp.done` after `rp.cancel()`; the probe's `ctx.Done()` branch runs `handleExit`, which dispatches `request bgp watchdog withdraw` through `DispatchCommandArgs` with its own 5 s timeout, to watchdog, which is another participant of the same transaction. Coarse participants apply in name order (`participantsWithoutOperations` sorts), so healthcheck's apply runs and is awaited before watchdog's. `runProbe` never takes `m.mu`, so the lock itself is not the deadlock; the hazard is that healthcheck's apply reply waits on a cross-plugin command round trip issued from inside the transaction, so it stalls up to 5 s per stopped probe and, if the round trip cannot complete during an open apply, ends in the timeout with the route left announced | apply does NOT wait for stopped probes: under `m.mu` it swaps the probe set and starts new probes, releases `m.mu`, cancels the stopped probes and returns; each stopped probe's `handleExit` withdraws asynchronously. The withdraw is order-independent against watchdog's apply in the same transaction: if watchdog's apply removed the pool, watchdog's R-7 merge already withdrew the announced entry and the late command fails with "unknown group", logged at debug; if the pool stays, the entry ends withdrawn whichever lands first because R-7 keeps per-entry announce state. Rollback restarts the previous probes, with a fresh FSM (`newFSM`): rise/fall progress is not restored (N2), so AC-4 claims the previous probe SET, not the previous probe state. Ordering against the NEW probe (design review round 2, ISSUE-2, read 2026-10-14): with the wait gone, a changed probe's old `handleExit` (watchdog withdraw, then `ipt.removeAll()`) runs unordered against the new probe of the same name, whose `runProbe` checks at once from `StateInit` and with `rise 1` announces at once; a late withdraw lands after that announce, and with debounce the route stays withdrawn and the IPs stay removed. The same holds for a new probe of another name sharing the group, and on rollback. So each new probe carries the `done` channels of the stopped probes sharing its name or its group, collected under `m.mu` at the swap, and `runProbe` waits on them, inside its own goroutine and never under `m.mu`, before `waitReady` and its first dispatch. The wait does not select on its own `ctx`, so a probe cancelled while waiting still closes its `done` only after its predecessors closed theirs, which keeps the chain ordered across a reload followed by its rollback. After the wait, `runProbe` returns at once if `ctx.Err() != nil`, before `waitReady`: once `m.ready` is closed, `waitReady`'s `select` picks at random between `m.ready` and `ctx.Done()`, so without the check a cancelled probe could add IPs and dispatch (design review round 3, ISSUE-1). The wait is bounded by a sum, not by the 5 s dispatch timeout alone (design review round 3, NOTE-1, read 2026-10-14): a predecessor cancelled mid-cycle closes its `done` only after its in-flight probe command (`runProbeCommand`, bounded by `cfg.Timeout`, killed early by the cancel), its in-flight hooks (`runHooks`, `hookTimeout` 30 s each) and `handleExit`'s 5 s dispatch, so one generation can take `cfg.Timeout` + 30 s + 5 s, and a chain of generations (reload then rollback then reload) adds one such term per generation. `handleReset` holds `m.mu` across `<-rp.done`, so a reset of a probe that is still waiting on its predecessors holds `m.mu` for that whole sum and stalls any `applyConfig` (which takes `m.mu`) behind it; so `handleReset` takes the same shape as apply (decided by the main thread under the owner's delegation, 2026-10-14): under `m.mu` it swaps in the new `runningProbe` carrying the old probe's `done` (and the predecessors that probe still waits on) and cancels the old one, and it does not wait on `<-rp.done`; the new probe's own predecessor wait keeps the order. Test row: `TestHealthcheckResetDoesNotHoldLockAcrossExit` (a dispatch stub holding the old withdraw; a concurrent `applyConfig` returns while the reset's old probe is still held). Apply still returns without waiting. Tests: `TestHealthcheckApplyDoesNotWaitForProbeExit` (dispatch stub that blocks; apply returns), `TestHealthcheckChangedProbeWaitsForOldExit` (AC-16b), `bgp-healthcheck-probe-reload.ci` with probe and watchdog pool removed in one commit. ## Design Insights

- The no-op default hid every defect behind it: a guard nobody runs gives no wrong answer to notice (journal, IKE row 2026-08-24)

## Key Design Decisions
| Decision | Alternatives Considered | Rationale |
|----------|------------------------|-----------|
| Per-plugin handlers first, SDK refusal last | SDK default re-runs `OnConfigure` (investigation option b) | b is silently wrong for capability plugins, rib removal, role (race) and the bridge; owner chose c then a |
| Refuse at verify | refuse at apply | nothing applied, no rollback; Q1 confirms |
| No-op apply when own subtree unchanged | apply always | shared roots would restart services on unrelated edits |
| One verify function per plugin, side-effect free, registered as both `InProcessConfigVerifier` and `OnConfigVerify` | a reload-only verify beside the static one | two verifiers drift; the cos one already mutated the daemon (B1) |
| iface resolves profiles from the candidate it is handed | order cos apply before iface apply | no ordering mechanism exists at apply, and an order would be a second load-bearing fact nothing enforces |
| healthcheck apply never waits on a cross-plugin dispatch | wait for probe exit under the lock | the withdraw is a command round trip to another participant of the same transaction |
| Filter edits apply to subsequent UPDATEs only | re-evaluate stored routes here | import re-evaluation is owned by `spec-bgp-filtered-route-storage`; export re-advertisement by `spec-bgp-export-policy-reload-readvertise` |
| Q2 point 3 is a resolution pass after the parse (`resolveUnitQoS`) (confirmed by the owner 2026-10-15) | a resolve flag threaded through every parse function | same behavior, one place to read; the decomposer keeps the unresolved parse |
| iface resolves only against the delivered `class-of-service` section; none delivered means no profiles, never the installed registry (confirmed by the owner 2026-10-15) | fall back to the installed registry when the section is absent | the transaction delivers a read root whole whenever the tree holds it, so absent means absent; a fallback reintroduces the cos-before-iface ordering |
| An existing VLAN not in the previous config is set to the config's maps, and its undo writes nil (confirmed by the owner 2026-10-15) | leave its maps alone | the config is the authority at boot; the guest run showed a leftover VLAN programmed to the config |
| iface verify does nothing for a delivery with no `interface` section (confirmed by the owner 2026-10-15) | parse an empty interface tree | a `class-of-service`-only delivery has nothing for iface to check |
| The fake backend's `CreateVLAN` refuses an existing VLAN (confirmed by the owner 2026-10-15) | accept it silently | the kernel refuses it, and the fake accepting it hid the missing update step |
| Stage 2 (boot) stays lenient on an unbindable `listen-interface` and logs it; a reload is strict and fails the apply (R-13) (confirmed by the owner 2026-10-15) | strict at boot too | on the appliance, interfaces come up after the daemon, so a strict boot would leave the service down where a later bind succeeds; at reload the operator is present to read the refusal |
| VPP `qos_mark_disable` accepts -54 and -81 for a never-enabled mark (confirmed by the owner 2026-10-15) | accept one code | FDio/vpp `src/vnet/qos/qos_mark.c` `qos_mark_disable` returns either for "not enabled" |
| The routing-table registry is kept with no current reader, published by the routing-table `ConfigTx` (owner decision 2026-10-15, review ISSUE-4 / Q-c answer (b)) | (a) delete the registry now that `static` resolves against the candidate (R-9) | policy routing and VRFs will need the installed tables; their first consumer MUST read the registry rather than re-parse the `routing-table` section |

## Known Limitations
- Capability leaves are the BGP OPEN spec's; this spec does not make them reloadable
- A filter or policy reload re-evaluates no stored route and re-advertises nothing: imports wait for `spec-bgp-filtered-route-storage` AC-3, exports for `spec-bgp-export-policy-reload-readvertise`; the reload page says so
