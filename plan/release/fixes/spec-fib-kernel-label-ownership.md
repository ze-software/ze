## Task

`fib-kernel` is the one writer of the kernel FIB, and two owners feed it: the
system RIB (best-change events) and the label sources (LDP, RSVP-TE, OSPF
segment routing, BGP EPE, through `(mpls-fib, entry)` events). A table-0 push
and a system-RIB route for the same prefix are both protocol-250 IP routes in
the main table, so the kernel cannot tell the two owners apart. `fib-kernel`
must, and today it does not. Six defects follow, all read at the producing
functions on 2026-11-24 and none of them run:

| ID | Symptom | Root cause at the producer |
|----|---------|----------------------------|
| D-1 | A label source's push replaces a live labeled system-RIB route (BGP labeled-unicast) of the same prefix, while the system-RIB record still lists that route as installed | `addMPLSPushLocked` (`mplscontext.go`) chooses replace over exclusive add on `f.mplsInstalled`, and `recordInstalledLocked` (`fibkernel.go`) sets the same map for every system-RIB install that carries labels. One map answers for two owners. The reverse also holds: a system-RIB withdraw or unlabeled replace of the prefix clears the map (`processEvent`, `recordInstalledLocked`), so the push's own relabel is then an exclusive add that meets its own route |
| D-2 | Withdrawing a push that was never installed deletes the system RIB's route for the FEC, on a fresh box too | `delMPLSEntryLocked` (`mplsentry.go`) calls `delRichRoute(FEC, 0)` for every table-0 push removal without asking whether a push was installed. `ldpFIB.ProgramPush` records the FEC as wanted before the writer answers, so `ldpFIB.Remove` withdraws a push whose add was refused. `delRichRoute` deletes by prefix, protocol 250 and table (`ownedRouteKey`), which the system RIB's route matches |
| D-3 | A push relabel deletes the system RIB's route of the same prefix at another metric, and a system-RIB replace, withdraw or stale sweep removes or overwrites the push | `replaceRichRoute` goes through `replaceOwnedRoute` (`backend_linux.go`), which after the write deletes every other protocol-250 route of the prefix in the table. The system RIB installs at its protocol metric (`fibChange`, `internal/component/sysrib/fibimport.go`; `buildRichRoute` sets the kernel priority from it) and a push carries no metric, so the normal LDP case, an IGP route at its metric beside a push at priority 0, is exactly the pair this cleanup breaks. `delRichRoute` and `delListedLocked` name no priority, so a system-RIB withdraw and the stale sweep delete whichever protocol-250 route of the prefix the kernel matches first |
| D-4 | A new `fib-kernel` refuses the swap and pop entries its own previous run left, and never removes the ones no source wants any more | `addMPLSEntryLocked` asks for a replace only for an in-label in `f.mplsSwaps`, which a new process holds empty, so `addMPLSSwap` calls `RouteAdd` and the kernel answers `EEXIST`. `listZeRoutes` skips every route with no IP destination, so `startupSweep` never records an AF_MPLS entry and `sweepStale` never removes one |
| D-5 | A new `fib-kernel` refuses the table-0 push its own previous run left until the IP sweep removes it, and nothing applies it again afterwards | `startupSweep` records the leftover push like any protocol-250 route, but `addMPLSPushLocked` consults only `f.mplsInstalled`, so the re-applied push is an exclusive add over Ze's own leftover |
| D-6 | With `flush-on-stop` true, a stopping `fib-kernel` leaves the label sources' pushes and AF_MPLS entries in the kernel | `flushRoutes` builds its owned set from `f.installed`, `f.retained`, `f.staleTables` and `f.supersededTables`; a label-source push lives in `f.mplsInstalled` alone and a swap or pop in `f.mplsSwaps` alone |

The fix gives each owner a record of its own and makes every kernel write name
the slot it owns:

1. Label-source pushes get their own record, apart from the system RIB's.
   Replace, relabel and removal of a push are gated on that record alone.
2. Every write and delete names the route's kernel slot (table and priority).
   The cleanup after a replace removes only routes the caller's own record
   lists, never "every other protocol-250 route of the prefix".
3. The label-source record is saved through the plugin state store as it
   changes: which source holds each in-label, and which prefixes hold a
   label-source push. A new `fib-kernel` reads it at open, so it knows the
   owner of each route and label entry its previous run left without guessing
   from what the route looks like. The saved record is kept on the safe side
   of the kernel: a push leaves it before its kernel delete and before a
   system-RIB install into its slot, and comes back only when the push's
   record still holds it after the kernel answered: the kernel refused that
   delete, or installed nothing for that install. The kernel's error never
   decides it, because a system-RIB install can return an error after the
   kernel installed its route. The open drops what the kernel no longer holds
   (Data Flow, "Keeping the label-push record true").
4. The leftovers of a previous run are recorded with their slot, AF_MPLS
   entries included. A label source takes back by replace only what the saved
   record names as its own: a push over a leftover saved as a push, a source
   over its own in-label. The system RIB takes back any IP leftover in the
   slot it installs into, as it does today. A leftover with no saved owner is
   never handed to a label source.
   What no owner takes back is swept once BGP's deferred route selection is
   complete, as today, and the label sources are then asked once to apply
   again what was refused over a leftover.
5. A push identical to the recorded one is acknowledged without a kernel
   write.
6. The stop flush removes what both records and both leftover records hold.

A route BGP retained across the restart is therefore never replaced by a label
source, whichever owner applies first. RFC 4724 Section 4.1 requires
that: "When the Restarting Speaker restarts, it MUST retain, if possible, the
forwarding state for the BGP routes in the Loc-RIB and MUST mark them as
stale." BGP gives its best path the MED as metric, so a BGP route without MED
sits at IPv4 priority 0, the slot a push uses. A leftover saved as a push goes
to the first owner that applies for its slot, a label source by replace or the
system RIB by its install, as the slot of a fresh box goes to the first owner
that installs.

The design is Thomas's to approve. He has not been asked about it yet; the main
session split this work out of `spec-fib-dummy.md` on 2026-11-24 after its
seventh design judge refused the leftover-label design there. The first design
judge of this spec refused the version that let any label source take back any
leftover; the main session then ruled that the RFC text decides the contested
slot, and this version follows that ruling. The second design judge refused
the next version on two points. The label-push record and its saved copy could
name a slot the kernel no longer held a push in, after a device flush or a
crash during a removal. And the refusal of a system-RIB install over a
leftover saved as a push departed from `docs/architecture/core-design.md`
without saying so. The third design judge refused the next version on two
points. It kept a leftover at the push's slot through a system-RIB install at
another priority, which `core-design.md` says that install removes, and called
that agreement. And a crash between the system RIB's exclusive add into a lost
push's slot and the store write that forgot the push left the store naming the
system RIB's route as a push. This version keeps the record true through that
crash too (Data Flow, "Keeping the label-push record true", rule 3), lets the
system RIB's install at the push's slot replace a leftover saved as a push, and
states the leftover kept through an install at another priority as the
departure it is, put to Thomas as C-2 (Design presentation, "Documents departed
from" and "Choices for Thomas"). The fourth design judge refused that version
on one point: it wrote a lost push's FEC back to the store on any error from
the system RIB's add into the push's slot, and `programRouteLocked`
(`fibkernel.go`) also returns an error after the kernel installed the route.
It does so on a partial apply (`*supersededDeleteError`, which
`replaceOwnedRoute` returns when the write succeeded and a cleanup `RouteDel`
failed) and when `cleanupAfterInstallLocked` fails after a clean install
(`"delete"` and the cleanup error), and on both paths it has already run
`recordInstalledLocked`. The store could then name as a push a slot the system
RIB's route fills. This version writes a FEC back only when the label-push
record still holds it once `programRouteLocked` has returned, and keys every
other write-back on the records too (Data Flow, "One write per bucket per
batch", pass 3, and "Keeping the label-push record true").

**Behavior to preserve:**
- A first install into a slot `fib-kernel` holds no record for is an exclusive add, and a foreign route there refuses it with `EEXIST` (`mpls-kernel.md`).
- When a push and a system-RIB route want the same slot (main table, same priority), the first one installed holds it and the second is refused with `EEXIST` and reported by its owner (the label source's doctor check, or `fib-sync-failure` and the pending retry). Across a restart a slot the system RIB held is never given to a label source. A slot a push held goes to the first owner that applies for it, as on a fresh box.
- A push and a system-RIB route of one prefix at different priorities coexist; the kernel forwards by the lower priority.
- A swap or pop belongs to its source; another source's add or removal of that in-label is refused. This holds across a restart too.
- `flush-on-stop` false keeps every route and label entry in the kernel at stop.
- `startupSweep` writes nothing to the kernel, and the sweep waits for BGP's deferred selection as `waitAndSweepStale` does today. The signatures of `startupSweep`, `sweepStale` and `waitAndSweepStale` are kept, and so are the names and shapes of the fields `staleTables` (prefix to the list of tables a leftover was listed in) and `retained` (prefix to a boolean), which `rfc4724_restarting_fib_test.go` reads directly as `fib.staleTables[pfx]` and `fib.retained[pfx]`. The RFC-tagged test is therefore not edited. The slot priority and the push mark of each listing live in a separate record beside the two fields (Data Flow step 1).
- A system-RIB install of a prefix still removes the routes the system RIB's own records list for that prefix at other priorities of the table, as `replaceOwnedRoute` does today, with one exception stated in Data Flow step 5. That exception departs from `core-design.md`, "FIB Kernel", and waits for Thomas as C-2.
- The private push contexts (nonzero table) keep their own lifecycle in `mplscontext_linux.go`.
- A push from a second label source for a FEC another source's push holds replaces it, as today: which source wins a FEC two sources bind is not decided here (Known limits).

**Behavior to change:**
- D-1 to D-6 of the Task table.

## Data Flow

### Entry Point
- A label source applies an entry: `mplsfib.Apply` or `ApplyReplay` emits `(mpls-fib, entry)`, and `handleMPLSEntry` programs the batch under `f.mu` and acknowledges.
- The system RIB publishes `(system-rib, best-change)`, and `processEvent` programs the batch under `f.mu`.
- `fib-kernel` opens: `OnStarted` calls `startupSweep` before `run` subscribes.
- `fib-kernel` stops: `run` calls `flushRoutes` when `flush-on-stop` is true.
- The kernel notifies a route change: the route monitor calls `handleExternalChange` (`monitor.go`), which takes `f.mu`.

### Transformation Path
Two definitions hold for every step.

- **The slot priority** of a route is the priority the kernel stores it at: the metric for IPv4; the metric for IPv6, with 0 read as 1024. It is defined once, in one function, and every record, `ownsSlotLocked`, the delete key, the cleanup set and `replaceOwnedRoute` use that function. A slot is a prefix, a table and a slot priority.
- **The push's slot** of a prefix is the main table at the slot priority of metric 0: priority 0 for IPv4 and 1024 for IPv6. A BGP route without MED, and an IPv6 system-RIB route at metric 0 or 1024, want the same slot.

The saved label-source record:

| Part | Value | Meaning |
|------|-------|---------|
| Key pattern | `meta/fib-kernel/label-owner/{kind}/{bucket}`, registered in `register.go` and granted to `fib-kernel` with `statestore.RegisterPluginKeys` | One small value per bucket, so one change rewrites one value. A bucket is always written whole, from the records as they stand |
| `kind` | `in-label` or `push` | Which of the two label-source records the bucket holds |
| `bucket` | for an in-label, the label divided by 256; for a push, a 12-bit hash of the FEC | At most 4096 buckets of each kind, so one list call per kind, which the store bounds to 4096 keys, names every bucket that exists |
| Value | a list of pairs: in-label and source, or FEC and source | Who holds each entry of the bucket |
| When an in-label is saved | before the kernel write of its add; removed in the batch's third pass once the records no longer hold it: after the kernel delete, or when the add the kernel refused leaves `f.mplsSwaps` without it | The store names a source for every in-label the kernel holds, through a crash at any point. An entry the store names and the kernel lacks is dropped at the next open (step 1) |
| When a push is saved | after the kernel accepted it; removed before its kernel delete, whoever deletes it (its source, the sweep, the stop flush), before a system-RIB install replaces a leftover saved as a push, and before a system-RIB exclusive add into the push's slot of a FEC the label-push record holds; written back in the batch's third pass only when the label-push record, or a listing marked as a push, still holds it after the kernel answered: a delete the kernel refused, or a system-RIB install the kernel made nothing of. A system-RIB install the kernel made, even one `programRouteLocked` returns an error for, has the record forget the FEC (rule 3), so it never brings the FEC back | The store names a push only for a slot the kernel accepted a push in, and never across a write that could hand that slot to the system RIB's route, through a crash at any point. A crash leaves at worst a push the store does not name, which the next run treats as the system RIB's leftover. The direction RFC 4724 Section 4.1 forbids is a saved push that names a slot the system RIB's route holds; with this order no crash produces it, and a push the kernel removed behind `fib-kernel`'s back is covered by "Keeping the label-push record true" below |

**Where the store is called.** Always under `f.mu`, and before the acknowledgement where there is one, so the store and the records agree whenever another event is handled.

| Caller | What it saves |
|--------|---------------|
| `handleMPLSEntry` | the adds and removals of a label batch |
| `processEvent` | the forgetting of a push: the mark of a leftover saved as a push that a system-RIB install replaces (step 5), and every FEC of the label-push record whose push's slot a system-RIB install of the batch targets, out before the batch's kernel writes and back after them for each FEC the label-push record still holds once `programRouteLocked` has returned (rule 3 below) |
| `retryDuePending`, and `retryPendingAfterProgressLocked` at the end of a `processEvent` batch | the same as `processEvent` for the parked system-RIB changes it installs again: each retry pass is one batch for the store, with its own three passes, because it is a system-RIB install that can target a push's slot (`retryOnePendingLocked` calls `programRouteLocked`) |
| `sweepStale` | the forgetting of each leftover push and each stale in-label it removes (step 7) |
| `flushRoutes` | the forgetting of everything it removes (step 8) |
| `startupSweep` | the reconcile at open (step 1) |
| `handleExternalChange` | the forgetting of a push the kernel will not take back (step 9) |

**One write per bucket per batch.** No caller calls the store once per entry. Each caller above handles its batch (a label batch, a best-change batch, one sweep, one flush) in three passes.

1. The first pass writes nothing to the kernel. It finds the in-labels the batch will add, the pushes it will delete or let the system RIB replace, and, in a system-RIB batch, every FEC whose push's slot an install of the batch targets while the label-push record holds it. It writes each bucket they touch once: the in-label buckets with the adds in, the push buckets with all those pushes out. The label-push record itself keeps those FECs until the kernel answers.
2. The second pass makes the batch's kernel writes.
3. The third pass writes once each bucket the outcome changed, whole, from the records as they stand after the second pass, never from the error a kernel write returned. A push bucket names a FEC exactly when the label-push record, or a listing of the leftover slot record marked as a push, still holds it; an in-label bucket names an in-label exactly when `f.mplsSwaps` or the stale in-label record holds it with a source. So a push the kernel accepted goes in, a push whose delete the kernel refused goes back, an in-label deleted or whose add was refused goes out, and a FEC whose push's slot a system-RIB install of the batch targeted goes back only when the label-push record still holds it once `programRouteLocked` has returned. That record forgets the FEC in `recordInstalledLocked` on every install the kernel made, the partial apply included, where `programRouteLocked` returns an error with the route installed (rule 3), so the FEC goes back only when the kernel installed nothing in that slot.

The first store call that fails or times out ends the store calls of that batch. The kernel writes go on, every bucket still to write is marked dirty, the warning `fib-label-owner-unsaved` is raised, and the dirty buckets are written by the next batch that calls the store and at stop, whatever `flush-on-stop` says. A batch therefore waits on the store for at most one timed-out call, five seconds (R-5). A save the store refuses never undoes or holds back a kernel write: the entry forwards and is acknowledged.

**Keeping the label-push record true.** The kernel can remove a push without `fib-kernel` writing: it flushes the route with the device it went through, and it may send no notification of that (A-6). The label-push record and its saved copy must never then name a slot another owner's route fills. Five rules hold that, and the first four need no notification.

1. A push leaves the store before its kernel delete (the table above), so no crash leaves the store naming a push that is gone.
2. The open drops every saved push whose slot the kernel listing does not hold, and every saved in-label the label listing does not hold (step 1), as `fib-vpp`'s `restore` removes the saved entries VPP no longer holds.
3. A system-RIB exclusive add that the kernel makes into a slot the label-push record holds proves the kernel lost the push, or it would have refused the add. The FEC leaves the store in the batch's first pass, before that add is written, so a crash after the add finds the store already without it. The record forgets the FEC in `recordInstalledLocked` (step 5), which `programRouteLocked` calls on both of its paths that installed: a clean install, after which `cleanupAfterInstallLocked` can still fail and `programRouteLocked` return `"delete"` with the cleanup error, and a partial apply, where the write succeeded, a cleanup `RouteDel` of `replaceOwnedRoute` failed, and `programRouteLocked` returns the `*supersededDeleteError`. The third pass writes the FEC back only when the label-push record still holds it once `programRouteLocked` has returned, never because `programRouteLocked` returned an error, so the store gets a FEC back only when the kernel installed nothing in that slot. `processEvent` parks every change `programRouteLocked` returned an error for, the partial apply included, with `trackPendingChangeLocked`, and the retry (`retryOnePendingLocked`) is a system-RIB install under the same rule: after a partial apply the record no longer holds the FEC, so the retry takes nothing out of the store for it and writes nothing back, and after an add the kernel refused the retry repeats the three passes. A crash before the third pass leaves a live push the store does not name, the safe side of the table above: the next run treats it as the system RIB's leftover. The mirror holds for the other owner: a push's exclusive add that succeeds into a slot the system-RIB record holds proves the kernel lost that route, and the system-RIB record forgets it (step 2).
4. Every kernel write a record gates is checked against the kernel in the backend. A relabel replaces only when a protocol-250 route sits in the push's slot, and adds exclusively otherwise. A delete at IPv4 priority 0, which the kernel cannot tell from a delete that names no priority (A-2), first looks the slot up and sends no delete when no protocol-250 route sits there, so the removal of a push the kernel lost does not delete the system RIB's route at another metric.
5. A removal the kernel does notify is handled by the monitor (step 9).

With rule 3, a protocol-250 route in the push's slot of a FEC the label-push record holds is the push: `fib-kernel` is the only writer of protocol 250, and its only other write into that slot is the system RIB's exclusive add, which forgets the push whenever the kernel makes it.

Every ownership decision of this design is read from a record after the kernel answered, never from the error a write returned, because the two differ in one place: a system-RIB install can return an error after the kernel installed its route (rule 3). The other writes cannot. A push's own write (a relabel, a take-back, an exclusive add, the monitor's reassertion) hands the backend no other priority to clean up, so it is one route write and its error means the kernel wrote nothing in that slot. A delete names one slot, so its error means the route is still there. A swap or pop add is one AF_MPLS route write (`addMPLSSwap`). Each record is updated from those answers, and the store is written from the records.

1. **Open.** `startupSweep` lists the protocol-250 IP routes as today and fills `retained` and `staleTables` as today, with the names and shapes the RFC-tagged test reads. A new record beside them, the leftover slot record, holds the table, the slot priority and the push mark of each listing; the functions that drop a table from `staleTables` (`forgetStaleTableLocked`, `forgetOneStaleRouteLocked`, `sweepPrefixLocked`, `flushRoutes`) drop the listing from it in the same step, and `TestLeftoverSlotRecordFollowsStaleTables` holds the two together. `startupSweep` then lists the protocol-250 AF_MPLS in-labels and records each as a stale in-label. The listing is one method on a new interface beside `mplsBackend`, which `netlinkBackend` implements; a backend that programs label entries and lacks it gets no label listing, said in one log line. Then it reads the saved record: one list call per kind names the buckets, and each bucket is read once. Each IP listing at the push's slot is marked as a label-source push when the store names that FEC, and each stale in-label gets the source the store names for it, or none. Then it reconciles the store to the kernel: a saved push whose slot was not listed and a saved in-label that was not listed leave the store, each changed bucket written once. A kind whose kernel listing failed is not reconciled, so nothing of it is dropped on a listing that did not answer. Nothing here writes to the kernel. A listing the kernel refuses, a bucket the store cannot read, and each in-label left without a source are raised under `doctor-fib-sweep-incomplete`; an unread bucket leaves its entries without an owner. A `fibKernel` that was handed no store, as the unit tests that build one and call `startupSweep` directly have none, reads and saves nothing: every listing is unmarked and every stale in-label is without a source. `OnStarted` hands the store over before it calls `startupSweep`. The sweep worker starts when either leftover record holds an entry.
2. **Push add** (`addMPLSPushLocked`, table 0). The target is the push's slot. In order:
   - The label-push record holds the FEC with an equal entry (source, out-labels, next hop, path MTU): acknowledged, no kernel write.
   - The label-push record holds the FEC with another entry: a relabel, written through the checked replace of that slot with no other priority to clean up. The backend replaces when a protocol-250 route sits in the slot, which is the push (rule 3), and adds exclusively when none does, which is a push the kernel had removed.
   - The leftover slot record lists the push's slot for the prefix, marked as a label-source push: Ze's own push is taken back by a replace of that slot; the listing leaves the leftover record, and the prefix leaves `retained` once no listing of it remains.
   - The leftover slot record lists the push's slot for the prefix, not marked as a push: refused without a kernel write, with an error that wraps `EEXIST` and says the slot holds a route the previous run left for the system RIB. It may be a route BGP retained, and RFC 4724 Section 4.1 keeps it until BGP's route selection completes. `fib-kernel` notes that a replay is owed after the sweep.
   - Otherwise: an exclusive add. A route in the slot, the system RIB's live one included, refuses it with `EEXIST`. When the add succeeds into a slot the system-RIB record holds, the kernel had lost that route, or it would have refused the add (rule 3). The system-RIB record then forgets the prefix (`installed`, `forwarding`), and the change it held is parked on the pending retry (`trackPendingChangeLocked`) with `fib-sync-failure` raised, so the system RIB's route is reported as not installed and tried again, where the push refuses it like any install into a slot a push holds. A later system-RIB withdraw of the prefix cancels the retry and writes nothing (step 6).
   On success the label-push record holds the entry, and the FEC's bucket is written in the batch's third pass. `f.mplsInstalled` is neither read nor written.
3. **Push removal** (`delMPLSEntryLocked`, table 0). The label-push record holds the FEC for that source: the FEC leaves the store in the batch's first pass, the delete names the push's slot and is checked against the kernel (rule 4), and the record forgets the FEC when the kernel removed the route or answered that none is there. A delete the kernel refuses keeps the record, so the third pass, written from the records, puts the FEC back in the store. A leftover at the push's slot marked as that source's push is removed the same way. Otherwise nothing is written and the removal is acknowledged, as a swap or pop removal of an in-label nobody installed already is.
4. **Swap or pop add** (`addMPLSEntryLocked`). In order:
   - The in-label is in `f.mplsSwaps`: as today.
   - The in-label is in the stale in-label record with the applying source as its saved source: the backend is asked to replace, `mplsSwapOwned` checks the kernel again, and on success the in-label leaves the stale record and belongs to the source.
   - The in-label is in the stale in-label record with another saved source: refused with the error a live in-label of another source gets today, and a replay is owed after the sweep.
   - The in-label is in the stale in-label record with no saved source: refused without a kernel write, with an error that wraps `EEXIST` and names the report of step 1.
   - Otherwise: the source is saved in the batch's first pass, then the add is exclusive. When the kernel refuses it, `f.mplsSwaps` does not take the in-label, so the third pass, written from the records, removes the saved pair again.
   A removal, and `ActionRemoveLabelSource`, treat a stale in-label saved for the source as that source's own: it is removed through `delMPLSSwap` and forgotten in the store.
5. **System-RIB install or replace** (`programRouteLocked`). `ownsSlotLocked` answers for the target slot (prefix, table, slot priority). It is false when the label-push record holds that slot. Otherwise it is true when the system-RIB record holds the prefix in that slot, when the leftover slot record lists that slot, marked as a label-source push or not, or when the superseded record lists that table. The write at the target slot is a replace only when the answer is true; otherwise it is an exclusive add, whatever sits there, and a live push refuses it with `EEXIST` as it does today. Two cases touch the label-source record. When the listing the install replaces is marked as a push, the mark leaves the store and the leftover slot record in the batch's first pass, before the write, so the store never names as a push a slot the system RIB's route holds; if the kernel then installs nothing, `recordInstalledLocked` does not run and the listing stays, unmarked, which is the safe side, and after a partial apply it forgets the listing as after a clean install. When the target slot is the push's slot of a FEC the label-push record holds, the FEC leaves the store in the batch's first pass too, before the exclusive add is written (rule 3). When the kernel makes that add, it had lost the push, and the record forgets the FEC in `recordInstalledLocked`, which `programRouteLocked` calls on every install the kernel made: a clean one, one whose `cleanupAfterInstallLocked` then fails and makes `programRouteLocked` return `"delete"` with the cleanup error, and a partial apply, `*supersededDeleteError`, where the write succeeded and a cleanup `RouteDel` failed. The store already holds no push for it, and an error `programRouteLocked` returns after the write does not bring it back. When the kernel installs nothing, refusing the add with `EEXIST` because the live push holds the slot or failing it with any other error before the route is written, `recordInstalledLocked` does not run, the record keeps the FEC, and the third pass writes it back (rule 3). `processEvent` parks the change whenever `programRouteLocked` returned an error, whether the kernel installed the route or nothing, and the retry follows the same rule. A crash anywhere in that batch leaves the store naming no push for the slot, so the next run never reads the system RIB's route there as a push. The cleanup after the write deletes only the other slot priorities the system RIB's own records list for the prefix in that table: the previous metric of a metric change, the superseded listings, and the leftover listings that are not at the push's slot. A leftover at the push's slot is never in the cleanup set, marked or not (C-2, (a)). `recordInstalledLocked` forgets the listings the install took, through `forgetStaleTableLocked`, and keeps a listing at the push's slot that the install did not target: it stays in `staleTables` and in the leftover slot record, so the sweep removes it if no owner takes it back.
6. **System-RIB withdraw** (`processEvent`, `delChange`). The delete names the table and slot priority of the route the system-RIB record holds. For a prefix the system RIB did not install this run, it names each leftover listing of that table that is not at the push's slot. A leftover at the push's slot is never deleted by a withdraw, marked or not, for the reason step 5 leaves it out of the cleanup. A withdraw of a prefix neither record holds writes nothing. `f.mplsInstalled` is cleared as today, which no longer touches the push.

   One rule covers steps 5 and 6: a leftover at the push's slot leaves the kernel only when it is taken back in place (by the system RIB's install at exactly that slot, or by a label source through step 2 when the store names it as a push), or when the sweep or the stop flush runs. No install at another priority and no withdraw removes it. A previous run's push therefore forwards until one of the two owners takes its slot. A route BGP retained in that slot is safe from every label source and from every system-RIB install at another priority. A system-RIB install at exactly that slot replaces it, before BGP's selection completes too, when the system RIB selects another protocol's route for the prefix at that metric (Known limits). This rule is the departure from `core-design.md`, "FIB Kernel", that C-2 puts to Thomas, and the design is written for (a), keep it. If he picks (b), the push's slot gets no exception: an install's cleanup set holds every other listing of the table, at the push's slot too, and a withdraw of a prefix the system RIB did not install this run deletes every listing of the table, as today; a marked listing leaves the store in the first pass before its delete; and the removal of a marked listing by an install or a withdraw notes a replay owed, so the label replay after the sweep (step 7) installs the push again when its source has not applied it before. AC-10's "the push forwards throughout" then holds only when the label source applies before the system RIB, and AC-10 is rewritten to the outcome of (b).
7. **Sweep** (`sweepStale`, under `f.mu` for its whole body, after `SelectionComplete` or the delay, as `waitAndSweepStale` decides today). The sweep is one batch for the store. In its first pass every remaining listing marked as a push leaves the store. Each remaining IP listing is then deleted by its table and slot priority; a marked listing whose delete the kernel refuses stays in the leftover slot record, marked, so the third pass, written from the records, names it again. Each remaining stale in-label that has a saved source is removed through `delMPLSSwap`, for that source, and leaves the store in the third pass, after its delete; one with no saved source stays, as step 1 reported. Failures of both kinds are raised once under `doctor-fib-sweep-incomplete`. When it removed an IP leftover the sweep wakes the pending retry (`wakeRetryLoop`), so a system-RIB install refused over that leftover is tried again. `sweepStale` emits no event: it holds `f.mu` for its whole body, and a label source answers a replay request synchronously into `handleMPLSEntry`, which takes `f.mu`. After `sweepStale` has returned, `waitAndSweepStale` emits one `(mpls-fib, replay-request)` with `fib-kernel`'s token when a replay is owed, and the sources apply again what they want: an entry refused over a leftover that is now gone installs, and an entry `fib-kernel` already holds is acknowledged (a push without a kernel write).
8. **Stop flush** (`flushRoutes`). Beside today's set it removes each route of the label-push record by its slot, each in-label of `f.mplsSwaps` and each stale in-label that has a saved source, and forgets them in the records and in the store: the pushes in its first pass, before their deletes, the in-labels in its third pass, after theirs. A stale in-label with no saved source stays and is counted in the `doctor-fib-flush-incomplete` report. A stop with `flush-on-stop` false removes nothing and writes the dirty buckets once.
9. **Monitor** (`handleExternalChange`). The slot of the event and of the recorded change comes from the one slot priority function. A removal notification of a protocol-250 route is matched against the system-RIB record as today. When it does not match, and its prefix, table and priority are the push's slot of a FEC the label-push record holds, the push is written again from the recorded entry through the checked replace a relabel uses. A queued notification of an older delete in that slot then finds the push in place and rewrites it unchanged, and an empty slot gets an exclusive add. That write hands the backend no other priority to clean up, so an error from it means the kernel wrote nothing in the slot. When the kernel refuses it, as it does while the device is gone, the FEC leaves the store and then the record, the failure is logged and published through `(fib, external-change)` as a failed reassertion, and a later apply of the push by its source is an exclusive add. A `RouteEvent` carries no encapsulation, so the monitor decides from the records and the kernel's answer, never from what the removed route looked like.

## Design presentation

### What changes
- `fib-kernel` keeps one record per owner (the system RIB's, and a new one for label-source pushes beside the existing one for swaps and pops) and names table and priority on every kernel write.
- It saves the two label-source records in the plugin state store, so after a restart it knows which leftover was a label source's push, and which source held each in-label. A label source takes back only what the store names as its own, whatever the order in which the owners apply; the system RIB takes back any IP leftover in the slot it installs into, as today. What nobody takes back is swept after BGP's route selection, label entries included, and the label sources are then asked once to apply again what a leftover had refused.
- A route BGP retained across the restart is never replaced by a label source (RFC 4724 Section 4.1).
- The saved record is kept true when the kernel removes a push on its own, and through a crash at any point. A push leaves the store before its kernel delete and before a system-RIB install into its slot, and comes back only when the record still holds it after the kernel answered, so never after a system-RIB install the kernel made, even one that returned an error; the open drops what the kernel no longer holds; a push is forgotten when the system RIB's route takes its slot; and the monitor puts back a push whose removal the kernel notifies or forgets it when the kernel refuses.
- A previous run's leftover at the push's slot survives a system-RIB install of the prefix at another priority, so a restart keeps labeled forwarding until the label source applies again. `core-design.md` says that install removes it today; that departure is C-2, awaiting Thomas, (a) recommended.
- The store is written once per bucket per batch, and a store that does not answer costs a batch one five-second wait, not one per entry.

### Before and after
- **Before, D-1.** BGP labeled-unicast installs `10.0.0.9/32` with label 300 and no MED, so the kernel holds it at priority 0. LDP then binds the same FEC with label 16. `ip route show 10.0.0.9` shows `encap mpls 16 via <LDP peer> proto 250`; `ze show fib kernel` still lists the BGP route.
- **After.** `ip route show 10.0.0.9` still shows the BGP route with label 300, and `ze show doctor` reports LDP's push for `10.0.0.9/32` as refused under `doctor-fib-mpls-no-writer` with the kernel's `file exists`.
- **Before, the same pair across a restart.** `ze` restarts with `flush-on-stop false` and BGP graceful restart. The kernel still holds the BGP route at priority 0. BGP's best path comes back and the system RIB installs it; LDP then applies its push, and `ip route show 10.0.0.9` shows LDP's label 16 where BGP's label 300 was, as in D-1.
- **After.** While BGP defers its selection, `ip route show 10.0.0.9` shows the route the previous run left, label 300, whether or not LDP has applied its push: the store does not name that route as a push, so LDP's push is refused. When BGP has selected, the system RIB replaces the leftover with the same route. `ze show doctor` reports LDP's push as refused, as before the restart. Had BGP not selected the route again, the sweep would remove it after selection and LDP's push would install from the replay.
- **Before, a design that hands a leftover to the first owner that applies** (the version of this spec its first judge refused). In the same restart LDP applies first, because BGP is still deferring. The leftover is replaced by LDP's push, the prefix forwards with label 16 where the previous run forwarded it with label 300, and BGP's install is then refused: the forwarding state RFC 4724 Section 4.1 requires Ze to retain is lost.
- **Before, D-2.** A static route holds `10.0.0.9/32`. LDP's push for it is refused, and LDP later withdraws the binding. `ip route show 10.0.0.9` is empty.
- **After.** The static route is still there.
- **Before, D-3.** OSPF holds `10.0.0.9/32` at metric 20 and LDP's push holds it at priority 0. LDP's peer sends a new label. `ip route show 10.0.0.9` shows the push alone; when LDP later goes down the prefix has no route.
- **After.** Both routes are there after the relabel, and the OSPF route forwards when the push goes.
- **Before, a push the kernel flushed (the version of this spec its second judge refused).** LDP's push holds `10.0.0.9/32` through `eth1`. `eth1` is deleted, and the kernel removes the push with it. A static route for `10.0.0.9/32` at metric 0 through `eth2` then installs into the empty slot. LDP's peer sends a new label: the relabel replaces the static route, and `ip route show 10.0.0.9` shows `encap mpls` where the operator's static route was. After a restart the store still names the slot as a push, and LDP takes the static route's leftover.
- **After.** The static route's install makes `fib-kernel` forget the push, in the record and in the store. The relabel is refused with `file exists` and reported by `ze show doctor`, the removal writes nothing, and `ip route show 10.0.0.9` shows the static route throughout, after a restart too.
- **Before, D-4 and D-5.** `ze` restarts with `flush-on-stop false`. `ze show doctor` reports every LDP label as refused with `file exists` while `ip -f mpls route` shows them forwarding; a label LDP dropped during the restart forwards for ever.
- **After.** No refused label entry; the dropped label is gone after `sweep-delay`. An in-label RSVP-TE held before the restart refuses LDP after it, as it did before.

### Alternatives set aside
- **Decide leftover ownership with the push recogniser** (move `pushEntryFromRoute` to `internal/core/mplsfib`, mark each listed route push or IP, reclaim a push only over a push). Set aside: a labeled system-RIB route is also a protocol-250 route with an MPLS encap, so the recogniser cannot tell the owners apart, which is the seventh judge's finding on `spec-fib-dummy.md`.
- **Hand a leftover to the first owner that applies** (the first version of this spec). Set aside by the RFC: a BGP route without MED sits in the push's slot, BGP defers its selection after a restart, so a label source applies first and replaces the route RFC 4724 Section 4.1 says to retain. It also let LDP take RSVP-TE's in-label, which `mpls-kernel.md` forbids.
- **Take back only a leftover identical to the entry applied, and save nothing.** An identical entry needs no kernel write, so nothing is replaced and no page is strained. Set aside: a source whose entry changed across the restart (another out-label, another next hop, an in-label now bound to another FEC) is refused until the sweep, which waits for BGP's deferral, and the kernel forwards the old entry for all that time while the source has already advertised the new one.
- **Sweep an in-label that has no saved source**, as `fib-vpp` sweeps every leftover. It would heal a lost store without the operator. Set aside: `mpls-kernel.md` says "A replacement or withdrawal must match the recorded source", and there is none to match; it would be a departure for a case only a lost store produces (R-7).
- **Refuse a system-RIB install over a leftover saved as a push**, so the slot stays with the push across the restart whatever the order (the second version of this spec). Set aside: `core-design.md`, "FIB Kernel", says a stale route "stays one of Ze's own" and "an install of the prefix into that table replaces it instead of being refused by it". No RFC and no page asks for the refusal, and a fresh box gives the slot to the first owner that installs, so the restart now does the same for a push's leftover.
- **Remove a push from the store after its kernel delete** (the second version). Set aside: a crash between the two leaves the store naming a slot with no push, which the system RIB's route can fill.
- **Forget a push on a notified removal without writing it again.** Simpler by one kernel write. Set aside: the monitor already puts back a system-RIB route an operator or another program deleted, and a push deleted the same way would stay gone while its source still advertises the label.
- **Save every push before its kernel write**, as an in-label is saved. Set aside: a crash between the save and a refused add would leave the store naming as a push a slot the system RIB's route holds, and the next run would hand BGP's retained route to a label source.
- **A different `rtm_protocol` for label-source pushes.** It would let the kernel tell the owners apart and survive a restart with no store, and it cannot tell one label source from another without a number for each. Set aside: `ai/doors/forwarding.md` and `internal/core/rtproto` give `fib-kernel` one protocol number that every reader of the kernel (the monitor, `show mpls forwarding`, the doctor fixes, operators' scripts) filters on, and a second number is a wider contract change than the defects need.
- **Refuse a push from a second label source for a FEC another source holds**, as swap and pop do. Set aside here: it decides which source wins a FEC, which is a preference between label protocols and not a defect of ownership.
- **Keep the kernel write for an identical push.** Simpler, and harmless once the cleanup is exact. Set aside: the targeted replay `spec-fib-dummy.md` adds re-sends every push a writer already holds from the applies that arrived between its subscription and the replay, and each would be a kernel write and a lookup for nothing.

### Documents departed from
**`docs/architecture/core-design.md`, "FIB Kernel": "an install of the prefix into that table replaces it instead of being refused by it."** The page, and `replaceOwnedRoute` with `forgetStaleTableLocked` today, let a system-RIB install of a prefix into a table take every leftover startup listed in that table, at every priority. The design keeps that except for a leftover at the push's slot, which an install at another priority leaves in place (Data Flow steps 5 and 6). This departure waits for Thomas as C-2, (a) recommended.

    10.0.0.9  encap mpls  16 via 192.0.2.2 dev eth1 proto 250

      $ ip route show 10.0.0.9
      10.0.0.9 via 192.0.2.2 dev eth1 proto 250 metric 20
      $ ip -f mpls route show
      17 as to 16 via inet 192.0.2.2 dev eth1 proto 250

  Traffic for the FEC leaves unlabeled over the OSPF route until LDP applies its push again; transit traffic arriving with label 17 is still swapped, because the install touches no AF_MPLS entry.
- **After (the design, C-2 (a)).** The install replaces the metric-20 leftover in place and leaves the push, so both commands print what they printed at open, and the FEC forwards labeled throughout. When LDP applies its push, step 2 takes the leftover back by replace (the store names it as LDP's push); had LDP stopped binding the FEC, the sweep removes the push after BGP's selection completes or `sweep-delay` passes.

The page is edited in the same work to state that rule (Files to Modify). With (b) this departure is dropped, the row in Design documents becomes `agrees`, and the page sentence stays as written.

The first version of this spec departed from `docs/architecture/mpls/mpls-kernel.md`, "Constraint: the push shares the FIB with other writers", in two places, and this version removes both departures:

- "Only a genuine relabel of Ze's own push uses `RouteReplace`." The first version let a push replace any protocol-250 route the previous run left in the push's slot, without knowing whose it was. This version replaces such a leftover only when the saved record names it as a label-source push, so the route replaced is Ze's own push by record.
- "A replacement or withdrawal must match the recorded source." The first version let any source replace a leftover in-label and let the sweep remove one nobody had recorded. This version saves the source, lets only that source replace or withdraw, and leaves an in-label with no saved source alone.

The second version departed from `docs/architecture/core-design.md`, "FIB Kernel", without a `departs` row, and this version removes that part of the departure:

- "an install of the prefix into that table replaces it instead of being refused by it." The second version refused a system-RIB install over a leftover the store named as a push. This version lets the install at that slot replace it, after the mark left the store. Only the leftover kept through an install at another priority, above, still departs from the sentence. What that costs is stated in the Task section: a leftover saved as a push goes to the first owner that applies, as the slot of a fresh box does. RFC 4724 Section 4.1 and `mpls-kernel.md` are unaffected, because they protect a system-RIB or BGP route from a label source, and that rule is unchanged.

Both pages are still edited in the same work. `mpls-kernel.md` does not say today that the records are saved, how the saved record is kept true, that a label source takes back only its recorded own, or that `fib-kernel` asks for a replay after its sweep. `core-design.md` states the delete key by table, and it gains the priority; with C-2 (a) its leftover sentence becomes the rule above (Files to Modify).

## Known limits

- Which label source's push holds a FEC two sources bind stays "last applied", as today.
- A push the kernel removed without a notification is not put back by an identical re-apply: `fib-kernel` learns of it only at the next relabel, removal or install into that slot (R-3, A-6).
- The label replay at open, which makes a reload-started `fib-kernel` receive the sources' entries, is `plan/release/features/spec-fib-dummy.md` AC-21. This spec asks for a replay only after its sweep, and builds the token and the emit that request reuses.
- An in-label the store names no source for stays in the kernel until the operator removes it with the command the report gives (R-7). Only a lost, unreadable or unwritable store produces one.
- During BGP's selection deferral the system RIB still programs an IGP route for a prefix BGP retained, and its install replaces the retained route at the same priority or removes it at any other priority except, with C-2 (a), the push's slot, against RFC4724-4.1-1; this spec does not fix that, `spec-bgp-graceful-restart-rfc-defects.md` D7 does (journal row in `plan/journal/reconciler-claims-state-another-owner-installed.md` dated 2026-11-24, `reselectDeferredFamily`).
