## Task

The subscriber PPP control plane (`internal/component/l2tp/ppp`) ties the life of
the PPP link to the life of its NCPs. Four defects were confirmed at the producer
on 2026-10-28. The tree was re-read on 2026-11-20: part of the work has landed
through other commits, and this spec owns what remains. Each defect, with what
is still true today:

1. **One NCP going down killed the session.** Fixed in the tree: `handleNCPPacket`
   (`ncp.go`) no longer calls `fail` on Closed or Stopped, `ncpsComplete` counts
   Closed and Stopped as settled, and `TestNCPClosingOneFamilyPreservesOtherFamily`
   and `TestNCPTerminationGracePreservesIndependentFamily` prove one family's close
   leaves the other. **Remaining:** nothing bounds a link whose last NCP has
   finished. If both enabled NCPs settle in Closed or Stopped during the NCP phase,
   `runNCPPhase` returns true and `afterLCPOpen` emits `EventSessionUp` for a
   session with no network protocol. After session-up, the last open NCP reaching
   Stopped leaves LCP Opened for ever. RFC 1661 Section 3.7 forbids closing the
   link for that alone ("Conversely, the fact that one NCP has Closed is not
   sufficient reason to cause the termination of the PPP link, even if that NCP
   was the only NCP currently in the Opened state."). The same section names "the
   expiration of an idle-period timer" as a reason to terminate. The rule this
   spec sets is split between the NCP phase and the time after it. The NCP
   phase is every run of `runNCPPhase`: the first one, and the rerun after an
   LCP renegotiation of a session that was up. "After session-up" means the
   `run` loop outside the NCP phase. `EventSessionUp` is emitted only when at
   least one enabled NCP is Opened when the NCP phase settles. An NCP that opened
   and finished before the phase settled does not count: if IPv6CP opens and is
   terminated in the NCP phase, then IPCP reaches Stopped by Max-Configure, no
   NCP is Opened, so no `EventSessionUp` is emitted. The rule counts enabled NCPs only: a
   pool-declined or config-disabled family counts as never enabled, and a session
   whose configuration enables no NCP is outside the rule, a configuration choice
   rather than an NCP finishing, so `runNCPPhase` still returns at once with no NCP
   packet sent, as today. "Finished" means Stopped, Closed, or stopped by
   Protocol-Reject (the per-family rejected record); an NCP in Stopping or
   Closing has not finished yet, and neither has one in Req-Sent, Ack-Rcvd or
   Ack-Sent. An enabled NCP in Initial or Starting without the Protocol-Reject
   record is neither finished nor negotiating: that state is only transient,
   before its Open event or after LCP down. In the NCP phase, an NCP finishing
   does not end the phase while another negotiates. One rule bounds a
   session with no network protocol, in the NCP phase and after session-up: the no-NCP
   bound (`ipTimeout`: `ncp timeout` on L2TP; the fixed `defaultIPTimeout`,
   30 s, on PPPoE). It is armed at the moment the session enters "no enabled
   NCP is Opened": at the start of the NCP phase, or when the last Opened NCP
   leaves Opened for any reason (a peer Terminate-Request, a renegotiation the
   peer starts with a Configure-Request, a Protocol-Reject), and it is measured
   from that moment whatever follows (Naks, Max-Configure exhausted). While no
   enabled NCP is Opened it is never stopped or reset, whatever the families do
   (negotiating, answering Naks, Stopping, Closing, finished or rejected). An
   NCP reaching Opened cancels it. Today `runNCPPhase` (`ncp.go`) stops its
   convergence timer whenever no family negotiates and Resets it for each
   resumed Configure lifetime, so when IPv6CP opens and the peer terminates it
   (Stopping) while IPCP reaches Stopped by Max-Configure, the convergence timer
   stops. The phase still settles: the Terminate-Request from Opened ran zrc
   (`performNCPAction`, `LCPActZRC`), the IPv6CP Restart timer keeps running in
   Stopping (`applyNCPTransition`), `runNCPPhase` handles its expiry
   (`ncpRestartChannel`), TO- takes IPv6CP to Stopped, `ncpsComplete` holds,
   and `afterLCPOpen` emits `EventSessionUp` with no NCP Opened. The session
   then stays in the `run` loop with LCP up and no NCP for ever. After
   session-up nothing bounds it at all: an NCP renegotiating with a peer that keeps
   sending Naks (each valid Nak runs irc) keeps LCP up with no NCP Opened for
   ever. While some enabled NCP is Opened the bound is not armed and today's
   per-family behaviour is unchanged: in the NCP phase, each resumed
   Configure lifetime gets a fresh convergence bound, disabled while only
   termination grace remains beside the Opened family; after session-up, the
   families' Restart timers alone. While no NCP is Opened (every NCP finished,
   whether or not one opened earlier, as in the IPv6CP-then-IPCP case above,
   or one still negotiating, Stopping or Closing), LCP stays up and a reopen to
   Opened cancels the bound: in the NCP phase the phase then settles with an
   Opened NCP and the session comes up, or, while the other family's initial
   negotiation is still pending, keeps running under today's convergence
   bound. That bound is not restarted by the cancel: today `runNCPPhase` arms
   one timer when initial negotiation becomes pending (`timer.Reset` runs only
   while `convergence` is nil) and a family reaching Opened neither stops nor
   Resets it, so the still-negotiating family keeps the deadline measured from
   that arm time, and this spec keeps that. On expiry in the NCP phase the
   session ends through today's `fail` path (`session_run.go`):
   `EventSessionDown` with NAS Error and no LCP Terminate-Request (AC-12). On
   expiry after session-up Ze runs LCP Close, which sends an LCP
   Terminate-Request, and the session ends with `EventSessionDown`, cause Idle
   Timeout (AC-6): RFC 1661 Section 3.7 "the expiration of an idle-period
   timer" covers it, because the link carries no network protocol while no NCP
   is Opened.
2. **No NCP Restart timer.** Fixed in the tree: `ncp_restart.go` (`ncpRestart`,
   `armNCPRestartTimer`, `handleNCPRestartTimeout`) gives each family its own timer
   and counter from the admitted `LCPConfig`, dispatched from `runNCPPhase` and the
   `run` loop. **Remaining:** no test proves Configure-Request retransmission and
   TO- after Max-Configure (AC-7).
3. **Protocol-Reject naming IPCP or IPv6CP is ignored.** Still true: `codeToEvent`
   (`session_run.go`) maps an LCP Protocol-Reject to RXJ+, which is correct for the
   LCP automaton, but nothing reads the Rejected-Protocol field, so the named NCP
   is never stopped and Protocol-Reject outside LCP Opened is not discarded. An
   IPv4-only CPE (pppd with `noipv6`: pppd 2.5.5 runs IPv6CP by default) under a dual-stack pool keeps receiving
   IPv6CP Configure-Requests until that family's Max-Configure is spent. Ze ships no
   dual-stack pool today: the only registered pool handler, `poolPlugin.handle`
   (`plugins/pool/register.go`), declines every IPv6 request ("IPv6 not supported by
   static pool"), `runNCPPhase` then sets `disableIPv6CP`, and IPv6CP never starts.
   On a shipped Ze the defect is therefore reached through IPCP: a CPE that runs no
   IPv4 (pppd with `noip`) Protocol-Rejects IPCP and keeps receiving IPCP
   Configure-Requests.
4. **After session-up the unit descriptor was never read.** Mostly fixed in the
   tree: `readUnitFrames` (`session_run.go`) is the session's one unit reader,
   woken by `wakeUnitReader` after `PPPIOCCONNECT` and drained by
   `awaitUnitDrained`, and its frames reach `handleFrame` from the `run` loop
   (`TestUnitDescriptorNCPFramesAreHandled`; the `ppp-code-reject-xl2tpd` interop
   scenario has Ze answer an IPCP Terminate-Request from the unit). TLD on an NCP
   runs `withdrawNCPFamily`, which removes the IPv4 framed routes and address or
   stops the IPv6 service, and the kernel handle's `RemoveAddress` sets that
   family's NP mode to drop first (`kernel/session.go`, `dropOriginalNativeFamily`).
   **Remaining:** the withdrawal never reaches the transports. No per-family
   event exists in `ppp.Event`, the L2TP events or the subscriber events, and the
   route observer (`route_observer.go`) removes a session's routes only per
   network lifetime, on session-down or LCP-down, so after an IPCP close the
   redistributed /32 and the IPv4 framed routes stay announced, and after an
   IPv6CP close the IPv6 framed routes (Framed-IPv6-Route) stay announced. There is
   no IPv6 host route: IPv6CP negotiates only an interface identifier, and both
   IP-assigned handlers (`subscriber_bridge.go` `onSessionIPAssigned`,
   `pppoe/subsystem.go` `onSessionIPAssigned`) pass only an IPv4 peer. The framed
   routes of both families travel as one list: `authradius/extract.go`
   `extractFramedRoutes` puts Framed-Route and Framed-IPv6-Route into the same
   `FramedRoutes`, `reactor_kernel.go` carries it on the IP-assigned notice, and
   the observer's `assign` emits the whole list once, under one `framedEmitted`
   flag, through `emitFramedRoutes` (IPv4 and IPv6 unicast batches). `assign`
   returns on an invalid address, so an IPv6-only session never emits its IPv6
   framed routes: a defect fixed here. No test drives the unit reader
   through `run` to its exit (AC-11), and no test answers an unknown protocol read
   from the unit (AC-9).

A small visibility gap found in this work, fixed here: no command prints the
subscriber registry's IPv6 interface identifier. `subscriber.Session.IPv6InterfaceID`
is written (`subscriber_bridge.go` and `pppoe/subsystem.go` `onSessionIPAssigned`)
and read by no command, so neither an operator nor a test can see the IPv6 family
leave or return. `show subscriber id <id> detail` (`sessionFull`,
`subscriber/cmd/subscriber.go`) gains an `ipv6-interface-id` field beside `ipv4`,
read from the registry entry, written as 16 uppercase hex digits with no `0x` (the
raw-hex rule of `ai/rules/cli.md`), and omitted while the identifier is zero, as
`ipv4` is omitted while unset. `show l2tp sessions` does not read the registry:
it prints `assigned-addr` and `family` from the L2TP session's own `assignedAddr`,
which holds IPv4 only (`reactor_kernel.go`).

A second small defect found in this work, fixed here: PPPoE's `handlePPPEvent`
(`pppoe/subsystem.go`) is a type switch with no default arm, so a `ppp.Event`
type it has no case for is dropped with no log line. Of the seven `ppp.Event`
types (`events.go`: `EventLCPUp`, `EventLCPDown`, `EventSessionUp`,
`EventSessionIPAssigned`, `EventSessionDown`, `EventEchoRTT`,
`EventSessionRejected`), the switch has a case for all but `EventEchoRTT`,
which PPPoE deliberately ignores: the session loop emits one per LCP
Echo-Reply (`session_run.go`), and only the L2TP reactor relays it, for CQM.
This spec adds a `ppp.Event` type, so a consumer that misses one must be
visible. PPPoE's switch therefore gains an explicit no-op case for each event
it deliberately ignores, today `EventEchoRTT` alone, so that a default arm
cannot fire once per Echo-Reply per session, and a default arm for every other
type. The arm reports a defect in Ze's own code in the shape the L2TP reactor
uses for one (`reactor_kernel.go` `handleSessionIPAssigned`, its
counter-capture refusal): a Warn that names the event's Go type
(`fmt.Sprintf("%T", ev)`) and carries `code` `diagnostic.CodeDoctorInternalDefect`
and `fix` `ze show doctor`, beside `report.RaiseWarningFix(SubsystemName,
diagnostic.CodeDoctorInternalDefect, ...)` with the same fix and the type in its
detail; then it ignores the event. That code has a registered doctor check
(`diagnostic.Lookup` answers for it, `assignment_counter_diagnostic_test.go`),
which `ai/rules/user-facing-errors.md` asks of every Warn. The reactor's own
unknown-event fallback (`reactor_kernel.go` `handlePPPEvent`, "l2tp: unknown
ppp.Event type ignored; handlePPPEvent needs an updated switch") is a bare
`r.logger.Warn` with a `type` attribute, no doctor code and no report, so it is
not the shape copied here. `TestPPPoEUnknownEventIsLogged` guards both the
no-op case and the arm (AC-13).

Goal: an NCP opens and closes independently of the others for the whole life of
the session, as RFC 1661 Section 3.6 allows; the kernel, the redistribution
feed (IPv4: the /32 and the IPv4 framed routes; IPv6: the Framed-IPv6-Route
prefixes), the subscriber registry and RADIUS accounting hold exactly the families
that are open; and a session with no enabled NCP Opened stays up for one
no-NCP bound (`ncp timeout` on L2TP; the fixed `defaultIPTimeout`, 30 s, on
PPPoE), armed at the start of the NCP phase or when the last Opened NCP leaves
Opened, never stopped or reset while no enabled NCP is Opened, and cancelled by
an NCP reaching Opened; at its expiry a session that came up ends with Idle
Timeout, and one still in the NCP phase ends with NAS Error. Thomas's test of the result is Ze
as an L2TP LNS on his home line's case, an IPv4-only Ze against a CPE that offers
IPv6CP (stock pppd 2.5.5): Ze Protocol-Rejects the IPv6CP, the CPE parks it, the
session stays up on IPv4 past `ncp timeout`, and the CCP the CPE sends is
Protocol-Rejected because Ze runs no CCP. Ze ships no dual-stack pool (Task, 3),
so the IPv6 behaviour of this spec is proven by unit tests with a test handler
that accepts IPv6, and its interop proof belongs to
`plan/post-release/features/spec-l2tp-ipv6-subscriber.md` (Thomas's decision, C-3).

**Key insights:**
- Kernel proof for defect 4, Linux 7.2.9 `drivers/net/ppp/ppp_generic.c`, fetched from `git.kernel.org` stable tag `v7.2.9`: `ppp_input` puts a frame on the channel's own queue only when the channel has no unit, or the protocol is 0xc000 or above, or it is CCP fragment; every other frame goes to `ppp_do_recv`. `ppp_receive_nonmp_frame` then looks up the protocol's network-protocol index and, when there is none, queues the frame on the unit's file queue ("control or unknown frame - pass it to pppd"). `proto_to_npindex` maps only PPP_IP, PPP_IPV6, PPP_IPX, PPP_AT and the MPLS protocols, so IPCP (0x8021), IPv6CP (0x8057) and CCP (0x80fd) land on the unit fd, LCP (0xc021) and the auth protocols stay on the channel fd. The `readUnitFrames` and `pppSession` comments cite the same two functions at v6.12.
- Kernel transmit gate: `PPPIOCSNPMODE` sets the per-protocol NP mode of the unit; the kernel handle already drives it (`kernel/session.go` `Connect`, `familyMode`, `RemoveAddress`; `kernel/session_ops.go` `setIPv4Mode`, `setIPv6Mode`).
- RFC 1661 Section 3.7 decides the last-NCP case, so pppd is not consulted for it. The Implementation Note: "Conversely, the fact that one NCP has Closed is not sufficient reason to cause the termination of the PPP link, even if that NCP was the only NCP currently in the Opened state." The section's opening: "This might happen because of the loss of carrier, authentication failure, link quality failure, the expiration of an idle-period timer, or the administrative closing of the link."
- pppd reference, set aside for the last-NCP case: `np_finished` (`pppd/auth.c`, v2.5.5) closes LCP at once when the count of open network protocols reaches zero: `if (--num_np_open <= 0) {` / `/* no further use for the link: shut up shop. */` / `lcp_close(0, "No network protocols running");`. That contradicts the Section 3.7 note.
- pppd reference, still followed where the RFC is silent: `ipcp_down` (`pppd/ipcp.c`) sets the IPv4 NP mode to `NPMODE_DROP` and clears the addresses; the link stays up. `lcp_rprotrej` (`pppd/lcp.c`) dispatches the rejected protocol to that protocol's `protrej` routine, and `ipcp_protrej` lowers only the IPCP automaton. These come from the 2026-10-28 planning read and are re-read at the lab's pin, pppd 2.5.5, and quoted before coding (Thomas's brief).
- accel-ppp-ng reference: commit `d62d8aa` stops terminating the session on an IPv6CP Terminate-Request unless `ipv6=require`, citing RFC 1661 Section 3.7, and `ipv6cp_recv_proto_rej` (`accel-pppd/ppp/ppp_ipv6cp.c`) runs `ppp_fsm_lower_down` then `ppp_fsm_close` on the IPv6CP automaton alone. accel-ppp still ends the session on an IPCP Terminate-Request (`ipcp_recv`, `ppp_ipcp.c`): an asymmetry the RFC note does not support, so Ze follows pppd's symmetric rule. accel-ppp holds the IPv4 lease for the session (`alloc_ip` in `ipcp_opt_ipaddr.c`, released by `ap_session_finished` in `session.c`), not for the NCP.
- The L2TP lab already injects PPP into a live session: the relay (`internal/le/interoplab/l2tp/avprelay`) sits between xl2tpd and Ze, takes the tunnel and session header from the next LAC datagram after a marker file appears, and sends Ze a PPP frame built by `pppFrameBehind` (`pppinject.go`), as `ppp-code-reject-xl2tpd` does for an IPCP Terminate-Request.

**Behavior to preserve:**
- A pool handler declining IPv6 drops IPv6CP before it starts and Protocol-Rejects the peer's IPv6CP (`disableIPv6CP`, `rejectUnsupportedProtocol`). Both NCPs config-disabled skips the NCP phase, as today: `runNCPPhase` returns at once and sends no NCP packet. Such a session enables no NCP, so neither the last-NCP rule nor the session-up rule applies to it; both count only enabled NCPs, and a pool-declined or config-disabled family counts as never enabled. `TestRFC1661NoNCPPacketsWhenNoNetworkProtocol` stays unchanged.
- LCP RXJ+ handling of the LCP automaton itself (Opened RXJ+ stays Opened).
- `EventSessionIPAssigned` acknowledgement barrier before forwarding is enabled.
- LCP down (`resetNCP`) withdraws every family, disconnects the channel and waits for the transport's acknowledgement, as today.
- NCP frames are discarded before authentication completes (`ncpStarted` gate), from either descriptor.
- The pool lease lives for the session and is released on session-down.
- One family's close leaves the other family and the link up (landed behaviour).

**Behavior to change:**
- A Protocol-Reject in LCP Opened naming IPCP or IPv6CP is the RFC 1661 Down event for that NCP (Starting, out until LCP renegotiates, as pppd `fsm_lowerdown`), and Ze counts the NCP finished for the NCP-phase settle and the last-NCP rule; one received outside LCP Opened is discarded.
- Framed routes become per family: Framed-Route prefixes belong to the IPv4 family, Framed-IPv6-Route prefixes to the IPv6 family, each with its own emitted record in the observer. Each family's framed routes are emitted when that family is installed (IPv4 on the IPv4 IP-assigned, IPv6 on the IPv6 install, which today never emits them for an IPv6-only session), withdrawn on that family's release and re-added on its reinstall; session-down withdraws whatever each family still has.
- A family's withdrawal (TLD) emits a per-family release that both transports carry to the route observer. For IPv4 the observer removes the /32 and the IPv4 framed routes; for IPv6 it removes the IPv6 framed routes (there is no IPv6 host route). The other family's routes stay.
- The subscriber registry (`subscriber_bridge.go` `onSessionIPAssigned`, `pppoe/subsystem.go` `onSessionIPAssigned`) and RADIUS accounting (`authradius/acct.go` `onSessionIPAssigned` sets `peerAddr`, which `buildAcctPacket` reports as Framed-IP-Address) keep a withdrawn family today. After a release they drop it and regain it on reinstall.
- `EventSessionUp` is emitted only when at least one enabled NCP is Opened when the NCP phase settles. Today `runNCPPhase` returns true once every enabled NCP is settled, Opened or not, so a session whose IPv6CP opened and was terminated in the NCP phase and whose IPCP then reached Stopped by Max-Configure comes up with no NCP Opened. After: no `EventSessionUp`.
- One rule, the no-NCP bound (`ipTimeout`: `ncp timeout` on L2TP, `defaultIPTimeout` 30 s on PPPoE), replaces both today's stop-and-Reset convergence timer while no NCP is Opened and the absence of any bound after session-up. It is armed at the moment the session enters "no enabled NCP is Opened": at the start of the NCP phase, or when the last Opened NCP leaves Opened for any reason (a peer Terminate-Request, a renegotiation by a peer Configure-Request, a Protocol-Reject). While no enabled NCP is Opened it is never stopped or reset, whatever the families do (negotiating, answering Naks, Stopping, Closing, finished or rejected). An NCP reaching Opened cancels it. Today `runNCPPhase` stops its convergence timer whenever no family negotiates and Resets it per resumed Configure lifetime, so IPv6CP Opened then peer-terminated (Stopping) while IPCP reaches Stopped by Max-Configure stops the timer, yet the phase settles: the Terminate-Request from Opened ran zrc (`performNCPAction`, `LCPActZRC`), the IPv6CP Restart timer keeps running in Stopping (`applyNCPTransition`), `runNCPPhase` handles its expiry (`ncpRestartChannel`), TO- reaches Stopped, `ncpsComplete` holds, and `afterLCPOpen` emits `EventSessionUp` with no NCP Opened, after which the `run` loop keeps LCP up with no NCP for ever; and after session-up an NCP that left Opened and renegotiates with a peer that keeps sending Naks (each valid Nak runs irc) is never bounded, which also keeps LCP up with no NCP for ever. While some enabled NCP is Opened the bound is not armed and today's per-family behaviour is unchanged (in the NCP phase, a fresh convergence bound per resumed Configure lifetime, disabled while only termination grace remains beside the Opened family; `TestNCPConvergenceResumesDuringTerminationGrace` stays green, because the bound arms fresh when its IPv6CP leaves Opened and its Nak loop ends inside that bound). Expiry in the NCP phase is today's `fail` path: `EventSessionDown` with NAS Error, no LCP Terminate-Request (AC-12). Expiry after session-up runs LCP Close (Terminate-Request) and the session ends with `EventSessionDown`, cause Idle Timeout (AC-6); RFC 1661 Section 3.7 "the expiration of an idle-period timer" covers it, because the link carries no network protocol while no NCP is Opened. LCP stays Opened until then, and a reopen to Opened before it lets the NCP phase settle with an Opened NCP, or, after session-up, lets the session continue.
- "Finished", which the NCP-phase settle reads, means Stopped, Closed, or stopped by Protocol-Reject (the per-family rejected record); an NCP in Stopping, Closing, Req-Sent, Ack-Rcvd or Ack-Sent has not finished. An enabled NCP in Initial or Starting without the Protocol-Reject record is neither finished nor negotiating: that state is only transient, before its Open event or after LCP down.

## Data Flow (MANDATORY - see `ai/rules/architecture.md`)

### Entry Point
- PPP control frames from the subscriber: on the channel fd before `PPPIOCCONNECT` (all protocols) and after it (protocols at or above 0xc000); on the unit fd after it (protocols below 0xc000 with no network-protocol index).

### Transformation Path
1. Kernel `ppp_input` routes the frame to the channel queue or, through `ppp_receive_nonmp_frame`, to the unit queue.
2. `readFrames` (channel) and `readUnitFrames` (unit) hand owned frame buffers to the session loop (exists).
3. `handleFrame` dispatches by protocol: LCP to `handleLCPPacket`, IPCP and IPv6CP to `handleNCPPacket`, anything else to `rejectUnsupportedProtocol` (exists).
4. `handleLCPPacket`, on a Protocol-Reject in LCP Opened, reads the Rejected-Protocol field and raises the RFC 1661 Down event on the named NCP automaton (to Starting, as pppd `fsm_lowerdown`; from Opened the TLD withdrawal runs first), and sets that family's "rejected by Protocol-Reject" record, which the NCP-phase settle reads to count the NCP finished (its state alone, Starting, does not say it was rejected); outside LCP Opened it discards the packet (new).
5. The NCP automaton's TLD runs `withdrawNCPFamily` (exists) and, on success, emits the per-family release on `EventsOut` (new).
6. The L2TP reactor publishes the L2TP release notice under the session's order ticket and the bridge republishes it as the subscriber release; the PPPoE subsystem publishes the subscriber release directly; the route observer removes that family from its record: for IPv4 the /32 and the IPv4 framed routes, for IPv6 the IPv6 framed routes, and clears that family's emitted record for the reinstall. The IPv6 install notice carries the IPv6 framed routes, and the observer emits them on it even with no IPv4 address (new).
7. The no-NCP bound (`ipTimeout`) is armed when the session enters "no enabled NCP is Opened": by `runNCPPhase` at the phase start, and by `runNCPPhase` or the `run` loop when the last Opened NCP leaves Opened for any reason (Terminate-Request, a renegotiating Configure-Request, Protocol-Reject). While no enabled NCP is Opened it is never stopped or reset, whatever the families do (negotiating, Naks, Stopping, Closing, finished, rejected); an NCP reaching Opened cancels it. While some enabled NCP is Opened it is not armed, and in the NCP phase today's per-lifetime convergence bound applies unchanged: the Opened that cancels the no-NCP bound neither stops nor Resets the convergence timer a still-negotiating family runs under (`runNCPPhase` Resets it only while `convergence` is nil). A reopen to Opened in the NCP phase settles the phase with an Opened NCP and `EventSessionUp` follows. Expiry in the NCP phase: today's `fail` sends `EventSessionDown` with NAS Error and no LCP Terminate-Request (changed). Expiry after session-up: the session records Idle Timeout and runs LCP Close (Terminate-Request), and LCP's existing path ends the session with `EventSessionDown` (new).
8. The release also clears the family in the subscriber registry, and the L2TP release clears the IPv4 `peerAddr` in RADIUS accounting (new).

| Boundary | How | Verified |

### Integration Points
- `handleLCPPacket` - Protocol-Reject dispatch to the named NCP, LCP-Opened gate.
- `performNCPAction` TLD - emits the release after a successful withdrawal.
- `runNCPPhase` / `afterLCPOpen` and the `run` loop - the last-NCP rule.
- `route_observer.go` - a per-family release handler beside `assign` and `withdraw`, and per-family framed-route emission.
- `reactor_kernel.go` / `subscriber_bridge.go` and `pppoe/subsystem.go` - one release case each.

### Interop Tests (Scope: protocol)

All three run in the L2TP lab, `test/interop-l2tp/`, where xl2tpd and pppd 2.5.5 dial Ze's LNS through the transparent relay (`docs/labs/l2tp-interop.md`), and all three run Ze's IPv4-only pool, the only pool Ze ships (Task, 3). Thomas decided the interop proof on 2026-11-20 (C-3): the two IPv6 scenarios an earlier draft planned (`l2tp-lns-ipv4-only-pppd-rejects-ipv6cp`, `l2tp-lns-pppd-ipv6cp-terminate-after-up`) needed a dual-stack pool and move to `plan/post-release/features/spec-l2tp-ipv6-subscriber.md`, and these three IPv4-reachable scenarios replace them. Each scenario directory holds `ze.conf`, `xl2tpd.conf`, `ppp-options` and `README.md`, as `lcp-restart-timer-pppd` does; the redistribute directory also holds its own `frr.conf`, because the FRR peer mounts `frr.conf` from the scenario directory (`frrPeer` in `l2tp.go`), as `02-ppp-bgp-redistribute-frr` does. Each is registered in `register_scenarios.go` through `registerStandardScenario`, but that only names it: `standardScenarioPlan` prepares it through `prepareScenario`, which picks the peers by a switch on the scenario name, and `standardImageBuilds` picks the images the same way. `prepareScenario` refuses a name it does not list ("unsupported L2TP scenario", `l2tp.go`); `standardImageBuilds` refuses nothing, and for an unlisted name it silently omits the relay, FRR and RADIUS images, so the run fails later on a missing image. So each scenario also needs its plan case and its image case in `l2tp.go`. `l2tp-lns-pppd-ipv6cp-rejected-by-lns` and `l2tp-lns-pppd-noip-rejects-ipcp` join the existing relay case beside `ppp-code-reject-xl2tpd` (ze, relay, LAC). All three keep the standard one-LAC topology, so they extend those cases rather than taking a `register_*.go` of their own: `register_scale.go` exists because the scale scenario has its own topology, plan and images (several LACs, kl2tpd), which these do not. None needs the RADIUS peer or an IPv6 sysctl (A-7). The short `ncp timeout` the scenarios need comes from the `ncp timeout` leaf in each scenario's `ze.conf`, not from the lab's `ze.l2tp.ncp.ip-timeout` environment entry (`l2tp.go`), which no product code reads.

## Design presentation

### What changes

An IPCP or IPv6CP that the subscriber closes, Protocol-Rejects or never answers now ends only that family: Ze stops sending it, removes its address from pppN, and keeps the other family and the session up. Framed routes become per family, and each family's routes leave the redistribution feed on its release and return on its reinstall. Thomas's brief said "/32 or /128". For IPv4 that is the /32 host route plus the IPv4 framed routes (Framed-Route). For IPv6 there is no host route, because IPv6CP negotiates only an interface identifier, never an address; the IPv6 routes Ze announces for a subscriber are its Framed-IPv6-Route prefixes, so those are what the IPv6 release withdraws and the reinstall re-adds, beside the address, NP mode and service on pppN. Today both families' framed routes are emitted together once, from the IPv4 assignment, so an IPv6-only session never announces its IPv6 framed routes; that defect is fixed here. A Protocol-Reject naming an NCP is the RFC 1661 Down event for it, as in pppd (`ipcp_protrej`, `ipv6cp_protrej` call `fsm_lowerdown`): the NCP goes to Starting and stays out until LCP renegotiates. Ze counts that NCP finished, where pppd does not (pppd calls `np_finished` only from Closed or Stopped), so an IPv4-only CPE comes up as soon as IPCP opens rather than at `ncp timeout`. Most of the lifetime and the unit reader already landed through other commits; what this spec adds is the Protocol-Reject dispatch, the family release reaching the route observer on both transports, the release reaching the subscriber registry and RADIUS accounting, and one bound on a session with no network protocol. The no-NCP bound (`ncp timeout`) is armed when the session enters "no enabled NCP is Opened": at the start of the NCP phase, or when the last Opened NCP leaves Opened for any reason (a Terminate-Request, a renegotiation the peer starts with a Configure-Request, a Protocol-Reject). While no enabled NCP is Opened it is never stopped or reset, whatever the families do, Naks included; an NCP reaching Opened cancels it. Until it expires LCP stays up, because RFC 1661 Section 3.7 says one NCP closing is not reason to end the link, and a reopen brings the session up, or keeps it going. At its expiry in the NCP phase the session ends with NAS Error through today's `fail`, with no LCP Terminate-Request; after session-up Ze closes LCP (an LCP Terminate-Request) and ends the session with Idle Timeout, the idle-period timer that section names as a reason to terminate. While some enabled NCP is Opened the bound is not armed and today's per-family behaviour applies unchanged. The `ncp timeout` leaf's meaning widens accordingly: it bounds the NCP phase and also how long a session that came up may stay with no NCP open, a description-only change to `ze-l2tp-conf.yang` with no new leaf. An IPv4-only CPE on a dual-stack pool comes up with IPv4 and stays up, and its CCP gets a Protocol-Reject.

Ze ships no dual-stack pool: the only registered pool handler declines IPv6 (`poolPlugin.handle`, "IPv6 not supported by static pool"), so IPv6CP never starts on a shipped Ze. The interop proof therefore runs on Ze's IPv4-only pool, as Thomas decided (C-3). His home-line case is a CPE that offers IPv6CP against that pool: stock pppd 2.5.5 (IPv6CP on by default, so his brief's "no +ipv6" pppd is not IPv4-only), whose IPv6CP Ze Protocol-Rejects while IPv4 stays up, and whose CCP Ze Protocol-Rejects. The CPE rejecting an NCP Ze offers is proven on the wire through IPCP, by pppd `noip`. The IPv6 behaviour of this spec is proven by unit tests with a test handler that accepts IPv6, and its interop scenarios move to `spec-l2tp-ipv6-subscriber`.

### Before and after

1. A CPE that rejects an NCP Ze offers. On a shipped Ze (IPv4-only pool) that is pppd `noip`, which Protocol-Rejects IPCP (`l2tp-lns-pppd-noip-rejects-ipcp`). Before: Ze ignores the named protocol and keeps sending IPCP Configure-Requests until IPCP's Max-Configure is spent. After: the first Protocol-Reject naming 0x8021 stops IPCP; the wire log shows no further IPCP from Ze, no session comes up, and at the no-NCP bound the session ends with NAS Error (CDN). With a dual-stack pool, which Ze does not ship, the same change stops IPv6CP on an IPv4-only pppd (`noipv6`) and keeps IPv4 up; unit tests prove it here. Stock pppd against the IPv4-only pool (`l2tp-lns-pppd-ipv6cp-rejected-by-lns`, Thomas's home-line case) behaves the same before and after: Ze Protocol-Rejects pppd's IPv6CP and its CCP, and IPv4 stays up past `ncp timeout`.
2. Dual-stack subscriber sends IPv6CP Terminate-Request after session-up (unit tests with a test handler that accepts IPv6; on the wire this needs `spec-l2tp-ipv6-subscriber`, and the IPv4 form is `l2tp-lns-pppd-ipcp-terminate-redistribute`, where the `/32` leaves FRR on the IPCP release and returns on the reopen). Before: Ze answers Terminate-Ack, stops the IPv6 service, sets the IPv6 NP mode to drop and removes the IPv6 address from pppN, but emits no release, so the subscriber registry entry keeps the interface identifier (which no command prints today) and a redistribution peer keeps the subscriber's Framed-IPv6-Route prefixes. After: the same withdrawal, plus a release that clears the interface identifier from the subscriber registry, so `show subscriber id <id> detail` loses `ipv6-interface-id` and keeps `ipv4`, and withdraws the Framed-IPv6-Route prefixes from that peer, which keeps the /32 and the IPv4 framed routes; when the subscriber renegotiates IPv6CP, the address and the RA service return on pppN, `show subscriber id <id> detail` prints `ipv6-interface-id` again and the peer holds the Framed-IPv6-Route prefixes again. There is no /128 host route, before or after.
3. Both NCPs finish (IPCP Protocol-Rejected, IPv6CP Terminated). Before: the session reports up with no address, or stays up with LCP Opened and nothing to carry. After, in the NCP phase: no `EventSessionUp`, LCP stays up for a reopen of a Stopped or Closed NCP (the Protocol-Rejected IPCP cannot reopen until LCP renegotiates) until the no-NCP bound, armed at the phase start and never stopped or reset while no enabled NCP is Opened, expires; then the session ends with NAS Error through today's `fail`, with no LCP Terminate-Request. The same holds when an NCP opened and finished before the phase settled: IPv6CP opens and is terminated, then IPCP reaches Stopped by Max-Configure, and the bound runs from IPv6CP leaving Opened. Before: `EventSessionUp` with no NCP Opened, in either ordering: when IPv6CP is still Stopping as IPCP reaches Stopped, the convergence timer stops, but the IPv6CP Restart timer (armed by zrc, kept in Stopping) expires, TO- reaches Stopped, the phase settles and `EventSessionUp` follows; the session then stays up in the `run` loop with LCP Opened and no NCP for ever. After: no NCP is Opened when the phase settles, so no `EventSessionUp`. After, once the session was up: the last Opened NCP leaving Opened arms the bound, and LCP stays up and Echo is answered for one `ncp timeout`, whether the families are finished or still renegotiating (a peer that answers every Configure-Request with a Configure-Nak keeps a family negotiating; before, that held LCP up with no NCP for ever). If the subscriber reopens an NCP to Opened in that time, the session carries on. Otherwise Ze sends an LCP Terminate-Request, the L2TP CDN follows, and the Accounting-Stop carries Acct-Terminate-Cause Idle Timeout.
4. The existing `ppp-code-reject-xl2tpd` interop scenario. Its pppd runs `noipv6` against an IPv4-only pool, so IPCP is its only NCP. The final IPCP Terminate-Request is injected by the relay (`/run/ipcp-terminate`), so pppd never asked to terminate: Ze's Terminate-Ack reaches pppd while its IPCP is Opened, and pppd 2.5.5 `fsm_rtermack` `case OPENED:` runs down, calls `fsm_sconfreq` and enters REQSENT (the shared `fsm.c` path A-6 names for IPv6CP), so pppd renegotiates IPCP. Before: Ze answers the Terminate-Ack and its TLD (`performNCPAction`, `withdrawNCPFamily`) removes the framed routes and the IPv4 address from pppN and sets the IPv4 NP mode to drop (`kernel/session.go` `RemoveAddress` calls `dropOriginalNativeFamily`), but emits no release event, so the redistributed /32 and the subscriber registry's IPv4 address stay; `checkPPPCodeReject` returns once it sees the Terminate-Ack. After: on the Terminate-Request Ze withdraws the IPv4 family as before (address removed, NP mode set to drop) and now also emits the release event, so the /32 is removed and the registry address cleared; pppd renegotiates IPCP, Ze reinstalls the family on Opened (`onNCPOpened`), the session continues, and the no-NCP bound, armed when IPCP leaves Opened, is cancelled by its reopen and never fires, so no idle close happens. The checker is extended to assert the kernel withdrawal and then the reopen rather than stopping at the Terminate-Ack: polling inside the withdrawal window (the IPCP Stopping time before pppd's renegotiation is answered), never one read after a fixed sleep, it sees the IPv4 address leave the Ze container's pppN; then IPCP reaches Opened again on the wire log, the address is back on pppN, and a ping through the session passes.
5. `show subscriber id <id> detail` and RADIUS Interim-Update after an IPCP Terminate on a dual-stack session. Before: both still show the withdrawn IPv4 address (`ipv4`, `dns-primary`, `dns-secondary`). After: the detail prints `ipv6-interface-id` and no IPv4 fields, the Interim-Update carries no Framed-IP-Address, and both return to the address when IPCP reopens.

## Design Insights

- The deferred `PPPIOCCONNECT` (after NCP) means every NCP frame during the NCP phase arrives on the channel fd, so a defect on the unit path is invisible until the session is up.
- The kernel side of a family withdrawal was already right (NP mode dropped before the address goes); what was missing is the transports learning of it, so the redistribution feed and the kernel disagreed.
- A PPP frame the LAC sends without Address and Control can fall below the kernel's 14-octet L2TP data floor and reach the userspace tunnel socket instead of the PPPoL2TP session. The `.ci` fixture peer did exactly this until a3bb822aad, so its NCP frames never reached the session; the reactor's Debug log of a dropped data message now makes the case visible.
- Scenario timing, from the design judge's notes on the phase 5 scenarios: in `l2tp-lns-pppd-noip-rejects-ipcp` the `ncp timeout` (8 s) must exceed one `lcp restart-timer` (2000 ms), so a Ze that ignored the Protocol-Reject retransmits its IPCP Configure-Request before the session ends and the revert walk can show its red; in `l2tp-lns-pppd-ipcp-terminate-redistribute` the `ncp timeout` (20 s) must exceed the `lcp restart-timer` (10000 ms) plus pppd's 3 s IPCP retransmission, because Ze holds IPCP in Stopping for one Restart time and ignores pppd's Configure-Requests until Stopped, so the reopen waits for pppd's next one, and only a bound above both lets the reopen cancel it before a CDN. Each scenario's `README.md` states its own pair.

| Decision | Alternatives Considered | Rationale |

| Main-thread decision, not yet confirmed by Thomas (C-2): one rule, the no-NCP bound (`ncp timeout`), bounds a link with no enabled NCP Opened, in the NCP phase and after session-up. The existing `ncp timeout` serves as that timer, so no leaf is added |
| The no-NCP bound against RFC 1661 Section 3.6: "Because an implementation may initially use a significant amount of time for link quality determination, implementations SHOULD avoid fixed timeouts when waiting for their peers to configure a NCP." On L2TP the bound is the operator-configured `ncp timeout` (`ze-l2tp-conf.yang`), so the wait is not fixed. Recorded as an honest gap in the RFC1661-3.6-4 row of `rfc/short/rfc1661.md` (the row that carries this SHOULD), and as one open row in `plan/journal/schema-omits-a-leaf-the-backend-supports.md`: PPPoE has no `ncp timeout` leaf, though the backend already takes the value (`ipTimeout`) | add a PPPoE `ncp timeout` leaf in this spec; leave RFC1661-3.6-4 unannotated | a new PPPoE config leaf is a feature of its own (YANG, parser, docs, tests) beside a fix spec whose goal does not depend on it; the SHOULD is optional, so it is reported as a gap, never as met, and its row names the configuration each transport runs |

| LCP keeps RXJ+ for a Protocol-Reject of an NCP, and the NCP gets the stop | map to RXJ- | RFC 1661 Section 4.3 names "a Protocol-Reject of a NCP" as RXJ+ for the LCP automaton |
| The named NCP takes the RFC 1661 Section 4.1 Down event: from Opened the withdrawal runs (tld), then Starting; from Stopping, Req-Sent, Ack-Rcvd or Ack-Sent, Starting with the Restart timer cancelled; from Stopped, Starting (tls); from Closed or Closing, Initial; Initial and Starting are unchanged. Starting and Initial take no receive events, so the NCP stays out until LCP renegotiates. Ze counts it finished, for the NCP-phase settle and for AC-6 and AC-12, through a per-family "rejected by Protocol-Reject" record set by the dispatch and cleared when LCP renegotiates: `ncpNegotiationSettled` (`ncp.go`) reads only the NCP state, and Starting cannot tell a rejected NCP from one not yet started, so the state alone cannot carry it | Close the NCP (Closed), or count it as still negotiating as pppd does | pppd v2.5.5 `ipcp_protrej` (`ipcp.c`) and `ipv6cp_protrej` (`ipv6cp.c`) call `fsm_lowerdown` (`fsm.c`), which in OPENED runs the down callback and sets STARTING, in STOPPING, REQSENT, ACKRCVD and ACKSENT sets STARTING and cancels the timer, in STOPPED sets STARTING, and in CLOSED and CLOSING sets INITIAL. Divergence: pppd never calls `np_finished` on a protrej (`ipcp_finished` runs only from Closed or Stopped). Ze counts it finished so an IPv4-only CPE comes up as soon as IPCP opens, not at `ncp timeout` |
| Framed routes are per family: Framed-Route belongs to IPv4, Framed-IPv6-Route to IPv6, each with its own emitted record; a family's install emits its framed routes, its release withdraws them, its reinstall re-adds them, and session-down withdraws what each family still has. IPv4's release also removes the /32; IPv6 has no host route | keep one list under one `framedEmitted` flag, emitted from the IPv4 assignment and withdrawn only at session-down | the kernel already removes the IPv4 framed routes in `withdrawNCPFamily` (`subscriber-session-model.md`, Traps), so the feed must match per family; one shared flag would withdraw or re-add the other family's routes on a release, and it never emits the IPv6 framed routes of an IPv6-only session (`assign` returns on the invalid IPv4 address) |
| The close at the no-NCP bound's expiry after session-up reports Idle Timeout | User Request or NAS Error by what ended the last NCP; NAS Request | RFC 2866 Section 5.10 "Idle Timeout         Idle timer expired.": the close is caused by that timer, not by the NCP's end; `l2tpevents.TerminateCauseIdleTimeout` already exists |
| One unit reader goroutine per session, started with the session (landed) | start on connect, stop on disconnect | the unit fd lives for the session across LCP renegotiations; a read before connect yields nothing, and one lifetime matches `readFrames` |
