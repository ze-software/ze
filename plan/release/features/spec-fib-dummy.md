## Task

Thomas asked (voice-transcribed, read for meaning): "can you create a spec for a
dummy backend which does nothing for the fib". Asked what it is for, he chose
both purposes the main session offered:

1. **A control-plane-only box.** A route reflector or a route server selects
   routes and never forwards a packet for them, so Ze must not write the
   routes the system RIB selects into any forwarding table.
2. **Testing and benchmarking.** The whole route path (BGP, the protocol RIB,
   the system RIB, the best-change event and its consumer) runs end to end
   without the cost of programming the kernel.

The goal: a new plugin, `fib-dummy`, configured by `fib { dummy { } }`. It is
the operator's FIB choice, so the engine adds no data-plane writer beside it.
It receives every route the system RIB selects, holds it in memory, counts it,
and writes it nowhere. Every display says the routes are held and not
programmed. The block can be added to and removed from a running configuration
by reload, and each time the forwarding plugins that run are exactly the ones
the new configuration selects.

The contract is narrower than "the box never touches forwarding", and every
page and help text says so: `fib-dummy` stops the routes that pass through the
system RIB. A feature that writes forwarding state by its own path (a static
route in a named table, policy routing, the IPsec tunnel-source guard, interface
addresses and their connected routes) is not a FIB plugin and is untouched
(choice C-4).

What exists today and is not changed: `fib-p4` already declares that it
programs the FIB, names no data plane, and programs nothing, because its
P4Runtime client is not written. Thomas parked P4 on 2026-09-06 ("We do not
care about p4 at the moment"). This spec does not repurpose, rename or edit
`fib-p4`. `fib-dummy` is its own plugin, and it must not repeat the two defects
recorded against `fib-p4`: leaves that are accepted and reach nothing, and a
display that calls held routes programmed.

Four defects in the engine's reload path block the goal and are fixed here,
each with its own acceptance criterion, because "add the block by reload" is
false without them (`ai/INSTRUCTIONS.md`, "Done means done, and a blocker gets
fixed"):

- A reload that adds a FIB block leaves the writer the engine added on the
  operator's behalf running beside it (AC-5).
- A reload that removes the only FIB block leaves a running route producer
  with no writer (AC-6).
- A plugin a reload stopped stays in the process manager's configured set, so
  `request plugin restart` starts it again. After AC-5 that command would
  start the kernel writer beside `fib-dummy` (AC-17).
- A reload that replaces a bus endpoint running a compiled-in FIB plugin
  (`bus { endpoint k { internal fib-kernel; } }`) by `fib { dummy { } }`
  leaves the endpoint's writer running beside the dummy, because the reload
  judges the writer over the added roots only and treats a running FIB plugin
  as chosen (AC-20, C-6).

Two label writers also stay blind across such a reload, because neither asks
the label sources to re-apply their entries when it opens: `fib-dummy` (new)
and `fib-kernel` started by a reload. Both emit a targeted
`(mpls-fib, replay-request)` as `fib-vpp` does (AC-9, AC-21). Two of the four
label sources do not answer that request with every entry they want installed,
and are fixed here because "remove the block by reload and forwarding comes
back" is false without them: BGP EPE replays only the labels a writer already
accepted (`Source.ReplayLabels` reads `s.installed`), so a PeerNode SID label
`fib-dummy` refused never reaches the `fib-kernel` that replaces it; and on a
box booted with `fib dummy` EPE never acquires its label source (`fib-dummy`
refuses the `mplsfib.RemoveLabelSource` cleanup EPE requires before its first
installation), so it sends no add at all, and the replay must run that cleanup
against the writer that opens, and only that writer, before any label: a reload
starts the new writer before it stops `fib-dummy`, so a cleanup sent to every
writer would be refused again by the dummy (AC-22);
RSVP-TE replays an entry whose removal a writer refused, which RSVP-TE
withdrew, because a refused removal stays in `busFIB.installed` (AC-23).

One reload-window race remains between `autoLoadForNewConfigPaths` starting the
opening writer and `stopCollectedProcesses` stopping the displaced `fib-dummy`:
a live label apply (`mplsfib.Apply`, token 0) emitted by a label source while
both writers are subscribed reaches both, and `mplsfib.apply` joins
`fib-dummy`'s refusal into the return error, so LDP, OSPF segment routing and
BGP EPE record the live add as refused (and EPE withholds its SID
advertisement) even though the opening writer installed it and `fib-dummy` is
about to stop. Once `stopCollectedProcesses` has finished stopping any
`ProgramsFIB` process, it emits the typed signal `(mpls-fib, writer-stopped)`,
and each remaining data-plane writer (`fib-kernel`, `fib-vpp`) issues one more
targeted `(mpls-fib, replay-request)` with its own token, clearing those
window refusals and settling EPE's advertisement (AC-24).

A `fib-kernel` that opens after an earlier `fib-kernel` of the same box
stopped with `flush-on-stop` false (a reload back to `fib kernel`, `request
plugin restart fib-kernel`) still refuses its own previous run's label entries
after that replay: it does not track the AF_MPLS entries and table-0 pushes
that run left, so the replayed add meets `EEXIST`. An AF_MPLS swap or pop
that run left stays in the kernel and keeps forwarding while its source
reports it refused (that spec's D-4); a table-0 push it left is refused the
same way, then removed by the IP stale sweep, and applied again by nothing, so
it stops forwarding (D-5). That defect exists on every box that runs a label source over
the kernel, with or without `fib dummy`, and
`plan/release/fixes/spec-fib-kernel-label-ownership.md` fixes it (its D-4 and
D-5). This spec depends on that spec for the outcome on a box with such
leftovers, and claims AC-21 only on a box without them (Depends, Known
Limitations).

The first two exist today for `fib p4` and for `fib kernel`, and the third for
every plugin a reload removes; `fib dummy` is the first block whose whole
purpose they defeat.

- [ ] `rfc/short/rfc4724.md` - Graceful Restart, the Forwarding State bit

**Key insights:**
- The registry already separates "the operator chose a FIB plugin" (`ProgramsFIB`) from "this plugin reaches a data plane" (`DataPlane`). `fib-dummy` is the first plugin for which the first without the second is the finished design, not a missing client.
- With BGP alone and no `fib` block, nothing programs the kernel today: only a `NeedsDataPlane` producer (static, OSPF, IS-IS, LDP, RSVP-TE, BGP EPE) makes the engine add a writer. So for purpose 1 the block is what stops that auto-load and what makes the choice visible; for purpose 2 it is what pulls in the system RIB (`Dependencies: rib`) and gives the route path a consumer.
- A route reflector that needs its IGP routes in the kernel and only BGP kept out already has `rib { fib-withhold [ bgp ] }`. `fib dummy` is for the box where no selected route is programmed at all. The guide states both.
- Label producers wait for the writer's acknowledgement before they advertise a label. A dummy that acknowledged an installation that did not happen would make an LSR attract labeled traffic it drops. It answers with a refusal (choice C-3).
- Reload judges the writer only for newly added plugins, and treats "running" as "chosen". Both are why adding or removing a FIB block by reload leaves the wrong set of forwarding plugins.

**Behavior to preserve:**
- With no `fib` block and a `NeedsDataPlane` producer, boot loads the writer of the data plane `interface backend` selects (`test/static/static-no-fib-block-loads-the-fib-plugin.ci`), and refuses the whole selection when no plugin programs it (`doctor-plugin-no-dataplane-writer`).
- An explicit `fib` block always wins at boot: the engine adds no writer beside it.
- `fib kernel` beside `fib vpp` keeps committing and running (`docs/guide/vpp.md`, "To run both, write both"; the guard spec's AC-14).
- `fib-p4`: its registration, its three leaves, `show fib p4` and its help text, unchanged.
- `registry.Register` keeps refusing a second writer for one data plane.
- `fib-kernel` keeps its routes in the kernel when it stops with `flush-on-stop` false, whatever stopped it.

**Behavior to change:**
- A new block, `fib { dummy { } }`, and its plugin `fib-dummy`.
- At reload the engine judges the data-plane writer over the whole candidate (every producer that will run, every FIB plugin the candidate chooses), not over the added plugins only. Three outcomes change, each with an acceptance criterion: an engine-added writer stops when the candidate chooses a FIB plugin (AC-5); it stops when the reload removes the last producer that needs it (AC-16); and the selected plane's writer starts when the last chosen FIB plugin is removed while a producer runs (AC-6).
- Not changed: a reload that changes `interface backend` does not swap a running engine-added writer for the other plane's. Today's behavior stays, the running writer is kept, because moving the interfaces from one data plane to another under a running daemon is a design of its own and not part of a dummy backend. The guard spec's AC-13 already refuses such a reload while a feature of the old plane remains. The judgement of this spec acts only when the chosen FIB plugins or the set of producers change, and even then it never swaps a running engine-added writer for another plane's: when no FIB plugin is chosen and a producer will run, a running engine-added writer is kept, and the selected plane's writer starts only when none runs (Data Flow step 2, row 3). So a reload that changes `interface backend` together with the producer set keeps the running writer too.
- A plugin whose stop an accepted reload made final leaves the process manager's configured set, so `request plugin restart` refuses it (AC-17). So does a plugin a rejected reload started and `rollbackStartupProcess` stopped (A-8).
- "Chosen" at reload is the candidate selection the data-plane verdict judged: the candidate tree's config roots, and its bus endpoints plus the recorded `--plugin` list. The loader hands that selection to the plugin server with the candidate tree, so the judgement reads the verdict's own value (Data Flow step 2). A FIB plugin named by `--plugin` is never stopped by the writer judgement (AC-7, AC-16).
- A reload that adds, removes or changes a bus endpoint that runs a compiled-in `ProgramsFIB` plugin (`bus { endpoint k { internal fib-kernel; } }`, in the daemon or with `process separate`) stops the writer the old endpoint ran, its `flush-on-stop` respected, and starts what the candidate selects (AC-20; C-6 (b), recommended, awaiting Thomas). An endpoint of any other compiled-in plugin is not judged by this rule: what a reload does with it is the bus spec's. An external endpoint stays refused at reload by `RefuseChangedDeclarations`, as the bus spec keeps it.
- `fib-dummy` and `fib-kernel` ask the label sources for a targeted label replay when they open, so a writer a reload starts receives the entries the sources want installed (AC-9, AC-21).
- BGP EPE answers that request according to whether it has acquired its label source. While `!s.acquired` (every cleanup so far refused, as on a box booted with `fib dummy`), `ReplayLabels` runs the body of `publishLocked` with the replay's apply function in place of the live one: every batch that body applies, the `ActionRemoveLabelSource` cleanup and each add, is applied with `mplsfib.ApplyReplay` tagged with the request's token, so it reaches the writer that asked and no other. The writer a reload is replacing (`fib-dummy`, still subscribed until `stopCollectedProcesses` stops it) never sees it and cannot join its refusal. The acknowledged cleanup comes first and the adds follow only once it is accepted (`nlri-bgpls.md`: "Before its first installation ... EPE requires acknowledged `mplsfib.RemoveLabelSource` cleanup"); the same body then clears and fills `s.installed`, sets `s.acquired`, runs `forgetSettledLocked` and emits the snapshot, so no second install path exists. Today that body applies only live batches (`RemoveLabelSource` and `emitLabel` call `mplsfib.Apply`, token 0). Once acquired, it answers with every PeerNode SID label it wants installed (`desiredLocked`), a label a writer refused included, and records a label a successful replay installed as installed. Either way the next publish neither cleans up again nor applies an installed label again (AC-22).
- RSVP-TE answers it with every entry it wants installed: a removal leaves `busFIB.installed` whatever the writer answers, so an entry RSVP-TE withdrew is never replayed, and a refused add, which the engine already rejects with its reservation, is applied again when the reservation is next refreshed: by the downstream neighbour's next Resv, or for an egress pop by the upstream neighbour's next Path, within that neighbour's refresh interval counted from `fib-dummy`'s stop (AC-23, A-13).
- Not changed here: what `fib-kernel` does with the label entries a previous run left. Today a source's replayed add of such an entry is refused with `EEXIST`; `plan/release/fixes/spec-fib-kernel-label-ownership.md` changes it, and this spec's AC-21 claims only a box without such leftovers.
- RSVP-TE records a label entry a writer refused on apply, as LDP does, so `rsvp-te-label-entries` reports it under `doctor-fib-mpls-no-writer` with the writer's cause; today it records replay refusals only (AC-18).
- After `stopCollectedProcesses` finishes stopping one or more processes whose registration declares `ProgramsFIB` (a committed reload removal or an auto-load rollback, never daemon shutdown), it emits the typed signal `(mpls-fib, writer-stopped)` (`mplsfib.WriterStopped`). Each remaining data-plane label writer (`fib-kernel`, `fib-vpp`) subscribes to that signal and emits one more targeted `(mpls-fib, replay-request)` with its own token, without holding its entry lock and without re-running VPP's stale-label snapshot, so any live label add of LDP, OSPF segment routing or BGP EPE that landed in the reload window while `fib-dummy` was still subscribed clears its joined refusal and settles EPE's SID advertisement (AC-24). `fib-dummy` does not subscribe to that signal, because every live apply in the window already received its joined refusal and a second replay would double-count `label-entries-refused`.

## Data Flow (MANDATORY - see `ai/rules/architecture.md`)

### Entry Point
- Config: the `fib/dummy` root, an empty container, delivered to the plugin as a config section.
- Events: `(system-rib, best-change)` batches from the system RIB; `(mpls-fib, entry)` batches from label producers.
- Commands: `show fib dummy` and `show fib dummy counters`, through the daemon dispatcher.

### Transformation Path
1. Boot or reload: the candidate tree holds `fib/dummy`. `registry.PluginsForConfigPaths` selects `fib-dummy`; dependency resolution adds `rib`.
2. The writer judgement runs over the candidate: producers that will run, FIB plugins the candidate chooses, the data plane. "Chosen" is the candidate selection the data-plane verdict judged: a `ProgramsFIB` plugin whose config root the candidate tree holds, or that the `candidatePluginSelection` value names (a bus endpoint of the candidate tree, or the recorded `--plugin` list). It is never read from the boot-time `s.config.Plugins`. The selection travels with the tree: `loadConfig` keeps the value it judged in `LoadConfigResult`, `diskConfigLoaders` answers it beside the map, and `ConfigLoader` and `ReloadConfig` carry it into `reloadConfig`; boot hands its own to the server through `ServerConfig`, and the server keeps the selection of the config it runs, so a rejected reload's recovery judges with it. A FIB plugin named by `--plugin` is thus chosen at every reload and is never put in the stop set. The producers that will run are the running processes, minus the stop set of this reload (owners of removed roots, their orphaned dependencies, and the `ProgramsFIB` processes the judgement stops), plus its start set (owners of added roots, their dependencies, and the writer or chosen FIB plugin the judgement starts), each counted as a producer when its registration declares `NeedsDataPlane`. A running process is matched to its registration through its config's `CompiledIdentity()` (which `plugin.RegistryNames` answers), so the endpoint `bus { endpoint k { internal fib-kernel; } }` is `fib-kernel`, in the daemon or with `process separate`, and an external endpoint is no compiled plugin. The judgement answers, over those inputs:

   | Chosen FIB plugins in the candidate | Producers that will run | Start set gains | Stop set gains |
   |-------------------------------------|-------------------------|-----------------|----------------|
   | The same as the running config's | The same set as the running ones | Nothing: the judgement acts only when the chosen FIB plugins or the set of producers change, so a reload that changes only `interface backend` swaps no writer and the running one is kept (Behavior to change, Known Limitations; the guard spec's AC-13 refuses it while a feature of the old plane remains) | Nothing |
   | One or more | Any | Each chosen one that does not run | Every running `ProgramsFIB` process that is not chosen (the engine-added writer; the writer of a removed or changed bus endpoint, AC-20) |
   | None | One or more | Nothing when an engine-added writer runs: it is kept whatever plane `interface backend` now selects, so no reload swaps it for another plane's, also one that changes `interface backend` together with the producers (Behavior to change, Known Limitations). Otherwise the selected plane's writer (AC-6, AC-20) | Every running `ProgramsFIB` process other than the writer kept or started |
   | None | None | Nothing | Every running `ProgramsFIB` process (AC-16) |

   A stopped writer stops after the producers the same reload stops, through `stopCollectedProcesses`, and keeps its `flush-on-stop` behavior.
3. The data-plane verdict judges the candidate at every door with the door's plugin selection: a FIB plugin in use that carries the mark "the choice to program no data plane", beside any other FIB plugin in use, is one finding (C-2). A FIB plugin is in use when the candidate tree holds one of its config roots or the selection names it, by a bus endpoint or by `--plugin`.
4. `fib-dummy` starts, draws a label replay token from `mplsfib.NewReplayToken`, subscribes to best-change and to label entries, then asks the system RIB for a broadcast replay and the label sources for a targeted replay with its token (`(mpls-fib, replay-request)`, as `fib-vpp` `requestLabelReplay` does). A `fib-kernel` the reload judgement starts does the same once its `(mpls-fib, entry)` subscription exists (AC-21). Each label source answers the request with every entry it wants installed, tagged with the token: LDP and OSPF segment routing their wanted sets, BGP EPE every label `desiredLocked` wants, a refused one included, once it has acquired its label source; while it has not (every `RemoveLabelSource` cleanup refused), EPE runs its publish with every batch tagged with the token, the cleanup first and the adds only once it is accepted, so the writer a reload is replacing, still subscribed until the reload stops it, sees none of them (AC-22); RSVP-TE every accepted add it has not withdrawn (AC-23). A source records each entry a successful replay installed as installed, so its next live apply does not send it again. An RSVP-TE entry a writer refused on apply was rejected with its reservation, so it is not in the batch: the reservation's next refresh applies it to the writer that now runs. Once `stopCollectedProcesses` has finished stopping one or more displaced `ProgramsFIB` processes (their exit and unsubscribe complete), it emits the typed signal `(mpls-fib, writer-stopped)` (`mplsfib.WriterStopped`); each remaining data-plane writer (`fib-kernel`, `fib-vpp`) subscribes to that signal and emits one more targeted `(mpls-fib, replay-request)` with its own token (without holding its entry lock and without re-running VPP's stale-label snapshot), closing the reload window for live label adds of LDP, OSPF segment routing and BGP EPE whose live `Apply` saw `fib-dummy`'s joined refusal while both writers were subscribed (AC-24). `fib-dummy` does not subscribe to `WriterStopped`, because it already joined its refusal to every live apply in the window. A replayed add is a first install like a live one: on a box whose kernel holds label entries a previous `fib-kernel` left, the add of such an entry meets `EEXIST` and is reported by its source until `plan/release/fixes/spec-fib-kernel-label-ownership.md` lands (Known Limitations).
5. Each best-change entry: install and replace store one value under the key (table id, prefix); remove deletes it. The stored value copies scalar fields only (next hop, interface name, protocol, route type, path count). A counter per verb is incremented. No string is built and nothing is logged per route.
6. Each label batch addressed to the plugin (`EntryBatch.Addresses` with its token: a live batch, a broadcast, or the replay it asked for): the refusal counter is incremented by the number of entries, and the batch is acknowledged with one refusal (C-3). The label source records the refusal and its own label-entries doctor check reports it. For RSVP-TE that record is new: `busFIB.emit` records the refused entry with the cause before it returns the error to the engine (AC-18).
7. When an accepted reload makes a plugin's removal final, the plugin's name leaves the process manager's configured set; so does the name of a plugin a rejected reload started and `rollbackStartupProcess` stopped.
8. `show fib dummy` answers one row per held route; `show fib dummy counters` answers one document. Both are data; the pipe layer renders them.

## Blast Radius

| Question | Answer |
|----------|--------|
| What breaks if this is wrong? | The plugin: a display that misstates what a control-plane box holds. The reload judgement: a reload that stops the kernel writer of a forwarding router, or leaves it running beside a block that says nothing is programmed |
| How is it reverted? | The plugin is one package and its generated registrations: a single commit revert. The reload judgement is a separate commit and reverts alone |
| Who else touches this path? | `spec-dataplane-compatibility-guard` (`1f82b2727d`): `plugin/registry/registry.go`, the plane names, the pages on data planes. `spec-fib-depth` (in progress): `fib/vpp`, label writers. `plan/release/fixes/spec-explicit-plugin-and-attach-config.md`: the loaders of `startup_autoload.go` |

## Design presentation

### What changes

Ze gains a third way to answer "where do the selected routes go": nowhere. An
operator writes `fib { dummy { } }`. The system RIB keeps selecting routes and
every protocol behaves as before, but no plugin writes those routes to the
kernel or to VPP. The `fib-dummy` plugin holds each selected route in memory and
counts the changes, so `show fib dummy` lists what a real backend would have been
given, each row marked as not programmed, and `show fib dummy counters` gives the
counters. The block has no setting. It cannot be written beside another FIB
block: the commit is refused with the line that fixes it. It can be added to and
removed from a running configuration by commit, and each time the forwarding
plugins that run are the ones the new configuration selects. `ze doctor` says
when routes are being held instead of programmed, and why.

### Before and after

1. **Stopping the kernel writer on a box with static routes.** Before: the only
   way is `fib { p4 { } }`, which names a P4 switch, logs one line per route and
   answers `show fib p4` under the help "Show the routes this backend programmed
   into the P4 forwarding pipeline". After: `fib { dummy { } }`, and `show fib
   dummy` under the help "Show the routes fib-dummy holds and programs nowhere".

2. **`show fib dummy`.** After, as a table:

   | table | prefix | protocol | next-hop | paths | programmed |
   |-------|--------|----------|----------|-------|------------|
   | 254 | 10.0.0.0/8 | static | 192.168.1.1 | 1 | no |
   | 254 | 203.0.113.0/24 | bgp | 192.0.2.1 | 1 | no |

   The row fields:

   | Field | Type | Description |
   |-------|------|-------------|
   | `table` | number | The route table the change named |
   | `prefix` | prefix | The selected prefix |
   | `protocol` | text | The protocol that won the selection |
   | `route-type` | text | Omitted for an ordinary route; `blackhole`, `unreachable` or `prohibit` otherwise |
   | `next-hop` | address | Omitted when the route names none |
   | `interface` | text | Omitted when the route names none |
   | `paths` | number | The number of equal-cost paths |
   | `programmed` | text | Always `no` |

3. **`show fib dummy counters`.** After, one document:

   | Field | Type | Description |
   |-------|------|-------------|
   | `forwarding` | text | Always `none`: no route is written to any forwarding table |
   | `routes-held` | number | Routes held now |
   | `installs`, `replaces`, `removals` | number | Changes received since the plugin started |
   | `invalid-changes` | number | Changes refused for an invalid prefix |
   | `label-entries-refused` | number | MPLS entries refused |
   | `since` | time | When the plugin started |

4. **`fib dummy` beside `fib kernel`.** Before: not expressible. After, at
   commit, reload, start and `ze config validate`:
   "fib dummy is configured beside fib kernel" /
   "fib dummy is the choice to program no route, and fib kernel programs the kernel data plane" /
   "delete fib dummy, or delete fib kernel".
   Beside `fib p4`, which declares no data plane, the second line ends "and fib
   p4 is another FIB plugin". With `ze --plugin ze.fib-kernel` and no `fib
   kernel` block: "fib dummy is configured and the plugin fib-kernel is
   selected" / the same second line / "delete fib dummy, or start ze without
   --plugin ze.fib-kernel". `ze doctor` prints the same finding under
   `doctor-dataplane-mismatch`.

5. **Adding a FIB block by commit on a router whose writer the engine added.**
   Before (shown with `fib p4`, the only such block today): the commit succeeds
   and the kernel writer keeps running and keeps programming every new route.
   After: the engine-added writer stops in the same reload, and the log says
   which plugin stopped and that the configuration now chooses the FIB plugin.

6. **Removing the only FIB block by commit while static routes remain.** Before:
   the block's plugin stops and no writer starts; the static routes stay
   selected and unprogrammed until a restart. After: the writer of the selected
   data plane starts in the same reload and programs them.

7. **`ze doctor` on a box with `fib dummy` and static routes.** After, a warning
   under `doctor-fib-dummy-holds-routes`: "fib dummy is configured, and this
   config loads static, whose routes reach forwarding only through a data-plane
   writer" / "fib dummy holds those routes and writes them to no forwarding
   table" / "delete fib dummy".

8. **LDP on a box with `fib dummy`.** After, in `ze show doctor`, from the
   `ldp-label-entries` check, one error under `doctor-fib-mpls-no-writer` for
   each entry, such as: "ldp: the data plane does not hold the label pop of
   in-label 16; the writer did not install it: fib dummy programs no label, so
   this entry is not installed; delete fib dummy, or remove the label
   protocol". The words before the last colon are the existing check's. This
   holds today for LDP, OSPF segment routing and BGP EPE. For RSVP-TE,
   before: `rsvp-te-label-entries` stays silent for an entry the writer
   refused on apply, because `busFIB.emit` records nothing; it reports only an
   entry a replay did not restore. After: the same kind of row appears from
   `rsvp-te-label-entries` (item 11).

9. **Removing the last route producer by commit.** Before: the engine-added
   writer keeps running with nothing to write. After: it stops in the same
   reload, once the producer's routes are withdrawn from the kernel.

10. **`request plugin restart fib-kernel` after a commit stopped that plugin.**
    Before: accepted, and the plugin starts again though the configuration no
    longer runs it. After: refused as a plugin the configuration does not run,
    and completion no longer offers the name.

11. **An RSVP-TE label entry a writer refuses on apply.** Before: the engine
    refuses the LSP and `ze show doctor` holds nothing from
    `rsvp-te-label-entries`. After: one error under `doctor-fib-mpls-no-writer`
    naming the entry and the writer's cause, cleared when a later apply of the
    same slot succeeds.

12. **Benchmarking the route path.** Before: the perf DUT is a route server,
    so no route reaches the system RIB or a FIB writer. After: `./le perf` with
    `PERF_CONFIGS_DIR` naming the route-path overlay runs `bgp-rib`, the system
    RIB and `fib dummy`. Around each pass the runner reads `show fib dummy
    counters` from the running DUT, and the run fails unless, once the pass
    has ended, `routes-held` is back to its value before the pass and
    `installs` and `removals` have
    each risen by the routes sent times the iterations (one warmup and
    `DUT_REPEAT`). `./le perf record history` refuses the result, naming the
    overlay directory.

13. **`ze --plugin ze.fib-kernel` with no `fib` block, then a reload.** Before
    and after: `fib-kernel` keeps running. The writer judgement counts a
    plugin named on the command line as chosen.

14. **A reload that replaces `bus { endpoint k { internal fib-kernel; } }` by
    `fib { dummy { } }` (C-6, (b) recommended, awaiting Thomas).** Before:
    the reload is accepted, `fib-dummy` starts for its root, and `fib-kernel`
    keeps running from the boot-time endpoint, because the writer judgement
    reads only the added roots and treats a running FIB plugin as chosen;
    `show plugin list` holds both. After: the same reload stops `k` and starts
    `fib-dummy`, as a restart with the new config would, and
    `show plugin list` holds `fib-dummy` alone among the FIB plugins. The
    writer judgement adds nothing for an endpoint whose plugin is not a FIB
    plugin. An external endpoint the reload adds, removes or changes is still
    refused with `restart ze`. That is the After of (b). After, under (a):
    the reload is refused whole with a refusal naming the endpoint `k` and
    the fix `restart ze`, and `k` keeps running until the restart.

15. **Labels across the conversion: LDP, then BGP EPE and RSVP-TE.** LDP, before: after a reload adds
    `fib { dummy { } }`, LDP keeps the labels the stopped kernel writer had
    accepted, and nothing reports that no writer holds them; after a reload
    removes the block again, `fib-kernel` holds none of the entries the dummy
    refused, because it never asks for them. After: `fib-dummy`
    asks the label sources to re-apply their entries when it opens, refuses
    each, and `ze show doctor` reports them under `doctor-fib-mpls-no-writer`;
    `fib-kernel` asks the same when a reload starts it, so on a box whose
    kernel holds no label entry an earlier `fib-kernel` left,
    `ip -f mpls route show` lists one entry per in-label and the findings
    clear. On a box that booted with `fib kernel`, the stopped writer's label
    entries are still in the kernel, and the new `fib-kernel` refuses LDP's
    replayed add of each with `EEXIST`, as it does today after `request plugin
    restart fib-kernel`; that stays so until
    `plan/release/fixes/spec-fib-kernel-label-ownership.md` lands.

    BGP EPE on a box booted with `fib dummy`. Before: `fib-dummy` refuses
    EPE's `RemoveLabelSource` cleanup, so EPE sends no PeerNode SID label and
    advertises no SID, and `bgp-epe-label-entries` reports every wanted label;
    after a reload removes the block, `fib-kernel`'s replay request is
    answered with nothing, and the labels and SIDs stay missing until the
    next peer or config change. After: the replay request makes EPE run its
    publish for `fib-kernel` alone, every batch tagged with `fib-kernel`'s
    token, the cleanup first and then one add per peer. `fib-dummy` is still
    running at that moment, because the reload starts the new writer before
    it stops the old one, but it never sees those batches, so its refusal
    does not block them. `ip -f mpls route show` lists each PeerNode SID
    label, the SIDs are advertised, the findings clear, and the next peer or
    config change sends no cleanup and no add again.

    BGP EPE on a box converted to `fib dummy` by reload. On VPP, a label
    refused while the dummy ran reaches `fib-vpp` in the replay batch when
    the block is removed, and `fib-vpp` re-claims the labels its previous run
    left. On the kernel, the PeerNode SID labels the first `fib-kernel`
    installed are still there, the new `fib-kernel` refuses their replayed
    adds with `EEXIST`, and because it answers the batch once, EPE reports
    every label of it as refused; that stays so until
    `plan/release/fixes/spec-fib-kernel-label-ownership.md` lands.

    RSVP-TE. Before: a removal the writer refused (an LSP torn down while
    `fib-dummy` ran) is replayed to the `fib-kernel` that replaces it,
    installing forwarding for an LSP RSVP-TE withdrew. After: it is not
    replayed, and `rsvp-te-label-entries` reports the refused removal. An add
    `fib-dummy` refused is not replayed either: the transit or ingress entry
    returns with the downstream neighbour's next Resv, and an egress pop with
    the upstream neighbour's next Path, within that neighbour's refresh
    interval after `fib-dummy` stops: a refresh that lands while the dummy
    still runs beside the new writer is refused too (A-13).

    Live label adds during the reload window. Before: between the opening
    writer's start (`autoLoadForNewConfigPaths`) and `fib-dummy`'s stop
    (`stopCollectedProcesses`), a live `ActionAdd` from LDP, OSPF segment
    routing or BGP EPE reaches both writers, gets `fib-dummy`'s refusal joined
    into `mplsfib.Apply`, and leaves a stale `doctor-fib-mpls-no-writer`
    finding (and an unadvertised EPE PeerNode SID) even after `fib-dummy` stops.
    After: once `stopCollectedProcesses` has stopped any displaced
    `ProgramsFIB` process, it emits `(mpls-fib, writer-stopped)` and each
    remaining data-plane writer (`fib-kernel`, `fib-vpp`) issues one more
    targeted replay request with its own token, clearing those findings and
    settling EPE's SID advertisement (AC-24).

### Alternatives set aside

| Alternative | Why set aside |
|-------------|---------------|
| Use `fib p4` as the dummy, or rename it | Thomas parked P4 and its display is under review; its three leaves are accepted and read by nothing, and its help calls held routes programmed. A dummy built on it inherits both defects, and a P4 client written later would take the dummy away |
| Count only, hold no route (C-1 (b)) | Cheapest, and enough for a benchmark. Set aside as the default because purpose 1 needs the operator to see which routes would have been programmed, and the sibling commands `show fib kernel` and `show fib vpp` list routes. Left to Thomas |
| A pure marker: declare `ProgramsFIB`, subscribe to nothing | The smallest plugin. It cannot show that the route path reaches it, so neither purpose has evidence, and a benchmark would run with no consumer of best-change |
| A leaf on the block, such as `hold-routes` or `log-routes` | Every leaf needs a reason and a reader. No use needs one today, and an unread leaf is the recorded defect of `fib p4` |
| One command, `show fib dummy summary`, beside the route list | `docs/architecture/api/commands.md` forbids "a subcommand for scope or presentation". The counters are a subject of their own (changes since start, refused labels), so the command is named for them; the number of held routes is also `show fib dummy \| count` |
| Allow `fib dummy` beside `fib kernel` as a mirror (C-2 (b)) | The two blocks disagree about whether routes are programmed, and the mirror shows nothing `show fib kernel` does not. It also makes the label refusal poison the real writer's answer (R-1) |
| Accept and hold label entries, answering success (C-3 (b)) | The label channel's contract is that the answer is the install result and that a producer must not advertise a failed one. Answering success would make an LSR advertise labels it drops |
| A data plane named `none`, selected by `interface backend` | It would remove interface configuration with it, and it puts a non-plane in the plane vocabulary the guard spec has just reduced to `kernel` and `vpp` |
| A tree validator registered by the dummy, with its own doctor code | A tree validator is handed the tree alone. It cannot see a FIB plugin named by `--plugin`, so "refused at every door" would be false, and it would be a second view of the plugin selection beside the verdict's. The refusal is a rule of the data-plane verdict, which reads one mark the dummy sets, as it reads `HostSideDataPlane` |
| The dummy raises its own doctor code for refused label entries | Every label source already records a writer's refusal and reports it from its own check under `doctor-fib-mpls-no-writer`; a second code would report one fact twice |
| Swap the engine-added writer when a reload changes `interface backend` | Moving the interfaces between data planes under a running daemon is a design of its own. Today's behavior stays, and the guard spec's AC-13 refuses the reload while a feature of the old plane remains |
| Leave the configured-set defect to `spec-plugin-restart-bounded-and-configuration-true.md` | After AC-5 one command would start the kernel writer beside the dummy. The fix is small and on this work's own path, so it is done here and that spec's item 1 is repointed |
| Stop the engine-added writer from inside the dummy, or by a claim the kernel and VPP writers read | A plugin would reach into another, and the writers would go silent instead of stopping. The engine added that writer, so the engine removes it |
| Flush the kernel routes when a writer is displaced at reload (C-5 (b)) | It changes what `flush-on-stop false` means for every writer stop, which is a decision about `fib-kernel`, not about the dummy |
| Reorder `reloadConfig` so the displaced writer stops before the new writer starts | Compensation ordering when the new writer fails to start or the config transaction rolls back needs a design of its own; emitting `(mpls-fib, writer-stopped)` after `stopCollectedProcesses` reuses the targeted replay AC-21 already adds and handles both committed and rolled-back reloads in one place |

  boot, so no reload removes it." In the bus grammar, a reload that replaces
  `bus { endpoint k { internal fib-kernel; } }` by `fib { dummy { } }` is
  accepted and leaves `k` running beside `fib-dummy`.
- After: an endpoint that runs a compiled-in plugin is configured by reload
  (the bus spec's rule), and the writer judgement judges every one that runs
  a `ProgramsFIB` plugin: a reload that removes or changes it stops the writer
  it ran, with that writer's `flush-on-stop` behavior, and starts what the
  candidate selects; a new such endpoint starts its plugin. An external
  endpoint changes only when ze restarts.
- What a user sees: the reload of item 14 succeeds, `k` stops, and
  `show plugin list` holds `fib-dummy` alone among the FIB plugins, as after a
  restart with the same config.
- The alternative, (a): refuse such a reload whole with "restart ze", through
  `RefuseChangedDeclarations` extended to compiled-in FIB endpoints. It keeps
  this page's "read only at boot" rule in the bus grammar, and departs instead
  from `hub-architecture.md` ("it concerns the external plugins and their
  modules alone: every other part of the config reloads without a restart")
  and `ai/doors/hub-engine.md` ("they change only when `ze` restarts, and
  nothing else in the config needs one"), both of which would be corrected in
  the same work. Leaving today's behavior is neither: it keeps two FIB
  plugins running against a config that says nothing is programmed.

## Known Limitations

- `fib dummy` covers the routes the system RIB selects. Features that write forwarding state by their own path are untouched (C-4). Refusing them beside the dummy needs the per-feature data-plane declaration that `spec-dataplane-compatibility-guard` (`1f82b2727d`) added.
- Routes a kernel writer installed before a reload replaced it stay in the kernel when its `flush-on-stop` is false (C-5). The doctor check that reports routes Ze owns in the kernel while no kernel writer is selected is homed in `plan/release/validation/spec-doctor-coverage-10-forwarding.md` as its AC-111 (`doctor-fib-kernel-routes-no-writer`, `test/plugin/doctor-fib-kernel-routes-no-writer.ci`); that amendment is made.
- A reload that changes `interface backend` does not swap the running engine-added writer for the other plane's: the running writer is kept, as today. Moving the interfaces between data planes under a running daemon is a design of its own; the guard spec's AC-13 refuses such a reload while a feature of the old plane remains, and this spec's writer judgement acts only when the chosen FIB plugins or the set of producers change, and when it acts with no FIB plugin chosen it keeps a running engine-added writer rather than start the other plane's (Data Flow step 2, row 3), so a reload that changes `interface backend` together with the producers keeps the running writer too.
- A `fib-kernel` that opens over label entries an earlier `fib-kernel` left (a reload from `fib dummy` back to `fib kernel` on a box that booted with `fib kernel`, `request plugin restart fib-kernel`, or a Ze restart, whatever `flush-on-stop` says) refuses the sources' replayed adds of those entries with `EEXIST`. An AF_MPLS swap or pop so left stays in the kernel and keeps forwarding while its source reports it refused (that spec's D-4). A table-0 push so left is refused the same way, then removed by the IP stale sweep, and nothing applies it again, so it stops forwarding (D-5). AC-21, AC-22 and AC-24 claim their outcomes only on a box without such leftovers. `plan/release/fixes/spec-fib-kernel-label-ownership.md` owns the fix (its D-4, D-5, D-6), and this spec's outcome on such a box depends on it (Depends). So does the sequence "boot with `fib kernel` and LDP, reload to `fib dummy` and back, then `request plugin restart fib-kernel`": no test of this spec covers it, and that spec's tests own the leftover reclaim.
- Two narrow reload-window races remain while both the opening data-plane writer and the displaced `fib-dummy` are subscribed to `(mpls-fib, entry)`: (1) a live `ActionRemove` landing in that window is already carried out in the data plane by the opening writer, so no stale forwarding stays, while `fib-dummy`'s joined refusal leaves a removal finding in the source's `refusals` (and in EPE's `s.installed` for the retired peer) until the next live apply of that slot or EPE publish, because replay re-applies wanted adds only; (2) a live RSVP-TE `ActionAdd` landing in that window is installed by the opening writer before `fib-dummy`'s joined refusal causes RSVP-TE to reject the reservation and release its newly allocated in-label, so the reservation returns on the neighbour's next Resv or Path refresh (A-13) and, if that refresh allocates a different in-label or never arrives, the in-label installed in the window remains owned by `mplsSourceRSVPTE` until reused or writer stop.
- Until `plan/release/fixes/spec-fib-kernel-label-ownership.md` lands, a replayed label entry meets its D-1 to D-3 exactly as a live one does: a replayed push can replace or delete the system RIB's labeled route of the same prefix, and a system-RIB change can remove the push. AC-21 claims nothing about which owner holds a kernel slot; it claims only that the replay reaches the writer that asked.
- The `| implied` view does not exist yet. When `plan/release/fixes/spec-explicit-plugin-and-attach-config.md` (which absorbed `spec-bus-2-implied-display-and-grant-refusals.md`) builds it, a box with `fib dummy` shows no implied writer, and a box without it shows the engine-added one: that view reads what the loaders report, which this spec keeps correct at reload.
