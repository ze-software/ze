## Task

**The work.** Write a public row for the 32 enrolled RFCs that have none, or
decide they should not have one. The row came from
`rfc-ledger-single-declaration` on 2026-09-01, which named it a Known Limitation
of that spec rather than an omission: the 32 were grandfathered before the
single-declaration move and are grandfathered after it. `Support` set to `-` in
a summary's own `## Meta` table is now their explicit declaration, so the state
is a decision a reader can see rather than an absence. Deciding whether each
deserves a row is editorial work on the public page, not ledger plumbing, which
is why it is separate work rather than a defect.

**Why it matters.** `renderStatusBacklog` (`internal/le/rfc/sections.go`) states
the cost in the artifact it generates: every MUST-level requirement these RFCs
declare is gated, "so the obligation is enforced while the public page says
nothing about the RFC at all". A reader of `docs/features/rfc-status.md` cannot
tell that ze holds itself to rfc4862 or rfc6482, because the page carries no row
for either.

**The 32, as derived today (2026-09-05).** The set is DERIVED, never listed:
`renderStatusBacklog` computes `enrolled - rows` and renders it into
`ai/RFC-REQUIREMENTS.md` under "Enrolled without a public status row". Today it
holds: rfc792, rfc905, rfc1071, rfc2003, rfc2348, rfc2349, rfc2473, rfc2782,
rfc2784, rfc2890, rfc3031, rfc3786, rfc4213, rfc4576, rfc4862, rfc5561, rfc6071,
rfc6138, rfc6397, rfc6482, rfc6549, rfc6996, rfc7012, rfc7427, rfc7440, rfc7611,
rfc7950, rfc8097, rfc8571, rfc8707, rfc9319, rfc9728. The implementation re-runs
the derivation rather than trusting this paragraph, and it reconciles it against
the 40 summaries that carry `| Support | - |` today, because the two counts are
not the same number and the difference has not been read.

**The ratchet the work must respect.** `checkPublicRowMonotonic`
(`internal/le/rfc/check_status.go`) grandfathers the existing 32 and refuses any
NEW enrolment without a row, so the number can only shrink. Writing rows shrinks
it; deciding that an RFC should not have one has to be recorded where a reader
meets the decision, not only in this spec.

**What one row costs.** `renderStatusPage` (`internal/le/rfc/render_ledger.go`)
moves four authored cells verbatim from the summary that owns them and
synthesizes no prose, because "a support claim is a product judgement, and a
generator that wrote the prose would be inventing the claim it exists to
publish". So each row is authored in that RFC's own `rfc/short/<stem>.md` Meta
table, and `./le rfc index-update` regenerates the page. A hand edit to
`docs/features/rfc-status.md` is destroyed by the next run.

**The judgement each of the 32 needs.** For each stem: what ze implements of it,
what it does not, and whether the RFC is a dependency ze speaks (rfc1071's
checksum, rfc792's ICMP) or a document ze merely cites. A support claim that
overstates is worse than no row, because `./le rfc check` refuses a clean
support claim beside a known unmet MUST.

## Data Flow (MANDATORY - see `ai/rules/architecture.md`)

### Entry Point
- A `## Meta` table in `rfc/short/<stem>.md`, authored by a person.
- `./le rfc index-update` reads every summary and regenerates the public page and the requirement census.

### Transformation Path
1. `Collect` reads `rfc/short/*.md`.
2. `renderStatusPage` places each row in its section and writes `docs/features/rfc-status.md`.
3. `renderStatusBacklog` derives the enrolled stems with no row and writes them into `ai/RFC-REQUIREMENTS.md`.
4. `./le rfc check` compares the claims against the gated requirements.

### Boundaries Crossed
| Boundary | How | Verified |
|----------|-----|----------|
| Summary ↔ public page | generated by `./le rfc index-update` | No |
| Summary ↔ gate | `./le rfc check` reads the claim beside the requirements | No |

### Integration Points
