Rust, Zig or C may come to mind first when you think about control over memory. In Ze, I use Go, but bring the same attention to where memory is allocated and how it is reused.

An unnecessary allocation looks harmless until a router repeats it for every route. When designing Ze, I brought some older programming habits to a language with a garbage collector.

This article was co-authored with Claude and revised with OpenAI Codex. The architecture and design decisions are mine. Claude helped with implementation, tests and measurements, and with organising and drafting the original text.

From the Amiga to Ze

As a young and very inexperienced programmer, I learned assembly and low-level programming on the Amiga. I followed the demo scene, where programmers produced remarkable results within very limited memory and processing power. Those experiences still shape how I look at software.

When I wrote ExaBGP, I wanted an ordinary program to be able to announce routes without implementing BGP itself. I also wanted the code to be easy to read and understand, so that other people could contribute and add support for more RFCs. I valued that accessibility more than performance. ExaBGP was never designed to be a particularly memory-efficient or CPU-efficient implementation. Ze, however, is.

To my mind, too many newer RFCs give too little attention to efficient processing or compact protocol layouts. Modern machines make the constraints I grew up with much less pressing for everyday software development, but the knowledge still informs my design decisions. Knowing assembly is useful even when I am writing Go.

With Ze, I wanted efficiency to be part of the design from the start. Go has a garbage collector, but we can write the repeated processing much as we would in C, allocating working storage ahead of time and managing its reuse ourselves. Pools let us keep buffers available and decide when they can hold new data, instead of creating and discarding an object for every operation. Avoiding those allocations can substantially reduce the work left to the garbage collector, although the runtime still manages the underlying memory.

Before adding an object or copying a message, we should be able to explain why that storage is necessary. Following a BGP UPDATE through Ze makes those decisions concrete, because an unnecessary operation here can be repeated for every route.

Use the data we already have

A BGP UPDATE arrives as a sequence of bytes containing route announcements or withdrawals, together with attributes such as the next hop and AS path. Ze receives those bytes in a buffer, an area of memory used to hold them. One way to process the UPDATE would be to decode every attribute into a Go object, work with those objects, then encode them again when sending the route onwards. If the code only needs the next hop, decoding every attribute wastes CPU cycles and may also allocate memory for data it never uses.

Ze's WireUpdate keeps the received bytes and provides access to the attributes within them. Its attribute index records where values occur, and a caller can read the next hop without constructing decoded objects for every other attribute. Several readers can also share the same stored message while it remains available. The input still has to be validated, so the saving comes from avoiding representations and copies which that processing does not require.

Sharing stops being suitable when one reader needs different bytes. If policy changes an attribute before an UPDATE is sent, the other readers must still see the original message. Ze's buffer-first approach lets the encoder write the changed message directly into output storage supplied by its caller. The necessary new representation then goes into its destination without an intermediate message that would immediately be copied again.

A fixed size makes reuse straightforward

The traditional maximum BGP message size is 4,096 bytes, which is also a common memory-page size. A page is a unit in which the operating system maps memory. An implementation handling messages within that limit can allocate a pool of fixed-size buffers, then cycle through them as messages arrive and processing finishes. Once enough buffers are available, receiving the next message need not require another buffer allocation.

The size limit has since been extended: RFC 8654 allows messages up to 65,535 bytes when the receiver has advertised support, with exceptions for OPEN and KEEPALIVE. A pool must accommodate the messages a session can receive. The useful principle survives the change in limit: reserve suitable storage and reuse it once its readers have finished.

Ze's mixed-size overflow pool, MixedBufMux, uses 64 KiB blocks that can serve one extended message or sixteen 4 KiB messages. Once all the borrowed slices are returned, the block can be used in either form again. The memory can therefore follow the mix of small and large messages without being tied to separate pools for each size.

Reuse needs a clear stopping point

After the readers have finished with an UPDATE, its storage can hold another message. Keeping available buffers in a pool avoids allocating fresh storage for each arrival, but introduces a release decision: the code returning a buffer has to respect every reader's permitted lifetime.

Garbage collection does not make this reuse safe. Returning a buffer to a pool leaves its underlying memory allocated, and a slice, a view of the bytes in that memory, can still refer to it. If the next message overwrites the buffer before that reader has finished, code expecting the old route will read a different message. The memory remains accessible throughout; its contents have changed too soon.

Ze therefore has explicit rules for how long readers can use shared bytes. An event handler can inspect a received UPDATE during delivery, but keeping it afterwards requires a snapshot in independent storage. Taking that copy before returning lets later processing continue after the original buffer has been reused. Avoiding every copy would defeat the point if a retained route could change underneath its reader.

A pool occupies memory even while its buffers sit unused, so fewer allocations can come at the cost of keeping more memory between bursts. Ze's shared buffer pools support a budget for growth and release surplus blocks when they have been returned and the remaining blocks have room. Those limits apply to the pools concerned, without bounding the daemon's total memory use, and growing storage still requires allocations.

Store repeated route attributes once

The routing information base, or RIB, keeps routes long after their receive buffers have been reused, so it needs independent storage. Keeping a copy of the whole packet would also keep bytes the RIB no longer uses. Giving every route its own attribute values avoids that waste but introduces another: many of those values are identical across the routing table.

Routes often share an AS path or the same communities, the values operators attach to routes for policy. Ze's RIB storage stores common attributes individually, using an attribute pool to keep equal values together. The first occurrence is copied into independent storage, and later routes hold references to the existing value for as long as they use it. This technique is called interning.

Sharing individual attributes lets two routes with different preferences still share the same AS path. Changing one value does not require another copy of all the others. Here, the saving concerns memory retained for the life of a route, as well as the temporary allocations avoided during message processing.

Apply the same approach to text

Many of these patterns will be familiar to anyone who has read code by Daniel J. Bernstein, usually known as DJB. Earlier in my career we used his mail server, qmail, and I worked on it for a long time, writing many patches. His approach to building text in reusable storage influenced how I write software.

DJB's stralloc interface keeps track of a string's length and available capacity, so more text can be appended without another allocation while space remains. Go's byte slices remind me a lot of stralloc, with their explicit length and capacity.

Go's fmt package follows the C library's familiar printf and sprintf style with Printf and Sprintf. The standard library also provides strings.Builder, which assembles a string from successive writes while minimising copying.

This matters when Ze produces text for an application, the job ExaBGP began with. Converting each route value into a string before joining the strings can create temporary storage even if the binary processing reused its buffers. An address followed by a separator and a number can instead be written into consecutive bytes of one buffer, without first turning the number into a separate string. Once the result has been consumed, the same buffer can be reset and used for the next value.

Ze's textbuf.Buffer follows that builder pattern, with typed methods for appending values such as addresses and integers, and includes 128 bytes of storage. A local buffer initialised with Reset can build short text without a separate heap allocation. A caller that consumes the completed bytes before resetting the buffer can read them directly, without copying the result.

If the text has to survive reuse of the buffer, the caller requests an independent string. The implementation copies bytes held in the buffer's built-in array, or transfers the storage if the bytes are already held in a separate allocated array. Either way, the string remains available and the buffer is emptied. The text buffer design explains how the choice follows from how long the result will be kept, just as it does for an UPDATE.

Recomputing can cost less than fetching

The relative cost of computation and memory access has changed over the years. A calculation that once justified keeping its result in memory can now be cheaper to repeat than to fetch from main memory. For a value that takes only a few instructions to regenerate from data already at hand, looking up a saved copy can cost more than doing the work again.

Keeping a result in a program's cache does not guarantee that it is in the CPU's cache. The CPU keeps recently used data in small, fast caches, with L1 closest to the executing instructions, followed by larger but slower levels such as L2 and L3. When a loop's working data stays in L1, repeated accesses can be many times faster than fetching it from main memory. Keeping more calculated results can enlarge that working data enough to lose the advantage.

Caching remains useful when it avoids expensive computation, and regenerating a value still requires access to its inputs. The choice depends on how much work the calculation takes and where the data is when we need it. In Ze, avoiding unnecessary representations helps keep the data used together compact, as well as reducing allocations.

Check that the intended saving exists

Choosing a design that avoids temporary storage does not establish how much memory its implementation allocates. Go's compiler can keep some values in a function's local storage while allocating others on the heap, and the result can change with the compiler. We therefore need to measure the compiled operations, even when the code appears to avoid allocation.

Go has excellent profiling and diagnostic tools. With pprof, CPU profiles show where the program spends its CPU time, while heap and allocation profiles distinguish memory still in use from the total allocated over time. The reports connect those costs to functions and source lines, and can be read as text as well as explored visually.

This tooling makes AI-assisted optimisation particularly effective for me. An agent can follow an expensive call back into the code and try a focused change, then run the same workload again to compare CPU time and allocations. It helps the agents optimise Ze and gives me evidence to assess their changes, including whether the saving is worth any added complexity.

Ze's allocation assertions exercise repeated operations once their working storage is available. The UPDATE rebuild tests, for example, provide an available output buffer and require peer-specific attribute changes to allocate no heap memory. The community-removal test separately checks which values remain and their order. Both checks are necessary, because reducing allocations would be useless if rebuilding the message changed its meaning.

These checks cover the named operations; session creation, pool growth and other forwarding work still allocate memory.

The original measurements published with this article used Go 1.26.5 on an Apple M4 Max running macOS on arm64, with allocation reporting and medians of five runs. They have not been rerun for this revision.

These microbenchmarks do not measure storing a complete new route, TCP throughput or route convergence, and their timings are not performance targets for a different compiler or machine.

A useful way to apply this elsewhere is to follow one piece of data from input to final use, recording its representation and how long each reader needs it. Each copy should have a reason why the existing bytes cannot serve the next operation. A different representation or an independent lifetime can justify new storage, while transferring ownership of existing storage may require no copy at all.

Reuse adds development work. We have to define who owns the storage and when a reader must stop using it, then check that the intended saving exists without changing the result. For a rarely used operation, that bookkeeping can cost more effort than the saving justifies. On a path repeated for each route, removing an unnecessary copy removes the same cost from every repetition.

Addendum: Goose and memory management

Since this article was first written in August 2026, Wouter van Oortmerssen's Goose programming language has become publicly available, with compiler releases in October. Its approach to memory management is particularly interesting in the context of the decisions above.

Goose's memory model places dynamic values on data stacks assigned by the compiler, rather than allocating individual objects on a general-purpose heap. Growing a value advances a pointer through reserved address space, and leaving its owning scope makes the storage reusable by moving that pointer back. The compiler checks that references cannot outlive their owners. Compact layouts also let nested data sit together, avoiding a separate allocation for each part.

There is a connection with arenas in Zig or Odin, where a programmer groups allocations that can be released together, for example at the end of a request. Goose makes scope-based storage and its lifetime checks part of the language itself. I find that worth following: the relationship between data layout and lifetime directly shapes how programs are written.
