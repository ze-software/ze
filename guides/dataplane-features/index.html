Features by Data Plane: Linux Kernel and VPP

Ze can forward packets through the Linux kernel or through VPP. Most of Ze is control plane and is the same on both. The features that write forwarding state are different: each one has a kernel implementation, a VPP implementation, or both. This page lists them, so that you can see what a VPP deployment keeps and what it loses before you select it.

How the data plane is selected

No single switch selects VPP. Four parts of the configuration each select their own backend.

Configuration Values Default What it selects
interface backend netlink, vpp netlink Who creates and configures interfaces. PPPoE subscriber sessions and the automatic route writer follow this leaf.
firewall backend nft, vpp nft Who carries the firewall and NAT rules: nftables, or VPP ACL and NAT44.
traffic control backend tc, vpp tc Who shapes traffic: Linux queueing disciplines, or VPP policers.
fib kernel, fib vpp a block for each writer none Who writes routes. Without a fib block, Ze loads the writer for the data plane that interface backend names.

The vpp value of each leaf exists only in a build that has the ze_vpp tag. A build without the tag refuses the configuration and names the tag.

Ze checks each selection against the features under it. Ze does not compare the selections with each other. For example, a configuration with interface backend vpp and the default firewall backend nft commits. The section Features that only program the kernel says what that combination does.

Summary

"Refused" means that the commit, the daemon start and ze config validate all refuse the configuration and name the path. "Not built" in the VPP column means that the feature has a kernel implementation only. Ze accepts its configuration and programs the kernel, whichever interface backend is selected.

Interfaces

interface backend selects the backend. The schema marks each node that only some backends implement, and the commit refuses a marked node that the selected backend does not implement.

A refusal names the path, the selected backend and the backends that implement the node:

<path>: feature not supported by backend "vpp" (supported: netlink)

On VPP, BGP still uses Linux sockets. The VPP Linux Control Plane plugin shows each VPP interface to Linux as a TAP device, and BGP binds on that device. The VPP guide describes the namespace limit of that arrangement.

Routes and MPLS

One plugin writes routes for each data plane: fib-kernel for the kernel and fib-vpp for VPP. Ze refuses a second writer for the same data plane. fib p4 is in the schema and reaches no data plane today.

Feature Kernel (fib-kernel) VPP (fib-vpp) Limits
IPv4 and IPv6 routes from the system RIB ✓ ✓ VPP routes go to the table that fib vpp table-id names.
Automatic writer for static, OSPF, IS-IS, LDP, RSVP-TE and BGP EPE routes ✓ ✓ Ze loads the writer for the selected interface backend. A build without that writer refuses to start.
MPLS label push on an IP route ✓ ✓ The kernel must have MPLS support. Ze refuses to start when it does not.
MPLS transit swap and pop ✓ ✓ VPP uses MPLS table 0. VPP has no MTU for each route, so Ze does not install the path MTU of an entry and logs one warning.
MPLS push into a private table (RSVP-TE facility backup) ✓ Refused when the entry arrives VPP has no packet mark context.
SRv6 service routes ✓ ✓ VPP: one encapsulation policy for each Service SID. Ze allocates no egress Service SID and installs no remote endpoint behavior.
show mpls forwarding ✓ ✓ The command reads the data plane that interface backend selects.

fib vpp needs interface backend vpp. fib-vpp resolves each next-hop interface to a VPP interface index, and that lookup refuses while another interface backend is active. The commit does not check this pair, so the refusal comes when a route is installed.

Firewall and NAT

firewall backend selects the backend. The vpp backend translates filter chains to VPP ACL rules and NAT chains to VPP NAT44. It refuses at commit every rule that it cannot translate exactly, and the refusal names the table, the chain and the term.

Control-plane policing, policy routing, the local DDoS responder and the FlowSpec firewall bridge add their own tables to the same backend. The vpp backend checks those tables against the same limits when Ze applies them.

Traffic control

traffic control backend selects the backend. The vpp backend has no queueing scheduler. It builds each class as a VPP policer, and it refuses at commit what a policer cannot do.

Feature tc vpp Limits on VPP
htb, tbf ✓ ✓ At least one class. With more than one class, each class needs a protocol or dscp filter.
hfsc, fq, fq_codel, sfq, netem, prio ✓ Refused
Filter on protocol, dscp ✓ ✓ One value steers to one class.
Filter on mark ✓ Refused The Linux packet mark has no VPP equivalent.
Root rate of a qdisc ✓ Refused The class policers carry the rates.
Ingress policer ✓ Refused The L2TP shaper uses it for the upload rate of a subscriber.

Features that only program the kernel

These features have one implementation, and it writes Linux kernel state. They have no backend leaf, and the commit does not look at interface backend for them.

Feature What Ze programs
IPsec Kernel XFRM states and policies. The configuration has no way to select another IPsec data plane.
L2TP Kernel L2TP tunnels and PPP interfaces.
Flow export packet sampling A tc sample action on each listed interface, read through the kernel psample channel.
Policy routing ip rule entries, and firewall tables on the selected firewall backend.
firewall backend nft nftables tables in the kernel.
traffic control backend tc Queueing disciplines on kernel interfaces.
sysctl Kernel tunables. They are applied to the Linux kernel whatever the data plane, so a setting about kernel behaviour works the same on a VPP box. A key about packet forwarding, such as rp_filter, acts only on the packets that reach Linux, not on the packets VPP forwards.

With interface backend vpp, VPP owns the network cards and forwards transit packets itself. Linux sees a VPP interface only as the TAP device that the VPP Linux Control Plane plugin creates. A feature in the table above that handles packets then acts on the packets that reach Linux through that TAP device. It does not act on the packets that VPP forwards. Ze accepts such a configuration today and does not warn about it. sysctl is the exception for settings about kernel behaviour: those apply to the Linux kernel as they do on any data plane.

To filter or shape the traffic that VPP forwards, select firewall backend vpp and traffic control backend vpp. IPsec, L2TP, flow export sampling and policy routing have no VPP implementation.

BFD and the DHCP server have no code that is specific to a data plane.
