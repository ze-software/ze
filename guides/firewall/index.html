Backend

Backend Platform Default Mechanism
nft Linux ✓ google/nftables netlink library
vpp Linux with VPP ✕ GoVPP ACL classify pipeline and NAT44-ED 
firewall {
    backend nft;
}

backend vpp needs the VPP component, which only a build with the ze_vpp tag carries. Selecting it starts that component with the firewall and orders the firewall after it; backend nft does not start it, though the firewall still starts after VPP when a vpp {} block runs it. In a build without ze_vpp, ze config validate, a commit and daemon boot all refuse firewall backend vpp before anything is applied, naming the leaf and the ze_vpp tag, where the config used to pass validation and fail at apply.

Clean-shutdown teardown

flush-on-shutdown controls whether stopping the ze process removes ze-owned tables from the kernel. It defaults to true: an orderly stop (SIGTERM, e.g. systemctl stop ze) tears the tables down so a stopped daemon leaves no rules behind. It keys off how the process exits, and is unrelated to BGP graceful restart -- that concerns only RIB/FIB route retention while a peer re-establishes and never restarts the daemon, so it never reaches this path.

Set it to false to use ze as a one-shot provisioner: apply the firewall (and interface) configuration, let the process exit, and leave the rules running in the kernel -- the way nft -f programs a ruleset and returns. Nothing is torn down when ze quits.

firewall {
    backend nft;
    flush-on-shutdown false;   # one-shot: program the rules, exit, leave them running
}

A crash (SIGKILL, panic, power loss) never runs the shutdown path, so ze-owned tables always persist across a crash regardless of this setting. The option governs every ze table producer that shares the backend -- the firewall component, control-plane-protection, policy-routes, and ddos-local -- and the firewall component performs the teardown as a single ordered actor so plugin table removal never races the backend close.

The reconcile deadline

Ze serializes the whole firewall reconcile: a snapshot of every owner's tables followed by one Backend.Apply, under one process-wide lock. The owners are the firewall component, control-plane-protection, policy-routes, and ddos-local. A dataplane call that never returns therefore does not stall one owner, it stalls all of them.

Each backend bounds one dataplane round-trip. Neither bound can be turned off. A value below the floor or above the ceiling clamps, and an unparseable value falls back to the default, because an unbounded call is the failure this guard exists to prevent. The ceiling is one shared constant, firewall.MaxBackendDeadline, which the latency histogram's last finite bucket is also derived from.

Backend Bounds Environment variable Default Range
nft One nftables netlink round-trip ze.firewall.nft.netlink-timeout 10s 1s to 60s
vpp One VPP binary-API round-trip ze.firewall.vpp.reply-timeout 10s 1s to 60s

The VPP backend previously ran with no bound at all. govpp's default reply timeout is 0, which govpp documents as disabling the timeout, and Channel.ReceiveReply has no context arm, so a wedged VPP held the process-wide reconcile lock indefinitely.

When the deadline expires the apply fails, and ze logs an error saying the dataplane did not answer within the backend deadline and its ruleset is now behind the registry. That log sits outside the metrics path, so it is written whether or not telemetry is enabled.

A dataplane that is ABSENT is a different condition and is deliberately not reported as a timeout: VPP not running, or a connect wait that ran out, means the reconcile failed for a reason with a different fix, and there is no ruleset to be behind.

Metric Type Labels Meaning
ze_firewall_apply_duration_seconds histogram result Time spent in Backend.Apply. result is ok, timeout, error, or panic.
ze_firewall_apply_timeout_total counter Reconciles that failed because the dataplane did not answer within the backend deadline.
ze_flowspec_rules_refused_total counter reason FlowSpec routes received from a peer that did not become a firewall rule. reason is unknown-protocol, unsupported-component, unsupported-action, parse, or max-rules.

The result label is what separates a healthy-but-slow apply from one that gave up: a backend deadline of 10s and a 10s successful reconcile land in the same latency bucket, and only the label tells them apart. Both signals derive from one result value, so they cannot drift apart. A backend that panics is recorded as panic rather than lost or filed as healthy.

A refused FlowSpec route is otherwise invisible: it is never registered, so no reconcile fails and show firewall has nothing to render. The peer believes ze filters the traffic and ze does not, which is what the counter reports.

Tables and Chains

Ze owns all tables whose kernel name starts with ze_. A table contains one or more chains; a base chain has a type, hook, priority, and default policy.

firewall {
    backend nft;
    table wan {
        family inet;
        chain input {
            type filter;
            hook input;
            priority 0;
            policy drop;
            term allow-ssh {
                from {
                    destination-port 22;
                    protocol tcp;
                }
                then {
                    accept;
                }
            }
        }
    }
}

Tables another feature installs

A ze_ table is not always one the firewall { } section declared. A feature that needs kernel state of its own publishes a table through the same backend, so it appears beside yours in show firewall ruleset <name> and is withdrawn with the configuration that asked for it.

system conntrack module <helper> is another: each listed helper publishes ze_conntrack_helpers (family inet) or ze_conntrack_helpers_ip (family ip, for helpers the kernel registers for IPv4 only). Each holds one ct helper object per kernel helper and transport, and prerouting and output chains at priority -5 that assign it by destination port, so the assignment runs before your own chains at priority 0. A chain of yours at a priority below -5 sees the connection before the helper is attached. The per-helper ports are in the configuration guide, system conntrack.

One example: a BGP peer configured with connection { ttl { max N; } } (RFC 5082 GTSM) gets ze_gtsm, an input chain with two kinds of term for that peer.

Term Matches Why
dangerous-<peer>-listen TCP from the peer to Ze's listen port with a TTL (IPv4) or hop limit (IPv6) below the peer's floor, then drop The SYN reaches the listener before the accepted socket carries its own floor, so a spoofed SYN would otherwise cost a SYN-ACK and a request socket
dangerous-<peer>-type<N>-quoted-<side> (IPv4 only) An ICMP error which quotes that peer's BGP session and arrives below the floor The related messages RFC 5082 Section 6.1 covers

A GTSM dynamic group gets one listen term per range, named dangerous-<address>-<length>-listen, with the range as its source and the group template's floor. A SYN to the listen port from any other source, or from the peer to any other port, matches no term: RFC 5082 Section 3 forbids dropping a packet GTSM classifies as Unknown.

A session source inside a wider GTSM range on the same port (a static peer, or a dynamic group whose range is longer) owns its own SYNs, because the listener gives the connection to that session. It gets a claimed-<source>-listen term that accepts its TCP to the listen port, after its own drop term when it has a floor and before the wider range's drop, so the range never judges it by the range's floor. The accept ends only the ze_gtsm chain; every other table still sees the packet. A prefix two sources share is judged only by the one the listener picks: a static peer before a group range of the same address, and the first of two groups whose ranges are the same prefix.

Every term carries a packet counter (the nft backend adds one to each rule), so show firewall ruleset gtsm shows how many below-floor SYNs each dangerous-...-listen term dropped.

The ICMP terms name the session by the header the error quotes (the peer as the quoted destination, and the BGP port), whoever sent the error. They therefore read the quoted header as a raw payload compare (@th,192,32 0xc0000202 is 192.0.2.2) and carry no ip saddr. show firewall ruleset gtsm lists the table, and removing the peer's ttl block removes its terms; the table goes with the last GTSM peer. The full list of table owners is in table ownership.

Table Families

inet (dual-stack), ip, ip6, arp, bridge, netdev.

A table of family arp sees the ARP header where the other families see the IP header, so a match that reads the IP header or the transport header behind it is refused there at verify: source-address, destination-address, source-port, destination-port, protocol, connection-state, connection-mark, tcp-flags, a named-set match, and the IRR and domain-group leaves. The error names the leaf and says "family arp carries no IP header"; move the term to a table of family ip, ip6 or inet. icmp-type, icmpv6-type and dscp keep their own family refusals.

A table name a feature installs is reserved for that feature, in every family, whether or not the feature is configured. A table of yours whose kernel name (ze_ + its name) is one of them, such as vrrp, vrrp_owner_arp, vrrp_owner_nd, copp or iface_rpf, is refused at verify with the owner that holds it: two owners in one kernel table would overwrite each other's chains. Rename the table. The reserved set depends on the features your build includes, because a feature compiled out of the build reserves nothing. The reserved names are listed in table ownership, Rule 2.

Chain Types

filter, nat, route.

Hooks

input, output, forward, prerouting, postrouting, ingress, egress.

destination-local matches a packet addressed to the router itself: its destination is an address the kernel holds on one of the router's interfaces when the packet is seen, so an address added later, such as one a DHCP client learns, matches with no commit. A packet the router forwards to another host does not match. A destination translation that carries it publishes a port of the router without capturing transit traffic to the same port:

firewall {
    backend nft;
    table publish {
        family ip;
        chain prerouting {
            type nat;
            hook prerouting;
            priority -100;
            policy accept;
            term publish-web {
                from {
                    protocol tcp;
                    destination-port 8080;
                    destination-local;
                }
                then {
                    dnat { to "192.168.10.5:80"; }
                }
            }
        }
    }
}

The nft backend lowers it to fib daddr type local. It is valid in a table of family ip or ip6, and verify refuses it in inet, arp, bridge and netdev. The kernel provides the lookup per family, and Ze's kernel is built with the ip and ip6 ones, so a dual-stack port is published by one term in an ip table and one in an ip6 table. The vpp backend refuses it at commit, because a VPP ACL has no lookup of the router's own addresses.

Literal source and destination prefixes must use the network address. For example, source-address 10.10.10.1/30 is refused because it matches the network 10.10.10.0/30. The error identifies the term and gives the corrected statement, source-address 10.10.10.0/30. The same rule applies to IPv6. To match one host, use /32 for IPv4 or /128 for IPv6. Named-set references such as source-address @trusted-hosts keep their existing behavior.

Offline validation, startup and configuration verify apply this check before the firewall changes. A refused reload keeps the active configuration and rules.

Protocol names

protocol takes one of ten names. The set is the same everywhere a protocol is matched: the firewall config, policy routes, DDoS mitigation terms and FlowSpec routes learned from a peer all resolve against one table, so a name that commits is a name every backend can program.

Name IANA number
icmp 1
tcp 6
udp 17
gre 47
esp 50
ah 51
icmpv6 58
ospf 89
vrrp 112
sctp 132

On a host that runs IPsec, a rule on esp keeps deciding on the peer's bare ESP. On a Child SA whose inbound state is UDP-encapsulated, Ze's ESP form fast path adds a UDP header to a whole bare ESP datagram at tc ingress, which Linux runs before every firewall hook, so a rewritten datagram would pass the rule as UDP to port 4500. The fast path therefore rewrites only while no nftables rule or chain policy on the input path (an ingress, prerouting or input base chain) could drop the peer's ESP. A term that drops or rejects protocol esp there, or a chain with policy drop that ESP reaches without an accept, keeps the fast path off: bare ESP reaches the rule as ESP, and what the rule lets through goes to the complete path, which is bounded to 5000 datagrams per second and arrives on ze-espform. show doctor reports it as doctor-ipsec-esp-form-firewall, naming the table, chain and term. To keep the fast path, accept protocol esp in a term ahead of the one that could drop it. Ze reads only the nftables ruleset, and learns of another program's commit only after it lands, so other filters and other programs have limits of their own. The known ones are rules loaded with iptables-legacy or with ebtables-legacy, BPF programs attached to a netfilter hook, tc programs Ze did not install, ip rule entries that select on ipproto esp, and commits from other programs: Both ESP wire forms lists each, with its fix. That list holds the limits known today, not every kind of filter a Linux host can run.

A protocol outside this set is refused where it enters. The config editor refuses it at commit; a FlowSpec route that names one is refused at translation, counted, and logged with the protocol number and the route key. Ze does not enforce a version of the rule with the protocol condition removed, because that rule is wider than the one that was asked for.

ICMP Type Names

Symbolic names for icmp-type: echo-reply, destination-unreachable, source-quench, redirect, echo-request, router-advertisement, router-solicitation, time-exceeded, parameter-problem, timestamp-request, timestamp-reply, info-request, info-reply, address-mask-request, address-mask-reply. Numeric values (0-255) are also accepted.

Symbolic names for icmpv6-type: destination-unreachable, packet-too-big, time-exceeded, parameter-problem, echo-request, echo-reply, mld-listener-query, mld-listener-report, mld-listener-done, nd-router-solicit, nd-router-advert, nd-neighbor-solicit, nd-neighbor-advert, nd-redirect, mld2-listener-report. Numeric values (0-255) are also accepted.

Interface Wildcard

A trailing * on an interface name produces a prefix match. For example, input-interface "l2tp*" matches any interface whose name starts with l2tp (l2tp0, l2tp1, l2tp-peer42, etc.). Without the *, the match is exact.

A PPPoE client is matched by its configured name. The session device of pppoe-client pppoe0 is the kernel device pppoe0 on every session and every reconnect, so output-interface "pppoe0" matches the WAN, as in a masquerade rule. Do not write ppp* for the client: the kernel names pppN only the subscriber sessions of an L2TP LNS or a PPPoE access concentrator, which have no configured name. On such a box, ppp* matches the subscribers and never the client.

TCP MSS Clamping

tcp-mss-set writes a fixed upper bound. tcp-mss-clamp-to-pmtu takes the bound from the route instead: the kernel computes it for each packet as the smaller of the MTU of the route the packet takes and the MTU of the route back to its source, less the fixed headers (40 bytes for IPv4, 60 for IPv6, as RFC 6691 asks). It is the nftables tcp option maxseg size set rt mtu, and what VyOS writes for adjust-mss clamp-mss-to-pmtu on an interface.

The lan-services topology scenario proves tcp-mss-set 1400 and masquerade on a CPE converted from VyOS: a SYN offering 1460 arrives at the server with 1400, one offering 1300 arrives unchanged, and the server sees the CPE's WAN address as the source.

Both forms are clamps. An MSS already at or below the bound is left alone, because the kernel skips a two-byte MSS write that would raise the value, and a SYN without the option is not changed. A term carries one of the two, never both.

The kernel computes the route MSS only at the forward, output and postrouting hooks. Verify refuses the leaf in a chain of another hook, and in a regular chain that a chain of another hook reaches through jump or goto, naming the table, the chain, the term and the hook it found. The table family must be ip, ip6 or inet. The vpp backend refuses both actions.

A home CPE behind PPPoE clamps every SYN it forwards onto the PPPoE session. The term matches TCP without a flags condition: only a SYN carries the MSS option, and a segment without the option passes unchanged. With the session MTU at 1492, a SYN offering 1460 leaves with 1452 over IPv4 and 1432 over IPv6:

firewall {
    backend nft;
    table cpe {
        family inet;
        chain forward {
            type filter;
            hook forward;
            priority 0;
            policy accept;
            term clamp {
                from {
                    output-interface "pppoe*";
                    protocol tcp;
                }
                then { tcp-mss-clamp-to-pmtu; }
            }
        }
    }
}

NAT rule placement in nftables

ze config validate checks NAT placement before the nft backend installs the rules. NAT base chains use family ip, ip6 or inet, a priority greater than -200 so connection tracking runs first, and one of the hooks below.

Action Allowed hooks
snat input, postrouting
masquerade postrouting
dnat, redirect prerouting, output

When a NAT term is in a regular chain, every base chain that reaches it by jump or goto must have type nat and an allowed hook. A regular chain with no entry path passes the hook and chain type checks. An ip or ip6 table requires a target address from that family. An inet table can use a target from either family, and that rule translates only that family.

If a term fails validation, the error identifies its table, chain and term. For a regular chain it names the offending base chain when an entry path caused the refusal.

NAT Exclude

In a NAT chain, exclude emits a Return verdict so matched traffic skips the NAT translation. This replaces the VyOS nat destination rule N exclude pattern.

firewall {
    backend nft;
    table nat-rules {
        family ip;
        chain prerouting {
            type nat;
            hook prerouting;
            priority -100;
            policy accept;
            term skip-local {
                from {
                    destination-address 10.0.0.0/8;
                }
                then {
                    exclude;
                }
            }
            term dnat-web {
                from {
                    destination-port 80;
                }
                then {
                    dnat { to "10.1.1.1"; }
                }
            }
        }
    }
}

Control-plane protection (CoPP)

control-plane-protection bgp builds its own table, inet ze_copp, beside the firewall component's tables. It is an access list on TCP to the protected ports (179 unless protected-port says otherwise), as RFC 7454 Section 4 recommends:

  • an established or related connection is accepted;
  • a connection from a trusted-source prefix is accepted;
  • a connection from a configured BGP neighbor is accepted: the remote ip of each static peer and the range of each dynamic group, read from the bgp configuration, so adding or removing a peer updates the list on reload;
  • TCP to a protected port from any other source is counted and dropped.
set control-plane-protection bgp rate 100/second
set control-plane-protection bgp trusted-source 203.0.113.10/32

rate is optional and limits new connections from the neighbors only. over-limit-policy defaults to drop; set accept to observe a new rate before you enforce it. Neither setting admits an unknown source. Without the control-plane-protection bgp container Ze builds no access list. The chain policy stays accept, so SSH, ICMP and every port the table does not name stay reachable. ze doctor names any part of ze_copp the kernel does not hold. Design: CoPP for BGP.

Changed from earlier builds, for a configuration you carry forward:

Before Now
rate was mandatory rate is optional; without it the table is the access list alone
over-limit-policy defaulted to accept, which counted and admitted it defaults to drop; write accept to keep the old behaviour
a trusted term's name carried the prefix as written. trusted-192.0.2.0/24 it is trusted-192.0.2.0-24: / and : are written -, because the firewall's name check refuses both
any source could open a connection to a protected port only a configured neighbor or a trusted-source can

Global Options

The global-options container provides keyword toggles for common network security defaults. Each keyword maps to a kernel sysctl. At config apply time, the firewall component emits these as sysctl defaults via EventBus. Explicit sysctl { setting { ... } } entries always override global-options (three-layer priority: config > transient > default).

firewall {
    backend nft;
    global-options {
        all-ping enable;
        syn-cookies enable;
        source-validation strict;
        log-martians enable;
    }
}
Keyword Sysctl enable disable
all-ping net.ipv4.icmp_echo_ignore_all 0 (allow) 1 (ignore)
broadcast-ping net.ipv4.icmp_echo_ignore_broadcasts 0 (allow) 1 (ignore)
syn-cookies net.ipv4.tcp_syncookies 1 0
receive-redirects net.ipv4.conf.all.accept_redirects 1 0
send-redirects net.ipv4.conf.all.send_redirects 1 0
source-validation net.ipv4.conf.all.rp_filter disable=0, strict=1, loose=2 -
log-martians net.ipv4.conf.all.log_martians 1 0
ipv6-receive-redirects net.ipv6.conf.all.accept_redirects 1 0

IRR Prefix-List Filtering

Firewall rules can match traffic by ASN or AS-SET using IRR-resolved prefix lists. The firewall-irr plugin fetches nothing. The irr plugin fetches, schedules and stores every list a consumer enforces, under the settings of system irr (docs/guide/irr-filtering.md); firewall-irr tells it which lists the firewall rules name, reads what it stored, and populates nftables interval sets. BGP and the firewall naming the same AS-SET share one stored copy, and the stored copy survives a restart: the firewall programs it at start without asking the IRR server again.

Operator Workflow

  1. Fetch prefix data: update irr asn 13335
  2. Inspect what is stored: show irr, and what the firewall enforces: show firewall irr
  3. Commit a term whose from-block names the ASN:
firewall {
    backend nft;
    table wan {
        family inet;
        chain input {
            type filter;
            hook input;
            priority 0;
            policy drop;
            term from-cloudflare {
                from {
                    source-asn 13335;
                }
                then {
                    accept;
                }
            }
        }
    }
}
  1. Fetch every referenced list again now: update irr all

Fetch the data first. The commit is refused while the ASN or AS-SET has nothing stored, and the refusal names the reference and the command that fetches it. A commit sends no IRR query itself. A term reaches the kernel as two rules, one for the IPv4 prefixes and one for the IPv6 prefixes, so the table family must be inet.

The prefix sets belong to the firewall-irr plugin, not to the table that names them. The two arrive at different times, and that one table waits: while a rule names a set no owner has registered, the table holding it is not programmed and the daemon logs table held back. Every other table is programmed as usual. The plugin registers the sets moments later and the table lands.

That line staying in the log means the prefixes never arrived. show firewall irr says which reference is missing, and update irr asn <N> or update irr as-set <name> fetches and stores it; the firewall programs the table on the irr plugin's notice. On a fresh install the irr plugin fetches every referenced list at its first start, and refreshes each one every system irr refresh-interval seconds (3600 by default, 0 for manual only).

Config Leaves

Leaf Type Description
source-asn uint32 (1-4294967294) Match source address against IRR-resolved prefixes for this ASN
source-as-set string Match source address against IRR-resolved prefixes for this AS-SET
destination-asn uint32 (1-4294967294) Match destination address against IRR-resolved prefixes for this ASN
destination-as-set string Match destination address against IRR-resolved prefixes for this AS-SET

IRR Settings

The IRR server, the source address and the refresh period are the irr plugin's, set once for BGP and the firewall:

system {
    irr {
        server whois.radb.net;
        refresh-interval 3600;  /* 0 = manual only; 60-86400 = seconds */
    }
}

The PeeringDB endpoint asked for a bare ASN is system peeringdb url. firewall irr holds only the interface bindings; it has no server, URL or interval of its own.

A commit is refused when a referenced ASN or AS-SET has nothing stored, or a stored list holding no prefixes, with an error naming the reference and the command to run:

firewall irr: nothing is stored for as-set AS-CUSTOMER-A
fix: update irr as-set AS-CUSTOMER-A

A daemon start reads its configuration without that check, because a commit is what runs it. The firewall then programs what is stored, and a reference with nothing stored is held back until the irr plugin stores its list.

A refresh that fails, or that succeeds without returning prefixes, keeps the stored list in force: an empty answer never replaces a stored prefix list, because a filter built from an empty list drops everything the operator wrote it to accept. The irr plugin counts each fetch under ze_irr_refresh_outcomes_total, and a fetch that panics costs that fetch, not the plugin, and counts under its panic label.

One firewall set holds 500000 prefixes, and each family has that bound of its own. A reference whose IPv4 or IPv6 list is longer is refused: the commit fails, the apply fails, and the sets already programmed stay in force. Ze does not program a part of the list, because a set that holds part of it drops traffic an accept rule was written to pass, and passes traffic a drop rule was written to block. Narrow the reference, or clear it.

show firewall irr reports each reference as ok, stale, oversized, unreadable or missing, with the stored copy's as-set, server, generation, counts, data-age-seconds, and stale-since for a stale one. ze doctor reports the same conditions:

  • doctor-firewall-irr-stale-data: a reference is enforcing prefixes the IRR has stopped confirming.
  • doctor-firewall-irr-no-data: nothing is stored for a reference, or a list with no prefixes, so it filters nothing.
  • doctor-firewall-irr-oversized-data: a reference is longer than a firewall set holds, so the rules naming it are not programmed.
  • doctor-firewall-irr-stored-copy-unreadable, -stored-copy-behind, -interest-unsaved and -not-programmed: what the running plugin could not read, apply or save.

Run ze show diagnostic <code> for the full description. ze_irr_data_age_seconds is the age of the oldest stored data.

Prefixes are removed only on purpose: clear irr asn <N> and clear irr as-set <name> remove the stored copy, and the firewall drops the list on the notice. Use them when an AS-SET is deregistered upstream.

Per-Interface Source Validation

Bind an AS-SET to a customer-facing interface. Packets arriving on that interface with source addresses not in the AS-SET's IRR-resolved prefixes are dropped (ingress source validation, BCP 38).

firewall {
    irr {
        interface eth1 {
            source-as-set AS-CUSTOMER-A;
        }
        interface eth2 {
            source-as-set AS-CUSTOMER-B;
        }
    }
}

The plugin generates a ze_irr_iface table with a prerouting base chain. For each bound interface, accept terms match input-interface + source-address in set for both IPv4 and IPv6, followed by a drop term for that interface. Unconfigured interfaces pass through unfiltered (chain policy accept).

A binding whose AS-SET has no prefixes produces no terms at all, not a lone drop term. A lone drop term would drop every packet arriving on the interface while the apply reported success, so one unhelpful answer from an IRR server would take a customer-facing port down. The plugin logs the skipped binding, and config commit rejects the binding before it gets that far.

The same reasoning covers one family. A refresh that returns IPv4 prefixes and nothing for IPv6 keeps the last known good IPv6 list, so the IPv6 accept term stays and the drop term does not become the only rule for that family.

Same fail-closed semantics apply: config commit rejects if any bound AS-SET has no cached prefix data. Removing an interface binding removes its filter on the next apply.

DNS-Sourced Address Groups

A domain group holds one or more DNS names, and its nftables set holds the addresses those names resolve to. The firewall-domain plugin asks the daemon's resolver for each name, programs the answers, and asks again when that answer expires. An operator who wants to permit or deny a service that publishes its addresses in DNS writes the name once instead of transcribing addresses and re-transcribing them each time they move.

A permit rule keyed on a DNS name trusts whoever controls that name. Ze caps what one name may contribute at 64 addresses per family and honors the hub's DNSSEC setting, and it does not otherwise constrain what a name resolves to. That is an operator decision, and dnssecDecision does no signature validation of its own: it sets the EDNS0 DO bit and trusts an upstream validating resolver.

Operator Workflow

  1. Resolve the group: update firewall domain-group cdn
  2. Inspect what it holds: show firewall domain-group cdn
  3. Commit a term whose from-block names the group:
firewall {
    backend nft;
    domain-group cdn {
        domain-names [ api.example.com cdn.example.com ];
        ttl-floor 300;
    }
    table wan {
        family inet;
        chain input {
            type filter;
            hook input;
            priority 0;
            policy drop;
            term from-cdn {
                from {
                    source-domain-group cdn;
                }
                then {
                    accept;
                }
            }
        }
    }
}

Resolve the group first. The commit is refused while its names have never resolved, and the refusal names the group and the command that resolves it. A term reaches the kernel as two rules, one for the IPv4 addresses and one for the IPv6 addresses, so the table family must be inet.

The sets belong to the firewall-domain plugin, not to the table that names them, so the same hold-back behavior the IRR section describes applies here.

Config Leaves

Leaf Type Description
domain-group <name> list An address group whose members are what its DNS names resolve to
domain-names leaf-list of string (1-255) The DNS names whose addresses fill the group
ttl-floor uint32 (1-86400), units seconds Shortest interval Ze waits before resolving a name again. Default 60
source-domain-group string (1-64) Match source address against the group's addresses
destination-domain-group string (1-64) Match destination address against the group's addresses

Refresh Schedule

Each name is re-resolved on its OWN answer TTL, and each family keeps its own schedule: a name with an A record at 60 seconds and an AAAA record at an hour is asked for on both clocks, and a change in one family does not reprogram the other. ttl-floor is the shortest Ze will wait whatever the answer says. A TTL of 0 means "do not cache" rather than "expired now", so it waits the floor too and does not spin.

The set is reprogrammed only when the addresses actually CHANGED. A name that keeps answering the same addresses costs one query and one write of its stored expiry (Restart and Recovery, below), so a 60-second TTL does not rewrite the kernel's sets 1440 times a day.

What a Failed Lookup Does

The response code decides, and the four outcomes are different:

The answer What Ze does
NOERROR The addresses are what the group holds. An empty answer is an empty set for that family
NXDOMAIN The name is gone. Its addresses are emptied and the change is recorded
SERVFAIL, REFUSED, any other code The server could not answer. The last good addresses stay
✕ The query never reached a server. The last good addresses stay

Only NXDOMAIN empties a set, because only NXDOMAIN says something about the NAME. Emptying on a SERVFAIL would enforce a DNS outage: for a permit rule that blocks every source the rule was written to allow.

Addresses are removed on purpose with clear firewall domain-group <name>, which drops them from memory and from zefs and re-applies the tables. Use it when a name is gone upstream for good.

The Change Log

Every change in what a name resolves to is appended to <config-dir>/firewall-domain-group.dns.jsonl, one JSON object per line, carrying the group, the name, the family, the addresses before, the addresses after, and the time. It answers "what did this name point at last week".

Only a CHANGE is recorded. A refresh that confirmed the same addresses writes nothing. The log keeps its most recent 10000 records and drops the oldest past that, so a name whose addresses rotate cannot fill the disk.

It is deliberately not the operator audit log (<config>.audit.jsonl). That log records operator actions and is bounded by how often a person acts; a rotating name is neither, and sharing the file would evict commit history.

Restart and Recovery

Resolved addresses are kept in zefs, so a box that reboots with its upstream DNS unreachable programs its domain-group sets from what it learned last time and resumes filtering without waiting for a query.

Each stored answer also keeps when it expires: the time it arrived plus its TTL, never less than ttl-floor and never more than a day. A restart asks again only for the names whose stored answer has expired, and asks for each of the others when its own expiry comes, so a reboot enforces the same addresses it enforced before. Every answer renews the stored expiry, including one that confirms the same addresses, so a name at the 60-second floor writes its entry up to 1,440 times a day per family. A name stored by a Ze that predates the expiry is asked for once at start.

The plugin runs as its own process: a panic while handling an answer costs one refresh cycle rather than the process, and a crash starts the plugin again with the cache intact: the plugin declares failure-policy: restart, and the cache is in the shared zefs store rather than in the process.

Observability

show firewall domain-group [<name>] reports each group with its names, the addresses being enforced per family, when those addresses were recorded (last-resolved), and what the last answer said. A family reads missing until it has been asked for once, which is a different fact from a family that answered and holds nothing.

ze doctor reports four codes:

  • doctor-firewall-domain-group-no-data: a referenced group has no addresses, so the rules naming it filter nothing.
  • doctor-firewall-domain-group-stale-data: a name in a referenced group has not resolved for more than a day, and Ze is still enforcing the addresses it learned before.
  • doctor-firewall-domain-group-unreadable-data: a stored answer of a referenced group cannot be read, so its name's addresses are missing from the set until the next answer rewrites it. update firewall domain-group <name> resolves it now.
  • doctor-firewall-domain-group-unsaved-answer: an answer could not be written to the store. The name goes on enforcing the addresses it held before, and a restart does not have the newer answer. The finding names the store error. Fix that cause, then run update firewall domain-group <name>. The next write that succeeds clears the finding. Only the running daemon reports this one, because only the plugin's process knows the write failed.

Run ze show diagnostic <code> for the full description. Four metrics carry the same state: ze_firewall_domain_group_addresses_cached, ze_firewall_domain_group_refresh_outcomes_total (labels unchanged, changed, nxdomain, error, panic), ze_firewall_domain_group_last_refresh_timestamp, which moves only when a refresh changed the addresses, and ze_firewall_domain_group_data_age_seconds.

Lifecycle

The firewall component registers with ze's engine via registry.Register. On boot and config reload, the reactor parses the firewall { } section, loads the selected backend, and calls Apply([]Table). On failure, sdk.Journal triggers a rollback to the previous state.

On a clean shutdown the component removes every ze-owned table (unless flush-on-shutdown false; see Clean-shutdown teardown), then closes the backend. Because the firewall component owns the shared backend, it is the single actor that performs this teardown -- plugins that register tables (control-plane-protection, policy-routes, ddos-local) do not run their own shutdown withdrawal, so table removal never races the backend close. A crash bypasses this path entirely, leaving tables in place.
