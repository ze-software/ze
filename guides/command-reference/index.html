This page explains the command model. For a live list of every command, run ze help command. ./le cli catalog update file <destination> writes the Markdown catalog from the same live registries.

ze help lists each top-level command name once. A command registered as a root keeps its owner's section and summary when the YANG tree also declares that name. Other YANG verbs appear under Operations.

For the generated cross-vendor migration view (Junos MX, Cisco IOS XR, Nokia SR OS, and VyOS), use the website's Command Equivalents page. The native renderer joins the live command registry with the curated vendor mapping in website/data/command-equivalents.json, so a new Ze command appears as unmapped until its vendor equivalents are added.

Conventions

Every command that takes a filename argument accepts - as an alias for stdin when reading and stdout when writing, so configs and data stream through pipes without temp files:

generate | ze config show -                 # read a config from stdin
ssh host cat rib.mrt | ze analyze show -    # analyse an MRT streamed in
ze config show - | ze config set - bgp session asn local 65001 | ze config validate -
ze config migrate -o - router.conf          # write the set form to stdout

stdin can be consumed once: a second - in a single command fails with a clear error rather than reading empty. A file literally named - is addressed as ./-. Interactive/history-dependent editor commands (ze config edit, ze config rollback, ze config history) reject - because they need a TTY or on-disk revision history that a pipe does not have.

When the input is on another machine, the daemon can inspect supplied bytes without reading a caller-named path. Use show config supplied dump, validation, fmt, graph, migrate, fix-plan or source with content <base64> and an optional name <filename> diagnostic label. Dump also accepts strip-private; fmt accepts check or diff. These read-only commands use the same producers as the file commands and do not stage or apply configuration.

Supplied migrate accepts format set|hierarchical; fix-plan returns repair candidates without applying them. Supplied source accepts an optional quoted path, such as path "bgp peer edge", and shows the masked source subtree before inheritance is resolved. These three also have daemon-host file forms under show config <operation> file <path>; remote filenames are confined to the daemon's configuration directories. Supplied input is at most 195,840 decoded bytes, and produced remote text is at most 8 MiB; larger conversions remain available through the local command on the host holding the file.

Daemon-host file commands that return complete configuration bytes or resolved values require edit authorization: show config dump, fmt, migrate, set, activate, deactivate and replace. They can return credentials, including reversible $9$ values. Permission is checked before the file is read, even when the requested form is a preview or strips private values. Caller-supplied forms remain read-authorized because their input belongs to the caller. show config source provides the read-authorized, masked view of a host file; an unparseable host file is refused because its secrets cannot be masked.

show config supplied diff content <base64> compares one encoded JSON object with before and after fields containing the two native configuration strings. Encode the whole object once. The combined object, or one ordinary source, is limited to 195,840 bytes before base64 encoding. The encoded content is masked in command records.

To change a detached source without changing the router, use show config supplied set, activate, deactivate or replace. Encode one JSON object containing before and after strings as content. For the editing verbs, before is the source configuration and after is one matching command, for example set bgp router-id 192.0.2.1. For replace, both are complete configuration sources. The result is configuration text to download or pass to another tool. dry-run returns the masked diff instead. Replacement validation warnings remain visible with either result. Invalid values, paths, replacement configurations and multiple commands are refused without changing a file or the live candidate. The registered browser forms accept the two inputs directly and compose the encoded request.

MRT analysis (le mrt show, density, and content filters) derives mixed-family ADD-PATH decoding from both actual directional OPEN messages in the same input. Missing or ambiguous negotiation is an explicit decoding error, not a successful partial count or filter nonmatch. Input files never inherit another file's session context. Replay, inject and serve do not negotiate ADD-PATH; they refuse Path-Identifier-bearing or ambiguous UPDATEs before writing them. Empty EOR messages remain safe to replay even under an ADD-PATH MRT subtype. An empty MP family still counts when deciding whether a mixed UPDATE needs both OPENs. BGP4MP replay also refuses trailing bytes beyond the declared BGP length and structurally truncated attributes, even with complete OPEN context.

Shell Commands

Run directly from the terminal. No daemon required (except ze signal, ze status, ze cli, and daemon-targeted ze show subcommands). Some ze show subcommands run locally: version, bgp decode, bgp encode, env, schema, yang, completion.

An external plugin's command is typed in the shell as any other command: ze show acme-monitor status. The ze binary does not hold it, because the plugin brings it in its own YANG, so ze asks the running ze, whose answer, exit code and format keyword (ze show acme-monitor status json) are those of ze cli -c "show acme-monitor status". A path the running ze does not know either is refused as an unknown command. With no ze running, ze starts no plugin: when the stored config declares an external plugin, the command is reported as not available, naming the plugin, why no ze answered, and the fix (ze start when none runs); otherwise it is an unknown command. Help and shell completion of such a command need the running ze: use ze cli.

ze

Start the daemon or access subcommands. When invoked with no arguments in an interactive terminal, shows a navigable menu of all commands grouped by section. When piped or scripted (stdin is not a TTY), prints static help and exits 1.

ze                               # Interactive command menu (TTY only)
ze start <config-file>           # Start daemon from a config file (keyword-first)
ze start                         # Start from the stored active config
ze -                             # Start daemon reading config from stdin

ze start <config-file> reads that file on every start. It creates database/ beside the file only when neither a tree nor a legacy blob exists. Daemon commits update that file and stored history. An external edit causes a commit conflict. Bare ze start reads the stored active config instead.

ze - does not create a missing store. Without a store, it uses a temporary in-memory CA and reports unavailable persistent features.

The bare ze <config-file> form was removed: a free-form path in the first position can collide with a command name (a config file named bgp or signal would dispatch as that command). Use ze start <config-file>. Reading config from stdin (ze -) is unaffected.

-f <file> Start from an explicit config file
--plugin <name> Load plugin before starting a YANG/native config (repeatable). Hub/orchestrator configs reject this; use plugin { internal ... } or plugin { external ... } in the config instead.
--pprof <addr:port> Start pprof HTTP server
-V, --version Show version (also available as ze show version)
--chaos-seed <N> Enable chaos self-test mode

--color Force colored output (even when not a TTY)

ze config validate

Validate a configuration file without starting the daemon.

ze config validate <config-file>
ze config validate -q <config-file>     # Quiet: exit code only
ze cli -c "show config validation <config-file> | json"   # the same verdict as JSON
Flag Purpose
-v Verbose output: a summary of a valid config, with one line per BGP peer
-q Quiet mode (exit code only)

The -v summary shows each BGP peer as the daemon builds it, after group inheritance and defaults: its name, address, remote AS, group, and any connection direction turned off. A peer the daemon skips is listed as incomplete instead, with the setting it lacks after inheritance (a remote IP, a remote AS, or a peer-level ip dynamic, which only a group accepts). A missing global local AS never reaches the summary: validation refuses it first.

Peers:
  - edge-a 192.0.2.1 AS64500 group edge
  - edge-b 192.0.2.2 AS64501 group edge (connect disabled)
  - bare-a: incomplete, the daemon does not start it: missing required session > asn > remote

Exit codes: 0 = valid, 1 = invalid, 2 = file not found.

A value the schema does not accept (outside an enumeration, a range, a length or a format, a list key included) is refused with the line, the setting's full path, the value, the accepted values with their help or the bounds or the format in words, a closest match when one is close, and a last line that is the file line to write:

line 11: ospf interfaces interface eth0 cost: "0" is outside the accepted range
cost accepts a value in 1..65535
fix: cost <1..65535>;

In a set-format file the fix is the set line, corrected. In the JSON form each such refusal is one diagnostic whose code names its kind (config-yang-enum, config-yang-range, config-yang-length, config-yang-pattern) and whose fix holds the fix line. Every kind, with examples: Value refusals.

Validation includes the commit-time backend capability gate: a config whose active backend leaf does not implement a feature it uses (e.g. backend vpp with a bridge, tunnel, wireguard, veth, or mirror entry) is rejected with one error per offending YANG path, matching the diagnostic the running daemon produces on reload. See Backend Capability Errors.

Some refusals are about the machine running the command, not about the file. Each carries a code of its own, so a config written for a router and validated on a workstation is not mistaken for a broken one; the same file validates on the host it is written for:

Code When
config-kernel-capability The config uses a subsystem this kernel cannot carry
config-node-other-os The config uses a node the schema holds only on another operating system (interface xfrm, interface pppoe-client and mirror exist only on Linux). The message names the node and its OS, and says to validate on that OS
config-host-backend A subsystem names no backend and this OS has no default (interface, firewall and traffic-control default to netlink, nft and tc on Linux only), or a hardware inventory a verifier reads (the CPU list for VPP) is absent here

ze show diagnostic <code> explains each one.

Validation warns, and still exits 0, for every EBGP peer direction that has no explicit import or export policy. RFC 8212 Section 3 closes that direction: Ze uses none of the routes the peer sends, or sends it none, so the session comes up and carries nothing. The warning uses the words of the daemon's establishment warning and names the editor command that adds a policy at the level the peer is configured at (RFC 8212 default):

configuration valid: router.conf

Warnings:
  warning: peer transit-a: RFC 8212: this EBGP peer has no import policy, so Ze uses none of the routes it receives from it; to exchange routes, run `set bgp peer transit-a filter import final accept`, then `commit now`
    fix: set bgp peer transit-a filter import final accept

Every finding that carries a fix prints it on a line of its own under the message, after fix:. A finding that also says why it matters prints that line first, as an operator error does: problem, why, then the fix.

Validation also warns when an IBGP peer has an eligible ordinary selecting owner and no export policy. Ze sends that peer no routes learned from other peers, while local announcements remain permitted. This warning uses doctor-bgp-learned-export-no-policy and names the editor command that adds the policy. An eligible explicit role, an internal peer without an ordinary owner, and a configured accepting or rejecting export policy raise no internal absence.

A dynamic group with no remote AS is judged only when each member's OPEN says whether it is EBGP. Its configuration alone cannot determine that session type.

ze config

Configuration management.

Editing:

ze config edit [file]            # Interactive editor
ze config edit --backup <artifact> [name]  # Edit a config inside a backup, no daemon
ze config set <file> <path> <value>
ze config set --backup <artifact> <name> <path> <value>
ze config deactivate <file> <path>  # Mark a node inactive (kept in file, skipped at apply)
ze config activate <file> <path>    # Clear the inactive flag on a node

deactivate and activate accept any node type: leaf, container, list entry, or leaf-list value. The deactivated node round-trips through save/load and is skipped at apply time. See docs/guide/config-deactivate.md.

Inside the editor (ze config edit, the SSH session, the web terminal and the web CLI bar), top alone moves to the root, and top <command> runs that one command as if at the root and leaves you where you are: top set bgp router-id 192.0.2.9, top show, top show | errors, top delete <path>, top run <command>, top load terminal relative merge. Only a command that moves you keeps its move, so top edit bgp goes to bgp. A fix line the editor prints inside an edit context reads top set <full path> ..., which is exact from any position. The editor commands are in Configuration Editor.

Storage:

ze config import <file>...       # Import files into the database
ze config import --name <n> <file>  # Import under a different name
ze config import --yes <file>...  # Replace existing configs without asking
ze config rename <old> <new>     # Rename a config in the database
ze config list                   # List stored and nearby configuration files
ze config list --backup <artifact>  # List the configs inside a backup
ze config cat <key>              # Print database entry

Configuration listing fails if the store or a searched directory cannot be read; it reports the cause and returns no partial list. A missing optional configuration directory is allowed, as is a genuinely empty store. The backup form lists only stored records and does not scan nearby host directories.

While ze runs and owns the store, ze config import sends each input to the daemon as update data config name <name> content <base64> after the same name checks and confirmation, and prints the same lines; an input over 195,840 bytes stops it before anything is sent. With ze stopped, an import into a config whose confirmed commit a stopped daemon left open is refused, naming ze start <config>. Configuration Editor gives the whole contract.

Inspection:

ze config validate <file>        # Validate configuration file
ze config show <file> [path...]  # Show the config tree at a path (one-shot)
ze config dump <file>            # Dump parsed configuration
ze config dump --strip-private <file>  # Same, with every secret masked
ze config diff <f1> <f2>         # Compare two configs
ze config diff <N> <file>        # Compare with rollback revision
ze config fmt <file>             # Format and normalize
ze config show --backup <artifact> <name> [path...]  # Read a config inside a backup
ze config diff --backup <artifact> <N> <name>        # Diff inside a backup

ze config diff and show config diff compare every part of the two configurations: the bgp block as resolved values (a value a peer inherits from its group shows on the peer, at peer/<name>/...), every other root as written (~ plugin/hub/client/edge-01/host: 10.0.0.1 -> 10.0.0.2), and the order of every ordered-by user list. A changed secret is listed with /* SECRET-DATA */ on both sides.

For a config that declares an external plugin, validate, dump, diff, fmt and graph ask the running Ze first, since only it holds that plugin's schema, and print its answer as a local one; --user <name> names the account that asks. With no Ze running they answer from the schema compiled into ze, and refuse a section of the plugin with the reason and one fix (docs/plugin-development/schema.md, "What works today").

From a daemon surface (SSH, the web, MCP, REST, gRPC) the daemon runs show config dump, validation, diff, history, graph and fmt only on a file inside the configuration directories show config list searches, never on standard input (-), and never rewrites a file with fmt -w; the refusal names the local ze command to run where the file is. The secret mask is the keyword strip-private there: show config dump strip-private <file>, and fmt --check and --diff are the keywords check and diff: show config fmt diff <file>. The diff arrives as the answer's warnings.

show config validation file <file> pending checks the saved <file>.draft, as ze config validate --pending <file> does locally. The daemon checks that the draft itself stays inside the allowed directories before reading it. show config history file <file> lists the selected file's stored revisions; the positional file spelling also remains available.

ze config rename <old-name> <new-name> moves the complete stored configuration, including its versions, pointers and saved editor work. If a daemon owns the store, it sends request data config rename old <name> new <name> to that daemon. The daemon refuses its running configuration and configured managed client identities. Destination collisions and unfinished publication intents also refuse the operation. A successful daemon answer must identify both requested names before the local tool reports success.

--backup <artifact> points edit, show, diff, set and list at the configs inside a backup artifact instead of the live store, with no daemon. A commit or a set publishes a new version and its pointers into the artifact, and the artifact's lock refuses a second writer. --backup with -f is refused. See "Backup mode" in docs/guide/config-editor.md.

show is the one-shot, non-interactive way to inspect a config subtree: ze config show ze.conf bgp peer edge1 prints only that subtree (list entries are addressed by key). With no path it prints the whole parsed tree; --json emits the subtree as a JSON object. Shell completion for the path tokens is served by the ze config completion engine (ze completion bash|zsh|fish).

Shell completion (--family, config sections):

ze completion flags <command path>   # Flags a subcommand accepts (registry inventory)
ze completion families               # Address families (completes --family <TAB>)

The generated bash/zsh/fish scripts (ze completion <shell>) complete subcommand flag names from the registry inventory and --family values from the address-family registry. Each record is the candidate, a tab, the summary, a newline. A summary carrying a tab or a newline is folded to single spaces, so one candidate never reads as two.

History:

ze config history <file>         # List rollback revisions
ze config rollback <N> <file>    # Restore revision N
ze config archive <name>         # Trigger the daemon's named config archive

Rollback uses the one-based revision order shown by history, including the active version when recorded. A stored rollback publishes a new active version and retains the previous active version as rollback. If a daemon owns the store, the local command sends request data config rollback name <name> revision <N> to that owner and requires a complete matching response before reporting success.

The daemon stages and reloads its running source. Other stored names commit without a reload. A loose file restores directly from its folder's history when that store has no daemon owner.

Form conversion:

ze config migrate <file>                        # Rewrite in the set form
ze config migrate format hierarchical <file>    # Rewrite as nested blocks

ze config migrate reads a config in either form and applies the format conversions --list names; Ze writes the conversion of one format change only once it has a stable release, so none is registered today. An ExaBGP config is converted by ze exabgp migrate (below).

Flag Purpose
-f Edit a loose file offline without bypassing store ownership
-o <output> Output file (migrate)
format <form> Output form, typed before the file: set (default) or hierarchical (migrate)
--dry-run Show which conversions the file needs without writing (migrate)
--list List the format conversions this binary carries (migrate)

ze secret

Decode a $9$ secret to its plaintext, or encode a plaintext. A ze:sensitive leaf (a BGP MD5 password, an API token, a pre-shared key) is stored in the reversible $9$ form, and every display path masks it. ze secret decode gives the operator the actual key from a config. It works offline, reads no config. The daemon forms below convert caller-supplied values with the same codecs.

ze secret decode '$9$...'        # Print the plaintext behind a $9$ value
ze secret decode -               # Read the $9$ value from stdin
ze secret encode '<plaintext>'   # Print a $9$ value for a plaintext
ze secret encode -               # Read the plaintext from stdin

Put the value in single quotes: an unquoted $ starts a shell variable, and the shell changes the value before ze sees it. Pass - to read the value from stdin, so it stays out of the shell history. One trailing line ending is dropped from stdin. A value that starts with - reads as an option, so pass it on stdin.

A ze:bcrypt leaf holds a one-way hash ($2a$, $2b$, $2y$, and the crypt forms $1$, $5$, $6$). A hash keeps no copy of the password, so ze secret decode refuses it and names ze config set to set a new password. ze secret encode refuses a value that already starts with $9$, because the config reads such a value as encoded.

The corresponding daemon commands are show secret encode content <base64> and show secret decode content <base64>. They convert only the caller's supplied bytes with the same codecs; they read no daemon configuration or key. Their file and paste controls accept the value directly. API callers encode the operand as padded base64. Literal bytes are preserved unless trim-line-ending is selected, which drops the one trailing line ending that the standalone stdin form drops. The answer has the same final newline as the standalone command. Supplied operands are masked in command records; decoded plaintext is deliberately returned to the requesting caller.

Exit code Meaning
0 Success
1 The value cannot be decoded or encoded: a one-way hash, no $9$ prefix, a damaged $9$ value, or an empty value
2 Usage error (no value, two values, an unknown option or action), or stdin could not be read

request restart

ze request restart restarts the daemon in place through the same dispatcher as SSH and the browser CLI. It requires permission to run request restart. The daemon answers restart initiated before it prepares its graceful stop. With BGP, the existing restart action writes the graceful-restart marker and closes sessions without a shutdown notification. Starting the process again uses exit 75 after teardown. The generated systemd unit and gokrazy's normal supervision loop start the next process; a foreground caller must start it again itself. The command does not reboot the host and takes no arguments.

ze signal

Send commands to the running daemon via SSH.

ze signal restart                # Graceful restart (with GR marker)
ze signal reboot                 # Graceful shutdown + OS reboot (with GR marker, requires root on Linux)

Flag Purpose
--host SSH host (default: 127.0.0.1 or ze_ssh_host)
--port SSH port (default: 2222 or ze_ssh_port)

Exit codes: 0 = ok, 1 = not running, 4 = command failed. Reload is transactional: the daemon stages the new config as a candidate version, runs verification and apply, then promotes the candidate to active only after the runtime accepts it.

ze bgp

BGP protocol tools (offline, no daemon needed).

ze bgp decode <hex>              # Decode one BGP message from hex
ze bgp decode -                  # Decode one hex message for each line of standard input
ze bgp decode pcap <file>        # Decode every BGP message in a capture
ze bgp decode pcap -             # Decode a capture read from standard input
ze bgp encode <route-command>    # Encode route command to BGP hex
ze bgp plugin cli                # Plugin debug shell (5-stage handshake + interactive)
ze bgp plugin cli --name <name>  # Debug shell with custom plugin name

# Also available via YANG verb dispatch (no daemon needed), answering data:
ze show bgp decode <hex>
ze show bgp decode type open <hex>
ze show bgp encode <route-command>
ze show bgp encode family ipv6/unicast part nlri <route-command>

ze show bgp decode and ze show bgp encode answer data, so a pipe applies to them (ze cli -c "show bgp decode <hex> | json"), and their text rendering is the output ze bgp decode and ze bgp encode print. A decode answers each message as its hexadecimal and its decoding in the Ze event format; an encode answers the family, the part of the UPDATE it carries and the hexadecimal. A typed payload that does not decode is refused by show bgp decode, with the decoder's reason, on every surface; ze bgp decode prints that reason on stdout and exits 1, as it always has. The options keep working on both spellings, and each option that selects what is answered also has a keyword, which is the form a remote surface takes:

Command Option Keyword
decode --open, --update, --notification, --keepalive type <open|update|notification|keepalive>
decode --nlri <family> nlri <family>
decode -f, --family <family> family <family>
decode pcap <file> pcap <file>
decode --plugin <name> (repeatable) plugin <name>
encode -f <family> family <family>
encode -a <asn>, -z <asn> local-as <asn>, peer-as <asn>
encode -i path-id include
encode -n, --no-header part nlri, part body
encode --asn4=false asn-width two-octet

A choice given both ways is refused. --json on decode is a rendering option of the local command only. The forms that read standard input (decode -, decode pcap -, and encode with no route) need the local ze process.

A plugin named on decode is asked to decode every capability and NLRI before the registered decoders are, and the answer lists the plugins it was decoded under. The registered decoders answer what no named plugin decodes, so a registered plugin decodes its capabilities and families without being named. <name> forks ze plugin <name> --decode, ze.<name> runs the plugin in a goroutine and ze-<name> calls it in-process; a name no registered plugin decodes under is refused, with the names that do. --plugin /path/to/program runs a third-party program that answers the same decode capability <code> <hex> and decode nlri <family> <hex> requests on standard input. Only the local ze process runs a program path, so the plugin keyword takes a name.

The pcap keyword precedes the path, so the first word after decode is always a keyword or a hex payload and never an ambiguous file name. request plugin restart

Restarts a configured plugin without restarting ze, whether it runs or not. A plugin can stop for good on several paths: its failure policy left it stopped, the respawn limit disabled it, a restart failed, or its startup handshake failed. ze doctor names each such plugin under doctor-plugin-stopped, with this command as its fix. A running plugin can hold state only a new process clears: a config-committed it was never told of, an event it failed to apply, a post-startup callback it never received. ze doctor names this command as the fix of those rows too, and as the last step of a dropped subscription's fix, once the plugin subscribes in a namespace the build registers. A row that counts entries past what the doctor keeps names ze show log recent instead, which lists them. The command runs in the daemon.

ze request plugin restart <name>     # <name> is the plugin's configured name

The name may also follow its keyword, ze request plugin restart name <name>, which is the form the web admin page posts. Both forms are the same command.

Restarting a running plugin stops it, which cuts the commands it was serving, and starts it again; its failure policy is not applied, so a plugin whose failure stops ze does not stop ze here. The order lifts a respawn-limit disable and resets the plugin's respawn count, because the limit guards against a crash loop nobody asked for and this restart was asked for. The daemon then respawns the plugin and runs its startup handshake again, which delivers the running configuration, and answers plugin <name> started again, or plugin <name> was running: stopped and started again (the was-running field says which).

The restart waits 3 seconds, the daemon's stop budget, for the stopped process to clean up after its calls into ze. When one of those calls has not returned by then, the restart fails rather than wait: the new process is stopped, the plugin stays down under doctor-plugin-stopped, and the answer is plugin <name> did not start again with the cause the stopped process has not finished its cleanup. Until that cleanup has run, every restart of the plugin is refused with the same cause and starts nothing, and so is a reload that would start it again, because the late cleanup would remove what a new process registered under the same name. Once the call returns, the restart works again. A call that never returns ends only when ze restarts, so the answer and the doctor-plugin-stopped row name the restart once the call has returned, and a restart of the ze daemon if it never does: sudo systemctl restart ze only when ze runs under ze.service, otherwise ze signal stop, then a start the way ze was started.

show vpn ipsec dataplane

show vpn ipsec dataplane sa                  # The Security Association Database the kernel holds
show vpn ipsec dataplane sa spi <spi>        # Matching SAs, by SPI (1-4294967295)
show vpn ipsec dataplane policy              # The Security Policy Database the kernel holds
show vpn ipsec dataplane drift               # Where engine belief and kernel state disagree

Every other show vpn ipsec command reports what the IKE engine believes it installed. These three read the kernel back, so a kernel expiry, an external flush, or a policy a rekey stranded becomes visible.

show vpn ipsec sa lists, under virtual-ip, the inner addresses an IKE SA leased its peer from a remote-access pool (RFC 7296 Section 2.19), and an empty list for a peer bound to no virtual-ip-pool.

sa lists each installed ESP SA with its SPI, addresses, if_id, mode, reqid, encryption and integrity algorithm names, replay window, byte and packet counters, and the add and use timestamps. It never renders key material. policy lists each policy with its selector prefixes and ports, direction, priority, upper-layer protocol, if_id, tunnel endpoints, and the peer that installed it. A port reads any under a zero mask, a decimal number under mask 0xffff, and <port>/0x<mask> under any other mask, so a masked selector never appears as one exact port. A policy Ze did not install reports its owner as unknown.

drift names each expected Child SA identity the kernel does not hold and exits non-zero when it finds one. Identity includes SPI, destination, protocol, and XFRM interface ID. Extra kernel SAs are permitted during rekey. Engine belief and the kernel dump come from one observation, taken under a generation check. A failed observation, an install or a removal running across the read, and a Child SA whose removal has started each return an error rather than a clean result.

A backend that cannot enumerate the dataplane, VPP and the noop backend among them, reports that it cannot rather than rendering an empty table. So does a process without CAP_NET_ADMIN, a security module's denial (EACCES), a kernel built without CONFIG_XFRM_USER, and a daemon that loaded no dataplane backend at all, each with its own fix. An empty table would answer "nothing is installed" to a question nobody asked the kernel.

RFC 4303 Section 2.1 reserves SPI 0, so the spi selector refuses it rather than reading it as "every SPI".

show bgp takes an optional family argument and carries no subcommand of its own. A token that names no family and no subcommand comes back as an unknown command, so a mistyped subcommand is not reported as an invalid family. The family is the last token the command reads, so a token after it is refused the same way: show bgp ipv4 rubbish names no command and answers no summary.

The two aliases and the column order are declared on show bgp, and a command inherits a declaration from its own path or an ancestor of it. The BGP owner confines the parent's metadata with an inheritance boundary. The first keyword under show bgp supplies an empty floor: show bgp peer covers show bgp peer 192.0.2.1 detail, including selector spellings and newly registered branches. So no child command under show bgp inherits the parent's | summary or | peers.

A single accepted family token remains an argument of show bgp, so show bgp ipv4 | peers keeps the summary's aliases, columns, shape and address fields. The boundary uses the same family predicate as the overview handler; a token after the family still meets the child floor. A child's own declaration on an equal or longer path takes precedence.

That empty floor is not a claim about a child's answer. A command on the branch root or deeper declares its own order and keeps it. Twenty commands under show bgp declare one, and each of the twenty also declares whether its answer holds rows. ze help command "<path>" --json answers what one of them declares.

show bgp rpki declares an alias of its own on that same branch root, so show bgp rpki | summary answers the RPKI counters and not the peer aggregates.

That bare command answers the seven validation counters and one row for each cache server, as siblings. That shape is what leaves | summary a half to select. The RPKI plugin declares the alias on its registry.Registration, which every reader that links the composition root sees, so ze help command --json and ./le cli list both list summary on the command. Each row carries the command's summary under description and its long explanation under description. The full RPKI command list is in docs/guide/rpki.md.

show bgp summary was a second spelling of this command until 2026-08. It is removed, not aliased, so it answers an unknown-command error. show bgp gives the ordered table, and show bgp | summary gives the aggregate fields that show bgp summary | summary gave. An authorization entry keyed on the literal show bgp summary matches nothing after the removal; key it on show bgp.

ping / traceroute

show ping and show traceroute use Ze's internal ICMP engine and work without the daemon running (registered as local handlers). monitor ping and monitor traceroute also work offline, streaming results until Ctrl-C. Through the daemon, ze cli -c and SSH stream them the same way from the router, and MCP, REST, gRPC and the web admin console get one sample: the rows of a bounded ping run, or one traceroute probe round.

ze show ping 8.8.8.8                          # 5 probes, 5s timeout
ze show ping 8.8.8.8 count 10 timeout 3s      # count 1-100, timeout 1s-30s
ze show ping 8.8.8.8 size 1400                # ICMP payload bytes (1-65507)
ze show ping 8.8.8.8 size 1400 do-not-fragment honor-cache   # DF bit set, kernel path-MTU cache honored
ze show ping 8.8.8.8 size 1400 do-not-fragment bypass-cache  # DF bit set, cached path MTU ignored
ze monitor ping 8.8.8.8 interval 500ms        # stream until Ctrl-C (100ms-30s)
ze monitor ping 8.8.8.8 count 5               # stop after 5 probes
ze monitor ping 8.8.8.8 size 1400 count 20    # 20 probes carrying a 1400-byte payload

size is the ICMP payload length, not the total packet: size 1400 sends 1400 bytes of payload plus the 8-byte ICMP and 20-byte IPv4 headers. This differs from ping(8), whose familiar "64 bytes" counts the whole ICMP message (56 payload + 8 header). Omit size and the engine sends its small default payload. The 65507 ceiling is what still fits a 65535-byte IP datagram after both headers.

Both commands take count (1-100) and size (1-65507). They mean the same thing in each: show ping runs a bounded batch and prints a summary, while monitor ping streams live statistics. Omitting count on monitor ping streams until Ctrl-C, which is the difference between them; monitor ping additionally takes interval (100ms-30s). The two accept identical arguments whether or not a daemon is running.

do-not-fragment sets the Don't Fragment bit on every probe, on show ping, resolve ping, show traceroute and resolve traceroute, and it takes one of two values. do-not-fragment honor-cache honors the kernel's cached path MTU: a probe larger than the cached value is refused at send time. do-not-fragment bypass-cache ignores the cached value, so the probe is put on the wire at its full size and the path answers for itself. The keyword without a value is refused, as every keyword of an operational command is. Absent, the DF bit is clear and the kernel fragments a probe larger than the path, as before. monitor ping does not take the keyword. Linux only: elsewhere the keyword is refused as unsupported and a probe without it still runs.

A probe the path refused for its size is a reply row with status too-big, next-hop-mtu-reported (bool) and, when true, next-hop-mtu (int, the octets the router reported). A probe the kernel refused against its cached path MTU, which honor-cache asks for, has status too-big-cached with the cache's estimate, never reached the wire, and is left out of sent. When any probe was refused, the summary carries the same two keys with the smallest value reported. A refusal with no usable value (RFC 1191's zero from an old router, or an IPv6 value below 1280) says next-hop-mtu-reported: false and carries no next-hop-mtu key. Every run with the keyword also carries path-mtu (int, octets) on the summary: the estimate the kernel holds for the destination once the probes have run. The key is absent when the kernel holds no estimate.

Ping runs on a raw ICMP socket when the daemon holds CAP_NET_RAW, and otherwise on Linux's unprivileged ICMP socket when the daemon's group is inside net.ipv4.ping_group_range; do-not-fragment and the reported MTU work on both. Traceroute needs the raw socket and refuses to run without it. ze doctor reports the state before the first probe: doctor-icmp-probe when neither socket opens, naming which of the two fixes applies, and doctor-icmp-probe-unprivileged when ping runs on the fallback.

show crashes

ze show crashes              # List crash reports with size, kind and readiness (JSON)
ze show crashes latest       # Display the most recent crash report
ze show crashes name <file>  # Display a specific crash report

show crashes is served by the daemon when reachable; when no daemon is running it falls back to reading the crash files in-process. That fallback matters most here: you inspect a crash precisely when the daemon has died, so the command must work with no daemon.

Each row carries a kind. panic is a Go panic this daemon caught and wrote itself. kernel is a kernel fault, which leaves no process behind to write a report: the kernel writes its own record into a reserved memory region, and Ze reads it on the next boot. Both kinds live in one directory, share the ze.crash.keep retention count, and are listed by this one command.

Crash reports contain the panic stack trace or the kernel backtrace, ring buffer context (last 64 log entries), version, build date, and uptime. Crash files are stored in the autodetected crash directory (see ze.crash.dir env var).

The listing also carries a readiness block, which answers configured and armed separately:

Field Meaning
configured system crash-dump enabled is set in the running config
armed the RUNNING kernel booted with the reservation, and its record store is readable
reason what to do next when the two disagree
region, reserve-megabytes the reservation the running kernel carries
directory-writable a crash directory was resolved and is writable
pstore-available kernel crash records can be read back
memory-image the same two states for the full-memory-image option, with shortfall-bytes when the target lacks room

The two fields come from different places on purpose. A reservation is a kernel boot argument, so a commit looks like it took effect and changes nothing until the box reboots into an image built with image.crash-dump. Reporting one field would hide exactly that gap. See docs/guide/appliance.md for the reservation and docs/guide/configuration.md for the config leaves.

Three ze doctor checks report the same facts with stable diagnostic codes: doctor-crash-capture-unarmed, doctor-crash-capture-pstore and doctor-crash-directory-unwritable.

clear interface counters

ze clear interface name <name> counters    # Reset counters on one interface

Every interface is reset only when all is typed. The bare ze clear interface counters is refused and names the all form, so a prefix typed by mistake never resets every counter. One interface is selected with the name keyword before its value, as show interface name <name> does. A trailing token after either form is refused with the usage line rather than silently defaulting to "all".

The clear verb resets runtime/operational state without touching configuration. Backends that expose a real counter-reset syscall (VPP's sw_interface_clear_stats, once wired) zero the kernel counters directly. Linux netlink has no generic counter-reset, so ze falls back to a per-interface baseline: the current raw counter values are captured, and every subsequent show interface [counters] read subtracts the baseline before returning so the operator sees "since last clear" deltas.

Wrap detection: if a subsequent read observes a raw counter lower than its baseline (interface bounce, driver reload, delete+recreate), ze treats it as a kernel-level reset, drops the baseline, and returns the raw value. Subsequent reads resume from the kernel's new zero without underflow.

At a shell, the command dials the daemon's address (the one ze cli connects to) once, for at most one second, and closes the connection without sending anything. It is what the session-start hook ze create agent skill installs runs, and it never fails a session.

Through the daemon (ze cli, SSH, REST, gRPC, MCP, web) the answer is the version, a line saying the caller reached the daemon, and the guide. It carries no directory and dials nothing, so a read-only caller does not learn where the daemon keeps its config.

ze pipe

Apply pipe formatting to stdin. Offline commands that print text rather than answer data do not pass through the YANG-dispatched pipe infrastructure. ze pipe provides the same operators as a standalone filter.

<command> | ze pipe json [compact]     # Format as JSON (pretty or compact)
<command> | ze pipe yaml               # YAML output
<command> | ze pipe table              # Box-drawing table
<command> | ze pipe text               # Space-aligned columns
<command> | ze pipe ndjson             # One compact JSON object per line
<command> | ze pipe match <pattern>    # Grep lines (case-insensitive)
<command> | ze pipe count              # Count items (JSON-aware)

<command> | ze pipe last <n>           # Take last N items

ze data

Inspect a live tree read-only, or modify a tree or explicit blob artifact offline. Mutations refuse an active writer, except rm, which sends its removal to the daemon that owns the store. Keys are raw, namespaced paths, and list recursively lists matching keys.

ze data --path /etc/ze/database list meta/
ze data --path /etc/ze/database cat meta/instance/name
ze data write <key> <file>         # A file of "-" reads stdin
ze data import <file>...           # Import as the config <basename>, a new version when it exists
ze data rm <key>...                # Through the daemon while ze runs
ze data registered [pattern]
ze data check
ze data repair --output <new-path>
ze data backup <file> [spare <n>]  # Copy every key to one blob artifact
ze data restore <file> config [name <source-name>]  # Commit the artifact's config
ze data restore <file> full        # Replace the whole tree with the artifact's keys
ze data encode [--crc|--header] [--cap N] <string|->

show data list prefix <prefix> selects the same key prefix as the local list command. show data registered pattern <exact-pattern> selects one registered key description; an unknown pattern is a refusal on both routes, rather than an empty success. Omitting either selector retains the complete inventory.

show data encode content <base64> [part full|header|crc] [capacity <bytes>] uses the local encoder and returns its exact frame, header or CRC bytes. part defaults to full; capacity defaults to input length plus ten percent. The declared capacity must hold the input and is at most 8,388,480 bytes, so the frame fits one daemon answer. The registered input descriptor supplies a native browser file/paste control; no live store is opened or changed.

--path <store> selects the exact tree directory or .zefs artifact. Without it, commands use database/ under the configured directory. Data commands never initialize a missing live store.

check verifies every frame and names corrupt keys. A corrupt frame exits 1 before the history walk, because a frame that does not read cannot be told apart from a missing one: run repair, then check the output. With every frame intact, it walks config history, where each dated entry file/<stamp>/<name> holds sha256:<hex> and the bytes live once under object/<hex>. Each finding is one row, <severity>: <kind>: <key>: <detail>:

Kind Severity Meaning
orphan-object warning ✕
dangling-entry error the entry names an object that is absent or does not hash to its name
malformed-entry error the entry value is not sha256: plus 64 lowercase hex
wrong-hash-object error the object's bytes do not hash to its name, both hashes named
dangling-pointer error meta/config/<name>/<pointer> names a stamp whose entry does not resolve
removed-during-check warning a writer removed the key after the walk listed it, so it was not read

check reads a live store while ze writes it, so the daemon can remove a key after the walk lists it and before the walk reads it. That key is not an error and is not skipped in silence: it is named on one stdout line, removed while the check ran, not read (<n>): <key>, <key>, a directory key ending in /, and the closing line counts it apart from what was read, ok: <n> entries read, <n> removed during the check not read, magic ok, container ok. No error is drawn from a removed key: an entry whose object was removed, and a pointer whose entry was removed, are not judged dangling. The exit code is the one the other rows give.

repair preserves the source and writes verified keys to a new tree or blob. It refuses an existing output. It then drops every dangling or malformed entry and every wrong-hash object from the output, one dropped: row each, keeps orphan objects, and reports every pointer left naming a dropped entry without moving it. A key the daemon removed from the source while the walk ran is not in the output: it gets one removed: <key> line, and the summary line counts it, <n> recovered, <n> skipped, <n> removed while the repair ran -> <output>. Integrity exits are 0 for success, 1 for corruption, skipped or dropped keys, or a history error, and 2 for an I/O failure or unsafe path. A removed key does not change the exit code.

Both run while ze runs: neither opens the live store as its writer. A remote operator runs the same through the daemon, below: show data check answers the rows check prints, and request data repair path <file> writes the salvage on the daemon's host. Installing a repaired store in place of the live one needs ze stopped.

backup copies every key of the store, at any depth and in any namespace, to one new blob artifact under one write lock, so a commit is in the backup whole or not at all. The artifact is exact-fit unless spare <n> names a percentage from 0 to 100, is created mode 0600, and holds credentials and private keys. It refuses an existing file and every name the live store owns in its folder (database, database.zefs, *.lock, database.import-intent, the .replaced-* names and the init and import stages). It is offline only: while a daemon owns the store it refuses, naming as host:port the SSH endpoint ze init recorded in meta/ssh/default (or saying that none is recorded, or that the record cannot be read) and the live route, request data backup path <file>.

restore <file> config runs ze data check's verification over the artifact, then commits one config from it as a new version of this device's config (the name in meta/instance/name, or ze.conf). The active pointer moves to the new version, the previous active becomes the rollback, and file/active/<name> holds the new bytes. Credentials, identity, runtime state and every other version are unchanged. The artifact's config is its active version, or its file/active/<name> mirror when it has no pointer (a seed). name <source-name> selects one config from an artifact that holds several. Without it the artifact's only config is taken, else the one named like this device; any other case is refused, listing the artifact's configs. A differing source name is printed. A staged candidate refuses the restore. It is offline only: while a daemon owns the store it names the live route, request data restore path <file> config. A confirmed commit a stopped daemon left open on this device's config refuses it with that window's refusal, naming ze start <config>, because that daemon's next start reverts the commit and would undo the restore.

ze data restore <file> full replaces the whole live tree with every key of the artifact, history, credentials and identity included. The previous tree moves to database.replaced-<stamp>, and an unrelated database.zefs beside it moves to database.zefs.replaced-<stamp>. The artifact stays at its name, unchanged. An artifact that fails ze data check is refused before anything is written. The canonical seed name <configdir>/database.zefs is refused before the store lock, because the live store refuses that name: import it with ze init --from, or move it to another name and restore that. A full restore is offline only: while a daemon owns the store it names the daemon's SSH endpoint and asks you to stop the daemon; there is no live full restore. The restore records a durable database.import-intent before it moves anything. When it is interrupted, every opener, ze start included, refuses and prints ze data restore <file> full, and that command alone finishes the restore.

rm removes each key it is given, printing removed <key> for each and then <n> entries removed from <store>. A key the store does not hold is an error line, and the next key is still removed. It exits 0 when at least one key was removed and 2 when none was. While a daemon owns the store, the store refuses the local writer, so rm sends each key to that daemon as delete data key <key>, one command per key, and prints the same lines with the same exit codes. It reaches the daemon the way ze doctor does: the address and login of the store it was given (the ze.ssh.* settings, then what ze init recorded), with no password prompt. The daemon command reaches runtime state only, so while ze runs rm removes runtime-state keys only, and its refusals are the ones delete data key gives below. When no daemon answers, rm keeps the store's refusal, says why the daemon did not answer (no listener at its address, no credentials to log in, or no answer) and names the command that fixes that, and exits 2. With ze stopped, rm removes any key.

write writes the bytes of a file, or of stdin for -, into one key, creating it or replacing it, and prints wrote <key> (<n> bytes) into <store>. While a daemon owns the store, write sends the bytes to that daemon as update data key <key> content <base64>, by the route rm takes, and prints the same line with exit 0. The daemon command writes runtime state only, and its refusals are the ones update data key gives below. A file over 195,840 bytes is refused before anything connects, with the daemon's own refusal: one SSH packet carries the whole command, and 195,840 bytes is what it holds. Write a larger value with ze stopped. With ze stopped, write writes any key, of any size. An empty file is the one input the two routes answer differently. While a daemon owns the store it is refused before anything connects: the daemon command takes no empty content, because a key is taken out with delete data key, never emptied. With ze stopped it writes an empty key.

import lands each file in the config named by its file name, under the key file/active/<basename>, and prints imported <key> (<n> bytes) per file and <n> files imported into <store>. Stdin (-) is refused on both routes, because it has no file name to name the config: import it with ze config import --name <name> -. A config the store already holds is committed as a new active version and the previous one is kept as rollback, as ze config import replaces one, so a daemon started after the import runs the imported config. A config the store does not hold yet is written as its key. While a daemon owns the store, import sends each file to that daemon as update data config name <name> content <base64>, one command per file, by the route rm takes, and prints the same lines. A file the daemon refuses is an error line and the next file is still sent, so a refusal of the third file leaves the first two imported. A file over 195,840 bytes is refused before anything connects; restore a larger config from a backup file on the daemon's host with request data restore path <file> config. The command exits 0 when at least one file was imported and 2 when none was. With ze stopped, a file whose config has a confirmed commit a stopped daemon left open is refused with that window's refusal, naming ze start <config>, because that daemon's next start reverts the commit and would undo the import. An unfinished file-commit record also refuses an offline import before its active bytes or history change. Recover that publication before importing again.

The daemon answers these store commands on every surface (SSH, REST, gRPC, MCP, the web), acting on the store it owns. The request data commands read or write a file on the daemon's own host:

request data backup path <absolute-file> [spare <n>] [force]
request data restore path <absolute-file> config [name <source-name>] [client <name>]
request data repair path <absolute-output>
delete data key <key>
update data key <key> content <base64>
update data config name <name> content <base64>
show data check

Caller-owned artifacts use private transfer tokens instead of daemon-host paths:

request config artifact import artifact <id> name <config-name> transfer <token>
request config artifact restore config artifact <id> [name <source-name>] [client <name>]

Import accepts complete raw input under one basename, including unvalidated configuration bytes. Existing configurations gain a native active version; new names gain their active file key. Restore checks and selects the artifact's active configuration, then uses the current daemon's ordinary candidate and reload. An unserved managed client, ambiguous source, pending candidate, open confirmed-commit window or missing reload owner refuses the affected restore. Both commands require edit authorization and retain their source unchanged. Abort completed source transfers after use and delete artifacts when finished.

request data repair path <absolute-output> writes the salvage ze data repair --output writes, from the store the daemon owns, while it runs. The daemon holds its own writes for the walk, so a key it would write or remove meanwhile waits, and the copy is one moment of the store. The history of the copy is then repaired as ze data repair repairs it. It answers path, recovered, recovered-keys, skipped, a row per skipped entry and per history finding, and a warning when an entry did not read or a history key was dropped. Each history row retains its severity and its action (reported or dropped). Unresolved history errors fail the command while retaining the salvage result and the command that checks it. The local repair shares that verdict and exits 1 for unresolved errors. It also answers vanished and one vanished-keys row per key removed during the walk, which the held writes keep at zero on the daemon. A relative path, a .. element, a symlink, an existing path, a name the store owns in its folder and a path inside the live tree are refused, each naming the rule. The live store is not changed; check the copy with ze data --path <output> check. The built-in read-only profile is denied it.

If the complete repair report exceeds the 8 MiB response limit, the command fails with its path, counts, salvage-written: true and details-omitted: true. The saved salvage remains available. The answer names the command that checks it, instead of presenting a partial list as the complete report.

show data check answers the store's integrity verdict: entries, corrupt-entries, vanished-entries, history-checked and one findings row (severity, check, kind, key, detail) per corrupt entry, per key removed during the check (kind removed-during-check, a warning) and per history finding, the rows ze data check prints. Any error row makes the answer an error. | json and | table render the same rows. In ze cli -c it runs in your own process over the store --path or the configured directory names; every other surface asks the daemon, which checks its own store with its writes held for the walk.

delete data key <key> removes one runtime-state key while ze runs: a key under meta/ outside meta/config/. It answers key. A configuration key (under file/ or meta/config/, or outside both) is refused before the store is touched, because a raw removal bypasses its versions, pointers and history; the refusal names update data config name <name> content <base64>. A key a plugin is granted is refused while that plugin runs, because the plugin manages the key while it runs: the refusal names the plugin and ze request plugin restart <name>. A key granted to a plugin that does not run, and a key no plugin is granted, are removed. Until the daemon has started its plugins, a key a plugin is granted is refused, because the daemon cannot tell yet whether that plugin runs. A key the store does not hold is an error, as it is for ze data rm. The built-in read-only profile is denied the command. Runtime state includes the login and HTTPS credentials, so removing one of them can lock you out: meta/auth/local/... holds the local administrator's name, password hash and SSH public keys, meta/ssh/... the SSH login the CLI uses, and meta/web/cert and meta/web/key the HTTPS certificate and private key.

update data key <key> content <base64> writes one runtime-state key while ze runs, creating it or replacing it with the bytes content decodes to, and answers key and bytes. content is base64 (RFC 4648 Section 4, with = padding), 4 to 261,120 characters: 1 to 195,840 bytes, the most one SSH packet carries with the command around it. The bound is the same on every surface. A longer content, an empty one and one that is not base64 are refused before the command runs, naming the bound or the encoding and never the value; a larger value is written with ze data write while ze is stopped. A configuration key and a key whose granted plugin runs are refused as delete data key refuses them, before the store is touched. The audit log, the accounting record, the SSH exec log and the session transcript record the command with <redacted> in place of the content. The built-in read-only profile is denied the command. The credential keys named above can be restored this way from a copy, without stopping ze.

update data config name <name> content <base64> imports one config while ze runs and answers name, version and bytes. name is a file name with no directory; a path, . and .. are refused. For the daemon's own config, the content is staged as the candidate and the same reload a SIGHUP runs promotes it, as request data restore ... config does: the config becomes active only when the reload accepts it, and a config the reload refuses leaves the active config, its pointers and the daemon unchanged, with the reload's reason in the refusal. The import is refused while a commit confirmed window is open, with the window's own refusal, and while another change is staged, naming commit or discard. Any other name is committed as a new active version, the previous one kept as rollback, and nothing reloads; on a hub, a name of the form client-<name>.conf is the config the hub serves to that managed client, and the hub pushes config-changed to it. Such a name is refused, as request data restore ... client refuses it, when the hub has no client entry of that name or the daemon serves no managed client, because no client would fetch it. content has the bound and the encoding of update data key; a larger config is restored from a backup file on the daemon's host with request data restore path <file> config. The records hold <redacted> in place of the content, and the audit log records the import under data-config-import. The built-in read-only profile is denied the command.

Both refuse a relative path, a .. element and a symlink, each naming the rule. backup walks the daemon's own store under its write lock and answers path, keys and bytes. force replaces an existing file and never lifts the refusal of a name the store owns. restore stages the artifact's config as the candidate and runs the reload a SIGHUP runs: the config becomes active only when that reload accepts it, and a refused config leaves the active config and its pointers as they were. It answers path, source-name, config-name and version.

client <name> restores the config a hub serves to one managed client instead of the hub's own. The selected config becomes a new active version of client-<name>.conf under the store guard, and file/active/client-<name>.conf holds it. The hub does not reload. The write pushes config-changed to the client, which fetches the config and applies it through its own reload. The source selection is the same, with client-<name>.conf in place of the device's name. A daemon that serves no managed client refuses, and so does a hub with no client <name> entry under plugin hub server. The answer also carries client.

request peer <sel> teardown [<code>] [<msg>] write Graceful close with NOTIFICATION
request peer <sel> notify <code> <subcode> [<text>] write Close one peer's session with a NOTIFICATION of exactly that error code and subcode (each 0 to 255, assigned or not). The text, as UTF-8, is the RFC 9003 Shutdown Communication under Cease 2 and 4 and the Data field under every other pair; no text sends no Data. A text that does not fit is refused and the session stays up: more than 128 octets under Cease 2 and 4 (RFC 9003 Section 3, as Ze cannot know the peer takes 255), more than 4075 octets otherwise, or text that is not valid UTF-8. Every word after the subcode is the text, so a text can hold the words code, subcode, text or hex; a text whose first word is text or hex is typed after the keyword text. The keyword form notify code <code> subcode <subcode> [text <text> | hex <octets>] is the same command, and the one MCP and the web form send. One specific peer only
request peer <sel> notify <code> <subcode> hex <octets> write The same, with the Data field given verbatim as one word of hexadecimal digits, two per octet (request peer 192.0.2.1 notify 6 2 hex 0474657374). Ze sends the octets as they are, with no encoding and no check of their content, so the form can test how a peer handles a malformed Data field. More than 4075 octets (8150 digits), an odd number of digits, or a character other than 0-9, a-f or A-F is refused and the session stays up. The ExaBGP bridge sends this form for teardown

request peer <sel> enable write Release the hold of disable or of the config shutdown container; the peer connects straight away. Takes no argument
request peer <sel> flush write Block until all queued updates for peer are on the wire

show bgp peer <sel> capabilities and show bgp peer <sel> statistics answer one row for each matched peer, under a peers key, whatever the number of matched peers:

{"peers": [{"peer": "192.0.2.1", "state": "idle", "negotiation-complete": false}]}

A capabilities row adds a negotiated object once the session negotiates.

The negotiated object carries paths-limit when the session negotiated PATHS-LIMIT (capability 76) for a family that also negotiated ADD-PATH. The send map holds the limit the peer advertised, which caps the number of paths Ze announces to that peer for each prefix. The receive map holds the limit Ze advertised, which is what Ze asked the peer for. A family with ADD-PATH and no limit is in neither map, because no limit is not a limit of zero. The same object appears under capabilities on show bgp peer <sel> detail.

When a peer advertised a valid FQDN capability (code 73, draft-walton-bgp-hostname-capability), show bgp, show bgp peer list, and show bgp peer <sel> detail include its hostname and/or domain on the peer row, and show bgp peer <sel> detail (capabilities.fqdn) and show bgp peer <sel> capabilities (negotiated.fqdn) carry the same fields under fqdn. Empty halves and absent capabilities are omitted, and strings containing invalid UTF-8 or control characters are withheld.

Until 2026-08 each command answered a bare object for one matched peer and an array for several. show bgp peer * statistics | count therefore answered on a router with three peers, and was refused on a router with one. A script that reads the single-peer form must now read the first element of peers.

Peer rows come in ascending order of peer address and port. This holds for every command that reads the reactor's peer table, show bgp, show bgp health and these two included. The order was the Go map order until 2026-08, so | first 1 answered a different peer on each call.

The peer selector comes first (peer <sel>, matching show bgp peer <sel> ...), then the direction (import/export), then optional filter <NAME>, then update <HEX>.

<HEX> is a hex-encoded full BGP UPDATE message (including the 19-byte header). The 0x prefix is optional.

Optional: source-asn4 false to paste an UPDATE as received over a two-octet session (default: ASN4). The dry-run first merges its AS4_PATH and AS4_AGGREGATOR into the four-octet form, as the live import does (RFC 6793 Section 4.2.3), and explains that route, which is the one the filters see.

On export, route-kind learned is the default and route-kind local predicts a local announcement. The result reports simulated-route-kind. A resolved explicit role keeps its default for either choice, identified by role-default: true. The choice is read-only and authorizes no live route. Import refuses this argument; unknown values are also refused. Without an export policy, an internal destination rejects learned routes and permits local routes, while an external destination rejects both. An internal learned-route rejection reports policy.final-source: learned-export-policy.

Output is structured JSON with fields: direction, peer, action (accept/reject/modify/undetermined), trace (per-filter decisions), text-before, text-after, changed-attrs, and wire-changes (the wire-level attribute operations the chain applies, such as AS_PATH set, which text-before and text-after cannot show). An export dry-run toward an internal peer lists no AS_PATH operation, because the export chain applies no as-path-prepend or remove-private toward one (RFC 4271 Section 5.1.2).

If the remote AS is unresolved, action is undetermined and reason tells you to wait for establishment and repeat show policy test. No filter executes, including a single-filter override. Trace and text are empty, with no wire changes. For a known EBGP session, an absent direction has a rejecting final. policy reports the simulated route class's effective final: final-source: rfc8212 marks the RFC 8212 default reject on an EBGP direction with no policy, and undetermined an absent direction whose session type is not known yet.

The chain show policy chain and show policy test read is the peer's effective chain, so it carries the members a plugin inserted as well as the ones the operator named: on a peer with an RFC 9234 role, the upstream check bgp-role:upstream-asn appears in the import chain of a provider, peer or rs session and in the export chain of a peer or rs-client session (BGP roles, "The Upstream Check a Role Inserts").

text-before and text-after name every attribute the UPDATE carries. Five of those names first appeared on 2026-09-04: origin, med, local-preference, atomic-aggregate and cluster-list. The renderer named a Go type no parser built for each of them, so the dry-run output was silent about all five.

This command does not forward routes, update the RIB, populate cache, or mutate peer state.

ze cli with no command argument runs the interactive model in the CLIENT process and expands the pipe chain there. Only the aliases compiled into Ze itself are registered in that process, so an alias a PLUGIN declares, such as show bgp rpki | summary, comes back as pipe error: unknown pipe operator: summary. It resolves over ze cli -c "<command>" and in the interactive session a plain ssh client reaches, where the daemon expands the chain.
