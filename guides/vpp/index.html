Why VPP is in Ze

Ze is a BGP daemon. BGP produces forwarding decisions; something else has to carry the packets. The default answer on Linux is the kernel route table, programmed via netlink by the fib-kernel plugin. That works, but it puts every packet through the kernel's software forwarding path, which tops out at a few Mpps on commodity hardware and starts dropping under bursty load.

VPP (the FD.io Vector Packet Processor) is a user-space software router built on DPDK. It takes the NICs away from the kernel, batches packets into vectors, and walks each vector through a graph of forwarding nodes with hot caches. On the same hardware where the kernel loses packets, VPP forwards at line rate: roughly 35 Mpps on a 4-core Xeon D-1518, with numbers like 18 Mpps per thread for MPLS and around 14 Mpps per thread for VXLAN. IPng Networks has run this stack in production on AS8298 for several years.

Adding VPP to ze is not about replacing BGP. It gives ze a forwarding-plane answer for IXP route servers, production edge routers, and gokrazy appliances on small hardware such as an N100 mini-PC. The control plane stays in ze (BGP, RIB, config, CLI, web UI). The forwarding plane becomes VPP. The two talk through a small, typed interface (GoVPP over a Unix socket).

How the two halves fit together

┌──────────────────────────────────────────────────────────┐
│                          ze                              │
│                                                          │
│   BGP reactor ──▶ protocol RIB ──▶ sysRIB                │
│                                     │                    │
│                              ┌──────┴──────┐             │
│                              │             │             │
│                         fib-kernel     fib-vpp           │
│                         (netlink)      (GoVPP)           │
│                              │             │             │
│                              ▼             ▼             │
│                       Linux FIB       VPP FIB            │
│                        (local)        (transit)          │
│                                                          │
│   vpp component: starts VPP, binds NICs, watches health  │
└──────────────────────────────────────────────────────────┘

Ze keeps two FIB backends and runs them side by side. fib-kernel still programs the Linux route table so local services (SSH, the web UI, BGP TCP sessions) keep working. fib-vpp pushes the same best routes into VPP's FIB via the GoVPP binary API, so transit packets are forwarded by VPP at DPDK speed. Both plugins subscribe to the (system-rib, best-change) event on the EventBus and react independently.

BGP sessions themselves still use Linux sockets. VPP's Linux Control Plane (LCP) plugin mirrors every VPP interface as a TAP device, so ze's BGP reactor bind()s and connect()s exactly as it does on a kernel NIC. VPP is invisible to the BGP code path.

Which namespace those TAPs land in is a separate question, and it is the one live limitation here. LCP creates them in the namespace named by vpp.lcp.netns, which defaults to dataplane, following the IPng production convention that isolates the forwarding plane from the management plane. Ze's BGP reactor has no network-namespace awareness: it binds in whatever namespace the ze process itself runs in. So on the shipped default, ze's BGP cannot bind on an LCP-shadowed interface unless ze is itself running in the dataplane namespace.

Setting vpp.lcp.netns to host or root does not work around this. To VPP those are ordinary namespace names: it resolves the value to the path /var/run/netns/<name>, and ze passes the same leaf to VPP as its global default netns, which VPP falls back to for any pair that carries no namespace of its own. So host asks VPP for a namespace literally called host, which normally does not exist.

Two remedies work today. Leave vpp.lcp.netns empty: that clears VPP's global default netns, and LCP then creates the TAPs in VPP's own namespace, where ze runs. Or run ze's BGP in the namespace the leaf names. Nothing else does, until BGP learns to bind inside a named namespace (specced, not implemented).

ze doctor reports doctor-vpp-lcp-netns for any non-empty vpp.lcp.netns, and a BGP stanza is not required to see it: host and root get one warning of their own, because the value is wrong even where nothing binds. On Linux the check also opens the namespace directory, and reports a namespace that is absent (LCP pair creation would fail at apply) separately from a probe that could not answer. Run ze show diagnostic doctor-vpp-lcp-netns for the detail.

The accepted character set for the leaf is what VPP can carry through: printable, no whitespace, no path separator, under 256 characters. VPP's own parser reads the leaf with unformat(line_input, "netns %s", &ns), and %s ends at a space, tab, newline, or carriage return rather than refusing the input. So netns my ns would reach VPP as my, VPP would build /var/run/netns/my, that namespace would not exist, and LCP pair creation would fail at apply on a config ze had accepted. Config verify refuses the value instead.

A second check covers the plugin rather than the namespace. Enabling vpp.lcp makes ze write a startup.conf that loads linux_cp_plugin.so. A VPP built without it accepts the config and then fails the WHOLE apply at the binary-API layer, with a raw VPP error that names the failing message rather than the missing plugin. ze doctor reports doctor-vpp-lcp-plugin first. The probe reads the RUNNING VPP with vppctl show plugins, not the filesystem: what matters is what the loaded VPP has, not whether a copy exists on disk. An absent enabled leaf reads as on, matching the YANG default.

Severity follows what the probe proved. A probe that answers and does not list the plugin is an ERROR, and ze doctor reports the host as not ready. A probe that cannot answer degrades to a WARNING and never claims the plugin is missing. vppctl exits non-zero identically for an absent binary, an absent socket, and a wedged VPP. A zero exit counts as an answer only when the output carries the Plugin path is: line VPP prints ahead of the plugin rows: empty or truncated output lists no plugin at all, so it is a WARNING too. None of those is evidence about which plugins VPP loaded.

What ze does for you

When vpp.enabled is true, ze takes ownership of the whole VPP lifecycle. You do not run systemd start vpp; you do not edit /etc/vpp/startup.conf; you do not dpdk-devbind your NICs by hand. Ze does the following, in order, every time it starts or VPP crashes:

Step What ze does Code
1 Parses the vpp { ... } YANG section into VPPSettings internal/component/vpp/config.go
2 Validates PCI addresses, socket paths, netns names, size strings config.go: Validate
3 Renders startup.conf (unix, api-segment, socksvr, cpu, buffers, dpdk, plugins, linux-cp, linux-nl, memory, statseg sections, some conditional) startupconf.go: GenerateStartupConf
4 Loads vfio, vfio_pci, vfio_iommu_type1 kernel modules dpdk.go: loadVFIOModules
5 For each configured PCI address: saves its original driver and driver override, selects vfio-pci for that device and binds that exact address. A device already using vfio-pci keeps its existing ownership. dpdk.go: bindPCI
6 Execs the VPP binary with -c <generated startup.conf> vpp.go: runOnce
7 Connects one non-reconnecting GoVPP transport to the configured API socket (10 attempts, 1 s apart), retaining its actual Unix peer. Managed mode matches that peer to the child's atomic process descriptor, then waits for the configured original startup CLI file on the same generation. conn.go: Connect, process_exit.go: bindManagedProcess, startup_cli.go: activateManagedRuntime
8 Opens the configured statistics mapping and checks that its actual Unix peer is the same live physical API process before reading or publishing counters. Starts optional telemetry. runtime_stats.go, process_peer.go
9 Checks selected plugin APIs, then emits ("vpp", "connected") and completes service readiness. runtime_stats.go: activateRuntimeStatsGeneration
10 Waits for VPP to exit. On crash: emits ("vpp", "disconnected"), backs off (1 s, 2 s, 4 s, capped at 30 s), restarts, emits ("vpp", "reconnected"). fib-vpp replays the RIB on reconnect. vpp.go: Run loop, fibvpp.go: reconnect handler
11 On shutdown: kills the exact supervised VPP child and joins its wait, then restores each owned NIC's original driver and driver override. A NIC that originally had no driver returns to that state. vpp.go: waitVPPConnection, dpdk.go: UnbindAll

The point is that VPP's system-level prerequisites (vfio module load, NIC unbind, original driver and override restoration) are part of ze's job, not the operator's. This matters on a gokrazy appliance where there is no systemd and ze is PID 1 for the data plane.

Binding changes only the configured PCI device. Ze uses its driver_override and the driver's exact-address bind file, without adding a vendor/device-wide VFIO registration or rescanning the bus. Cleanup keeps the original state until both driver and override restoration succeed. Retrying the same binder resumes from the observed native state, so a confirmed detach or driver bind is not repeated. These receipts belong to the running manager; they are not an on-disk recovery journal.

Ze reads driver_override_raw when the kernel provides it. Only its absence permits the legacy getter; a legacy (null) is ambiguous and is refused before changing the NIC. Upgrade to a kernel that provides driver_override_raw before binding that NIC. Captured spaces, tabs and carriage returns are preserved; only the final framing newline is removed, and nonempty restoration writes gain no extra newline.

The vpp-dpdk doctor check reads the same original-state prerequisite for each configured, present PCI device without binding it. Its diagnostic retains the failed native path and cause. A device already using VFIO remains borrowed and does not require an unused original override snapshot.

An ordinary requested child kill is clean only after the original command has been reaped with its expected exit status. A separate cleanup failure remains an error even when shutdown was requested. The manager returns that cause and stops before starting another child if native child cleanup is unresolved; failed NIC restoration is also returned, with its original receipt retained. Physical process-exit proof and successful NIC restoration are separate facts. Configuration replacement keeps that joined manager until its original cleanup receipt confirms restoration. A failed bind rollback also retains the same binder. A later configuration retry first retries that exact cleanup; it cannot start a fresh manager while the original native cleanup is unresolved.

The generator targets upstream VPP v26.06 grammar. In particular, it writes buffers { default data-size 2048 ... }, linux-nl { nl-rx-buffer-size 67108864 }, and memory { main-heap-size ... }. The deployment reference maps every emitted directive to its release-pinned consumer. Grammar matching and unit tests are not proof of native startup: the installed VPP plugins, hugepage reservation, CPU affinity and device/namespace permissions must also support the selected configuration.

Managed VPP consumes the startup file Ze generates. To select an AF_PACKET profile, set vpp.plugins.dpdk false with no DPDK interfaces, explicitly enable vpp.plugins.af-packet, and select vpp.memory.hugepage-size default when the profile uses native base pages. uRPF remains enabled for configured IPv4 reverse path policy; the selected image must contain it. Omitted settings retain the existing DPDK-enabled, AF_PACKET-disabled, 2M startup bytes. No unavailable plugin or failed hugepage allocation selects another configuration.

An optional vpp.startup-cli-file names the original command file. After the retained API socket peer matches the supervised child's atomic process descriptor, the manager sends one synchronous native exec <path> request on that exact connector generation. Statistics activation and service readiness wait for its correctly typed successful reply, stream close, live context and unchanged generation. A native command or transport failure follows the existing child kill, completed wait and original transport closure path. The independent retained pidfd observer alone proves physical death; its notification can precede the child's reap. The manager still joins the original child before returning or restarting. The generator omits asynchronous unix exec for this setting, which prevents a second execution. Pure configuration verification rejects a path that is relative or could escape its native token. Managed startup checks the original file before configuration/binding and before each child exec: it must be readable and regular. The check opens without waiting for a FIFO peer, reads one byte, and closes that same file while retaining original filesystem errors. It does not parse or rewrite the native command program. Empty files are permitted by the file preflight; native VPP still decides whether their command program can execute. External supervision owns its own startup and neither inspects nor executes this file. doctor-vpp-startup-cli-file reports the exact path and its repair.

These controls do not create an AF_PACKET interface or its Linux Control Plane pair. The declared managed bootstrap must provide those before PPPoE accesses can prepare. The native acceptance scenario must observe the actual executable, its generated -c path and config hash, the declared image's loaded plugins, real API/statistics readiness and original connector/process identities. An exec wrapper that replaces the generated configuration, an external-mode run, or a unit rendering result cannot supply that managed-startup evidence. The complete restart, accounting, pool and productive fresh-session checks remain required.

Running against an externally supervised VPP

Set vpp.external true when something other than ze owns the VPP process -- a systemd unit, a container sidecar, or the Python stub the functional tests use. In this mode ze skips steps 3, 4, 5, 6 and 11 of the table above: no startup.conf generation, no vfio module load, no NIC unbind, no exec vpp, no NIC restoration writes on shutdown. Ze still connects via GoVPP at step 7, opens statistics and optional telemetry at step 8, then emits lifecycle events and completes readiness at step 9. It blocks on context cancellation instead of cmd.Wait at step 10.

Typical configurations:

vpp {
  enabled  true;
  external true;
  api-socket /run/vpp/api.sock;
}

The operator owns startup.conf, owns the systemd unit, owns the vfio bind. Ze owns the API socket conversation and the FIB programming.

Use this for:

  • Systemd deployments: the system VPP unit starts before ze, ze connects to its API socket on startup.
  • Gokrazy containers: a sidecar image bundles vpp and ze; the supervisor starts VPP first, then ze with external true.
  • Functional tests: ./le test functional vpp drives the compiled Go VPP stub instead of a real VPP. See docs/functional-tests.md for the harness.

The real-VPP deployment action, ./le test deployment vpp, stops each Ze daemon by signalling its exact command inside the container, not the host docker exec client. Each replacement must reach its own startup marker before the harness inspects retained VPP state. A policer or ACL left by the previous daemon therefore cannot make a failed replacement look like a successful restart. A stop returns only once the daemon has exited, because a stopping ze still owns its config store while it finishes recording its boot configuration, which on a slow disk takes seconds. It waits up to two minutes after SIGTERM, then sends SIGKILL. A daemon that needed SIGKILL, or that is still running after it, fails the run with its command named, and no further daemon starts, since it may still own the store the next one would open.

vpp and vpp-iface start their container through the lab Docker wrapper, which labels it with the run that owns it. Ctrl-C or SIGTERM ends the run and still removes the container. A scenario the interruption caught ends at once with the interruption as the run's error, never a FAIL for a feature the run did not finish probing. When the removal fails, the report's container-removal-error names the reason and the verb exits 1; run ./le test integration clean to remove it. A run killed outright leaves a labeled container that the next lab start or that cleanup removes.

Configuring VPP

PPPoE access follows interface backend. When a VPP PPPoE provider is installed and access interfaces are configured, its registration selects pppoe_plugin.so and the enable-pass-nd-and-dhcpv6 startup flag automatically. The candidate must enable both VPP and LCP; a missing provider or disabled prerequisite is refused before apply. No separate plugin toggle is required.

The vpp { ... } container lives in the main ze config. Minimal example:

vpp {
  enabled true;
  dpdk {
    interface 0000:03:00.0 {
      name xe0;
    }
    interface 0000:03:00.1 {
      name xe1;
    }
  }
}

This selects the default heap, buffer count, stats segment and LCP settings. Starting native VPP also requires the host prerequisites below and the selected plugins. Add cores, tune memory, or change the stats poll interval when the defaults do not fit the workload.

Enabling FIB programming

The VPP component starts VPP, but it does not program routes. That is fib-vpp's job, and it has its own switch under the fib container:

fib {
  vpp {
    enabled true;
    table-id 0;
  }
}
Path Type Default What it controls
fib.vpp.enabled boolean false Enable route programming. Off means the plugin loads but does nothing.
fib.vpp.table-id uint32 0 VRF table ID. 0 is the default VRF.
fib.vpp.batch-size uint16 256 Max routes per GoVPP batch.
fib.vpp.batch-interval-ms uint16 10 Max milliseconds to wait before dispatching a partial batch.

fib-vpp depends on the vpp subsystem and on the RIB plugin. If VPP is disabled or the GoVPP channel fails to open, the plugin programs no route and logs an ERROR naming the cause; the rest of ze keeps running. When VPP connects, the plugin opens its writer and asks the system RIB to replay every route. Until then show fib vpp answers the cause as an error, never an empty route list.

SRv6 service routes

The received egress Service SID is the policy's segment. Ze allocates a separate local BSID for steering and shares the policy across prefixes using that SID. Replacement installs new steering before releasing the old policy; withdrawal releases a policy only after its final reference. This does not allocate egress Service SIDs or install remote endpoint behaviors.

Provide the IPv6 underlay route, encapsulation source, and required tables. fib.vpp.table-id selects the policy and outer IPv6 lookup table. A nonzero per-route table override selects destination steering, not the underlay table. The existing Service-SID resolvability check remains a prerequisite.

Ownership uses durable daemon keys under meta/fib-vpp/srv6/. Restore validates confirmed policy contents and live steering references before mutation. An unconfirmed creation found live fails closed with its BSID in the error; matching contents alone do not authorize adoption or deletion. Preserve that state for operator reconciliation. External writers must not race Ze's live ownership checks: VPP has no conditional steering replacement.

The ownership namespace admits at most 4,096 keys in total, not 4,096 routes. Policy, steering, and temporary ordinary-route fallback records all count. A transition reserves its complete growth before the first state or hardware write; replay and withdrawal of existing keys remain possible at the limit.

IP/SRv6 transitions retain durable planned and confirmed ordinary-route ownership by prefix and table. Restart restores confirmed cleanup ownership; an uncertain IP mutation fails closed for operator reconciliation. This is installation history, not inspection of a hidden API-source route: VPP's dump can expose the winning SR steering source instead. Other writers must not replace Ze-owned ordinary API-source entries, even sequentially. Matching live routes are never adopted as proof of ownership.

Normal Ze restart can reuse confirmed live ownership. Managed-VPP reconnect retires the old consumer, restores ownership, and requests system-RIB replay. Replay is partial, not a snapshot: omitted owned live routes remain until explicit withdrawal. External-VPP process restart does not emit the managed reconnect event. The real VPP proof defines state, packet, and restart assertions; prepared code is not observed forwarding evidence.

System prerequisites

VPP is not a user-space toy; DPDK needs real kernel cooperation. On a general-purpose host Ze cannot set kernel boot parameters, so you reserve hugepages yourself. On the gokrazy appliance Ze owns the kernel cmdline: set image.hugepages (and optionally image.memory-bytes) in appliance.json and ze appliance build bakes default_hugepagesz/hugepagesz/hugepages into the boot cmdline for you (see the appliance guide). ze doctor reports doctor-vpp-hugepages when VPP is enabled but the reservation is missing, insufficient, or clamped.

The boot-time reservation proof is ./le test qemu vpp-hugepages. Its invocation root covers the native host build, appliance build and boot-time SSH assertions; SIGINT, SIGTERM or SIGHUP ends the active owned command group and prevents a later phase or renderable verdict payload. QEMU is joined before the work directory is removed. Normal completion first sends QEMU SIGINT and preserves its existing ten-second shutdown grace; cancellation or an error closes the owned group immediately. Host process-fixture tests establish that lifetime contract only: a hugepage reservation still needs the actual booted kernel's show host kernel and show host memory answers.

Supported NICs through DPDK include Intel i210/i350, X520/X540, X710/XL710 and E810 families, plus VirtIO for VMs. Mellanox ConnectX-5 and later use RDMA in a bifurcated driver mode; the current ze implementation is DPDK only and does not yet bind Mellanox NICs.

Observing what VPP is doing

Two places expose VPP state through ze:

  1. Prometheus metrics. The stats poller exports per-interface counters (rx/tx packets, bytes, drops, errors), per-node clocks and vectors-per-call, and system-wide vector and input rates. Poll interval is configurable via vpp.stats.poll-interval.
  2. The show fib vpp command. Dumps the routes fib-vpp believes it has installed in VPP, as JSON [{"prefix": ..., "next-hop": ...}, ...]. Before the plugin has started, or while it has no VPP connection, it answers an error saying why instead.

Direct VPP introspection (vppctl show int, vppctl show ip fib) is still available through the CLI socket ze writes to /run/vpp/cli.sock.

Implementation status

Configured interface names can differ from VPP's names: a VLAN named qos0.100 may appear as loop1.100 in VPP. Link and address reads resolve the configured name through the same registered interface index used by writes, so a reload updates the existing VLAN. If that registered index cannot be read, the reload refuses instead of treating the VLAN as absent and creating it again. An unregistered name is looked up as an exact VPP interface name.

The implementation status differs by subsystem:

Phase Scope Status
vpp-3 MPLS label stacks on IP routes processMPLSChange dispatches labeled route installs and replacements to addMPLSRoute, and removals to delMPLSRoute. The GoVPP backend sends IPRouteAddDel with a label stack for installs, every label in uniform mode, so the label TTL is copied from the IP TTL. Transit swap and pop entries from LDP and RSVP-TE arrive as (mpls-fib, entry) events: fib-vpp creates MPLS table 0 and installs each entry as two MplsRouteAddDel routes, one per value of the S bit, never in fib.vpp.table-id. A pop imposes the Implicit NULL label; an egress pop with no next hop looks the packet up in IP table fib.vpp.table-id of its FEC's family. VPP has no per-route MTU, so an entry's path MTU is not installed and fib-vpp warns once. A push into a private table (an RSVP-TE facility-backup context) is refused, because VPP has no packet-mark context. mpls { enable true; } on a unit enables MPLS input on the VPP interface.
vpp-4 VPP-native iface.Backend: managing interfaces directly via GoVPP instead of through the kernel In tree. Backend registers as "vpp" and loads cleanly under interface { backend vpp; }. Interface lifecycle (CreateDummy/Bridge/VLAN, Delete, SetAdminUp/Down, SetMTU), addressing, bridge port add/del, query (ListInterfaces, GetInterface, GetMACAddress, SetMACAddress), and monitor (WantInterfaceEvents -> EventBus) all wired against vendored GoVPP. Tunnels (GRE/GRETAP/IPIP + VXLAN as a new kind), mirror (SPAN), wireguard, and LCP TAP pairs are now implemented (spec-followup-vpp-iface, GoVPP binapi vendored). GRE tunnels and wireguard interfaces are proven against real VPP 25.10 by; LCP pairs are unit- and wiring-tested but their real-VPP proof needs a VPP build shipping linux_cp_plugin.so/linux_nl_plugin.so (the ligato/vpp-base image does not). An interface apply that runs before the vpp handshake completes is deferred whole and performed when EventConnected fires (VPP backend). internal/le/test/deployment.Answerdocs/features/interfaces.md
vpp-5 L2 cross-connect, bridge domains, policers, ACLs, SRv6, sFlow Depends on vpp-4. Each feature is independent. (VXLAN tunnels landed with spec-followup-vpp-iface.)
(netns) Netns-aware BGP listening: BGP binds inside a named network namespace Not in tree. RealListenerFactory.Listen binds via net.ListenConfig in whatever namespace the ze process runs in; nothing in the BGP reactor references a network namespace. So with the default vpp.lcp.netns of dataplane, BGP reaches an LCP TAP only if ze itself runs in that namespace (see "How the two halves fit together"). Specced, not implemented; ze doctor reports doctor-vpp-lcp-netns meanwhile.

The three-strategy framing in docs/research/ze-vpp-analysis.md explains the bigger picture: strategy 1 (IPng / VyOS style, netlink intermediary) is the safe default, strategy 3 (direct FIB programming, what ze does) is where ze differentiates by skipping the kernel entirely and converging sub-second on a full table.
