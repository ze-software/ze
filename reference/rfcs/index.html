Every row below is declared by the RFC's own summary, in the ## Meta table of rfc/short/<stem>.md. A row belongs here only when current docs, source code, tests, or learned closure notes tie the RFC to a Ze feature, and a summary that ties to none writes | Support | - | instead.

The per-requirement detail behind each row is published at /quality/rfc-compliance/<stem>/, one page for every summary under rfc/short/, naming each requirement, the tests bound to it, the audit verdict a reader recorded, and every gap and untested MUST under its own requirement id. The 24 of 240 summaries (10.0%) with no row on this page are published there too, and the index at /quality/rfc-compliance/ links all of them.

Area is the one cell an author writes, a classification. Every other cell is derived, and no author can change it:

  • Proof is N of M MUST proven: of the M MUST-level requirements the summary gates, the N whose tests a recorded break still verifies (rfc/discrimination/<stem>.json). A tag with no verifying record proves nothing here. An RFC whose requirement list has not been walked against the RFC's own text (no valid rfc/extraction/<stem>.json) reads not walked and publishes no number, because its list bounds nothing. A walked RFC gating no MUST-level requirement reads no MUST rows.
  • Evidence counts the proven rows by the strongest kind of test behind each (interop, then functional, editor, unit), so the counts sum to N.
  • Unmet lists the requirement ids the summary annotates {gap}, {partial} or {linux-limit}, and those an audit judged not met, at every level.

A brief table (Internet-Drafts and other standards) carries Area, Proof and Unmet and leaves Evidence out, so an unmet requirement of a draft is still named by its id.

How strong the proof behind a row is. Every requirement's evidence is listed in that RFC's own file under rfc/requirements/, with a kind/tier cell per test link. kind is the layer the test exercises (unit, functional, editor, interop); tier is whether anything executes it. verify means it runs in ./le verify current on every push. interop/nightly runs only in the scheduled, advisory evidence-nightly workflow -- so a requirement whose evidence is entirely nightly-tier is marked **nightly-only** on its row there, and counted in its own column of the coverage rollup in ai/RFC-REQUIREMENTS.md. A tag in a suite no pipeline runs is refused outright rather than published with a caveat.

./le rfc check refuses an enrolled RFC that carries an unmet requirement and renders no row here, and a row that disappears while its summary remains.
