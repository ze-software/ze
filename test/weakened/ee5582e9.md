# Test weakenings this commit accepts

Two changes are recorded here, and the table below carries both.

## 1. The DF probe rows moved to a Linux-only file

Nothing left the suite. Every probe row is the SAME body, moved from
`probe_test.go` to `probe_linux_test.go` under `//go:build linux`, so the
checker reads the departure from one file and cannot see the arrival in the
other. `git show --stat` carries both halves.

The move is what makes these rows run at all. `UDPTransport.SendDF` answers
`probe.ErrDFUnsupported` and writes nothing off Linux, because no other platform
Ze builds for carries `IP_MTU_DISCOVER` or `IP_RECVERR`
(`internal/component/ike/transport/udp_other.go`). Every row below asks the
engine to send a probe, so on darwin each asserted a send the platform declares
absent: they failed, eleven of them after a five-second owner-loop timeout. On
Linux they run exactly as before, in the ordinary unit pass.

## 2. The End-of-RIB wait, removed by owner ruling (2026-09-18)

Ze no longer holds a peer's End-of-RIB for the route-pushing processes attached
to it. A process that creates routes is treated like a peer when the marker is
decided, and Ze does not wait for a peer's marker before sending its own.

Each End-of-RIB row below asserted an outcome of that wait, so each asserted a
behavior the product no longer has. None asserted a REQUIREMENT that survived
the ruling: where a claim did survive, it was restated rather than dropped, and
the restatement is named in the row. No `.ci` case lost an assertion about the
bytes Ze puts on the wire. What four of them lost is an assertion about WHERE
the marker sat in the stream, which was an artefact of the 2s wait and is not
something RFC 4724 gives a peer any right to.

| Test | Reason |
|---|---|
| TestInitialSyncClosesTheQueueGateBeforeItWaitsForRoutePushingPlugins | End-of-RIB. The gate-close it pins still happens and is still tested. Restated as TestInitialSyncShutsTheQueueGateAndFreesTheRailsWithTheMarker, which asserts the same close and the same rail release, against the marker instead of against a wait that no longer exists. The name was the only thing that could not survive, because it names the wait |
| TestAPISyncTimeoutNamesTheProcessThatNeverReported | End-of-RIB. Deleted outright, and nothing replaces it. It pinned the WARN a 2s timeout logged; there is no timeout, so there is no line to pin. The diagnostic need it served is met by the two Debug lines this commit adds to SignalAPIReady, which say when a report is credited and when the last named process has reported. Those fire on the positive case and do not need a failure |
| TestInitialSyncBarrierCreditsOnlyTheProcessesItNames | End-of-RIB, 7 assertions to 3. The three claims it makes about CREDITING all survive and are all still asserted: an unnamed process does not release the barrier, a repeat report is not credited twice, and the last named report does release it. Proven to discriminate: with the not-named guard in SignalAPIReady forced false, this test goes red. What went is the four assertions that read the WIRE. The old test could watch the marker appear only because a wait held it back; with the wait gone the wire says nothing about who was credited, so reading it would assert a coincidence rather than the rule |
| TestInitialSyncSuppressesAnotherProducersEORWhileItsOwnIsOwed | End-of-RIB, 6 assertions to 4. The suppression under test is unchanged and still asserted both ways. The two that went were the setup's observation of the wait: the test used to reach the owed-marker state by driving sendInitialRoutes into its api-sync wait and asserting it got there. It now sets initialSyncEOROwed directly, which is the state the guard actually reads, so the arrangement no longer asserts how the state was reached |
| initial-sync-barrier-raw | End-of-RIB, 7 expectations to 6. The removed one asserted the marker arrived AFTER the raw plugin's routes, which held only because the wait delayed the marker past them. Every frame the case asserted is still asserted; what is gone is the claim that the protocol owes that order. It does not: RFC 4724 Section 2 makes a route pushed after the marker an ordinary update |
| ipv4-announce-withdraw | End-of-RIB, 9 expectations to 8, same removal and same reason as initial-sync-barrier-raw |
| ipv6-announce-withdraw | End-of-RIB, 9 expectations to 8, same removal and same reason as initial-sync-barrier-raw |
| plugin-attributes | End-of-RIB, 12 expectations to 11. Two changes, and they cancel rather than reduce. The marker-position assertion goes for the reason above, and a second `expect=` for a marker that the AnnounceEOR guard SUPPRESSES also goes: it asserted a frame Ze never sent, and passed only by matching the first marker. That one was a false assertion before this commit, so removing it is a defect repaired rather than a weakening accepted |
